从信号到系统：WiFi 感知的平台化拆解

September 14, 2026 September 15, 2026 物理世界开发 WiFi 感知, CSI, Home Assistant, Matter, 智能家居, 边缘计算 信号与图像处理系列 7637 字 16 分钟阅读
🔊

前三篇把物理、检测算法和两个开源项目讲完了，但到"家里灯自动亮起来"之间还差一层：平台侧。原始的 CSI 和检测器分数是给机器看的，智能家居要的是"浴室有人"“老人一小时没活动"这种能写进自动化的状态。这篇拆平台这一层：分数怎么变成事件，事件怎么变成语义，语义怎么接进 Home Assistant 和 Matter，商用平台怎么分工边缘和云，802.11bf 又是怎么把这套角色分工写进协议的。所有机制都有活例子——开源侧看 ESPectre 和 RuView，商用侧看 Cognitive Systems 和 ADT。

平台栈：功能诞生在哪一层

把平台侧横着切开，是四层，每层有自己的职责和产物：

    E --> P["平台层<br/>实体 + API + 规则<br/>产物：实体与自动化"]
    P --> C["生态层<br/>HA / Matter / 云<br/>产物：通知与联动"]

分层的关键不是画框，而是每层替上一层挡掉一类错误：终端层用尺度不变特征挡掉增益跳变，边缘层用防抖和规则挡掉单次误判，平台层用实体模型和权限挡掉误触发，生态层用时间、在户这类外部条件挡掉"技术上对但情境上错"的联动。后面按层拆。

从分数到事件：防抖、迟滞、冷却

检测器每秒输出几十次"这一秒有没有动"的概率，但自动化不能直接消费它——无线环境的方差摆在那里，就算检测器准确率 97%，每小时仍有几十次机会出错，而智能家居对误报的容忍度接近零。半夜一次误触发就足以让用户关掉整个集成。

所以事件化是三件套。防抖：连续 N 次评估同向才翻转，ESPectre 的 motion_on_hits: 4 / motion_off_hits: 3 就是配置项——注意进和出的 N 不一样，进严出松，这是迟滞：状态翻转后不会因为一次"静"的评估就跳回去，防止临界状态下实体抖动。冷却：触发类事件（如跌倒）上报后强制静默一段时间，RuView 的跌倒检测是 3 帧防抖加 5 秒冷却——跌倒不会一秒摔三次，但振荡的信号会一秒报警三次。三件套全是十几行的状态机，却是"演示能用"和"家里敢用"之间的全部距离。

每秒一次评估：
  检测器判"动" → on_hits += 1, off_hits = 0
  检测器判"静" → off_hits += 1, on_hits = 0
  on_hits ≥ 4  → 实体置"动"
  off_hits ≥ 3 → 实体置"静"

关键在两个计数器互为清零：一帧"静"就把 on_hits 打回零重攒。所以单帧误判至多给计数器加一，而翻转需要连续四个加一——这不是玄学的"防抖”，是精确到行的计数逻辑。

从事件到语义：平台真正消费的东西

“运动"这个事件太低级了，写不出"老人长时间没活动"这种自动化。平台在事件之上再加一层语义状态：带时间窗和组合条件的规则层。

RuView 的做法最成型：每个节点暴露 21 个实体——11 个原始信号加 10 个语义状态（有人在睡、疑似跌倒、浴室占用、老人长时间无活动等），而且每个语义状态带自己的 precision/recall 报告（精确率 precision：报出来的警报里有多少是真的；召回率 recall：该报的里面实际报出了多少——两个数合起来才说明一条规则能不能上生产线）。这个设计值得停下来看：感知系统最诚实的表述不是"能检测跌倒”，而是"疑似跌倒这个状态，在测试集上精确率 X%、召回率 Y%"。把模糊的感知拆成可量化的事件，平台才可运营——出了误报，能定位到具体哪条规则、看它的指标、调它的参数，而不是"AI 又抽风了"。

语义规则的逻辑都是朴素组合：浴室占用 = 浴室节点运动且未在 N 分钟内清除；老人异常 = 白天时段无任何活动且其他房间有活动历史（人在家）；有人在睡 = 卧室长时间静止叠加呼吸特征存在。没有任何一条是黑盒——这也是为什么三层规则里每条都能单独标注指标。

上面这张图把从信号到灯亮的完整链路演了一遍：原始 CSI 幅度越过阈值（红点），检测器这一票只点亮防抖计数器的一格，四格集满二值传感器才翻转"静→动"，语义层在实体之上组合出"浴室占用"，自动化再叠加时间条件把灯打开。回程是迟滞的——连续 3 次"判静"才复位。单帧误判永远走不到灯那里。

房间级占用：把节点聚合成"家"的视图

单节点回答"这条链路附近有没有人"，平台要回答"人在哪个房间、家里有没有人"。做法是节点与房间绑定加聚合，但聚合本身是一个独立的状态机，两个方向的难度完全不对称：

    O -->|"全部静默<br/>超过空置时限"| V

    style O fill:#4CAF50,color:#fff,stroke:none

占用方向容易：房间里任一节点过了防抖就置位。空置方向难——原理篇讲过，WiFi 感知检测变化而非存在，证明不了"房间是空的"。所以"未占用"从来不是测出来的，是超时推出来的：全部节点持续静默超过空置时限（浴室几分钟、客厅十几分钟的量级），状态才降级。这解释了为什么市面上的占用传感器都有 hold time / 空置时限配置项——它是把"测不到"安全地解释成"没人"的唯一手段，也是"人在书房打字、客厅灯却灭了"这类投诉的直接根源：时限设短了。时限的取舍没有免费午餐，只能在误关灯和常明灯之间按房间用途权衡。

节点密度与交叠：每 50~70 m² 一个节点（RuView 篇的部署几何），覆盖相互交叠，单节点漏报时邻居兜底。跨房间追踪（客厅→走廊→卧室的轨迹）在学术演示里好看，产品里少做——算一笔账就明白：走廊穿越段两三米、步速 1 m/s，节点只有两三秒的采样窗，扣掉防抖时间凑不齐一次状态翻转，轨迹断裂是常态。实用的平台退一步只做房间级占用，把"追踪"留给安防场景的专用部署。RuView 的房间指纹是条折中路：不绑定节点，编码器直接识别"这是哪个房间"，换节点不用重配映射——代价是得先在目标房间采过数据。

接进生态：Home Assistant 与 Matter

先补齐四个名字——后文全部踩在它们上面，不玩智能家居的读者需要知道它们各自是什么。

Home Assistant（HA）：开源的智能家居中枢，2013 年起步、Python 写成，跑在树莓派、NAS 或随便一台旧电脑上。它做的事是"收编"：把不同品牌、不同协议的设备统一抽象成实体（entity）——每个实体有一个状态（开/关、23.5 ℃、有人在），外加属性和可调参数。自动化引擎盯着状态变化执行联动（“当 X 变成 Y，就做 Z”）。说"感知接进 HA"，具体含义就是：检测结果变成 HA 里的一批实体，从此能被两千多种集成共享的自动化体系消费。

MQTT：物联网世界最通用的消息协议，1999 年为石油管道遥测设计，极轻量。模型是发布/订阅：设备把消息发到一个"主题"（topic，比如 home/bedroom/motion），中间的 broker 像邮局一样分发，任何订阅了这个主题的程序都能收到。HA 的 MQTT Discovery 是个聪明约定：设备往约定的主题发一条 JSON 自我介绍（“我叫卧室运动传感器，类型 binary_sensor”），HA 看到就自动把实体建好——所谓"零配置接入"，配置只是从人肉填表挪到了设备自报家门。

ESPHome：开源的 ESP 芯片固件框架。用 YAML 描述"这块板子有哪些传感器、引脚怎么接、要暴露哪些实体"，它负责编译和烧录，再通过自有协议与 HA 直连。对 ESPectre 这类项目意味着：不写一行固件代码，检测结果就自动变成 HA 实体和可调参数。

Matter：CSA 连接标准联盟（原 Zigbee 联盟，苹果、谷歌、亚马逊、三星都在里面）推出的智能家居互联标准，2022 年发布 1.0，跑在 IP 之上（WiFi、以太网、Thread）。它解决的问题是生态孤岛：过去买一个设备先要问"支不支持我家那套"；Matter 的答案是设备类型标准化的"集群"（cluster）——一次认证，苹果家庭、Google Home、Alexa、SmartThings 全都认。感知类设备对应的就是 occupancy sensing 集群。不支持 Matter 的老设备可以经"桥"（bridge）映射进来。

在这个底座上，感知接进平台的路有三条，成本和覆盖各不同：

路径配置成本生态覆盖适合
MQTT + Discovery低（一个 broker）HA 为主DIY、快速上手（ESPectre 浏览器烧录走这条）
ESPHome 原生 API低（同一套 YAML）HA 专属ESP 项目深度集成，诊断与在线调参全套透传
Matter高（需桥接或认证）全部主流生态商用产品、跨生态分发（RuView 走 Matter 桥）

实体模型的分工有讲究：运动是 binary_sensor（device_class 选 motion 还是 occupancy 有实际差别——motion 语义是"这一刻在动"、抖动多，occupancy 语义是"区域内有人"、自带保持时间），移动评分是 sensor（自动化里做梯度条件：“评分超过 X 才升级通知”），判定阈值做成 number 实体允许在线调——它本质是"这个房间多敏感"的用户偏好，该跟亮度一样可调。再挂一组诊断实体，价值在排查时兑现。ESPectre 的诊断集是四个链路指标，每个精确对应一类故障：

指标掉下去说明什么对策方向
回调率驱动没收到包，或回调被阻塞查流量模式、查任务阻塞
接收率空口有包但被丢弃查信道拥塞、混入模式配置
准入率收到了但没进时间栅格到达太抖，换流量源
槽位占用率栅格长期吃满目标 pps 定高了，往下调

四层指标从下往上逐级排除：先确认包进得了驱动，再确认进得了栅格，最后才轮到怀疑检测器——TROUBLESHOOTING.md 给的排查顺序就是这个逻辑。这套"把部署问题定位到层"的思路，值得所有传感器类集成的抄。

单个自动化写完只是开始，规模化的做法是把"房间 + 时段 + 通知对象"参数化成模板——HA 的 Blueprint 就是干这个的，RuView 自带 3 个起步 Blueprint。语义状态配 Blueprint，才是感知接进平台的标准姿势：新增一个房间，是填一次参数，不是复制粘贴一段 YAML。

商用平台：边缘与云的分工

商用系统物理层一模一样，差别在运营面。先算一笔决定架构的带宽账：一个 CSI 节点 100 pps × 56 子载波 × 4 字节（I/Q 各 int16）≈ 22 KB/s，四节点 mesh 就是 90 KB/s 上下，一个月原始数据 200+ GB——把原始 CSI 推上云既不经济、也不必要的延迟敏感，隐私上更不可接受。所以行业的共同选择是漏斗式上传：原始信号在边缘消化，边缘只产出事件和语义（每分钟几条、每条几十字节），云端看得见"发生了什么"，看不见"信号长什么样"。

Cognitive Systems 的 WiFi Motion 就是这个形状：感知软件嵌进路由器/网关——任何 802.11n 以上的平台都能跑、OTA 下发，单个 AP 也能工作，mesh 组网后每个节点（包括 IoT 设备）都是阵列的一员；实时运动检测留在网关边缘，行为模式、历史趋势、模型更新在云上（基于 AWS EKS 的基础设施）。云上那部分解决的是规模化运营，边缘替代不了：几百户的误报率遥测、按硬件型号分组的检测参数、新检测模型的灰度发布、特定户型的阈值基线对比——只有云端聚得起来。Plume 的 Motion Aware 是这套技术装进 ISP 的 mesh 平台，随网关卖进上百万家庭，用户无感——感知只是网关的又一项服务。

ADT 收下 Origin AI 后是另一种闭环：感知接进布防状态机。离家布防时，运动事件才升级为警报、通到专业报警中心；在家时同一个事件只是自动化输入。安防语境还要叠加确认逻辑——单一传感器的运动不直接派单，门磁加运动的先后触发这类多源相关才升级，因为专业监控每派一次单都有真金白银的成本，误报率直接吃掉利润。同一个"运动"，在安防和家居两种语境里走完全不同的上报路径，这就是平台层存在的意义。华为把运动检测做进企业级 AP，卖点是"复用现有网络做周界"、免部署额外传感器——路由不耽误，顺带保安。

802.11bf：把角色分工写进协议

开源项目里"谁发包、谁测量、怎么对表"各搞一套（RuView 的 TDM 时隙、espargos 的共享时钟），802.11bf-2025 把这些角色标准化成一套可互操作的流程，分三步。

第一步，Measurement Setup（协商）：Sensing Initiator（发起感知会话的一方）和 Sensing Responder（参与测量的一方）交换参数达成一致——带宽、探测周期、报告内容。这一步把"订阅感知"变成标准动作：应用说要什么（类型、速率、时延），网络答能给什么，应用不必自己去解析 CSI。

第二步，Measurement Instance（测量）：典型流程是发起方（常见为 AP）先发 NDPA 帧宣告、紧接着发 NDP 探测帧，各响应方用收到的 NDP 测信道，把结果通过反馈帧交回。NDP 里没有数据、只有训练字段——一个纯为测量而生的帧型；响应方的反馈走的则是波束赋形报告的既有通道，协议没有为感知另起炉灶。

第三步，Reporting（报告）：测量结果按统一格式回传。格式统一的价值要跟现状对比才看得到：今天 Intel 5300 和 ESP32 的 CSI 格式互不相通，每个数据集、每个工具链都要写各自的解析器；格式互通之后，同一套检测算法才可能跨厂商跑。

三个边界值得知道。其一，bf 标准化的是 MAC 层流程，CSI 到手之后的滤波、特征、检测仍在标准之外——ESPectre 们的算法空间没有被收窄。其二，发起方是 AP 还是 STA 对应不同的测量实例流程，实现时对表要先认角色。其三，RuView 的 ADR 里有一张直白的映射表——TDM 发时隙对应 Initiator、收时隙对应 Responder、一个 TDMA 轮回对应 Measurement Instance、探测帧对应 Sensing NDP——开源自己长出来的架构与标准殊途同归，反过来印证这套角色划分就是这类系统的自然形状。bf 的最终意义：参数协商和报告格式一旦互通，“你家路由器触发、邻居家网关测量"的跨厂商感知才有协议基础，感知从厂商私有功能变成网络的基础服务。

隐私工程：平台侧的必修课

WiFi 感知设备的本质是"能看见作息的传感器”，平台侧的隐私设计是架构问题，不是免责声明。把数据按敏感度排成阶梯，设计原则自己浮现出来：原始 CSI（KB/s 量级，理论上可反演姿态与作息）→ 特征（每秒几个数）→ 事件（每分钟几条）→ 语义状态（每小时几条）——每上一级，敏感度和可反演性都降一档，而自动化需要的信息一点没少。所以底线是分层的：能只出语义就不出事件，能只出事件就不出特征，原始信号默认不出节点。

RuView 的 BFLD 层把这套原则落成了工程：原始波束赋形反馈不出节点、身份嵌入只存内存、跨站点关联用按日轮换的 BLAKE3 密钥哈希做到密码学不可行——按日轮换意味着即便某天的关联密钥泄露，爆炸半径也只有当天；Ed25519 见证链给测量记录做防篡改存证。ESPectre 默认本地处理、原始 CSI 上传默认关闭，是同一原则的单节点版。

商用侧压力更大：数据落在谁的网关、什么进云、保留多久、谁能访问，是 ISP 采购时真会被问的问题。边缘/云分工在隐私上顺便给出了正确答案——云端只有事件和统计，泄露面天然小。给做集成的工程师一条自检就够：你这个平台的对外接口里，有没有任何一个字段能让第三方推出"这户人家几点睡觉"？有，就往下砍一层。

从信号到通知：延迟预算

把各功能的"信号到通知"时间排成一张表，能看到平台设计的另一层逻辑——功能的时间常数由被测物理量决定，而不是由算力决定：

功能信号 → 通知时间花在哪
运动状态翻转约 4~5 秒1 秒检测窗 × 4 次防抖
跌倒警报数秒级3 帧防抖，触发即报；冷却只压重复
呼吸率读数10~30 秒0.1~0.5 Hz 的信号，至少看满一两个周期才有可信 BPM
房间空置分钟级空置时限是对"测不到"的安全解释，宁慢勿误
老人异常小时级语义定义本身就是"长时间无活动"

运动要快——跌倒和入侵都是秒级的事；体征要慢——跳来跳去的 BPM 没有消费价值，稳定才可读；空置要更慢——把人误判成"不在家"的代价（半夜关暖气、误触离家模式）远高于慢几分钟。延迟不是性能缺陷，是每种功能自己的物理常数；平台层的职责是把这些时间常数分别守住，不被一个"全局刷新率"抹平。

至此四篇走完一条完整的线：电磁波怎么把房间写进信号（原理），信号怎么变成"有没有动"（ESPectre），怎么变成"人在哪、姿态如何"（RuView），最后怎么变成"家里知道发生了什么、并做出反应"（这篇）。物理是共通的，越往上层越接近产品——而每一层的可靠性，都是下一层敢不敢用的前提。
