全模态 AI 交互技术调研：视觉、听觉、对话与任务执行

🔊

2024 年 GPT-4o 发布会上一段"边听边说、能被打断"的语音演示，把全模态交互从论文里的名词变成了产品方向。两年过去，这件事在业界分成了两条实现路线：一条把听、看、说塞进同一个模型端到端做完（Omni 模型）；另一条用 VAD、ASR、LLM、TTS 一串模型拼流水线。这篇把两条路线的技术实现、成熟度和代表开源项目捋一遍，信息核实于 2026 年 10 月。

全模态交互拆开是五件事

一段"像人一样"的交互，背后至少五层能力：

  • 听：语音变语义——ASR，或者模型内部的音频 token
  • 看：图像和视频进对话——VLM 抽帧理解，或者连续视频流
  • 说：语音生成——TTS，或模型直接吐音频 token
  • 接得住：全双工轮次管理——什么时候该开口，用户插话怎么处理
  • 干得了：把对话变成动作——function calling、GUI 操作、机器人控制

延迟是贯穿五层的硬指标。人对话时的轮次间隔平均约 200ms（Stivers 等 2009 年发表在 PNAS 的跨语言测量）；ITU-T G.114 把交互式语音单向延迟 150ms 以内列为优质、400ms 以内可接受。落到语音 Agent 产品上，2026 年行业常见的达标线是 p50 < 800ms、p95 < 1.5s——离"像人"还有约四倍差距。两条实现路线的分歧，本质上就是这 800ms 怎么花、以及情感和打断能力放在哪一层。

路线一：单模型端到端（Omni 模型）

架构套路：音频变 token，LLM 直接生成语音

端到端方案的技术关键在音频的表示。波形没法直接进 LLM，业界用神经 codec 把音频压成离散 token，码率普遍压到 12.5–25Hz（每秒 12.5–25 帧 token），语义信息和声学细节要么分开建模，要么分层填充：

Codec码率特点
EnCodec（Meta）75HzRVQ 早期代表，MusicGen 一系沿用
Mimi（Kyutai）12.5Hz，约 1.1kbps声学流从 WavLM 语义特征蒸馏而来，全双工友好
CosyVoice2 tokenizer25Hz语义 + 声学 token，flow matching 解码
Qwen 语音 tokenizer12.5Hz 多码本0 号码本承载语义，其余约 9 个声学码本由 MTP 模块逐帧补全

在 codec 之上，开源界把"文本生成"改成"语音生成"的写法主要有五种：

  1. Thinker-Talker（Qwen2.5/3-Omni）：LLM 主干（Thinker）出文本，旁边挂一个流式语音模块（Talker）预测音频 token，再经 Code2Wav 卷积网络出波形，文本和语音两条解码头共享 Thinker 的隐藏状态
  2. LLM 出语音 token + 流匹配解码（GLM-4-Voice、Kimi-Audio）：语音 token 当语言 token 训练，解码器用 CosyVoice 一系的 flow matching 模型
  3. 文本与音频 token 交错（Mini-Omni、Chroma）：一条序列里两种 token 按比例混排，训练配方最简单，天然能"边想边说"
  4. 并行双流（Moshi）：RQ-Transformer 同时建模用户流和助手流，文本流人为延迟几步当"内心独白"——开源界唯一成熟的原生全双工配方
  5. 交互层与思考层分离（DuplexOmni，以及 Freeze-Omni 的状态分类器版本）：轮次策略和内容推理解耦

音频和视觉各自过编码器进入 LLM 主干（Thinker），Thinker 一边吐文本一边把隐藏状态喂给 Talker；Talker 按帧预测离散语音 token，Code2Wav 把 token 还原成波形。整条链路都是流式的，首包延迟不依赖整句生成完毕。图中编码器实际是两个：音频编码器（如 Qwen3-Omni 约 650M）和视觉编码器（约 540M），用 TMRoPE 做音视频时间对齐。

几个值得单独说的点：

  • Qwen3-Omni 仍是开源标杆：211ms 首包（技术报告口径，MoE 架构激活参数少）、视频输入、原生工具调用、119 种文本语言，Apache-2.0 没有商用门槛。但 2026 年 Qwen 的新一代全模态（3.5-Omni、3.8-Omni-Realtime）全部走了 API 不开源，开源线的推进转移到了面壁、阶跃、智源、Kyutai 这些队伍手上。
  • 全双工分两派：原生并行流（Moshi、FLM-Audio、MiniCPM-o 4.5 的 Omni-Flow）和系统级拼装（Kyutai Unmute 给任意文本 LLM 套一层语音壳、小红书 FireRedChat 用 pVAD + 端点检测 + 级联管线拼全双工）。Qwen3-Omni、Step-Audio 2 这类主力模型目前还是半双工加演示级打断。
  • 最弱的一环是打断质量：判断用户开口是"真插话"还是"嗯、对"这类附和（backchannel），闭源 API 明显领先——OpenAI GPT-Live-1（2026-09 进 API，真全双工 + SIP 电话）、字节 SeedRealtime（2026-08，音视频双工上豆包 App）、阿里 Qwen-Audio 系 Realtime 的语义打断。开源全双工的延迟（MiniCPM-o 4.5 的诚实口径 0.5–0.9s）也还落后于闭源。
  • 推理服务 2026 年补上了：vLLM-Omni 和 SGLang-Omni 把 Omni 推理拆成 Thinker → Talker → Code2Wav 的多阶段异步图，Qwen3-Omni 这种模型才谈得上并发部署；开源模型的原生全双工 serving 目前还是 vLLM-Omni 的 RFC 状态，没正式发布。

训练侧：把推理塞进语音回路

Step-Audio 2 把 CoT 强化学习引入语音模型（开源的 2 mini 是同一配方），Step-Audio-R1.1 专做音频推理，MiMo-Audio 用 RL 后训练把 MMAU 拉到 64.5。更前沿的是 2025 下半年集中出现的"边说边想"论文群（Shanks、Mind-Paced Speaking、Thinking While Speaking），思路一致：说话模型保延迟，推理模型异步补智商。OpenAI GPT-Live-1 的官方架构口径就是"一个模型说、另一个模型想"——闭源前沿和开源论文在这个问题上收敛到了同一个方向。

每一级都是可独立替换的服务：VAD 判断有人在说话，轮次检测判断说完了没有，ASR 出文字，LLM 做理解和决策（含工具调用），TTS 出声。视觉帧在 LiveKit、Pipecat 这类框架里走旁路通道进 VLM，理解结果并入 LLM 的上下文，不占用语音链路。

轮次检测是 2025 到 2026 年单点变化最大的环节：从"VAD 静音计时"演进到音频原生的端点模型——LiveKit Turn Detector v1 直接听原始音频（不再等转写），Pipecat 的 Smart-Turn 用 8M 参数的分类器在 CPU 上跑，Deepgram 干脆把端点检测塞进 ASR 模型。识别"说完了还是喘口气"的准确率，直接决定对话自不自然。

延迟预算上，一条全流式管线大致是：VAD/端点 50–200ms，ASR 收尾 50–150ms，LLM 首 token 300–800ms（最大头），TTS 首包 100–200ms，网络 50–100ms。Pipecat 官方基准全管线约 700ms；但独立实测真实电话链路（openbenchmarks 对 Telnyx 平台的测量）首音频字节中位数 1,296ms——组件延迟加总与真实体验之间的差距主要来自多厂商拼接的网络跳数。p50 < 800ms 达标线的瓶颈基本都在 LLM 首 token 和网络，而不是 ASR、TTS 这些组件本身。

级联还是端到端

维度级联管线端到端 S2S
延迟全流式约 500–800ms，靠工程压200–400ms 起步，理论上限占优
情感与副语言过文本瓶颈即丢失，靠 TTS 情绪标记补原生保留（气息、笑声、方言、语速）
打断靠 VAD/EoT 拼装，逻辑自己写原生（但开源质量参差）
可控性与调试每级有文本可查，换模型自由黑盒，换底座 LLM 等于重训
工具调用文本层最成熟可用，可靠性弱一截
合规与部署组件可分别驻留、分别审计整模型一体，分域难

2026 年生产环境的主流仍是级联，电话场景尤其如此——电话网 8kHz 音频和多数 S2S 模型的 16–48kHz 训练分布不匹配，一进 PSTN 就露怯。端到端的优势在自然度和打断，级联追不上；于是出现了混合形态：S2S 模型打底管对话节奏，异步调用推理 LLM 做工具和复杂任务。GPT-Live-1 的"一个说一个想"就是这套的闭源版，LiveKit 文档里对应的做法叫 half-cascade。

会话怎么开始：唤醒词之外的入口

前面整条链路都在讨论"对话进行中"，但还有个前置问题：对话怎么开始。唤醒词是常开设备的默认答案，却不是唯一入口，而且它的角色在收缩——从"每条指令喊一次"退到"每个会话喊一次"。按触发方式分：

  • 按键/点按：手机语音助手的事实标准——ChatGPT Voice、Gemini Live 都是点按开一个持续会话，耳机长按、方向盘按键同理。零误触发、零待机功耗，代价是得先摸到设备
  • 一次唤醒、会话内免唤醒：唤醒词只负责开会话，进去之后靠全双工和轮次检测持续对话（超级小爱连续对话、Alexa Follow-Up、Gemini Live），直到超时退出
  • 常开免唤醒 + 说话对象判断：麦克风一直监听，没有关键词，难点变成"这句话是对我说的吗"。场景型方案用上下文锁定对象（AI 外呼、Drive-thru 点餐、会议纪要——接通即对话）；多人环境靠音区拾音（车内多音区）和声纹识别消歧
  • 视觉唤醒：看一眼加开口才响应，下一小节单说
  • 存在感知：毫米波雷达（LD2410 一类）、PIR、BLE 靠近感知做预唤醒——人走近了抬增益、亮屏、起管线，是否开口交给 VAD
  • 手势/动作：抬腕对话（Apple Watch）、雷达手势、AirPods 对话感知（用户一开口自动压低媒体音量）
  • AI 主动发起：闹钟、提醒、异常事件（哭声检测）、proactive agent 主动搭话——发起者反转成设备，难点变成打扰控制

视觉唤醒：看一眼就开聊

视觉唤醒已有一个完整落地的产品形态：Google Nest Hub Max 的 Look and Talk（2022 年 I/O 发布）。设备端摄像头跑人脸检测、视线估计和头朝向判断（有效距离约 1.5 米），响应需同时满足几个条件——有人在说话、脸是 Face Match 注册过的、视线朝向屏幕，视频全程不出设备。Google 还给它加了一条可访问性理由：对听障用户，不用喊出唤醒词的交互更友好。机器人领域同一件事叫注意力估计（attention estimation）——判断"你在看我、在跟我说话"，是桌面机器人"看你就搭话"的底层技术；研究侧 2025 年有注视触发激活的方案（对着头像保持注视一段时间即静默发起对话）。开源模型侧，MiniCPM-o 4.5 的 Omni-Flow 把视频流和音频流对齐到同一时间轴，正好是"持续看 + 持续听"交互的模型基础；自己拼最小原型的话，MediaPipe 面部/虹膜关键点加 Silero VAD 就够。

国内带屏产品公开落地的多数还是"语音免唤醒"，目光唤醒集中在带屏音箱和机器人的研究/demo 里。原因也直白：视线估计在暗光、侧脸、戴眼镜场景下的准确率，加上常开摄像头的隐私解释成本，都比常开麦克风难一个量级。

为什么唤醒词还没死

工程账很清楚：常开关键词检测跑在专用 DSP 上只要几毫瓦，音频命中关键词前不出设备（隐私），两个字的名字顺手解决了"对谁说话"的歧义。免唤醒的每条路线都在这三项上付代价。各家入口方式横向对比：

入口方式待机开销误触发风险对谁说话的消歧隐私顾虑典型场景
唤醒词极低（DSP 几 mW）低天然消歧音频不出设备音箱、IoT
按键/点按零无无歧义无常开麦克风手机、耳机、车机
会话内免唤醒极低低（交给 EoT）会话锁定音频不出设备连续对话模式
常开免唤醒中（流式管线常开）高音区/声纹麦克风常开外呼、点餐、会议
视觉唤醒中（视觉管线常开）中视线 + 声源融合摄像头常开，最难解释带屏音箱、机器人
存在感知低（雷达/PIR）低（只预唤醒）弱，谁走近都触发低（无音视频）智能家居、门禁
手势/动作低中近距离自然消歧看传感器类型手表、耳机
AI 主动发起—打扰风险由事件锁定取决于触发传感器提醒、看护

落到选型上就是：电池供电、隐私敏感、嘈杂多人环境用唤醒词；手机和耳机用按键；带屏与具身设备往多模态注意力走；电话类场景的信道本身就是唤醒，什么都不用加。

视觉怎么接：单帧问答到连续视频流

给实时语音 Agent 加"眼睛"，2026 年有两条挂法：

抽帧进 VLM——默认做法。开源选型集中在 Qwen3-VL 家族（2025-09 起，2B–235B，Apache-2.0，上下文 256K 可扩到 1M，小时级视频按秒级时间戳索引，GUI 和 3D grounding 内建）、InternVL3.5（至 241B MoE）、GLM-4.5V（106B MoE，MIT）、MiniCPM-V 4.5（8B 端侧，视频 token 压缩 96 倍）。框架采样视频帧送 VLM，理解结果进对话上下文，成本和延迟都可控。

流式视频——一直开着看。StreamingVLM（MIT Han Lab + NVIDIA，注意力锚 + 16 秒视觉窗口 KV 缓存，单张 H100 跑 8fps 无限长流）、Apple StreamBridge（主动式流式助手）、MiniCPM-o 4.5 的 Omni-Flow 把视频流和音频流对齐到同一时间轴。“持续观察 + 随时插话"的实时视觉助手，2026 年刚从论文走向可用。

GUI agent 是"看 → 干"的完整支线，也是视觉通向执行的最短路径：

  • 开源模型：UI-TARS-1.5-7B（OSWorld 42.5%）、OpenCUA-72B（45.0%）、阿里 GUI-Owl/Mobile-Agent-v3（AndroidWorld 73.3%）、Simular Agent S3（自报 72.6%，过了 OSWorld 的人类基线 72.36%）
  • 闭源：Claude computer use、Gemini 3 内建 computer use、OpenAI Agents API 的 computer-use 工具，成绩普遍在 61% 起步
  • 单应用静态任务接近饱和之后，OSWorld 2.0（2026-06，长时程多应用工作流）把各家分数打了回去——长时程任务仍是这条支线的短板
  • 运行时生态已成熟：browser-use（MIT，约 78k stars）、UFO³、Mobile-Agent

对语音 Agent 来说，GUI agent 就是它的"手”：说话下指令，agent 在屏幕上执行，不需要为每个应用写集成。

执行层：function calling、MCP 与具身 VLA

数字世界的执行已经标准化：function calling 走 LLM，外部系统走 MCP，屏幕操作交给 GUI agent。物理世界的执行是另一套模型栈——VLA（vision-language-action）：

  • openpi（Physical Intelligence 的 π0/π0.5，Apache-2.0）：知识隔离微调只动约 1.4% 的权重，单张 A100 跑 10–15 小时适配新任务
  • NVIDIA GR00T N1.6（3B，2025-12）：双系统架构，跨机器人本体，Jetson Thor 上部署
  • OpenVLA-OFT（MIT）：并行解码 + 动作分块，动作生成快 26 倍
  • LeRobot / SmolVLA（Hugging Face，450M）：社区级机器人栈，SO-101 桌面机械臂就能玩
  • 国产开源：智元 GO-1（OpenGO-1）、宇树 WLA-1.0（Qwen2.5-VL 底座进化）
  • 闭源参照：Figure Helix（7B VLM 系统 2 跑 7–9Hz，80M 系统 1 跑 200Hz，2026 年加了全身控制的系统 0）、Gemini Robotics 1.5/2.0（ER 模型当大脑编排 VLA）

Helix 的 S1/S2、GR00T 的系统 1/2、Gemini 的 ER + VLA，收敛在同一个架构上：慢的大脑（VLM，装互联网知识、语言、规划）加快的手（扩散或流匹配动作策略），中间用抽象任务描述衔接。这对对话系统的含义很直接：给语音对话模型接机器人，不是再训一个更大的端到端模型，而是让对话层充当系统 2 的一部分，动作交给 VLA——和前面 S2S 加异步推理 LLM 的分工方式是同一个思路在不同层的重演。

两条路线怎么选

按场景给结论：

  • 做产品（客服、外呼、语音助手）：级联管线。LiveKit 或 Pipecat 起步，ASR/LLM/TTS 自选。国内自部署链路 2026 年已齐——Qwen3-ASR 或 FireRedASR 进、任意 LLM 中间、CosyVoice 3 出。要自然度直接上托管 S2S：GPT-Live-1、Gemini Live、豆包 SeedRealtime、Qwen-Omni-Realtime 都支持打断，部分支持视频流输入
  • 研究或自托管全双工：Moshi（原生双流）、MiniCPM-o 4.5（视频 + 音频全双工，可端侧）、FLM-Audio；系统级方案看 FireRedChat（小红书开源，pVAD + 端点检测 + 级联/半级联可插拔）
  • 加眼睛：Qwen3-VL 抽帧起步；要实时流上 StreamingVLM；端侧一体化看 MiniCPM-o 4.5
  • 加手：屏幕任务用 UI-TARS-1.5 或 GUI-Owl 加 browser-use；机器人用 openpi 或 GR00T N1.6

一个绕不开的坑：开源不等于可商用。OpenAudio S1-mini、Spark-TTS 的权重是 CC-BY-NC-SA（禁商用），TEN VAD 的许可带非竞争条款，GLM-4-Voice 的权重挂智谱自定义许可——选型时逐个核权重许可，别只看代码仓库的 LICENSE 文件。

评测基准与已知短板

基准分三类看：

  • 静态多模态理解：MMAU-Pro（音频，Qwen3-Omni-30B 以 62.9 居开源榜首）、OmniBench、WorldSense、Video-MME——这类 QA 型基准头部已逼近饱和，区分度在下降
  • 实时交互行为：Full-Duplex-Bench 从 v1（2025-03）迭代到 v3（2026-04），专测停顿、附和、轮次切换、语音重叠，v3 连"带结巴的语音里调工具"都测；Sierra 的 τ-voice 用真实客服任务评语音 Agent。GPT-Live-1 发布时自称在 Full-Duplex-Bench 上比上代高 30 个百分点
  • 任务执行：OSWorld-Verified（桌面 GUI）、AndroidWorld（移动 GUI，UI-TARS-2 与 Mobile-Agent-v3 都到 73.3）、LIBERO 和 AgiBot World（具身）

到 2026 年 10 月仍然难的事：

  1. 打断质量：插话和附和的区分没有公认基准，开源全双工的延迟与闭源 API 有可感差距
  2. 音频幻觉：全双工模式下模型把自己的输出听成输入的"自听循环"，是 2026 年还在发论文的活跃问题
  3. 延迟口径混乱：首包 211ms、响应 195ms、80ms 各说各话，定义不同，对比前先看测的是什么
  4. 离散 token 的音质天花板：Ming-flash-omni 2.0 把语音生成退回连续 tokenizer，说明纯离散路线的音质税还在
  5. 长时程任务：OSWorld 2.0 上所有系统都明显回落，视觉 + 执行的长链条是当前最短板

两条路线没有谁替代谁：级联管线的可控性让它继续当生产默认，端到端模型的自然度和打断能力守住"像人"这条线，而 2026 年真正的新形态是两者的混合——说的模型和想的模型分工。开源侧的最短跟进路径：语音对话从 Qwen3-Omni 或 Moshi 起步，管线从 LiveKit 或 Pipecat 起步，Omni 推理服务看 vLLM-Omni，实时交互评测盯 Full-Duplex-Bench。
