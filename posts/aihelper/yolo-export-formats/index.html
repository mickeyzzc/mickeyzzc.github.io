YOLO 模型导出全解：22 种格式、参数与选型

September 6, 2026 September 6, 2026 AI工具 YOLO, 模型部署, ONNX, TensorRT, OpenVINO, 边缘计算 AI 工程实践系列 4598 字 10 分钟阅读
🔊

2026 年 5 月写《YOLO 部署落地》的时候，Ultralytics 官方导出表是 17 行。到 9 月整理这篇时再打开文档，已经涨到 22 行，多出来的行清一色是 NPU 厂商链路——ExecuTorch、Axelera、DEEPX、Hailo、昇腾、Apple Core AI 这类。表格变长的方向很明确：训练框架和推理硬件在分家，PyTorch 管训练，部署端各玩各的运行时，导出是两边唯一的桥。

好消息是 API 没变，还是那一行：

from ultralytics import YOLO

model = YOLO("yolo26n.pt")
model.export(format="onnx")

格式多，用法单一：改 format 参数就行。真正的工作量在两张表上——一张格式表（选哪种），一张参数表（怎么导）。这篇把两张表摊开，再给一版选型速查。

22 种格式全表

严格说是 1 个源格式加 21 个导出目标：PyTorch 那一行是本体，其余 21 行的括号里就是 format 参数的取值。产物列是导出后磁盘上多出来的东西——单文件还是目录，后文会解释为什么这个区别重要。

格式（format 参数）产物主要目标
PyTorch（本体）.pt训练与微调，一切导出的起点
TorchScript（torchscript）.torchscriptlibtorch C++ 部署，PyTorch 原生链路
ONNX（onnx）.onnx跨平台交换枢纽，几乎所有运行时都认
OpenVINO（openvino）目录Intel CPU / iGPU / NPU
TensorRT（engine）.engineNVIDIA GPU 与 Jetson
CoreML（coreml）.mlpackageiOS / macOS，直接进 Xcode
TF SavedModel（saved_model）目录TF Serving 与 TF 生态
TF GraphDef（pb）.pb旧 TF 链路，无元数据
TF Edge TPU（edgetpu）.tfliteGoogle Coral，恒 batch=1
PaddlePaddle（paddle）目录飞桨生态
MNN（mnn）.mnn阿里系移动端
NCNN（ncnn）目录腾讯系移动端、嵌入式 CPU
IMX500（imx）目录索尼树莓派 AI Camera，仅 n 号模型
RKNN（rknn）目录瑞芯微 RK3588 等，name 指定芯片

DEEPX（deepx）目录DEEPX 边缘芯片

LiteRT（litert）.tfliteGoogle 端侧运行时，原 TFLite
Hailo（hailo）目录Hailo-8/10h（树莓派 AI Kit）
Huawei Ascend（ascend）目录华为昇腾 NPU
Apple Core AI（coreai）.aimodelApple 新一代 NPU 链路

表里有三个细节值得单独说：

  • 元数据。除 pb 外，所有产物都带 Ultralytics 元数据（类别名、输入尺寸、任务类型）。所以 YOLO("yolo26n.onnx") 加载导出产物后可以直接 predict 和 val，预处理和后处理配置跟着模型走，不用自己另写一份。
  • 别名与改道。tensorrt/trt 会归一到 engine；8.4.83 起 tflite 和 tfjs 被标记弃用，传了会收到警告并实际导出 LiteRT——Google 把 TFLite 和 TF.js 统一成了 LiteRT。本系列旧文里 format="tflite" 的写法还能跑，产物已经变成 LiteRT 链路的了。
  • 目录型产物。OpenVINO、SavedModel、RKNN 这类导出的是目录，不是单文件，命名统一是 yolo26n_<format>_model/ 的形式（如 yolo26n_rknn_model/）。拷贝部署时要整个目录一起拷，漏掉里面的 XML 或权重文件加载时才报错，现场排障很烦。

导出参数：要动的开关其实不多

官方参数表二十来项，日常真正要动的就这几个：

参数默认作用
formattorchscript目标格式，21 选 1
imgsz640输入尺寸；不传则用 checkpoint 里记录的训练尺寸
quantize不设（FP32）16=FP16，8=INT8；half/int8 的继任者
dynamicFalse可变输入尺寸，仅 TorchScript / ONNX / OpenVINO / TensorRT / CoreML / MNN 支持
simplifyTrueonnxslim 精简计算图，走 ONNX 的导出都生效
opset最新ONNX opset 版本，运行时版本对不上时降它
nmsFalse把 NMS 烘进模型，conf/iou/max_det 随之生效
end2end不设YOLO26/YOLOv10 专用，False 退回传统 NMS 链路
batch1静态 batch 上限；Edge TPU 恒为 1
device自动cpu / 0 / mps / npu / dla:0，TensorRT 强制 GPU
data自动挑选INT8 校准数据集 YAML
workspace自动TensorRT 构建空间上限（GiB）
name按格式NPU 芯片型号：RKNN 默认 rk3588，Hailo 默认 hailo8l，昇腾默认 Ascend310B4

几个参数值得展开：

quantize 与 half/int8 的交接。老文章（包括本系列）里写的 half=True、int8=True 已被 Ultralytics 标记弃用，导出时会收到警告，分别映射到 quantize=16、quantize=8，旧写法还能跑。INT8 是训练后量化（PTQ），需要喂几百张有代表性的图做校准——data 指向数据集 YAML，fraction 控制用量。不指定时 Ultralytics 会自动挑一个任务相关的校准集，但拿自己的业务数据校准，精度才有保证。

nms 与 end2end。nms=True 把后处理烘进模型，导出产物输出的就是最终框，部署端少写一段 NMS 代码，conf 和 iou 阈值也在导出时定死。YOLO26 和 YOLOv10 本身是端到端无 NMS 架构，输出已经是最终检测；反过来 end2end=False 能退回传统 NMS 链路——老推理环境吃不下新输出格式时用得上。

dynamic 与 batch 的组合。dynamic=True 允许可变输入尺寸，但动态 batch 要显式给最大值（比如 batch=16），不给我的实测里直接报错。固定尺寸的摄像头场景就别开 dynamic，静态 shape 引擎优化得更狠。

导出机制与边界

不管 format 选哪个，流水线前半段都一样：关梯度、conv+BN 融合，用假输入跑一遍前向拿到计算图，检测头按目标格式重排输出分支。后半段才分路：

    A --> C["ONNX 中转<br/>TRT RKNN<br/>Hailo Ascend"]
    A --> D["TF 中转<br/>SavedModel<br/>LiteRT"]

    classDef path fill:#2196F3,color:#fff
    class A src

三条路各有代表。直接转换系：TorchScript、CoreML、ExecuTorch、PaddlePaddle、IMX500，以及 OpenVINO——新版从 torch.fx 直转，不经 ONNX。ONNX 中转系最大：TensorRT、MNN、TF SavedModel、RKNN、昇腾、DEEPX、QNN、Hailo 八家都先把图导成 ONNX 再交给各自编译器，opset 和 simplify 管的就是这一步。TF 中转系服务 LiteRT 和 Edge TPU，链路是 ONNX → SavedModel → tflite。量化发生在转换里：FP16 是权重精度转换；INT8 是训练后量化，要拿 data 数据集跑几百张前向收集激活范围。导完会自动加载产物跑一遍推理验证，并把类别名、imgsz、task 写进元数据。

21 个格式看着通用，每一格都有前置条件。模型侧，整套 API 只服务 Ultralytics 家族；CoreML 的内置 NMS 只支持检测任务，IMX500 只认 v8n/11n，任意 PyTorch 模型真正通用的只有 ONNX 和 TorchScript 两条路。导出机侧，TensorRT 要 NVIDIA GPU 和配套 CUDA；rknn-toolkit2、Hailo 编译器、CANN 都是 Linux 工具链；Edge TPU 编译器在非 x86 Linux 上直接报错——实际项目里 NPU 格式普遍在一台 Linux 编译机上集中导出。

最根本的限制是算子覆盖：导出本质是算子级翻译，目标端不认识任何一个算子就失败。YOLO 全 Conv/Concat/Upsample 的规整结构，加上官方对各家工具链逐个适配，才有这么宽的覆盖面；换成带复杂注意力或动态 shape 的模型，同一张表立刻窄很多——Swin 和 RT-DETR 的 ONNX 导出难缠是出了名的。

主流格式能力矩阵

22 种挨个对比没有意义，多数 NPU 格式是"给指定芯片用的"没得选。真正需要横向比较的是这 11 种：

格式FP16INT8动态尺寸导出内置 NMS元数据
ONNX✅✅✅✅✅
TorchScript✅✅✅✅✅
TensorRT✅✅✅✅✅
OpenVINO✅✅✅✅✅
CoreML✅✅✅✅✅
TF SavedModel✅✅❌✅✅
LiteRT✅✅❌❌✅
NCNN✅✅❌❌✅
MNN✅✅✅✅✅
RKNN仅 INT8✅❌❌✅
TF Edge TPU仅 INT8✅❌❌✅

矩阵没列的三种是功能面最窄的：pb 量化、动态、NMS 全不支持还丢元数据；PaddlePaddle 和 ExecuTorch 的导出参数只有 imgsz/batch/device，能用但没什么可调的。

矩阵之外的注脚：INT8 全系是 PTQ，都要 data 校准；CoreML 的内置 NMS 只对检测任务生效；IMX500 对 detect/pose/segment 强制开 NMS，不用手动传；TensorRT 的 FP16 要求 GPU 设备导出。

性能：只有量级，没有现成答案

同机对比的经验量级如下，来源是 Ultralytics 官方 benchmark 和各运行时自己的公开数据：

对比（同机）常见量级备注
TensorRT FP16 vs PyTorch FP322–5×engine 绑定 GPU 架构与 TRT 版本
OpenVINO vs PyTorch（CPU）1.5–4×上 INT8 再快一截
ONNX Runtime vs PyTorch（CPU）1.2–2×收益主要来自图优化与算子融合
NCNN vs TFLite（ARM 手机）1.5–3×ncnn 官方 benchmark 的长期口径
INT8 vs FP161.3–2×掉多少 mAP 必须 val 验证

这些数字是量级参考，不是承诺。imgsz、batch、后处理写法、具体芯片型号都会动它，同一张卡上 640 和 1280 的加速比能差出一倍。Ultralytics 导出完会自动跑一遍推理验证，正式部署前再用 yolo val model=xxx.onnx data=... 量一遍 mAP，两个数都过线才算导出成功。

iPhone 和 Mac 走 CoreML，.mlpackage 直接拖进 Xcode；Android 上 NCNN 在低端 ARM 芯片上常年领先，MNN 是同类替代；RK3588 用 rknn 并记得 name 参数；树莓派 AI Kit 是 Hailo 芯片，树莓派 AI Camera 是索尼 IMX500（只认 n 号模型）；骁龙手机的 NPU 走 qnn。

TensorRT、RKNN、QNN、Hailo 的导出链路内部都先过一遍 ONNX，opset 参数控制的就是这一步。所以专有格式导出报错时，先在 ONNX 层排查——旧的 onnxruntime 跑新 opset 的模型是最常见的翻车点。

最后压缩成一句话：先用 ONNX 把链路跑通，再往目标硬件的专用格式迁。ONNX 一般就能拿到大部分加速，专有引擎多出来的那部分，要用可移植性和工具链耦合来换——值不值，yolo val 测过再定。
