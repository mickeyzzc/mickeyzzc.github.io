Needle 2 拆解：14MB 的端侧工具调用模型

September 4, 2026 September 6, 2026 AI工具 Needle, 端侧AI, 函数调用, 边缘计算, 小模型 AI 工程实践系列 5662 字 12 分钟阅读
🔊

2026 年 8 月，YC 孵化的 Cactus Compute 发布了 Needle 2：45M 参数，CQ2 量化后整个模型是单个 14MB 二进制文件，跑完整会话的峰值内存约 28MB，Apache-2.0 开源，论文挂在 arXiv（2607.18363）。官方口径叫 “foundation model for tiny devices”，但它和动辄几 B 参数的语言基础模型不是一回事——它只干一件事：读入用户指令和工具 schema，输出 JSON 函数调用。

这篇文章把它的架构和工程取舍捋一遍，过一遍 Python、CLI、C API、WASI 四条接入路线的开发案例，再把它放回端侧模型里找同类：谁跟它是同一个赛道，差距在哪，什么时候该选谁。

为什么 45M 也敢叫基础模型

初代 Needle 是 26M 参数的 encoder-decoder（12 层编码器 + 8 层解码器，全程没有 FFN），从 Gemini 3.1 的工具调用数据蒸馏而来：200B token 预训练花了 27 小时 TPU 时间，之后在 2B token 的单轮函数调用数据上做后训练，只用了 45 分钟。Needle 2 换成一套更激进的极简架构（下文细说），任务定义没变。

“基础模型"这个说法站得住，关键在一点：它不针对任何具体 App 做训练。工具列表是运行时输入的变量——把自家设备的 schema 喂给它，它就能调用这些设备；换一套 schema，权重不变。所谓 foundation，指的是"设备控制的通用底座”，不是"什么都能聊"。

单一任务的取舍

Needle 2 的行为设计相当偏执：

  • 所有问题都是函数调用。离题的输入返回空数组 []，没有自由文本兜底。真需要对用户说话，走一个内置的 type: respond 伪调用，function_calls 留空。
  • 可选字段没有证据就不填，不猜。对设备控制来说，“猜一个房间名"比"拒绝执行"危险得多。
  • 环境状态走 system facts。日期、时区、电量、网络、位置在会话开始作为"事实"注入，并且只有日期事实存在时，模型才被允许解析"明天"“今晚"这类相对时间——这是把幻觉的口子从源头堵上。
  • 会话共享一套工具集。后续轮次都是对同一批工具的裸查询，reset() 只回滚对话、不清工具。

这套设计对应的是语音助手、智能家居、机器人这类"指令 → 动作"的链路，对话只是副产品。它做结构化抽取也是同一个格式：把要填的记录 schema 当成唯一的工具申报，输出语法合法由解码器保证，不存在单独的"JSON mode”。

图上三个环节值得展开：工具多的时候，内置对比学习头给 schema 做向量检索，每轮只把 top-5 放进上下文；生成阶段，工具 schema 会被编译成字节级 grammar 约束每一步解码，JSON 语法层面不可能出错；置信度来自单独的校准头（post-hoc 头分数和解码概率取小），低于阈值不执行，走上报分支——这是它敢在无网设备上跑的前提。

有一个对调试很友好的细节：返回的 reasoning 字段是模型对每个参数来源的简短推导（'ten minutes' -> minutes 10），它不走语法约束——只有调用本身被 grammar 锁死，推导保持自然可读，排查"模型到底怎么理解这句话"时直接看这个字段就行。

14MB 是怎么压出来的

参数少只是第一步：45M 按 bf16 也要 90MB。真正把体积打到 14MB 的是架构和量化的叠加。架构名叫 SAN（Simple Attention Network），几个关键件：

  • 没有 FFN。Transformer 的参数大头在 FFN，SAN 用 Hadamard 乘性层替代——逐通道缩放，参数量省一个数量级。
  • Walsh-Hadamard 变换做 token 混合。固定矩阵，n log n 复杂度，零参数。
  • engram 记忆。n-gram 哈希表充当一部分 KV 记忆，重复出现的模式不占网络权重。
  • hyper-connections。多通道残差替代单一 residual stream，四条残差流并行。
  • Sinkhorn 归一化。路由 logits 过双随机归一化，稳定训练。

量化层面用 Cactus 自家的 CQ2（每参数 2 个多 bit，45M × 2.5bit 正好 ≈ 14MB），权重和推理引擎一起烤成单个二进制——不依赖 PyTorch 或 llama.cpp，支持 ARM64、x86-64、ARMv7、RISC-V、WebAssembly，甚至 MIPS32el（Ingenic 摄像头、路由器 SoC）。

内存有界是另一个工程点：256-token 滑动窗口，工具 schema 以 KV sink 形式常驻，会话滚多长内存都不涨，峰值约 28MB。这个数字正好卡进 ESP32-P4（带 PSRAM 的 MCU）的预算；社区还有人报告在 ESP32-S3 的 11MB 里跑起来过。

速度的官方数字：树莓派 5 约 500 tok/s 解码，Meta Quest 3S 和 Apple Vision Pro 400–1500 tok/s，200 美元以下的安卓机 300–700 tok/s。纯 CPU，不要求 NPU。

开发接入：从装饰器到裸 schema

先装 Python 包：

pip install cactus-needle

Needle 靠读工具描述来决定调什么、参数怎么填，所以描述写得好不好就是全部。描述工具有三种粒度，控制力从弱到强。

最省事：函数加装饰器。签名给参数类型，docstring 就是工具描述，run() 把"模型选调用 → 本地执行 → 结果回喂 → 给出最终答案"整个循环跑完：

import needle

@needle.tool
def get_weather(city: str):
    "Get the current weather for a city."
    return {"city": city, "temp_c": 27, "sky": "clear"}

agent = needle.Needle(tools=[get_weather])
print(agent.run("what's it like in Lagos right now?")["reasoning"])

from typing import Literal

@needle.tool
def set_thermostat(temperature: int, mode: Literal["heat", "cool", "auto"] = "auto"):
    """Set the thermostat.

    Args:
        temperature: target temperature in Celsius
        mode: heating strategy to use

agent = needle.Needle(tools=[set_thermostat])
agent.run("make it 21 and cool the room")

语法级约束：needle.Field 配合 Annotated 内联挂在参数上，范围、正则、长度、条数全部编译进解码 grammar。下面的转账工具，金额必须大于 0 且不超过 10000，收款人必须匹配 handle 正则——不是"提醒模型别乱写”，是"写不出来"：

from typing import Annotated

@needle.tool
def send_money(
    amount: Annotated[float, needle.Field(gt=0, le=10000, description="USD, up to 10,000")],
    to:     Annotated[str,   needle.Field(pattern=r"^@[a-z0-9_]+$", description="recipient handle")],
    memo:   Annotated[str,   needle.Field(max_length=80)] = "",
):
    "Send money to a handle."
    return {"sent": amount, "to": to}

Field 支持的约束基本把常用校验凑齐了：description、enum、const、ge/le/gt/lt、multiple_of、min_length/max_length、pattern、format、min_items/max_items、unique_items。

confidence 是两个信号取小：校准头对"完整输入 + 刚生成的调用"打出的分，和调用 token 本身的解码概率。两个信号都认可才执行，所以失败模式是"拒绝并升级"，而不是"错误执行"。

from pydantic import BaseModel

class Invoice(BaseModel):
    vendor: str
    total: float
    due_date: str

invoice = needle.extract("Invoice from Acme Corp, $1,200.00, due 2026-09-01", Invoice)
print(invoice.vendor, invoice.total)   # -> Acme Corp 1200.0

手动循环：不想让 run() 包办时，complete() 返回裸调用，自己执行、自己回喂。多步链路里，后一个调用的参数可以依赖前一个的结果——先 search_for_contact 拿到 contact_id，再调 send_instant_message；最后一步可以用 type: respond 输出纯文本总结：

python

import json
response = agent.complete("dim the living room to 30")
if response["type"] == "call":
    result = set_lights(**response["function_calls"][0]["arguments"])
    response = agent.complete(json.dumps(result))   # 把执行结果喂回去

装饰器做的事只是拼一个 JSON schema，needle.Needle(tools=...) 直接接受裸 schema 数组——这就是 CLI 用的 tools.json 的同一形状。要从 OpenAI 工具链迁移的话，{"type": "function", "function": {...}} 包装也能直接喂，引擎会先归一化。

部署形态：CLI、HTTP、C API 与 WASI

Release 页按平台给预编译产物，从 Mac、树莓派到摄像头 SoC 都有对应目录：

设备目录产物形态
macOS / Windows / Linux（x86-64、ARM64、ARMv7、RISC-V）平台对应目录CLI + 静态库
Android / iOS / watchOS / tvOSandroid-*、ios-arm64 等静态库
MIPS32el（Ingenic 摄像头、路由器）linux-mipselCLI + 静态库
浏览器 / Nodewasmneedle.js + needle.wasm
WASI 组件宿主wasm-component组件 + WIT 契约

命令行两种用法——单次查询即走，或者起一个本地 HTTP 服务给同机其他进程调用：

./needle --tools tools.json --tool-index tools.idx --serve

工具超过 5 个后检索自动介入：初始化时每个 schema 被内置对比头编码一次，每轮只把得分前 5 的工具放进上下文并重建 grammar。没被选中的工具不是"概率低"，是根本不可达——比软提示可靠。tools.idx 按 schema 指纹缓存向量：schema 没变就秒加载，变了只重算变化的部分。

system facts 是可选的一轮环境声明：

text
1

date: 2026-07-21 Tue 14:30; locale: en-US; device: phone; battery: 62%

支持的键有 date、locale、device、battery、network、location、user、assistant。“明天早上 7 点"只有存在 date: 事实时才会被解析成绝对时间，否则人话原样透传。放这里的指令性文字不会带偏模型——它是事实通道，不是 prompt 注入点。

嵌入设备走 C API：包含 needle.h，链接目标平台的 libneedle.a，四个生命周期函数 needle_load / needle_init / needle_complete / needle_reset：

c
1
2
3
4

int rc = needle_load(model_bytes, model_size);
if (rc < 0) return 1;
rc = needle_init(system_prompt, tools_json, nullptr);
if (rc < 0) return 1;
rc = needle_complete(query, 256, output, sizeof(output));
if (rc < 0) return 1;

这里有个容易踩的坑：返回值语义不统一。needle_load 失败返回负数，但 needle_init 和 needle_complete 成功时返回的是正数（缓存前缀 token 数 / 生成 token 数）——判断一律用 >= 0，不能把非零当错误。另外，API 拥有的是进程级全局会话：一个 worker 进程加载一份模型档案、独享一份引擎和 KV cache，要服务并发会话或多个微调版本，就起多个 worker。

WASI 路线把引擎打包成 WASI Preview 2 组件（导出 cactus:needle/engine@2.0.0），WIT 契约同样是 load / init / complete / reset 四个函数，模型字节在运行时传入——同一个组件既能加载基础模型也能加载微调版，不用重编引擎；每个组件实例独享一个会话，没有隐藏的宿主状态。

微调是全开放的：在自己的工具和领域数据上端到端训练，导出 .cact，像基础模型一样分发。官方 playground 把"生成数据 → 训练 → 导出"做成了按钮流程；初代 Needle 的经验值是每个工具至少 120 条样本。本质上，它把"为你的设备写 prompt 工程"换成了"为你的设备做轻量训练”——工作量没有消失，只是换了形态。

同类模型对标

比之前先捋定位。端侧模型里和 Needle 2 同台的是两拨人。

专用函数调用模型——任务同款，比的是调用准确率和跑得动的最低硬件：

模型出品方参数量说明
Needle 2Cactus Compute45M文本→JSON，CQ2 量化后 14MB，Apache-2.0
FunctionGemmaGoogle270MGemma 3 270M 的函数调用特调，2025 年 12 月发布，附微调配方
Octopus v2Nexa AI2B2024 年发布，主打 Android 端侧函数调用

通用端侧小模型——顺带支持工具调用，多出来的参数买的是对话和通用语义能力：

模型出品方参数量说明
LFM2.5-230MLiquid AI230M卷积+注意力混合架构，官方推荐用于抽取和轻量 agent 流程
Gemma 3 270MGoogle270M定位就是"拿来微调的底座"，FunctionGemma 的基座
Qwen3-0.6B阿里通义0.6B这一档里通用能力最全，工具调用只是能力之一
Apple 端侧 FMApple未公开（业界普遍估计 3B 级）Apple Intelligence 本地底座，闭源

Cactus 自己的 benchmark 结论是：Needle 2 与 FunctionGemma 270M、LFM2.5-230M、Apple 端侧模型互有胜负，同时体积小 5–70 倍，量化 2-bit 对对方的 f16。这个说法比"全面领先"克制，但有两点要泼冷水：benchmark 是官方自报；各家论文的工具集和 schema 复杂度不同，跨论文数字本来就不能直接比。

真正的分野在硬件门槛。上表其余模型的部署下限是"百 MB 内存起步的手机"，Needle 2 是"几十 MB 内存的 MCU"。45M 和 270M 之间差的那几倍参数，买的是 schema 理解的泛化性和对话兜底；Needle 2 把这些全砍了，换回来三样东西：MCU 能跑、JSON 语法保证合法、内存不随会话变胖。

两条线的差距不是"谁更强"，是分工：需要跟用户说话、处理开放输入，通用型；输入输出都是结构化的设备控制，专用型的性价比高得多。

什么时候选它，什么时候别

适合的场景：

  • 语音助手、智能家居、机器人的指令路由：一句话映射到一个设备函数调用
  • App 内的意图识别和结构化抽取：申报一个记录 schema，输出语法保证合法
  • 隐私敏感、必须完全离线的链路
  • 硬件预算是 MCU / 可穿戴级别，塞不下 1B 模型
  • 前端内嵌：WASM 产物让"文本进 JSON 出"整个跑在浏览器里，桌面应用同理

不适合的：

  • 开放对话：它没有对话能力，type: respond 只是兜底
  • 长上下文：256-token 窗口是硬上限，别指望它读文档
  • 多步复杂 agent 编排：45M 的语义鲁棒性撑不住复杂规划，这类任务通用小模型更稳

收个尾：Needle 2 没有发明新任务，它把"端侧函数调用"从通用 LLM 的附带技能做成了专用模型，用架构加量化把硬件下限从手机拉到了 MCU。benchmark 自报、生态单一维护方、论文还新，这些都是要盯的风险。但"14MB 单文件、28MB 内存、JSON 语法保证合法"这三个数字足够具体——具体到可以在 ESP32-P4 上直接试一把，再决定要不要把它接进自己的设备链路。
