onvif-device-rs 教程：用 Rust 实现一台 ONVIF 相机

October 2, 2026 MiBeeOSS Rust, ONVIF, 监控摄像头, 开源 MiBee 开源项目实践系列 5217 字 11 分钟阅读
🔊

onvif-device-rs 管的是 ONVIF 的另一半：onvif-go 是「连相机」，这个库是「当相机」——让 NVR 把你的设备当成一台 ONVIF 摄像机来发现、读信息、取流、控云台、收事件。适用场景：把 Linux 板子或工控机做成 ONVIF 相机、给 NVR 开发造测试桩、把 PC 摄像头挂进 NVR。它是 Rust 侧此前没有的 ONVIF 设备端实现，从 MiBee 的树莓派相机固件原样抽出，响应字节级稳定，与 MiBeeNvr 逐字节互操作。

这篇按「能直接抄去用」的标准写：从 cargo new 到完整虚拟相机程序，每个配置逐字段说明，每个注入缝给完整实现。

crates.io 上当前 0.7.0，要求 Rust 1.80。命名有一段必须交代的公案：crates.io 的 onvif-rs 名字被一个 2018 年的空占位仓库占着，lumeohq 的同名库是 WSDL 生成的客户端、与本项目无关——所以 crate 以 onvif-device-rs 之名发布，仓库保留 onvif-rs 原名，README 里写清楚了消歧义。

可选 feature 只有一个：tls（默认关）。默认关的原因写在 Cargo.toml 注释里——嵌入它的产品依赖默认 features，不能平白多出一条 TLS 依赖栈。要 HTTPS 时显式开。

use std::sync::Arc;
use std::time::Duration;

use onvif_device_rs::config::DeviceConfig;
use onvif_device_rs::device::{DeviceHandler, DeviceServiceHandlers};
use onvif_device_rs::discovery::DiscoveryServer;
use onvif_device_rs::media::{
    GetProfilesHandler, GetSnapshotUriHandler, GetStreamUriHandler, OnvifMediaConfig,
};
use onvif_device_rs::ptz::PtzState;
use onvif_device_rs::server::{OnvifConfig, OnvifServer};

#[tokio::main(flavor = "current_thread")]
async fn main() -> anyhow::Result<()> {
    let device_ip = detect_local_ip(); // 你的宿主自己知道自己的 IP
    let port = 8080u16;

    // 1. 服务配置：端口与凭据
    let config = OnvifConfig {
        port,
        username: "admin".to_string(),
        password: "set-a-real-password".to_string(),
        ..Default::default()
    };
    let mut server = OnvifServer::new(&config);

    // 2. 设备身份：六个字段都会出现在 NVR 的设备列表里
    let device = Arc::new(DeviceServiceHandlers::new(
        DeviceConfig {
            name: "My Camera".into(),
            manufacturer: "My Company".into(),
            model: "Cam-X".into(),
            firmware: "1.0.0".into(),
            hardware_id: "cam-x".into(),
            serial_number: "SN-001".into(),
        },
        port,
        device_ip.clone(),
    )?);

    // 3. Device 服务：时间查询必须匿名（digest 要先拿时间才能算）
    server.register_anonymous_action("GetSystemDateAndTime");
    for action in ["GetDeviceInformation", "GetCapabilities", "GetServices", "GetScopes"] {
        server.register_handler(action, Box::new(DeviceHandler(Arc::clone(&device))));
    }

    // 4. Media 服务：一份媒体配置喂给三个 handler
    let media = Arc::new(OnvifMediaConfig::new(1920, 1080, 25, 2_000_000, 8554, device_ip.clone()));
    server.register_handler("GetProfiles", Box::new(GetProfilesHandler::new(Arc::clone(&media))));
    server.register_handler("GetStreamUri", Box::new(GetStreamUriHandler::new(Arc::clone(&media))));
    server.register_handler("GetSnapshotUri", Box::new(GetSnapshotUriHandler::new(media)));

    // 5. PTZ：状态机 + 注册全部动词
    let ptz_state = Arc::new(PtzState::new());
    for action in ["ContinuousMove", "AbsoluteMove", "RelativeMove", "Stop", "GetStatus",
                   "GetPresets", "SetPreset", "GotoPreset", "RemovePreset", "GetNodes",
                   "GetConfigurations"] {
        server.register_handler(action, Box::new(onvif_device_rs::PtzHandler(Arc::clone(&ptz_state))));
    }
    // 宿主起一个 50ms 循环推进状态机（ContinuousMove 的位移在这里发生）
    tokio::spawn({
        let state = Arc::clone(&ptz_state);
        async move {
            loop {
                state.tick(50);
                tokio::time::sleep(Duration::from_millis(50)).await;
            }
        }
    });

    // 6. 事件：宿主探测到移动时注入
    let events = server.enable_events();

    // 7. 启动 SOAP 服务与发现
    let mut soap = server.start().await?; // 0.0.0.0:8080
    let mut discovery = DiscoveryServer::with_identity(&device_ip, port, "My Camera", "Cam-X")
        .with_uuid("f472b01e-0000-1000-8000-000000000001") // 固定 UUID：重启不当新设备
        .start()
        .await?; // UDP 3702

    // 8. 示例：每 30 秒注入一条移动事件
    for _ in 0.. {
        tokio::time::sleep(Duration::from_secs(30)).await;
        let mut ev = onvif_device_rs::Event::new("tns1:VideoSource/MotionAlarm");
        ev.data.push(onvif_device_rs::SimpleItem::new("State", "true"));
        ev.data.push(onvif_device_rs::SimpleItem::new("Score", "87"));
        events.publish_event(ev);
    }

    // 收尾（示例到不了这里；实际由你的退出路径调用）
    discovery.shutdown().await?;
    soap.shutdown().await?;
    Ok(())
}

逐段说：

  • 设备身份：DeviceConfig 六字段会出现在 NVR 的设备列表里，DeviceServiceHandlers::new 对身份做校验——空字段和 unknown 占位直接拒绝，库不想让「My Camera, unknown, unknown」出现在真实 NVR 里，所以必须显式给实名（serial_number 可留空）。
  • 匿名白名单：GetSystemDateAndTime 是 ONVIF 规范的硬要求——客户端要先匿名拿到设备时间才能算 digest，这条不开放，后面全部 401。
  • 动作注册模型：一个动作一个 handler。DeviceHandler 一个实例服务 Device 服务的多个动作；Media 三个 handler 全是数据驱动的，OnvifMediaConfig::new(宽, 高, 帧率, 码率, rtsp端口, ip) 一份配置喂进去，GetProfiles/GetStreamUri/GetSnapshotUri 的应答就有了。
  • PTZ 状态机：PtzState 是纯状态机，NVR 发 ContinuousMove 它记下速度向量，tick(50) 推进位置，GetStatus 报当前位置。把状态机的输出接去驱动真实云台（或什么都不接），NVR 看到的就是一台云台功能完整的相机。
  • 两个 server：OnvifServer 监听 TCP 上的 SOAP，DiscoveryServer 在 UDP 3702 组播上答 Probe（启动发 Hello，关闭发 Bye）。两个句柄都带 #[must_use]——丢掉句柄等于停服。

跑起来后用任意 ONVIF 客户端验证（比如 onvif-go 的命令行）：onvif-quick -host <你的IP>:8080 -user admin -pass set-a-real-password，发现、认证、取流、PTZ 应该全部应答。

NVR 从两条路进来：组播发现（Probe 进、ProbeMatches 出）和 SOAP over HTTP（动作请求进、响应出）。请求解析对命名空间前缀宽容——客户端爱用什么前缀都接；响应序列化用显式前缀（tds:/trt:/timg:/tt:），所有插值都过 XML 转义。你的宿主代码只写在 handler 和注入接口里。

字节级稳定契约

这个库有一条要写在最前面的规矩，README 用加粗写着：不要改响应元素名、命名空间前缀和属性顺序，除非重跑消费端互操作测试。原因是消费端（比如 MiBeeNvr）在裸字节流上按 local-name 匹配响应，不过完整 XML 解析——改一个元素名都可能打断对方。crate 的测试里有一组 golden 响应字符串把这些钉死，改 golden 视同破坏性变更。

对接方的另一面也成立：NVR 那头的解析器如果是字节匹配型的，你升级这个库不需要做任何事——golden 测试保证线格式不变。

认证：写保护、读开放

认证三件套：verify_username_token 常数时间比较（nonce 空是 PasswordText，非空是 PasswordDigest——digest 的算式是 BASE64(SHA1(base64_decode(Nonce) + Created + Password))）、ReplayGuard 的 nonce 缓存加新鲜度窗口防重放、按来源的认证失败限速锁定（auth_failure_limit 次失败锁 auth_lockout_secs 秒）。

默认策略是务实的：动作名以 Set/Remove/Create/Go 开头的走 WS-Security，读操作开放——NVR 的轮询读不该被密码挡住，而改配置的动作必须过认证。要全开放没有反转开关，但可以不设凭据加 allow_no_auth = true（测试用）。

fail-closed 是硬的：配了空密码又没显式 allow_no_auth，start() 直接报错——「看起来安全实际裸奔」的配置活不过启动。想在自己的 handler 里预检请求，parse_soap_request(xml) 公开可用，返回 ParsedSoap{action, body_xml, username_token}。

媒体面：配置即广告

要分清一件事：这个库返回的是 URI，不是媒体。OnvifMediaConfig 里填的分辨率、码率、RTSP 端口会被如实写进 GetProfiles 和 GetStreamUri 的应答，但真正在 8554 端口上伺候 RTSP 的是你的宿主（RTSP server、ffmpeg 管道都行）。库把「NVR 问什么」答对，「流本身」由宿主喂。

OnvifMediaConfig 全字段（new(w, h, fps, bitrate, rtsp_port, ip) 覆盖常用项，细调用结构体字面量）：

字段说明
camera_width / camera_height / camera_fps / camera_bitrate写进 GetProfiles 的编码参数
rtsp_port / stream_pathGetStreamUri 拼出 rtsp://<ip>:<port><path>
snapshot_port / snapshot_pathGetSnapshotUri 指向的截图端点；端口 0 表示不支持快照（回规范 fault）
profile_token / video_source_token / encoder_token三类 token，NVR 按 token 选流
encodingVideoEncoding::H264 等
video_source_name视频源名
device_iploopback 来源回落到这里（反向代理场景）

未知 profile token 的 GetStreamUri 会回落主码流（fail-open），NVR 拿错 token 也不会扑空。

PTZ：没有电机也能装云台

PtzState 的全部方法：

方法行为
tick(dt_ms)宿主 50ms 一调，推进 ContinuousMove 位移与 AbsoluteMove 缓动
continuous_move(vel) / stop()NVR 下发，记速度向量/清零
absolute_move(target) / relative_move(delta)目标位置指数缓动 / 相对微调
save_preset(name) / save_preset_with_token / goto_preset / remove_preset / list_presets预置位族，内存态
get_position() / get_status()当前位置（x/y ∈ [-1,1]，zoom ∈ [0,1]）与运动状态

把这套状态机的输出去驱动真实云台（或什么都不驱动），NVR 看到的就是一台云台功能完整的相机——给没有电机的设备补 PTZ 语义、或者测 NVR 的云台逻辑，都是它存在的意义。

启用后，事件服务的 CreatePullPointSubscription、PullMessages（长轮询）、Renew、Unsubscribe 全部在库内路由，订阅地址挂在 SOAP 监听器上；publish_event 按订阅的主题过滤扇出。几个内置常量要心里有数：订阅队列 100 条、慢消费者丢最旧；订阅默认 1 小时、上限 24 小时靠 NVR 的 Renew 续；单次长轮询上限 60 秒（NVR 要 PT0S 立即返回也合法）。不启用事件时这些路由 404，线格式与未启用前逐字节一致——能力广告（GetCapabilities）也同步收敛。

struct MyParams; // 桥到你的 ISP/传感器

impl onvif_device_rs::imaging::ImagingParams for MyParams {
    fn get_param(&self, name: &str) -> Result<f64, onvif_device_rs::imaging::ImagingParamError> {
        match name {
            "Brightness" => Ok(read_brightness()), // 归一化 [0.0, 1.0]
            _ => Err(onvif_device_rs::imaging::ImagingParamError::InvalidName(name.into())),
        }
    }
    fn set_param(&self, name: &str, value: f64) -> Result<(), onvif_device_rs::imaging::ImagingParamError> {
        write_brightness(value)
    }
}

onvif_device_rs::imaging::register_imaging_actions(&mut server, Arc::new(MyParams));

register_imaging_actions 一次注册 GetImagingSettings/SetImagingSettings/GetOptions 三个动作；参数按 ONVIF 名（Brightness、Contrast、Exposure…）读写，值域归一化 [0,1]，越界返回 ImagingParamError::OutOfRange{value, min, max} 会变成规范 fault。曝光/白平衡模式有默认实现可覆写。

发现与 TLS

DiscoveryServer 的细节：with_identity(ip, port, name, hardware_id) 的名字和硬件 ID 会出现在 NVR 的发现列表里；with_scopes 加自定义 scope；with_uuid 固定 EndpointReference 的 UUID——NVR 按 UUID 记设备，不加这个，进程重启会被当成一台新相机。ProbeMatches 是单播 UDP 回包，突发负载下可能撞满发送缓冲，库内置了最多三次、指数退避的重发。

TLS 打开 tls feature 后配 tls_cert_file/tls_key_file 即可，两者必须成对——「证书半套」在启动时报错，没有静默的 HTTP 回落。证书在启动时读一次，之后改文件要重启。

生产项目里的用法

设备端库的消费方天然是「想把不是相机的东西变成相机」的项目。这个库从 MiBee 的 Rust 相机固件原样抽出，现役宿主两个，按功能对照：

功能生产项目用法
身份 / 媒体配置 / 发现mibee-eye-rsRust 相机的 ONVIF 面：OnvifMediaConfig 广告它的 RTSP 流，DiscoveryServer 让 NVR 一搜就到
PTZ 状态机 / 事件注入mibee-eye-rs检测器出的事件经 publish_event 推给在订的 NVR，PTZ 语义对商用 NVR 完整可用
多协议并存 / GB 35114mibee-eye-notebookPC 的摄像头和麦克风变成一台 ONVIF/国标设备，同一进程里 RTSP/RTMP 直出与 ONVIF 接入并存

看完整实现：mibee-eye-rs 把「Linux 板子变 ONVIF 相机」做成了完整产品——采集、编码、RTSP 供流、ONVIF 应答、事件推送一条龙，本篇每个接缝（媒体配置怎么填、事件从哪来、UUID 怎么固定）在它里面都有对应代码；mibee-eye-notebook 是同一套库的 PC 形态，适合参考「没有 V4L2 硬件时怎么接系统摄像头」。与 onvif-go 的客户端对练是现成的：一边跑 mibee-eye-rs、一边用 onvif-go 的 onvif-quick 或 MiBeeNvr 去添加它，发现、认证、取流、事件全链路当场验证。

排错清单

现象原因处理

PTZPtzState + tick 循环纯状态机，无电机可模拟
事件enable_events() + publish_event主题过滤、有界队列、长轮询
摄像参数register_imaging_actions(server, params)亮度对比度等 get/set/range
TLStls feature + 证书对both-or-neither，fail-closed
