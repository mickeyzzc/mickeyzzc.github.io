MiBeeVision：给 MiBeeNvr 的录像装上理解引擎

November 9, 2026 November 9, 2026 MiBeeOSS NVR, 目标检测, ONNX, ByteTrack, 自托管, Rust MiBee 项目实践系列 6443 字 13 分钟阅读
🔊

NVR 管住了一件事：录像一定在。但录像多了之后新问题来了——几十个 G 的回放谁来看？事后拖进度条找「那个人什么时候进来的」，靠的还是人眼。MiBeeNvr 的浏览器端 AI 能在实时预览页开着的时候盯画面，页面一关就没了。缺的是一个独立于页面、全天候跑在录像上的理解组件。

这就是 MiBeeVision：MiBee 生态的视频流 AI 后期处理引擎，也是 MiBeeNvr 的「AI 大脑」——对 NVR 录下的视频做目标检测、多目标跟踪与区域规则判定，输出结构化事件与带框快照，再直接回写 NVR。一句话分工：NVR 负责「录得下」，MiBeeVision 负责「看得懂」。录像生成后自动逐段分析，录像列表上每一段都被打上 AI 标记，人/车出现、区域入侵、越界、徘徊都变成可回查的事件。

它和 NVR 内置的浏览器端 AI 是什么关系

MiBeeNvr 自带浏览器端 AI 检测，推理跑在浏览器的 Web Worker 里。两者互补而非替代，边界很清楚：

浏览器端 AI（NVR 内置）MiBeeVision（服务端）
运行位置浏览器内 Web Worker独立进程（可与 NVR 同机或分机部署）
分析时机打开页面时的实时画面录像生成后逐段自动分析，7×24 不依赖页面开着
事件留存以实时画框为主结构化事件落库 + 带框快照，可回查可追溯
规则ROI 多边形（只圈区域内目标）区域入侵 / 越界 / 徘徊等事件规则
结果去向实时画面回写 NVR：录像列表 AI 标记 + AI 事件页

两者独立开关、互不影响。只开浏览器端 AI，等于只有「有人在看」的时候才有判断；只开 Vision，实时页面上少了即时画框。一起开着，实时有人看、事后有得查，才是完整的用法。

技术形态

  • Rust 单二进制：Linux x86_64 / aarch64 双架构，无外部依赖——唯一随包携带的是 ONNX Runtime 的动态库（推理运行时动态加载，这是它必须显式指定路径的原因）。
  • FFmpeg 解码：直接消费 NVR 录像段，不需要预先转码，录像是什么格式就解什么格式。
  • 内嵌 Web 配置页（默认端口 :9092）：填 NVR 地址与 API Key、选摄像头、画规则区域，保存即生效——全程图形化，不手工编辑配置文件。

选择「独立进程」而不是把 AI 塞进 NVR 主程序，是个有意的架构决定：分析是持续吃 CPU 的活，NVR 主机（常见是低功耗 NAS 或 ARM 盒子）未必扛得住；独立进程意味着它可以被挪到另一台机器上，NVR 的采集回放不受牵连。

架构：Source → Pipeline → Sink

Vision 采用管道式分层架构，每一层以接口抽象、按配置组合：

层职责说明
Source产出录像段与 NVR 同机时用 local_file（共享录像目录，直接读本地文件）；分机部署时用 http_download（从 NVR 下载后分析）。配置页保存后自动生效
Pipeline把画面变成判断FFmpeg 解码抽帧 → YOLOv8n 目标检测（ONNX Runtime）→ ByteTrack 多目标跟踪 → 区域入侵/越界/徘徊规则判定
Sink把判断变成记录事件写入 SQLite/libSQL；每条事件生成带框快照；状态与事件回写 NVR

Source 层的两种方式对应两种部署哲学：local_file 要求 Vision 与 NVR 共享录像存储目录，录像段零网络拷贝，适合分析进程与 NVR 同机的情况；http_download 让分机部署成为可能——把吃 CPU 的分析负载从 NVR 主机上剥离出去，NVR 该干什么干什么，分析机器只管拉录像段来算。两种方式都在配置页选择并保存，切换不需要动命令行。

运行形态是 serve 常驻服务：进程常驻，持续消费 NVR 新生成的录像段。摄像头选择、规则区域、传输方式都在配置页改，保存后管线自动重启生效。

三条设计原则值得单独说：

  • 与 NVR 解耦：Vision 是独立进程，NVR 挂了 Vision 不受影响，反之亦然——分析组件不该和存储组件绑死在一条命上。数据与语义的中枢在 NVR：它决定「哪些录像段给 Vision 分析」，也消费「Vision 判定出的结果」。
  • 每层可替换：录像段来源、检测模型、事件输出都以接口抽象。换模型、换存储、增加输出渠道，都是「加一个实现」，不改既有链路。
  • 零云依赖：推理、规则判定、存储全部在本地完成，没有任何外部服务调用。

能力面：Lite v0.1.0 的清单

下表是当前发布版（Lite v0.1.0）的能力清单，以及规划中 Pro 版的增量：

能力说明Lite v0.1.0

检测这块没有可配置项：YOLOv8n 随二进制内置，不需要单独下载模型、不需要选模型，录像段解码抽帧后直接进检测器。这是个刻意的取舍——Lite 的定位是「装上就能用」，模型可换性留给后续版本。

跟踪是检测和规则之间的那一环，也是容易被低估的一环。检测框逐帧交给 ByteTrack 做跨帧关联，同一个目标在连续帧间保持同一个 ID，形成轨迹。跟踪的意义在于把「每帧都有框」升级成「这个目标从哪来、到哪去、在区域里待了多久」——没有轨迹，徘徊检测和越界方向判定都无从谈起；没有跟踪，同一个目标跨帧反复出现还会被反复计数，事件列表会被同一个目标刷屏。

三种事件规则

三类规则都在配置页按摄像头配置（规则名 + 区域顶点），保存即生效。总表先看触发条件和典型场景：

规则触发条件典型场景
区域入侵目标进入划定区域院子、店铺门口、仓库
越界目标跨越划定边界线（含方向判定）围墙、院门、通道
徘徊目标在区域内长时间停留周界、门前、ATM

三者的分工按「空间语义」划开，各自对应一类现实问题。

区域入侵回答的是「谁进了不该进的地方」。在配置页为摄像头画一个多边形区域——院子的一角、仓库的门廊、店铺的柜台前——只要跟踪器认定某个目标进入了这个区域，事件即刻产生。它适合那些「出现即异常」的场景：Normal 状态是空的，有人就是信号。

越界回答的是「谁从错误的方向穿了过去」。它画的不是面，而是一条边界线，并带上方向判定——围墙、院门、通道口这类「只能从指定侧通过」的位置最适合。方向这个维度是入侵规则给不了的：院门内侧外出是日常，外侧翻进来就是事件，同一条线，方向反了语义就反了。

徘徊回答的是「谁在这里停了太久」。目标进入区域不算事，停留超过时长阈值才算——周界边有人来回溜达、门前有人长期逗留、ATM 前有人站着不走，都是「停留」本身构成信号的场景。它建立在跟踪给出的轨迹之上：没有「同一个目标待了多久」这个量，徘徊就无从判定。

同一个摄像头可以同时配多条规则，各自画各自的区域和线，互不干扰。

与 MiBeeNvr 的协同

Vision 与 NVR 是一对天然搭档：NVR 出画面（录像），Vision 出判断（检测/跟踪/规则），判断结果再回到 NVR 呈现。接线三步：

  1. 在 NVR 生成 API Key：「设置 → AI 检测 → 生成 API Key」，生成的 Key 以 mbv_ 开头；
  2. 在 Vision 配置页填入：浏览器打开 http://<Vision主机IP>:9092，填 NVR 地址、粘贴 mbv_ API Key，点「测试连接并拉取摄像头」；
  3. 选摄像头、画规则：选择要分析的摄像头（Lite 为 1 路），配置规则名与区域顶点，点「保存」——管线自动重启并开始分析。

有两个前置漏掉任何一条，典型症状都是「配置页能打开，但永远不出事件」：

前置漏掉的后果
必须设置 ORT_DYLIB_PATH 指向随包的 libonnxruntime-*.so推理库加载失败，管线无法处理录像段（配置页仍能打开，极具迷惑性）
必须用 mbv_ 开头的 API Key，而不是网页登录 token（mbs_ 开头）回写 AI 事件返回 401，NVR 录像的 AI 状态永远为空

mbs_ token 只对浏览器网页会话有效；mbv_ API Key 才是发给 Vision 这类外部组件用的。两者长得像，但用途严格分开。

部署拓扑有两种，配置页里选传输方式（[transport].type）并保存：

拓扑传输方式要求
Vision 与 NVR 同机local_fileVision 能直接读 NVR 录像存储目录（共享存储路径一致）
Vision 与 NVR 分机http_downloadVision 能通过网络访问 NVR；录像段先下载再分析

跨机部署时如果日志出现「打开视频失败，跳过： No such file or directory」，几乎都是误把 local_file 用在了没有共享存储的分机拓扑上——传输方式与拓扑必须匹配。

结果流向三条线：NVR 录像段进 Vision 分析后，一路变成录像列表的 AI 状态标记（处理中 / 完成），一路变成 AI 事件（区域入侵 / 越界 / 徘徊）回写 NVR 的 AI 事件页，一路变成带框快照留在 Vision 本地。全链路打通的自检标准很明确：Vision 配置页状态区显示「管线 运行中 / NVR 已连接」，且几分钟后 NVR 录像列表的 AI 状态列出现 completed。

版本搭配上，Vision 使用独立版本线（mibee-vision-vX.Y.Z），与 NVR 版本号无关；请使用与 Vision Lite 同期或更新的 MiBeeNvr 版本，确保 AI 状态与事件接口可用。

排错速查

部署和接线环节的故障，症状高度集中，一张表列完：

症状原因处理
配置页能打开，但永远不出事件ORT_DYLIB_PATH 没设或路径不对，推理库加载失败指向随包的 libonnxruntime-*.so，重启服务
回写 AI 事件返回 401，AI 状态永远为空用了 mbs_ 开头的网页登录 token到 NVR「设置 → AI 检测 → 生成 API Key」拿 mbv_ Key
日志报「打开视频失败，跳过： No such file or directory」跨机部署误用了 local_file传输方式改为 http_download（或真正共享录像目录）
配置页拉不到摄像头列表NVR 地址不通或 Key 无效先确认浏览器能访问 NVR；核对 mbv_ Key 是否粘贴完整

最后一道自检：配置页状态区显示「管线 运行中 / NVR 已连接」，且几分钟后 NVR 录像列表的 AI 状态列出现 completed——四个字出现，整条链路就是通的。

事件怎么变成通知：与 Bell 的衔接

Vision 自己不发通知，它的产出是「回写 NVR 的事件」。通知出口在生态的另一环：MiBeeNvr 内置告警通知外发能力，把相机离线、画面冻结、存储健康、移动侦测、AI 事件等以 mibee-alert/1 JSON 报文 POST 到 webhook 接收端，AI 事件对应 ai.detection 类型（快照 URL 随通知携带）。MiBeeBell 是这个外发能力的开箱即用接收端——所以完整链路是：Vision 分析出事件 → 回写 NVR → NVR 按告警规则外发 → Bell 管道做去抖、冷却、静默 → 送到你选的渠道。每一环各司其职，Vision 不越界做通知，Bell 不关心检测。

同类产品都在什么位置

视频 AI 这个赛道不小，打法分三类：一体化 NVR+AI、给现有 NVR 加 AI 层、通用视觉 API 服务器。

路线代表你得到什么你要付出什么
一体化 NVR+AIFrigate（MIT 开源）录制+检测一体；Coral TPU / OpenVINO / GPU / CPU 多档推理；MQTT 事件 + 官方 Home Assistant 集成；Frigate+ 订阅做自定义模型训练把整个录像管线交给它；通知与展示层自己在外部搭
智能家居向 NVRScryptedHomeKit / HA 联动顺滑NVR 能力围绕家居平台展开
通用视觉 APIDeepStack（已停更）/ CodeProject.AI / DOODS一个出「框和标签」的 API，谁都能接规则语义、跟踪、事件生命周期、回写展示全部自己补；上游维护风险自担
商业 NVR 外挂 AIBlue Iris + CodeProject.AIWindows 上成熟的录制 + 外挂检测商业授权；Windows 常驻；AI 进程要自己养
商用智能 NVRAcuSense / WizSense 一类开箱即用的本地智能检测绑定厂商硬件与云激活，事件生态封闭，对接要二次开发
给现有 NVR 加理解层MiBeeVision检测→跟踪→规则→事件→回写一条龙，产出住在 NVR 里，通知经 Bell 出绑定 MiBeeNvr 生态；Lite 单摄像头 CPU

Frigate 是开源赛道公认的一体化标杆：录制与检测一体，硬件加速生态最全，对 Home Assistant 用户几乎是无缝。选它等于把录像管线也交给它管——对已有 NVR 的用户这是一次迁移，通知和展示还要在它之外另搭。Frigate+ 订阅可以训练自定义模型，这是固定内置模型之外的一条路，代价是持续订阅。

Blue Iris + CodeProject.AI 是 Windows 阵营的组合拳：商业 NVR 挂一个通用 AI 进程。这条「通用 API」路线的维护风险这两年看得比较清楚：DeepStack 网站关停、社区整体迁移；CodeProject.AI 接棒之后，2025 年社区也对它的前景有过讨论、对 2.8/2.9.5 两个版本的可靠性有过抱怨。API 服务器只出「框和标签」——区域规则的语义、事件生命周期、回写展示，全都要自己补一层。

Scrypted、Shinobi、Viseron 各有 AI 路径，分别偏智能家居、插件生态、本地优先，维护节奏和生态广度参差。商用智能 NVR 开箱即用，但封闭生态里的事件想接进自己的通知链路，基本靠二次开发。

MiBeeVision 占的是「给现有 NVR 加理解层」的位置：检测、跟踪、规则、事件、回写展示一条龙，产出直接住在 NVR 里（AI 徽标 + AI 事件页），通知走 NVR 外发加 Bell 管道——不换 NVR，也不搭第二套系统。边界同样如实：绑定 MiBeeNvr 生态，不是通用 NVR 组件；Lite 是单摄像头 CPU 推理，检测模型固定 YOLOv8n，不可换模型；多摄像头与 GPU 加速在规划中的版本里。要 Home Assistant 深度联动或 Coral 加速，Frigate 是更成熟的答案。

几个常见问题

需要 GPU 吗？ Lite 版不需要：ONNX Runtime CPU 推理，普通 x86 服务器或 ARM 设备即可。GPU 加速（CUDA / TensorRT）与多摄像头在 Pro 版（规划中，发布时间待公布）。

结果存在哪里？ 两处：NVR 侧是录像列表 AI 标记 + AI 事件页；Vision 本地是结构化事件（SQLite/libSQL）+ 带框快照。NVR 侧看结果，Vision 侧存原始记录。

想分析已经录好的历史录像怎么办？ 对存量录像的批量补分析在 Pro 版能力清单中（规划中，发布时间待公布）。当前 Lite 面向新产生录像的持续分析。

支持 Windows / macOS 吗？ 不提供，当前平台为 Linux x86_64 / aarch64。需要在这两个桌面系统上看结果的话，打开 NVR 的页面即可——结果住在 NVR 里，分析主机是什么系统并不重要。

版本、许可与边界

MiBeeVision 使用独立版本线（mibee-vision-vX.Y.Z），不跟 MiBeeNvr 的版本号走，两者各自演进。两档发行：

Lite（已发布 · 免费）Pro（规划中，发布时间待公布）
当前版本v0.1.0（2026-10 发布）—
摄像头单摄像头多摄像头
推理CPU（ONNX Runtime）GPU 加速（CUDA / TensorRT）
分析方式录像生成后逐段分析另含历史录像批量补分析
分发随 MiBeeNvr 发布会免费分发待公布

许可口径照实说：软件本体是闭源专有软件，版权归 MiBee Studio 所有，Lite 版随 MiBeeNvr 发布会免费分发；内置检测模型 YOLOv8n 采用 Ultralytics AGPL-3.0 许可，使用本程序进行检测即视为接受 AGPL-3.0 的相关义务，商业闭源分发需另行取得授权（或将模型替换为宽松许可模型）。

边界收束一遍：Lite 是单摄像头、CPU 推理、固定模型，面向「新产生录像的持续分析」；它绑定 MiBeeNvr 生态而非通用 NVR 组件；历史录像补分析、多摄像头、GPU 加速都在 Pro 的规划清单里，发布时间待公布。它在工作室生态里的分工是：NVR 管采集、回放和告警外发，Steward 管设备资产，Bell 管通知管道，MiBeeVision 补上「录像里发生了什么」这一环。
