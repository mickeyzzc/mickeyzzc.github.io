五个协议库同天发版：onvif-go 进 v2、国标设备侧收官、onvif-c 首发

September 21, 2026 September 21, 2026 MiBeeOSS Go, Rust, C, ONVIF, GB28181, 监控摄像头, ESP32, 开源 MiBee 开源项目实践系列 5701 字 12 分钟阅读
🔊

MiBee 的相机接入层跑两条协议：ONVIF 是国际市场的通行标准，海康、Axis、大华都说它；GB/T 28181 是国内安防的国标，政企项目绕不开。这套协议栈按「协议 × 语言 × 角色」拆成五个独立库开源，全部从生产代码中抽出，最近一轮发布里五个库在同一天打了 tag：onvif-go 进入 v2 稳定线，onvif-device-rs 登上 crates.io，gb28181-go 与 gb28181-rs 完成国标 2022 版设备侧能力收官，onvif-c 作为第五个成员首发。这篇按库交代各自的能力边界、关键设计取舍和遗留限制，以各仓库当前发布为准。

package main

import (
    "context"
    "fmt"
    "log"

    "github.com/mickeyzzc/onvif-go/v2/onvif"
)

func main() {
    client, err := onvif.NewClient("http://192.168.1.100/onvif/device_service",
        onvif.WithCredentials("admin", "pass"),
        onvif.WithAutoClockSkew()) // 容掉设备时钟偏差，海康系 401 的头号根因
    if err != nil {
        log.Fatal(err)
    }
    if err := client.Initialize(context.Background()); err != nil {
        log.Fatal(err)
    }

    info, _ := client.Device().GetDeviceInformation(context.Background())
    fmt.Printf("%s %s (fw %s)\n", info.Manufacturer, info.Model, info.FirmwareVersion)

    profiles, _ := client.Media().GetProfiles(context.Background())
    mainToken := onvif.SelectMainProfile(profiles) // 选分辨率最高的主码流，不是 profiles[0]
    uri, _ := client.Media().GetStreamURI(context.Background(), mainToken)
    fmt.Println("主码流:", uri.URI)
}

onvif-go：v1.2 到 v2.2 的三级跳

这一轮连发三版，各管一件事。

v2.0.0 从 rc 系列毕业，是这条线的首个稳定版。两个补齐的大件：服务端的 Events PullPoint 服务真正落地——CreatePullPointSubscription、PullMessages（长轮询）、Renew、Unsubscribe 都在订阅地址上服务，宿主经 PublishEvent 接缝注入自家分析事件，WSPullPointSupport 的宣告与实现终于一致；客户端按规范解析双层通知——合规相机把 tt:Message 包在 wsnt:Message 里，穿透包装层才能拿到 MotionAlarm 的 State 和 Score。v1 迁移到 v2 多数情况只是换 import 路径（模块路径带了 /v2 后缀）。顺带说一句生态背景：Go 侧星数最高的旧库 use-go/onvif 不止停更，在新 Go 版本上已经编译不过——自己养一条稳定线的意义正在于此。

v2.1.0 是线格式正确性版本：线格式的 ground truth 换成官方 WSDL/XSD 集。最有代表性的一修是，对大华这类严格的设备，此前的 PTZ/成像/证书载荷请求发出去是空壳——命名空间错位，设备认不出字段，回 HTTP 200 然后静默什么都不做。全量 WSDL 审计把双向的错位都修了。能力面新增两块都指向 Profile M：Media2 客户端给出编码无关的配置模型，GetVideoEncoderConfigurationOptions 按支持的编码逐项上报——这是 H.265/AV1 时代对接新相机的正路；Analytics 客户端加 metadata 流解析器，规则与分析模块的增删改查、帧、跟踪目标、包围盒、地理位置都能解。服务端有了 TLS（Profile T 的传输基线）。要提醒的是，这版在 v2 线内改了受影响面的线上字节——「线格式正确」优先于「字节不变」——对接方如果有依赖旧形状的解析器，升级前看一眼 CHANGELOG。

v2.2.0 补齐与 Rust 孪生的最后一项 PTZ 差距：服务端预置位族齐装（SetPreset、RemovePreset、GetConfigurations、GetNodes，全部 WSDL 正确命名空间），客户端 GetConfigurations 解码 pan/tilt 和 zoom 限位——此前是解析了又丢掉。

onvif-device-rs：命名落定，能力对齐

命名上有个插曲：crates.io 上 onvif-rs 这个名字被 2018 年的空占位仓库占着，此前只能走 git 依赖分发。现在的解法是 crate 以 onvif-device-rs 之名上了 crates.io，cargo add 直接可装（最新 0.7.0）；仓库保留原名，README 写清了与 lumeohq 同名客户端库的消歧义。

v0.7.0 与 onvif-go v2.2.0 是孪生发布，两库的能力差距清单清零：SystemReboot 线格式应答（只答协议，不执行重启）、WS-Discovery Hello/Bye 通告（尽力而为，丢了不影响 Probe 应答）、TLS 监听器（tls cargo 特性门控，默认关，证书配置不完整直接 fail-closed）、事件 pull-point 全族（宿主经 publish_event 注入，扇出到全部在订订阅，Concrete/ConcreteSet 主题过滤，长轮询）。Create 类动作走 WS-Security、读操作开放；不启用事件时路由 404，线格式逐字节不变。

安全面上有个正中靶心的修复：quick-xml 0.36 → 0.41（RUSTSEC-2026-0194/0195，高危 7.5）。两条通告都指向不可信 XML 解析面——恰好是这个库的日常业务。解析循环迁到新事件模型上，跨拆分文本事件的实体密码现在能正确累积。

国标设备侧：孪生收官

gb28181-go v0.11.0 与 gb28181-rs v0.12.0 是一对孪生版本，同一份目标：GB/T 28181-2022 的「平台→设备」面齐装——每类控制、配置、订阅、对讲流程都有解码后的线格式路径与宿主回调。

  • 控制/配置：DeviceControl 子命令组（IFrameCmd、RecordCmd、GuardCmd、AlarmCmd、TeleBoot、PTZCmd 透传）；PTZCmd 位级解码，Go/Rust 共享同一份 golden 字节表，而且表由平台侧构造器生成——编码与解码不会各自漂移；DragZoom；DeviceConfig 加 ConfigDownload 与 HomePosition。
  • 订阅/通知：SUBSCRIBE/NOTIFY 框架，告警、目录变化、移动位置三类通知器；9.4.2 节的 MediaStatus 完成通知——BYE 中止的会话保持静默，不误报。
  • 对讲：接收（G.711 sink）、上行（设备到平台 20ms RTP）、语音广播端到端（平台发起、设备应答、音频 INVITE 回呼、平台推流）。协商出的上行编码律暴露给宿主。
  • 生命周期：优雅注销（REGISTER 带 Expires: 0 走完整 401 流程）、SIP-Date 校时观察。

gb28181-rs 侧另有三件自己的事：X-GB-Ver 协议协商（2022 版附录 I，可选开启，不配置则线格式逐字节不变）、2022 版五组信息查询的最小应答、ILP32 编译修复——32 位目标重新可编，CI 加了专门的防回归 job。

修复里最值得记的是 gb28181-go 的 ACK 竞态：gosip 上游在无锁状态下改写在途请求的顶层 Via（上游 issue #87），并发场景下 ACK 会挂错 dialog。全部 ACK 路径改成从发送前的 INVITE 快照构建之后，race detector 的 89 份报告归零。这个修复顺带说明了为什么设备侧坚持手写 SIP、平台侧才站在 gosip 上——设备的 SIP 子集小到可以手写并完全掌控，平台面对的场景杂，借成熟栈的力划算。

平台端：从 MiBeeNvr 抽出来的完整国标平台

平台端的出身和设备端一样，是生产代码：从 MiBeeNvr 的国标接入实现里整体抽出（v0.2.1 完成提取），之后陆续合入，现在 README 的包清单是这样的：

  • platform/：设备/通道注册表（保活存活窗口）、MPEG-PS 解复用（无 PSM 时带音频回退启发式）、RTP 端口池、PTZ 与 A505 命令构造、RTP 接收重组（UDP 与 TCP-passive、抖动缓冲、SSRC 锁定）。四批迁移已落三批，README 如实标注。
  • platform/sip/：gosip 之上的完整平台服务器——digest 认证、保活离线检测、目录刷新加三类 SUBSCRIBE、INVITE/BYE 会话管理，附一排固件怪癖补丁（投机 ACK、REGISTER 源端口轮换、长 GOP 的 IDR 看门狗）。
  • platform/cascade/：级联——本级作为下级向上级注册，聚合目录上报、INVITE 转发、录像段回放。
  • psmux/：PS/RTP 复用器（H.264/H.265、G.711、超 60KB 访问单元切分），设备推流与级联转发共用一套。
  • conformance/：设备与平台的本机回环一致性套件——真实的 device.Server 对真实平台 SIP 服务器，从 digest 注册到 RTP/PS 逐字节往返，每次 CI 对一遍全部协议读法。
  • security35114/：GB 35114-2017 A 级安全的可选实现（build tag 隔离）——SM2 证书双向认证的 REGISTER、SM2 信封里的 VKEK 协商、带密 SM3 的 Note 头完整性，设备侧和平台侧都有。

平台端单二进制这件事顺带成立：PS 解复用都在库内，不外挂媒体服务器进程——这些包的出身本就是 MiBeeNvr 的国标接入代码，抽出来之后别的 Go 项目也能这样用。

onvif-c：第五个成员

链路图里最底下那块。几个 ESP32 摄像头固件此前各自长着一份 ONVIF 实现（四个板型仓库），维护重复，这次抽成 plain C 组件统一养：onvif-c v0.1.0。

它是五个库里最「物理」的一个，约束直接写进了设计：

  • 约 10KB 代码足迹、零第三方依赖，目标平台 ESP-IDF。没有 XML 解析器：动作识别用 strstr()，响应用 snprintf() 拼，全部请求级缓冲。内存模型简单到从传感器回调上下文里调用也安全。
  • 覆盖面是刻意的最小充分集：NVR 接入一台相机要问的全部动作（GetSystemDateAndTime、GetDeviceInformation、GetCapabilities、GetProfiles、GetStreamUri、GetSnapshotUri），加 MotionAlarm 主题的 Pull-Point 事件（State 加 0-100 的 Score）。
  • PullMessages 不做长轮询、立即返回——esp_http_server 的 worker 永不阻塞，这是 ESP-IDF 线程模型里的硬约束。
  • 板级差异全部收在 onvif_c_config_t 一个配置接缝里：厂商、型号、序列号、IP、流地址、HTTP 端口、事件开关，库内零硬编码。固件侧移植层约百行。
  • 字节稳定照旧是契约，而且比 Rust 版更细：Device/Media 信封用 soap:/tds:/trt:/tt: 前缀（小写 utf-8 声明），Events 信封用 s:/tev:/wsnt:（大写 UTF-8）——两种风格并存，因为各自就是生产 NVR 实际在说的方言，README 明说不要「统一」它们。
  • 明确不做的写进了 Security 一节：不做 ONVIF 认证。够到端口的谁都应答，只放完全可信的内网或反向代理后面。精简的刻意取舍，不是疏漏。

质量面上，tools/onvif_probe.py 提供无硬件冒烟测试：跑遍全部动作加完整订阅周期，退出码 0 即全过。

谁在生产环境里用

「真机打磨」不是修辞。五个库的出身就是产品，现在也仍在产品里每天跑：

  • MiBeeNvr：自托管录像机，在低功耗设备上 7×24 跑。onvif-go 客户端连海康、Axis 的商用相机，gb28181-go 平台端收国标设备注册——平台侧的包正是从它的国标接入代码里抽出来的。
  • MiBee Eye 开源相机家族：把 Linux 板子变成 ONVIF/国标相机——mibee-eye-go 跑 gb28181-go 设备端加 onvif-go 虚拟相机，mibee-eye-rs 跑 gb28181-rs 加 onvif-device-rs，两个设备端库正是从这条相机产品线里抽出来的；mibee-eye-notebook 则把 PC 的摄像头和麦克风变成一台 ONVIF/国标设备，GB 35114 安全特性在它上面开着跑。
  • 四个 ESP32 相机固件（esp32s3-n16r8-cam、ai-thinker-esp32-cam、seeed-esp32s3-cam、luatos-esp32s3-a10-camera）：onvif-c 组件随固件同步携带，库的改动先在真机上过一遍再发布。

同一台 NVR 既要连商用相机，又要收自建固件注册上来的国标流——客户端、设备端、平台端三个角色在一条产线上互相对咬，库里的每一次互操作修复，起点都是这条链路上真机报出的问题。

工程门槛

这些库每天吃进去的都是不可信输入——SOAP 请求体、discovery Probe 数据报、MANSCDP 报文、digest 与 UsernameToken 字段——五个仓库的 CI 为每一处解析面挂着 fuzz 或属性测试。

Go 与 Rust 的孪生库共享同一份 golden 字节表：媒体面与信令的跨语言一致性靠断言维持，谁的封装改了谁先红，不靠「同一份设计」这句话。

「真机优先于规范」是这些库的底色，这轮更新给它加了个精确的分工：v2.1.0 之后，线格式的 ground truth 是官方 WSDL/XSD——真机负责喂互操作行为（认证梯队、时钟偏差、怪固件补丁），规范负责钉死每个元素的归属，两件事各管各的。

状态与限制

  • onvif-go v2.2.0：首个稳定线。v1 到 v2 主要是 import 路径迁移；v2 线内升级注意 v2.1.0 的线格式修正。
  • onvif-device-rs v0.7.0：与 onvif-go 能力对齐完成，crates.io 分发。
  • gb28181-go v0.11.0：设备侧 2022 收官；平台端可用，迁移四批落三批。
  • gb28181-rs v0.12.0：与 Go 孪生同能力；不含平台端角色，刻意。
  • onvif-c v0.1.0：不做认证；事件单订阅；C 组件没有 crates.io 这回事，vendor 进固件工程就是分发方式。
