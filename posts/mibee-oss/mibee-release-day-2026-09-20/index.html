一天发四版：Steward 进路由器、Nvr 上桌面，onvif-c 与 serialtap 首发

September 20, 2026 MiBeeOSS MiBeeSteward, MiBeeNvr, ONVIF, OpenWrt, ESP32, 串口调试, Go, 开源 MiBee 开源项目实践系列 4103 字 9 分钟阅读
🔊

2026 年 9 月 20 日，四个仓库在同一天打了 tag。正好各管一段：

  • 看清网里有什么——MiBeeSteward v0.6.0
  • 自制摄像头被认出来——onvif-c v0.1.0
  • 把画面录下来、随时回看——MiBeeNvr v0.13.0-preview.1
  • 调固件时旁边有人帮你记日志——serialtap v0.1.0

前两个是老项目的例行迭代，后两个是第一次点 tag。逐个讲这版值得动手玩的，以及背后为什么这么做。

MiBeeNvr v0.13.0-preview.1：装在自己电脑上，路数往上堆

这版最能感知的变化是部署形态：录像机不再只属于服务器。Windows 给了双击安装的 Setup exe，装完缩进系统托盘（打开界面、退出、改监听端口都在托盘菜单里）；macOS 给了 DMG，装完在菜单栏。工程上为这个形态做的事比看起来多：Windows 端按 GUI 子系统编译，全程没有 cmd 黑窗；升级是运行中换二进制；卸载器会先停掉正在跑的服务再自删，避免把自己删进半死状态；macOS 的菜单栏助手在真机上磨了好几轮对话框可见性和「退出后又复活」的问题。桌面模式默认只听 127.0.0.1、走本地免密信任——这是刻意的边界：桌面形态就是给这台机器自己用的，要远程访问请回到服务端部署。未签名 DMG 首次打开需要右键 → 打开。

装在自己电脑上之后有个实际玩法：指定几路摄像头录成素材、文件直接落本机。剪辑、留证、做演示都不用再从别的机器倒。

不想存盘的人这版也照顾到了：存储设置里新增全局「默认启用录像」开关，关掉后所有未单独设置的摄像头（含国标自动注册进来的通道）只直播不写盘，保存即热生效。

重头戏在存储与 I/O，方向是多路写入的低功耗设备怎么扛得住：

  • 每段录像一个独立的写入状态：FD 常驻、写合并、锁分片——多路同时写不再挤一把锁
  • 写入前 fallocate 预分配、收尾 truncate，减少文件系统元数据抖动
  • posix_fadvise 管理 page cache，合并缓冲自适应，避免大合并把内存吃穿
  • 进程级 I/O 预算调度：合并、清理、转码共用一个令牌桶限速，给录制主路径让路——后台任务再重，录像不断流
  • 删除也计费：按字节速率护栏加目录局部性分组，清理旧录像不再把 SD 卡和 USB 盘打爆
  • 闪断相机的碎段攒批一次折卷，写放大降到 1/N

配套的还有规划式 WAL 检查点（空闲期被动触发、journal 限额）和自适应 GOMEMLIMIT（配合 systemd/Docker 内存配额）。两个默认关闭的实验特性（顺序追加桶、转码碎段门槛）留给愿意吃螃蟹的人。

MJPEG 录像这版改成了单文件 AVI 容器——旧的「每帧一个文件」布局在低功耗设备上就是 I/O 灶：一路 15fps 的 MJPEG 相机每分钟制造 900 个小文件，目录项和元数据写放大都吃不消。旧录像不动照常回放，想整理用 mibee-nvr repair mjpeg-containerize 一条命令迁移。顺带一提，MJPEG 相机现在也有了正经的 RTSP 输出地址（RTP/JPEG，RFC 2435），第三方监控软件可以直接拉。

可靠性方面修了几个外部报告的真问题：SDP-only 参数集的相机直播全黑（握手时拿不到参数集的老相机很常见）、hls.low_latency 配置不生效、空 playlist 从假数据改成 404；合并与转码之间一系列跨引擎竞态也逐个堵上了。

获取渠道两个消息：手机 App 因备案推迟；飞牛商店入驻申请递了没回音，暂时仍走 GitHub 安装升级——不过这版把飞牛统一网关下的 SPA 崩溃和登录翻转修好了，离线在线双包齐全。另有 Gitee 镜像（只保留最新稳定版）和 Home Assistant 官方集成。

注意这是预览版：功能冻结、供提前验证，已部署实例的更新检查不会推预览版，跑生产等正式版。这版还有位新贡献者首次参与就合并了 45 个 PR，存储 I/O 优化的主力实现就出自他手。

MiBeeSteward v0.6.0：先看清网里有什么

网络资产清点工具，回答「网里到底连了什么、每台是谁家的」。这版的关键词是住进路由器：安装包给了 tarball、opkg .ipk、apk .apk 三种形态，安装器从 uci 派生网段、开常驻被动源、修 ICMP 权限，agent 的注册信息可以内联也可以留空后补（服务停着，步骤打印在日志里）。装完 LuCI 里多一个服务入口，改端口改密码点页面就行——首启全程不碰 SSH，密码直接在浏览器里创建，安装器不再打印任何临时凭据。

住在路由器上，能看到别处看不到的东西：WiFi 关联记录（谁、信号多强、连了多久）、DHCP 分配（谁拿了什么 IP、自称什么主机名）、DNS 查询（谁在问什么域名）。这版把 DHCP 租约主机名和旁听的 mDNS/SSDP 公告直接喂进指纹分类器——那些从不应答任何探测的智能插座、扫地机、空气检测仪，也能认出品牌和品类；新增的米家生态主机名语料覆盖了十几个以前「一问三不知」的设备家族。上周对照实测里留的尾巴——双宿路由器上被动目击会记错网段——这版按 IP→CIDR 归属修掉了，配了分来源计数。

担心扫自己家？演示模式起一个假网络随便玩，玩完一键清空。

分布式形态补齐了多视角拨测：探测计划经命令通道下发各 agent，结果按视角分轨回流，界面并排对比；agent 的网段扫描原生调度，漫游设备不再被过期租约误杀。SNMPv3 凭据只存在 agent 本地加密库里，线上跑的只有凭据名。

工程侧值得一说的是 openapi.yaml 成为 API 唯一事实来源：TS 和 Go 客户端都从它生成、CI 查漂移，前端手写的 wire 类型全部退役——这轮修掉的「趋势图读不存在的字段」正是手写类型的经典翻车。升级侧有两件事要注意：列表端点统一分页包裹、裸数组消失（手写脚本对照调整）；(ip, network) 唯一索引在全新安装上从未生效，升级首启会自动去重重建，迁移前先备份。质量战役把 CI 覆盖率推到 85%，顺带挖出并修掉 4 个真实缺陷。

二进制 CGO-free，32 位 ARM 路由器 make build-linux-arm 本地出包。

onvif-c v0.1.0：协议库家族的第五个成员

ONVIF 和国标的协议栈，此前是四个库并行：Go 的 onvif-go、gb28181-go，Rust 的 onvif-rs、gb28181-rs。今天补上第五块拼图 onvif-c——ESP-IDF 的 plain C 设备端库。

来历不神秘：几个 ESP32 摄像头固件里各自长着一份 ONVIF 实现，维护重复，于是把共用部分抽出来统一养，固件侧只留板级差异（厂商、型号、序列号、IP、流地址、HTTP 端口），全部收在 onvif_c_config_t 一个配置接缝里，库内零硬编码。

覆盖面是刻意的「最小充分集」——恰好是 NVR 接入一台相机要问的全部动作：

  • SOAP Device/Media：GetSystemDateAndTime、GetDeviceInformation、GetCapabilities、GetProfiles、GetStreamUri、GetSnapshotUri
  • Pull-Point 事件：MotionAlarm 主题，State 加 0-100 的 Score
  • WS-Discovery 应答器：UDP 3702 组播，Probe 单播回应，Hello 每 30 秒广播，WiFi 未就绪时持续重试
  • 可选 mDNS：_onvif._tcp，构建里没有 espressif/mdns 时干净剔除

几个设计取舍值得点出。事件服务不做长轮询——PullMessages 立即返回，esp_http_server 的 worker 永不阻塞，这在 ESP-IDF 的线程模型里是硬约束。没有 XML 解析器、没有动态状态：动作识别用 strstr()，响应用 snprintf() 拼，全部请求级缓冲，代码足迹约 10KB、零第三方依赖，95% 行覆盖。移动侦测的接入点是一个非阻塞 hook，从 WiFi-CSI 之类的传感器回调上下文里直接调也安全：

c

onvif_c_motion(true, 87);   /* MotionAlarm State=true Score=87 */

产线血统也说明质量：响应 XML 与 MiBeeNvr 字节级对齐（NVR 端解析不惊不乍），和海康级客户端实际对过。tools/onvif_probe.py <ip> 提供无硬件冒烟测试，跑遍全部动作加完整订阅周期。

一个必须说死的边界：这个库不做 ONVIF 认证。够到端口的谁都应答，只放完全可信的内网。保持精简的刻意取舍，不是疏漏。

serialtap v0.1.0：批量调试的副产品

写那几个 ESP32 固件时的副产品：板子一多，逐台开串口监视器实在熬人，于是有了这个 Linux 上的插上即记采集器。

设计上最讲究的是身份：以 USB 物理口（by-path）为准——设备重枚举换 ttyUSB 号不影响归属，同型号无序列号的适配器（CH340 就不出序列号）也不撞车。1 秒轮询发现设备，每设备一个采集协程，插上即采、拔走即停，CH340/CH343/CP210x/FTDI/原生 USB-CDC 都认。

日志是双通道：serial-日期.log 全量落盘（毫秒级逐行时间戳），events-日期.log 只记事件——内置 ESP-IDF 常见故障签名（rst:0x 复位 banner、E ( 错误级、Guru Meditation、WDT、Backtrace），正则可自己扩。decode-backtrace 把 Backtrace 地址帧交给 addr2line 翻成 源文件:行号，ESP-IDF 工具链自动发现。崩溃后复盘从「肉眼扫几万行日志」变成「看事件流、点开翻译好的调用栈」。

调试固件难免要刷机。刷写安全门解决了 esptool 和常驻采集器抢口的经典事故——flash 命令经 unix socket 编排：让口 → esptool → 自动回采，板子不会被两头拉扯进 ROM 下载模式；release 还能临时把口让给外部工具，空闲 3 秒自动收回。

背后有个值得记录的实测发现：open/close 串口设备都会给板子一拍复位脉冲，连 ESP32-S3 的原生 USB-JTAG 口也一样——USB_SERIAL_JTAG 外设在硅内实现了和 CH340 一致的自动复位语义，实测 open 后 3 毫秒就出现 rst:0x15 (USB_UART_CHIP_RESET)。这是宿主侧 CDC 握手线行为，用户态绕不开。所以 serialtap 的纪律是每物理设备恰好 open 一次、长期持有，绝不周期性重开；静默看门狗默认关闭，只对保证有周期输出的设备显式开。跨读取块的行拼装和端口关闭时的 …partial 标记保证日志零丢失。

纯 Go 静态二进制：无 CGO、无 libudev，vendor 齐全可离线构建，linux-amd64/arm64 交叉编译即拷即用。
