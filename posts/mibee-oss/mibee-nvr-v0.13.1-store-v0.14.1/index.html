MiBeeNvr 发版记录：商店上线 0.13.1，仓库已到 0.14.1

October 31, 2026 MiBeeOSS MiBeeNvr, NVR, ONVIF, GB28181, 飞牛, NAS, Go, 开源 MiBee 项目实践系列 2819 字 6 分钟阅读
🔊

10 月 30 日，MiBeeNvr 的两个发布渠道在同一天各走了一步：GitHub 仓库打出 v0.14.1；飞牛（fnOS）应用商店完成了 v0.13.1 的审核并上线。九月底递入驻申请时还没回音（上一次发版记录里记过一笔），这次审核加上线压在同一天完成，速度出乎意料。只是过审的版本已经落后仓库两步——0.14.0 和 0.14.1 都还没进商店。

这篇把这两个版本放在一起讲：0.13.1 为什么存在、带着什么已知坑；0.14.1 修了什么；中间补一段 0.14.0 的要点——0.14.1 建立在它之上，而博客的进度此前只写到 0.13.0 预览版。

v0.13.1：商店形态逼出来的补丁版

v0.13.0 引入了首启校验码：初始化向导要求输入一个只打印在启动日志里的校验码，防止局域网里其他设备抢先注册管理员账户。这个安全设计在服务器部署上没毛病，但飞牛、群晖这类商店装完没有终端——提示文案指向的「启动日志」用户根本看不到，初始化卡死在第一步。v0.13.1（10 月 19 日）专为此打的补丁版，只含这一个修复：

  • 飞牛统一网关打开的向导免填校验码：请求经网关验证过 NAS 管理员身份，局域网对端伪造不了网关身份，安全模型不变；直连 IP:9090 完成初始化仍需校验码
  • 校验码同时写入数据目录的 setup-code.txt——Docker 部署就是挂载出来的数据卷，文件管理器就能看；完成初始化后自动删除，未完成初始化时每次重启自动更新
  • 提示文案按部署形态给出真实取码路径（数据卷文件 / 容器日志 docker logs）

这个坑值得记一笔的地方在于它的来历：商店部署形态反过来给项目提了需求，补丁版就是回应。

已知坑也要说清楚：v0.13.0 / v0.13.1 的 RTMP 推流接入在收到带音轨的推流时会崩溃——gortmplib v1.0.2 对未注册音轨回调的空指针缺陷，OBS / ffmpeg 一类发布端推入带音轨的流时进程 SIGSEGV，自动重连形成崩溃循环，表现为整个 NVR 反复重启、界面全黑。只影响 RTMP 接收方向且带音轨的推流（RTMP 接入默认关闭），拉流相机的录像、回放、直播都不受影响。0.14.0 已修复（gortmplib 升到 v1.0.4 并注册音轨回调）。商店里的 0.13.1 用户如果开了 RTMP 接收，建议尽早换到 0.14.x。

v0.14.0：0.14.1 的地基

10 月 24 日的功能版，信息量大，挑主干讲：

  • 远程访问：无需公网 IP 和端口映射，外网直接访问 Web 界面与蜂探 App。内置隧道以 NAT 穿透直连为主、必要时中继回落，隧道端到端加密；设备注册带 Ed25519 身份密钥，凭据轮换断裂后可自愈重注册。默认关闭，背景调研见NVR 远程访问方案综述
  • 独立录音与实时监听：网络拾音器（GB28181 语音通道 / RTSP 音频）作为独立音频设备接入，零解码直通监听、即时起播并显示真实波形，录像时间轴关联音轨，支持 WAV 导出
  • 设备管理页重构：摄像头与拾音器统一管理，分组折叠加类型筛选
  • SIP 门铃：Doorbird 类门铃/对讲接入，来铃弹窗与呼叫记录；DLNA 投放：内置 UPnP AV 媒体服务器，录像直接投到电视
  • 每周录制计划：相机级「时间段 × 星期」组合计划，支持跨夜时段，计划外不落盘
  • 相机时钟校正：内置 SNTP 服务器加一次性校时探测，避免时间漂移把检索和鉴权搞乱
  • GB/T 28181 转正为生产支持：经海康 2026 版固件真机全流程验证；全双工语音对讲；GB35114 A 级国密证书互认
  • Linux 原生包（deb / rpm，amd64/arm64 一条命令安装）；新增俄语界面

修复挑值得记的：录像段改按 IDR 边界切转，段边界不再丢帧；被重启打断的延时摄影合并窗口自动补跑；老固件 ONVIF 认证降档修复（这个问题在 0.14.1 还会再进一步）；飞牛统一网关下 WebSocket 升级兼容；更新检查只认正式版 tag，开发版构建不再误报「有可用更新」。拒播事故防复发三件套（媒体缓存强制重验证、SPA 构建指纹、孤儿录像行启动清扫）也在这个版本落地。代码贡献来自 genelee26（每周录制计划、IDR 分段、自适应写密度）和 Urdin-at（俄语界面）。

0.13.0 的存储与 I/O 深度优化此前已有实测成篇，不在这里重复。

v0.14.1：老旧设备的发现与接入

10 月 30 日的兼容修复版，重点是把两类老设备接进来。

ONVIF 老固件相机的两处卡点都出在协议细节上。认证阶梯此前会被一种老固件行为卡死：Digest 交换被拒后返回空 200 响应体，客户端停在原地不再降档，这类相机被发现后永远卡在初始化。现在阶梯正确前进到 PasswordText / Basic / 匿名档位（onvif-go v2.7.1）。端点解析重排为 GetServices 优先：老固件常把自报的 service 地址写成过期值或指向错误主机，新逻辑能解析出正确的 Media 与事件端点；SOAP 改用规范紧凑线格式，对线格式挑剔的老机型兼容性更好（onvif-go v2.7.0）。NVR 自己的 raw-SOAP 实现全部退役，统一走 onvif-go；流地址探测改为按需门控，不再对刚发现的相机发起多余探测。

GB/T 28181-2011 老设备与平台的对接修复：GB2312 编码解析、2011 版报文形态钉板、DeviceInfo 应答线格式三处修复——级联上联老上级平台不再报错（gb28181-go v0.15.0）。

另有一个数据修复：编辑相机时「录像中含音频」设置不再被意外丢弃。

新特性按默认关闭交付：

  • 飞牛四件套：Release 页同时提供原生与 Docker 两类 fpk——原生包（应用名 mibee-nvr-native，无 Docker 依赖，单个静态二进制加内嵌 Web 界面，空闲内存约 30MB，按 aarch64 / x86 择一）与 Docker 包（离线版双架构镜像内嵌、在线版 KB 级按架构拉取）。原生包与 Docker 版可并存，独立端口和数据目录；代价是不含 FFmpeg，转码类功能不可用，录制、直播、API、通知不受影响
  • RTSP 相机的 Opus 音轨可直接录制与回放；HTTP-FLV 直播携带 AAC 音频，浏览器里直播有声
  • 外发告警 webhook：事件转发到自定义 HTTP 端点，HMAC 签名，默认关闭
  • GB35114 B / C 级（逐帧视频签名与媒体加密）面向 -tags gb35114 源码构建与 gb28181-go 生态设备，官方构建不含，A 级行为与既有部署完全不变

依赖整备顺带做了一轮：onvif-go v2.7.1、gb28181-go v0.15.0、全量依赖扫描清掉安全告警；许可证补 SPDX 标识（AGPL-3.0-only）。

商店与仓库的两个节奏

两条渠道的版本差现在是实打实的两版。商店里的 0.13.1 用户拿到了校验码修复，RTMP 坑也在（默认关闭就无感）；要升到 0.14.x 还得过下一轮审核。不走商店的用户，Release 页的 fpk 四件套和 Docker 镜像现在就是 0.14.1，升级后行为与 0.14.0 一致——所有新特性默认关闭或零配置，数据库与存储结构自动迁移。

0.13.1 这次是审核与上线同天完成。商店渠道能不能保持这个速度跟上 0.14.x，下一轮审核见。
