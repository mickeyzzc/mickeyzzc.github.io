MiBeeNvr 的自适应录像与存储设计

October 18, 2026 October 18, 2026 MiBeeOSS NVR, 自适应录像, 存储, Pixgate, MiBeeVision, 压缩域, 开源 MiBee 开源项目实践系列 9017 字 19 分钟阅读
🔊

外界写 MiBeeNvr 自适应录像的文章，对机制的表述大多停在「动静感知、能省磁盘」这一层：靠什么信号判活、切换瞬间为什么不丢帧、对哪类相机会失效，很少讲透。这篇把这三层全部拆开：每个机制先白话、再上图、最后给参数，文末附完整术语表。机制描述基于 v0.13.0 文档与发布记录整理（2026-10）；版本演进的时间线见《MiBeeNvr：从 v0.1.0 到 v0.12.0》。

文中会出现与 Frigate、Blue Iris、群晖 Surveillance Station、ZoneMinder、Shinobi 的对比——目的是选型参考。选型是取舍，不是排名。

三分钟版本

监控画面 95% 以上的时间什么都没发生，但连续录制仍以全帧率、全码率往硬盘里写。自适应录制就是治这件事的：

  • 画面安静时，自动降为「延时摄影级」的稀疏写入——每 30 秒只留一个关键帧
  • 一旦检测到活动，立即恢复全帧率录制，切换瞬间零丢帧
  • 实测静态场景磁盘占用下降约 75%–98%（口径见下文）

「检测活动」用的是 P 帧大小统计：不解码、不跑 AI 模型、近零 CPU 开销。这是与其他方案差异最大的一点，下文详谈。

服务端没有「AI 判定 → 自动事件录像」这条链路——这是基于硬件定位的主动取舍，对应的解法叫 MiBeeVision，文末讲。

为什么「动静」能靠字节数看出来

这一节是后面所有机制的地基。

一段视频不是一张张等大的照片

摄像头出来的 H.264/H.265 流，画面被切成一段段 GOP（Group of Pictures）。每个 GOP 的开头是一个 I 帧（关键帧），它不依赖别的帧，自己就能解码出一张完整画面。I 帧之后跟着一串 P 帧，每个 P 帧只记录「和上一帧相比的变化部分」。

关键就在 P 帧：画面越静，P 帧越小。空无一人的走廊，P 帧可能只有几十 KB；有人走过，编码器要描述他的轮廓、动作、阴影，同一个 P 帧可能膨胀到几百 KB。安静期的 GOP 靠一两个大 I 帧撑着，其余全是碎小的 P 帧。所以「P 帧尺寸序列」本身就是一条廉价的活动曲线，不用解码任何一帧就能看到。

同一路相机，写盘量能差出多少

2K H.265 相机对着基本静态的工作室，文档实测口径：

场景每小时写盘
连续录制约 2700 MB
自适应录制（小时均值）688 MB
完全无人时段（稀疏段折算）约 81 MB

稀疏段折算的账：5.6 MB / 248 秒 ≈ 81 MB/h，对同时段全帧率的约 190 MB，约 34 倍差距。

这个招数有一个天敌

如果相机的码率被「压平」——不管有没有人，每秒吐出的字节都差不多——P 帧大小就看不出动静了。部分智能编码器相机正是如此（画面常驻静止但码率恒定）。这是压缩域判活的盲区，兜底方案是 pixgate 和分层录制，见下文。

硬件定位，以及对服务端 AI 的克制

MiBeeNvr 的设计基准是 1GB 内存的低端 ARM 板（树莓派 3B 为验证基线），进程内存 512MB 上限，单静态二进制，零外部依赖。所有功能设计都要过这道预算线。

在这个预算里，常驻一个推理模型不现实——它要么吃掉内存，要么逼你上 Coral/GPU，那就改变了「一台旧设备今天就能跑起来」这个前提。所以核心链路不依赖任何模型。AI 放在两处，都在预算线之外：

  • 浏览器端：检测在观看者的设备上跑（ONNX Runtime Web + WebGPU），多人观看多人分摊算力，服务器始终在预算内；代价是不是 7×24 无人值守的
  • 外部 Vision（MiBeeVision）：推理跑在另外的机器上（Jetson / Coral / x86），NVR 保持轻和笨，结论通过 API 回来，文末详述

这和存储的关系很直接：判活越便宜，才敢越频繁地判；敢判，才敢把「没人时段」的写入密度压下来。压缩域信号把判活成本压到近零，pixgate 经典 CV 覆盖压缩域的盲区，Vision 承接真正需要语义的那一层——三层成本从低到高，各管一段，谁都不越预算。

核心机制：压缩域判活

白话版

NVR 不解码画面，盯着每个 P 帧的字节数和一个「滚动基线」比。基线是这条流最近一段时间的典型 P 帧尺寸，用 MAD（中位数绝对偏差，一种抗抖动统计）维护。某个 P 帧突然大到基线的数倍（默认 5 倍），就认定「有活动」，立刻切回全帧率。反过来，画面连续安静超过 60 秒，就降为稀疏模式：每 30 秒只写一个关键帧，音频同时停录。

为什么值得为它设计预缓冲

「不写全量」路线最大的风险不是省不够，是活动的头几帧不在盘上。GOP 预缓冲就是为这个风险上的保险：

思路相通的先例：Blue Iris 有 pre-trigger buffer，群晖有 5–300 秒预录——区别只在来源，它们靠预先决定录什么，这里的冲刷靠缓冲里恰好有的东西。

稀疏期写什么，回放什么样

没人时段以压缩时间轴呈现：合并时，超过 2 秒的驻留样本被压到 0.1 秒帧距。一段 122 秒的稀疏段，合并后文件里只有 0.4 秒——回放时无人段快进、有人段实时，同一个文件内自动变速。数据库里的行保持墙钟时间轴，回放页的日时间轴 seek 经过 timeline_map 映射，落在产物内的正确位置。

群晖的 Smart Time Lapse 和 Blue Iris 的 Periodic 模式在做同一族事情：用更少的字节表示更长的没人时间。MiBeeNvr 把这件事放进了日常录像流，而不是一个独立功能开关。

pixgate 像素域门控

为什么需要它

压缩域有一个原理性盲区：雨点打在水面上、树叶摇、有人走过，都是真实的像素移动，都会让 P 帧变大。码率域分不清「雨」和「人」。还有一类相机更麻烦：智能编码器把码率压平了，P 帧大小干脆和动静脱钩，压缩域在这类流上直接失效。

所以需要像素域这一层：抽帧解码，用经典计算机视觉判「有没有成块、持久的前景」。这一层不新——ZoneMinder 的 zones、Shinobi 的 regions、Blue Iris 的 motion zones 都是这个思路。

整条链路，以及每一级在治什么

级治什么病
① 背景模型（EMA）「站着一动不动的人几分钟后会被误判成背景」——前景学得慢，站久了也认得出
② 自适应差分阈值夜间增益带来的全屏颗粒噪点——阈值跟着噪声中位数走，不读作前景
③ 照度阶跃抑制车灯扫过墙面、IR-cut 翻转——单次突变直接抑制，只有「灯真的留在那」才重建背景
④ 连通域最小面积区分雨和人：雨是一把小而散的短命块，人是一个大而持久的单块（中距离的人在 480p 子码流上约占网格 2–8%）
⑤ ROI 掩膜天空、水面、街道这些「永远在闪」的区域，画多边形排除掉
⑥ ghost 吸收开灯、停车、镜头水滴这类静止新前景，持续 5 分钟后并入背景、停止触发；移动的物体质心一直在漂，永远不会被吸收
⑦ 持久性迟滞连续 2 个活动样本才确认，连续 3 个安静样本才释放——单帧噪声触发不了

代价与前提，不瞒着

  • 需要 ffmpeg（和转码共用的可选依赖），缺失时门控自动关闭并告警一次，其余功能不受影响
  • 需要可达的子码流（rtsp / onvif / gb28181 相机；srt / rtmp 推流相机不适用）
  • 开销：480p 级子码流 1fps 采样，每相机约 10–20ms/帧软件解码，低于 2% 单核
  • 云台转动期间门控自动失明，防转动误触发，转完后重建背景模型
  • 判定结果以 pixgate.activity 事件上事件总线（带 area_pct / 质心 / flood / ghost 字段），UI 和自动化可直接订阅；Prometheus 有 nvr_pixgate_samples_total / nvr_pixgate_triggers_total 遥测

它和 video_exit: false 是设计搭档：把 video_exit 设为 false 后，视频尖峰一律不再退出稀疏模式——雨再大也留在延时里，只有 pixgate、音频、相机事件、外部 API 这些「确凿信号」才恢复全帧率。适合「没人就绝不升帧率」的场景，比如楼道和门口。

分层录制：给压缩域失效的相机兜底

对码率被压平的相机，单层自适应可能永远不降级。分层录制的办法是两条腿走路：

  • 子码流 24/7 连续录成 layer=1 基线——480p 级、60 秒一段、低码率，永不漏拍
  • 主码流保持 adaptive 密度——近空场景配 video_exit: false + pixgate，主码流只录事件，全高画质

子层段和主流录像同一目录树，sub_ 文件名前缀，merge_status='sublayer' 天生终态、永不参与合并，遵循普通保留期清理。录像列表 API 用 ?layer=1 / ?layer=0 切换可见性。

Blue Iris 的「子码流连续 + 主流触发」（direct-to-disc BVR，回放时子上采样）和群晖的「高级连续录像」是同一族思路——Blue Iris 用户实测过 1 小时 3.90GB → 120MB。差异在触发来源：它们靠配好的触发器，MiBeeNvr 靠压缩域/pixgate 自动判，外加子层段可以直接喂外部 AI。

噪声工程三件套

这三项都是被真实用户案例逼出来的：

配置治什么
noise_floor_bytes夜间编码器把码率压到几百字节/帧时，相对倍数指标被抖动点燃——「日志里说活动，回放画面没动」。设一个绝对字节下限，低于它的 P 帧永远不算尖峰
auto_noise_floor（默认开）从延时驻留帧自校准：稀疏模式里的帧按构造就是静止的，其 p99 尺寸 ×1.25 就是这台相机自己的噪声天花板。只对码率饥饿流生效，健康码率流行为不变
video_exit: false常驻延时：视频尖峰一律不退出稀疏，只有 pixgate / 音频 / 相机事件 / 外部 API 才升帧率。治雨天、水面、树叶

显式地板和自校准地板取较大者生效——显式值给硬下限，自校准在饥饿流上再抬高。

活动分、热力时间轴、按内容清理

每段录像带一个活动分

压缩域分析器给每段录像打活动分（motion score），录像库直接可用：按「有活动 / 安静 / 场景切换」过滤、设最低活动分、详情页一键把时间轴按活动分上色（绿=安静 → 红=活跃）。

v0.13 起打分器有两项防失真设计：

  • 绝对码率置信度：纯相对指标在码率饥饿流上会造假高分。置信度按段内中位 P 帧字节绝对锚定（约 400B 以下归 0，约 1200B 以上全信，中间线性爬升），榜单和清理按「活动分 × 置信度」解读
  • 像素优先路由：开了 pixgate 的相机，若像素域前景序列对某段覆盖足够，活动分改由像素域合成（0.8 × 前景占空比 + 0.2 × 面积幅度），对夜增益噪声和编码器刷新帧免疫

磁盘满了，先删最没用的

水位默认 85%。到达水位时，优先删除活动分最低的安静片段——同样的磁盘，留下更多「有事件」的录像。Frigate 的 retain 阶梯是「按类型分级留」，这里是「同类型内按内容排删除顺序」，同一个想法的两个方向。

eval-replay：调参不碰生产

判定逻辑是「P 帧尺寸序列 + 配置」的纯函数，所以一份已完成的录像就能回答「换这组参数，门控会怎么做」——不用接相机、不用解码：

MiBeeVision：AI 放在它有硬件的地方

架构与数据流

NVR 监听段完成事件，检查 Vision 心跳健康，在段落盘后、合并前的窗口期主动把段推给 Vision（push_mode: notify 通知消费者拉取，或 upload 直接推字节）。

为什么是主动推：早期 Vision 是定时来 NVR 拉录像的，78% 的请求撞上 404——段文件在它来之前已经被合并或清理掉了。改成推送后，视频数据在合并进程动手之前就已经到了 Vision 手里。心跳超时（默认 60s）未恢复，NVR 暂停推送；恢复后错过的段自动补偿重推——补偿有界：2 小时窗口、最多 500 段、200ms pacing，防止恢复 burst 打爆消费端或磁盘。

vision.instances 支持同时接多个消费端，各自独立的地址、身份、启停；相机通过 vision_targets 选择接哪些实例（空 = 全部）。不同实例可以挂不同模型，按场景分流：

低清段喂 AI：解码成本砍到 1/4–1/16

两条低清通道（v0.12.0 落地，issue #512–#537）：子流分析层（sub_layer_cameras）按需拉子码流录成独立低清分析段——不进录像库、不参与合并、消费成功即删；tiered 子层段（tiered_cameras）直接复用正式录像库的 layer=1 行，主流段让位不再推送。4K 主码流录像完全不受影响。对消费端来说，判一段 480p 的视频比判 4K 便宜一个数量级。

结论怎么回来

两条路，都通向同一个动作——把主流拉回全帧率：

  1. Vision 把 AI 事件写回 NVR（录像列表 AI 标记 + 事件），回放时直接看到
  2. 任何外部系统（包括 Vision 自己、家庭自动化、脚本）调外部触发 API：

MiBeeVision Lite v0.1.0

2026-10-18 发布，几个事实：

  • 定位：MiBeeNvr 的 AI 检测组件——对 NVR 录制的视频做目标检测与跟踪，按区域 / 越界 / 徘徊规则生成事件，结果回写 NVR
  • 形态：Linux x86_64 / aarch64 单二进制，内置 YOLOv8n 模型 + ONNX Runtime 1.17.1（CPU），Lite 版单摄像头、CPU 推理
  • 部署：默认 9092 端口带 Web UI，填 NVR 地址、粘贴 mbv_ 开头的 API Key、选摄像头、画规则区域即用
  • 鉴权：必须用 API Key（mbv_ 前缀），网页会话 token（mbs_）回写会 401
  • 传输：Vision 与 NVR 不同机时 [transport].type = http_download；local_file 模式要求共享录像存储目录
  • 许可：闭源专有软件，版权归 MiBee Studio，随 MiBeeNVR 免费分发；内置 YOLOv8n 为 Ultralytics AGPL-3.0
  • 版本线：独立于 MiBeeNVR 的 vX.Y.Z，各自演进

Lite 是这条路的第一个脚印：单摄像头、CPU。它不改变 NVR 的任何预算——跑在另外的机器上，NVR 至多付出一点推送带宽。

每家一段话：力气花在哪

  • Frigate：把服务器侧 AI 事件录像做到了同类最强——对象检测驱动保留策略、review 界面、Home Assistant 集成深度是它的护城河。它要 Coral/GPU 和 Docker，这是路线的代价，不是缺陷。在「AI 判定后自动存事件」这件事上，MiBeeNvr 明确不如它
  • Blue Iris：把「子码流连续 + 主流触发」做成了成熟功能（direct-to-disc BVR + pre-trigger buffer），Windows 上开箱即用，触发器生态丰富。它的省存储实测数据（1 小时 3.90GB → 120MB）是有说服力的民间口径
  • 群晖 Surveillance Station：NAS 原生的监控中枢——高级连续录像、Dual Recording、Smart Time Lapse、边缘录像，加上套件授权模式。已经有群晖的话，它是摩擦最小的路
  • ZoneMinder：最老牌的开源 NVR 之一，事件体系成熟，zone 类型（Active/Inclusive/Exclusive/Preclusive/Inactive）是做 ROI 掩膜时的参考。LAMP 栈在低配设备上压力大，这是它路线的代价
  • Shinobi：Node.js 技术栈，事件驱动录像（Trigger Record + Buffer Time）配置灵活，多租户存储配额是特色。纯事件录像在「连续性」上是另一条路线

摄像机侧智能编码的角色

H.265+（海康）、Smart H.265+（大华）、Ultra H.265（宇视）、Zipstream（Axis）、WiseStream（Hanwha）用背景建模、动态 GOP、ROI 编码把基线码率砍下来，厂商宣称同画质下比标准 H.265 再省 20–40%。它和 NVR 侧的门控是互补关系，不是替代关系。两个坑（详见《从 H.265 到 AV1/AVS》）：智能编码是私有扩展而非标准，跨品牌通常退化为标准 H.265，容量规划别把它的节省算进去；码率被压平的智能编码会破坏一切压缩域判活——任何靠码率变化判动静的方案都受影响，这类相机直接上分层录制 + pixgate。

边界清单

#边界后果缓解
1稀疏期回放是压缩时间轴无人时段的缓慢变化看不清；产物文件时长远小于墙钟，可能被误认为损坏文档明示；与「子码流实时帧率连续」（BI/群晖路线）是本质取舍
2无服务端 AI 链路不能像 Frigate 那样无人值守地回答「昨天几只猫来过」MiBeeVision + 外部触发 API
3压缩域对码率恒定相机失效可能永不降级tiered + pixgate 组合
4纯推流相机（RTMP/SRT）用不了分层与 pixgate只有单层 adaptive视频尖峰+音频+外部触发仍可用
5MJPEG 无压缩域信号；AAC/Opus 无音频触发这两类相机自适应退化MJPEG 有暗帧过滤+AVI 容器优化；音频需 G.711
6GOP 预缓冲常驻 32MB/相机路数极多时内存预算要重算1–64MB 可调，必须容纳一个完整 GOP
7单人项目长期维护风险是选型时的真实变量文档与工程深度见项目 docs

术语表

术语白话
I 帧 / 关键帧不依赖其他帧、能独立解码出完整画面的一种帧，GOP 的开头
P 帧只记录「和上一帧的差异」的帧，画面越静它越小
GOP两个 I 帧之间的一串帧，监控常见 1–30 秒
码率每秒多少字节（kbps/Mbps），码率 × 时间 ≈ 磁盘占用
VBR / CBR变码率/恒码率。VBR 静时省、动时费；CBR 恒定可预测
压缩域不解码，直接看帧的字节数、帧类型等「信封上的信息」
像素域解码成画面后逐像素比对（背景差分、连通域等）
语义域用 AI 模型判断「这是一个人/一只猫」，最贵也最准
预缓冲内存里常驻最近一段视频，触发时补写，保证事件头不丢
子码流相机同时输出的第二路低分辨率低码率视频
MAD中位数绝对偏差，一种抗个别极值抖动的统计方法
EMA指数移动平均，「慢慢学」的背景模型
连通域把相邻的前景像素连成块，用块的面积和寿命区分雨和人
ROI感兴趣区域，掩膜则相反——排除掉的区域
ghost静止的新前景（停的车、镜头水滴）被背景吸收的过程
迟滞确认要连续 N 个活动样本、释放要连续 M 个安静样本，防抖动
timeline_map墙钟时间与变速产物内偏移的对照表，回放 seek 靠它
