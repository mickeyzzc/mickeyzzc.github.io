mibee-eye-notebook 的多模态 AI：九个本地模型怎么分工配合，以及和市面项目的对比

October 3, 2026 October 3, 2026 MiBeeOSS 多模态, 语音交互, 目标检测, VLM, Rust, ONNX MiBee 开源项目实践系列 6009 字 13 分钟阅读
🔊

前面两篇调研把"看、听、说、接话、干活"的全模态交互从模型和管线两个角度捋了一遍。这篇落到实践：mibee-eye-notebook（下文简称 notebook）正在尝试的，就是把调研里那套多模型配合的思路在一个 Rust 项目里跑通。先拆解它自己怎么组合模型，再对照市面上一批同方向的开源项目，看看大家殊途同归的地方和各自不同的取舍。

notebook 是什么

一句话：跑在笔记本（或任何 Linux 机器）上的本地采集代理。它采集本机摄像头和麦克风，编码成 H.264/AAC，通过 RTSP / RTMP / ONVIF / GB28181 四种协议对外提供流媒体服务，给 MiBee NVR 当一台"软件摄像头"。这是 MiBee Eye 家族的一员，和 mibee-eye-rs、mibee-eye-go、mibee-eye-webui 共享前端与 API 规范。

工程底子决定上层建筑，先交代三个约束，后面所有模型选型都是从这里推出来的：

  • Rust 单二进制，六个 crate（protocols / streaming / web / security / capture / observability），约 6 万行，运行时不依赖 ffmpeg、不依赖 Python——视频编码用 OpenH264 进程内完成，AI 推理全部走 ONNX Runtime、llama.cpp、sherpa-onnx 三条原生路线
  • 资源预算：空闲 CPU <5%、内存 <200MB、并发流 ≤16（信号量控制）。这个预算直接排除了"常驻一个大模型听所有声音"的方案
  • 全离线优先：所有模型文件落在本机 models/ 目录，断网也能用；引擎全部"故障开放"（fail-open）——模型缺失或 feature 未编译，只把能力位从 API 里摘掉，服务本身照常跑

九个引擎各管一层

notebook 的端侧智能目前有九个模型引擎，按"常开程度"分四层：

层引擎模型常开干什么
感知唤醒词 KWSsherpa-onnx zipformer是听"小蜜蜂"三个字
感知语音活动 VADSilero VAD（2.3MB）是有没有人说话
感知声音事件YAMNet（16MB）是婴儿哭、狗叫、玻璃碎
感知视觉检测NanoDet-m + ByteTrack 跟踪是画面里有什么、进没进区域
理解转写paraformer（zh / 三语 zh-yue-en，234MB）唤醒后中文转文字
理解声纹CAM++（27MB）唤醒后是不是注册用户、说话归属
决策应答分诊Laya（322M，int8 924MB）唤醒后这句话要不要过 LLM
生成对话Qwen3 GGUF（llama.cpp）决策通过后回复
生成画面描述Qwen3-VL-2B + mmproj（llama.cpp mtmd）告警触发后一句话说清告警画面

另外还有三个外围件：PP-OCR v4/v5（按 API 调用，不在常开链路）、MeloTTS（读出 LLM 回复）、pyannote 分离 + ct-transformer 标点（meeting 模式，转写会议并区分说话人）。模型全加起来约 1.7GB，全部 Apache-2.0 或 MIT 许可。

这个分层对应一个简单原则：便宜的模型常开，贵的模型按事件触发。Silero VAD 单帧推理不到 1ms、NanoDet-m 是轻量检测器，这两个 7×24 跑；Qwen3 和 Qwen3-VL 是这里最贵的算力，只在决策引擎放行或告警上升沿出现时才加载调用。

语音交互闭环走读

语音链路是模型配合最密的一条，从麦克风到扬声器一共六步：

    B --> C["paraformer<br/>离线转写"]
    C --> D["Laya 分诊<br/>回答 / 设备 / 忽略"]
    D --> E["Qwen3<br/>LLM 回复"]
    E --> F["MeloTTS<br/>语音播报"]

逐步说清楚每一步在判什么、错了会怎样。

唤醒 + 声纹门控（谁在说）。唤醒词"小蜜蜂"跑在 sherpa-onnx 的流式 zipformer 上；唤醒命中后不是立刻开窗录音，而是先用 CAM++ 对唤醒词本身那句话做声纹验证——取最近 verify_window_secs 的音频提嵌入，和注册档案比对，分数过阈才开窗，陌生人只记一条日志。这是上一篇调研里"个性化 VAD"的等价实现：只响应注册用户。两个配套设计：注册流程复用 KWS 路径（对着设备喊 N 次唤醒词完成注册，不用单独的注册界面）；每次交互的转写归属到最佳匹配的注册人（record tagging）。源码注释里有一句诚实的定性：这是便利性过滤，不是安全边界——短语音的声纹本来就宽松，家人声线相近也可能通过。这句话值得写进任何用声纹做产品的人的文档里。

转写（说了什么）。paraformer 离线转写唤醒后采集的音频段，中文为主，可切三语模型（普通话/粤语/英语）——同一个引擎换一对模型文件的事。转写结果以 voice_transcript SSE 推给前端。

分诊（该不该接）。这是整条链路里我最有兴趣的一步。Laya 是一个 322M 参数的非自回归分类模型（mmBERT 结构，int8 后 924MB），对每条转写做三分类：answer（值得回）/ device（是设备指令）/ ignore（当没听见）。低于置信度阈值（默认 0.35）只上报 voice_decision 事件、不行动——决策引擎自己也是 fail-open 的，模型缺失时调用方保持原行为（全部转给 LLM）。它的位置在 LLM 前面：一条"嗯今天天气不错"的闲聊，在 322M 分类器这里就被拦下，不用惊动 4-bit 量化的 Qwen3。这正是上一篇调研里"两层门控"模式的落地——轻量分类器先挡一道，省 LLM 调用也省延迟。选非自回归模型做分诊还有一个理由：单次前向就是结果，没有 token 循环，延迟可预期。

回复与播报。过了分诊的话进 Qwen3（llama.cpp，贪心解码，/no_think 关思考模式），回复经 MeloTTS 变成语音读出来，chat_reply SSE 同步给前端。TTS 是全项目唯一走子进程的引擎——sherpa-onnx 的 offline-tts CLI——原因是它链接了 GPL 的 espeak-ng，用进程边界把 GPL 代码隔离在 Apache-2.0 主二进制之外。

另外还有一个 follow-up 窗口：一次唤醒后的若干秒内再说话不需要重新唤醒（转写事件的 follow_up 标志位），这就是"一次唤醒、会话内免唤醒"的会话窗口实现。

告警链路走读

视觉和听觉的告警是另一条多模型配合的链路，方向相反：不是"人触发模型"，而是"模型触发人"。

mermaid
flowchart TD
    A["摄像头视频流"] --> B["NanoDet 检测<br/>+ ByteTrack 跟踪"]
    B --> C["上升沿 + 冷却<br/>告警判定"]
    C --> D["alarm SSE<br/>+ GB28181 NOTIFY"]
    C --> E["Qwen3-VL<br/>异步画面描述"]
    style A fill:#FF9800,color:#fff
    style B fill:#2196F3,color:#fff
    style C fill:#9C27B0,color:#fff
    style D fill:#4CAF50,color:#fff
    style E fill:#4CAF50,color:#fff

检测与判定。NanoDet-m 对采集帧做目标检测，ByteTrack 子集做跟踪（骑在检测框上，零额外推理），用户在界面上画入侵区域和越线，zone_event 由跟踪轨迹和区域的几何关系产生。告警的触发是上升沿 + 冷却：目标从无到有触发一次，冷却期内不再重复——没有上升沿逻辑的话，一个坐在沙发里的人会让告警每秒响一次。

描述不拖累告警。告警画面会异步交给 Qwen3-VL（llama.cpp 的 mtmd 多模态路径，2B Q4_K_M + mmproj 投影器）生成一句中文描述（“有人推门进入客厅"级别），走 alarm_description SSE。这里的调度设计值得记下：单飞（in-flight 去重，同一时间最多一个描述在跑）+ 描述间隔下限 120 秒——检测框抖动不会堆出一排推理任务；而且描述绝不延迟告警本身，alarm 先发，描述后到。VLM 是整条链路最慢的环节（CPU 上秒级），把它放在告警后面的异步分支，是"贵模型不能挡路"的又一次应用。

声音告警。YAMNet 对麦克风做 0.96 秒滚动窗口的音频事件分类（婴儿哭声、狗叫、警报声一类），投票平滑（连续 3 票才算数）压误检，逐类冷却压重复，被接受的边沿发 source: "audio" 的告警。Silero VAD 的语音存在标志同时供给语音环路——有人在说话就不该把人声判成异常事件，两个引擎共享同一条 16kHz 监听流，这是音频侧的"一份数据多个消费者”。

meeting 模式：谁在说的会议版

开着 [meeting] 配置时，notebook 变成一台会议记录器：pyannote 分离模型（1.5MB，MIT）切出"谁在什么时候说话"，CAM++ 对每段提嵌入做聚类归并到人，paraformer 逐段转写，ct-transformer 补标点。四个小模型串成一条"分离 → 归属 → 转写 → 整理"的流水线。models/README 里有一条实测记录：默认阈值 0.5 下，零样本聚类把 4 个说话人的样本聚成了 5 类——聚类阈值要按房间调。这种把已知缺陷写进文档的做法，比"支持会议纪要"四个字可信得多。

市面上还有谁在这么干

多模型配合不是 notebook 独有的路线。2026 年 10 月这批活跃的开源项目，几乎都在做同一件事——用多个单模态模型拼出多模态能力。按场景分五类：

项目stars拼了哪些模型端/云许可
Frigate36.3k目标检测（Coral/GPU）+ VLM 描述（qwen3-vl 经 Ollama/llama.cpp）本地MIT
xiaozhi-esp32（+ server）30.4k + 10.7kESP-SR 唤醒 + AEC + ASR→LLM→TTS 或 Qwen realtime 端到端 + 声纹端 + 服务器MIT
Screenpipe21.8k屏幕无障碍树/OCR + Whisper/Deepgram 转写 + 任意 LLM 插件本地优先源可得商业许可
Open-LLM-VTuber14.0ksherpa-onnx/FunASR/Faster-Whisper + 任意 LLM + GPT-SoVITS/CosyVoice + Live2D本地MIT（资产隔离）

挑几个和 notebook 血缘最近的展开：

Frigate（36.3k★，NVR 领域事实标准）的多模态配合和 notebook 的告警链路几乎是同构的：运动检测 → 目标检测 → 快照 → VLM 只看事件帧。它的 GenAI 层 2025 年之后接入了 Ollama、llama.cpp、Gemini、OpenAI 等 provider，本地默认示例就是 qwen3-vl:4b——和 notebook 用 Qwen3-VL 描述告警画面是同一个模型家族、同一个触发模式。区别在 Frigate 的 VLM 永远不见原始视频流，只看事件快照，门控比 notebook 更保守。

xiaozhi-esp32（30.4k★，中文创客圈最大的 AI 硬件项目）是端云分工的代表：ESP32 端只做唤醒词（ESP-SR）、回声消除和 Opus 编码，ASR/LLM/TTS 全在服务器（官方免费给个人用户的 Qwen realtime，或自建 xiaozhi-esp32-server）。138 种板型适配、设备端 MCP 控制扬声器/LED/舵机。它的"经典管线 + 端到端语音模型"双轨并存，正好是前两篇调研里级联和 S2S 两条路线在一个产品里的共存。notebook 走的是它的反面——把整条链路塞回端侧——两种取舍对应不同的供电和网络假设。

Home Assistant 的 Wyoming 生态最值得学的是降级阶梯：文档明确写了三档——弱硬件跑 speech-to-phrase（固定短语识别，几百条命令全端上）、N100 级跑完整本地 Whisper、少数语种才落云。配套的 Voice PE 硬件（$69）用 ESP32-S3 跑唤醒词 + XMOS XU316 芯片做 AEC/降噪/AGC——专用 DSP 处理音频前端、通用芯片跑协议，这个分工和车舱四音区的思路一致。notebook 目前只有"全本地一档 + 引擎各自 fail-open"，还没有这种显式的档位设计，这是差距。

Screenpipe（21.8k★）证明了"持续记录 + 事后检索"这条路的商业可行性，也演示了许可作为架构决策：从 MIT 转成源可得商业许可，同时保持本地优先。它的技术演化方向值得注意——从持续录屏转向事件驱动捕获（无障碍树优先、OCR 兜底），本质上就是"便宜的门控先跑、贵的模型后跑"，和 notebook 的分层是同一个原则在不同传感域的应用。

Open-LLM-VTuber（14.0k★）和 notebook 技术栈重合度最高（sherpa-onnx + FunASR + CosyVoice 一系），它的许可是 MIT 代码 + Live2D 示例资产单独授权——和 notebook 把 GPL TTS 隔离在子进程里是同一种"哪些部分开放"的主动设计。

还有两个反例同样有信息量：OpenRecall（2.9k★）13 个月没有更新，说明"复刻 Rewind"这个方向光有想法没有工程纪律撑不住；Brilliant Labs 的 Noa 曾经是开源 AI 眼镜的标杆（Whisper + GPT-4o + Moondream 多代理云栈），2026 年 org 已清空公开仓库——多模态产品死掉，多半不是模型问题。

殊途同归的四个模式

把这批项目和 notebook 放在一起看，健康的多模型配合项目收敛出了四个共同模式：

  1. 门控级联，不是单模型。所有活跃项目都是便宜感知常开（唤醒词、VAD、运动检测、OCR）+ 贵模型按事件触发（LLM、VLM）。没有一个把大模型常开跑。这不是模型能力问题，是功耗、延迟和误触发三笔账算下来的必然结果——上一篇调研推导的结论，在几十个项目里被独立验证
  2. 降级阶梯是标配。Wyoming 三档、Willow 的 400 条端上命令、xiaozhi 的经典管线与端到端双轨、Screenpipe 的本地 Whisper 与 Deepgram 可选——能力分档、按硬件选择，比"全有或全无"的部署现实得多
  3. 许可隔离是显式的架构层。GPL TTS 关进子进程（notebook）、Live2D 资产单独授权（VTuber）、piper 分裂成 GPL 和 MIT 两条线、Screenpipe 整体转商业许可——多模型项目拼的组件许可五花八门，“哪部分开放"必须当成设计决策提前做
  4. 工具层在向 MCP 收敛。xiaozhi 的设备端 + 云端 MCP、Screenpipe 的 MCP server、Omi 的 MCP——多模态感知之后的"执行"环节，正在统一到同一个协议上

notebook 在这个坐标系里的差异化位置：Rust 单二进制 + 全本地 + 无 Python 依赖。生态里绝大多数项目是 Python 或 TypeScript 拼 services（faster-whisper + Ollama + Piper 这个配方已经被无数个一位数 star 的项目复制），运行时形态是"一屋子进程”。notebook 把九个模型装进一个进程（外加一个被迫隔离的 TTS 子进程），代价是每个引擎都要找 Rust 原生路线（ORT / llama.cpp / sherpa-onnx），收益是部署面：一个二进制 + 一目录模型文件，systemd 拉起就能跑。

留着没做和下一步

对照前两篇调研的完整图景，notebook 的多模态还有几块明确的空白：转写之后的应答决策目前只有 Laya 一个单点分类器，没有状态机（会话内的"沉默/附和/回应"三分类还没实现，follow-up 窗口是无条件续听的）；VLM 只在告警后看单帧，没有连续视频流的理解；TTS 是离线合成的整句播报，没有流式首包优化，语音对话的端到端延迟还到不了调研里 800ms 的产品线。

这些空白基本就是接下来几个版本的工作清单。做不做、先做哪个，判断标准和这篇的分层原则一致：哪个空白挡住了"便宜门控 + 贵模型按需触发"的完整闭环，就先补哪个。
