接管 onvif-go：真机修复、依赖清零与服务门面重构

August 27, 2026 August 27, 2026 MiBeeOSS Go, ONVIF, 监控摄像头, 开源 MiBee 开源项目实践系列 4135 字 9 分钟阅读
🔊

MiBeeNvr 接入相机走 ONVIF 协议，底层用的就是这个库。ONVIF 是 IP 视频监控设备的事实标准：设备发现、媒体 Profile、云台控制、事件订阅，都是一套 SOAP over HTTP 的服务约定；不同品牌只要声称兼容 ONVIF，理论上就能用同一套调用对接。

onvif-go 是这条链路在 Go 语言里的实现。这不是我们从零写的项目：它的上游是 0x524a/onvif-go——那位作者把它重写成了现代形态的 client 加虚拟相机 server（git 历史里还能追溯到社区更早的一批 Go ONVIF 尝试）。但进入 2026 年之后上游停了：最后一次 PR 合并停在 1 月中旬，此前 v1.0 到 v1.1.3 集中发布的节奏没有再继续，仓库里三条 Improve Test Coverage 的 issue 从 2025 年 11 月开着至今无人认领。同一时期，我们在自家相机池里踩到了两个只有改库才能解决的问题。

2026 年 7 月 fork 接管，先把两个真机问题修掉；8 月把工程底座整个翻新了一遍并发布了 v1.2.0。下文按三部分记录：这个库的能力面、两处真机修复的来龙去脉、这次接管的工程账目。

上游为什么停在原地

先摆事实。上游的时间线大致是：

  • 2025 年 11 月：v1.0.0 到 v1.1.3 一周内连发，设备、媒体、PTZ、成像、发现这些核心服务成形；
  • 2025 年 12 月：补齐 Event 与 DeviceIO 服务，Media WSDL 全量操作做完；
  • 2026 年 1 月中旬：最后一次合并，此后主分支再无实质变化。

从纯工具项目的角度看，“功能做完了所以不更新了"可以理解——协议稳定，代码不会腐烂得那么快。但我们的处境不一样：MiBeeNvr 对它近乎全量依赖，发现相机、读配置、取流地址、云台、事件全部经这个库出去。库停在原地，等于 NVR 的整个相机接入层停在原地；遇到 bug 只有两条路可走，绕过去，或者自己修。

后续的两个真机问题都印证了一件事：绕不过去。

这个库能做什么

ONVIF 把设备能力拆成一组 SOAP 服务，这个库对应地提供 client 端的七个服务门面（facade）：

门面入口典型操作
Deviceclient.Device()设备信息、能力集、系统时间、重启，网络/WiFi/证书/存储配置
Mediaclient.Media()Profile、取流 URI、抓图 URI、视频编码、音频、OSD 叠加
PTZclient.PTZ()连续/绝对/相对转动、停止、预置位、状态查询
Imagingclient.Imaging()成像参数读写、聚焦驱动
Eventsclient.Events()PullPoint 订阅与事件拉取
DeviceIOclient.DeviceIO()继电器输出、视频输出配置
Securityclient.Security()设备侧用户管理

围绕 client 本体，还有四个辅助件值得单独说：

  • discovery 包：WS-Discovery 组播探测加定向探测。discovery.Discover(ctx, timeout) 一次调用返回网内可发现的设备列表；
  • server 包：虚拟 ONVIF 相机，实现了 Device/Media/PTZ/Imaging 四个服务。自动化测试不必插真机即可覆盖请求—响应语义，CI 里尤其有用；
  • testing 包：mock server、golden 文件、capture 回放。testdata 下的 captures 目录收着各品牌真机的 SOAP 抓包，作为回归素材——修 bug 不是对着协议文档猜，而是对着真实报文验证；
  • cmd/：discover、onvif-quick、onvif-diagnostics、onvif-server 四个命令行小工具。

调用方只面对 Client 与门面两层：Client 只管连接、凭据、时钟偏移这类底层事务，具体操作挂在对应服务的门面上，最终收口到 internal/soap 完成 SOAP 封装与 WS-Security 签名。一个对嵌入式部署有分量的细节：go.mod 里没有一个 require 块，整个库只依赖标准库。

兼容面上，这个库在 Hikvision、Axis、Dahua、Bosch、Amcrest、HiSilicon 方案 OEM 机以及 ESP32 上的最小 ONVIF 实现上都跑通过——其中一部分来自我们自己的测试相机池。

两处真机修复

这两个问题都在接管的第一周修掉，也是"必须接管"的直接证据。

时钟偏移打垮认证

现象：部分部署点上，Hikvision 相机对所有带鉴权的请求统一返回 sender not authorized。凭据没错，digest 算法也没错。

根因在 WS-Security UsernameToken digest 的时间窗上。Password_Digest 由 nonce、Created 时间戳与口令共同算出，接收方会校验 Created 是否落在自己的回放窗口内——Hikvision 的窗口是 ±5 分钟。NVR 主机跟着 NTP 走，相机却不一定接 NTP，两边时钟一发散，Created 就飘出窗口，digest 整批作废。这类问题只在时钟不一致的现场出现：实验室里几台相机时间齐刷刷的，怎么测都对。

修法是给 Client 和底层 SOAP 层各加了 SetClockSkew：先用 GetSystemDateAndTime 量出设备时间与本地时间的偏移，签名时把 Created 改成按设备时钟算出的时刻——回放窗口认谁的钟，签名就用谁的钟。默认偏移为零，行为与从前一致，不设置就不生效。

排查路径本身不复杂，门槛在于想到往时钟上查：报错文案指向鉴权失败，很自然会先核对凭据和加密方式。真正的判断依据是把本地时间与相机的系统时间放在一起看一次偏差。

能力清单里的旧地址

背景：相机因 DHCP 重新分配或 AP 漫游换了 IP，这是 NVR 自愈逻辑要处理的常态场景之一。但 GetCapabilities 返回的 XAddrs 里，media_service 等子服务的地址仍然是相机记住的旧 IP——设备人在新地址上应答，能力清单里却还写着一条已经失效的旧地址。

上一版代码对此有一个 fixLocalhostURL，专门处理相机在能力应答里报出 loopback 地址（127.0.0.1、localhost、::1）的固件怪癖，对"旧但可路由"的地址无能为力。结果就是 GetProfiles 打向旧地址，no route to host，录像启动被卡住。

修法是 fixServiceURL：任何 capability XAddr 的 host 与 device_service endpoint 的 host 不一致，就重写为我们实际抵达相机所用的地址——这个地址按定义是最新的；各子服务自身的端口保持不变。原先的 loopback 修正成为它的子集。

mermaid
flowchart TD
    CAP["初始化获取<br/>能力 XAddrs"] --> CMP{"host 与当前<br/>可达地址一致?"}
    CMP -- "一致" --> USE["原样使用"]
    CMP -- "不一致" --> RWR["改写为可达 IP<br/>保留服务端口"]
    RWR --> GO["各子服务 endpoint<br/>指向正确新址"]

    classDef base fill:#E3F2FD,stroke:#1565C0,color:#1565C0
    classDef q fill:#FFF3E0,stroke:#E65100,color:#BF360C

    class USE,GO ok

这处修复打通了 NVR 的 IP 重新发现链路：rediscovery 更新 device_service 地址之后，Initialize 能产出指向新地址的各服务 endpoint，自愈流程不再卡在"找到了新 IP 却用不了"这一步。

以上是使用层面看得见的变化。接下来是这次接管的工程账目，写给评估迁移成本的人和打算读源码的人。

工程账目

身份与工具链重置

  • module path 从 github.com/0x524a/onvif-go 改为 github.com/mickeyzzc/onvif-go，随 v1.2.0 生效；
  • Go 1.26 起，.go-version 固定工具链版本；
  • 六个 CI workflow 合并为 ci.yml（lint + race 测试 + build）与 release.yml（跨平台 CLI 产物）两个，删掉 codecov、sonar 及若干过期 workflow 的死配置；
  • golangci-lint 配置重建为与 MiBeeNvr 同一套 v2 规则集，Makefile 重排；
  • LICENSE 以续行方式保留原作者版权声明，整体仍为 MIT；README 重写为 continuation 说明。

这段没什么技术含量，但它决定一个 fork 是私有补丁堆还是可以正常协作的项目——别人 go get 到的是一个完整身份，而不是一座孤岛。

先把基线跑绿

盘点时发现有六个测试失败是上游遗留的，逐个处理后可以分成两类。一类是真 bug：StorageConfigurationData.StorageURI 字段缺 xml 标签，字段名永远不会匹配到设备实际发出的 StorageUri 元素，存储配置的 URI 解析出来恒空——显式补上标签修复。另一类是测试自身的问题：有用 SOAP 1.1 信封喂只认 1.2 的 Envelope 类型的，有断言还停留在 loopback 修正之前的语义上的，还有 Windows 回环网卡命名导致的探测失败。

从此 make test 全绿。此后的一切重构，都是在出了错会立刻报警的地基上做的——这层保障没铺好之前就动大规模改动，等于蒙着眼睛拆承重墙。

第三方依赖清零

上游曾顺手引入一条 RTSP 工具链：rtspeek 只被那个两千多行的交互式 CLI onvif-cli 消费。这次的取舍是把整条砍掉——CLI 删除，连同十几个互相重叠或已经过期的 example、误提交进仓库的一个 Linux ELF、一次性脚本和重复的抓包目录。go mod tidy 之后，go.mod 里一个 require 都不剩。

对一个要嵌进固件、要在 NVR 里长期跑的库来说，依赖树就是审计成本。现在这项成本是零。

API 收拢为服务门面（BREAKING）

改动最大的部分。上游形态是几百个操作方法平铺在 Client 类型上，Client 同时背连接管理、SOAP、下载传输三摊事。这次收拢成上文那张架构图的两层结构：

// 从前的平铺方法
client.GetDeviceInformation(ctx)
client.GetProfiles(ctx)

// 现在：按服务域组织
client.Device().GetDeviceInformation(ctx)
client.Media().GetProfiles(ctx)
client.PTZ().ContinuousMove(ctx, token, speed, timeout)

Client 只留下连接、凭据、时钟偏移与下载四类底层事务；七个门面无状态、按需构造，跨 goroutine 共享同一个 Client 是安全的。配套动作：三千九百行的 media.go 按主题拆成 profiles/stream/encoder/audio/osd 五个文件；一百三十个原来藏在方法体内的局部类型提升为包级类型——零重名冲突，测试、server 包和外部工具从此可以直接引用这些 ONVIF 数据结构。

格式化（gofumpt + goimports 全树）单独成一个提交保证后续 diff 可读，golangci-lint 报告清零。

v1.1.x 平铺方法v1.2.0 门面调用

client.GetProfiles(ctx) / client.GetStreamURI(...)client.Media().GetProfiles(ctx) / client.Media().GetStreamURI(...)

新项目从零对接多品牌 ONVIF 相机、又不想背上 SOAP/XML 解析方向的第三方依赖树的，直接用这条 continuation 线即可；已有部署要迁过来的话，除了 import path 与门面调用的替换，没有其他迁移项。
