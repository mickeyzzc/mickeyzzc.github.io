MiBeeSteward v0.4.0: 路由器常驻发现 + OpenWrt 部署 + 设备持久化重写

July 29, 2026 MiBeeOSS Go, OpenWrt, 路由器, 被动发现, 设备发现, 开源 MiBee 开源项目实践系列 7361 字 15 分钟阅读
🔊

v0.3.0 发容器镜像时有个绕不开的前提：容器得 --network host 才能看到完整的 ARP 表，否则 MAC 发现数直接归零。根因是 network namespace——容器看不见宿主机那张塞满 30 行的 /proc/net/arp。

v0.4.0 把这个约束推到了一个更彻底的位置：**如果发现程序本身就跑在网关上呢？**网关是整个 LAN 流量的必经之路，DHCP 租约、conntrack 连接表、hostapd 的无线客户端、dnsmasq 的 DNS 查询日志——这些数据就在它眼皮底下，不需要再去 SNMP 探测交换机、不用扫端口、零额外网络流量。这版让 center 或 agent 直接常驻在路由器上，把这四个被动数据源接进来。

主题是三件事：路由器常驻发现、OpenWrt 一等公民部署、设备持久化重写。完整发布说明见 GitHub Release v0.4.0。

两个概念先说清：ARP 和「Tier-1 源」

后面整篇都在讲"哪种部署形态能看见多少设备"，可见性的根子埋在两个概念里——ARP 表和被动数据源的层级。先把这两个讲透，后面的对比图就一目了然。

ARP 表：设备的「电话簿」

设备之间通信要靠 IP 地址，但网卡只认 MAC 地址（网卡的物理编号，出厂烧死、全球唯一）。矛盾怎么解决？靠 ARP（地址解析协议）——设备每次要和某个 IP 通信前，先在局域网里喊一嗓子"谁是 192.168.1.5？把你的 MAC 告诉我"，被点名的设备应答，双方就把"IP ↔ MAC"的对应关系记进一张表，下次直接查表不用再喊。这张表就是 ARP 表，Linux 下可以直接读 /proc/net/arp。

为什么这张表是设备发现的命脉？因为它记录了"这台机器最近和谁通过话"。一个 LAN 里，网关（路由器）要和所有设备通信，所以它的 ARP 表最全——基本就是整张局域网的设备清单。一台普通主机只和少数设备打过交道，ARP 表就稀疏。

被动数据源的层级：Tier-1 和 Tier-2

被动发现指的是"不去主动探测（不扫端口、不发 SNMP 查询），靠系统已有的数据来认设备"。MiBeeSteward 把这些数据源分两层：

  • Tier-1（本地直读）：程序所在主机自己就有的数据——DHCP 租约文件、conntrack 连接表、hostapd 的 WiFi 客户端、dnsmasq 的 DNS 日志。读它们就是读本地文件，零网络流量。但前提是这台主机本身得是网关——只有网关才有 dhcp_leases、才跑 hostapd、才记 DNS 查询。
  • Tier-2（跨设备去查）：要向别的设备要数据——SNMP 查交换机 / 路由器的 ARP 表、监听 mDNS / SSDP 组播。能拿到 ARP 表的设备不止网关一个（交换机也有），所以 Tier-2 适用面更广，但要付出网络流量、且实时性不如 Tier-1（ARP 表是"最近通信过"，conntrack 是"此刻在通信"）。

有了这两个概念打底，下面的四种环境对比就清晰了：差别全在"能读到多全的 ARP 表“和”能不能开 Tier-1 源“这两件事上。

路由器常驻发现：主机就是网关时的四个数据源

MiBeeSteward 的被动发现一直分两个层级：Tier-1 是「主机自身能直接拿到的本地数据」，Tier-2 是「要跨设备去查的」（SNMP ARP、mDNS/SSDP 组播）。v0.2.0 的被动发现走的是 Tier-2——读路由器 SNMP ARP 表、本地 /proc/net/arp、组播监听。v0.4.0 补齐了 Tier-1，而且只在主机本身就是网关时才有意义。

四个源各自覆盖一块「网关才知道的事」：

数据源文件 / 来源看到什么
dhcp_leases/tmp/dhcp.leases 等路由器发过租约的所有客户端
conntrack/proc/net/nf_conntrack此刻正在通信的连接，相当于"谁在线"的实时视图
hostapdhostapd 客户端列表哪些设备正连在 WiFi 上
dns_log跟踪 dnsmasq 查询日志设备最近查过哪些域名（识别辅助信号）

其中 conntrack 最值得说。SNMP ARP 表告诉你"这台设备的 IP 和 MAC 最近通信过”，但 conntrack 告诉你"这台设备现在正在和谁通话"——连接表里只剩 30 秒未超时的活跃流。对于"这台设备到底在不在线"这种判断，conntrack 比 ARP 表更接近真实。

这四个源都是opt-in，且优雅降级。配置里不开就不读；开了但文件不存在（比如这台路由器没跑 hostapd、是个纯有线网关），源会自己禁用并记一条日志，不会让程序 crash。这一点和 v0.3.0 非特权镜像里 LLDP/CDP raw frame 的 stub 设计是同一个思路——能力缺失时降级，不假装能跑。

部署环境全景：路由器、物理机、虚拟机、容器各能看见什么

MiBeeSteward 能跑在四种环境里。区别不在于"哪个更高级"，而在于一个共同根因：程序运行在哪个 network namespace 里，以及那个 namespace 是不是 LAN 广播域的一员。这个事实决定了它能看见多少设备。

四种环境横向对比，先看一张总表，每种能看见什么一目了然：

环境ARP 表Tier-1 源主动探测实测 MAC 发现额外网络流量

ARP 表和 Tier-1 源是被动发现的两条命脉——前者决定 MAC 能不能认全，后者决定网关视角的"实时在线 / 已租约 / WiFi 客户端"能不能拿到。主动探测（TCP / SNMP / HTTP 端口扫描）四种环境都能出去，但它只回答"这个 IP 开了哪些端口"，不回答"这个网络上有哪些 MAC"。四种环境各自的取舍拆开看。

路由器（OpenWrt）

程序就是网关本身。四个 Tier-1 源全开——这些数据本来就在路由器本地，零额外网络流量：

  • dhcp_leases → 路由器发过租约的所有客户端，含已休眠的设备（它们不再回 ARP，但租约记录还在）。
  • conntrack → 此刻正在通信的连接，相当于"谁在线"的实时快照。
  • hostapd → 哪些设备正连在 WiFi 上（无线客户端清单）。
  • dns_log → 设备最近查过哪些域名（喂给识别引擎当辅助信号）。

MAC 发现不需要 SNMP 探测交换机，因为网关自己维护着整张 LAN 的邻居关系。保真度最高，实时性也最好：conntrack 反映的是"此刻"的活跃连接，而不是 ARP 表那种"最近通信过"。

家庭和小办公网络的网关绝大多数跑 OpenWrt——GL.iNet、小米、华硕这些路由器要么原生 OpenWrt，要么能刷。这是覆盖率最高的网关落地点。但 OpenWrt 不是普通 Linux，有几个现实约束：Flash 极小（16 / 32MB，装不下 Go 二进制的依赖链）、init 系统是 procd 而非 systemd、默认用 UCI 配置且服务非特权运行、CPU 是 ARMv7 / MIPS。v0.4.0 对这些逐个做了适配——procd init 脚本（deploy/openwrt/mibee-steward.init 和 mibee-agent.init）是 UCI 配置的服务：开机自启、崩溃重启、非特权运行；新增 ARMv7 构建目标覆盖低功耗路由器，init 脚本做了去重让 center 和 agent 共用同一个目标。代价是路由器资源紧张，但换来的是网关视角的最高保真度。

物理主机

程序作为 LAN 的一员跑在裸机 Linux 上。可见与不可见：

  • ✅ 完整 ARP 表——宿主机的 /proc/net/arp，宿主和 LAN 上其他设备通信积累下来的邻居表。只要这台机器平时和 LAN 有正常流量，表就是满的，测试 LAN 实测 31 / 31。
  • ✅ raw frame / eBPF——LLDP / CDP 的 raw frame 发送和 eBPF 被动观测都能跑（普通用户或 root 配好对应能力即可）。
  • ✅ 全部主动探测——端口扫描、SNMP、TLS 证书采集全可用。
  • ❌ Tier-1 源——这台机器不是网关，没有 dhcp_leases / conntrack / hostapd / dns_log 可读。

这是非网关形态里保真度最高的。用 systemd unit 管理，v0.1.0 起就有。短板只有一个：休眠设备（不回 ARP 的那批）认不全——但这是所有非网关形态的共同局限，只有路由器的 dhcp_leases 能捞到它们。

虚拟主机

VM 的保真度完全取决于网卡模式，根因还是 network namespace。一张表说清两种模式的可见性差异：

网卡模式ARP 表看得见看不见
桥接（bridged）完整整个 LAN 的邻居—
NAT仅虚拟网关宿主、虚拟网关LAN 上其他所有主机
  • 桥接网卡：VM 的虚拟网卡直接桥接到物理 LAN，接入同一个广播域，等价于物理主机——能看完整 ARP，保真度 ≈ 裸金属。
  • NAT 网卡：VM 有自己的隔离网络，流量经宿主 NAT 转发，等价于 Docker 的 bridge 容器——VM 只看得到虚拟网关，LAN 上其他主机全瞎，MAC 发现退化。

这个差异最容易在 VM 上踩到：同一台 VM，网卡模式从桥接切成 NAT，发现结果可以从"满血"直接掉到"几乎为零"。libvirt / KVM 默认经常给 NAT，VirtualBox 的 host-only + NAT 组合同理。如果 VM 里跑发现结果不对，第一件事查网卡模式，不是查程序。

容器

最细分的形态，v0.3.0 专门为它发了三种 compose profile，根因还是 netns。三种 profile 能看到的 ARP 表差出一个数量级：

Profile能读到的 ARP 表发现保真度
bridge（默认）仅 docker0 网关一条0 / 26，MAC 发现归零
host（推荐）宿主的完整 ARP 表30 / 31，≈ 裸金属
macvlan容器作为 LAN 设备的独立 ARP完整，直接和 LAN 通信

bridge 是最容易误用的：它是 docker 默认值所以最方便，但容器在独立 netns 里，TCP / SNMP / HTTP 主动探测能出去，读 /proc/net/arp 却只读得到 docker0 网关一条。所以生产扫描唯一该选 host。

容器还有一层特权维度。GHCR 上的官方镜像是非特权变体，LLDP / CDP raw frame + eBPF 是 no-op stub（需要 CAP_NET_RAW / CAP_BPF / CAP_NET_ADMIN）。需要的话本地 make docker-build-priv 构建特权变体。好消息是 Bridge-MIB / Q-BRIDGE / CDP / STP / TLS / 端口扫描这些主动探测全不依赖 raw socket，普通 host 网络容器已经能扫出绝大多数设备。

怎么选

  • 家里有能刷 OpenWrt 的路由器 → agent 装路由器上，网关视角，保真度最高、零额外流量。
  • 有常开的 Linux 物理机（家庭服务器、工位机）→ 裸机 systemd，≈ 裸金属保真度。
  • 只有 VM → 确保网卡是桥接；NAT 模式下发现基本失效。
  • 想快速试一下 → docker host 网络；千万别用默认 bridge 跑生产扫描。

一句话：先确定 netns 归属，再谈发现保真度。同一个程序、同一份配置，换个部署形态结果可能天差地别，差别全在它能看到哪张 ARP 表。

设备持久化重写：堵住双写裂缝

这是这版最底层、也最容易被忽略的改动，但它解决的是一个潜伏已久的正确性问题。

问题：两条独立的写入路径

v0.4.0 之前，设备行（devices 表的一行）有两条独立的写入路径，语义不一致：

mermaid
flowchart TD
    SYNC["同步扫描路径"] -->|"写入 devices"| ROW["device 行"]
    SCHED["定时扫描路径"] -->|"写入 devices<br/>语义不同"| ROW
    ROW --> BAD["同一行被两条路径<br/>用不同语义覆盖<br/>→ 不一致"]

    classDef src fill:#E3F2FD,stroke:#1565C0,color:#1565C0
    classDef bad fill:#FFEBEE,stroke:#C62828,color:#B71C1C
    class SYNC,SCHED src
    class ROW,BAD bad

同步扫描（前端点一下"立即扫描"）和定时扫描（cron 触发）本来该是同一件事，但两条路径各自维护了一套写设备的逻辑，字段更新的时机、空值处理、状态机推进的步调都不一样。结果就是同一台设备在两条路径下可能留下内容不一致的行——这种 bug 极难复现，因为它取决于哪条路径最后写。

修复：单一写权威

v0.4.0 的做法是确立单一写权威（single device writer）。runner.applyDeviceBridge 成为 device 行生命周期的唯一仲裁者，所有写入都收拢到这一个入口：

mermaid
flowchart TD
    SYNC["同步扫描"] --> BRIDGE["runner.applyDeviceBridge<br/>唯一写权威"]
    SCHED["定时扫描"] --> BRIDGE
    BRIDGE --> ROW["device 行<br/>两条路径留下相同的行"]

    classDef src fill:#E3F2FD,stroke:#1565C0,color:#1565C0
    classDef proc fill:#FFF3E0,stroke:#E65100,color:#BF360C
    classDef ok fill:#E8F5E9,stroke:#2E7D32,color:#1B5E20
    class SYNC,SCHED src
    class BRIDGE proc
    class ROW ok

改完之后，同步扫描和定时扫描留下的是逐字节相同的行——同样的输入，同样的输出。这不是性能优化，是正确性修复：消除了"两条路径谁后写谁赢"的不确定性。

设备替换检测

同一类问题还有设备替换。路由器换了、摄像头换了，但 MAC 没变（比如重新刷了固件）——这种情况下 IP 变了但身份字段（厂商、型号）还是旧的。v0.4.0 的规则是：MAC 相同但 IP 不同时，IP 持有者胜出，它的身份字段被强制覆盖。这避免了"换了设备但画像还停在旧值"的脏数据。

静默失败的修复

router_arp 和 multicast 这两个 Tier-2 源在 v0.3.0 里有个隐蔽的问题：文件缺失或权限不足时会静默失败——不报错、不记日志、结果集里直接少一块，你根本不知道它没在工作。v0.4.0 改成禁用自己并记录原因，和前面 Tier-1 源的优雅降级是同一个处理方式。

网络对账：揪出 IP 漂移的设备

这是和路由器常驻发现配套的一个后台任务。

DHCP 续期、设备休眠后重新上线、手动改 IP——都会让设备的 IP 漂移。如果漂到它登记网段之外，就是配置和数据对不上了：你把一台设备登记在 192.168.1.0/24，但它现在出现在 192.168.2.0/24，要么是这台设备物理挪了位置，要么是网段配置错了。

对账任务后台扫一遍，把这些"IP 漂出网段"的设备挑出来，标记给人工修正，不自动改。这是个有意的取舍：自动迁移 IP 容易把"设备真挪了"和"配置写错了"两种情况混为一谈，反而掩盖问题。让它冒泡到人，人决定怎么处理。

可配置性

之前探测阈值和心跳节奏是硬编码的，想调得改代码。v0.4.0 把几个关键参数提到配置 + 环境变量：

参数含义
scanner.lost_threshold连续几次探测不到才判定设备"丢失"
heartbeat.tick_interval_seconds心跳轮询间隔
heartbeat.offline_threshold连续几次心跳缺失才判定离线
heartbeat.offline_backoff_ticks离线后的退避节奏

每个都支持 MIBEE_* 环境变量覆盖，传 0 表示用默认值。环境变量覆盖的好处是容器部署时不用改配置文件，docker run -e 就能调。

UI 与前端加固

这版前端动得不少，挑几个实质性的：

  • 侧边栏重组。拓扑合并进 Devices 页，不再单独占一个入口——拓扑本来就是设备视图的一个维度，拆成独立页反而割裂。
  • 搜索 / 排序 / 分页全部挪到服务端。以前前端拉全量再过滤，数据一多就卡；现在服务端处理，结果集再大也不会丢。
  • DataTable XSS 修复。用 html() helper 对值做转义，堵住表格渲染的注入点。
  • 七个表单加 Zod schema 校验。前端在提交前先校验，减少无效请求。

设备类型方面，新增了手机（phone）和打印机（printer），完全由 YAML 数据文件驱动——加一个设备类型现在就是加一条 YAML，和 v0.2.0 的指纹库同一个数据驱动的路子。

速率限制调整

全局速率限制从 100 提到 600（rate_limit.global_per_minute）。原因是 v0.3.0 之后多标签页和后台轮询会互相挤占配额——开几个标签页就把限额吃光，正常的扫描请求被挡。提到 600 之后多标签页能正常工作；同时 SPA 静态资源被豁免，不计入限额。

升级

center / agent 都是 drop-in 升级，替换二进制即可。Docker 路径 docker pull 新 tag 重启。

已知限制

几个和 v0.3.0 一致、v0.4.0 没动的：

  • 单实例 SQLite——center 还是单实例，没有集群。规模到这个量级前不打算做。
