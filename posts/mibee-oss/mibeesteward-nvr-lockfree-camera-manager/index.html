MiBeeNvr 的无锁相机管理器：冷启动从秒级到毫秒

November 10, 2026 November 26, 2026 MiBeeOSS Go, 并发, 流媒体, 开源 MiBee 项目实践系列 4369 字 9 分钟阅读
🔊

监控列表在启动那几分钟里点不动：9 台相机的部署，一次 /api/cameras 请求要等 14.9 秒，后面虽然回落到 1.4 秒，还是一直在抖。多画面监控页的最近帧轮询跟着卡——相机重连那段时间，每一格画面几百毫秒才刷一次。

问题不在解码，也不在网络。相机管理器当时只有一把粗粒度的 cm.mu（sync.RWMutex），生命周期路径把它按在慢 I/O 上：录像器 Stop 要 join goroutine，启动要拨号做 ONVIF 握手，配置保存要写磁盘。任何一台相机启动、停止、更新，所有读请求都得排队。

这道题的形状是读多写少：读侧是列表、轮询、健康检查，每秒几十次；写侧是相机生命周期，几分钟才一次，但每次都带着几秒的网络握手。粗粒度锁把两种完全不同的节奏绑在了一起。

卡在哪把锁

cm.mu 罩着整个管理器的状态：recorders、hubs、配置、启动失败记录都在同一把锁后面。读侧的密度不低——/api/cameras 列表、每格 500ms 的最近帧轮询、健康检查的状态采样，全都要拿这把锁。写侧一旦进来，慢操作就整段占着它。

最典型的是 ONVIF 录像器自己的 r.mu。Start 从头到尾握着它：Connect、GetProfiles、GetStreamURI、RTSP DESCRIBE 探测、HTTP MJPEG 探测、委托录像器启动，一整串握手下来几秒。这段时间里，同一台相机的 Status()、Delegate()、RTSPURL() 全部阻塞，而最近帧轮询正走这条路径。一台相机在重连，它那一格画面就定住。

两层锁叠在一起放大了问题：全局 cm.mu 让任何一台相机都能拖住所有读，录像器自己的 r.mu 让同一台相机的状态查询陪着握手一起等。改之前实测到的形态是：启动阶段 /api/cameras 一次 14.9s，之后 1.4s 并持续抖动；重连期间最近帧轮询数百毫秒；一台相机的 ONVIF 重启能把其他相机的读也堵上秒级。

快照顶替大锁

改法是把状态本身和状态变更分开。管理器多了一个 snapshot atomic.Pointer[snapshot]，里面四张 map：

  • recorders：相机 ID 到正在运行的录像器
  • hubs：相机 ID 到 StreamHub，拉流和推流共用同一对象
  • configs：相机 ID 到配置指针
  • failedStarts：启动失败记录，交给健康自检做自动恢复

快照一旦 Store，任何人都不得原地改它。所有读操作——GetRecorder、GetHub、Status、statusSnapshot、CameraCount、GetCameraConfig、流地址解析——只做一次原子 Load，然后直接读 map，不拿任何锁。四张 map 是同一次发布的，读到的视图天然对齐：相机的录像器、hub、配置不会横跨两个版本。

这里有个隐含契约：快照不可变靠的是约定，不是语言层面的强制。clone() 是浅拷贝，复制 map 头、共享指针；录像器、hub、配置的不可变性由生命周期路径保证——要换就换指针，不原地改字段。一旦有人在发布后改了对象的字段，已经持有这份快照的读者都会看到被改过的值，写时复制的前提就不成立了。

func (cm *CameraManager) apply(fn func(s *snapshot) *snapshot) {
    cm.configMu.Lock()
    defer cm.configMu.Unlock()
    cur := cm.loadSnapshot()
    next := fn(cur.clone())
    cm.snapshot.Store(next)
}

apply() 是唯一的写入口：在 configMu 里取当前快照、clone、交给调用方修改、再 Store。10–50 台相机的量级，这次拷贝是纳秒级的，configMu 只罩住这一步。慢 I/O 全部发生在 apply() 之外——握手、拨号、录像器启停都不在锁内。

GetOrCreateHub 的「先查后建」也因此变成原子操作：快路径读快照；慢路径在 apply 内再查一次，两个并发调用返回同一个 hub，不会各建一个。这解决的不只是性能：重复建 hub 会让拉流和推流指向不同对象，画面能出来，状态却对不上。

图里两条路是分开的：读请求只碰快照，一次原子加载就走；生命周期操作只有发布那一下碰 configMu，真正耗时的拨号、握手、启停都在锁外，并且同一台相机的生命周期用 sync.Map 里的一把短锁串行。读和慢 I/O 从此不共用一把锁。

锁只锁一瞬

拆完之后管理器里不是没有锁，是每把锁只管一件事：

  • configMu：序列化 apply() 的快照拷贝、配置切片改动和写盘。只做纳秒级 map 拷贝和毫秒级磁盘写入，绝不跨网络或录像器启停。
  • auxMu：管定时任务、关键帧提取器、帧轮询器这些辅助生命周期句柄，和注册表读路径彻底分开。
  • startStopMu：串起顶层 Start/Stop。应用装配时 Start 是 detached 跑的，启动就绪不等相机；Stop 可能在 Start 还在注册录像器时到来，没有这把锁就会漏掉正在注册的录像器。
  • lifecycleMu + withCameraLifecycle：每相机一把 *sync.Mutex，懒加载在 sync.Map 里，只包住单次 start/stop/restart。

最后这把是关键补充。快照化解决了读不阻塞，但没解决「同一台相机被两个 goroutine 同时启动」：手动重启撞上健康自检的自动重启，或者更新配置撞上重新发现，后一个会把前一个的录像器从快照里覆盖掉，前一个的 goroutine 还在跑，却再也找不到——泄漏到进程退出。withCameraLifecycle 只串行同一台相机的操作，不同相机互不等待。相机删除时把对应 mutex 从 sync.Map 里删掉，避免键一直增长。

ONVIF 录像器那侧也做了同样的收缩：Start 只用一个短锁做「已在运行」检查，整段握手在 r.mu 外跑，最后再用一个短锁发布 delegate、流地址和状态；Status() 在短锁内取出 delegate 指针，然后到锁外调用它。握手几秒，状态查询不再跟着堵。

数字

同一部署的实测，9 台相机：

指标此前之后
启动阶段 /api/cameras14.9s，随后 1.4s 且持续抖动稳定 20–23ms
多画面最近帧轮询重连时数百毫秒稳定 1.5–2ms
ONVIF 重启期间的读阻塞秒级约 20ms 稳定
录像器启动串行，一台慢握手拖住全部并行，同一秒启动 4 台

录像器能并行启动，是因为慢握手不再占全局锁；apply() 只负责把结果发布出去，一台相机握手慢，不会挡住其他相机注册。

别人怎么做

读多写少、写里夹着慢 I/O 不是 MiBeeNvr 独有的题。做 NVR 和流媒体的项目都在解它，只是复杂性的落点不一样。下面几个例子的技术细节来自各自官方 live 文档或 README，这里只取和这道题直接相关的部分。

Frigate：把选择权交给运行时

Frigate 的相机管理围绕 go2rtc 展开。live 视图有 jsmpeg / MSE / WebRTC 三种技术，按带宽和播放器错误自动切换——网络差就降档，播放器报错就换协议。默认开 smart streaming：画面里没有活动物体时只更新静态画面（当前官方文档写的是每分钟一帧，早期版本是一秒一帧），有活动才切回实时流。画质选择按设备存 localStorage，还提供 Auto 档，按连接能力自动降档、恢复（出处：Frigate 官方 live 文档）。

这条路的复杂点在协议栈和客户端适配：服务端要把同一路流包装成三种协议，客户端要处理切换和错误回退。它基本不用面对「相机管理器的读被慢 I/O 占住」——状态查询走的不是一条会被握手长期占住的路径，问题在流媒体层就被化解了。

go2rtc：协商放进独立的一层

go2rtc 自己是个零依赖的独立流媒体应用。核心手段是 two-way codec negotiation：同一路相机配 RTSP 源加 FFmpeg 转码源，按浏览器的能力自动匹配——支持 H264 就直出，只认 MJPEG 就走转码。它明确不做复杂转码，交给 FFmpeg（出处：go2rtc README 的 codec negotiation）。

这里的取舍是隔离：协商和转码发生在流媒体层，NVR 主逻辑不用碰协议适配。代价是多一层部署单元，以及多源配置的维护成本。

ZoneMinder：重型状态机

ZoneMinder 是传统集成式监控——capture、analysis、recording、monitoring 一体，接 V4L 和 IP 相机，依赖 MariaDB。相机和事件被建成重型状态机模型，状态持久化在数据库里（出处：ZoneMinder 官方文档）。

这种模型里读路径要过数据库，一致性由事务保证，代价是每次状态查询都比读内存贵得多。它面对的「读阻塞」形态和 MiBeeNvr 不同：瓶颈在数据库，不在进程内的一把锁。

差异在哪

摆在一起能看出两条路线。Frigate / go2rtc 是流媒体网关思路：把复杂性放在协议协商和多技术栈，用独立进程或独立层把慢操作隔出去。MiBeeNvr 是单进程 NVR，没有独立网关层，复杂性只能落在内存模型上——COW 快照加细粒度锁。

同一道题——读多写少、写里夹慢 I/O——Frigate 用多技术栈和客户端自动切换把选择权推给运行时，go2rtc 把协商隔离到独立层，MiBeeNvr 用不可变快照消除读写耦合，让读路径一次原子加载就走完。差别来自部署形态：网关可以拆进程、可以带转码资源，单进程 NVR 得在自己的地址空间里把读写分开。

共同的经验是：写路径含不可控慢 I/O 时，把「状态发布」和「状态变更过程」分开，比单纯细化锁粒度更有效。细化锁只是缩短等待，快照把读写彻底解耦——写再慢，读拿到的永远是上一次完整发布。代价是 COW 拷贝和写时复制的复杂度：发布后不许原地改字段，这条靠约定维持，一旦破坏，整个读路径的正确性跟着失效。所以没有竞争的锁不必改成原子指针，下面这些就是反例。

不是哪儿都要无锁

同一份并发文档里还记着几个评估过但没做的决定，它们反过来说明这把尺子该怎么用。

StreamHub.Broadcast 用的是另一个模式：拿 h.mu 只为快照消费者列表，随即释放，再逐个调用消费者回调。每个 hub 只有一个 RTP 生产者，订阅和退订只在播放/停止时发生，锁在热路径上根本没有竞争。把消费者列表换成写时复制的原子指针、用 CAS 做增删的提案被否决了：缓存 IDR 的那份数据还要用 h.mu，换成 COW 就等于同时维护两套同步机制；CAS 重试和每次增删的分配也换不来什么。

EventBus 的订阅者通道是多生产者、单消费者：很多相机和 goroutine 并发 Publish。手写 SPSC 环在这里是错的拓扑，多生产者下会丢写甚至内存损坏；Go channel 本来就是合适的原语。

录像器内部则把字段分了三层：生命周期和分段状态（status、cancel、muxer、segStart、audioTrackID）由 mu 保护多字段一致性；跨 goroutine 的编解码配置（codec、audio）一次性写进 atomic.Pointer，发布后只读；writeFrames 独占的字段（trackID、路径、帧计数）刻意不加锁，因为只有那一个 goroutine 碰。

真正起作用的是持锁时间和访问模式：锁跨了慢 I/O，读就得等；把发布动作缩到一次 map 拷贝，读写自然分开。无锁只用在读路径被慢 I/O 拖住的那一处，其余保留原有的同步原语。
