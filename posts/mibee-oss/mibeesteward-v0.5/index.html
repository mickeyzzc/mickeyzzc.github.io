MiBeeSteward v0.5.0: 企业落地的三件事

August 20, 2026 September 1, 2026 MiBeeOSS Go, SNMP, RBAC, 配置备份, 网络管理, 开源 MiBee 开源项目实践系列 8100 字 17 分钟阅读
🔊

把内网设备管理系统带进公司或更严格的环境，会撞上三堵墙：SNMP 只支持到 v2c，口令在网线上明文跑，安全审计过不了，不少加固环境干脆把它禁用——采集直接瘫痪；权限只有管理员和普通用户两档，多人共用时分不清谁能操作、谁只能看；网络故障复盘问「这条配置什么时候被谁改的」，答不上来。

能过安全审计了

  • SNMP 升级到 v3：口令不再明文传输，还支持加密通道
  • 凭据加密存储，界面上永不回显明文
  • 禁用 v2c 的严格环境可以正常接入了

多人共用有分寸

  • 三种角色：管理员、操作员、只读查看
  • 每个人只看得到授权给他的网段；没授权的资源不提示「无权限」，直接当作不存在
  • 旧部署的用户升级后自动按只读工作，无需迁移

配置变更有据可查

  • 路由器、交换机的配置自动定时备份，变了才存新版本
  • 任意两个版本之间一键对比差异
  • 配置一变就产生事件记录，「什么时候被谁改的」有了答案

还多了两样

  • 内置通知：设备掉线、恢复、新增直接发 webhook 或邮件，不用为一台设备的告警专门维护监控系统
  • 外网拨测：自己的网站、邮件服务器这类公网服务也纳入监控，证书快到期会提醒

问得出的问题，都要答得上。

MiBeeSteward 在 v0.1.0 到 v0.4.0 的四个版本里，逐步形成了一条完整的内网设备管理链路：主动扫描与指纹识别负责设备的发现和分类；v0.2.0 引入 agent 与被动数据源（SNMP ARP、mDNS/SSDP 组播监听）把发现范围扩展到多网段，v0.4.0 进一步让 center 和 agent 常驻路由器，直接读取 DHCP 租约、conntrack、hostapd 客户端与 DNS 查询日志；心跳探测维护在线状态，变更检测输出设备的新增、变更、丢失事件；LLDP、CDP 与 Bridge-MIB 数据支撑 L2 拓扑；内网 HTTPS 服务的 TLS 证书也在采集范围内。部署形态覆盖物理机、虚拟机、容器与 OpenWrt 路由器。

这套能力的边界在内网，适配的环境是个人与小型团队。v0.5.0 沿两个方向扩展：一是适配要求更严格的使用环境——SNMP 升级到 v3、多角色权限体系、设备配置备份，分别对应企业网络中 v2c 被禁用、系统多人共用、配置变更有审计要求这三类场景；二是把探测范围从内网延伸到外网，新增对公网端点的拨测。

SNMPv3 支持

MiBeeSteward 依赖 SNMP 从交换机、路由器采集设备身份与拓扑数据，此前支持 v1 与 v2c。v2c 使用明文 community 认证，口令在链路上明文传输，网络上抓包即可获得；在多数企业的安全基线中 v2c 无法通过审计，相当一部分加固环境直接将其禁用。在这类网络中，MiBeeSteward 的 SNMP 采集完全不可用——这是此前企业落地的主要障碍之一。

v0.5.0 加入 SNMPv3 支持（USM 模型，authNoPriv 与 authPriv 两个安全级别），设备身份采集与全部拓扑走查在 v3 下功能完整。SNMP 凭据以 AES-256-GCM 加密存储，管理界面不回显口令原文。

v1 / v2c（此前）v3（v0.5.0）
认证明文 communityUSM 用户名 + 认证协议（MD5 / SHA / SHA-2）
传输明文authPriv 级别下加密（AES / DES）
凭据管理community 随配置分发加密落库，读取时脱敏
加固环境通常被禁用可正常使用

两点边界：存量 v1/v2c 部署升级后行为不变，创建第一条 v3 凭据之前不需要任何额外配置；agent 侧的 v3 支持推迟（凭据在分布式环境下的分发与轮换需要单独设计），agent 仍使用 v1/v2c。

多角色权限与网络作用域

此前的权限模型只有 admin 与 user 两档，user 可以看到全部网络与设备。单人使用没有问题；多人共用时暴露两个缺陷：无法区分"可以操作"与"只读查看"，也无法限制某个用户的数据可见范围。值班人员只需要查看状态，分支机构或代管（MSP）场景中各方只应看到自己的网段。

v0.5.0 将权限模型重构为三个角色加对象级作用域：

  • 角色分为 admin（全部权限）、operator（可执行扫描与设备操作，不可管理用户和权限）、viewer（只读）。旧部署中的 user 账户升级后自动按 viewer 工作，无需数据迁移。
  • 网段授权：管理员为每个非管理员用户指定可见的网段集合。
  • 作用域模式 rbac.scope_default 默认为 open，非管理员可见全部网络，与旧行为一致；设置为 closed 后，非管理员只能看到被授权的网段，未授权的资源返回 404——不提示"无权访问"，因此不泄露资源是否存在。

设备配置备份

网络故障复盘的第一个问题通常是"配置在什么时候被谁改过"。此前的 MiBeeSteward 无法回答：它记录设备的状态，但不采集设备自身的运行配置。

v0.5.0 加入配置备份：按计划通过 SSH 登录路由器、交换机、防火墙，拉取 running-config 并做版本化存储；内容与上一版相同时不生成新版本，发生变化时记录新版本并产生 device_config_changed 事件，进入变更检测与通知规则的处理范围。设备详情页提供配置历史与任意两个版本的 diff 对比，配置变更从此有据可查。

该功能默认关闭（scanner.config_backup.enabled），启用需要配置主密钥并为设备绑定 SSH 凭据。真机端到端验证（GL-MT3000）推迟到下一版本，当前代码路径完整、API 层已验证。

内置事件通知

在此前的版本中，要获得"设备掉线发送通知"的能力，需要额外部署 Prometheus 与 Alertmanager——为一个通知维护两套监控系统，成本与需求不成比例。

v0.5.0 内置通知规则引擎：按事件类型（掉线、恢复、新增、变更、配置变更）、作用域（全网、网段、单设备）、目标通道（webhook、邮件）配置规则，匹配的事件经既有通知分发器投递。每条规则对每台设备有独立的冷却窗口，网络抖动的设备不会重复告警。它的定位是事件路由而非告警引擎：没有阈值、静默窗口与路由树，需要这些能力时仍应使用 Prometheus 体系。

外网拨测

发现与监控的范围此前限于内网。v0.5.0 新增拨测模块，对显式配置的外部端点做周期探测：http / tcp / icmp 模块探测可用性，tls 模块以及 https 目标会采集完整证书链——到期时间、签发者、信任判定、TLS 版本与密码套件。内网 TLS 证书清单的能力由此延伸到公网域名：自有站点的可用性、邮件服务的 TLS 端口、证书到期时间，都能纳入同一套监控与告警。

SNMPv3 实现细节

  • 加密凭据库：新表 snmp_credentials 存 USM 凭据（用户名、auth/priv 口令及协议、安全级别），落盘 AES-256-GCM 加密，密钥是 security.master_key（恰好 32 字节，可用 MIBEE_SECURITY_MASTER_KEY 环境变量覆盖）。
  • 探测侧：SNMP 探测的版本循环加了 Version3，authNoPriv（MD5/SHA/SHA-2）和 authPriv（再加 AES/DES）凭据按目标逐个尝试；8 个 OID 的身份采集和 LLDP-MIB / CDP-MIB / Bridge-MIB / Q-BRIDGE-MIB / STP-MIB / IF-MIB 的拓扑走查在 v3 下全部可用。
  • API 与前端：凭据 CRUD 写时加密、读时脱敏，口令永不回显；扫描表单和设备页带 v3 选项和安全级别下拉框。

RBAC 实现

旧的 RequireAdmin 一刀切中间件替换为能力图（capability graph）加对象级授权：

  • 每条路由挂一个能力（CapDeviceRead、CapScanTrigger、CapDeviceWrite……），角色映射到能力集，admin 继承全部；users.role 的 CHECK 加宽，旧值 user 保留为 viewer 的别名。
  • 网段授权落在 user_network_grants 表，配套管理接口（/api/v1/users/{id}/network-grants、/api/v1/networks/{id}/grants）与用户页 UI。
  • closed 模式的作用域覆盖整个读取面：设备列表与详情、扫描任务/运行/结果、变更、拓扑统一过滤；扫描面同样对象级，scan_tasks.network_id 记录任务归属网段，非管理员只能看到和触发自己网段内的任务。
  • 防呆设计：rbac.scope_default 的值无法识别时回退 open，配置文件里的拼写错误不会让全体非管理员瞬间失去可见性。

流程说明：调度 sweep 挑出绑定了凭据的路由器/交换机/防火墙，SSH 拉取运行配置后先算 hash——内容和上一版相同就丢弃，只有变了才落一个新版本并发 device_config_changed 事件。版本列表里每一条都是真实变更，没有重复快照。

  • 厂商命令矩阵：JunOS 是 show configuration | display set；HP / Aruba / H3C / Comware 是 display current-configuration；Cisco IOS/NX-OS、Arista、华为 VRP、Mikrotik 和未知厂商统一兜底 show running-config。host key 用 TOFU（首次信任）记录。
  • 存储与读取：版本落在 device_configs（按 device_uuid 版本化）；读取 API 是 GET /devices/{id}/configs 列表 + /diff?a=&b= 两版对比；设备详情的"配置历史"标签页做 unified diff 着色渲染。
  • SSH 凭据与 SNMPv3 共用同一个 AES-256-GCM master-key 加密，写时加密、读时脱敏。

通知器规则模型

规则引擎订阅变更检测的 Watcher，匹配的事件走既有分发器（webhook/email 通道、3 个 worker、每用户已读状态）。规则模型是单张 notification_rules 表：

  • 事件类型：device_lost / device_recovered / device_added / device_changed / device_config_changed
  • 作用域：全部 / 单网段 / 按 UUID 单设备
  • 目标通道与启用开关
  • cooldown_minutes（默认 30）按（规则 × 设备）冷却，叠在变更检测器自身的 liveness cooldown 之上，两层窗口防抖。

拨测实现

  • http / tcp / icmp 复用心跳探测器；tls（及 https 目标）调用 CollectCertChain 采全证书链，SNI 自动推导。
  • 引擎 10 秒 tick 重新读取启用目标，增删改即时生效无需重启；重启后 next-due 从 last_run_at 恢复，不产生启动风暴；全局 8 并发上限；同一目标的定时与手动探测互斥。
  • 三张表：probe_targets / probe_results（追加式历史）/ probe_tls_certs（当前证书链，delete-then-insert；一次握手瞬断保留上一条已知良好链——与扫描器的"当前态"语义刻意不同，拨测关心"上次正常时的状态"）。
  • Prometheus 指标：mibee_probe_up / mibee_probe_duration_seconds / mibee_probe_cert_expiry_timestamp_seconds，deploy/prometheus/alert_rules.yml 附带目标掉线与证书到期两条示例告警规则。
  • 结果保留 retention.probe_results_days（默认 30 天），由既有清理服务回收。

存活判定时序化与身份键

设备存活此前建模为离散的 device_changed 事件，每次状态翻转都写一行变更日志。测试网运行一段时间后积累了 7 万多行，其中绝大多数是设备休眠、唤醒产生的翻转，真实变更被淹没。v0.5.0 的修复分三层：

  • device_liveness 时序：心跳存储里每设备每 tick 记一条判定样本，走既有的 buffered-write / WAL 通道。上层查询 OnlineRatio（窗口在线比例，区分抖动和真转换）、OfflineDuration、LivenessHistory。devices.status 仍是权威，时序数据可丢弃。
  • 分层事件：状态翻转被 liveness 层消费，不再写 device_changed；设备的新增、变更、丢失保持原有语义。
  • 卫星表改用 device_uuid 作键：心跳目标与各卫星表以稳定 UUID（而非会变化的 IP）为键，地址变化不再分叉历史；顺带修复了设备第二次扫描显示陈旧数据的回归。

配套的两个小修：lease sweeper 的 flap 计数从硬重置改为衰减，抖动设备会趋向"丢失"而不是永远乒乓；静默设备自动清理——扫描发现但从未有心跳的设备，带 MAC 的 7 天（retention.silent_device_days_mac）、无 MAC 的 24 小时（retention.silent_device_hours_no_mac）后自动删除，手动登记的设备永不自动删除，重新上线重置计时。设备详情补充了 last-seen / offline-since / last-online 字段。

MAC 的 U/L 位：一次误判和修正

这版有一个功能上线三周后被推翻重做，值得记录。

第一版把 MAC 第一个字节的 U/L 位（locally administered 位）当作"随机化 MAC"的判定依据：该位为 1 即认为地址是随机的，设备身份从 MAC 降级为 (ip, network_id)，以避免把 iOS/Android 的隐私随机地址当作稳定身份。

按 IEEE 802 / RFC 7042，U/L 位只表示"地址由本地分配"，无法区分两种情况：iOS/Android 的隐私随机化（每次重连都变）与软路由、虚拟化网卡、手工配置的本地地址（本地分配但长期稳定）。测试网随即暴露问题：7 台稳定的软路由和 NAS 被误判为"随机化"，一台 R68s 因身份降级被拆分到两个网段。

修正：身份降级整体撤销，设备身份回到 MAC 优先（无 MAC 才退回 (ip, network_id)）；该位保留为纯观测标志，字段从 mac_is_randomized 改名 mac_is_locally_administered，UI 标签从 “Randomized” 改为 “Locally Admin."，提示语明确说明该位无法区分随机与固定。multicast 位语义无歧义，保持不变。

结论：一个二进制位承载不了"随机化"这样重的语义，它的定义边界只到"本地分配”。

OUI 厂商推断：三档最长前缀匹配

OUI 查询按最长前缀匹配三档 IEEE 注册表：MA-S（/36，9 位十六进制）、MA-M（/28，7 位）、MA-L（/24，6 位）。

必须用最长前缀的原因：MA-S / MA-M 子块是从其他厂商的 /24 OUI 中划出再指派给另一厂商的。不做最长前缀匹配，一个 8C1F64B14 开头的 MAC 会被标为"IEEE Registration Authority"（/24 块的注册者），而它实际属于 Murata（/36 子块的受让人）。

    S36 -- "未命中" --> S28{"/28 命中?<br/>MA-M 7 位"}
    S28 -- "命中" --> V
    S28 -- "未命中" --> S24["/24 兜底<br/>MA-L 6 位"]
    S24 --> V

    classDef base fill:#E3F2FD,stroke:#1565C0,color:#1565C0
    classDef q fill:#FFF3E0,stroke:#E65100,color:#BF360C
    classDef ok fill:#E8F5E9,stroke:#2E7D32,color:#1B5E20
    class MAC base
    class S36,S28,S24 q
    class V ok

匹配从最长的块开始：先试 /36（MA-S），未命中退到 /28（MA-M），再退到 /24（MA-L）兜底，命中的前缀与组织名记入 scan_attributes。

  • 新增字段 oui_prefix（命中的 6/7/9 位块）与 oui_vendor（IEEE 组织名，即网卡硅片厂商）。它与既有 vendor 字段是分开的：vendor 是设备通过 SNMP/HTTP/TLS 自报的品牌，OEM、贴牌、虚拟化场景下两者不同。
  • 开箱即用：scanner.oui_path 为空时自动加载内嵌的精选表（go:embed，手工维护的 CC-BY-SA 子集）；完整 IEEE 数据集（All rights reserved 的事实数据）保持可选下载，不并入指纹语料（许可边界的完整说明见 docs/fingerprint-spec.md §8）。
  • scripts/fetch-oui.sh 重写：抓取三份 IEEE CSV 合并为一份；同时修正了一个既有错误——下载域名原来写的是 standardeee.org，正确的是 standards-oui.ieee.org，旧脚本一直在从非权威副本下载。

其他改进

  • 失效指标的修复。HeartbeatFailures 告警规则一直存在于配置中，但 mibee_heartbeat_checks_total 与另外 5 个指标只注册、从未在生产代码中递增，告警表达式恒为 0。根因是 collectors 位于 handler 包，service 层递增会造成 import cycle。这版将它们移入中性的 internal/metrics 包并完成生产者接线；prometheus.metrics_path 同步从"可配置但硬编码 /metrics“改为实际生效。
  • sqlc 漂移护栏。提交的 internal/db 生成代码起落后于 schema——提交历史里生成代码已长期落后，全量重新生成会破坏约十个调用点。这版将查询列集修正、重新生成收敛为空 diff，CI 增加 sqlc-verify（v1.31.1）：generate 产生 diff 即失败，schema 与查询变更必须随生成代码一起提交。
  • 拓扑可视化。分层力导向布局，图例兼作图层开关；搜索时弱化无关节点；选中节点高亮邻居；边可下钻本地/远端端口、VLAN、STP 角色；大图通过增量重建保持交互性能。
  • HTTP 面加固。RealIP 仅信任 server.trusted_proxies 配置的代理，不再无条件信任 X-Forwarded-For，客户端 IP 无法通过伪造报文头欺骗；service 层校验错误改为 sentinel 类型，handler 以 errors.Is 映射为 400，用户输入错误不再返回 500。
  • 前端。破坏性批量操作增加确认；五个编辑弹窗增加未保存离开确认；DataTable 行支持键盘操作；扫描页通过 AbortController 取消长扫描；修复 SSE 永久显示"已断开"的问题；日期与数字格式跟随界面语言；空态与错误态区分显示。测试侧落地了第一批 .svelte 页面渲染测试（login / devices / scanner / probe 四页）。
  • 分层债务清偿。最后四个直连数据库的写 handler（network CRUD、agent token、agent command、scanner result 批量删除）迁入 service 层，handler/service 分层约定至此没有遗留例外。

升级

  • 所有新配置默认关闭：scanner.config_backup 为 off，rbac.scope_default 为 open——升级后行为与 v0.4.0 一致。
  • users.role 的 CHECK 加宽，旧 user 行继续按 viewer 工作；新表（device_liveness、snmp_credentials、ssh_credentials、device_configs、user_network_grants、probe_targets / probe_results / probe_tls_certs、notification_rules）启动时幂等创建。
  • 迁移自动执行，执行前先做 VACUUM INTO 备份。
  • center / agent 替换二进制即可；Docker 路径 pull 新 tag 重启。二进制 CGO-free（纯 Go + modernc.org/sqlite），amd64 的 steward 25 MB、agent 18 MB；GHCR 镜像仍为非特权变体，需要 LLDP/CDP raw frame 与 eBPF 时本地执行 make docker-build-priv 构建特权变体。

推迟与限制

  • agent 侧 SNMPv3：分布式凭据分发的设计未定，agent 保持 v1/v2c。
  • 配置备份的真机端到端冒烟（GL-MT3000 真机）：下一版本补。
  • center 仍为单实例 SQLite，不变。
