MiBeeNvr 的 H.265 WASM 直播：按解码耗时诚实降级

November 17, 2026 November 26, 2026 MiBeeOSS H.265, WASM, 流媒体, 开源 MiBee 项目实践系列 4092 字 9 分钟阅读
🔊

浏览器对 H.265 的原生支持太零散：WebRTC 的 WHEP 轨道带不了 H.265，HTTP-FLV 用的 mpegts.js 解不开，HLS 走 MSE 在不少浏览器里看着「支持」、实际把 fMP4 字节丢掉，画面停在 readyState=1（HAVE_METADATA）。同一路 H.265 摄像头，协议选错就是黑屏，用户只能看到转圈。

MiBeeNvr 用 libde265 的 WASM 软解兜住这条路：NAL 送进 WASM，解出 YUV，转成 RGBA，再交给 Canvas2D 或 WebGL2/WebGPU 渲染。它不依赖 HTTPS——WebCodecs 在非安全上下文里是 undefined，纯 HTTP 也能看 H.265。但软解把代价从服务端挪到了观看者的 CPU 上：4K 流实测只有约 0.2fps，源帧率却是 15–25fps。解码跟不上，积压的帧越堆越多，最后用户看到的是画面下半截发绿发白的遮蔽块。

同一件事在主流 NVR 里有另一条解法：先把 H.265 转成 H.264 再交给浏览器，兼容性在服务端解决。go2rtc 和 Frigate 走的就是这条路；MiBeeNvr 把问题接到端侧，用 WASM 软解兜底，再给软解加一层按实测耗时触发的降级。两条路付出的代价落在不同的机器和不同的代码上，分开说。

别人怎么做

go2rtc 是一个零依赖的独立流媒体程序，RTSP、WebRTC、MSE、HLS 各种输入输出都能接。它对 H.265 的态度写在 README 的 codecs-madness 表里：桌面 Chrome 136+ / Edge / Android Chrome 136+ 的 WebRTC 和 MSE 才有 H.265；Apple 这边的 WebRTC H.265 要 Safari 18+，iPhone Safari 14+ 的 MSE 直接标着 no!，而 HLS 在 Apple 设备上反而能带 H.265。同一台设备换个协议，答案就变。

它的解法不是自己解码，而是选路。URL 上挂 codec filter，比如 ?mp4 或 ?video=h264,h265&audio=aac，从已有源里挑出合适的轨道；源里没有需要的 codec，就再挂一个 FFmpeg 源补上。README 说得很直白：不打算在 go2rtc 里内嵌复杂转码算法，交给 FFmpeg，包括硬件加速。多源自动匹配（multi-source two-way codec negotiation）是它的核心特性。README 的 negotiation 例子很具体：一台相机视频能给 H.264/H.265、音频能给 AAC/PCMU/PCMA，浏览器收 H.264/VP8/VP9/AV1、发 OPUS/PCMU/PCMA；两边音频对不上，就在同一条流里挂一个 FFmpeg 源把音频转成 OPUS。它不会去改浏览器解码器，而是把流补齐。在它眼里，H.265 是协议和轨道问题，不是解码器问题。

Frigate 把这条路线推得更彻底。Frigate 的 live 文档建议相机直接配 H.264 + AAC，明确劝退 H.264+/H.265+ 这类 smart codec——这些非标准编码会去掉关键帧，拉长起播时间；I-frame 间隔要和帧率对齐，否则首帧来得太晚。播放器的降级链是 MSE → WebRTC → jsmpeg：配了 go2rtc 默认走 MSE，MSE 失败或需要双向语音才尝试 WebRTC，还不行就退到 jsmpeg。播放器出错时 UI 会给一句解释，startup、mse-decode、stalled 三类各配「发生了什么 / 怎么试」。WebRTC 这条路本身也带不了 H.265；Frigate troubleshooting 文档给 H.265 相机的建议是：把 live 指向 H.264 子码流、H.265 主码流只用于录像，或者用 go2rtc 的 #video=h264#hardware 转码，并提醒软件 HEVC 转码很吃 CPU。它的排查顺序也是这个思路：先看 go2rtc 日志，再在 1984 端口的 web UI 里分别试 MSE 和 WebRTC 链接，然后从 /api/go2rtc/streams 看协商出来的真实 codec。确认是 H.265 之后，下一步才轮到转码。

两边的共同点是都把「能不能看」翻译成「服务端有没有给出浏览器能解的轨道」，UI 的职责是解释和引导改配置。代价是转码 CPU：go2rtc 把它外包给 FFmpeg，Frigate 文档自己承认软件 HEVC 转码开销大、建议开硬件加速。这条路成立的前提是你能控制服务端，且有转码余量。MiBeeNvr 的场景是纯 HTTP、没有 HTTPS，也未必有转码服务可用，于是把问题接到端侧。

花屏从哪来

WASM 解码器每收到一帧都要调用 libde265 的 pushNal 和 decode。push 失败意味着参考链断了，后面的 P 帧拿不到参考帧，解出来就是带遮蔽区的坏图。错误隐藏填出来的区域不是原画面内容，是解码器「尽量别让整帧崩掉」的兜底；对监控画面来说，这种块比少一帧更显眼。更隐蔽的是 libde265 的 warning（错误码 ≥1000）——它不是硬错误，但解出的图可能带隐藏区域，照样会闪出来。

以前这里的策略是硬扛：继续推、继续解，解不出来就重试。在弱客户端上这条路走不通。解码耗时一旦长期超过帧间隔，队列只会越来越长，画面就越来越花。

拿耗时当尺子

现在的降级判断不看设备型号，也不看静态能力表，只看两个实测数字。

一个是解码耗时：每帧进入 decode() 时打点，出来时算差，用 EMA 平滑，_decodeMsEma = ema * 0.8 + ms * 0.2。另一个是源帧间隔：从相邻两帧的 90kHz PTS 差算出毫秒值（(pts - lastPts) / 90），同样用 EMA 平滑，系数是 0.9/0.1，只接受 1–10000ms 的间隔，拿不到就用 66ms 兜底。

两个 EMA 的权重不一样。解码耗时是短促尖峰，0.2 让它跟得上单次卡顿；帧间隔来自源端 PTS，0.1 把它压稳，免得一次抖动把预算抬上去。预算取源帧间隔而不是固定值——同一路 1080p 20fps 与 4K 15fps 留给解码的时间完全不同，固定 66ms 会把前者误判成解不动。

前 4 帧不判断，让 EMA 和帧间隔先稳下来。之后 _decodeMsEma 超过预算的 1.5 倍就进关键帧模式；只有回落到预算的 0.5 倍以下才退出。两个阈值拉开距离是故意的——解码耗时在阈值附近抖动时，模式不会来回翻。

只解关键帧

进入关键帧模式后，_keyframeOnly 让所有非关键帧直接返回 null——每个 GOP 只解一个 IDR，输出一张稳定静帧，而不是积压一串解一半的坏帧。关键帧模式不是简单丢帧：它把输出收敛到每个 GOP 一张能独立解码的图，参考链断了也不会牵连下一轮。还有一层独立保护：push 失败后 _skipUntilKeyframe 置位，跳到下一个 IDR 为止；一旦拿到干净图，标志清掉，正常解码恢复。

降级模式下 libde265 报 warning 的图也不再往外送。这些图带着遮蔽区，闪一下就是花屏；丢掉它们，画面就停在上一张干净的帧上。代价很清楚：帧率没了，但画面不花。等码流分辨率降下来、或者客户端闲下来，解码耗时回落到预算的一半以下，全帧率会自动恢复，不需要人工介入。

能力表会骗人

协议选择那一层用的是同一套思路。浏览器有个现成的答案：MediaSource.isTypeSupported('hvc1')。在 Chromium/Edge 上它返回 true，因为系统注册了给原生 <video> 用的 HEVC 解码器；但 MSE 的 SourceBuffer 会把追加进去的 fMP4 字节静默丢掉，video.buffered 始终是空的，hls.js 和 mpegts.js 就卡在 readyState=1 黑屏。

go2rtc 那张 codecs-madness 表讲的是同一件事——同一台设备在不同协议下的 H.265 答案不一样。区别是它把答案列出来让人照表配，MiBeeNvr 不假设表准，直接跑一次。建一个临时 MediaSource，加上 video/mp4; codecs="hvc1.1.6.L93.B0" 的 SourceBuffer，塞一段真实的 HEVC init segment，等 updateend，然后看 video.buffered.length 是否大于 0。结果缓存在 sessionStorage 的 mibee_mse_h265_probe 里，同一会话不再重复探。真探要建 MediaSource、追加字节、等事件，不能放在每次协议切换的同步路径里；缓存只到会话级，换标签页会重探，一次误探不会带进后续会话。探测完成前一律按不支持处理，先把 H.265 路由到 WASM/WebCodecs 播放器——那条路是确定能出图的。类似地，probeCaps() 把 webCodecs、mseH265、wasmH265、webgpu、webgl2、hevcDecode 六项能力一次性探完缓存，避免在响应式路径里反复探测引发连接风暴。

诚实给用户看

降级不是悄悄换一种画面糊弄过去。播放器状态通过 statechange 事件上报，左上角状态点按真实状态变色；进入降级前先把最后一帧干净图截下来做 freeze frame，切协议时显示的是定格画面而不是黑闪。跨协议降级时，失败立刻切，持续 degraded 超过 8 秒才切（去抖），并弹一次提示；H.265 走不了 WebRTC 时界面直接说明已切换到其它协议以兼容。用户手动选定的协议会被钉住，自动降级和升级都不再动它——用户的选择优先。和 Frigate 在 UI 上写出播放器失败原因类似，MiBeeNvr 把状态跟着状态点走，用户不用翻浏览器 console 也知道现在走的是哪条路。

取舍落在哪

两条路绕的是同一个坑：H.265 的兼容性没有唯一答案。转码路把不确定性收在服务端，端侧只拿到 H.264；软解路把不确定性留在浏览器，靠运行时反馈收住。

转码路（go2rtc / Frigate）端侧软解（MiBeeNvr）
兼容性在哪解决服务端给浏览器能解的轨道浏览器内把 H.265 解成 YUV 再渲染
CPU 谁付服务端，需要转码余量，最好有硬件加速观看者，4K 流实测远低于源帧率
实现复杂度codec 协商 + FFmpeg 源 + 配置引导EMA、双阈值、关键帧模式、能力真探、状态上报
失败时用户看到UI 解释原因，引导换 H.264 流或开转码状态点变色 + 定格帧 + 一次提示
协议前提WebRTC 需要安全上下文和端口配置纯 HTTP 可用，不依赖 HTTPS

三件事可以拿去别的项目：静态能力表会骗人，isTypeSupported 和浏览器型号表都只是声明，注入真实数据实测、再用运行时反馈兜底更可靠；降级决策要有滞回，1.5 进、0.5 出，不然阈值附近的抖动会把模式来回翻；降级要让用户看见，状态、定格帧和提示都在，就不必用静默替换假装一切正常。

怎么选有很具体的判断：相机能改成 H.264、服务端有转码余量，转码路最省事，Frigate 文档也是这么建议的；手里只有 H.265 源、链路是纯 HTTP、又不想给服务端加一个转码进程，端侧 WASM 才值得做——代价就是上面那一整套运行时逻辑。

转码把 CPU 和复杂度放在服务端，WASM 把两者放到浏览器里——这是两条路真正的差异。选哪条，取决于你能控制哪一端。
