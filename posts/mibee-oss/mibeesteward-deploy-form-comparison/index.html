MiBeeSteward 装在哪：路由器形态与主机形态的对照实测

September 18, 2026 September 18, 2026 MiBeeOSS Go, OpenWrt, 软路由, 被动发现, 设备发现, 开源 MiBee 开源项目实践系列 3604 字 8 分钟阅读
🔊

MiBee Steward 是一个开源的网络设备管理系统（Go 单二进制，负责局域网设备的自动发现、识别和台账），有三种部署形态：直接跑在路由器上、跑在网内一台普通主机上，或者一台 center 配若干轻量 agent 管多个网段。这次用同一张物理网，把三种形态做了同版本、同参数的对照实测，把环境、过程和数据摆出来，回答"装在哪"。

结论先行：扫描能力与识别质量和形态无关——同版本同参数下，三种形态的扫描耗时和判定结果完全一致；真正拉开差距的是被动发现和跨网段能力，而这由设备的网络位置决定。

实验环境

工作室两个 /24 网段。主网段是日常设备：手机、笔记本、摄像头、米家生态、开发板，三十多台；第二网段安静些，放着 NAS 和几台常驻微型服务器。两段之间由一台 RK3568 软路由（4GB）双臂互联——它在两个网段各持一个地址，既是网段间的路由，又是看得见两侧的二层成员。下文描述和截图均已脱敏（IP 换为文档假段，设备名泛化）。

橙色是双臂软路由，蓝色是两个网段；虚线表示两段同属一张物理网，中间没有第三台设备。

同一张网恰好能同时摆下三种形态：

  • ① 路由器上的 center，天然横跨两段；
  • ② 第二网段一台 ARM 微型服务器（4GB）上的 center，只见本段；
  • ③ 同一台微型服务器做 center，主网段再放一块 armv7 开发板跑 agent。

①② 构成"路由器对主机"的前两组对比，③ 是项目的分布式形态（设计文档），作为第三组。

对比方法

  • 同一份源码、同一版本构建两种产物：OpenWrt 的 ipk 装进软路由，裸二进制配 systemd 跑在微型服务器。两边都是 ARM64。
  • 两边清空数据库，从零开始积累。
  • 不刻意拉平发现源：软路由开 DHCP 租约、conntrack 这些路由器天然有的源；微型服务器开 ARP 缓存、组播监听、网关 ARP 表的 SNMP 轮询。比的就是两种形态各自的自然表现。
  • 扫描同参数（全流水线、/24 网段、50 并发），同一秒触发。

流程：先做 8 分钟纯被动观察（不触发任何扫描），再全量扫描，最后采样资源占用。

被动发现：8 分钟，42 台对 34 台

清库重启后什么都不做，8 分钟被动观察结束时的账：

被动信号源软路由微型服务器
DHCP 租约表（本网段权威）有没有
conntrack（“谁正在说话”）有没有
ARP 缓存 + mDNS/SSDP 组播有有
跨网段可见性有没有
八分钟被动建档42 台34 台

软路由多出的 8 台主要来自 DHCP 租约表。它是本网段的 DHCP 权威，凡拿过租约的设备都留有记录——包括对主动探测完全不应答的休眠 IoT 设备。米家云绑定设备是典型：本地通道全关、mDNS 不回、TCP 不通，但 DHCP 握手总要做，租约里的主机名（如 viomi-waterheater-xxx）配上主机名指纹库，这些设备直接带着品牌和类型入册。conntrack 补上"谁正在说话"的实时视图。

微型服务器没有租约表，靠两条路滚出 34 台：ARP 缓存递归扩张（每发现新 IP 就触发一次识别扫描，扫描流量又让对端 ARP 表项回流），加上共享二层上人人可听的 mDNS/SSDP 组播。主机形态的被动发现够用，但有天花板——租约权威和 NAT 全景物理上拿不到。

主动扫描：107.667 秒对 107.640 秒

同时触发全量扫描：

指标软路由微型服务器
全量扫描耗时107.667 s107.640 s
存活判定35 台35 台

耗时差 27 毫秒，调度噪声级；存活判定一台不差。扫描耗时由探测超时的结构决定，与算力无关，所以两台性能不同的机器跑出了同一份答案。

识别质量同样对齐：共同 35 台设备上，类型判定 100% 一致。唯一的品牌差异是一台 NAS——微型服务器侧恰好抓到它 SSDP 自播的 SERVER 头，多认出一个软件品牌，属于被动证据的时间窗口偶然。

扫描完成后两边账本合并干净：微型服务器的 34 台全部被扫描重新覆盖，没有独有盲区；软路由 42 台里有 7 台扫不到，全部是另一个网段的设备。

跨网段：路由器的红利与代价

那 7 台来自 conntrack。软路由是两段之间的路由，跨网段转发表项在它眼里一览无余——路由器形态不仅本段看得全，跨段也看得见，这是位置给的结构性优势。

代价当场暴露：这 7 台外网段设备被直接记进了本网段清单。被动发现路径（DHCP、conntrack）目前不做网段归属过滤，被动看到的设备不管属于哪段都会入册。这个问题在第三组对比里进一步放大：路由器 center 的 49 台台账中有 14 台主网段设备被记进了第二网段。多网段部署时需要留意，此问题已在修复计划中。

第三组：center + agent

agent 的部署成本很低：一个 20MB 左右的裸二进制，systemd 拉起，配置里填 center 地址和一枚令牌。它用与 center 完全相同的流水线扫主网段，一轮 /24 约 110 秒——和前两台 ARM64 的 107.6 秒再次对齐，这次连指令集都换了（armv7）。

agent 与 center 之间走拉模型，一轮扫描的完整生命周期如下：

这条链路有两个实用性质：路由器上不需要开任何入站端口，agent 在 NAT 后照常工作；网络无变化时上报只刷一轮租约，开销可以忽略。主网段 33 台设备经 agent 入册，与 center 本地扫描共用同一套以 MAC 为主键的资产体系。

两种跨段方案摆成表：

路由器 center（双臂）center + agent
部署组件一个进程center + 每个远程网段一个 agent（约 20MB）
覆盖网段两段，原生每段一个采集点，扩展就是加 agent
台账入册49 台（含两段）主网段 33 台（经 agent）
网段归属14 台记错段边界清晰
/24 全量扫描耗时107.667 s110 s 上下（armv7）
存活信号本地心跳，30 秒一跳扫描报告刷租约，节奏必须快过 TTL

最后一行是两种形态的分水岭。center 的心跳会跳过 agent 网络（跨网段探测必然超时），agent 网段的存活改由扫描报告刷新的租约提供——扫描节奏必须快过租约 TTL，这是部署时要算清的参数。这次实验就栽在这里：6 小时一轮的定时扫描配上 5 分钟的默认 TTL，每轮扫描结束 5 分钟后整段设备集体显示离线，等下一轮扫描才"复活"。把扫描提到 5 分钟一轮、TTL 放宽到 15 分钟后进入稳态：

资源占用与内存要求

设备形态稳态内存扫描峰值结果
RK3568 软路由（4GB）center约 164 MB187 MB正常
ARM 微型服务器（4GB）center约 112 MB175 MB正常

同一台agent—初始化至 103 MBOOM

扫描峰值两边一致，因为工作集相同；稳态差约 50MB，来自路由器侧被动源的常驻缓存（租约追踪、连接表追踪、按 IP 的观测缓存）。对 /24 规模的网络，“扫描峰值 ≈ 稳态 + 50MB"可以作为容量规划参考。

内存是硬门槛。实验中一台 512MB 的 MT7981 旅行路由（厂商固件，常态可用内存约 90MB）装入 center 后触发 OOM，管理页面直接失去响应；换 agent 形态同样在初始化阶段被 OOM 击杀。据此项目增加了低内存配置模板和启动前的可用内存预检。路由器形态建议至少 1GB 内存。

选型结论

  • 扫描与识别，三种形态无差别；识别质量跟随版本走。
  • 被动发现由位置决定：DHCP 租约权威、NAT 全景、跨网段可见性是路由器形态的结构性优势，主机侧调参补不来。
  • 主机形态被动能力够用（8 分钟 34 台），但有明确天花板。
  • 多网段优先 center + agent：每段一个采集点，网段归属清晰，扩展就是加一台 agent；路由器形态跨段"能看”，但被动路径的网段归属过滤尚在修复，现阶段会记错段。

落到场景：单网段的小型网络（家庭、小工作室都一样），一台内存充裕（≥1GB）的软路由单机全包，体验最完整；多网段或设备规模上来之后，center 放在一台常驻主机上管台账，每个远程网段配一个 agent；512MB 的小盒子，让它继续专心做路由器。

如果看到这里你也想清点一下自己的网络：项目开源在 GitHub（AGPLv3），仓库在这里，Release 页有 Linux amd64/arm64 的单文件二进制和 OpenWrt 的 ipk/apk 包，装好就是本文截图里那个界面。指纹语料是纯数据文件，自家设备认不出的，可以照着指纹语料说明补一条规则，库越厚认得越准。部署上拿不准的，来 Discussions 聊。
