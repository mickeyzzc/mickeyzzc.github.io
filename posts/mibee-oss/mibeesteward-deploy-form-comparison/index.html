MiBeeSteward 装在哪：软路由、主机、center+agent 实测对比

September 18, 2026 September 18, 2026 MiBeeOSS Go, OpenWrt, 软路由, 被动发现, 设备发现, 开源 MiBee 开源项目实践系列 6043 字 13 分钟阅读
🔊

我维护一个开源的网络设备管理系统（MiBee Steward，Go 写的单二进制，负责局域网设备的自动发现、识别和台账）。它能直接跑在路由器上，也能跑在网内一台普通主机上；网段多的时候还有第三种：一台 center 带几个轻量 agent。到底装在哪更合适，我不想凭印象回答。手里正好有两个网段和几台闲置设备，就把三组对比都做了。

先说结论：同版本、同参数下，几种形态的扫描能力和识别质量没有任何差别；差别全在"被动发现"和"跨网段"这两层，而且由安装位置决定，调参补不来。过程里还顺带撞出我们自己代码的两个 bug 和一个设计缺口，外加一台 512MB 内存路由器的翻车记录，都记在下面。

我家的网，也就是这次的实验台

后面三组对比全部发生在这张物理网上，所以先把它摆出来（本文的描述和截图都做了脱敏：IP 换成文档用的假段，设备名全部泛化）。

家里是两个 /24 网段。主网段是日常那一摊子：手机、笔记本、几个摄像头、一墙角米家生态、七八块开发板，三十多台。第二网段安静些，放着 NAS 和几台常驻小主机。两段之间由一台 RK3568 软路由双臂互联——后文"路由器形态"用的就是这台。它在两个网段各持一个地址，既是网段间的路由，又是看得见两侧的二层成员。

橙色是双臂软路由，两侧蓝色是两个网段；虚线只表示两段同属一张物理网，中间没有第三台设备。这套拓扑省事的地方在于，三种部署形态可以同时摆进同一张物理网，连"两边环境不一样"这个变量都省了：① 路由器上的 center，它自己就横跨两段；② 第二网段主机上的 center，只看得到自己那段；③ 还是这台主机上的 center，主网段再配一块 agent。前两种就是下文的前两组对比；第三种是项目设计里的分布式形态（设计文档）：center 管台账，每个远程网段放一个轻量采集器，扫完往回报。以前一直没条件认真试——现在主网段正好闲着一块 armv7 开发板，这次一并做了。

第一次对比是错的

先交代一下我走过的弯路。我最初直接拿两台已经在跑的实例做对比：一台 RK3568（4GB）软路由跑 iStoreOS，一台 4GB 的 ARM 小主机跑 Armbian，同一网段。结果看起来很漂亮——路由器 55 台、主机 38 台，而且主机那边设备品牌识别明显更丰富。我当时差点就写成结论了。

写之前多看了一眼版本号：路由器上是一个月前的旧构建，主机上是当天的新版。这一个月里我们合入了米家生态的主机名指纹、mDNS/SSDP 服务公告指纹、被动观测接入识别层等一批识别语料。也就是说，“主机认得更准"完全可能是版本代差，跟部署形态没关系；而设备数量差，两边数据积累时长也不同，没法归因。

环境没控住的对比，数字再好看也是自欺。于是推倒重来。

这次怎么控变量

  • 同一份源码树、同一个版本号构建两份产物：OpenWrt 的 ipk 装到软路由，裸二进制配 systemd 跑在主机。两边 CPU 都是 ARM64，指令集层面无差别。
  • 两边都清空数据库，从零开始。旧库是几个星期累积下来的，混杂着迁移痕迹和历史心跳状态，不清没法比。
  • 软路由保持路由器本来的配置：DHCP 租约、conntrack 连接跟踪这些"只有路由器才有"的发现源全部开启；主机开它那侧能开的：ARP 缓存、组播监听、对网关 ARP 表的 SNMP 轮询。不刻意拉平，比的就是两种形态各自的自然表现。
  • 扫描任务用同一套参数（全流水线、/24 网段、50 并发），同一秒触发，消除网络状态随时间的漂移。

被动观察先跑八分钟（不触发任何扫描），然后做全量扫描，最后采集两边的内存占用。

被动发现：8 分钟，42 对 34

清库重启后什么都不做，八分钟被动观察结束时，两边各自发现了这么多：

被动信号源软路由主机
DHCP 租约表（本网段权威）有没有
conntrack（“谁正在说话”）有没有
ARP 缓存 + mDNS/SSDP 组播有有（ARP 雪球）
跨网段可见性有没有
八分钟被动建档42 台34 台

有意思的不是 42 对 34，是两边的设备各自从哪来的。

软路由的 42 台来自三路信号叠加。最可靠的一路是 DHCP 租约表——整个网段的地址都是它发的，凡拿过租约的设备都留了记录，包括那些对一切主动探测都不应答的休眠物联网设备。米家的云绑定设备是典型：WiFi 模块固件把本地无凭据通道全关了，mDNS 查询不回、常见 TCP 端口不通，但 DHCP 握手总要做。租约里的主机名（比如 viomi-waterheater-xxx、chuangmi-camera-xxx）配上我们新加的主机名指纹库，这些"哑设备"直接带着品牌和类型入册。第二路是 conntrack：作为网关，谁正在通信，它的连接表里就有一条。第三路是 ARP 缓存配合单机识别——每冒出一个新 IP 就地对它做一次完整识别扫描，所以每台设备一进清单就是有名字、有类型的，不是裸 IP。

主机那 34 台也比我预期得多。它没有租约表，但有一个我称为"ARP 雪球"的机制在滚：初始 ARP 缓存只有自己通信过的几台，但每发现一个新 IP 就触发识别扫描，扫描流量本身让对端的 ARP 表项回流到本机缓存，于是又有新的"已通信 IP"可查——递归扩张。加上共享二层上任何主机都能听到的 mDNS/SSDP 组播自播（NAS 的 avahi 服务集、DLNA 服务的 SERVER 头），八分钟滚出 34 台。主机形态的被动发现够用，只是有天花板：租约表和 NAT 连接表这两样，物理上就拿不到。

主动扫描：107.667 秒对 107.640 秒

同时触发全量扫描，结果摆在一起：

指标软路由主机
全量扫描耗时107.667 s107.640 s
存活判定35 台35 台

耗时差 27 毫秒，调度噪声级别；存活判定一台不多一台不少。

这个数字我认为是整个实验里最值得记下来的：扫描行为是跨平台确定的。同一个二进制、同一套参数、同一个网络，产出的存活集和耗时逐毫秒对齐——两台机器的 CPU 性能差异完全没体现，因为扫描耗时取决于探测超时怎么设计，而不是 CPU 快慢。

识别质量同样对齐。共同那 35 台设备上，类型判定 100% 一致——同一份指纹语料喂同样的证据，判定自然相同。唯一的品牌差异是一台 NAS：主机侧的组播监听恰好抓到了它 SSDP 自播的 SERVER 头（MiniDLNA/1.3.3），多认出一个软件品牌；软路由没赶上那条组播报文。被动证据有时间窗口的偶然性，单台差异说明不了能力差。

那被动阶段攒下的设备呢？扫描完成后两边的清单合并得很干净：主机的 34 台全部被扫描重新覆盖（它没有独有盲区），软路由 42 台里有 7 台是扫描扫不到的——全部是另一个网段的设备。

意外收获：跨网段视野，和一个 bug

这 7 台是 conntrack 给的。软路由同时是两个网段之间的互联路由，跨网段流量的转发表项在它眼里一览无余——这算路由器形态白捡的一项能力：它看得全本网段，也看得见"谁在跨网段说话”。

但这项能力立刻暴露了一个我们自己的 bug：这 7 台外网段设备被直接记进了本网段的设备清单。被动发现路径（conntrack、DHCP）绕过了我们在上报层做的 CIDR 边界检查——那个闸门只拦了主动扫描的上报。单实例部署里这只是清单混入几台"别人家的设备"，多采集点部署时这个问题会放大，已经在修复计划里：设备入库时按发现来源做一次网段归属过滤。

第三组：一台 center 管两段，还是 center 加 agent

先看路由器形态的"原生跨段"。同版本同参数，它的 center 不需要任何额外组件，台账里本来就有两段设备——我采样时是 49 台。但代价当场可见：其中 14 台主网段设备被记进了第二网段的网络。被动路径绕过了 CIDR 边界检查（就是上一节那个 bug 的现场版，后台的网段对账指标直接从 14 起跳）。跨段视野是真的，网段归属管得松，这两句话同时成立。

再看分布式这边。agent 是个 20MB 上下的裸二进制，systemd 拉起，配置里填 center 地址和一枚令牌就完事。它用和 center 完全相同的流水线扫主网段，一轮 /24 下来 110 秒上下——和前面两台 ARM64 的 107.6 秒再次对齐。“扫描行为跨平台确定"第三次得到验证，这次连指令集都换了。

上报走拉模型，调度器就住在 center 进程里，一轮的完整生命周期长这样：

agent 每 60 秒来问一次有没有新指令，指令随下一次拉取带走，center 到点把扫描指令入队就行——整条链路不在任何一侧开入站端口，agent 藏在 NAT 后面也照常工作。反熵哈希让稳定网络上的上报便宜到可以忽略——网没变化时一轮就是几十次索引更新。台账这头，主网段 33 台设备经 agent 入册，身份以 MAC 为主键，和 center 本地扫出来的是同一套体系——一台设备在哪段被发现，都是同一条资产。

第三组跑完，结果摆成表：

路由器 center（双臂）center + agent
部署组件一个进程center + 每个远程网段一个 agent（约 20MB）
覆盖网段两段，原生每段一个采集点，想加段就加 agent
台账入册49 台（含两段）主网段 33 台（经 agent）
网段归属检查松：14 台记错段每段独立采集，归属天然正确
/24 全量扫描耗时107.667 s110 s 上下（armv7）
存活信号本地心跳，30 秒一跳扫描报告刷租约，节奏必须快过 TTL

最后一行是这两种形态真正的分水岭。翻车就翻在这一行：部署完当天，仪表盘上主网段三十多台设备集体飘红。翻 center 日志做了个减法才对上时间：每台的"已离线时长”，恰好等于当前时刻减去上一轮扫描再减 5 分钟，分毫不差。机制是这样的：分布式形态里 center 的心跳会正确跳过 agent 网络（跨网段探测必然超时，不去凑那个热闹），存活信号改由扫描报告刷新的"租约"提供；租约默认 5 分钟过期，而我给 agent 设的定时扫描是 6 小时一轮。于是每轮扫描结束 5 分钟后，整段网络在台账上"死亡"，尸检五个多小时，等下一轮扫描复活。

单机形态里 30 秒一跳的心跳，在分布式形态里等价于"扫描节奏必须快过租约 TTL"。这个约束哪份文档都没写，是那一片红色教的。修法不优雅但诚实：agent 提到 5 分钟一轮，租约放宽到 15 分钟，留出两轮余量。更对的修法是让 agent 的被动发现也参与续租——代码注释声称它已经这样工作，实际没有，这是本次实验留下的第二个待修缺口。

顺带还炸出一个渲染层的 bug。对比期间我一直开着路由器 center 的网页，那天它恰好全网健康——零台离线——结果仪表盘冻死在加载骨架上。后来查实：后端把空列表序列化成 JSON null（Go 的 nil slice 就是这个行为），前端模板 overview?.abnormal.length 里那个问号只护住了前半截，null.length 抛异常，把整个渲染调度器带崩。“所有设备健康"反而是触发条件——不把两套实例摆在一起对比，这种坑日常根本踩不到。

内存占用

设备形态稳态内存扫描峰值结局
RK3568 软路由（4GB）center约 164 MB187 MB正常
ARM 小主机（4GB）center约 112 MB175 MB正常
MT7981 旅行路由（512MB）center——OOM，直接装不上
同一台agent—初始化到 103 MB同样被 OOM 击杀

峰值一致好理解——同一份扫描的工作集；稳态差约 50MB，主要是路由器侧被动源的常驻缓存（租约表追踪、连接表追踪、按 IP 的观测缓存）。对 /24 规模的网络，“全量扫描峰值 ≈ 稳态 +50MB”，这个实测数可以直接拿去做容量规划。

真正的教训来自表格最后两行那台设备。我另有一台 MT7981 方案、512MB 内存的旅行路由器（厂商原厂固件），想在上面也验证一遍，结果装上 center 后整个路由器管理页面直接打不开了。上去看：可用内存只剩 15MB，OOM killer 已经把机器上原有的一个 overlay 组网守护进程杀了，负载冲到 20，web 服务拿不到资源。停掉我们的进程立刻恢复。不死心又测了轻量的 agent 形态——初始化进行到 103MB 时同样被 OOM 击杀。

这台机器装着厂商全家桶加两个 overlay 组网客户端，常态可用内存就只有 90MB 上下，而我们的进程无论 center 还是 agent，光是加载指纹库和识别引擎就要 90-100MB。512MB 的路由器不是"紧”，是物理上装不下——前提还是你没有把内存分给别的东西。这次翻车促成了两个改进：安装脚本增加低内存配置模板（SQLite 页缓存从默认 64MB 砍到 8MB、并发减半、设置 Go 的软内存上限），以及启动时先检查可用内存，不够就直接拒绝启动并提示换设备——宁可不让装，也不能把用户的路由器搞挂。

所以装在哪

把数据摆在一起，选型其实很清楚：

  • 扫描和识别，三种形态无差别。识别质量跟着版本走，跟上发版比什么都重要——这也解释了为什么我第一版对比会得出"主机认得准"的错误印象。
  • 差异全在被动发现这一层。路由器多出来的能力来自它的位置：DHCP 租约表（休眠哑设备唯一可靠的信号源）、conntrack 实时连接表（谁正在说话）、跨网段视野。这些不是主机调参能补的。
  • 主机形态不是没有被动能力——ARP 雪球加组播监听，八分钟 34 台，大部分活跃设备都能覆盖——但天花板明确。
  • 跨网段：路由器形态"能看"，分布式形态"该看"，是两回事。路由器天生跨段，但被动路径目前不检查网段归属（14 台记错段的现场还摆着）；center 加 agent 的方案每段一个采集点，归属天然正确，代价是存活判定换了一套机制——扫描节奏必须快过租约 TTL，部署前要想清楚这一点。

所以我的建议是分场景：单网段的家庭环境，一台内存宽裕的软路由（≥1GB）单机全包，体验最完整；网段多或设备规模上来之后，center 放在一台常驻主机上管台账，每个远程网段丢一个 agent，发现交给有位置优势的采集点，台账集中一处；等被动路径的网段归属过滤修完，路由器形态跑双网段也是个省钱的选择。至于 512MB 的小盒子，让它继续做好路由器。

如果看到这里你也想清点一下自家的网：项目开源在 GitHub（AGPLv3），仓库在这里，Release 页有 Linux amd64/arm64 的单文件二进制和 OpenWrt 的 ipk/apk 包，装好就是本文截图里那个界面。指纹语料是纯数据文件，自家设备认不出的，可以照着指纹语料说明补一条规则，库越厚认得越准。部署上拿不准的，来 Discussions 聊。
