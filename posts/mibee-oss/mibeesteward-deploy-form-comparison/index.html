MiBeeSteward 装在哪：软路由、主机、center+agent 实测对比

September 18, 2026 September 18, 2026 MiBeeOSS Go, OpenWrt, 软路由, 被动发现, 设备发现, 开源 MiBee 开源项目实践系列 3494 字 7 分钟阅读
🔊

MiBeeSteward（GitHub，AGPLv3，Go 单二进制）做设备层的自动发现、识别和资产登记，支持三种部署形态：直接跑在软路由上、跑在网内一台主机上、多网段时用一台 center 带若干轻量 agent。三种形态在扫描能力、被动发现视野和资源开销上差别在哪，本文在同一套环境里做了受控实测。

结论

  • 主动扫描与识别：三种形态没有差别。同版本、同参数下，存活集和耗时逐毫秒对齐，类型判定 100% 一致。识别质量取决于指纹语料的版本，与安装位置无关。
  • 被动发现：软路由形态占优，优势来自位置。DHCP 租约表和 conntrack 连接表只有网关有；主机形态靠 ARP 递归扩张和 mDNS/SSDP 组播监听也能覆盖大部分活跃设备，但这两样信号源物理上拿不到。
  • 跨网段：分布式形态每个网段一个采集点，网段归属天然正确；双臂软路由一台也能看两段，但被动发现目前不按网段归属过滤，两段设备会混在一个清单里。
  • 资源：center 稳态 110–165 MB，全量扫描峰值 ≈ 稳态 +50 MB；512 MB 的小路由器装不下。

测试环境

家庭网络两个 /24 网段：主网段三十多台日常设备（手机、笔记本、摄像头、米家生态、开发板），第二网段放 NAS 和几台常驻小主机。一台 RK3568（4GB）软路由双臂互联两个网段，承担"软路由形态"；第二网段一台 4GB ARM 小主机（Armbian）承担"主机形态"，同时也是分布式形态的 center；主网段一块 armv7 开发板跑分布式形态的 agent。本文描述与截图均已脱敏（IP 为文档假段，设备名泛化）。

对比方法

  • 同一份源码、同一个版本构建两份产物：OpenWrt ipk 装软路由，裸二进制配 systemd 跑主机；两侧均为 ARM64。
  • 数据库清零，从零开始积累。
  • 各形态开启自己可用的被动源：软路由用 DHCP 租约表、conntrack；主机用 ARP 缓存、组播监听、对网关 ARP 表的 SNMP 轮询。不刻意拉平，比较的是各形态的自然表现。
  • 扫描参数一致（全流水线、/24、50 并发），两侧同一秒触发。
  • 顺序：被动观察 8 分钟（不触发扫描）→ 全量扫描 → 采样内存。

被动发现：8 分钟，42 对 34

被动信号源软路由主机
DHCP 租约表（本网段权威）有没有
conntrack（实时连接表）有没有
ARP 缓存 + mDNS/SSDP 组播有有
跨网段可见性有没有
8 分钟被动建档42 台34 台

差异全部来自信号源。

软路由的 42 台由三路信号叠加：DHCP 租约表记录所有拿过地址的设备，包括对主动探测一律不响应的休眠物联网设备——米家云绑定设备关掉了本地无凭据通道（mDNS 不回、常见 TCP 端口不通），但 DHCP 握手必然发生，租约主机名（viomi-waterheater-xxx、chuangmi-camera-xxx）配上主机名指纹语料即可带品牌入册；conntrack 提供实时连接表，谁正在通信一目了然；ARP 缓存配合新 IP 触发的识别扫描，设备入册即有名字和类型，不是裸 IP。

主机的 34 台靠两个机制：每发现一个新 IP 就触发识别扫描，扫描流量使对端 ARP 表项回流本机缓存，可查的"已通信 IP"随之递归扩张；加上二层网络上任何主机都能听到的 mDNS/SSDP 组播自播（NAS 的 avahi 服务集、DLNA 服务的 SERVER 头）。主机形态的被动发现够用，天花板同样明确：租约表和连接表，位置决定拿不到。

主动扫描：107.667 s 对 107.640 s

指标软路由主机
全量扫描耗时107.667 s107.640 s
存活判定35 台35 台

耗时差 27 ms，属调度噪声；存活判定完全一致。扫描行为与平台无关——耗时由探测超时的结构决定，两台机器的 CPU 差异没有体现。识别同样对齐：35 台共同设备类型判定 100% 一致（同一份指纹语料喂同样的证据）；唯一差异是一台 NAS 的软件品牌，主机侧恰好听到它 SSDP 自播的 SERVER 头（MiniDLNA/1.3.3），属被动证据时间窗口的偶然性。

被动阶段攒下的设备随后被全量扫描合并：主机的 34 台全部重新覆盖，没有独有盲区；软路由的 42 台中有 7 台扫描不可达——都是另一网段的设备，来自 conntrack 对跨段流量的可见性。这是软路由形态附带的能力：作为网段间的路由，跨段流量的转发表项在它这里一览无余。

分布式形态：center + agent

center（约 24MB，内嵌 Web UI）管台账，agent（约 18MB 裸二进制）按网段部署，systemd 拉起，配置 center 地址和一枚令牌即可。agent 用与 center 完全相同的流水线扫描本段：本轮实测 /24 一轮约 110 s，与前述两台 ARM64 的 107.6 s 对齐——连指令集都不同，扫描行为依旧一致。

上报为拉模型：agent 只发起出站 HTTPS，约 60 s 轮询一次命令通道，两侧都不开入站端口，agent 在 NAT 后照常工作。每轮上报附带状态哈希，网络无变化时 center 走快速路径只续租、不逐台合并。设备身份以 MAC 为主键，同一台设备无论在哪段被发现都是同一条资产。

两种跨段方案的对比：

软路由 center（双臂）center + agent
部署组件一个进程center（~24MB）+ 每段一个 agent（~18MB）
覆盖网段两段（双臂）每段一个采集点，加段即加 agent
网段归属被动发现暂不按网段过滤，实测 14 台记入另一段每段独立采集，归属天然正确
/24 全量扫描耗时107.667 s约 110 s（armv7）
存活信号本地心跳，30 s 一跳扫描报告续租，周期须短于租约 TTL

最后一行是分布式形态的关键部署约束：center 不对 agent 所在网络做心跳探测，存活信号由扫描报告刷新的租约提供，而租约有时限。因此 agent 的定时扫描周期必须短于租约 TTL——当前版本租约 15 分钟，agent 默认 5 分钟一轮，留两轮余量；调整扫描周期时要把这笔账算进去，否则设备会在两轮扫描之间被判定离线。

内存实测

设备形态稳态内存扫描峰值结果
RK3568 软路由（4GB）center约 164 MB187 MB正常
ARM 小主机（4GB）center约 112 MB175 MB正常
MT7981 旅行路由（512MB）center——OOM，装不上
同一台agent—初始化至 103 MB同样 OOM

峰值一致是同一份扫描工作集；稳态差约 50 MB，来自软路由侧被动源的常驻缓存（租约表、连接表、按 IP 的观测缓存）。对 /24 规模的网络，“全量扫描峰值 ≈ 稳态 +50 MB” 可直接用作容量规划经验值。

512 MB 设备的结论是装不下：实测一台 MT7981、512 MB 内存的旅行路由器（原厂固件，常态可用内存约 90 MB），进程加载指纹库和识别引擎即需 90–100 MB，center 与 agent 均触发 OOM。安装脚本为此提供低内存配置模板（SQLite 页缓存 64→8 MB、并发减半、设置 Go 软内存上限），启动时做可用内存预检，不足则拒绝启动。512 MB 的机器让它继续做路由器。

选型建议

  • 单网段家庭环境：一台内存宽裕（≥1GB）的软路由单机全包，被动发现视野最完整——DHCP 租约表和 conntrack 都在手上。
  • 多网段或设备规模上来：center 放常驻主机管台账，每个远程网段一个 agent。每段独立采集，网段归属天然正确；agent 也可以部署在该段的路由器上（OpenWrt 形态 B），同样读取该段的 DHCP 租约与 conntrack，等于把软路由形态的被动优势复制到每一段。
  • 双臂软路由一台看两段：可行且省一台设备，但注意被动发现暂不按网段归属过滤，两段设备会混在清单里。
  • 512 MB 小盒子：装不下，让它做路由器。

项目开源在 GitHub（AGPLv3）：仓库与 Release 页（Linux amd64/arm64 单文件二进制、OpenWrt ipk/apk 包），装好即本文截图中的界面。指纹语料是纯数据文件，自家设备认不出可按指纹语料说明补一条规则。部署问题可到 Discussions 交流。
