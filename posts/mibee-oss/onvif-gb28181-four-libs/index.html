拆出来的四个协议库：ONVIF 与 GB28181 的 Go/Rust 实现

August 29, 2026 September 1, 2026 MiBeeOSS Go, Rust, ONVIF, GB28181, 监控摄像头, 开源 MiBee 开源项目实践系列 3840 字 8 分钟阅读
🔊

MiBee 的相机接入跑两条协议：ONVIF 是国际市场的事实标准，海康、Axis、大华、Bosch 都说它；GB/T 28181 是国内安防的国标，政府和国企项目绕不开。设备端（树莓派相机固件，Go 和 Rust 各一个实现）和 NVR 端（MiBeeNvr，Go）都要说这两条协议，协议栈一直长在项目内部。

问题有两个。一是这些代码被互操作细节腌透了——digest 认证的 qop 处理、SIP Via branch 的唯一性、MANSCDP 报文的属性/元素双形式、TCP 帧头的字节数——它们是拿真平台一个个磨出来的，换个项目就要重磨一遍。二是 两周前做选库调研 时就发现，业界这两条协议的开源库分布很不均匀，有几个位置没人站。

所以这次把协议栈从项目里拆出来，按「协议 × 语言」拆成四个独立库开源。onvif-go 是 7 月接管的续维护线（接管记在此），另外三个是这次新发布的。

NVR 侧用 onvif-go 对接商用相机（左边两条协议里它只当客户端），gb28181-go 的平台侧包规划从 MiBeeNvr 提取；自建相机固件一侧，Go 固件用 gb28181-go 的设备包，Rust 固件用 gb28181-rs 加 onvif-rs。同一个 NVR 同时面对商用相机和自建固件，四套实现对得上。

onvif-rs：Rust 侧的 ONVIF 设备端

写一个「让 NVR 把你当成相机」的库，比写客户端少见得多：SOAP HTTP server 按动作注册 handler，WS-Discovery 应答器在 UDP 组播 239.255.255.250:3702 上回 ProbeMatches，WS-Security 校验 UsernameToken（PasswordText 和 PasswordDigest，常数时间比较）。覆盖 Device/Media/Imaging/PTZ 四个服务，PTZ 是纯状态机——没有电机的设备也能对 NVR 装出云台。

这个库最特殊的约束是字节级稳定。MiBeeNvr 出于性能考虑用裸 SOAP 字节流按 local-name 匹配响应，不经过完整 XML 解析——这意味着相机侧响应的元素名、命名空间前缀、属性顺序都不能变，改一个字节都可能打断消费端。onvif-rs 的 133 个测试里有 golden 字符串把这些钉死，README 里用加粗写着「不要改响应元素名，除非重跑消费端互操作测试」。元素命名严格跟官方 WSDL（GetStreamUriResponse → MediaUri → Uri）。

还有个命名插曲：crates.io 上 onvif-rs 这个名字被一个 2018 年的空占位仓库占着，lumeohq 的同名 WSDL 生成式客户端是另一回事，两边都合不上。所以 onvif-rs 走 git 依赖分发，等真要发 crates.io 时得起别的名字。

gb28181-rs 与 gb28181-go：国标设备端的两种语言

这两个库是同一份职责的两种实现：把一个媒体源注册到国标 SIP 平台，向它推流。REGISTER 加 digest 认证（MD5 和 SHA-256、qop=auth）、目录/设备信息/状态查询、心跳保活、INVITE 驱动的实时流、RecordInfo 查询加匀速回放和下载、SIP INFO 播放控制，UDP 和 TCP 都走。

两边都选择了手写 SIP，不引 SIP 框架。理由在调研时就清楚了：GB28181 只用 SIP 的一个小子集（REGISTER/INVITE/MESSAGE/BYE/ACK/OPTIONS），Rust 侧没有成熟的 SIP 栈可用，引框架的收益盖不过适配成本。gb28181-go 的平台侧包倒是建立在 gosip 上——平台面对的场景杂，自己写的理由不成立。

「拿真平台磨过」不是修辞，两个库的修复记录可以直接列：

  • digest 认证的 URI 匹配和 qop=auth 处理——照 RFC 写会在部分平台认证失败；
  • Via branch 必须逐请求唯一——复用会被当成重传；
  • TCP 媒体流的 $ 帧头是 4 字节不是 3 字节（gb28181-rs #3、两边同源的 #14）；
  • INVITE SDP 里出现 TCP 媒体 offer 时要接受而不是忽略（#14）；
  • REGISTER 响应要按 CSeq 匹配，过期周期的响应直接跳过（gb28181-rs #11）；
  • MANSCDP 报文有元素形式和属性形式两种写法，编码解码都要认，字符集横跨 GB2312/GBK/GB18030/UTF-8。

这些点每一个都对应一次真机联调失败。库的 API 设计也从这个现实出发：采集和存储不管，宿主注入两个接口——FrameSource（实时 H.264 帧）和 RecordingSource（录像段索引），协议层的信令状态机、MANSCDP 编解码、H.264 → MPEG-2 PS → RTP 的封包全部在库内。测试用带界通道、满了就丢的 MockFrameHub 起草稿。

两个注入接口只定义数据从哪来（帧订阅、录像段查找），信令时序和封包细节对宿主不可见。Rust 和 Go 两个版本走同一套设计和同一套修复清单，manscdp 编解码在 Go 侧单独成包，gb28181-go 的设备包和规划中的平台包共用它。

明确不做的也写进了文档：gb28181-rs 不含平台角色、不做 SIP over TLS/WebSocket、不支持 H.265（封包层留了宿主扩展点）。这些是当前生产用不到，做出来也验证不了的部分——不是愿景清单。

业界同类库现状

星数与最后活跃时间截至 2026-08，数据来自 GitHub。

Go 的 ONVIF 客户端是一条断代的谱系。use-go/onvif 星数最高（499★），2024 年 9 月之后没有推送；yakovlevdmv/goonvif（103★）2020 年就停了；0x524a/onvif-go（29★）2026 年 7 月停滞，就是 onvif-go 接管的那条线。Go 生态里找一个持续维护、真机验证的 ONVIF 客户端，选择面比星数分布显示的要窄。

Rust 的 ONVIF只有 lumeohq/onvif-rs（142★）一个像样的存在，WSDL 生成的客户端。设备端（server）方向在 Rust 里此前没有实现——onvif-rs 填的是这个空位，而且它和客户端库不构成竞争关系，一个管「连相机」，一个管「当相机」。

GB28181的成熟开源实现几乎都在平台侧：WVP-GB28181-pro（7.2k★，Java，国标平台的事实标准）和 gowvp/owl（797★，Go，国标 NVR）是平台参考；Rust 侧的 gmv（197★）是包含设备接入到流媒体分发的完整平台。设备端（把摄像头注册到平台）的独立可复用库，Go 侧大多长在平台项目的内部，Rust 侧直接是空白——GitHub 按「gb28181 + Rust」搜索，设备端定位的库此前一个都没有。

一句话概括现状：平台侧和客户端侧不缺实现，缺的是设备端和 Rust 侧——恰好是自建相机固件最需要的位置。

四个库的共同做法

原样提取，不重写。三个新库都是从生产代码 verbatim 抽出来的，不是照协议文档重新实现。重写的代码要重新交一遍互操作学费，提取的代码带着全部修好的坑。代价是 API 形状带着历史烙印（v0.1.0，接口未冻结），这个代价比交学费便宜。

TDD 加分支保护。三个新库都在严格测试驱动下开发，CI 跑 rustfmt、clippy -D warnings、go vet、go test -race，main 分支只接受 PR 合并且 CI 必须绿。onvif-rs 的 133 个测试里含 golden 响应字符串，改坏一个元素名测试就红。

双语 README，中英对照。国标库的受众里有海外做对华设备对接的工程师，ONVIF 库的受众里有中文开发者，两边都不含糊。

什么场景会用上

自建 NVR 或 VMS，接商用相机——onvif-go，它的兼容性矩阵（海康、Axis、大华、Bosch、Amcrest、HiSilicon OEM、ESP32 最小实现）是真机抓包喂出来的。DIY 相机固件或模拟器——树莓派、工控板做的相机要接国标平台，gb28181-rs（Rust）或 gb28181-go 设备包（Go）；要接 ONVIF 生态的 NVR，onvif-rs。写测试桩——onvif-go 的 server 包和 onvif-rs 都能当虚拟相机，不用插真机就能测 NVR 的发现、取流、PTZ 逻辑。

状态与限制

三个新库都是 v0.1.0：接口在收敛但未冻结，采用前看一眼 README 的 Status 一节。gb28181-go 的 platform/ 包和 manscdp 独立发布还在进行中；onvif-rs 因为 crates.io 命名占用只能走 git 依赖。四个库每天在 MiBee 的生产环境里跑——NVR 和两版树莓派固件就是它们的第一批用户。
