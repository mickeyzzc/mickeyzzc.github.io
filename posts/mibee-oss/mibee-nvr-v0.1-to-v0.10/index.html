MiBeeNvr：从 v0.1.0 到 v0.10.0

May 6, 2026 September 19, 2026 MiBeeOSS NVR, Go, RTSP, ONVIF, H.265, 小米摄像头, 延时摄影, 转码, 流媒体, 开源 MiBee 开源项目实践系列 15209 字 31 分钟阅读
🔊

MiBeeNvr 是我给自己家摄像头写的 NVR，2026 年 5 月 6 日发布 v0.1.0，7 月 28 日发到 v0.10.0-preview，不到三个月迭代了九个版本——v0.8 没有单独的发布帖，它暴露的问题成了 v0.9 的主线。之前每个版本单独成篇，这篇把 v0.1.0 到 v0.10.0 的发布记录按时间线合并改写成一篇：每一步做了什么，为什么这么做。

为什么自己写一个 NVR

家里有几类摄像头：几台小米，几个用 ESP32 自己搭的，还有多台树莓派 CSI。之前用云存储，不满意的地方很具体：小米摄像头默认只能通过米家 app 看，录像要么塞 SD 卡（容量有限，还得经常插拔），要么上云——云存储一个月几十块，隐私上也不放心，数据在别人手里，说不清哪天拿去训练 AI 或给了第三方。ESP32 摄像头录像存 SD 卡，查看和回放都不方便。

市面上的开源方案也试过：ZoneMinder 要装一整套 LAMP，部署比我的项目还复杂；Shinobi 配置复杂；Frigate 不错但偏 AI 检测，还依赖 Docker，太重。

所以目标很明确：

  • 单文件二进制，下载就能跑
  • 资源占用少，树莓派都能跑
  • 支持多种摄像头，特别是小米私有协议
  • Web 界面清爽，自动清理旧录像

现成方案都不合适，那就自己写一个。

架构与技术选型

MiBeeNvr 用 Go 写，前端是 Svelte 5——整个 SPA 编译成静态资源后 embed 进二进制，部署只要一个文件。后端技术栈：

  • modernc.org/sqlite：纯 Go 实现的 SQLite，无 CGO 依赖，交叉编译无压力
  • chi 路由；gortsplib 处理 RTSP/RTP；pion/rtp 处理实时流

选 SQLite 是因为单文件、零部署、并发读对家用场景够用，最重要的是不用额外装数据库。设计取向可以概括成「简单粗暴」：单个二进制、无外部依赖、AMD64/ARM64 交叉编译、YAML 配置、内置 Web 界面。

v0.2.0 时的整体数据流长这样——录制、存储、后处理、直播、网络出口各自独立：

摄像头接入录制器，录制器一路写存储（MP4 分段加 SQLite 元数据），一路把帧分支给按需生成的 HLS 直播；存储层之上挂合并和清理两个后处理引擎，最右侧是 API、Web 界面、WebDAV、FTP 这些出口。

搞 MiBeeNvr 的时候顺带做了几款 ESP32 摄像头固件，都设计成 MiBeeNvr 的上游采集端：MiBeeCam（ESP32-S3-A10，MJPEG 流加移动检测，带屏调试方便）、AI_Thinker ESP32-CAM 固件（十几块钱一块，支持 SD 卡和 NAS 上传）、MiBee Cam（XIAO ESP32-S3 Sense，AVI 分段录制，后来加了 ONVIF 自动发现）。链接在文末。

我自己是一台 ARM64 小主机，512MB 内存、2GB 存储，接 4 路：树莓派 CSI 走 MediaMTX 桥 RTSP、ESP32-S3 走 HTTP JPEG、两台小米走协议转接，30 秒分段，开 WebDAV 和 FTP。设置完基本不用管。要外网访问的话，前面加层 Nginx/Caddy 反代配 HTTPS——MiBeeNvr 自己不做 HTTPS，这种事交给反代更合适。

v0.2.0：能直播，录像会合并

v0.1.0 只能看录像不能看实时画面；录像 30 秒一小段，一路一天 2880 个文件；所有摄像头共用一个保留天数。v0.2.0（2026-05-12）一次补了 15 个特性，挑重点说。

HLS 按需直播。基于 gohlslib，有客户端请求才启动，没人看自动释放；异步帧写入把直播和录制管线解耦，互不干扰。H.264/H.265 都支持。带宽紧张时可以配置低分辨率子码流自动切换。

录像段自动合并。定期把同一摄像头的小段合并成大 MP4，全局和每摄像头都能配策略，Web 端有合并进度面板。文件数量下来之后，管理和数据库查询都快了。

每摄像头独立保留天数。门口留 30 天、阳台留 7 天，各配各的 retention_days。

ESP32-CAM 直连。新增 HTTP JPEG 协议，只能出 MJPEG 的几十块钱摄像头不用再折腾转码；前端用 Canvas 做了个 MJPEG 帧播放器，比直接刷 JPEG 图流畅。

装起来更容易。Docker 双架构镜像、一键安装脚本、mibee-nvr init 交互式初始化、health 健康检查命令、明文密码自动转 bcrypt。协议和编码拆成了两个独立字段（rtsp + h265），告别 rtsp_h264 这种组合写法。

这一版还搭好了 ONVIF 设备发现的框架，以及 Chart.js 统计图表、明暗主题自动跟随、中英文切换、响应式布局。

v0.3.x：小米摄像头内置与全协议直播

v0.3.0（05-20）主打小米摄像头深度集成，v0.3.1（05-22）补上多协议流媒体。这两版之间的架构反复值得单独讲。

从 go2rtc 依赖到内置实现

小米摄像头不走标准 RTSP，用私有的 miss（Mi Secure Streaming）协议，多层加密——知道摄像头 IP 也没法用 VLC 直接拉流。最早靠 go2rtc 做协议转换：用小米账号登录拿设备列表和密钥，建立 P2P 连接，解密后转成标准流给 NVR。全程不刷机、不拆摄像头。

mermaid
sequenceDiagram
    participant NVR as MiBeeNvr
    participant CLOUD as 小米云
    participant CAM as 摄像头
    NVR->>CLOUD: 小米账号登录
    CLOUD-->>NVR: passToken + 设备列表
    NVR->>CAM: CS2/TUTK P2P 握手
    CAM-->>NVR: miss 加密视频流
    NVR->>NVR: 解密 → 录制/直播

账号认证换密钥，P2P 握手建链，之后视频流在局域网内传输，解密后进录制和直播管线。

这个方案的问题很快暴露：CS2 P2P 连接约 20 分钟就超时卡死；go2rtc 是独立项目，出问题难定位；要维护两个容器，端口和资源都打架。

第二阶段试着把 go2rtc 的小米代码移植成插件系统——Go 接口注册、init() 挂载，甚至实验了 gRPC 进程隔离。现实是实时预览多了几层中间环节，性能明显下降，代码库也变得难懂，一个简单的功能要跨进程通信。

v0.3.0 把插件系统整个删掉，小米代码迁进内置的 internal/xiaomi/ 包——单二进制，无外部进程，无 Docker 依赖。这轮折腾的结论：对这个阶段的项目，简洁比扩展性重要。当然后来协议越接越多，那是另一回事——流媒体侧的可扩展性由 StreamHub 解决，见下文。

内置后的接入体验是三步：网页里用小米账号登录，设备列表自动出来，点添加就开始录像。.camera. 摄像头、.cateye. 猫眼、.feeder. 喂养器都能识别，不需要额外的协议转换容器：

归档录像

换摄像头（坏了、搬家、升级）时历史录像想留住——传统 NVR 删摄像头就删数据。v0.3.0 引入三态管理：Active（录制中）、Disabled（暂停）、Archived（只读）。归档时输入 DELETE 确认，系统自动合并片段、把摄像头移出实时列表，录像完整保留——能播放、能下载、能单独删除、能设归档组保留期。

StreamHub 与六种流媒体协议

v0.3.0 时代直播只有 HLS，延迟 5-15 秒，对实时监控来说不行。v0.3.1 引入 StreamHub——多消费者帧分发器：录制器把帧广播给 StreamHub，HLS/WebRTC/FLV 各自订阅，加新协议只需实现一个新消费者，录制器代码不动。

协议延迟编码方向适用场景
WebRTC (WHEP)<1sH.264拉流实时预览、对讲
HTTP-FLV1-3sH.264/H.265拉流Web 低延迟监控
LL-HLS2-5sH.264/H.265拉流低延迟兼容方案
HLS5-15sH.264/H.265拉流最大兼容性
RTMP—H.264推流OBS 等推流工具
SRT—H.264推流远程/不稳定网络推流

WebRTC 走 WHEP 标准（pion/webrtc v4），每个 H.264 摄像头最多 2 个 peer，空闲自动驱逐，还有僵尸连接检测；RTMP 基于 gortmplib 支持推流接入，OBS 可以直推；SRT 基于 gosrt 接收不稳定网络下的远程推流。前端 ProtocolSwitcher 一键切协议，下拉里显示各协议的预估延迟，H.265 摄像头自动排除不支持的选项。

这一版还有：15+ 项安全加固（路径验证、认证硬化、速率限制、SQL 注入防护）、前端完整迁移到 Svelte 5 runes 语法（国际化 500+ 键）、Setup Wizard 首次运行向导（自动检测浏览器支持的协议，按 LL-HLS > WebRTC > HTTP-FLV > HLS 推荐优先级）。

v0.4.0：录像有声音，挂了自动恢复

v0.4.0（05-25）解决两件事：MP4 录像一直是无声的；摄像头断连只能靠用户盯着重启。

音频录制

每个摄像头单独开 audio_enabled: true。RTSP 摄像头常用 AAC，小米和 ONVIF 设备常用 G.711 μ-law/A-law——MP4 容器不原生支持 G.711，做法是用自定义 box 类型（ulaw/alaw）直接封装原始帧，不转码、零 CPU 开销；AAC 走标准 mp4a box。代价是部分通用播放器不认自定义 box，MiBeeNvr 自己的播放器没问题。

健康监控

背景：社区反馈最多的问题是小米摄像头频繁断连，而开发者访问不了用户的本地网络，定位不了是网络、固件还是协议实现的问题。所以除了自动恢复，还要把健康事件记录下来——用户截图提 issue，就能针对性排查。

三层检测由浅入深：

mermaid
flowchart TD
    L1["连接层<br/>RTSP/ONVIF/CS2"] --> L2["码流层<br/>帧率/码率/关键帧"]
    L2 --> L3["画面层<br/>冻结/黑屏检测"]
    L3 --> SCORE["健康评分引擎"]

    classDef layer fill:#FFF3E0,stroke:#E65100,color:#BF360C
    classDef hub fill:#E8F5E9,stroke:#2E7D32,color:#1B5E20
    class L1,L2,L3 layer
    class SCORE hub

连接层看 RTSP 会话、ONVIF 响应、CS2 P2P 心跳；码流层统计帧率、码率、关键帧间隔；画面层做冻结和黑屏检测。每层独立阈值、独立冷却时间，结果汇到评分引擎生成综合分数——连接层权重最高（连接断了其余免谈），码流层次之，画面层兜底（连接和码流都正常但画面冻住了，多半是摄像头本身的问题）。

检测到异常后的自动恢复带安全边界：

mermaid
flowchart TD
    A[检测异常] --> B{安全边界内?}
    B -->|是| C[指数退避重试]
    B -->|否| D["停止恢复<br/>标记故障"]
    C --> E{恢复成功?}
    E -->|是| F[恢复正常<br/>重置计数]
    E -->|否| B

    classDef detect fill:#E3F2FD,stroke:#1565C0,color:#1565C0
    classDef decision fill:#FFF3E0,stroke:#E65100,color:#BF360C
    classDef success fill:#E8F5E9,stroke:#2E7D32,color:#1B5E20
    classDef failure fill:#FFEBEE,stroke:#C62828,color:#B71C1C
    class A detect
    class B,E decision
    class C,F success
    class D failure

最多连续恢复 N 次，超过就停止并标记故障，避免无限循环；重试间隔指数退避（1s→2s→4s→8s），不会把设备或网络打崩；同一摄像头冷却期内不重复告警。健康事件持久化，Web 端有时间线页面，GET /api/cameras/{id}/health 可查单摄像头详情。

播放稳定性与树莓派

HLS 之前可能在任意帧开写 segment，播放器拿到不以关键帧开头的片段就是黑帧——改成等 IDR 帧再开写，牺牲一点边界精度换每个 segment 首帧可解码。新增基于信用的帧率限流：消费者有帧预算，消费一帧减一个信用，生产者有信用才发帧，低性能设备不再被突发帧卡死。LL-HLS 两个参数为树莓派调优：backBuffer 0.5→2.0 秒，liveSync 2→3 秒——树莓派上的播放从经常卡顿变成基本流畅。

新增 ARMv7 二进制（树莓派 2/3、玩客云这类设备），架构覆盖 amd64/arm64/armv7。这一版测试套件 1651 个用例通过，覆盖率 60.7%。顺带还有 ONVIF 编码自动检测、小米云端元数据同步、敏感字段加密存储。

rpi-cam：自己造一个 ONVIF 服务端

ONVIF 客户端开发有个现实问题：得有一个能跑的服务端来对调，光看协议文档和抓包不够。手边树莓派 3B + OV5647 跑的 MediaMTX 没有 ONVIF 服务端模式，NVR 发现不了它；现成方案要么性能差、要么只支持 Device 服务、要么带 CGO。MiBeeNvr 的 ONVIF 客户端用 0x524a/onvif-go，服务端用同一个库就是天然兼容，于是写了 rpi-cam：完整 Profile S（Device/Media/PTZ/Imaging）+ WS-Discovery、RTSP（gortsplib，和 MediaMTX 同库）、RTMP 推流、相机参数控制、数字 PTZ，零 CGO。

硬件转码

不少摄像头只出 H.265，浏览器直接放不了。这版的转码系统自动检测输入编码、按需启动硬件加速转码（H.265→H.264），转码过程做冻帧防闪，配了任务状态监控页面。

重连策略与社区问题

录制器重连从纯指数退避改成分级退避加随机抖动：1s→5s→10s→60s，每一级带抖动，多个摄像头同时断线不会同时重连造成雪崩。RTSP 连接超时也开放了配置。

社区反馈的稳定性问题集中修了一批：

  • CS2 缓冲区满不再触发整个 P2P 会话重建——改为丢最旧帧推入新帧，对视频流来说丢一帧远比重建会话便宜。顺带修了约 20 分钟连接挂起的 UDP 写入数据竞争。
  • Docker 首次启动崩溃：自动生成配置时 HLS 默认值没填，segment_count 校验拿到 0 报错——autoInitConfig 先调 ApplyDefaults()。
  • DB 目录不存在导致 unable to open database file (14)、绿联云 NAS 权限不匹配、容器重启丢权限等部署问题逐个修掉。
  • 只支持 TUTK 的型号（如小米智能室外摄像机 4 Pro 三摄变焦版）需要商业授权，明确提示不支持；能走 RTSP 的建议 RTSP 接入。

ONVIF 兼容性当时也如实标注：rpi-cam 保证了自身实现正确，真实商用摄像头的边界情况还需要时间验证，遇到问题欢迎带型号提 issue。

v0.6.0：延时摄影、转码与可观测

录像跑起来之后存储最先告急：单路 1080p 一天写几十 GB，30 天留存一块 1TB 盘就没了一大半。社区讨论里延时摄影呼声最高——画面大部分时间静止的摄像头，压成延时只需要约 5% 的空间。v0.6.0（06-05）的主线就是把延时摄影和转码做出来。

延时摄影 v1

管道是多阶段的：RTSP/MJPEG 源按间隔抽 JPEG 帧 → 静止检测跳帧 → 序列落盘 → 滚动合并与每日合并。抽帧间隔默认 30 秒，带 5% 随机抖动——多个摄像头同一瞬间发起 RTSP 会话会有 CPU 尖峰。静止跳帧复用健康模块的冻帧检测（比较相邻帧直方图），连续 3 个周期无变化就暂停抽取，画面恢复再继续。

合并有两条路径。Go 原生合并把 JPEG 帧直接当 H.264 IDR 帧封装进 MP4——纯 mux 零编码，树莓派 3B 上约 5% CPU 就能实时合并 10 路 1080p JPEG，代价是文件体积大。FFmpeg 合并把序列重编码为 H.264，体积缩小 5-10 倍，适合长期存档。滚动合并为每个摄像头维护一个合并协程，新 segment 触发时取消旧协程——这里有个竞态：旧协程的 defer 清理可能误删新协程的登记项，用创建时的所有权 ID 校验解决（清理时只有自己仍是活跃条目才删除）。

转码系统与回填

任务队列落 SQLite，录制完成通过事件总线自动入队，前端轮询任务状态，失败任务可重试。最有用的是回填：选一段历史日期范围批量创建转码任务，目标编码可选 h264/hevc/mjpeg。ARM 平台检测不到硬件编码器（/dev/dri/renderD128 或 V4L2 编码节点）时自动降级 libx264。历史清理做成翻页式，避免一次删大量记录把 SQLite WAL 撑大。

铺路的一版

internal/ai/ 搭好 ONNX Runtime 推理框架——通过子进程解耦 CGO 依赖，YOLOv11n 模型就绪，只差一个 feature flag。可观测性接入 Prometheus 指标和 VictoriaLogs 远程日志，社区问题靠数据排查不再靠猜。

一批杂项修复和加固：非标准 H.265 SPS 字段导致 hls.js 黑屏——HLS 写入前拦截修补 SPS；COOP/COEP 头只在 HTTPS 下启用（strict 模式在 HTTP 下会破坏 WebSocket）；录制器加 5 秒帧看门狗，等不到 SPS/PPS 主动重连，防协程泄漏；录制起点做 PTS 有效性校验，防 0 时长录像把前端总时长算成 NaN；测试套件从约 340 秒优化到 88 秒（并行化 + WAL + mock 时钟）；文档从单个 2000 行的 api-reference 拆成 19 个模块化文件，中英双语同步。

发布前在真实摄像头环境验证，同期的三个自研摄像头项目也做了适配改造，见 camera-test-machines：三个摄像头测试项目。

v0.7.0：延时摄影 v2 与小米双摄

v0.6 的延时摄影很快被社区列出几个硬伤：JPEG 序列吃存储、H.265 摄像头的延时片段放不了、双摄小米只能抓主镜头、H.265 HLS 偶尔直接 panic。v0.7.0（06-14）围绕这些展开。

延时摄影 v2

核心变化：合并不再经过 FFmpeg 和中间 JPEG 序列。关键帧抽取器在第一帧缓存 SPS/PPS，之后每个关键帧以 H.264/H.265 NAL 单元形式落盘，合并时纯 mux 封装进 MP4——零编码，产出直接可播。

H.265 HLS panic 与连接稳定性

#20 报告的 H.265 HLS panic：H.265 流首帧到达时 muxer 可能还没建好，写入路径没有防护，直接走到未初始化的指针上。重构后的 StreamHub 集中管理 muxer 生命周期——写入前检查就绪状态，未就绪触发自动恢复重新初始化，而不是 panic。#18 的小米摄像头反复重连是连接层的同类问题：UDP miss connect 超时后 PONG 响应处理不当，连接状态机卡死，表现为设备掉线反复重连。修复包括 PONG 健壮性处理、退避加随机抖动、重连时清理 CS2 缓冲残留。

小米双摄

CW500、室外摄像头 4 这类双摄设备两组镜头共用一个设备 ID。v0.7.0 在添加摄像头时支持通道选择——通道参数作用于 MISS URL 解析阶段，每个镜头对应独立 recorder 实例，录制、转码、延时管道各自独立。顺带修了连接测试里特殊字符密码把 URL 拼错的问题——「测试一直失败但实际能录」这种状态最迷惑人。

转码分层与前端整理

转码模块做了分层重构：任务管道（SQLite 队列 + Worker 池）、硬件探测（V4L2M2M/VAAPI/NVENC，初始化时一次完成并缓存，探测不到的后端直接关闭）、编码器抽象（硬件/软件统一命令构造接口）拆成三层——之前加一个编码器要改四五处，现在只动抽象层。补了 libx265 软编码，H.265 摄像头没硬件编码器也能保持编码不变转码。

前端 Dashboard 做了轮大整理：浏览器端 AI 检测模块只做了识别没做跟踪，实际用处不大还占资源，从前端移除（后端 ONNX 框架保留）；摄像头的 Enabled 开关移除——它和录制、流媒体、转码的状态机纠缠，禁用的摄像头偶尔还会因事件总线触发录制，启停统一走录制器生命周期；转码任务收进独立历史页。

摄像头项目同步

测试依赖的三个自研摄像头项目同步更新：MiBeeHomeCam 改名 MiBee Cam，加了 ONVIF WS-Discovery 自动发现（Synology、Milestone 这类 NVR 能自动发现它），MJPEG 挪独立端口，帧广播器落地解决 PSRAM 争用；rpi-cam 迁移为 mibee-eye-raspi，定位从树莓派扩展到所有 libcamera 兼容 ARM 板（香蕉派 M5、香橙派 5 行为一致）；MiBeeCam 修了硬编码测试 WiFi 凭证的遗留 bug。

v0.9.0：零配置发现，顺手还债

v0.8 没有单独的发布帖。它在开发中暴露的存储瓶颈和摄像头管理器锁问题，成了 v0.9.0（07-19）的主线之一：9 路摄像头挂在 Banana Pi M5 上，/api/cameras 冷启动卡 14.9 秒——不是遍历慢，是管理器的 RWMutex 被 recorder 启动、ONVIF 握手这些秒级慢操作握着写锁，所有读操作排队。这版在 9 台真实摄像头（CW500 双摄 ×2、DS-2CD2047G2、户外摄像头 4、IMILAB A1、Dafang、Xiaofang、Aqara G2、小米云台）上做了回归验证。

ONVIF 零配置自动发现

之前添加 ONVIF 摄像头：知道 IP → 设置页 → 手动填 Profile，5 台以上就成负担。v0.9 实现双模式发现：被动监听 UDP 3702 的 WS-Discovery Hello（设备上线即感知），主动每 60 秒 Probe 扫描（最小 30 秒，照顾树莓派 3B 的性能）。发现的设备统一走注册管线：按 endpoint + stable_id 去重（覆盖已归档设备）→ 信息补全（品牌/型号/序列号持久化）→ 没凭据的进 pending_activation，前端弹激活按钮，填一次密码就通——激活时做真实的 GetStreamURI + RTSP DESCRIBE 测试，不再只做 HTTP HEAD。启动时有 10 秒宽限期，避免设备还没完成 DHCP 就被扫描错过。

摄像头管理器无锁化

方案是写时复制（COW）原子快照 + 每摄像头独立生命周期锁：所有读路径走不可变的原子快照，完全无锁；写入路径只持纳秒级的 map 拷贝加磁盘写入，从不跨 I/O；per-camera 的锁串行化单个摄像头的 start/stop，ONVIF 握手不再持有全局锁。Banana Pi M5 上 9 路实测：

14.9 秒里大部分不是在做有用的事——几个 recorder 串行启动，每个做 ONVIF 握手加 RTSP 连接，期间写锁把其他 8 路和所有读路径全挡在外面。

FFmpeg 变可选，TUTK 老设备接入

FFmpeg 是当时唯一的第三方二进制依赖，部署前都得确认装没装。v0.9 把它降级为可选加速器：录制、回放、直播、Relay、延时、合并在无 FFmpeg 时全部能跑，只有 H.265↔H.264 像素级转码还需要它。新增纯 Go 的 MP4 盒探测包 mediaprobe（codec/duration/resolution/frame-count），比 ffprobe -count_frames 快 10-100 倍。

小米旧设备（Dafang、Xiaofang、Aqara G2 等）走自研 TUTK P2P 协议，之前接不进任何 NVR。这版从 go2rtc 移植 TUTK 传输层独立实现：TransCode/XXTEA 加密、session0/16/25 三种会话（session25 带 5 深度分片重组）、自定义 ChaCha20-Poly1305 DTLS 套件，支持 7 个旧型号。MISS 协议补了双向语音、PTZ 云台、电池设备 RPC 唤醒、画质 auto/hd/sd 选择。

还债清单

  • 格子协议自动选择：按每路编码和浏览器解码能力自动选协议，运行时降级链 webrtc→flv→hls→mjpeg，全失败转静态快照；ONVIF 全自动化顺带关了 4 个历史 issue（元数据持久化、真实流测试、按分辨率选 Profile、Hikvision digest 时间偏移）。
  • 数据修复 CLI：repair duration 修正 duration=0（FastProbeDuration 只读 stts box，比全解析快 100 倍——4285 个片段 30 分钟修完，原估要 10+ 小时）、repair merge-status、repair fragments 清理永远无法合并的死段。
  • golangci-lint v2 全面规范化，修掉一批数据竞争，Go/npm 依赖全部升到最新。
  • 跨模块修复：摄像头 start 接口把 HTTP 请求的 ctx 传进 recorder，响应一返回 ctx 取消、recorder 直接退出——「启动了又马上停」；合并窗口时区偏移；时间线 2000 条上限截断（提到 10000）；添加摄像头只按 ID 去重导致同一设备重复注册（生产环境攒了 777MB 冗余视频），改为 endpoint + stable_id 双重去重。

公告也放在这版：v0.9.0 是自 v0.1.0 以来最后一个稳定兼容版本，下一个大版本会有破坏性变更（迁移路径精确给出，不静默破坏）；要长期稳定可锁定 v0.9.x。

v0.9.1 补丁

发布次日跟进，四件事：

  • i18n：脚本交叉比对代码引用和翻译字典，发现 19 个被引用但字典里没有的 key——用户在界面上看到的是原始 key 名；转推配置整段硬编码英文，补 14 个 key。en/zh 字典 1341→1377，parity 校验 0 缺失。
  • 录像碎片：MP4 muxer 在分段关闭前把所有样本驻留内存，分段越长内存越高。按可用 RAM 设上限：≤2GB 封顶 30 秒，>2GB 封顶 2 分钟，碎片数量直接减半；新增周期回填（默认 10 分钟一批 500 条），历史 pending 不再重新累积。
  • 社区 bug：TUTK 已支持但添加预检没同步更新，仍标记不兼容把用户挡在外面；群晖 9090 端口冲突补文档；「合并策略使用全局默认」点了没生效——DELETE 走的 Upsert 用 COALESCE 保留原值，传 nil 等于 no-op，新增 ClearCameraMerge 真正清空。
  • 文档审计：全部公开文档过了一轮准确性校准（9 CRITICAL + 3 MODERATE + 1 MINOR，18 个文件）。有代表性的：双向音频的协议支持写反了（文档说仅 CS2，实际仅 TUTK）；timelapse 文档在描述一个不存在的合并窗口能力——8h/24h/7d/30d 这些值实际被静默 clamp 到 1h；Prometheus 指标名写错。README 定位也从「树莓派专属」改成跨平台轻量 NVR——项目实际早就跑在 x86、Banana Pi、群晖上了。

v0.10.0：H.265 全链路与架构清理

v0.10.0-preview.1（07-28）是自 0.8.0 以来最大的一次发版，主题不是加功能，是把底层清干净。v0.9 预告的破坏性变更在这版兑现——全部列明、给迁移步骤、不静默破坏。注意这是 preview 版，不建议生产使用。

H.265 全链路

0.9.x 的 H.265 是半成品：直播依赖 WebCodecs，而 WebCodecs 要求 HTTPS secure context，局域网裸 HTTP 放不出来；合并产物在 Edge 上经常黑屏；延时合并不工作。这版端到端修通。

直播侧引入 @yume-chan/libde265 WASM 解码器，纯 HTTP 也能播。前端自动探测：HTTPS 优先 WebCodecs 拿硬件加速，不可用回退 WASM 软解——两条路都通到播放器，没有「播不了」这个出口。

ok 是稳定运行 30 秒以上；degraded 检测到解码异常但先观察 8 秒防抖，不立刻切协议；failed 确认挂了，降级到候选链下一个协议——webrtc → flv → hls → mjpeg 依次试，全部失败转静态快照。8 秒防抖是踩坑调出来的：太短被瞬时网络抖动误触发，太长用户盯着卡画面干等。

链路其余是时序和数据一致性问题：编码探测结果双写 YAML + DB（probe once, persist forever），不再每次启动重探——探测结果和实际流编码不一致会出现黑屏和协议风暴；SPS/PPS/VPS 捕获挪到录制判定之前（live-only 模式此前永远抓不到参数集，回放黑屏）；回放按运行时编码 + MSE 探测路由，H.265 强制走 WASM 不误走 MSE；延时合并修了 hvcC box 的 numNalus 并改用保守的 Main-tier 默认值（解决 Edge HEVC 扩展拒绝播放），周期合并正确区分 H.265/H.264 帧——之前只收集 JPEG，H.265 相机的延时合并必然失败。

Timelapse v3

v0.7 的重写去掉了 FFmpeg，但合并窗口的 1h 硬上限还在——8h/24h/30d 这些值被静默 clamp，v0.9.1 审计时确认文档描述的是一个不存在的能力。v3 真正解禁：natural-day/8h/12h/24h/7d/30d 全部生效，默认值从 1h 改成 natural-day（本地午夜对齐）。新增 timelapse_merges 表（schema v29），每个合并产物有完整 DB 记录（相机、窗口、时长、codec、帧数、状态），前端通过 merges API 发现、播放、删除。周期合并折叠中间产物（默认不保留，每天每相机省约 1.5GB）；响应带 X-Timelapse-Codec 头，前端按编码选播放器——H.264/H.265 用 <video>，MJPEG 用帧轮播。

MJPEG、WebRTC 与认证

ESP32 这类 MJPEG 相机原来走 HTTP 轮询，每帧一个请求，延迟和连接数都下不来。改成 WebSocket 流式单连接推帧，两头同时降。WebRTC 加了 streaming.webrtc.ice_servers 配置（STUN/TURN 列表），配上就能跨网访问，不再限局域网。认证换成 HMAC 签名的无状态 token——不占服务器会话内存，过期可控，这也是给 sidecar 架构做的准备。

架构大清理

重构集中在三处，运行时行为零变化：

  • config 按子系统拆文件（camera/merge/timelapse/transcoding/streaming/health/ai/server），入口只管加载拼装
  • DI 组合根拆出 helpers 和 router，只做「把谁注入给谁」
  • API 路由从单一 god-method 改为按领域注册，端点零丢失

拆分改变的是「加新东西要动哪里」：以前加新协议要在巨大的 config 里找位置、在 god-method 里塞端点；现在改动收敛在自己的子系统里。这是 sidecar 路线能推进的前提。

配套工程：API gzip（体积降一个数量级）+ ETag + view=summary 轻量端点 + 录像列表 limit（默认 50 / 最大 500），grid 轮询流量大降；录像页移除 gallery 视图（v0.9 预告过，时间轴和列表视图加强覆盖）；TUTK 的一套 ChaCha20-Poly1305 DTLS 实现确认零引用后整段删除——死代码不清理，后面接 sidecar 协议适配层就会踩到；CI flake 根治（goroutine 生命周期管理），全量 go test ./... 第一次做到一次性 0 失败。

AI 检测的 INVALID_PROTOBUF 花了最多时间：最初怀疑 CDN 截断模型下载，真根因是 streaming-gzip 中间件给二进制响应追加了错误的 gzip trailer——ONNX 模型是二进制 protobuf，被中间件「补全」坏。修复四层防御：中间件对二进制 content-type 不 gzip；下载层 retry + Range 请求 + 原子写；Docker 镜像预置模型，运行时不再下载；前端缓存检测到损坏自动重下。模型分发和完整性校验正是 sidecar AI 的核心问题，这层防御是基础。

稳定性修复挑几个：删录像时同步删合并产物（以前泄漏在磁盘上），repair reclaim-orphan-merges 清理历史泄漏（--dry-run 先看能回收多少，20ms 删除间隔对 USB 硬盘友好）；启动扫描异步化，8 分钟阻塞变 8 秒启动；合并回填积压排空 8500+ pending。

破坏性变更

  • 组合协议串（rtsp_h264、http_jpeg 等）启动时硬错误拒绝，必须拆成 protocol + encoding 两字段
  • DB schema v28→v29（迁移前自动备份到 <db>.pre-v29-backup）；v0.9.x 以下不能直升
  • /api/timelapse/{id}/thumbnail、/preview 移除，换 /api/timelapse/merges 系列
  • 默认值变化：磁盘清理阈值 95→85（避开 HDD 90% 满后的性能悬崖），合并窗口默认 natural-day

完整迁移步骤在仓库 docs/ 的升级指南（中英双语）。

Sidecar AI 方向

架构清理不是为清理而清理。NVR 往下走两个方向：更强的 AI 能力（更复杂的检测、多模态推理、事件触发），更多的摄像头（更多协议、更多厂商）。共同约束是 AI 推理和协议适配不能拖累视频管线——录像、直播、合并必须保持稳定低延迟。

主进程保持轻量稳定，AI 推理和协议适配以独立 sidecar 挂载——可以独立升级、独立崩溃不影响主进程，新接一个厂商私有协议加一个 sidecar 就行。帧总线走高吞吐数据流（共享内存或 Unix Domain Socket），控制/健康通道走配置下发和指标上报，两条通道 QoS 要求不同，物理分开。sidecar 的通信协议和部署形态在后续专题展开，这版先把主进程的领域边界打清楚。
