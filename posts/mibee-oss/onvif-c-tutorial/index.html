onvif-c 教程：给 ESP32 固件装上 ONVIF 设备端

October 3, 2026 MiBeeOSS C, ONVIF, ESP32, 监控摄像头, 开源 MiBee 开源项目实践系列 4543 字 10 分钟阅读
🔊

onvif-c 是五个协议库里最「物理」的一个：ESP-IDF 上的 plain C ONVIF 设备端组件，约 10KB 代码足迹、零第三方依赖。ESP32 相机固件想被 NVR 发现、读设备信息、拿到流地址、上报移动侦测事件，加这一个组件就够了。它没有 XML 解析器——动作识别用 strstr()，响应用 snprintf() 拼——内存模型简单到从传感器回调上下文里调用也安全。四个 MiBee 相机固件仓随固件同步携带它，库的改动先在真机上过一遍再发布。

客户端一侧不用这个组件：连相机用 onvif-go 或 onvif-device-rs，这篇全讲设备端。

#include "onvif_c.h"
#include "esp_http_server.h"

static httpd_handle_t s_httpd;

static const char *my_ip(void)
{
    static char         ip[16] = "0.0.0.0";
    esp_netif_ip_info_t info;
    esp_netif_t        *sta = esp_netif_get_handle_from_ifkey("WIFI_STA_DEF");
    if (sta && esp_netif_get_ip_info(sta, &info) == ESP_OK) {
        snprintf(ip, sizeof(ip), IPSTR, IP2STR(&info.ip));
    }
    return ip;
}

static const char *my_stream_uri(void)
{
    static char uri[64];
    snprintf(uri, sizeof(uri), "http://%s:81/stream", my_ip());
    return uri;
}

static bool my_events_gate(void)
{
    return true;
}

void app_main(void)
{
    /* ... 先起 WiFi 和 esp_http_server（s_httpd = ...）... */

    const onvif_c_config_t cfg = {
        .manufacturer     = "MiBee",
        .model            = "MiBeeCam",
        .hardware_id      = "ESP32-S3",
        .firmware_version = "v0.1.0",
        .serial           = "aabbccddeeff",
        .uuid             = "f472b01e-0000-1000-8000-aabbccddeeff",
        .ip               = my_ip,
        .stream_uri       = my_stream_uri,
        .events_enabled   = my_events_gate,
        .mdns_hostname    = "mibeecam-demo",
    };
    onvif_c_start(s_httpd, &cfg);
}

逐段说：

  • onvif_c_start 往现成的 httpd 上挂路由（/onvif/device_service、/onvif/media_service，开了事件再加 /onvif/events_service），并启动 WS-Discovery 应答任务。它要求 httpd 已经 httpd_start 过。
  • serial、uuid、ip、stream_uri 四个回调是必填的，缺一个 onvif_c_start 返回 ESP_ERR_INVALID_ARG。ip 回调在 WiFi 没连上时返回 NULL 或 "0.0.0.0"，各服务会自己重试，不用你通知。
  • 字符串是按引用收的，不拷贝——头文件原话是 “must outlive onvif_c_start”。像示例那样用静态缓冲或字面量，别传栈上临时变量。
  • uuid 不带 urn:uuid: 前缀；它同时是 WS-Discovery 里的设备 UUID，NVR 靠它记住设备，写死一个比每次随机生成好。
  • 板级差异全部收在这一个结构里：厂商、型号、IP、流地址、HTTP 端口、事件开关，库内零硬编码。

#include "esp_mac.h"

static char s_serial[13];
static char s_uuid[37];

static const char *my_serial(void)
{
    if (s_serial[0] == '\0') {
        uint8_t mac[6] = {0};
        esp_read_mac(mac, ESP_MAC_WIFI_STA);
        snprintf(s_serial, sizeof(s_serial), "%02x%02x%02x%02x%02x%02x",
                 mac[0], mac[1], mac[2], mac[3], mac[4], mac[5]);
    }
    return s_serial;
}

static const char *my_uuid(void)
{
    if (s_uuid[0] == '\0') {
        uint8_t mac[6] = {0};
        esp_read_mac(mac, ESP_MAC_WIFI_STA);
        // 由 MAC 确定性派生，重点在"每次开机相同"
        snprintf(s_uuid, sizeof(s_uuid),
                 "f472b01e-0000-1000-8000-%02x%02x%02x%02x%02x%02x",
                 mac[0], mac[1], mac[2], mac[3], mac[4], mac[5]);
    }
    return s_uuid;
}

流地址回调跟着你的实际服务走——固件用 RTSP 就回 rtsp://<ip>:554/stream，用 MJPEG over HTTP 就回 http://<ip>:81/stream。真实移植层的参考是 esp32s3-n16r8-cam 固件的 main/onvif_port.c，约百行：身份取自 MAC/efuse、IP 取自 WiFi 管理、流地址取自 RTSP 服务、事件闸门读配置。

库在链路里的位置

mermaid

    NVR -->|"UDP 3702"| DISC["发现任务<br/>Probe / Hello"]
    HTTPD --> LIB["onvif-c<br/>strstr / snprintf"]
    DISC --> LIB
    LIB -->|"回调取值"| FW["固件移植层<br/>约百行"]

    classDef nvr fill:#E3F2FD,stroke:#1565C0,color:#1565C0
    classDef lib fill:#F3E5F5,stroke:#9C27B0,color:#6A1B9A
    classDef fw fill:#E8F5E9,stroke:#2E7D32,color:#1B5E20
    class NVR nvr
    class HTTPD,DISC,LIB lib
    class FW fw

NVR 走两条路进来：UDP 3702 上的 WS-Discovery（答 Probe，每 30 秒左右发一次 Hello），和 HTTP 上的 SOAP 动作请求。库收到请求用 strstr() 认出动作，需要数据时回调移植层（IP、流地址这些现取现答），响应体用 snprintf() 拼好交回 esp_http_server。每请求独立缓冲，没有动态状态。

事件：一行注入

移动事件的上报就一个函数：

c
1

onvif_c_motion(true, 87);   /* MotionAlarm State=true  Score=87 */

它可以在传感器或 CSI 回调上下文里直接调——永不阻塞（锁竞争时丢弃事件）、没有 I/O，事件只在「有存活的 Pull-Point 订阅且 events_enabled 闸门返回 true」时才入队。没订阅就调它，等于空操作。放进检测任务里就是：

void motion_task(void *arg)
{
    for (;;) {
        if (read_pir_or_motion_detector()) {
            onvif_c_motion(true, 87);          /* 87 换成你自己的打分 */
        } else {
            onvif_c_motion(false, 0);          /* 恢复也要报，NVR 好消警 */
        }
        vTaskDelay(pdMS_TO_TICKS(1000));
    }
}

订阅模型有三个值要知道：单订阅，新订阅顶掉旧订阅（两台 NVR 同时订同一台相机会互相顶）；授予时长 1 小时，空闲 120 秒过期，靠 NVR 的 Renew 续约；PullMessages 立即返回、不长轮询——esp_http_server 的 worker 永不阻塞，这是 IDF 线程模型里的硬约束，不是偷懒。诊断口 onvif_c_events_subscribed() 报当前有没有存活的订阅，可以拿它做「NVR 在不在看」的联动（没人订阅就跳过高成本检测）。

发现与看门狗

WS-Discovery 应答器在 UDP 3702 组播上答 Probe，周期性发 Hello，socket 或组播成员关系没就绪时一直重试直到 WiFi 起来。wdt_watch_discovery 是可选项：把发现任务挂到 esp_task_wdt——发现循环自带 5 秒接收超时节拍，任务卡死时停止喂狗、看门狗触发。宿主工程先初始化看门狗，再打开开关：

验收：onvif_probe.py

验收不用插 NVR：tools/onvif_probe.py 从笔记本直接跑完整冒烟测试。

console
1

python tools/onvif_probe.py 192.168.1.123 15

它把六个动作全打一遍（GetSystemDateAndTime / GetDeviceInformation / GetCapabilities / GetProfiles / GetStreamUri / GetSnapshotUri），再做一轮完整的事件订阅周期（CreatePullPointSubscription → PullMessages 循环 → Renew → Unsubscribe），进度逐行人读，最后一行输出机器可读 JSON：

json
1
2

{"ip": "192.168.1.123", "checks": {"GetSystemDateAndTime": true, "...": true},
 "pulls": 15, "errors": [], "events": 0, "all_required": true}

退出码 0 表示全部必测动作应答正常，2 表示创建或首调失败；事件服务缺席不算失败（对应没开事件的固件）。把它接进 CI 或产测脚本，每次烧录后自动验一遍 ONVIF 面。

内存与线程模型

为什么敢在传感器回调里调 onvif_c_motion：组件内没有动态分配、没有跨线程锁持有——核心三个文件（XML 应答、Probe 应答、事件环形缓冲）是纯 C 无 ESP-IDF 依赖，请求级缓冲用完即还；esp_idf/ 一层只是把 SOAP 挂到 esp_http_server、把发现跑成独立任务。这也是它能同时伺候多个 NVR 轮询而不抖的原因：每个请求独立拼包，互不共享状态。

两套信封前缀方言是刻意的：Device/Media 信封用 soap:/tds:/trt:/tt:（小写 utf-8 声明），Events 信封用 s:/tev:/wsnt:（大写 UTF-8）——各自都是真实 NVR 在生产里对话过的字节，对接方若问起，答案在 README 里：不要「统一」它们。

生产项目里的用法

这个组件本身就诞生在生产里：从 MiBee Cam 固件抽出、四个 ESP32 相机固件仓 vendor 它随固件同步携带，库的改动先在真机上过一遍再发布。对它做集成验收时，任何商用 NVR 或 ONVIF Device Manager 都能当消费方。按功能对照：

功能生产项目用法
基础集成 / vendoresp32s3-n16r8-cam · seeed-esp32s3-cam · luatos-esp32s3-a10-camera · ai-thinker-esp32-cam四个板型的固件都带着它，NVR 接入 ESP32 相机的全部 ONVIF 面由它应答
移植层esp32s3-n16r8-cammain/onvif_port.c 约 100 行参考实现：MAC/efuse 身份、WiFi 管理器的 IP、RTSP 服务的流地址、配置闸门
移动事件注入esp32s3-n16r8-cam · ai-thinker-esp32-cam人脸/移动检测出分喂 onvif_c_motion，NVR 那头收 MotionAlarm
流地址接驳各固件RTSP 固件（esp32s3-n16r8-cam 带 digest 认证的 RTSP server）回 rtsp:// 地址，MJPEG 固件回 http://…/stream

看完整实现从 esp32s3-n16r8-cam 入手——它的板子资源最全（ESP32-S3 加 OV3660），onvif_port.c 就是本篇移植层一节的出处；其余三个仓是同一组件在不同约束下的形态：ai-thinker-esp32-cam 是经典 ESP32 加 OV2640 的最紧资源版本，seeed-esp32s3-cam 的 RTSP 带 G.711 音频，luatos-esp32s3-a10-camera 在无 PSRAM 的单芯片上跑。同一组件四处移植、四种约束，正说明配置接缝收得干净。

排错清单

现象原因处理
onvif_c_start 返回 ESP_ERR_INVALID_ARG四个必填回调缺一补齐 serial/uuid/ip/stream_uri
NVR 能发现但读到的地址不对http_port 没流进 XAddr/订阅地址填真实的 esp_http_server 端口
设备重启后 NVR 里出现重复设备UUID 每次随机生成由 MAC 派生固定 uuid
带凭据的 NVR 拒绝添加设备组件没有认证流程，谁到端口都能应答部署在可信内网或反向代理后面；需要认证就换带 WS-Security 的设备端
事件时有时无没订阅、闸门关着，或被另一台 NVR 顶掉单订阅语义；查 onvif_c_events_subscribed() 和闸门回调
字符串内容显示异常传了栈上临时变量，字符串已被回收字符串按引用收，必须活得比服务久
烧录后 ONVIF 面异常回调返回了错误数据onvif_probe.py 逐动作定位，JSON 里 errors 有明细
对接方要「统一」两套命名空间前缀Device/Media 用 soap:/tds:/trt:/tt:，Events 用 s:/tev:/wsnt:别统一——两套各自是真实 NVR 在生产里对话过的字节，README 明说
