MiBeeSteward：从 v0.1.0 到 v0.5.0

July 5, 2026 September 20, 2026 MiBeeOSS Go, 设备管理, 网络发现, SNMP, 分布式, OpenWrt, 开源 MiBee 开源项目实践系列 8329 字 17 分钟阅读
🔊

MiBeeSteward 是我给自己工作室写的设备管理与监控系统：一个 Go 二进制，把网络设备的发现、分类、监控、管理串成一条线。2026 年 7 月 5 日发 v0.1.0，8 月 20 日到 v0.5.0，五个版本把「单网段扫描器」演进成「能过企业审计的分布式系统」。之前每个版本单独成篇，这篇把 v0.1.0 到 v0.5.0 的发布记录按时间线合并改写成一篇。

为什么自己写

做工作室运维，最头疼的不是某个具体问题，而是设备多起来之后的「不知道」：哪个设备还活着、上面跑了什么服务、网络里什么时候多了台新机器。这种「不知道」积累到最后就是故障。

之前的方案是拼凑的：Zabbix 做监控，Nmap 扫网络，Excel 记资产，Prometheus 看指标。每个工具单独看都不错，合在一起就是数据孤岛、重复配置、部署复杂。于是用 Go 重写了一个，目标是单二进制、零外部依赖（纯 Go + modernc.org/sqlite，CGO-free）、下载就能跑、ARM64 优先——树莓派和小主机无压力。

技术栈上没什么冷门选型：Chi 路由、sqlc 生成查询、koanf 配置、JWT 认证；前端 SvelteKit 5 + Tailwind 4 + ECharts，编译产物经 go:embed 塞进二进制；SNMP/ICMP/TCP/HTTP 探测原生实现；eBPF 走 cilium/ebpf，可选编译标签，默认构建零依赖。

定位要说清楚：它不是 NVR，也不是告警平台，核心是回答「网络里发生了什么」。和现有工具的关系可以一句话说清——NetBox 是资产管理数据库，不关心设备在不在线；Zabbix/Nagios 是重型监控平台，一个完整部署要数据库、Web、代理一堆组件；Nmap 输出一条开放端口的线，业务含义要自己理解；Prometheus 生态里 node_exporter 只暴露指标，「哪些设备该被监控」没人回答。MiBeeSteward 把这几块各取一部分揉在一个二进制里，用「还活着吗」做核心，资产管理是副产品。要录像用同工作室的 MiBeeNvr，要告警接 Alertmanager。

v0.1.0 的底子：探测、扫描与指纹

探测子系统

「定期问一声还活着没」是最基础的能力。四种探测（ICMP/TCP/HTTP/SNMP）统一实现 Prober 接口，装饰器提供指数退避重试（1s→2s→4s），三振出局：连续 3 次失败才标离线，恢复自动上线，网络抖动不误报。

Scanner v2：扫描之后自动识别

这是最独特的一块。传统工具分两类：扫描器（Nmap）只做端口扫描不关心业务含义，监控类（Zabbix）假设你已经知道要监控什么。Scanner v2 填这个缝——五层插件架构（Probe 探测 → Classifier 分类 → ServiceHandler 深度采集 → Persistence 持久化 → Orchestrator 编排），扫描之后自动把「开放端口」翻译成「这台是海康摄像头，跑着 RTSP 和 ONVIF」。

开箱即识别的服务：

分类器探测方式识别目标附带信息
SSHTCP 端口 + 特征字节SSH 服务版本号
HTTPHTTP GET 响应Web 服务 / APIServer 头、页面标题
RTSPTCP 端口 + 协议握手摄像头/视频流支持的方法集

分类器支持级联深度采集——发现 HTTP 后自动去扫 /metrics，发现 Prometheus 端点后自动检测 node_exporter 并解析主机信息，扫一个发现一串：

eBPF 被动观测与 Prometheus 集成

eBPF 被动观测是实验特性（make build-with-ebpf，需内核 BTF ≥ 5.8）：TC ingress 程序挂网卡上，嗅 ONVIF WS-Discovery 组播和 TCP 特征字节，作为主动探测的旁证（置信度 0.6）。思路的价值在「只看不说」——对主动探测敏感的环境（工控、医疗），被动嗅探不产生任何流量。

Prometheus 集成是原生方向而非上报：/metrics 暴露自身指标，/sd 作为 HTTP 服务发现输出全部设备，/api/v1/dashboard/query 只读代理查已有 Prometheus。可以直接扔进现有 Prometheus + Grafana 体系，不需要额外 exporter。

v0.2.0：分布式发现与变更检测

v0.1.0 有两个明显短板：center 只能看见自己所在的 LAN，而工作室的真实情况是办公室、机房、家里各一个网段；而且它只记录状态，不告诉你变了什么——新接的 NAS、换 IP 的树莓派全淹没在设备列表里。v0.2.0（07-13）冲着这两个痛点来。

center + agent，过 NAT 的 pull 模型

新增 mibee-agent 二进制：跑在远程 LAN 里，用和 center 一样的 scannerv2 引擎扫本地，把结果汇报给 center。协议选 push 报告 + pull 命令的混合模型，agent 是唯一主动方，center 不开任何 inbound 端口——agent 出站 HTTPS 即可，跨 NAT 场景防火墙一个洞都不用打。

mermaid
sequenceDiagram
    participant A as mibee-agent
    participant C as center
    A->>C: POST /agents/report<br/>(存活设备 + 状态哈希)
    C-->>A: 200 OK
    loop 每 60s 轮询
        A->>C: GET /agents/commands
        C-->>A: 待执行命令(可空)
        A->>C: POST /commands/{id}/ack
        Note over A: 执行扫描<br/>硬截止 15min
        A->>C: POST /commands/{id}/complete
    end
    Note over A,C: center 宕机时<br/>backfill 队列(cap=100) 有序重投

report 信道每 30 秒推一次存活设备，command 信道每 60 秒拉一次临时扫描命令。两个工程细节是踩坑换来的：agent 触发的扫描有 15 分钟硬截止——没有截止时间的话，一次卡住的 TCP read 会把命令永远钉在「已确认」状态，agent 看着活着实际不干活；center 宕机期间 agent 的报告压进容量 100 的内存队列，恢复后有序重投，短时重启不让任何网段失联。

反熵哈希快路径

安静网段每 30 秒的报告内容和上次完全一样，center 每次都跑一遍 device bridge（指纹分类、推断、写库）就是在反复算同一道题。解法：每次上报带 X-Network-State-Hash（存活设备集的标识 + 分类字段做 SHA-256），center 比对——一致就只刷新租约时间戳，不一致才逐台过 bridge。哈希只覆盖「变了才算真变了」的字段，RTT、last_seen 这类天然会变的字段不进哈希，否则快路径永远失效。这个设计借鉴 Dynamo 风格的反熵但大幅简化：真相只在 agent 一侧，center 不需要合并副本，只需要决定「要不要重算」，一个哈希比对就够。

双轨掉线判定

center 自管网段用连续扫描判定：每轮没出现的设备 miss_count +1，连续 2 轮 miss 才标掉线。agent 管管网段用租约判定：每次上报刷新租约（TTL 5 分钟），后台 LeaseSweeper 每 60 秒扫一遍，过期即掉线——按 30 秒上报间隔，约连续 10 次漏报才判掉线。不统一是因为信号源不同：自扫的信号是「这一轮扫到了没」，天然离散逐轮；上报的信号是「最后一次见到是什么时候」，agent 整段静默时没有「轮」的概念，硬套 miss_count 会傻等下一轮。两条路径写同一张表、发同一个 device_lost 事件，上层无感。

变更检测与被动发现

变更引擎是 center 进程内的 Watcher，三类事件落 change_log：device_added（新设备）、device_changed（身份字段变了）、device_lost（掉线）。device_changed 跟踪 12 个字段（名称、类型、品牌、型号、MAC、IP、状态、开放端口、服务、两个 URL、扫描属性），每条事件存结构化 before→after 差异，不是整条快照——查起来直接看到「IP 从 .143 变到 .144」。消费走分页查询、SSE 实时流和 mibee_changes_total 计数器。

被动发现补定时扫描的盲区：两轮扫描之间新上线的设备要等下一轮。三个数据源各自可开关——路由器 SNMP ARP 表（跨子网覆盖最广）、本地 ARP 缓存（读 /proc/net/arp，零流量）、组播监听（mDNS + SSDP，只听不发，能捡到摄像头、打印机、IoT、Mac、UPnP）。

MAC 优先的已知主机预检是关键优化：设备 DHCP 续期从 .143 漂到 .144，靠 MAC 直接认出来，不必触发一轮昂贵的识别扫描。凌晨两点上线的设备也能立刻拿到 device_added 事件。

指纹规则数据化

v0.1.0 的识别规则是 Go 里的 if/switch，加一个签名要改代码重编译。v0.2.0 把规则变成 YAML 数据，启动时由 RuleClassifier 加载——加一条设备签名就是写一条 YAML。开箱约 2554 条：20 条手写 builtin + 约 2534 条从 Rapid7 Recog 语料导入（Apache-2.0，许可证干净；nmap 的 NPSL 许可证不干净，故意不导入）。少数没法声明式表达的逻辑留在 Go 里并有文档说明（SNMP bitmask 启发式、摄像头交叉证据融合、字节偏移分类器）；再加一个 parity 测试断言数据驱动分类器和被替换的手写分类器字节级一致，迁移引入的行为差异 CI 里就挡住。指纹引擎独立成 mibee-fingerprints-go 模块，别的项目可以复用。

这一版还开了 L2 拓扑的头：Bridge-MIB 邻居探测走交换机 FDB 表，搞清哪个 MAC 在哪个端口后面，存进 device_neighbors。探测集从 13 个扩到 15 个，新增 SMB2 Negotiate（解方言和 OS 串）、可靠的 FTP banner、TLS 证书 CN（识别 OpenWrt/GL.iNet/iStoreOS——后者要把证书 CN 和 issuer 组织两个字段联合判定才准）。

v0.3.0：拓扑、证书与容器镜像

v0.3.0（07-18）收三个具体的尾：拓扑画不全、TLS 证书没人管、部署门槛高。

L2 拓扑：为什么需要三个半 MIB

v0.2.0 只靠 Bridge-MIB，跨厂商环境会漏边。补上三个各管一段：

MIB提供合并键
Bridge-MIBMAC↔ifIndex 基础邻接MAC
CDP-MIB厂商邻居身份（device id、平台串、IP）device id
Q-BRIDGE-MIBVLAN-aware MAC→端口MAC
STP-MIB端口角色（root/designated/转发/阻塞）STP port id

合并键不同是关键——三条数据流各自落到 device_neighbors，最后用 MAC 主键加 EnrichDeviceByMAC 把同一台设备在不同协议下的事实合并成一行。IF-MIB 的 ifName 解析把数字 ifIndex 翻译成 GigabitEthernet0/1 这种人能读的名字；CDP/LLDP 邻居的平台串（如 Cisco ISR4321）喂给 RuleClassifier 推断厂商型号，再用 MAC 对上设备表里的已知设备——v0.2.0 里 neighbor_device_id 一直是 NULL，就是这条推断链没接上。前端出整张按类型着色的径向拓扑图，连线按发现协议着色。

TLS 证书清单

从 v0.1.0 起 TLS 服务只抓证书 CN 当指纹用，「证书还有几天过期」答不出来——内网一堆自签证书，过期那天服务突然挂掉。v0.3.0 给 8 个 TLS-wrapped 协议（https/ldaps/smtps/imaps/pop3s/ftps/ircs/telnets，handler 总数 21→29）加了完整证书链采集。实现上是一个 CollectCertChain 核心被 8 个 handler 共享——Go 的 crypto/tls 在 tls.Dial 完成握手，PeerCertificates 直接返回完整链，证书链解析和上层跑什么应用完全无关，共享是自然结果。数据落 host_tls_certs，(ip, port) 索引服务设备详情查询，not_after 索引服务「未来 N 天过期」的巡检扫描。前端状态色：绿=有效、琥珀=15 天内过期、红=已过期。

容器镜像与 netns 保真度

第一次发布官方多架构镜像到 GHCR。三种 compose profile 的取舍背后是这版最硬的工程发现，在 31 台设备的测试 LAN 上实测：

部署形态发现的设备 MAC 数
裸金属31 / 31
docker --network host30 / 31
docker 默认 bridge0 / 26

bridge 模式 MAC 发现数是零，不是 bug，是 network namespace 的物理事实：被动发现要读 /proc/net/arp，而 NAT 容器有独立 netns，它的 ARP 表只有网桥 gateway 一条——容器从没和 LAN 上其他主机直接通信过。

所以 bridge profile 只适合 UI demo，生产扫描用 host（共享宿主 netns，保真度 ≈ 裸金属），macvlan 让容器作为 LAN 设备出现。非特权镜像里 LLDP/CDP raw frame 和 eBPF 是 no-op stub——需要 CAP_NET_RAW 等能力，缺失时降级跳过而不是假装能跑；需要的人 make docker-build-priv 本地构建特权变体。主动探测（TCP/SNMP/TLS/Bridge-MIB）全不依赖 raw socket，host 网络容器已能扫出绝大多数设备。同一个事实也适用于虚拟机：网卡桥接 ≈ 裸金属，NAT 模式发现基本失效——VM 里结果不对，先查网卡模式再查程序。

v0.4.0：路由器常驻发现

容器要 host 网络、物理机要休眠设备认不全，那更彻底的位置是：发现程序本身就跑在网关上。网关是 LAN 流量的必经之路，DHCP 租约、连接表、WiFi 客户端、DNS 查询日志全在它眼皮底下。v0.4.0（07-29）把这四个 Tier-1 本地数据源接了进来（Tier-2 是 v0.2.0 就有的跨设备查询：SNMP ARP、组播监听）：

数据源来源看到什么
dhcp_leases/tmp/dhcp.leases 等发过租约的所有客户端，含已休眠设备
conntrack/proc/net/nf_conntrack此刻正在通信的连接，「谁在线」的实时视图
hostapd客户端列表哪些设备正连在 WiFi 上
dns_logdnsmasq 查询日志设备最近查过哪些域名，识别辅助信号

conntrack 最值得说：ARP 表告诉你「最近通信过」，conntrack 告诉你「现在正在通话」——对在线判定更接近真实。四个源全部 opt-in 且优雅降级：不开不读，开了但文件不存在（比如纯有线网关没跑 hostapd）就自禁用并记日志，不 crash。

OpenWrt 成为一等公民：procd init 脚本（UCI 配置、开机自启、崩溃重启、非特权运行）加 ARMv7 构建目标，覆盖 Flash 只有 16/32MB 的低功耗路由器。四种部署环境的保真度差异一句话总结：先确定 netns 归属和是不是网关，再谈发现保真度——路由器形态 Tier-1 全开零额外流量，物理机 31/31，host 容器 30/31，bridge 容器和 NAT 虚机归零。

底层还修了一个潜伏已久的正确性问题：设备行此前有同步扫描和定时扫描两条独立写入路径，语义不一致，同一台设备可能留下内容冲突的行——这种 bug 取决于哪条路径最后写，极难复现。v0.4.0 确立单一写权威（runner.applyDeviceBridge 成为 device 行生命周期的唯一仲裁者），两条路径留下逐字节相同的行。配套：MAC 相同但 IP 不同时 IP 持有者胜出，身份字段强制覆盖，堵住「换了设备画像还停在旧值」；后台对账任务揪出 IP 漂出登记网段的设备，标记给人工修正不自动改——自动迁移会把「设备真挪了」和「配置写错了」混为一谈。

v0.5.0：企业落地的三件事

到 v0.4.0，这条内网设备管理链路已经完整。把系统带进公司或更严格的环境，会撞上三堵墙：SNMP 只支持到 v2c（明文口令，安全审计过不了，加固环境直接禁用——采集瘫痪）；权限只有 admin/user 两档（多人共用分不清谁能操作、谁只能看）；「这条配置什么时候被谁改的」答不上来。v0.5.0（08-20）逐个拆墙。

SNMPv3

USM 模型，authNoPriv 与 authPriv 两个安全级别：认证升级为用户名 + MD5/SHA/SHA-2，authPriv 下传输加密（AES/DES）。凭据 AES-256-GCM 加密落库，界面永不回显明文。设备身份采集和全部拓扑走查（LLDP/CDP/Bridge/Q-BRIDGE/STP/IF-MIB）在 v3 下功能完整。存量 v1/v2c 部署升级后行为不变；agent 侧 v3 推迟——分布式环境下的凭据分发与轮换需要单独设计。

多角色 RBAC

admin/operator/viewer 三角色，旧 user 升级后自动按 viewer 工作。每条路由挂一个能力，角色映射到能力集；网段授权落在 user_network_grants 表。作用域默认 open（与旧行为一致），设为 closed 后非管理员只见授权网段：

设备配置备份

按计划 SSH 登录路由器、交换机、防火墙，拉运行配置做版本化存储：

厂商命令矩阵：JunOS 用 show configuration | display set，HP/Aruba/H3C/Comware 用 display current-configuration，Cisco IOS/NX-OS、Arista、华为 VRP、Mikrotik 和未知厂商兜底 show running-config；host key 走 TOFU。内容不变不生成新版本，版本列表里每条都是真实变更；变化产生 device_config_changed 事件，进变更检测和通知的处理范围。设备详情页有任意两版本的 diff 对比。SSH 凭据与 SNMPv3 共用同一套 AES-256-GCM 加密。功能默认关闭，真机端到端验证（GL-MT3000）留到下一版。

通知、拨测与时序化

内置通知：按事件类型（掉线/恢复/新增/变更/配置变更）、作用域（全网/网段/单设备）、通道（webhook/邮件）配规则，每条规则对每台设备独立冷却（默认 30 分钟），叠在变更检测自身的冷却之上两层防抖。定位是事件路由不是告警引擎——没有阈值和路由树，要这些仍用 Prometheus 体系。

外网拨测：探测范围从内网延伸到公网端点，http/tcp/icmp 复用心跳探测器，tls 及 https 目标复用 CollectCertChain 采全证书链——到期时间、签发者、TLS 版本与密码套件。引擎 10 秒 tick 重读配置即改即生效，重启后从 last_run_at 恢复不产生启动风暴，全局 8 并发。证书表用 delete-then-insert 保留「上次正常时的链」——一次握手瞬断不该清掉已知良好状态。

存活判定时序化：设备存活此前建模为离散 device_changed 事件，每次翻转写一行，测试网跑一段时间攒了 7 万多行变更日志，真实变更被休眠唤醒的翻转淹没。v0.5.0 把它改成 device_liveness 时序——每设备每 tick 一条判定样本，供在线率、离线时长、历史查询；状态翻转由 liveness 层消费，只留丢失/恢复事件。卫星表改用稳定 device_uuid 作键，IP 变化不再分叉历史。

两次身份层面的修正

MAC U/L 位误判。第一版把 MAC 首字节的 U/L 位（本地分配位）当「随机化 MAC」的判定依据——该位为 1 就身份降级，避免把 iOS/Android 隐私随机地址当稳定身份。按 IEEE 802/RFC 7042，这个位只表示「地址由本地分配」，区分不了「每次重连都变」和「软路由、虚拟化网卡的本地地址（本地分配但长期稳定）」。测试网随即打脸：7 台稳定的软路由和 NAS 被误判为随机化，一台 R68s 因身份降级被拆到两个网段。修正：身份降级整体撤销，回到 MAC 优先；该位保留为纯观测标志，字段改名 mac_is_locally_administered，UI 标签同步改。一个二进制位承载不了「随机化」这么重的语义。

OUI 最长前缀匹配。OUI 厂商查询按最长前缀走三档 IEEE 注册表：MA-S（/36，9 位十六进制）、MA-M（/28，7 位）、MA-L（/24，6 位）。必须最长前缀：MA-S/MA-M 子块是从其他厂商的 /24 OUI 中划出再指派给另一家的，不做最长匹配，8C1F64B14 开头的 MAC 会被标成「IEEE Registration Authority」（/24 块的注册者），实际属于 Murata（/36 子块受让人）。新增 oui_prefix 和 oui_vendor 字段与既有 vendor（设备自报品牌）分开——OEM、贴牌、虚拟化场景下两者不同。顺带修了一个既有错误：OUI 下载域名原来写的是 standardeee.org，正确的是 standards-oui.ieee.org，旧脚本一直在从非权威副本下载。
