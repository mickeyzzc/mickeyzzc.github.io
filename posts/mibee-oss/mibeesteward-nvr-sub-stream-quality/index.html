MiBeeNvr 的子码流体系：让手机看监控不卡不烫

November 13, 2026 November 26, 2026 MiBeeOSS 流媒体, HLS, WebSocket, 开源 MiBee 项目实践系列 4319 字 9 分钟阅读
🔊

手机上看监控最烦的两件事：发烫、卡顿。多画面监控页一次开四五路，每路都在收高分辨率的主码流，手机一边解码一边收包，电池掉得肉眼可见，画面还一顿一顿。多数人第一反应是换手机或者把 WiFi 切到 5G，其实瓶颈不在网络，在送过来的那一路流本身。

摄像头一般不止输出一路：高分辨率的主码流用于录像，另有一路低分辨率低码率的子码流，原本就是给预览用的。MiBeeNvr 把子码流做成按需拉取的一等公民——谁要看，谁触发拉取；没人看，子码流连接自己停掉。录像永远走主码流，和预览彻底分开。

要定的有两件事：谁决定这一刻送哪一路，客户端又怎么知道自己拿到的是哪一路。开源 NVR、转流网关和商业系统在这两件事上做法不同，差别在工程代价。

代价谁在付

没有按需子码流时，预览只能跟着录像那一路主码流走，看的人替这路流付全部代价：带宽按主码流的码率走，解码按主码流的分辨率算。多路同看时这些代价直接乘以路数，发热和掉帧就是这么来的。

现在多了一层分流。多画面监控页顶部的 流畅 / 高清 切换默认 流畅；单路直播页按摄像头给画质开关；GB28181 级联上报也能按摄像头切到子码流，上级平台预览不再吃满上行带宽；外部 AI 分析消费子流切片，解码成本大约是主流的 1/4~1/16。这些消费方共用同一个前提：录像那一路主码流不动。

代价转移到 NVR 侧的一路额外 RTSP 拉取，相机侧也跟着多一条连接；这路拉取只在有人要子流的时候存在。

按需拉取

子码流的生命周期由引用计数管着。每个要看子流的端点在建立连接时调用 Acquire，refs 加一；断开时 Release，refs 减一。计数归零不立刻停拉，而是挂一个默认 30 秒的空闲定时器；期间再有 Acquire 进来就取消定时器、继续复用同一路拉取。定时器真的走到时才停掉 RTSP 拉取、删除 source，并回调 onRecycle 让上层取消订阅。

这里有个容易忽略的细节：回收发生在定时器回调里，真正的拆除被丢到独立 goroutine，回调里还要再看一眼 refs——如果这间隙有人重新 Acquire，就保留现有 source，不杀掉一次刚建立的新引用。代码里叫 same-hub identity guard。WebRTC WHEP 的引用是会话级的（SetOnSessionEnd），会话结束才释放。

图里把一次观看的来回走完：请求进来先加引用，已有引用就直接接入；首次 Acquire 触发 RTSP 拉取并发布到 StreamHub(camid/sub)；断开减引用，归零后空闲 30 秒才回收。录像那一路的 hub 不在图里，它和这条链路没有引用关系。

几个超时都能在配置里查到：idle_timeout_s 默认 30，ready_timeout_s 默认 8（典型 RTSP 连接加首个关键帧是 1~4 秒）；拨号每次 5 秒，失败按退避重试到 ready 超时；流中断 15 秒没帧就重连。子流目标可以手填 RTSP 地址，也可以用 ONVIF 子流 profile token（留空自动发现，取主 profile 之外分辨率次高的那个）。ONVIF 的元数据可能不实——标着 H.264 实际给 H.265——所以 NVR 以 RTSP DESCRIBE 的实探为准。

四路可选

四个直播端点都能要子流，但写法不一样：

端点子流请求
WebSocketstream/ws?quality=sub
HTTP-FLVstream.flv?quality=sub
HLS路径式 .../stream/sub/index.m3u8
WebRTC (WHEP)POST .../stream/webrtc?quality=sub

HLS 走路径而不是 query，原因是分片用相对地址寻址，query 没法跟着每个分片走。路径里的 sub 段就是资源身份的一部分；index.m3u8 是多变体播放列表名，stream.m3u8 和 playlist.m3u8 是兼容别名，其他名字返回 404 而不是空列表。低延迟 HLS 默认开，列表里带 #EXT-X-PART 分片。

WHEP 这里是硬限制：WebRTC 只承载 H.264，子流是 H.265 就只能回退主码流；子流确实是 H.264 时才建立真正的子流会话。

前端还有一道防黑屏的判断。effectiveQuality() 只在已知子流编码是 H.264、或浏览器能通过 MSE 解 H.265 时才请求 sub；编码未知先给 main，切换画质时重新挂载播放器。/protocols 回报 sub_stream 的 available / source / reason / codec，消费方必须响应式读取——只读一次会把画质钉死在主码流上。

这四种写法都是请求，不是承诺。服务端拿到请求后还要过一遍本地事实：子流有没有配、拉没拉起来、编码浏览器能不能解。决定权在服务端，客户端只能事后知道结果。

业界的画质协商

Frigate 和 go2rtc 把同一件事拆成了两层：传输层先协商能力，客户端再记自己的偏好。按 Frigate 官方 live 文档，直播有三种技术——jsmpeg、MSE、WebRTC——按网络带宽、播放器报错和是否需要双向语音切换。jsmpeg 不依赖 go2rtc，但只出 detect 那一路的低分辨率、无音频画面；配了 go2rtc 默认走 MSE；WebRTC 要显式开启，多在 MSE 失败或用双向语音时启用。

同一份文档里的 smart streaming 省的是另一部分带宽：没有可检测的活动时不推实时流，只按极低频率刷新一张静态图（当前文档写的是每分钟一帧，早期版本是每秒一帧），有动静再无缝切回实时流。它省的是「没人看的时候」，子码流省的是「有人在看但要轻量」，两者的前提不一样。

画质选择放在 UI 里，按设备、按摄像头存在浏览器 localStorage。streams 列表下拉里除了主码流和子码流还有一个 Auto 档：从第一条开始，连接跟不上就往列表下退，恢复了再往上走；想立刻试回最高档，另有单独的 Try highest quality。WebRTC 也不是永远可选——连不上、编解码不支持、浏览器不支持时，选项在 UI 里置灰，旁边写原因，详细原因进浏览器控制台；不可用时自动回到 MSE 或 jsmpeg。这里的状态在客户端：换一台设备、换一个浏览器，选择不跟着走。

go2rtc README 把这件事做得更底层。同一路流可以配多个源——一条 RTSP 原流加一条 FFmpeg 转码源——跨所有源替浏览器做 codec 匹配，文档叫 multi-source two-way codec negotiation。URL 上还能直接写 codecs filter，例如 ?video=h264,h265&audio=aac，只从已有源里挑，不新造 codec；要新 codec 就交给 FFmpeg，README 明说没有在 go2rtc 内嵌复杂转码的计划。它的 codecs-madness 表把 H.265 的碎片化列得很直白：Chrome 136+ 和 Safari 18+ 才在 WebRTC 里支持 H.265，Firefox 只有 H.264，iPhone Safari 14 没有 MSE 但有 HLS，桌面 Safari 不吃 HTTP progressive 流。

Frigate 的 go2rtc 文档还给了 restream 的另一个用途：让 record、detect、live 从同一条 restream 取流，减少连到相机的连接数。相机对并发连接有限制时，这一条比画质切换更实际。MiBeeNvr 没有这么做——录像和预览本来就是两条独立的 RTSP 拉取，预览各端点之间才用 refcount 共用一条子流拉取。共用范围窄，但录像链路完全不被预览牵动。

MiBeeNvr 也不做传输层的 codec 协商，不替浏览器记偏好。它只维护一个事实：子流拉起来了没有、编码是什么、这一刻实际送出的是哪一路，然后把这个事实用各协议自带的方式回报出去。代价是每加一种直播协议就要配一个告知位置；收益是服务端看见的就是客户端拿到的，不必在浏览器里维护一份画质状态。

两种思路的代价

客户端自选加自动适应，状态落在 localStorage：切换是本地行为，服务端不参与，新增端点不用改协议。代价是同一台相机在手机和电脑上可能长期停在不一样的质量档，首次访问和未识别客户端要有一套默认策略，Auto 的降档逻辑每个客户端各写一遍，排查问题得翻浏览器控制台。Frigate 把不可用的技术选项置灰并写明原因，就是在补这个代价——不告诉用户为什么灰，用户会以为功能坏了。

服务端如实回报，状态落在 NVR：所有客户端读到同一个事实，刷新页面、换浏览器都不丢。代价是协议侧的重复劳动——HTTP 端点加响应头，HLS 把画质做进资源路径，WebSocket 加带内首帧，三者互不相通，改一次告知格式要动三处。还有兼容性债务：老客户端不认识新字段必须能跳过，否则升级一次就把旧版播放器全打断。

两条路线的分歧在状态放在哪一侧。MiBeeNvr 选服务端这一侧，是因为它的消费方不止浏览器：GB28181 上级平台、外部 AI 分析、脚本都会来取流，这些客户端没有 localStorage，也不一定会解析播放器的状态机。把结论放在服务端回报里，它们拿到的是同一句话。

回退明说

回退是常态：相机没配子流、拉取失败、H.265 子流撞上只收 H.264 的 WHEP，都会落到主码流。关键是别让客户端猜。

FLV、HLS、WHEP 这些还保有 HTTP 语义的端点，用响应头 X-Stream-Quality: main|sub 回报实际送出的那一路——注意是实际送出的，不是请求的那一路。前端拿到 main 不会黑屏，脚本也能据此判断。

WebSocket 没法这么做：101 升级响应由 upgrader 自己写头，升级前设的响应头到不了客户端。所以实际画质走带内首消息——QualityInfo，类型 0x06，格式 {type:1}{quality_len:1}{quality}，quality 是 ASCII 的 main 或 sub。服务端的 ServeWS 在 CodecInfo（0x01）之前发它，audio-only 的观众也发；不认识这个类型的老客户端直接忽略，向前兼容。

三种协议把结论放在三个不同位置：HTTP 响应的头、HLS 的资源路径、WebSocket 的首帧。回报的是实际送出的流，不是客户端要的流；结论放在客户端一定拿得到的地方；用独立字段携带，老客户端遇到未知字段直接跳过。

和前面的业界做法对照，差别更清楚：go2rtc 的 codecs filter 写在 URL 上，是客户端表达「我要什么」；Frigate 的 Auto 档按连接能力自己降档，是客户端自己做的决定，服务端不必声明实际送出哪一路。MiBeeNvr 反过来，请求里的 quality=sub 只表达意图，结论由服务端在响应里补上。前者把代价留在浏览器状态和 Auto 逻辑里，后者把代价留在协议告知和旧客户端兼容上。

看得见

排查时不用猜。GET /api/cameras/{id}/protocols 的 sub_stream 条目给出可用性、来源和原因；GET /api/streams 的流快照里，主码流和 camid/sub 是两个 hub，consumer id 前缀区分 ws / flv / hls / webrtc 等类型，计数器是累计值，要两次采样做差才算得出 fps 和码率。仪表盘的链路树把子流画成独立虚线分支，带差分 fps/kbps 和消费方类型，有消费才出现、回收后消失。

日志里认三个关键词：sub-stream live 是拉起，recycled reason=idle 是空闲回收，WHEP: sub-stream not servable over WebRTC 是 H.265 子流回退主码流——这是预期行为，不是故障。
