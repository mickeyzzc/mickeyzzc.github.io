MiBeeNvr 的 AI 检测：为什么把推理放浏览器端，以及为什么选 YOLO11n

July 28, 2026 MiBeeOSS NVR, YOLO, ONNX, AI, 目标检测, WebGPU MiBee 开源项目实践系列 4419 字 9 分钟阅读
🔊

MiBeeNvr 的 Smart Features 里有一项 AI 检测，走的是浏览器端推理——后端服务器不做任何推理，ONNX 模型文件送到浏览器，用 ONNX Runtime Web 在客户端执行。模型选的是 Ultralytics 的 yolo11n.onnx。

这个决定在 NVR 产品里不算常见。大多数开源 NVR（Frigate、go2rtc 生态）把 AI 推理放在后端，因为后端能拿到原始流、能常驻、能上 GPU。MiBeeNvr 把推理挪到浏览器，是一个有明确取舍的架构选择，不是凑合。这篇拆两件事：为什么把推理放浏览器端，以及在这个前提下为什么选 YOLO11n。

为什么推理放在浏览器端

这个决定的根因是 MiBeeNvr 的核心定位：单二进制、零外部依赖、能在 1GB RAM 的 ARM 设备上跑。AI 检测作为附加功能，不能反过来要求升级硬件，更不能为了它破坏单二进制的约束。

如果走后端推理，最直接的路径是 libonnxruntime。但它是 C 库，意味着 Go 要走 CGO 链接。一旦引入 CGO，代价是一连串的：ARM 交叉编译要额外处理 C 工具链、二进制不再纯静态、Docker 镜像要带对应的 glibc 版本、不同架构（amd64/arm64/armv7）要分别构建。一个为了"附加功能"引入的依赖，把整个项目的部署模型拖回复杂态，不划算。

把推理放到浏览器端，这几条约束全部绕开：

  • 后端不碰 C，保持纯 Go 单二进制，交叉编译零负担
  • 推理算力随浏览器数量扩展（每个 viewer 各自推理自己看的流），而不是随摄像头数量扩展——5 个摄像头、1 个人看，只跑 1 路推理；后端方案则是 5 路常驻
  • 浏览器已经解码了视频帧（<video> 元素），推理直接复用，不需要后端再传一遍原始流或解码
  • 模型文件只有 5.4MB，下载一次后 Cache API 缓存，后续打开秒加载

后端在整个 AI 链路里只做三件事：存配置、发模型文件、转发视频流。画面数据从不经过后端的推理路径。

这个架构的代价也是明确的：浏览器关了，推理就停了；没有 viewer 在看的时候，没有检测结果产生。所以它适合的是"实时轻量检测"——你在看画面的时候顺便叠一层框。需要 7×24 常驻、需要录像段的事后重推理、需要 GPU 加速重模型的场景，是另一套系统，下面单说。

浏览器端推理的工程实现

选定了浏览器端推理，实现上有几个绕不过去的工程问题。这几个问题的解法，比"用哪个模型"更能体现这个架构的取舍。

模型分发的健壮性

模型文件从 Ultralytics 的 GitHub release 下载。GitHub release 走的是 Azure blob CDN，给的是 1 小时签名的 URL。在国内到 GitHub 的网络下，连接会被静默截断——不是报错，是传到一半 TCP 就断了，留一个不完整的文件在磁盘上。下次启动 NVR 看到这个文件就以为下好了，直接发给浏览器，ONNX Runtime Web 解析被截断的 protobuf 报 ERROR_CODE 7（INVALID_PROTOBUF）。

所以 download_model.go 做了三重防御：

  1. 断点续传——用 HTTP Range 请求，从 .part 文件已有大小接着下，而不是每次从头来
  2. 退避重试——失败后按 1s/2s/4s/8s/16s 退避，最多 5 次
  3. 完整性校验——下载完按 Content-Length 严格校验大小（带一个 5MB 的绝对下限兜底），过了才原子重命名 .part → 最终文件名，不过就重来

这三层是独立的防御——网络抖动靠重试兜，大文件断流靠 Range 续，静默截断靠大小校验抓。任何一个环节不过，模型都不会以损坏状态对外服务。

ONNX Runtime Web 的加载陷阱

ORT 的加载方式踩了一个很深的坑。直觉做法是 import('onnxruntime-web') 走 Vite 的代码分割。但这会触发一个误导性极强的 bug：Vite 的 ESM 代码分割会破坏 ORT 内部基于 import.meta.url 的 WASM/worker 路径解析，ORT 找不到 wasm 文件，报出来的错误是 INVALID_PROTOBUF——和模型损坏的错误码一模一样。

排查这个 bug 花了不少时间，因为错误指向"模型坏了"，实际是"ORT 的 wasm 加载路径被 Vite 破坏了"。最后的解法是不走 Vite 的 import，改用 <script src="/ort.min.js"> 加载 UMD bundle，手动设置 ort.env.wasm.wasmPaths = '/ort/'。另外因为页面没有 COOP/COEP 头，拿不到 SharedArrayBuffer，所以强制 numThreads = 1 单线程跑。

推理管线

ObjectDetector 类实现完整的推理管线，从 VideoFrame 到 Detection[]：

mermaid
flowchart LR
    VF["VideoFrame"] --> PRE["预处理<br/>letterbox 640"]
    PRE --> INF["ONNX 推理"]
    INF --> PARSE["输出解析<br/>84×8400"]
    PARSE --> NMS["NMS"]
    NMS --> MAP["逆 letterbox"]
    MAP --> EMA["EMA 平滑"]

    classDef step fill:#E3F2FD,stroke:#1565C0,color:#1565C0
    class VF,PRE,INF,PARSE,NMS,MAP,EMA step

每一步的细节：

  • 预处理：OffscreenCanvas 做 letterbox resize 到 640×640，填充灰色（114），RGBA → CHW Float32 归一化到 [0,1]。用 OffscreenCanvas 而不是普通 canvas，是为了不在主线程做像素搬运。
  • ONNX 推理：输出 tensor [1, 84, 8400]——4 个 box 坐标（cx/cy/w/h）+ 80 个类别分数，共 84 通道，8400 个 anchor。
  • 输出解析：每个 anchor 取 80 个类别分数的最大值，sigmoid 激活，过滤低于置信度阈值的，cxcywh → xyxy。
  • NMS：按置信度排序，贪心抑制 IoU > 0.45 的重叠框。
  • 逆 letterbox：把 640×640 坐标系下的框反向映射回原始帧坐标。
  • EMA 平滑：指数移动平均（alpha=0.3）跟踪检测框，未匹配的框在 15 帧后移除——不然目标短暂离开画面再回来，框会闪。

跳帧（frame_skip）默认每 3 帧推一次（30fps 视频上约 10fps 推理），靠缓存上一帧的平滑结果填充跳过的帧。

检测结果只在这个浏览器标签页里画 canvas overlay，不上报后端。每个 viewer 独立调参（置信度、NMS 阈值、跳帧、EMA alpha），持久化在 localStorage。

为什么选 YOLO11n

浏览器端推理这个前提，直接把模型选型范围收窄了。

第一层筛选是 ONNX 导出成熟度。浏览器跑 ONNX，模型的 ONNX 导出必须干净、社区验证充分。Swin 这种 Transformer 结构的 ONNX 导出复杂、动态 shape 多；YOLO-NAS 的导出依赖 supergradients 框架；RT-DETR 的 ONNX 文件 >50MB。YOLO 系列的 ONNX 导出是 Ultralytics 官方一等公民，社区跑通的案例最多，自然进了候选池。

第二层筛选是模型大小。浏览器要下载模型，5.4MB 的 YOLO11n 在多数网络下 1-2 秒加载完，Cache API 缓存后秒开。换成 20MB+ 的模型，首次加载要等 5-10 秒，体验断崖式下降。所以只能看 nano 级别。

在 YOLO 的 nano 级别里，YOLO11n、YOLOv8n、YOLOv5nu 三代的对比（数据来自 Ultralytics 官方 benchmark，COCO val2017，640 输入）：

指标YOLOv5nuYOLOv8nYOLO11n
mAP50-9534.337.339.5
参数量 (M)2.63.22.6
FLOPs (B)7.78.76.5
主干模块C3C2fC3k2
注意力模块无无C2PSA

注：这里用 YOLOv5nu（anchor-free 更新版，Ultralytics 当前默认），不是 2021 年的老 v5n。老 v5n 的 mAP 只有 28.0，参数 1.9M，但精度差太多，不在同一代对比里。

YOLO11n 在精度最高（39.5）的同时，参数量和 YOLOv5nu 持平（2.6M）、FLOPs 最低（6.5B）。精度-速度比是三代里最好的。YOLOv8n 精度接近但 FLOPs 高了 34%、模型文件大了 15%。

放到浏览器场景里，FLOPs 的差距很实在。没有 WebGPU 的设备走 WASM SIMD 后端，6.5B FLOPs 和 8.7B FLOPs 的单帧推理时间差，在 Intel 笔记本上实测大约是 80-120ms 对 110-150ms 的差距。配合 frame_skip=3，每帧推理摊到 100ms 间隔里，YOLOv8n 就开始吃力了。

YOLO11n 相比 YOLOv8n 的结构改进，主要集中在两处，都冲着效率去：

C3k2 替换 C2f。YOLOv8 的 backbone 和 neck 用 C2f，YOLO11 换成 C3k2。C3k2 是 C2f 的子类，内层重复单元可以切换——浅层用标准 Bottleneck（行为等同 C2f 但通道更窄），深层切换成 C3k（带可配置 kernel 的 CSP 模块）做更细的特征提取。同等感受野下参数利用率更高。

C2PSA 空间注意力。YOLO11 在 SPPF 之后、neck 之前新增了 C2PSA——一个带位置敏感注意力（Position-Sensitive Attention）的 CSP 模块。输入通道拆两半，一半跳过，一半过若干 PSABlock（多头自注意力 + FFN），再合并。让模型关注图像关键区域，对小目标和遮挡场景更有效。YOLOv8 没有这个模块。这是 YOLO11n 参数更少但 mAP 反超 YOLOv8n 的主因之一。

这两处改进的净效果就是上表那组数字：精度涨 2.2 个点，参数持平，FLOPs 降 25%。对浏览器端推理来说，FLOPs 降意味着每帧 CPU 时间降，意味着同样的 frame_skip 下更流畅，或者同样流畅度下能少跳帧少漏检。

和 MiBeeVision 的分工

MiBeeNvr 还集成了另一个 AI 方案——MiBeeVision，一个独立的 Rust AI 后端。它和浏览器端推理不是二选一的关系，而是分工：两个系统覆盖不同场景，在 NVR 里并存。

浏览器端 YOLO 解决的是实时轻量检测——你看画面的时候顺便叠一层框，零部署、插上摄像头就能用。代价是没有 viewer 就没有检测，模型也受限于浏览器算力只能跑 nano 级。

MiBeeVision 解决的是重推理——它跑在独立的、有 GPU 或 NPU 的机器上，对录像段做事后分析，或者做浏览器跑不动的重模型。它通过 API Key 认证（mbv_ 前缀），把检测结果通过 POST /api/ai/events 回写给 NVR，NVR 存进数据库供历史检索。有活跃 AI 事件的录像还会被清理策略保护，不会被误删。

    BR --> OV["Canvas 叠加框<br/>本地，不上报"]
    NVR <=="录像段 / API Key"==> MV["MiBeeVision<br/>独立 Rust 后端"]
    MV =="/api/ai/events 回写"==> NVR
    NVR --> HIST["AI 事件历史<br/>录像保护"]

这两条路径在 NVR 的 /api/ai/* 接口上是分开的：status/config/zones 服务浏览器端 ONNX 的配置和 ROI 区域；events/stats 是 MiBeeVision 的回写和查询。同一个 NVR 里两套并存，各管各的。

需要即开即用的实时检测就用浏览器端，默认就有；需要 7×24 常驻、重模型、GPU 加速的时候，部署 MiBeeVision 做补充。这是两套系统存在的意义，不是谁替代谁。

选型的逻辑链

把上面的取舍串起来，YOLO11n 不是随便选的，是一连串约束递推的结果：

  1. 单二进制、无 CGO → 推理不能放后端 → 放浏览器端
  2. 浏览器下载模型 → 模型要小 → 只能看 nano 级
  3. ONNX 导出要成熟 → YOLO 系列
  4. nano 级里精度-速度比最好 → YOLO11n

模型本身（C3k2、C2PSA）的结构优势，是这个选型链最后一环的加分项，不是出发点。出发点是"浏览器端推理这个架构约束下，需要一个能跑得动的 nano 模型"，YOLO11n 恰好在精度、参数、FLOPs 三个维度上都做到了 nano 级里最好的平衡。
