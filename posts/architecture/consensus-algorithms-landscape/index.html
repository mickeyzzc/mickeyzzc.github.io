分布式共识算法全景：从 Paxos 到 DAG-BFT，四类协议的边界与选型

August 12, 2026 August 29, 2026 架构设计 分布式系统, 共识算法, Paxos, Raft, BFT, 区块链, 选型 技术与工程选型系列 8690 字 18 分钟阅读
🔊

etcd 用 Raft，Cosmos 用 Tendermint，Bitcoin 用 PoW，Sui 用 Mysticeti——它们都叫「共识（consensus）」，但解决的根本不是同一个问题。机房里几个已知身份的节点选主，和公链上一群匿名节点对账本达成一致，约束条件差出一个数量级。把所有共识算法捏在一起比吞吐，是很多选型文章读起来糊涂的根源。

这篇按故障模型把主流共识分成四类，从单值共识的具体问题切入：先讲三条边界划出的设计空间，再逐个看代表算法的消息流和它在优化什么，最后落到选型。关键算法配时序图，结尾附一个能直接 go run 的 PoW 示例。

共识到底要解决什么问题

先看一个具体场景。你有 3 台数据库副本，分别在北京、上海、深圳，存着同一个账户的余额。现在一条转账要把余额从 100 改成 90。如果三台各改各的，万一北京改了、上海因为网络抖动没收到、深圳收到的是一条乱序的旧消息——三份数据就不一致了，后面的查询会读到三个不同的余额。

共识要解决的就是：让这 3 台最终都对「余额 = 90」这件事达成同一个、不可反悔的结论，哪怕其中一台恰好宕机、哪怕网络丢几条消息。

这里有两层概念，分清了对后续理解很有帮助：

  • 单值共识（consensus）：对「某一个值」达成一致。这是最基础的问题，Paxos 的原始论文（单法令/synod）就只解决这个。
  • 状态机复制（State Machine Replication, SMR）：真实系统要的不是对一个值一致，而是对「一连串操作」的顺序一致——转账 1、转账 2、转账 3 必须按同一个顺序应用到所有副本。Multi-Paxos / Raft / PBFT 本质都是把「单值共识」串起来做 SMR。

理解了 SMR，就明白为什么共识是所有「可信状态」的地基：数据库副本一致、etcd/ZooKeeper 选主与配置同步、区块链账本顺序，全建立在上面。

为什么没有一个万能算法：三条绕不开的边界

如果有万能算法，就不需要这么多名字了。问题在于三条理论边界把设计空间卡死了。

边界一：节点能坏到什么程度——故障模型

模型节点能干什么例子
崩溃-停止（Crash）突然停机，不撒谎机房断电、进程崩溃
崩溃-恢复（Crash-Recovery）重启，磁盘状态可恢复拔电后重启
拜占庭（Byzantine）任意行为：谎报、伪造、合谋被入侵的节点、公链上的作恶者

CFT（Crash Fault Tolerant）算法假设节点只会崩；BFT（Byzantine Fault Tolerant）算法假设节点会撒谎。这是第一条分界线——你对面的节点到底可信到什么程度。

边界二：FLP 不可能性——为什么不能「完全异步 + 确定性」

1985 年 Fischer、Lynch、Paterson 证明：在严格异步的网络里（消息延迟没有上限），没有任何确定性共识算法能同时保证 safety 和 liveness，哪怕只允许一个节点崩溃。

直觉上很好理解：算法没法区分「一个节点挂了」和「它只是很慢」——如果一直等它，可能永远等下去（丢 liveness，系统卡死）；如果不等它就推进，它事后可能冒出一条旧消息造成冲突（丢 safety，出现两个矛盾的决议）。两条路都走不通。

所以实用协议都做了让步：要么假设「部分同步」——存在某个未知时刻 GST（Global Stabilization Time）之后网络会变好，Raft/PBFT/Tendermint 都靠这个；要么引入随机化打破对称（HoneyBadger），让敌手没法精确卡住系统。记住这一点，后面每个算法的「为什么这么设计」基本都能追到这。

边界三：容错上限——为什么 BFT 要 3f+1 而 CFT 只要 2f+1

这个上限的推导值得展开看一下。

  • CFT 最多容忍 f < n/2：即需要 n ≥ 2f+1 个节点。投票凑「多数派」即可，因为两个多数派（各 f+1 以上）必有交集，而 CFT 节点不撒谎，交集中的节点能保证两个多数派不冲突。
  • BFT 需要 n ≥ 3f+1：即最多容忍 f < n/3 的恶意节点。

为什么 BFT 多要一个 f？关键在「交集里必须至少有一个诚实节点」。BFT 里每个多数派是 2f+1 个节点，任意两个多数派的交集至少 f+1 个；如果系统里总共只有 f 个恶意节点，那么这 f+1 个交集节点里至少有 1 个是诚实的——正是这个诚实节点，保证两个多数派不可能同时确认相互冲突的值。CFT 因为节点不撒谎，交集只要非空就行（2f+1 够）；BFT 因为节点会撒谎，交集必须「至少一个诚实」，这才被逼到 3f+1。

把这个推导记住，PBFT 为什么用 n=3f+1、为什么每阶段凑 2f 个投票，就都有依据了。

一张地图：四大家族

按「是否需要信任节点身份」加「是否允许恶意行为」，主流共识分成四类：

家族假设容错典型场景代表算法
CFT节点只崩不骗f<n/2机房、联盟内部Paxos、Raft、Zab
BFT节点会骗，但身份已知n≥3f+1许可链、联盟链PBFT、HotStuff、Tendermint、IBFT
PoX无准入、匿名算力/资金公链PoW、PoS、DPoS
DAG/混合用图结构突破线性吞吐视协议高吞吐链Mysticeti、Shoal、Narwhal

下面逐类进到消息流层面。

CFT 家族：节点只会崩

2PC：最早的尝试，以及它为什么阻塞

两阶段提交（2PC）是最古老的「共识」，服务分布式事务的原子提交。它有一个协调者和若干参与者：

  1. 协调者发 Prepare，每个参与者投票「能提交」或「不行」。
  2. 若全员同意，协调者发 Commit；否则发 Abort。

它的硬伤是阻塞：如果协调者在发出 Commit 之前崩溃，参与者收不到最终决定，既不敢提交（怕别人 abort）也不敢放弃（怕别人提交），只能永远等。3PC 加一个 PreCommit 阶段和超时来缓解，但在网络分区下仍可能不一致，生产里很少直接用。

更要紧的是：2PC 解决的是「原子提交」（一件事要么全做要么全不做），不是通用状态机复制，而且对协调者这个单点很敏感。所以现代系统通常用 Paxos/Raft 做副本复制，事务层再叠在上面。

Paxos：用编号抢占提案

Paxos（Lamport, 1998）是第一个被严格证明正确的异步容错共识。它的核心思想可以用一句话概括：用一个全局唯一、单调递增的「提案编号（ballot）」抢占地盘，编号大的总能覆盖编号小的，而一旦某个值被多数派接受，后来者必须沿用这个值。

它分两个阶段，Proposer（提议者）和 Acceptor（接受者）之间的消息流如下：

mermaid
sequenceDiagram
    participant P as Proposer
    participant Q as Acceptor 集合
    P->>Q: ① Prepare(ballot=N) 广播给所有 Acceptor
    Q-->>P: ② Promise 多数回：「承诺拒旧编号」+ 回带已接受的值
    Note over P: 凑够多数；若已有被接受的值，则沿用它
    P->>Q: ③ Accept(ballot=N, value) 广播
    Q-->>P: ④ Accepted 多数确认
    Note over P,Q: 多数 Accepted → 该 value 被 chosen（已选定）

两个阶段对应两件不同的事：

  • Prepare/Promise（抢占 + 探测）：Proposer 用编号 N 去问「我能不能用 N 提案？」Acceptor 的规则是——如果 N 比我之前承诺过的都大，我就承诺不再接受任何更小编号的提案，同时把我已经接受过的值告诉 Proposer。这一步既抢到了地盘，又探明了「之前是不是已经有人定过值」。
  • Accept/Accepted（定值）：Proposer 凑够多数 Promise 后，发 Accept。关键规则：如果 Promise 里有人带回「已接受的值」，Proposer 必须用那个值（编号最大的那个），不能用自己原本想提的值；只有没人接受过值时，才能用自己的新值。

第 1 轮（A 先动）：
  A 用 ballot(1,A) 发 Prepare → a1/a2/a3 都没见过更大编号，回 Promise(空)。
  A 收到 a1/a2 多数 Promise，没人接受过值 → A 用自己的 X。
  A 发 Accept(1,A, X) → a1/a2 回 Accepted → X 被 chosen。

第 2 轮（B 后到，想定 Y）：
  B 用更大的 ballot(2,B) 发 Prepare。
  此时 a1/a2 的已接受值是 (1,A,X)，编号 (2,B)>(1,A)，于是回 Promise，并回带「我已接受 X」。
  B 收到多数 Promise，按规则必须沿用 X（不能改成 Y）。
  B 发 Accept(2,B, X) → 最终值仍是 X。

无论 B 多想定 Y，最终都是 X——这就是 Paxos 的 safety。两个 Proposer 并发「决斗」时，可能谁的多数都凑不齐（互相打断），这时靠随机退避（先回退的那个让一让）打破对称，这正是真实 Paxos 实现的标配。

Paxos 的麻烦在于：它只定义了「单值」，要做成能用的日志复制（Multi-Paxos）得自己加 Leader、加日志槽位、加重传，每个工程实现都得重新趟坑。所以它以「难理解、难实现」出名。

Raft：把共识拆成三个子问题

Raft（2014）的目标就一个：可理解性。它的出发点是「Paxos 之所以难，是因为 Proposer/Acceptor/Learner 三种角色搅在一起」，于是 Raft 用一个强 Leader 把数据流变成单向：所有客户端请求只找 Leader，Leader 再往 Followers 推。

它把共识拆成三个子问题。首先是角色与选举：

mermaid
stateDiagram-v2
    [*] --> Follower
    Follower --> Candidate: 选举超时，没收到 Leader 心跳
    Candidate --> Leader: 拿到多数票
    Candidate --> Follower: 见到更高 term，或超时重来
    Leader --> Follower: 见到更高 term
  • 任期（Term）：Raft 的时间单位，单调递增的逻辑时钟。每次选举开启一个新 term。
  • Leader 选举：每个节点有个随机的选举超时（比如 150–300ms）。谁先超时，谁就把自己升级成 Candidate、term+1、先投自己一票，然后向其他节点拉票（RequestVote）。拿到多数票就成了 Leader。随机超时是关键——它让节点们几乎不会同时发起选举，避免反复平票。
  • 日志复制：客户端发命令给 Leader → Leader 把命令追加到本地日志 → 通过 AppendEntries（心跳也复用这个）发给所有 Follower → 一旦多数 Follower 确认，Leader 标记该条目 committed 并通知 Follower。AppendEntries 里带 PrevLogIndex/PrevLogTerm 做日志匹配，保证所有副本的日志最终一致。
  • 安全性：靠几条规则保证「已 commit 的条目不会丢、不会改」，比如「Leader 的日志一定是最完整的」（选举时只投给日志至少和自己一样新的候选人）。

Raft 如今是云原生的事实标准：etcd、Consul、TiKV、CockroachDB 都用它或它的变体。抓住「强 Leader + 随机选举超时 + 日志按 majority commit」这三点，就掌握了 Raft 的主干。

BFT 家族：节点会撒谎

节点可以任意作恶，需要 n ≥ 3f+1。经典是 PBFT（1999），它的三阶段是为了在「有 f 个恶意节点」的前提下同时防住两种攻击：主节点作恶和副本各执一词。

PBFT：为什么要三个阶段

mermaid
sequenceDiagram
    participant PR as 主节点 Primary
    participant R as 副本集合 (n=3f+1)
    PR->>R: ① Pre-Prepare：主节点广播提案
    R->>R: ② Prepare：副本互相广播，各收齐 2f 个
    R->>R: ③ Commit：副本互相广播，各收齐 2f 个
    Note over R: 收齐 2f 个 Commit → 各副本本地执行

每个阶段都在防一种坏情况：

  • Pre-Prepare：主节点（primary = view mod n）负责提案。但主节点可能作恶——比如给不同副本发不同内容。所以光主节点说了不算。
  • Prepare：副本们互相广播「我收到了这个提案」，每个副本要凑齐 2f 个 Prepare（含自己隐含的，合起来超过 2f+1）。这一步保证「所有诚实副本对这一轮投什么达成一致」，把主节点的作恶空间挤掉。
  • Commit：再互相广播一次、再凑 2f 个。这一步保证「即便某个副本接下来掉线，其他副本也不会执行一个别人没法确认的值」——为视图切换（view-change）留出余地。

为什么要 Prepare 和 Commit 两层？因为只有一层多数派，没法同时满足「主节点坏了能换」和「换主之后不推翻已执行的值」。两层投票加上 2f 这个阈值（在 3f+1 里，2f+1 个诚实/可验证签名能压住 f 个恶意），才把 safety 钉死。代价是通信复杂度 O(n²)——每个副本都要和别的副本两两通信。

主节点宕机或作恶时，副本靠 view-change 换主（新主 = (view+1) mod n）。PBFT 之后的所有 BFT 算法，基本都在想办法让 view-change 更便宜。

HotStuff / Tendermint / IBFT：各自优化了什么

  • HotStuff（2019）：把 PBFT 的「副本两两互发」改成「每阶段只让 Leader 聚合 +2/3 签名再广播」，通信复杂度从 O(n²) 降到 O(n)（线性），并且支持流水线——多块同时在途。Aptos 的 AptosBFT 衍生自它。顺带一提，HotStuff 和以太坊 Casper FFG 结构同源——Dahlia Malkhi 既是 HotStuff 作者之一，也撰文把 Casper FFG 放进 BFT 视角分析过。
  • Tendermint / CometBFT（Cosmos）：轮转提议者 + 两轮投票换即时最终性——一个区块一旦拿到 +2/3 预提交就不可回滚。好处是最终性干净，代价是每个区块都要全量投票。
  • IBFT / QBFT：PBFT 思路在 EVM 生态的落地。IBFT 对应 EIP-650（2017，正式论文 arXiv:2002.03613 by Moniz 等），是 Quorum / 企业以太坊部署最广的许可链共识之一；QBFT 是企业以太坊联盟（EEA）在 IBFT 上做了 Dafny 形式化验证后的演进标准，GoQuorum、Hyperledger Besu 都在用，确定性最终性、无分叉。
  • HoneyBadger：另一条路——用可靠广播 + 加密随机化在完全异步网络里达成共识，不依赖部分同步，抗分区但吞吐偏低，适合高对抗环境。

一个常被搞混的点：QuePaxa 是 CFT，不是 BFT

QuePaxa（SOSP'23，EPFL DEDIS，论文 Escaping the Tyranny of Timeouts in Consensus）在网上不少科普里被归成「异步 BFT」。我去翻了它的官方仓库和 Cloudflare 的介绍，两边都写得很明确：QuePaxa 是崩溃容错（CFT），「和 Raft 一样不处理拜占庭故障」。它解决的不是恶意节点，而是 Multi-Paxos/Raft 共有的痛点——靠超时做 Leader 更换，Leader 一变慢或被 DDoS，系统就在超时等待里卡住。

QuePaxa 用随机化对冲（hedging delays）加多臂老虎机动态选主，做到安全性与超时无关：慢 Leader 不会拖垮正确节点，WAN 遇 DoS 时中位延迟仍 <380ms。论文实测 LAN ~584k cmd/s、WAN ~250k cmd/s，跟 Multi-Paxos 同一量级（基准对手就是 Multi-Paxos/Raft/EPaxos 这些 CFT）。Cloudflare 的 Meerkat（2026）是它的首个公开落地，Rust 实现，跑过最多 50 个全球副本的 PoC——但截至发文仍是内部实验项目，没有进入生产，别被「已投产」的说法带偏。

把它放进 BFT 这章一起讨论，只是因为它和异步 BFT 共享「免超时」这个议题，不是因为它能抗拜占庭。

公链 PoX：用经济成本替代信任

公链是「无准入、节点匿名、随时进出」的环境，没法假设「已知诚实」，于是 PoX 反过来想：让作恶的成本高于收益，用算力或资金替代身份验证。

PoW：用算力开彩票

PoW（工作量证明）的机制直白：节点（矿工）竞相找一个 nonce，让区块头的哈希值前导 0 达到难度目标。哈希函数没法预测、只能穷举，所以难算易验——挖矿要砸海量算力，但验证只需一次 SHA-256。

// 最小 PoW 演示：递增 nonce 直到哈希前导 0 达标。go run main.go
package main

import (
	"crypto/sha256"
	"encoding/hex"
	"fmt"
	"strconv"
	"strings"
	"time"
)

func mine(prefix string, difficulty int) (uint64, string, time.Duration) {
	target := strings.Repeat("0", difficulty)
	var nonce uint64
	start := time.Now()
	for {
		data := prefix + strconv.FormatUint(nonce, 10)
		sum := sha256.Sum256([]byte(data))
		hash := hex.EncodeToString(sum[:])
		if strings.HasPrefix(hash, target) {
			return nonce, hash, time.Since(start)
		}
		nonce++
	}
}

func main() {
	const difficulty = 4 // 前导 0 位数；难度 +1，期望工作量翻倍
	nonce, hash, elapsed := mine("block:micke:", difficulty)
	fmt.Printf("nonce = %d\nhash   = %s\n耗时   = %v\n", nonce, hash, elapsed)
	fmt.Println("验证只需一次 SHA-256——这正是 PoW 的「难算易验」。")
}

最长链规则是 PoW 共识的灵魂：当两个矿工同时出块造成分叉时，规则是「永远跟最长（累积工作量最大）的那条链」。要改写已经产出的区块，攻击者得重新算出比诚实网络更多的哈希——也就是掌控 51% 的算力，成本高到不划算。这就是 PoW 安全性的来源。代价也直白：能耗大、BTC 只有 ~7 TPS、而且只有概率最终性（一个区块越深埋在最长链里，被推翻的概率越低，但永远不是 0）。

PoS：用押金担保

PoS（权益证明）把「拼算力」换成「拼押金」。验证者抵押资金（以太坊是 ETH）换取投票权，提议者按 stake 加权伪随机选。以太坊的 Gasper = Casper FFG（对 checkpoint 做两轮投票敲定）+ LMD-GHOST（分叉选择规则选链头）。

安全性靠罚没（slashing）：验证者如果双重签名或搞环绕投票，会被销毁押金。所以攻击的成本等于「至少烧掉总质押的 1/3」——把作恶变成亏本生意，这就是经济最终性。它解决了 PoW 的能耗问题，也带来新挑战：无利害关系（Nothing-at-Stake，靠 slashing 解决）和长程攻击（旧私钥重建历史链，靠弱主观性检查点缓解）。

其它 PoX 变体：DPoS（EOS 21、Tron 27 个出块者）用代币投票选少量出块节点，高吞吐但更中心化；PoA 用身份当许可，常用于测试网；PoH（Solana）用可验证延迟函数当加密时钟配合 PoS 拿高 TPS，但出块时间表已知、易被 DDoS。

DAG-BFT：打破线性吞吐瓶颈

传统共识把交易排成线性区块：一个 Leader 出一个块、广播给所有人、确认了再出下一个。吞吐被两件事卡死——出块是串行的、广播的是越来越大的区块。节点越多、区块越大，越堵。

DAG（有向无环图）的解法是把块组织成图，让副本并行出块，核心一招是把「数据传播」和「共识排序」拆成两层：

Narwhal 是内存池层：验证者并行广播交易批次，自然形成一张 DAG，吞吐能到 ~16 万 TPS。Bullshark 在这张 DAG 上做共识排序。Mysticeti（Sui，NDSS'25）更进一步，做「无认证 DAG」——不等全量签名证书，直接在图上做 3 轮提交（BFT 理论下界），把延迟压到 ~390ms，比 Bullshark 降约 80%。Shoal / Shoal++（Aptos，FC'24 / NSDI'25）在 Narwhal 上叠流水线和领导者声誉，主动绕开慢主节点，多数场景消除超时停顿。

DAG 这条线还有几个方向：Avalanche 不搞 BFT 投票，靠反复随机采样少量对等节点形成「雪崩」式正反馈，亚秒收敛、Leaderless；Hashgraph（Hedera）用 gossip-about-gossip + 虚拟投票做异步 BFT；Algorand 用 VRF 密码学抽签选委员会；Slipstream（arXiv 2024）把「动态可用」（类最长链，容忍接近半数节点离线仍出块）和「最终性 gadget」（BFT，需 2/3 活跃）组合在同一条 DAG 上——可用链保活、最终链保最终性，适合真实世界频繁分区。

EPaxos 顺带一提：它是无主、冲突容忍的 Paxos 变体，任意副本都能当临时 Leader，无冲突命令走快速路径。它快速路径的法定数是 F + ⌊(F+1)/2⌋（5 副本即 F=2 时为 3）。网上有些文章写成 F + ⌊F/2⌋ + 1，代入 F=2 会算出 4，跟「5 副本下与普通多数相同」矛盾——正确记法是带 (F+1)/2 的那个。

怎么选

几条具体规则：

  • 内部系统、节点可信：默认 Raft（好运维）；已有 Paxos 栈就继续 Multi-Paxos；分布式事务用 2PC 叠在复制层之上。
  • 许可链/联盟链、有恶意节点：要确定性最终性选 PBFT / HotStuff / IBFT；完全异步高对抗选 HoneyBadger。
  • 公链、匿名、抗审查：要最大去中心化和安全选 PoW；要低能耗和较高最终性选 PoS（Gasper 类）；可接受较弱去中心化换 TPS 选 DPoS。
  • 吞吐是第一瓶颈：优先 DAG-BFT（Mysticeti / Shoal），它们靠「数据/共识分离」绕开了线性 BFT 在 100+ 节点时的 O(n²) 开销。
  • 金融结算要不可逆：选确定性最终性（Tendermint / PBFT / HotStuff / Mysticeti）；能接受「越深越安全」就用 PoW 的概率最终性，更简单。

一条线索串起来：内部用 Raft，要抗恶意且许可用 BFT，公链要安全用 PoW/PoS，要性能天花板用 DAG-BFT。 至于 QuePaxa 这类异步免超时的 CFT，瞄准的是「跨地域、慢 Leader、怕 DDoS」的控制面场景，等 Meerkat 真正投产了再考虑生产选型。
