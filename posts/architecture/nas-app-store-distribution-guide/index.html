把应用发到所有 NAS 与路由器 OS：飞牛、极空间、绿联、群晖、QNAP、TrueNAS、OpenWrt、iStoreOS 的打包与上架差异

🔊

2024 年 10 月，TrueNAS SCALE 24.10「Electric Eel」砍掉了 k3s 后端，把整个应用层从 Helm Charts 迁到了 Docker Compose。一夜之间，所有按旧教程往 TrueNAS 上加「custom train」的命令全失效了——24.10 把「Add Catalog」按钮也一并删掉。同一年，飞牛、极空间、绿联密集上线或重做了各自的应用中心，飞牛的 .fpk、绿联 2026 年 5 月新开的开发者平台，都在抢「应用生态」。

把这几件事并排放在一起，能看出 NAS / 路由器 OS 的应用分发正在分化成两条路：原生私有格式 + 审核制商店（群晖、QNAP、铁威马），和 Docker 镜像 + 轻量封装（TrueNAS、Unraid、飞牛、极空间、绿联）。开源 NAS（OMV）和路由器 OS（OpenWrt、iStoreOS）则几乎全押在 Docker 与系统包管理器上。

这篇把 14 个主流平台的「应用怎么发上去」拆开讲：打包格式、商店政策、签名要求、第三方侧载通道、个人开发者能走多远。如果你只想知道「我有一个应用，先发哪个平台」，直接跳到最后的决策树。

关键观察：右下两个象限（Docker-first + 系统包管理器）才是个人开发者的主战场。群晖 / QNAP / 铁威马的原生商店审核重、周期长，但 Docker 在它们上面也能跑——下面逐个展开。

一条贯穿全文的事实：除了几条私有原生格式外，所有 14 个平台底下都能跑 Docker。构建一个多架构 OCI 镜像（linux/amd64 + linux/arm64），你就有了一个通吃所有平台的基底。剩下的差异只是「这个镜像怎么落到它的商店/包格式里」。

国际 NAS：私有格式与审核制

群晖 DSM —— .spk + 审核制，社区源是真正出口

群晖的 .spk 是这套体系里最成熟的私有格式，但上架门槛也最高。DSM 7 之后规则收紧：所有包强制降权（sc-${packagename} 系统用户，不能再 root 运行），自签名 CSR 流程从 UI 里移除，只有群晖在发布流程里帮你签名的包才会出现在官方套件中心。要走官方，得签 Developer Distribution Agreement、过审核。

个人开发者的实际出口是第三方社区源：套件中心 → 设置 → 套件来源 → 添加，输进去就出现在「社区」分区。最大的社区源是 SynoCommunity（packages.synocommunity.com，仓库在 github.com/Synocommunity），把信任层级调成「Synology Inc. 和信任的发布者」即可。自己托管一个 Package Source 也行。手动安装（直接上传 .spk）同样可用，但未签名包可能被信任设置拦下。

DSM 7 的几个坑要提前知道：

  • 强制降权是硬性的。历史包（Duplicati、FileBot 等）大量因此重写，你的包必须声明并使用 sc- 作用域用户。
  • 按 DSM 大版本 × CPU 架构分别构建，toolchain 矩阵维护成本真实存在；DSM 7.2.x 的 toolchain 不匹配会报 invalid file format。
  • 官方声称全平台月下载约百万级，但那是「过了审核」之后的量，社区源没这个曝光。

QNAP QTS / QuTS hero —— .qpkg 走 Helpdesk 提交，签名过期是老问题

QNAP 的 .qpkg 用 QDK（QNAP Development Kit，github.com/qnap-dev/QDK） 构建。和群晖一样，QNAP 在审核时替你签名，开发者自己不能签——这也是 App Center 里三方应用带感叹号警告的原因（未签名）。

提交路径比较反直觉：构建 .qpkg → 手动安装自测 → 在 NAS 上装「Helpdesk」应用 → 通过 Helpdesk 提交包和元数据 → QNAP 审核。没有像群晖那样的「加第三方源」机制，分发基本只能靠手动上传 .qpkg。管理员可在 App Center → 设置 → 通用里打开「允许安装无有效数字签名的应用」来侧载。

两个坑：

  • 数字签名会过期，过期后 App Center 会停用该应用，用户必须重装新版本——历史上造成过批量应用停摆。
  • 现代 QNAP 上，Container Station（Docker）正越来越成为首选，App Center 里很多「应用」其实就是 Docker 的薄封装。如果你的应用已经容器化，直接走 Container Station 比打 .qpkg 省事得多。

铁威马 TerraMaster TOS —— .tpk，SDK 开源但生态最小

铁威马的 .tpk（TOS 7 也接受 .deb）目录结构偏 OpenWrt 风格，原生主要面向 C/C++ 交叉编译应用，工具链在 github.com/TerraMasterOfficial/app-pkg-tools（含 TOS 7 应用开发与发布指南、审核标准 Review_Standards.md）。容器化应用则走 Docker。

开发者计划是国产 NAS 里最早建立的（2020 年），有两条上架通道：官方应用市场（申请 + 审核），以及 2023 年上线的 TNAS 社区应用平台（tmnascommunity.eu，注册账号后自助发布，约 100 个免费应用）。社区应用经常比官方更新——比如 Jellyfin 在社区版更及时。

坑：官方文档偏稀疏，尤其 UI 集成部分；.tpk 原生开发是 C/C++ 交叉编译，比纯 Docker 工作流重。多数个人应用其实直接当容器发。

Docker-first 平台：镜像就是应用

TrueNAS SCALE —— 24.10 起是纯 Docker Compose，没有第三方目录

这是变动最大的平台，必须单独说。24.10「Electric Eel」彻底移除了 k3s/Kubernetes 后端，应用层从 Helm Charts 换成 Docker Compose；官方目录迁到 github.com/truenas/apps，旧的 truenas/charts（Helm 时代）作废。后续 25.04「Fangtooth」、25.10「Goldeye」延续 Compose 路线。

24.10 一并删除了「Add Catalog」选项——Helm 时代的第三方目录（最知名的是 TrueCharts）随之失效，TrueCharts 已停止支持 SCALE，建议用户迁移到独立 Docker / Proxmox。截至 25.04，自定义 train 仍未恢复（功能请求在 forums.truenas.com/t/custom-app-trains/25215）。

个人开发者实际怎么发：

  1. 发布一个标准 Docker 镜像（Docker Hub / GHCR）。
  2. 用户通过 TrueNAS UI 的 「Custom App」向导（指向镜像、配 env / volume / port）或直接贴 Docker Compose YAML 安装。
  3. 除非你的应用被合并进官方 truenas/apps（走 PR），否则没有商店列表、没有可发现性、没有审核。

结论：在 TrueNAS 上让应用「跑起来」极容易（就是 Docker），但拿到「可发现性」很难——官方目录是 PR 制，第三方目录被砍。任何讲 k3s/Helm/TrueCharts/「Add Catalog」的旧教程在 2026 年都已过时。

Unraid —— Community Applications 是事实上的商店

Unraid 的「应用」就是 Docker 容器 + 一个 XML 模板（定义镜像、网络、端口、路径、变量，装在 /boot/config/plugins/dockerMan/templates-user）。没有原生包格式，没有签名。

分发渠道是 Community Applications（CA）——一个社区维护的插件，几乎每个 Unraid 用户都装，聚合了 2000+ 个 Docker 容器和插件，事实上就是 Unraid 的应用商店（由社区运营，非官方公司产品）。

上架流程是所有平台里最轻的：把模板 XML 放在一个 GitHub 仓库里 → 提交仓库 URL 到 ca.unraid.net/submit（或论坛提交帖）→ 人工过一遍轻量审核 → 进入默认仓库列表，对几乎所有 Unraid 用户可见。参考模板仓库 github.com/selfhosters/unRAID-CA-templates、模板编写指南 selfhosters.net/docker/templating/templating/。

坑：Unraid 的 volume 映射用的是共享（share）路径（/mnt/user/...），不是任意 host 路径；模板不按 share 映射，用户会困惑。XML 模板是 Unraid 专有格式，不可移植——保持 Docker 镜像通用，单独配一份 Unraid 模板。

飞牛 fnOS —— .fpk 封装 Docker，社区商店已成型

飞牛的 .fpk 是它自己的私有格式，但底层就是 Docker 镜像 + docker-compose.yml + 元数据，被社区形容为「fnOS 的 APK/IPA」。用官方 fnpack（社区封装 fnpackup）打包。官方目前没有公开的开发者门户或 API，上架靠申请：飞书表单 trim-nas.feishu.cn/share、商业联系 jubao@infinities.com.cn、社区 club.fnnas.com（版块「应用中心&Docker」）。

但侧载通道完全开放，是个人开发者的实际路径：

  • 手动 .fpk 安装：应用中心 → 设置 → 手动安装 → 上传 .fpk（2025 年 11 月起官方开放离线安装）。
  • Docker：一等公民，官方很多应用本身就是容器，完整支持 Compose。
  • SSH：系统设置 → 终端和 SNMP 开启（默认禁 root 登录，sudo passwd root 后改 sshd_config）。

社区生态已经长出来了：github.com/conversun/fnos-apps 是第三方商店，115 个自托管应用打包成 `.fpk（Plex、Emby、Jellyfin、qBittorrent、Immich 等），每日自动同步。另有社区「FnDepot」去中心化应用源规范。

坑：.fpk 的 tag 不匹配坑——compose 里写裸 tag 1.0.x 但镜像推了 v1.0.x，安装会报误导性的 manifest unknown / EOF；.fpk 规范没有官方文档，靠社区项目逆向。

极空间 ZSpace（ZOS）—— 商店审核制，实际靠 Docker

极空间没有公开的原生打包格式，分发实质是 Docker 镜像 + 审核制官方应用。2025 年 10 月的新应用商店分三类：官方应用、第三方应用、Docker 应用，支持热更新。

个人开发者路径偏窄：商店没有公开自助门户，第三方应用靠授权合作——极空间和上游应用作者谈下授权后上架。消费级的「开放平台」只在企业 EZOS 线宣布过，没有公开的自助注册。实际可走的是 Docker（2025 年 4 月起支持 Compose）和 SSH（系统设置开启，admin 登录后 sudo -i 拿 root，提示符显示 ZOS）。

坑：SSH 配置在部分系统更新后会被重置，可能要重新开；商店很新，第三方目录小且受控。

绿联 UGOS / UGOS Pro —— 国产里对开发者最开放

绿联是国产 NAS 里唯一有公开、面向个人开发者的正式门户的。「绿联云开发者平台」developer.ugnas.com 在 2026 年 5 月 22 日正式上线（公告 lulian.cn/news/2185.html），定位全球化，首批合作方包括腾讯游戏、MiniMax。

应用跑在 Docker 上（社区票选「年度最佳功能」），商店用一键安装封装容器，自动处理 volume 映射、PUID / 权限。流程：developer.ugnas.com 申请（或邮件 developers_bd@ugreen.com）→ 提交应用 → 绿联审核 → 上架 UGOS Pro 应用中心 → 用户一键安装，30 天全功能免费试用。面向个人和团队，未披露注册费、保证金或分成比例（商业化条款需单独确认）。

侧载也全开：Docker（应用中心里先开启，默认关）、SSH。UGOS Pro SSH 在控制面板 → 终端机开启（端口 22）；老 UGOS 在设备管理 → 调试功能，端口 922——两代路径不同，别搞混。

坑：定位「低门槛入驻、高标准审核」——进去容易，过审（安全 + 体验）严；商业化条款不公开，要单独谈；开发者平台 2026 年 5 月才上线，生态还在起步，变动会快。

开源 NAS 与路由器 OS：系统包管理器为主

OpenMediaVault（OMV）—— Debian + apt，Docker 靠 OMV-Extras

OMV 是基于 Debian 的开源 NAS，没有自有应用商店，应用分发走 Debian 的 apt 包管理器 + Web UI 插件系统。装 Docker 的标准路径是装 OMV-Extras（wiki.omv-extras.org）：System → Plugins 搜 compose → 装 openmediavault-compose（OMV7 是 7.x，OMV8 是 8.x）→ Services → Compose → Settings → 「Reinstall Docker」→ 之后直接在 Web UI 里跑 docker-compose.yml。

个人开发者发应用到 OMV，就是发一个 Docker 镜像 + 一份 compose 文件，没有商店、没有审核、没有可发现性——OMV 的哲学是「你自己是管理员」。Debian 原生包想进官方仓库就走 Debian 标准的打包/赞助流程，与 NAS 无关。

OpenWrt —— 从 .ipk/opkg 迁到 .apk，LuCI 应用是标配

这是路由器 OS 里必须讲清的大迁移。OpenWrt 25.12（内核 6.12）起，apk（Alpine 的包管理器）成为默认，.apk 是包格式；传统的 opkg / .ipk 在 ≤ 24.10 仍用、装機量巨大但已被废弃。官方有「opkg to apk cheat sheet」。快照分支 2024 年底起就 apk-first 了。

打包路径：

  • Buildroot / SDK：每个包是 package/ 下的一个 Makefile，用 define Package/... 块。个人开发者用 OpenWrt SDK 单独构建一个包，不必编译整棵树。
  • 官方 feed：github.com/openwrt/packages（社区应用/库）、github.com/openwrt/luci（LuCI Web UI 应用 luci-app-*）。提交历史上是邮件 patch 带 Signed-off-by:，现在 GitHub PR 也明确接受。
  • 签名：仓库签名。opkg 用 usign（Ed25519，公钥在 /etc/opkg/keys/，校验 Packages.sig）；apk 时代支持本地签名密钥（2024 年 10 月落地）。
  • LuCI 应用：luci-app-foo = LuCI 管理界面上的一个 Web 页面，结构是 Makefile + controller + CBI model + 静态资源。这是 OpenWrt 上发「可配置应用」的标配方式。

**Attended Sysupgrade（ASU）**是分发语境里必须提的：标准 sysupgrade 会擦掉后装的应用，ASU（auc CLI 或 luci-app-attendedsysupgrade，或新工具 owut）把主板 + 已装包列表发给 sysupgrade.openwrt.org（代码 github.com/openwrt/asu），按需重建一个定制固件。进了官方 feed 的包会自动进 ASU 重建镜像，自托管的 feed 则不会——这是「进官方 feed」的实际价值。

坑：默认 musl libc（不是 glibc），预编译 glibc 二进制跑不了；没有 systemd，init 是 procd；很多设备 flash 只有 8/16/32 MB，重应用必须放外部存储；内核与 kmod 版本强绑定。个人开发者现实路径：要么进官方 feed（要过质量门槛和 maintainer 审核），要么自托管一个签名 feed（ipk/apk 放 GitHub Pages，用户加到 opkg.conf/apk 配置），后者更现实。

ImmortalWrt —— OpenWrt 国行 fork，包更多

ImmortalWrt 是 OpenWrt 的 fork（github.com/immortalwrt/immortalwrt），定位「为大陆用户加更多包、更多设备、默认优化与本地化」。维护自己的 feed（github.com/immortalwrt/packages），加了大量进不了上游的 China-specific 应用（代理、本地服务、驱动）。固件选择器 firmware-selector.immortalwrt.org。

发布意义上：应用进不了上游 OpenWrt 审核的，可能进得了 ImmortalWrt。约束和 OpenWrt 一样（musl、无 systemd、BusyBox），同步推进 apk 迁移，国内有 CERNET / 南大镜像加速。

OpenWrt 上的容器 —— 重应用的事实路径

路由器上跑重应用（比一个 LuCI 配置页大的任何东西），主流是 Docker/OCI 镜像：

  • 装宿主侧：dockerd + docker-compose + luci-app-dockerman（装它会拉依赖），或 luci-app-docker，或 Podman。LXC 也支持（lxc + luci-app-lxc，共享宿主内核）。
  • 分发：标准 Docker/OCI 镜像，走任何 registry，没有 OpenWrt 专有的容器打包。
  • 前提：需要真实磁盘，只有内置 flash 的设备要先挂外部存储 / overlay。

这是个人开发者的阻力最小路径——绕开 musl / flash / 内核版本约束，镜像自带 userspace。反过来，OpenWrt 自己也能跑在 Docker/LXC 里（AlbrechtL/openwrt-docker、wukongdaily/openwrt-istoreos），常用于 x86 NUC / Proxmox 上的「旁路由」——别和「在 OpenWrt 上跑容器」搞混。

iStoreOS / iStore —— OpenWrt 之上的应用商店聚合层

iStoreOS 是易有云（LinkEase）团队基于官方 OpenWrt 做的路由器 / NAS OS，标志性特性是 iStore 应用商店。关键区别：iStore 本身是 OpenWrt 的 .ipk 包（luci-app-store + luci-lib-taskd 等，从 istore.linkease.com/repo/all/store/ 下），但商店里的应用是混合的——轻量的是标准 luci-app-* .ipk，重的是 Docker 容器配一键安装入口。所以 iStore 不是纯 Docker 商店，而是 ipk 插件 + Docker 镜像的统一门面，「Docker」标签页 + DPanel 管理容器侧。

仓库：github.com/linkease/istore（UI：github.com/linkease/istore-ui），包缓存 github.com/linkease/istore-packages（防止插件突发更新搞坏固件）。文档 doc.istoreos.com/zh/guide/istore/。

上架路径（没有公开的正式提交规范，据仓库和社区指引推断）：把应用打包成标准 OpenWrt luci-app-* ipk 或 Docker 镜像 → 在 github.com/linkease/istore 或 github.com/linkease/istore-packages 开 issue / PR → 易有云审核，通过则收录，依赖可能被缓存进 istore-packages。社区（koolcenter.com）把提交问题统一导向 github.com/linkease/istore/issues，印证 GitHub 就是渠道。接受标准不公开，建议先开 issue 问。

坑：iStore 商店域名（istoreos.com、linkease.com）必须直连（DNS / 白名单问题是最常见报告）；iStoreOS 上的 Docker 需要足够存储（官方的「iStore 增强」工具部分就是为镜像源加速）；主要目标是 x86-64 和 arm64。

两个进不去的平台

华为家庭存储：没有面向第三方开发者的应用分发机制。只有少量官方合作插件（百度网盘 / 迅雷 / 玩物）通过「智慧生活」App 安装。没有开放平台、没有 SDK、没有商店。Docker 至今未上线（2022 预售承诺「以后会有」，到 2026 年中仍未交付），SSH 也不提供——这是社区最大抱怨。目标是在上面跑自研应用，目前无路。

联想个人云：基本是封闭设备。没有真正的应用商店或自有打包格式，没有公开开发者门户。Docker 在部分新固件里预装但仍是 beta / 非官方；SSH 不官方暴露，靠客户端「远程协助」开，或刷社区改版固件拿 root（TTL 后 22 端口 root 登录，盘挂在 /sata）。只能算极客通道，不是发布平台。

几个可直接套用的场景映射：

  • 「我就一个 Docker 镜像，想最快通吃」：多架构 OCI 镜像（amd64+arm64）推 Docker Hub + 阿里云 registry.cn，配一份通用 docker-compose.yml。飞牛、极空间、绿联、铁威马、TrueNAS、Unraid、QNAP（Container Station）、OMV 全覆盖。先发这套，商店是后面的事。
  • 「我要国产 NAS 商店曝光」：先绿联（唯一有公开门户），再飞牛 .fpk 社区商店（conversun/fnos-apps），极空间走商务谈授权。
  • 「我要国际 NAS 商店曝光」：群晖发 SynoCommunity（不是官方套件中心），QNAP 发 Container Station 的 Docker，Unraid 发 CA 模板（最轻），TrueNAS 走 Custom App（拿不到可发现性，认了）。
  • 「路由器原生轻应用」：OpenWrt 打 luci-app-foo 的 ipk/apk，自托管签名 feed；想进官方 feed 走 PR；China-specific 的考虑 ImmortalWrt。
  • 「重应用要跑在路由器上」：别打原生包，发 Docker 镜像，靠 luci-app-dockerman / iStore 的 Docker 标签页落地。
  • 华为 / 联想：放弃官方分发，别投入。

几个常见误读

「NAS 应用商店和手机应用商店一样，注册就能上」——不是。群晖、QNAP 是审核制且要签协议；极空间是授权合作制；TrueNAS 根本没有传统意义的商店。只有绿联（国产）和 Unraid 的 CA（国际）算接近「注册即上」的轻量流程。

「Docker 镜像发上去就等于上架了」——取决于平台。Unraid/绿联的 Docker 封装带商店列表；TrueNAS 的 Custom App 是「能跑但没列表」；飞牛要再包成 .fpk 才进社区商店。镜像落地 ≠ 商店可发现性。

「按 TrueNAS 旧教程加 custom train 就行」——2024 年 10 月起失效。24.10 砍了 k3s 和「Add Catalog」，TrueCharts 已退场。2026 年的 TrueNAS 只有官方目录（PR 制）和 Custom App / Compose 直贴。

「OpenWrt 还是 opkg + .ipk」——25.12 起默认是 apk + .apk。快照分支 2024 年底就迁了。新写的打包脚本要同时产出 ipk 和 apk，或只针对目标版本。

「iStoreOS = 纯 Docker 商店」——不是。iStore 是 ipk 插件（轻量 luci-app-*）和 Docker 容器（重应用）的统一门面，两套并存。

「签名是各平台的硬门槛」——只有群晖、QNAP 有明确官方签名流程且必须走它。其余平台（尤其国产）签名要求未公开，门槛是审核而非密码学签名。别把「未公开」当成「有强制签名」。
