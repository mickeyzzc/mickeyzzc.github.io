告警工具技术调研：核心实现拆解与自研空间评估（2026）

October 28, 2026 October 28, 2026 可观测性 告警, On-Call, 通知推送, 技术调研 可观测性系列 5271 字 11 分钟阅读
🔊

我打算做一个告警 / 通知类的工具，动手之前先把现有玩家的技术实现摸了一遍：核心机制是什么、哪些设计能直接借鉴、每一层还有没有进场空间。这篇是调研结果，不是选型导购，评估结论放在最后一节。文中机制均对照源码或官方文档核实（2026-10），star 数来自 GitHub API 同一时点。

框架：先把它们放进四层里

  • L1 通知投递：只负责把消息送到手机上。
  • L2 告警路由 / 聚合 / 降噪：接收上游事件，去重、分级、静默、按规则转发。
  • L3 事故管理 / On-call：值班排班、升级策略、事故时间线、复盘、电话呼叫。
  • L4 一体化平台：指标 + 日志 + 链路 + 告警打包成一个产品。

采集（Prometheus、Zabbix 这类）算 L0，不展开。一条告警从产生到值班人确认的路径：

推送层：门槛不在代码，在通道

同一层里六个代表项目的实现路径先横比一遍：

项目发消息到手机的通道可借鉴点
ntfyHTTP PUT / POST 到 /topicFCM 桥 + 应用内长连接topic 即 URL；SQLite 缓存离线补发
GotifyREST API无 FCM，客户端 WebSocket 保活app / client 双层 token
Apprise库调用 / 常驻 API不直接到手机，扇出到下游渠道URL scheme 插件注册表
BarkHTTP API直连 APNsdevice key 即 URL，通道即产品
Server酱HTTP API微信服务号模板消息通道资质即壁垒
PushDeerHTTP API服务号 + APNs 客户端同上，多端覆盖

ntfy——最值得抄的极简模型

机制：服务端是个极简的 topic 消息 broker，topic 就是 URL 路径，发布不需要注册，HTTP PUT / POST 带 X-Title / X-Priority / X-Tags 这些头就是完整的写入协议。订阅端按场景选形态：HTTP 长连接的 JSON / SSE 流、WebSocket、或 poll=1 + since= 的一次性拉取——since= 可以传时间戳、时长或消息 ID，离线期间漏掉的消息从服务端 SQLite 缓存里回放（单 topic 回放上限 10MB，超出截断并回 X-Messages-Truncated 头）。消息体是固定 JSON schema（id / time / event / priority / tags / actions / attachment），Android 端由 FCM 桥唤醒 app 再连流。附件单独上传落磁盘，消息里只带 URL 和元数据。

自研视角：整个服务端用 Go 起个雏形的工作量很小，说明 L1 的代码不是壁垒。真正的壁垒是通道：Android 保活要 FCM（海外）或厂商推送通道（国内，要企业资质），iOS 要 APNs 的 .p8 凭据，微信触达要服务号资质。Bark 和 Server酱能立住，靠的是通道，不是代码。

Gotify / Apprise——两个可以直接借鉴的接口设计

  • Gotify：应用 token 发、客户端 token 收，REST 入、WebSocket 出。消息落服务端数据库，客户端靠 WebSocket 订阅实时拉新、重连后从库里补——“存储与推送解耦"这个模式照抄比自己发明强。app 与 client 双层 token 是干净的权限模型：应用只能写、客户端只能读。
  • Apprise：最值得借鉴的是扩展模式——每个通知渠道是一个 URL scheme 解析器（bark://host/key、discord://id/token），配置即字符串，加渠道不改调用方。核心库是纯 Python 的无状态转换器：输入统一的 Notify 对象，路由到对应 scheme 的插件序列化成该渠道的 API 调用。想做"万能通知出口”，直接按这个模式写插件注册表。

路由与降噪层：算法密度最高的一层

Alertmanager——事实标准的四个核心设计

  • 去重与路由：每条告警按标签集算出 fingerprint 作为唯一标识，同一 fingerprint 的告警折叠成一条流；route 是嵌套 matchers 组成的树，告警沿树向下走到最深匹配节点，子 route 继承父配置，continue 标志决定匹配后是否继续下探——新服务、新团队的分流规则天然可扩展。
  • 分组：group_by 指定标签集合作为聚合键，同组告警在 group_wait 后合并发一条；group_interval 控制组内新增告警的跟进节奏；repeat_interval 控制未恢复告警的重发周期。三个时间参数的组合基本覆盖了"别刷屏"的全部需求。另有一个 per-alertname 上限开关，同名告警洪水时先砍数量保可用性。
  • 静默与抑制：silence 是"matchers + 时间窗"的手动静默；inhibition 是"A 发生时抑制 B"的规则（source_matchers 命中 + target_matchers 命中 + equal 标签相等），机房级故障压住实例级告警就靠它。
  • 高可用：Prometheus 向全部副本推送，不做负载均衡；副本间用 gossip 协议（memberlist）同步静默表和发送状态，同一通知只由一个副本发出。

自研视角：路由树 + 分组窗口已经是事实标准，重写没有差异化。Alertmanager 是 Apache-2.0 的 Go 单二进制，带静默管理 API——自研要么直接消费它，要么把这套语义抄完整，半吊子没人用。

Healthchecks——状态机可以直接照搬

机制：每个检查 = Period（预期心跳间隔）+ Grace Time（迟到宽限），或用 cron 表达式定义预期节奏（内部用 cronsim 求值，比 crontab 多了时区和秒级语义）；HTTP / 邮件 ping 驱动 up / down / late 状态翻转，翻转即事件，事件触发通知。内置 smtpd 收邮件心跳，通知出口预装 Apprise；每个检查暴露独立的 ping URL，脚本、cron、K8s Job 往 URL 打一次就算心跳，配合 Prometheus 抓的 /metrics 端点可直接观测检查自身的健康。

自研视角：死人开关是完整告警产品里最容易做的一块，Period + Grace 的模型和状态翻转逻辑直接照搬，别自己发明一套。

监控与告警平台层：已被占满

Uptime Kuma——单进程全家桶的范本

机制：Node.js 单进程，探测调度在进程内跑周期任务（最短 20 秒间隔），支持 HTTP(s) / TCP / 关键字 / JSON 查询 / WebSocket / Ping / DNS / Push / Docker 容器等十来种探测器；结果经 Socket.IO 推给前端，SQLite 单文件存储，90+ 通知渠道全在进程内实现。没有消息队列，没有微服务拆分——它证明了这个体量的产品单进程就够了。

自研视角：9.3 万 star、免费、一个 Docker 起服务，这个层没有进场空间。单进程架构本身值得中小产品借鉴。

夜莺 n9e——“不接管存储"是最值得抄的架构决策

机制：把 Prometheus / VictoriaMetrics / Elasticsearch / ClickHouse / Loki 注册成数据源，告警规则统一存在 n9e，由内置引擎对异构数据源做统一评估（规则表达式可以是 PromQL、日志查询或 SQL）——存储和采集全部复用现成生态，自己只做告警平面。事件进来后走处理管道：改写与富化标签、订阅、静默、条件路由分流，全程留执行记录（评估查询、事件、通知结果都可回查）；规则分布在多个评估引擎上，n9e-edge 可以把评估推到靠近远端数据源的位置执行。v9 的 AI 助手和 MCP Server 就架在告警事件流上。

自研视角：这是国内做告警层的正面参照，也意味着"再做一个开源告警层"没有空间。值得抄的是架构决策：不要自己造存储，把现成 TSDB 和日志库变成数据源；事件处理做成显式管道而不是散在代码里的 if。

L0 / L2 层四个代表放在一起：

项目层核心机制自研空间判断
AlertmanagerL2路由树 + 分组三参数 + 抑制 + gossip HA语义即标准，抄全或消费 API
HealthchecksL2 兜底Period / Grace / cron + 状态翻转可做完整产品里的一块，状态机照搬
Uptime KumaL0+L2Node 单进程 + Socket.IO + SQLite免费且 9.3 万 star，无进场空间
夜莺 n9eL2+L4数据源注册 + 统一规则评估，不碰存储正面参照，别再做开源告警层

On-call 与事故管理层：技术上最重的一块

PagerDuty——值班调度引擎拆解

  • 事件侧：Events API v2，外部监控 POST 一个事件（event_action 取 trigger / ack / resolve，带 dedup_key），同一 dedup_key 的事件折叠进同一个 incident 的生命周期。
  • 调度侧：值班表 = 多层轮换（每层有轮换时长、起始偏移、时间窗 restriction）按优先级叠加，override 临时插入；升级策略 = 一串"通知目标 + escalation_delay”，超时未认领自动跳下一级，直到有人确认。电话呼叫经 PSTN 网关打出。

自研视角：调度引擎是最重的工程量，也是这层的全部门槛。算法本身是公开文档化的成熟设计，按文档实现不难，难点全在边界情况：跨时区轮换、假期日历、覆盖嵌套、夜班互换。

incident.io / Rootly——两个可借鉴的产品形态

  • incident.io：整个产品挂在 Slack 上——Slack App 接收斜杠命令和按钮回调，事故频道自动创建、频道内时间线滚动、角色认领与状态变更都是 Slack 交互驱动；事件从检测到关闭的生命周期在 Slack 侧完成，Web 控制台做配置和复盘。AI 调查和 MCP 是架在事件流上的附加层（官网称为 Nexus 生产智能模型）。
  • Rootly：API 优先，所有对象（事故、排班、升级策略）先有 API 再有 UI，排班和策略带 Terraform Provider，一切状态可代码化——这是客户敢从 PagerDuty 迁过来的前提。

自研视角：协同层最值得借鉴的一点是"事故的一切状态可导出"。Opsgenie 用户被迫迁移的当下，迁移能力（导入器 + 双跑切换）本身就是产品功能，值得作为自研产品的第一优先级设计目标。

Grafana OnCall——一个反面教材

机制：Django / Celery 后端 + Grafana 插件前端，认证依赖 Grafana 的 externalServiceAccounts 特性开关，短信电话要么自配 Twilio 要么走 Grafana Cloud。开源版 2025 年 3 月进维护模式，2026 年 3 月归档。

自研视角：开源版强绑自家平台的结局就是被归档。要么开源版真正独立，要么明说引导上云，别做中间态。

机会评估：如果自研，我会怎么做

三条已核实的市场事实先摆出来：海外 on-call 单价 19-20 美元 / 用户 / 月（incident.io、Rootly 官网价），企业愿意为这层付费；Opsgenie 2027-04-05 关停，Atlassian 官方要求此前完成迁移；PagerDuty 股价较峰值跌约七成、2026 年 8 月裁员 15%（Nasdaq 行情与财报），龙头增长见顶。

  • 红海，别做：L1 推送（ntfy 3.5 万 star、Bark、Server酱、PushDeer，免费且成熟）、L0 监控（Uptime Kuma 9.3 万 star）、L2 路由（Alertmanager 事实标准 + Apprise 扇出）。共同点：免费、一两个人就能维护、没有付费空间。
  • 不现实，别碰：对标 PagerDuty / incident.io 的全球 SaaS。调度引擎可以按公开文档实现，但品牌、生态集成、资金是十年积累，后进者没有位置。
  • 有缝隙的三个方向：
    1. 国内原生 on-call。Opsgenie 退出、incident.io / Rootly 不支持国内 IM 和电话通道、夜莺的重心在告警规则而非事故协同。做"企微 / 钉钉 / 飞书 + 电话升级 + 排班引擎 + 复盘"的私有化产品，是对着迁移窗口进场。
    2. 国内通道插件。给 Apprise / Bark 补微信服务号、厂商推送通道的插件——小切口，先验证通道资质拿不拿得到，再谈产品。
    3. Opsgenie 迁移助手。2026-2027 窗口期的一次性生意，做成迁移工具或服务都行。
  • AI 的定位：夜莺、incident.io、Rootly 都把 AI 架在告警事件流上，说明 AI 是附加层，不是产品主体。自研时 MCP 接入是低成本加分项，别当卖点。

最后一层现实：这批项目大多一两个人维护，能养活自己的要么背后有商业公司（夜莺之于快猫星云），要么靠赞助（Uptime Kuma）。动手前先想清楚变现路径，否则大概率是又一个停更仓库。
