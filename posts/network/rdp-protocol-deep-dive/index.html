RDP 协议深度拆解：连接序列、图形管线与 UDP 传输

October 8, 2026 October 9, 2026 网络技术 RDP, 协议分析, MS-RDPBCGR, MS-RDPEGFX, MS-RDPEUDP, CredSSP, AVC444, 虚拟通道 网络开发实战 7552 字 16 分钟阅读
🔊

RDP 是这个星球上部署量最大的远程图形协议，但中文世界对它的理解大多停在"3389 端口 + mstsc 客户端"。微软把整套规范开放在 MS-RDP 系列文档里（learn.microsoft.com），协议本身值得认真读一遍：它是一个把"语义传输、混合编码、多通道复用、安全协商"四件事装进一个会话里的完整设计，很多取舍在自研远程方案时都能直接借鉴。

前文《远程桌面与远程终端技术方案全面调研》给出了全景，本文只拆 RDP 一个协议。全文按一次连接"从生到死"的时间顺序展开：先看两个端点之间怎么把连接建立起来（协议栈分层、五步握手），再看建立之后图形数据怎么传（图形管线、UDP 传输），最后看安全层怎么演进、每一帧怎么被调度。文中每条结论都标注了规范出处（MS-RDPBCGR、MS-RDPEGFX、MS-RDPEUDP、MS-CSSP），版本基线是现行的 Windows Server 2025 / Windows 11 24H2 一代客户端与服务端。

协议栈分层：PDU 套 PDU

先建立整体图景，再谈细节。看 RDP 的抓包你会发现，每个包都是"套娃"——图形数据外面套了好几层头，每层各干一件小事。协议文档里把这些封装后的包叫 PDU（Protocol Data Unit，协议数据单元），下文会反复用到这个词，记住它就是"一个完整的协议包"即可。

一条 TCP 3389 连接上，自内而外是这么叠的：

动画跟着一条绘图指令走完全程：它在 RDP 层产生，往下每经过一层就多包一层"信封"，右侧面板同步显示这个包当前的完整结构。四个信封各管一件事：

  • MCS 层（T.125，Multipoint Communication Service，多点通信服务）：把一条 TCP 连接"虚拟"成多条独立通道——剪贴板、声音、打印、图形各走各的，互不阻塞。包头里的通道号就是每条逻辑流的门牌号
  • 安全层：对数据加密、校验完整性，具体用 TLS 还是老式 RC4 由协商决定（安全层一节细说）
  • X.224：ISO 家族的面向连接传输协议，一个比 TCP 还老一辈的经典。RDP 借它做两件事：提供稳定的包传输，以及借它的握手报文完成第一轮安全协商（下一节的主角）
  • TPKT（RFC 1006）：名字唬人，干的活最简单——在每个包前面加 4 字节（版本号 + 长度），让接收方能从 TCP 字节流里准确切出一个完整的包。抓包时最先看到的就是它

这套分层是从 ITU-T T.120 系列会议协议继承来的（RDP 的前身是 T.128 应用扩展），所以术语里满是 MCS、GCC 这种老电信味——不是微软故意绕，是协议的族谱如此。规范文档对应关系：连接序列与通道在 MS-RDPBCGR（基础连接与图形远程），图形管线扩展在 MS-RDPEGFX，UDP 传输在 MS-RDPEUDP，CredSSP 在 MS-CSSP。

栈看清了，接下来按真实的时间顺序走一遍连接的建立。

连接序列：五道关，认证不过全免谈

RDP 建立一个会话要过五道关。为什么这么繁琐？核心原因只有一个：把认证放在最前面，认证不过，后面所有协议状态机都不存在——BlueKeep 那样的认证前攻击面就是这么被砍掉的（安全层一节细说）。五道关依次是：

动画里五条消息依次点亮，前两关解决"你是谁"，后三关解决"我们怎么干活"。每条消息对应下文一个小节。

第①关：X.224 协商——先对暗号

客户端发 X.224 Connection Request，里面带一个 RDP_NEG_REQ 结构。这一步像是双方对暗号：客户端列出自己支持的安全方式（requestedProtocols 位掩码），服务器从中拍板。

协议标志含义
PROTOCOL_RDP (0x00)旧版 RDP 安全层（RC4 加密，见安全层一节）
PROTOCOL_SSL (0x01)标准 TLS，认证仍靠 RDP 层的登录表单
PROTOCOL_HYBRID (0x02)TLS + CredSSP，即 NLA
PROTOCOL_HYBRID_EX (0x08)CredSSP + 提前用户授权（RD Gateway 场景）
PROTOCOL_RDSTLS (0x04)微软自定义的 RDSTLS 包装
PROTOCOL_RDSAAD (0x10)Microsoft Entra ID（原 AAD）认证，AVD/Windows 365 用（learn.microsoft.com）

服务器回 Connection Confirm 带 RDP_NEG_RSP，selectedProtocol 字段拍板用哪个。如果都不支持，回 RDP_NEG_FAILURE——很多"连不上"的诊断在这一步就该看，而不是等图形阶段报错。mstsc 与 FreeRDP 对 PROTOCOL_HYBRID_EX、RDSAAD 的支持差异，是某些 AVD 场景"Windows 客户端能连、第三方客户端不能连"的直接原因。

第②关：安全握手——验明正身

协商结果决定这一步做什么：

  • PROTOCOL_RDP：走老式的 Security Exchange PDU——客户端生成随机数，用服务器证书（512 位 RSA）加密后送上，双方用 MD5/SHA-1 派生 RC4 会话密钥。这条路在现代系统上应视为遗留
  • PROTOCOL_SSL：标准 TLS 握手，之后登录凭据在 RDP 会话里以表单形式提交（这就是"没开 NLA 时先弹登录界面"的由来——认证前协议栈已经全开）
  • PROTOCOL_HYBRID：TLS 握手之后接 CredSSP（MS-CSSP，微软的凭据委派框架，负责把 Windows 登录凭据安全地递给服务器）。CredSSP 是 SPNEGO 的搬运工——SPNEGO 是 Windows 单点登录的协商外壳，通常里面跑的就是 NTLMSSP 的质询-响应三步（域内则用 Kerberos）。中间有个 pubKeyAuth 字段：客户端把 TLS 证书公钥的哈希再加密一份传给服务器，用来检测"TLS 层之下还有人在改包"的中间人；最后 authInfo 字段把用户凭据加密送达。NLA 的全部意义在这一步兑现：认证完成前，MCS 通道、图形管线一概不存在——第①②关正是第③关之后一切的前置门禁

CredSSP 完成前连接只有 TLS 上的几个 TSRequest 报文；认证失败服务器直接断开，这也是 NLA 环境下暴力破解在 RDP 日志里表现为"连接建立即断"的原因。

第③关：MCS Connect——报出家底

MCS Connect Initial PDU 里塞着 GCC（Generic Conference Control，通用会议控制，可以理解为"会话参数总表"）Conference Create Request，客户端把所有自我描述一次性报出：版本（clientVersion）、桌面尺寸与颜色深度、键盘布局与 IME 状态、支持的加密级别、以及要 join 的虚拟通道清单（cliprdr 剪贴板、rdpsnd 声音、rdpdr 打印、drdynvc 动态通道……）。服务器在 MCS Connect Response 里确认。这一步是抓包判断客户端类型/版本最有效的一段——每个实现填的 core data 都略有指纹差异。

第④关：Channel Join——通道逐个点名

MCS 层的三板斧：Erect Domain（建域）、Attach User（拿到 userID）、然后客户端对声明的每个通道逐一发 Channel Join Request，服务器逐一确认。静态虚拟通道（SVC）在这里成型；动态虚拟通道（DVC，MS-RDPEDYC）只 join 一个 drdynvc 通道，之后 EGFX、Display 更新、视频重定向等再在它上面动态开子通道——这是 RDP 8.0 之后加功能不用改基础握手的关键设计。

第⑤关：能力协商——服务器先摊牌

服务器发 Demand Active PDU，把自己支持的所有能力集（capability sets，一组组"我会什么"的参数清单）一次性摊牌：位图缓存参数、绘图指令支持位、字形缓存分级、指针、声音、虚拟通道参数，以及 EGFX 的版本能力。客户端过滤出双方交集后回 Confirm Active PDU。随后是 Sync、Control（Cooperate/Request，决定谁有输入控制权——多用户协作会话的基础）、Font List/Font Map 三组短 PDU，会话激活，图形数据开始流动。

这个"服务器先摊牌、客户端收窄"的协商模型让 RDP 能兼容二十多年的实现差异：老客户端不认识新能力集就不带它玩，新客户端则通过 EGFX caps 再做一轮图形层细分协商（下一节）。

图形管线：指令、缓存与混合编码

会话激活后，屏幕上每个变化都要从服务器送到客户端。RDP 的做法不是无脑传截图，而是按"内容是什么"分三条路线并行：文字走指令、重图形走 EGFX 编码、视频区域走硬编码视频流。

指令与缓存：文字为什么近乎免费

基础路线上，服务器发的是绘图指令（orders）而非像素。主要的三类：

  • Primary orders：GlypheIndex/FastIndex（画字）、LineTo、OpaqueRect、PatBlt、MemBlt（位块搬运）等
  • Secondary orders：缓存管理——把字形、位图、画刷放进客户端缓存
  • Alternate secondary orders：帧标记（Frame Marker）等控制语义

文字路径最能体现语义路线的带宽优势：首次绘制某字形时服务器把字形轮廓放进客户端的分级字形缓存，之后每次输出文字只发"在缓存 2 号、索引 17 的字形，画到 (x, y)"——一屏文字的增量带宽常常不到 1 KB。滚屏用 MemBlt 指令从客户端已有位图里搬，类似 VNC 的 CopyRect 但指令化。

输入方向对称：键盘鼠标事件走 Fast-Path 输入 PDU（省略 TPKT 头的紧凑格式），几字节一个事件，这是 RDP 打字跟手的基础——输入延迟永远不受图形管线拥塞影响。

EGFX：重图形走编码

RDP 8.0 起，重图形内容改走 EGFX（MS-RDPEGFX，Graphics Pipeline Extension 的简称）——一个跑在动态虚拟通道上的子协议。每个 PDU 带三字段头（cmdId、flags、pduLength），关键的报文类型：

  • CapsAdvertise / CapsConfirm：客户端报出支持的能力版本（RDPGFX_CAPVERSION_8、_81、_10 到 _10.6 系）与能力标志（AVC444、AVC444V2），服务器确认后锁定编码档位
  • StartFrame / EndFrame：把一批 wire-to-surface 操作圈成一个帧，帧内所有 surface 更新同帧呈现
  • Wire-to-Surface-1：把一段编码位图（codecId 标明：PLANAR 无损、RFX_PROGRESSIVE 渐进、AVC_H264、AVC444、AVC444V2）投递到某个 surface 的指定矩形
  • Wire-to-Surface-2：纯色填充——单色区域连编码都省了
  • FrameAcknowledge：客户端回报 frameId 与 queueDepth（客户端积压待显示的帧数），服务器据此节流编码速率

surface 是 EGFX 的核心抽象，可以理解为一块离屏画布：服务器把桌面拆成若干 surface（主屏、视频区、窗口纹理），各自独立编码更新，客户端再合成上屏。这套模型后来被几乎所有现代远程协议（WebRTC 的 track、串流引擎的 layer）以不同形式重演。

AVC444：两条 4:2:0 流拼出 4:4:4

H.264 主流硬件编码器只支持 4:2:0 采样，而桌面内容里文字边缘的色度丢失极其刺眼。AVC444 的解法是数学化的：把 4:4:4 图像拆成两个 4:2:0 流——第一个流是 YUV 的 Y 平面加降采样的 UV；第二个流（Chroma420）携带色度残差信息，客户端解码后把色度升采样还原（learn.microsoft.com MS-RDPEGFX）。两个流各走一条 Wire-to-Surface 消息、共享同一个 frameId，客户端只在整个帧到齐后才确认。

代价是编码器负载接近翻倍，所以规范提供了 v2（AVC444V2）改进压缩色度流的编码效率，且 caps 里 4:4:4 是可协商项——这也是为什么在 mstsc 的组策略里能看到"优先使用 H.264/AVC 444 图形模式"这个开关：关掉它，文字-heavy 的场景反而可能更流畅，代价是颜色精度下降。

合流后的带宽特征

现代 RDP 会话的实际带宽构成大致是：文字窗口走指令+缓存（近零），静态区域不重发，视频/动画区域走 AVC 帧流，纯色区域走填充指令。这是"语义路线"在硬件编码时代进化出的混合形态——纯语义与纯视频路线各自的短板都被补掉了。

UDP 传输：MS-RDPEUDP 的双通道

图形管线解决"传什么"，UDP 解决"在坏网络里怎么传"。TCP 之上的 RDP 有个先天缺陷：队头阻塞——一个丢包触发重传时，MCS 层之后所有 PDU 都得等它。RDP 8.0 加了 UDP 传输扩展（MS-RDPEUDP，learn.microsoft.com），设计要点：

  • 建立：TCP 会话就绪后，服务器通过动态通道向客户端发起 multitransport 隧道创建，客户端用 UDP 连回服务器的 3389——UDP 通道是服务器发起的，方向与多数人的直觉相反
  • 双模式：RDP-UDP-R（可靠模式）带序列号、ACK 与重传，语义接近 TCP 但实现更薄；RDP-UDP-L（不可靠模式）不重传，丢了就丢，靠前向纠错（FEC，给一批包附加冗余校验包，丢一两个可就地恢复、不用重传）——每个数据报带 RDPUDP_FEC_HEADER，MS-RDPEUDP2 进一步把 FEC 分组化，若干原始包配一个冗余包
  • 分流原则：容得下丢的（音频采样、视频帧）走 L 模式，一个丢包只损失一帧不阻塞后续；指令类数据走 R 模式或仍留 TCP。音频与视频在弱网下的流畅度差异，很大程度来自这条分流
  • 加密：可靠通道沿用 TLS 保护，不可靠通道用 DTLS——同一会话两种加密通道并存

在 Azure Virtual Desktop / Windows 365 的 RDP Shortpath 体系里，这套 UDP 传输被进一步前移：托管网络下客户端与 session host 直接 UDP 连通（默认 3391），公网场景用 STUN（3478）探测、必要时 TURN（443）中继，TCP 反向连接只留作控制信道与回退（learn.microsoft.com）。Shortpath 建成后，延迟与抗丢包都有可观改善——微软文档给的场景数据里，弱网下的帧率提升尤为明显。

安全层：从 RC4 到 NLA 的三代

回看连接序列的第②关会发现：安全不是这套协议的补丁，而是长在握手里的。RDP 的安全层演进是一个协议内三代同堂的样本：

代际机制状态
RDP 安全层服务器 512 位 RSA 证书 + 客户端随机数，MD5/SHA-1 派生 RC4 会话密钥（40/56/128 位）遗留，与 NLA 互斥
TLS标准 TLS 保护 MCS 层，认证靠会话内表单可用，但认证前攻击面全开
NLA (CredSSP)TLS + SPNEGO 凭据认证，认证前无 RDP 协议面当前默认

BlueKeep（CVE-2019-0708）正是第一代遗留路径上的深渊：RDP 服务器会把客户端请求 join 的通道按名字匹配到内部通道，攻击者用一个特制名字让服务器把外部通道绑到内部的 MS_T120 上，通道关闭时内核驱动 termdd.sys 触发 use-after-free，认证前即可拿到 SYSTEM 级 RCE，蠕虫化传播（thezdi.com、malwaretech.com）。它的教训是结构性的：认证前暴露的每一段协议状态机都是攻击面——NLA 之所以被微软一路推成默认，就是把整个协议面挪到认证墙之后。

当前的两条新线：其一是 NTLM 退场（Windows 11 24H2/Server 2025 移除 NTLMv1，后续默认禁用）逼迫 CredSSP 场景往 Kerberos 与证书走；其二是 Entra ID 认证（PROTOCOL_RDSAAD）把 AVD/Windows 365 的身份体系从"域账号"迁到云身份——RDP 的认证层正在第二次换代。

自适应与节流：帧是怎么被调度的

连接建好、管线选对、链路通畅之后，还剩一个问题：带宽不够时先牺牲谁？RDP 的带宽自适应不是简单的"降画质"，而是三层反馈环：

  • 帧级：StartFrame/EndFrame 圈定帧边界，客户端 FrameAcknowledge 回报 queueDepth；积压超过阈值时服务器放慢编码，等效于自适应的发送窗口
  • 区域级：客户端可用 SuppressOutput 要求服务器暂停某区域输出、RefreshRect 定向刷新——窗口最小化、离屏区域直接停止更新
  • 网络级：Network Characteristic Detection 用带时间戳的探测 PDU 测 RTT 与带宽，服务器据此调整编码参数

这套分层节流加上 EGFX 的 surface 拆分，是 RDP 在"文字跟手 + 视频流畅"两难下的工程答案。对照前文调研篇的延迟预算表：RDP 把交互输入（几字节、可靠通道）与图形负载（大帧、可降级）分开调度，正是它能在办公场景守住体验的原因。

实现视角：规范之外的现实

规范之外有三条实现侧的现实值得记录。第一，mstsc 是参考实现但不是全功能上限：AVC444V2、RDSAAD 等新特性的第三方跟进有滞后，FreeRDP 的 EGFX/RDPEUDP 覆盖度决定了 xrdp、Remmina、RustDesk（导入 RDP 桥）等生态的上限。第二，服务端编码路径受系统版本支配：同一台客户端连不同年代的 Windows，协商出的图形档位可能完全不同——排查"为什么没有走 4:4:4"要从两端的能力集日志看起，FreeRDP 的 /gfx 调试输出是顺手的工具。第三，UDP 路径的排障优先级：UDP 3389（或 Shortpath 的 3391）被中间设备拦截时客户端静默回退 TCP，“变卡但不报错"的案例，多数应在 MTU/UDP 放行策略上。

协议本体就拆到这里。把这张图拼回前文的调研篇：RDP 的连接序列对应"认证先行”，EGFX 对应"语义+视频混合"，RDPEUDP 对应"绕开队头阻塞"——三条设计决策，就是远程图形协议三十年演进的骨架。
