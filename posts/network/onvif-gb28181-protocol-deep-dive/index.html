ONVIF 与 GB/T 28181 机制拆解：设备即插即用与系统级联网的两条路线

August 10, 2026 August 16, 2026 网络技术 ONVIF, GB28181, SIP, SOAP, WS-Discovery, RTSP, 视频监控, NVR 网络开发实战 8725 字 18 分钟阅读
🔊

MiBeeNvr v0.9 把 ONVIF 自动发现做进去之后，接入层的手工配置基本消灭了。接下来评估要不要支持 GB/T 28181 上联时，我先把两个协议的机制层完整翻了一遍——发现网上大量对比文章停留在「ONVIF 是国际标准、GB28181 是国标」这种口号层面，对写代码的人来说没有信息量。这篇把两个协议拆到信令流程和报文级别：ONVIF 怎么发现设备、怎么拿到流地址；GB28181 的 20 位编码怎么寻址、INVITE 怎么协商取流、PS 封装又是什么。

先说结论：这两个协议不在一个层面上竞争。ONVIF 解决的是「NVR 和摄像头之间怎么即插即用」，GB/T 28181 解决的是「平台和平台、平台和设备之间怎么跨网跨区域联网监管」。行业里的典型架构是两者串联：摄像头经 ONVIF 接入本地 NVR，NVR 再以 GB28181 上联监管平台。

读这篇不需要预先懂 SIP 或 SOAP——遇到陌生术语先查下面的速查表，正文中第一次出现时也会顺带解释。

拉流与推流：先理解两种取流模型

这两个协议最根本的差异不是报文格式，而是谁主动。理解了这一点，后面所有机制差异都会变得自然。

拉流模型（ONVIF/RTSP）：NVR 是主动方。它先发现设备、问设备要能力清单、要流地址，然后主动连接设备把流「拉」过来。好处是控制权完全在客户端，设备不需要知道外面有谁在用它；代价是客户端必须能「找到」设备——这就是为什么 ONVIF 需要一套发现机制。

推流模型（GB28181）：设备是主动方。摄像头或下级平台主动向上一级平台注册、汇报「我在线」，之后平台想看哪路流，就发 INVITE 告诉设备「把流推到这个地址这个端口」。好处是设备只要能「够得着」平台就能工作，天然适合跨网段、跨运营商的广域网场景，平台对设备有完整的调度权；代价是必须先有一套注册和目录体系——平台得先知道「谁注册上来了、它有哪些通道」。

一个记忆方式：ONVIF 是「我去店里挑货」，GB28181 是「供应商先登记进系统，我下单让它送货」。

ONVIF 机制拆解

WS-Discovery：四步发现加取流

ONVIF 的设备发现建立在 WS-Discovery（SOAP-over-UDP）上。思路很直接：新设备接进局域网后不知道谁来用，客户端也不知道网里有什么设备，于是约定一个「公告板」——所有人都往多播组 239.255.255.250:3702 发消息。从发现到拿到可播放的流一共五步：

mermaid
flowchart TD
    A["Probe 探测<br/>多播 239.255.255.250:3702"] --> B["ProbeMatch 应答<br/>返回设备服务地址"]
    B --> C["GetCapabilities<br/>拿到各服务端点"]
    C --> D["GetProfiles<br/>拿 Profile Token"]
    D --> E["GetStreamUri<br/>返回 RTSP 地址"]
    style A fill:#FF9800,color:#fff
    style B fill:#2196F3,color:#fff
    style C fill:#2196F3,color:#fff
    style D fill:#2196F3,color:#fff
    style E fill:#4CAF50,color:#fff

逐步拆开：

  1. Probe：客户端（NVR）向多播组发一个 Probe 消息，可以在里面带 Types（想找哪类设备）和 Scopes（想找哪个范围的设备）做过滤。
  2. ProbeMatch：所有符合条件且在线的设备各自回一条 ProbeMatch，带着自己的 XAddrs（ONVIF 服务地址，如 http://192.168.1.100/onvif/device_service）、Types、Scopes。注意这一步是多对一——网里 20 台摄像头就回 20 条。
  3. GetCapabilities：客户端挑中一台，向它的 Device 服务发 SOAP 请求，拿到能力清单：Media/PTZ/Events 各服务的地址、支持的 Profile 版本等。
  4. GetProfiles：向 Media 服务要 Profile 列表。一个 Profile 是「一路流的配置」（编码、分辨率、帧率），主码流子码流各是一个 Profile。
  5. GetStreamUri：选定一个 Profile Token，换取 RTSP 地址，然后走标准 RTSP 握手（DESCRIBE → SETUP → PLAY）拉流。

这里有个生产环境绕不开的坑：多播不跨网段。VLAN 隔离、防火墙挡掉 3702 端口、AP 隔离，任何一个都会让「搜不到设备」成为疑难杂症。所以成熟 NVR 的做法是发现加扫描双路：WS-Discovery 找同网段，网段扫描（逐 IP 探测 ONVIF 服务）兜底，手动添加 IP 保底。

Profile 体系：不是所有「支持 ONVIF」都一样

看到设备标注「支持 ONVIF」先问一句支持哪个 Profile——不同 Profile 是不同的能力集合，就像「支持 WiFi」要问是 WiFi 4 还是 WiFi 6：

Profile定位核心能力状态（2026-08）
S基础流媒体音视频流、PTZ、图像、事件2027-03-31 后停止新认证
T高级流媒体H.265、元数据、HTTPS 媒体流官方推荐的 S 继任者
G录像存储录像、存储、回放管理Final
M元数据/事件AI 结构化数据、事件可走 MQTT + JSONFinal
A / C / D门禁访问控制、门锁、外设Final
V云/VSaaS云视频、WebRTC 媒体、OAuth 2.0RC 状态
Q快速接入快速发现与初始配置2022-04 已废弃

Profile S 的停发是 2025-10-09 官方公告的：它强制 username-token 认证，不符合现代网络安全建议，2027-03-31 之后厂商不能再为新设备提交 Profile S 认证，新项目应按 Profile T 设计。这个时间点对正在做接入开发的人很重要——按 S 写的认证代码三年内就要面对迁移。Profile 体系更完整的动态（V、M 的演进和门禁侧的 OSDP）在全景篇展开。

三个新手常见疑问：

  • 为什么这么繁琐？ SOAP 是 2000 年代企业级 Web Service 的主流选择，XML 自描述、跨平台、工具链成熟（WSDL 可以直接生成客户端代码）。ONVIF 2008 年立项时这是个合理选择，代价就是今天的开发者要处理大量 XML。社区实践一般不手写 SOAP，而是用 WSDL 生成或封装库（见生态篇）。
  • PasswordDigest 怎么算？ 不是简单的密码哈希：SHA1(Nonce + Created时间戳 + 密码) 再 Base64。服务端会校验时间窗口——所以客户端必须先和设备对时（GetSystemDateAndTime），否则会随机收到认证失败。这是 ONVIF 开发排前二的坑（第一是各厂商 WSDL 实现的细碎差异）。
  • 报文长什么样去哪看？ Wireshark 抓 HTTP 端口就能看到完整 XML，比读规范直观得多。

GB/T 28181 机制拆解

20 位编码：一切寻址的基础

国标体系里每个设备、每个通道、每个平台都有一个 20 位编码，信令里的 From/To/Subject 全靠它寻址——你可以把它理解成监控系统里的「身份证号 + 电话号码」。结构是 8+2+3+1+6：

段长度含义示例（34020000001320000001）
中心编码前段8行政区划码（GB/T 2260）34020000（安徽芜湖）
行业编码2行业公安分类00
类型编码3设备/系统类型132（网络摄像机）
网络标识11=公安专网 等0
序号6单位内序号000001

常见的类型编码：111=DVR、118=NVR、131/132/134=各类摄像机、200=中心信令控制服务器（平台）、216=虚拟组织。很多文章把这段写成「前 8 位区域码 + 2 位类型 + 10 位序号」，类型码实际是 3 位，还带 1 位网络标识——写解析代码时按 8+2+3+1+6 切。

从编码能读出什么？看前 8 位就知道设备归哪个行政区划管，看 3 位类型码就知道它是摄像机还是平台。级联场景下上级平台靠它做路由：编码前缀相同的归同一个下级管。

SIP 消息解剖：读懂国标信令的钥匙

GB28181 的信令是标准 SIP，抓包看到的每条消息都有固定的骨架。以 INVITE 为例，下面几个头字段是理解国标流程的钥匙：

SIP 头作用国标里的用法
From / To标识发起方和接收方各带一个 20 位国标编码
Via记录请求经过的路径，带 branch 参数标识事务响应沿 Via 原路返回；branch 每个事务必须唯一
Call-ID标识一次会话同一会话内的请求共用
Contact发送方的直接联系地址注册后平台知道往哪找设备
Subject主题（国标扩展用法）携带「发送者ID:序列号-接收者ID:序列号」，标识点播的主体
CSeq命令序列号同一会话内递增，配对请求和响应

记住一条规则：请求和响应靠 Call-ID + CSeq + Via branch 三元组配对。很多自研 SIP 栈栽在 ACK 上——ACK 属于「独立事务」，它的 Via branch 必须取新值而不是复用 INVITE 的，复用会被设备端判为非法。

注册、心跳、目录：设备怎么上线

GB28181 的设备是主动注册的，和 ONVIF 的客户端主动搜方向相反：

mermaid
sequenceDiagram
    participant D as 设备/NVR
    participant P as 国标平台
    D->>P: REGISTER（20位编码 + Expires）
    P-->>D: 401 Digest 挑战
    D->>P: REGISTER + Authorization
    P-->>D: 200 OK
    loop 每 60s（默认）
        D->>P: MESSAGE Keepalive（MANSCDP XML）
        P-->>D: 200 OK
    end
    P->>D: MESSAGE 查询 Catalog（目录）
    D-->>P: 200 OK + DeviceList 通道列表

分三段理解：

  • 注册：设备向平台发 REGISTER，带自己的 20 位编码和有效期（Expires）。平台回 401 要求认证，设备用密码算出 Digest 摘要重发，通过后回 200 OK。之后设备周期性重新注册维持状态。这是标准 SIP Digest 认证流程。
  • 心跳：注册成功后设备每 60 秒（默认值）发一条 MESSAGE，Body 是 MANSCDP 格式的 XML（CmdType=Keepalive）。平台连续 3 次收不到就判离线——这就是国标系统的「存活检测」，比 ONVIF 那种「客户端下次去连才知道设备死没死」主动得多。
  • 目录：平台向设备发 Catalog 查询，设备回通道列表（每个通道一个 20 位编码 + 名称 + 型号等）。一个 NVR 下挂 16 路摄像头，在平台看来就是一个设备带 16 个通道，之后点播都是对「通道编码」发起。

实时点播：INVITE 怎么协商取流

点播是国标的核心流程，一个完整事务如下：

mermaid
sequenceDiagram
    participant P as 国标平台
    participant D as 设备/NVR
    P->>D: INVITE（SDP：收流地址端口 + SSRC）
    D-->>P: 100 Trying
    D-->>P: 180 Ringing
    D-->>P: 200 OK（SDP：rtpmap:96 PS/90000）
    P->>D: ACK（独立事务，Via branch 必须新值）
    D-->>P: RTP/PS 推流（H.264/H.265 ES 封装进 PS）
    P->>D: BYE（任一方结束）
    D-->>P: 200 OK

几个容易踩的细节，逐个展开：

  • INVITE 里的 SDP 说了什么：c= 行是平台自己的收流 IP，m=video 端口 RTP/AVP 96 告诉设备把流推到哪个端口，a=rtpmap:96 PS/90000 约定负载格式是 PS、时钟 90kHz，y= 行（国标对 SDP 的扩展）携带 SSRC。一句话：平台把自己的「收货地址」写进 SDP，设备照单发货。
  • s= 字段区分业务：s=Play 实时、s=Playback 回放、s=Download 下载。同一个 INVITE 骨架，改一个字段就是不同业务。
  • SSRC 是流的身份：十进制数字，实时点播首位 0、回放首位 1。RTP 是无连接的裸 UDP（或 TCP）数据，平台收到一包流数据时怎么知道它属于哪次点播？靠 RTP 头里的 SSRC 和信令事务对上。
  • ACK 是独立事务：上面 SIP 解剖一节说过，branch 必须新值。
  • 媒体方向是设备推流：方向与 RTSP 拉流正好相反。这一步之后信令就闲下来了，媒体流自己跑，结束时任一方发 BYE。

PS 封装：国标开发的第一道坎

与 RTSP 那种裸 RTP 分片（H.264 按 RFC 6184 打 FU-A）不同，国标强制把编码数据先封装进 MPEG-PS（Program Stream）再交 RTP 承载。数据要经过三层包装：

mermaid
flowchart TD
    A["ES 裸流<br/>H.264/H.265 NALU"] --> B["PES 包<br/>加时间戳与流标识"]
    B --> C["PS 包<br/>00 00 01 BA 起始头"]
    C --> D["RTP 包<br/>UDP/TCP 发送"]
    style A fill:#FF9800,color:#fff
    style B fill:#2196F3,color:#fff
    style C fill:#9C27B0,color:#fff
    style D fill:#4CAF50,color:#fff

从里到外：摄像头编码器吐出 ES 裸流（H.264 的 NALU 序列）；ES 装进 PES 包，打上 90kHz 时间戳；PES 加上 PS 头（00 00 01 BA 起始码的系统头）组成 PS 包；PS 包作为 RTP 载荷发出。一个 I 帧通常单独打成一个较大的 PS 包，后续 P 帧共享时间戳规则。

为什么要多这一层？两个原因：一是 PS 与编码解耦，H.264/H.265/SVAC 都能装，2011 年定标准时这样最稳妥；二是 PS 支持音视频多路复用在一个节目流里，对讲音频可以和视频同行。代价是平台端要能解 PS、设备端要会封 PS，工具链比裸 RTP 生僻——好在 FFmpeg 和 ZLMediaKit 都有现成的 PS 解复用能力，不用手写。

2022 版还把 RTP 时间戳写成了硬性要求（条款 4.3.6）：同一帧的所有 RTP 包时间戳必须相同，跨帧必须不同。早期不少设备的实现是随意的，导致平台端组帧靠猜，这是历史兼容坑的大头。

不只是点播：国标的完整功能面

点播之外，GB28181 定义了一整套业务信令，常用的有：

业务信令要点
录像回放INVITE 带 s=Playback + 时间段，设备按录像文件推流，支持倍速（INFO 信令控制）
录像下载INVITE 带 s=Download，语义是文件传输，平台端通常要处理进度和断点
云台控制MESSAGE 携带 MANSCDP 的 PTZ 指令码（方向/速度/预置位/巡航一体制编码）
语音对讲平台向设备发起 INVITE 建立反向音频通道，音频也走 RTP
报警订阅平台订阅设备的报警事件，设备出事时主动上报 MESSAGE
图像抓拍2022 版新增（条款 9.14），平台指令设备当场出图
设备升级2022 版新增（条款 9.13），平台远程推送固件
级联下级平台作为「设备」注册到上级平台，目录逐级上报，上级跨级调度

这张功能面对照 ONVIF 的 Profile 体系看很有意思：ONVIF 把能力切成 S/G/M 等等级分别认证，GB28181 是一个标准里全定义了、按需实现。所以「国标设备」的能力差异比「ONVIF Profile S 设备」更大，对接前先查对方支持哪些信令。

2022 版新在哪

GB/T 28181-2022 于 2022-12-30 发布、2023-07-01 实施，相对 2016 版的主要变化：

变化内容
编码升级正式支持 H.265 / AAC / G.722.1
RTP 时间戳硬性要求同一帧所有 RTP 包时间戳必须一致、跨帧不同（条款 4.3.6）
注册重定向302 重定向，支持平台迁移（条款 9.1.2.3）
远程升级设备软件升级信令（条款 9.13）
图像抓拍新增抓拍信令（条款 9.14）
PTZ 强化精准位置查询、巡航轨迹查询、位置变化事件订阅
安全第 8 章重写，新增「高安全级别」，与 GB 35114 国密体系对接

做平台对接时 2011/2016/2022 三个版本在野并存：新项目基本是 2022，存量设备大量是 2016，老系统里还有 2011。三版的信令细节和默认值都有差异（比如心跳周期、目录格式），版本协商是绕不开的工程量——设备注册时上报的设备类型和协议版本字段要严肃对待，别按单一版本写死。

安全机制：从 Digest 到国密

两个协议的安全栈对比：

层面ONVIFGB/T 28181
认证WS-Security UsernameToken（PasswordDigest）SIP Digest（401 挑战）
传输加密HTTPS / TLSTLS（SIPS over TLS）
高安全场景Profile T 要求 HTTPS 媒体流GB 35114：A 级 SM2 证书认证 / B 级 +SM3 逐帧签名 / C 级 +SM4 流加密

普通商用项目 Digest/TLS 就够；涉政企项目时 GB 35114 的国密三件套（SM2 椭圆曲线证书、SM3 哈希、SM4 分组加密）是验收硬指标，选信令库时提前确认国密支持。

两者关系：互补，不是替代

回到开头的问题。这两个协议的关系可以总结成三句：

  • 场景不同：多品牌混合的园区/海外项目走 ONVIF；国内政企、公安、跨区域级联走 GB28181。
  • 架构上是上下游：ONVIF 管 NVR 对设备的接入，GB28181 管 NVR 对平台的上联，现代 NVR 双栈是常态。
  • 开发成本不对称：ONVIF 是 SOAP/WSDL 的繁琐，坑浅但体力活多；GB28181 信令本身简单，但厂商兼容差异、NAT 穿透、版本碎片让它成为「坑深」的那一个。SRS 官方文档的原话是「希望大家降低期望，GB 的坑太难填了」——这句话比任何「国标很简单」的教程都诚实。

怎么抓包学习

机制读十遍不如抓一次包。两个协议都能零成本观察：

  • ONVIF：Wireshark 过滤 udp.port == 3702 看 Probe/ProbeMatch 多播交互，过滤设备 IP 的 HTTP 流看 SOAP 请求响应的完整 XML。
  • GB28181：过滤 sip 看注册的 401 挑战和心跳周期；过滤 rtp 用 Telephony → RTP → Stream Analysis 看媒体流的时间戳序列和丢包。
  • 没有真机也能搭环境：ONVIF 用模拟器（见生态篇的联调章节），GB28181 用 EasyGBD 模拟设备配 SRS/ZLMediaKit 做平台，完整闭环不需要一台摄像头。

媒体传输层（RTSP/RTP/WebRTC/RTMP/HLS/SRT）的协议内部机制我在前文做过 14 种协议的完整对比。监控协议的完整版图（GA/T 1400、JT/T 808、SVAC、GB 35114、ISAPI 等）在下一篇展开；双栈摄像头的真机表现与国际市场格局在第三篇；用什么库写进 NVR 在第四篇。
