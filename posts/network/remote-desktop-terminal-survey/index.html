远程桌面与远程终端技术方案全面调研

October 7, 2026 October 9, 2026 网络技术 远程桌面, RDP, SSH, VNC, RustDesk, 中继, 内网穿透, KVM-Over-IP, Mosh, 串流 网络开发实战 11682 字 24 分钟阅读
🔊

在一台设备上操作另一台设备，工程上拆开是三件事：把远端画面搬到本地（渲染问题）、把本地的键鼠送过去（输入问题）、在两边之间建立一条能穿过 NAT 的通道（连接问题）。前两问催生了 RDP、VNC、SSH 这些协议，第三问催生了 ID 寻址、穿透和中继网络这套基建。本文按这个拆法梳理远程桌面与远程终端的技术版图：两条渲染路线的分歧、RDP 的图形管线演进、Linux 桌面的 Wayland 变局、商业产品与 RustDesk 的连接逻辑、SSH 生态的断线补救、企业级接入层，以及 OS 之下的 KVM-over-IP 裸机层。

NAT 穿透的协议基础（STUN/TURN/ICE/DERP）在前文《P2P 信令与中继服务器技术调研》已详细拆解，本文不再重复原理，只讲产品怎么用这套东西；安防场景的落地见《NVR 远程访问 P2P 技术方案全面调研》。本文数据来自协议规范、厂商安全声明、GitHub 仓库与安全公告，关键数字标注时点或出处。

从字符到像素再到裸机：三层访问栈

远程访问工具按"离硬件多远"分层，每层解决不同的问题，也对应不同的故障假设：

    B --> C["系统层<br/>sshd · RDP 主机"]
    C --> D["裸机层<br/>BMC / KVM-over-IP"]

    style B fill:#f3e5f5,stroke:#9C27B0

    style D fill:#e8f5e9,stroke:#4CAF50

最上面的应用层是日常用的东西：字符终端（SSH）、图形桌面（RDP/VNC）、低延迟串流（Moonlight/Parsec）。中间的连接层负责把两台不在同一内网的设备连起来，商业远控和 Mesh VPN 各有一套做法。系统层假设操作系统活着——sshd 和 RDP 主机都是 OS 上的进程。最底下的裸机层连这个假设也不需要：BMC 是焊在主板上的独立小电脑，服务器没开机它也在运行，这是云厂商和机房管理数万台机器的底牌。

分层是为了划清责任：SSH 断线不是 SSH 的 bug，是 TCP 的语义；RDP 卡顿可能出在渲染也可能出在中继；这些都需要分开看。

两条渲染路线：语义与像素

所有远程图形方案都在回答同一个问题：远端屏幕变了，网络上传什么？答案分两派：

mermaid
flowchart TD
    S["屏幕变化"] --> A["语义路线<br/>RDP 绘图指令"]
    S --> B["像素路线<br/>VNC · 视频帧"]
    A --> C["带宽低<br/>绑定平台"]
    B --> D["通用性强<br/>带宽靠压缩"]
    style A fill:#e3f2fd,stroke:#2196F3
    style B fill:#fff3e0,stroke:#FF9800
    style C fill:#e3f2fd,stroke:#2196F3
    style D fill:#fff3e0,stroke:#FF9800

语义路线传输的是绘制动作：在那 (x,y) 画一行字、画个矩形、把这块缓存再画一遍。文字界面是它的主场——一行 16px 的中文，按像素传要几 KB，按"画这几个字"传只要几十字节。代价是协议要理解应用和窗口系统，平台绑定死：Windows 的绘图语义搬不到 Linux 上。

像素路线不理解内容，只传像素或视频帧。X11 时代的 VNC、今天的视频编码路线都属于这派。通用性是它的价值——任何能产出画面的系统都能被远控——带宽则全靠压缩算法和编码器撑。

两条路线的分水岭在 2010 年代中期被填平了一半：GPU 硬件编码器（NVENC、AMF、QSV）把 1080p 一帧的视频编码时间压到毫秒级，让"全屏都走视频编码"从奢侈变成日常。现代 RDP 实际是混合体——文字和窗口仍走语义指令，视频区域走 H.264/HEVC 帧，后面 RDP 一节展开。

X11：语义路线的最早实现

X11 从设计之初就是网络协议——应用是 X server 的客户端，可以跑在另一台机器上，ssh -X 把这条连接隧道加密转发而已。这是"网络透明性"的由来：单个应用的远程化是免费的。但它也是 X11 后来被诟病的根源：协议太老、通信面太宽，ssh -X 的不可信模式（X SECURITY 扩展）对现代应用基本跑不通，实践中大家用的 -Y 等于完全信任远端应用——远端进程可以监听你的键盘、抓其他窗口的内容。X forwarding 至今对跑个图形小工具有用，但作为日常远程桌面方案已经边缘化。

RDP：语义路线的集大成者

RDP 由微软从 T.128 协议发展而来，现行规范拆成一组 MS-RDP 系列（连接与图形主规范 MS-RDPBCGR、图形管线扩展 MS-RDPEGFX 等），默认端口 TCP/UDP 3389。

图形管线：从位图到混合编码

RDP 的图形演进是一条"语义不够、视频来补"的路线：

  • 早期：位图 + 绘图指令（glyph 缓存、画笔、填充），文字场景带宽极低，遇到视频和复杂图形就退化成大块位图
  • RDP 8.0（Windows Server 2012）：引入 EGFX 图形管线扩展，开始混合编码
  • RDP 8.1/10：加入 H.264 编码；AVC444 模式用两个 4:2:0 流拼出 4:4:4 色度，解决 H.264 采样掉色的问题，在 RemoteFX vGPU 场景默认开启（learn.microsoft.com）
  • 近年：Azure Virtual Desktop / Windows 365 加入 HEVC/H.265 帧编码与 RDP Multipath（learn.microsoft.com）；原生 AV1 还没进 RDP，但 Windows 侧的 DirectX 12 AV1 硬编码基建已经落地

这个混合管线的意义在于对症下药：终端窗口走指令和缓存（近乎零带宽），视频区域走硬件 H.264/HEVC（带宽可控），静态区域干脆不发。第三方实现（FreeRDP、xrdp）对 AVC444 的支持程度不一，这也是同一台 Windows 机器用不同客户端体验差距巨大的常见原因。

传输层：TCP 之外还有 UDP

RDP 8.0 起支持双传输（MS-RDPEUDP）：TCP 保证指令可靠到达，UDP 通道分可靠（TLS 保护）与不可靠（DTLS 保护）两类，后者用于容得下丢的音视频和 FEC 数据。弱网下 UDP 的价值是绕开 TCP 队头阻塞——一个丢包重传不再卡住后面所有指令。Azure Virtual Desktop 的 RDP Shortpath 会在 TCP 反向连接建立后自动尝试 UDP 直达（learn.microsoft.com）。代价是运维面变宽：UDP 3389 被防火墙拦掉时客户端只会默默退回 TCP，体验变差但不报错，排查时容易漏。

安全层：BlueKeep 与 NTLM 退场

RDP 的安全层演进了三代：早期 RDP 安全层（自制加密）→ TLS → NLA（Network Level Authentication）。NLA 基于 CredSSP，在完整会话建立前先完成用户认证，把认证前攻击面压到最小——这与 2019 年的 BlueKeep（CVE-2019-0708）直接相关：一个免认证的蠕虫级 RCE，影响 XP 到 Server 2008(R2)，没开 NLA 的老系统是主要受害者（nvd.nist.gov）。老的安全层与 NLA 互斥，等于一条协议里躺着两代安全模型。

当前的变化主线是 NTLM 退场：Windows 11 24H2 和 Server 2025 已移除 NTLMv1，微软的三阶段计划在后续版本默认禁用 NTLM（techcommunity.microsoft.com）。NLA/CredSSP 在没有 Kerberos 的场景（家庭网络、跨域）依赖 NTLM，所以这次退场会实际推动 RDP 认证往 Kerberos 和证书走——企业域内无感，家庭用户的 NAS/Synology 类场景会先撞到兼容性报错。

VNC 与 Linux 桌面的远程化

RFB：最朴素的像素协议

VNC 的底层是 RFB（Remote Framebuffer）协议，RFC 6143。模型简单到一句话能说完：服务端维护一个 framebuffer，客户端请求更新，服务端把变化的矩形按协商的编码发过来。编码 negotiation 是 RFB 的核心机制——客户端用 SetPixelFormat 和 SetEncodings 报告自己支持什么，服务端逐矩形选择最优编码（rfc-editor.org）：

编码原理适用
Raw原始像素万兆内网、首次全量
CopyRect“从你 framebuffer 的 (x,y) 拷过来”滚动、窗口移动
Hextile16×16 瓦片 + 背景/前景色通用
TightJPEG/zlib 混合（TightVNC 扩展）低带宽
ZRLEzlib + 行程压缩，标准里压缩率最好的通用默认

RFB 不理解窗口和应用，每个像素都当图像处理——这是它"笨"的地方，也是它长寿的原因：X11、Windows、macOS、BIOS 界面、Android 模拟器，只要能产出 framebuffer 就能被它接管。TigerVNC 至今是 Linux 发行版仓库里的常客（GitHub 7.5k stars，2026-10 时点），云控制台（如 OpenStack/noVNC）用浏览器直连 VNC 也是这条路线的延续。带宽密集型场景（视频、动画）里 RFB 会被视频编码路线甩开，但在低活动度管理场景（装个系统、配个服务）它依然够用。

SPICE、NX 与 xrdp

Linux 生态里还有三个值得一提的实现：

  • SPICE：KVM 虚拟化的原生图形协议，配合 QXL 半虚拟显卡把 2D 指令从 guest 里拿出来传给客户端，视频区域走流式通道——思想与 RDP 的混合管线同源。虚拟机桌面（oVirt、Proxmox 控制台）常用
  • NX / NoMachine：把 X11 协议做深度压缩和缓存后重传，商业公司 NoMachine 的免费个人版是目前 Linux 上开箱体验最接近 RDP 的方案之一；X2Go 是基于 NX 协议库的开源衍生，主打瘦客户端
  • xrdp：让 Linux 说 RDP 协议（GitHub 6.8k stars，2026-10 时点），Windows 自带 mstsc 直接连进来。架构上是网关：RDP 进来后桥接到 Xorg 会话或 VNC 后端。Linux 桌面远程化的"协议统一派"主力

Wayland：网络透明性的终结

Wayland 替换 X11 最大的隐形代价就是远程化。X11 的协议里天然长着"应用可以远程跑"；Wayland 是本地渲染协议，合成器直接持有窗口内容，网络透明性没有了。替代方案变成了"共享整个会话"，而且各合成器各自为政：

  • GNOME 自带 gnome-remote-desktop，走 RDP；GNOME 46 起支持从登录界面远程登录（经由 mutter 的特权 remote-desktop API）
  • KDE Plasma 自带 KRdp，同样走 RDP
  • wlroots 系合成器（Sway/Hyprland）依赖 wlr-screencopy 协议做画面采集，第三方工具自行编码传输

两大桌面环境不约而同选了 RDP 而不是 VNC——语义+视频混合管线的带宽优势在高清屏上已经无法回避。结果是个有趣的倒挂：Linux 上的远程桌面正在被微软的协议统一，xrdp 和各合成器内建 RDP 服务成了事实方向。

商业产品：ID 寻址与中继网络

一套通用的连接逻辑

TeamViewer、AnyDesk、ToDesk、向日葵、RustDesk，界面差异很大，连接层几乎是同一套：

mermaid
flowchart TD
    A["两端登录账号<br/>或交换临时码"] --> B["凭设备 ID<br/>经信令服务器找人"]
    B --> C{"NAT 穿透"}
    C -->|"成功"| D["P2P 直连"]
    C -->|"失败"| E["中继服务器转发"]
    style A fill:#e3f2fd,stroke:#2196F3
    style B fill:#f3e5f5,stroke:#9C27B0
    style C fill:#fff3e0,stroke:#FF9800

    style E fill:#fce4ec,stroke:#f44336

设备第一次安装时向厂商服务器注册，领一个数字 ID；控制端凭 ID + 密码/账号授权发起会话；信令层交换双方地址后尝试 UDP 穿透，成功走直连，失败走厂商的中继机房。这套设计面向的场景是"帮别人修电脑"——两台设备都不在公网、没有固定 IP、对方不会配路由器，ID 寻址把配置成本压到零。代价是厂商服务器看得到会话元数据（谁连谁、何时、多大流量），中继机房看得到（或至少搬运着）你的加密流量。

中继带宽是这个行业的核心运营成本，也是各家免费/收费档位分界的主要依据。商业产品按"单设备会话"组织连接，这与 Tailscale 那类按"全网状网络"组织的 Mesh VPN 是两种产品哲学——前者的目标是零配置单点接入，后者的目标是把整个网络搬平。

TeamViewer 与 AnyDesk

TeamViewer 的官方安全声明给出的架构数字：会话用 RSA 4096 位密钥交换 + AES 256 位会话加密，经主服务器握手后约七成连接能建立 UDP/TCP 直连，其余走全球中继（teamviewer.com 安全声明）。它的安全事件史也最有代表性：2016 年大量用户账号被登录（社区归因于密码复用和撞库，厂商与用户各执一词）；2024 年 6 月公司内网被 APT29/Midnight Blizzard 用窃取的员工凭据入侵，TeamViewer 声称网络隔离使生产环境和客户数据未受影响（the register 等）。作为远控行业的招牌，这两次事件一次指向用户侧认证、一次指向厂商自身基建——远控产品的威胁面两端都有。

AnyDesk 由前 TeamViewer 员工在德国 Erlangen 创立，核心资产是自研的 DeskRT 编解码器——针对屏幕内容（大量重复图案、文字边缘）而非自然视频设计的帧内压缩，官方口径编码+解码延迟低于 16ms、60fps 下 100 kbit/s 也能干活（anydesk.com）。2024 年 1 月其生产系统遭入侵，源代码和代码签名证书被窃，AnyDesk 吊销了全部证书并重置门户密码，声明终端用户设备未被波及（quorumcyber.com、akamai.com）。代码签名证书失窃意味着可能出现"签名合法"的恶意 AnyDesk 安装包——对分发链的攻击比攻击协议本身更省事。

区域市场的主流产品：ToDesk 与向日葵

区域市场的主力是 ToDesk 和贝锐向日葵，公开技术资料比国际厂商少。ToDesk 官方口径称用户过亿、部署了两百多个本土接入节点，主打直连率（bilibili/新浪众测的横评数据，2023-2025）；向日葵的资历更老，围绕它做了完整的收费生态。安全方面，向日葵 2022 年初被曝远程命令执行漏洞（CNVD-2022-10270/03672），影响个人版 Windows ≤11.0.0.33162，官方在 11.1.1.38222 修复，360 的 APT 报告显示该漏洞被用于真实攻击（antiy.cn）。远控工具的漏洞直接等于主机控制权，这类产品必须跟进更新。

Chrome Remote Desktop 与 Parsec

Chrome Remote Desktop 是 Google 用 WebRTC 做的远控：传输层是标准 WebRTC 栈（DTLS 加密的数据通道，ICE/STUN/TURN 协商，穿透失败退 Google TURN 中继），一次性协助码约 5 分钟有效，长期访问绑 Google 账号 + PIN（webrtc.org、windowsforum）。它的意义在于示范了"浏览器即客户端"：不用装软件、跨平台一致，代价是功能面窄、依赖 Google 服务。

Parsec 2021 年被 Unity 收购，走的是游戏串流技术路线做远程桌面：硬件 H.264/H.265 编码 + UDP 传输，官方口径附加延迟可低于 16ms、支持 4K60 4:4:4（unity.com）。它证明了视频路线在"打字也要跟手"的办公场景完全成立——只要编码延迟足够低。

RustDesk：开源自建路线

RustDesk 是这一类产品里最值得细看的开源实现（GitHub 125k+ stars，2026-10 时点），思路是"把商业远控的整套逻辑开源，服务器可自建"：

  • 架构：自建服务端是两个 Rust 二进制——hbbs（ID/信令/穿透协调）和 hbbr（中继），加一组 21115-21119 端口（github.com/rustdesk/rustdesk-server）
  • 加密：基于 NaCl 的加密体系；自建服务端并配置自己的 Key 后可做到端到端加密——公共服务器模式下走默认信任模型，安全敏感场景应自建（rustdesk.com 文档）
  • 编码：VP8/VP9/AV1 软件编码 + H.264/H.265 硬件编码可选，按网络和 CPU 自适应
  • 权限模型：连接时请求屏幕/键鼠/文件/剪贴板权限，支持无人值守与二次确认

RustDesk 的存在说明商业远控的技术门槛（信令+中继+编码）对一个有一定规模的团队不再是壁垒——125k stars 意味着大量用户宁愿租一台 VPS 自建中继也要把会话数据留在自己手里。对企业场景，自建 RustDesk + 内网穿透的组合实际上构成了 TeamViewer/AnyDesk 的替代路径。

游戏串流：视频路线的延迟标杆

远控产品的延迟指标一直在向游戏串流看齐，因为游戏串流把延迟预算抠到了极限。这条技术栈的开源代表是 Sunshine（LizardByte 维护，NVIDIA GameStream 停服后的社区接班者，GitHub 42k stars）+ Moonlight（开源客户端，19k stars，2026-10 时点）：服务端用 NVENC/AMF/QSV 硬编码 H.264/HEVC/AV1，UDP 传输，客户端硬解后直出。

延迟预算的公认口径（simula.no 感知研究、MMSys ‘17 云游戏测量）：

端到端延迟体验
< 20ms接近本地操作，难以区分
20-50ms敏感玩家可感知（部分人在 40ms 以下就能察觉），绝大多数场景舒适
50-100ms办公可用，动作游戏开始"漂"
> 100ms多数交互场景不可接受

拆开看，预算的大头曾经是编码：软件 x264 编一帧 1080p 要几十毫秒，NVENC 这类专用硬件把这一项压到毫秒级，采集-编码-解码全链路才有可能挤进 50ms。这就是为什么 2015 年前后视频路线的远控（VNC 系）和 2020 年后的视频路线（串流系）体验差了一个量级——协议没变，编码器变了。Moonlight/Sunshine 和 Parsec 证明这条路线的天花板很高，代价是它们假设两端网络质量可控、不做复杂的企业功能。

远程终端：SSH、mosh 与会话保持

SSH 协议的三层结构

SSH（RFC 4251-4254）分三层：传输层（TCP 22，密钥交换 + 服务器认证 + 加密）、用户认证层（密码/公钥/keyboard-interactive，GSSAPI 走 RFC 4462）、连接层（单条 TCP 上多路复用 channel，shell/scp/端口转发各占一个）（rfc-editor.org）。服务器信任用 TOFU 模型：首次连接把 host key 记进 known_hosts，之后不符即拒——StrictHostKeyChecking=accept-new（OpenSSH 7.6 起）是新主机的折中档。

近年 SSH 生态的三个事实值得记录：

  • 后量子密钥交换成为默认：OpenSSH 9.0（2022-04）起默认启用 sntrup761x25519 混合交换，10.0（2025-04）起默认换成 mlkem768x25519（NIST 标准化的 ML-KEM），10.1 对未走后量子交换的连接告警——防的是"现在截获、将来解密"（openssh.com）
  • DSA 密钥在 10.0 彻底移除，Ed25519 是当前推荐
  • regreSSHion（CVE-2024-6387，2024-07）：sshd 信号处理竞态，glibc Linux 上可达 root RCE——sshd 是全网暴露面最大的守护进程之一，同版本线的 9.8 顺手把每连接逻辑拆进了独立的 sshd-session 进程以缩小攻击面（openssh.com、qualys.com）

Agent forwarding 值得单独提醒：ssh -A 把签名代理转发到远端后，远端机器上的 root/同权限进程不需要偷走私钥，借你的 agent 发签名请求就能横向跳到 agent 能到的任何主机（MITRE ATT&CK T1563.001）。这是"私钥不出本机"承诺的边界——不出的是密钥文件，不是签名能力。

断线问题与三个补救

SSH 的连接层建立在 TCP 上，没有会话恢复语义：TCP 断了，channel 全销毁，前台进程收 SIGHUP。笔记本合盖、Wi-Fi 切 4G、火车过隧道，都会杀掉会话。这个问题 SSH 自己不解决，生态给了三个互补的答案：

工具机制补什么留什么遗憾
tmuxclient-server：server 持有会话状态，attach/detach 只进出客户端状态不解决弱网卡顿
moshSSP 协议跑 UDP，同步终端状态而非字节流连接存活、IP 漂移无 scrollback、无端口转发
Eternal TerminalTCP 2022 长连接自动重连连接存活需要较好的网络

tmux 的 client-server 架构是"现场保活"的经典解：SSH 断了，tmux server 还在，重连 tmux attach 恢复一切。mosh（mobile-shell/mosh，GitHub 14.5k stars）走得更远：初始认证借道 SSH，之后切到服务端开的 UDP 端口（默认 60000-61000），协议同步的是"终端该显示什么"这个状态而不是字节流——IP 变了、休眠唤醒了会话都不断；本地回显靠预测模型（打字立即显示、下划线标注未确认、错了回滚），高延迟链路上打字跟手（mosh.org USENIX ATC ‘12 论文）。它的遗憾也明确：两端 locale 必须一致（UTF-8 不对直接拒启）、不支持端口转发、alternate screen 应用会吞掉本地 scrollback。Eternal Terminal 选 TCP 路线，保留完整终端语义（scrollback 正常、支持端口转发），可作为 VS Code Remote-SSH 的传输层，代价是对网络质量的要求接近原生 SSH。

工程上的经典组合是 mosh + tmux：mosh 管连接和漂移，tmux 管窗口和回滚历史，互相补位。这套组合是移动网络下运维远程机的标配方案。

企业级接入层

个人远控解决"连上"，企业场景还要求"谁连的、连了什么、能不能审计"，这催生了一层网关/接入产品。

Teleport（gravitational/teleport，GitHub 21k stars）把 SSH 的长期密钥换成短期证书：用户经 SSO/MFA 签发几小时有效期的证书，RBAC 控制谁能上哪台机，会话全程录制可回放，协议覆盖 SSH、Kubernetes、数据库和 Windows RDP。它解决的核心问题是密钥 sprawl——没人说得清哪台机器上躺着哪个人的公钥时，短期证书至少保证了"现在有效的授权都是刚签发的"。

Tailscale SSH 走得更彻底：SSH 服务直接内建在 tailscaled 里，认证复用 tailnet 身份（IdP/SSO/MFA），SSH 自身的密钥认证整个被绕开，授权走 Tailscale ACL（tailscale.com）。这个设计的潜台词是：当网络层身份已经可信时，SSH 的认证层是重复建设。会话录制 2023 年起提供。

Cloudflare Tunnel 的思路是把端口藏起来：内网的 cloudflared 建立出站隧道，SSH/RDP/VNC 服务不再暴露公网端口，用户侧经 Zero Trust 身份验证接入，浏览器里直接渲染 SSH/VNC/RDP 会话（developers.cloudflare.com）。端口不暴露，扫描和爆破自然失效——这是把"远程访问的攻击面"问题转成了"出站隧道的管理"问题。

Apache Guacamole 是网关形态：浏览器即客户端（“clientless”），后端 guacd 守护进程向目标发起 RDP/VNC/SSH 连接，翻译成自研的绘图指令流推给浏览器 canvas（guacamole.apache.org）。适合把一堆异构协议收进一个带审计的 Web 入口。

Web 终端生态是这层的最轻形态：xterm.js 是事实标准前端组件（VS Code 集成终端就是它），ttyd（GitHub 12.5k stars）一条命令把终端分享成网页。这类工具适合临时调试和容器场景，注意同类的 GoTTY 已长期不维护（github.com）。

裸机层：KVM-over-IP

前面所有方案都假设操作系统活着。OS 起不来、引导失败、要进 BIOS 改设置或重装系统时，需要一层连 OS 都不依赖的远程：KVM-over-IP（Keyboard-Video-Mouse over IP）。

服务器主板上自带的形态是 BMC：一颗独立 SoC，独立供电（插电即活）、独立网口，采集显卡 framebuffer 画面、模拟 USB 键鼠、提供虚拟光驱挂 ISO 装系统——Dell iDRAC、HPE iLO 和 Supermicro 的 IPMI 都是这个东西的厂商品牌（dell.com/hpe.com）。云厂商管数万台服务器，靠的就是这层。BMC 自身有段著名的安全史：CVE-2013-4786 是 IPMI 2.0 规范级缺陷——认证过程的报文里直接返回用户密码的哈希，远程抓包即可离线爆破，几乎影响了所有厂商十年（nvd.nist.gov）；至今 BMC 网段隔离仍是机房铁律。

开源/消费级硬件让这层技术下放到了 homelab：

项目平台编码与延迟价位（2026-10 时点）
PiKVM树莓派（V4 用 CM4）H.264/WebRTC，官方标称 35-50ms$274.95（V4 Mini）
JetKVM自研 SoC（固件 Go，全开源）1080p60，30-60ms$69
NanoKVM（Sipeed）RISC-V SG2002MJPEG，90-230ms~$20-50

三个项目的取舍很清晰：PiKVM 功能全（ATX 电源控制、虚拟介质、IPMI/Redfish 兼容），JetKVM 把价格打到了 BMC 副厂件水平（2025 年众筹筹得约 590 万美元，jetkvm.com/kickstarter），NanoKVM 用 RISC-V 把成本压到五分之一量级、以延迟和编码质量为代价。共同点是都在 OS 之下工作——主板没进系统，这层照样能点亮屏幕、敲键盘、挂 ISO。

安全教训：远程访问是头号入口之一

远控工具天然是"给我你机器的控制权"类软件，攻击者对它的兴趣与用户相同。

行业数据：Verizon DBIR 的口径里，RDP 长期是勒索与系统入侵类事件的主要入口之一——2021 年前后的报告显示约九成勒索相关系统入侵事件中出现 RDP（securitymagazine.com）；2025 年版报告中凭据滥用仍是第一大初始访问向量（约 22%），边界设备（VPN/防火墙/远程接入）被利用占比从 3% 跳到 22%（verizon.com DBIR）。远程接入层从"顺路入口"变成了"主入口"。

产品侧事件（本文调研范围内的已证实事件）：

时间事件性质
2016TeamViewer 大量用户账号被登录用户侧凭据（撞库/复用争议）
2019BlueKeep（CVE-2019-0708）RDP 免认证蠕虫 RCE协议实现，未开 NLA 的老系统
2022向日葵 RCE（CNVD-2022-10270）产品实现，被实际利用
2024AnyDesk 生产系统入侵，源码+签名证书被窃供应链/分发链
2024TeamViewer 内网被 APT29 入侵厂商基建
2024regreSSHion（CVE-2024-6387）sshd RCE协议实现

规律不难看出：协议实现、用户凭据、厂商基建、分发链，四个环节都出过事。由此推出的防线事实也按环节摆：

  • 协议层：RDP 必开 NLA，绝不把 3389/22 裸暴露公网（DBIR 数据的主要来源就是扫描到的裸暴露端口）
  • 认证层：远控账号一律 MFA；agent forwarding 这类"代理能力"按需开
  • 网络层：优先套 VPN/Zero Trust（Tailscale、Cloudflare Tunnel），让远程协议只在可信网络内出现
  • 分发链：从官方渠道下载并核对签名（AnyDesk 证书失窃事件的直接教训）
  • 裸机层：BMC/IPMI 网段物理或逻辑隔离，这层一旦失守等于主机永久失守

场景与方案对照

把上面的技术事实按场景归位：

场景技术事实支撑的选择
临时帮人处理问题，对方不懂配置Chrome Remote Desktop / Quick Assist / ToDesk——ID 寻址 + 一次性授权，配置成本最低
自己的服务器日常运维SSH + tmux；移动网络下加 mosh 或 Eternal Terminal
家庭多设备长期互访Mesh VPN 打底（Tailscale/WireGuard），上面跑原生协议；RDP/SSH/VNC 都不用改配置
会话数据不想过第三方RustDesk 自建 hbbs/hbbr；或纯 Mesh VPN 内网直连
企业多人接入 + 审计合规Teleport（证书+录制）或 Cloudflare Zero Trust（浏览器网关），异构协议收 Guacamole
低延迟图形工作/游戏Moonlight + Sunshine / Parsec——硬编码 + UDP，延迟预算 50ms 内
OS 挂了、要进 BIOS/重装KVM-over-IP：PiKVM/JetKVM，服务器看自带的 iDRAC/iLO
老设备/厂商内置兼容VNC/RFB——最朴素的像素协议，什么都能接

这张表还有一个隐含前提：两端网络"允许"所选的连接方式成立。不同网络环境在 CGNAT 普及度、UDP 可用性、长距离链路质量上的差异，会直接改写穿透成功率与方案可行性——这一层环境变量在《复杂网络环境下的 P2P 直连与隧道方案全面分析》里单独展开。
