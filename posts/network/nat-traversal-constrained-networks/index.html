复杂网络环境下的 P2P 直连与隧道方案全面分析

🔊

系列前三篇覆盖了远程访问的全景（调研篇）、RDP 协议本体（深拆篇）和产品对比（对比篇），P2P 协议原理则在《P2P 信令与中继服务器技术调研》里拆过。还剩一层没有展开：网络环境本身。同一套 STUN/TURN/ICE，放进不同的网络约束，穿透成功率、可用方案和体验下限完全不同——CGNAT 密集的接入网、对 UDP 不友好的链路、互联质量参差的运营商网络、高峰期拥塞的长距离骨干，这些约束的组合方式在不同网络之间差异极大，选型逻辑必须跟着环境走，不能照搬。

本篇补这一层：先按可测量的属性把网络分成"受限"与"常规"两类并摆出事实，再算穿透成功率的环境账，然后给出自建隧道工具的完整谱系（frp、rathole、bore、EasyTier、Tailscale 自建 DERP、ZeroTier moon、wstunnel）、中继选址的工程账、场景匹配矩阵，最后是一套可以照着做的诊断方法。环境数据来自 APNIC Labs 实测（2026-10 抓取）与 GitHub API 实抓，链路延迟为经验量级，标注了口径。

先说清楚分类的依据：这是网络属性的分类，不是地理分类。判断一条宽带属于哪类，靠的是测量，不是它在哪座城市——同一栋楼里的两条宽带，一条拿动态公网 IPv4、一条挂在 CGNAT 后面，就分属两类。

受限环境的五个特征

接入网默认 CGNAT，公网 IPv4 稀缺。 IPv4 地址枯竭的运营商普遍不再默认分配公网 IPv4：申请要走流程且不保证给到，大量用户直接挂在运营商 NAT（CGNAT）后面。判断依据很直接：路由器 WAN 口拿到的地址落在 100.64.0.0/10（RFC 6598 的 CGNAT 保留段）或私网段，而 STUN 看到的反射地址又是另一个公网地址——两层 NAT 坐实。家庭路由一层 NAT 加运营商一层 NAT，映射组合翻倍，穿透难度不是翻倍而是指数上升（后文细算）。

动画里能看到关键细节：设备发出的每个包要连续穿过两层改写——家用路由器一层、CGNAT 一层，对端看到的只有 CGNAT 出口的地址和端口。穿透要让两端的映射同时对上，这正是双层 NAT 环境成功率骤降的几何原因。

IPv6 能力参差，但高 v6 环境是端到端直连的机会。 APNIC Labs 对全球各网络 IPv6 能力的广告位实测（stats.labs.apnic.net，2026-10 抓取）显示，各网络的 IPv6 能力占比（capable）从不足三成到近八成不等——同一套直连方案的可行性因此相差一个量级。在 v6 能力高的环境里，蜂窝网络几乎默认 v6，家庭宽带在路由器支持时也能拿到 /60 或更大的前缀；IPv6 端到端没有 NAT，“穿透"退化成"防火墙放行”。门槛同样明确：两端都要有 v6；路由器的 v6 防火墙默认拦入站，需要放行或做映射；个别应用对 v6-only 链路的兼容性要单独验证。

部分链路对 UDP 不友好。 具体的限速策略不公开、因运营商与网络类型而异，但工具生态是可查的证据：EasyTier 在 README 里明确写了内建 KCP/QUIC 代理是为了"缓解高 UDP 丢包环境"；wstunnel 这类"把 UDP 封进 WebSocket"的工具，社区的一个常见用途就是穿过对 UDP 不友好的链路。工程上的结论：不要假设 UDP 链路的质量下限，方案要有 UDP 退化时的备选（TCP/WSS 传输）。

Peering 质量参差是独立的劣化源。 运营商之间的互联路径在晚高峰普遍劣化（延迟抬升、丢包上升），跨运营商的同城路径有时比同一运营商的跨区域路径更慢。自建中继节点时，单线接入（单运营商上游）会让其他运营商的用户绕路——选 BGP 多宿主/多运营商互联机房是中继选址的第一原则。

长距离链路高峰拥塞。 跨海光缆与洲际骨干在晚高峰普遍经历带宽争抢，延迟抖动和丢包显著抬升；普通骨干与付费优化线路的差距在这时拉开。这决定了远距离中继的定位：能当兜底，不宜当主力。

常规环境的四个特征

  • 住宅宽带以动态公网 IPv4 为主：不少运营商的住宅网络仍默认发公网 IPv4（动态），CGNAT 在扩散但未成主流；VPS 生态默认带公网 IPv4 且便宜，“有一台公网机器"是容易满足的前提
  • IPv6 能力较高：APNIC 同口径下，v6 能力占比领先的网络多在六到八成区间，v6 端到端直连机会大
  • UDP 一般宽松：住宅与移动网络对 UDP 无歧视性限制，STUN/TURN 的标准剧本成功率高；企业网和校园网是例外，常见只放行 HTTP(S) 的出口策略——这正是 wstunnel 这类工具在企业场景的用武之地
  • 约束的位置不同：常规环境没有前述接入网与 UDP 问题，但企业合规（数据保护法规、审计要求）对流量路径有要求——差异是约束的种类，不是约束更少

穿透成功率的环境账

穿透成功率由两端的 NAT 类型组合决定（原理见信令与中继调研篇），受限环境的特殊性在于 CGNAT 把"NAT 类型差"从个案变成了默认：

端 A \ 端 B锥型 NAT（EI/AD）对称型 NAT / CGNAT
锥型 NAT（EI/AD）UDP 穿透成功率高看发起方向，成功率中等
对称型 NAT / CGNAT看发起方向，成功率中等成功率低，实践中当不可用规划

双端都挂在 CGNAT 后（CGNAT 密集环境里两台家用设备互联的常态）落在右下角——这就是为什么在这些环境里"直连"经常要靠运气，而方案设计必须以"打不通"为默认假设。

三层缓解，按优先级：

  1. IPv6 直连：两端都有 v6 时绕开 NAT 问题本身。蜂窝网络 v6 普及普遍高于家宽，家宽看路由器前缀。需要处理的只剩两端防火墙放行。对高 v6 环境这是成功率的数量级改善
  2. 端口映射/UPnP：有公网 IPv4 时 DDNS + 端口映射是确定性路径；UPnP/NAT-PMP 能自动化但要接受安全性 trade-off
  3. 自建 STUN 的穿透：frp 的 xtcp 等机制允许指定自建 STUN 服务器——默认公共 STUN 在部分链路不可达或不稳定时，这一项决定穿透功能是否可用

一条命令拿到决策依据：tailscale netcheck（官方 CLI 文档，tailscale.com/kb/1080）报告 UDP 是否可用、IPv4/IPv6 连通与公网地址、MappingVariesByDestIP（即对称型 NAT 判据）、UPnP/NAT-PMP/PCP 端口映射支持，以及各 DERP 节点延迟。这套输出基本等价于一次"网络环境体检”。

把建立过程连起来看：阶段一两端向 STUN 注册，拿到各自的公网映射；阶段二同时向对方映射地址发包，在两侧 NAT 上打通通路——打通即直连，延迟最低；任一环节失败（典型是对称型 NAT）就改走中继转发。下一节的自建工具谱系，全部围绕"中继保底、直连增益"这一个结构展开。

端口转发型：frp、rathole、bore

这一类的模型是"一台公网服务器做反代"，客户端从内网主动连出去，访客连公网服务器的映射端口。

frp（fatedier/frp，109.8k stars，Apache-2.0，2026-10 实抓）是自建穿透领域事实标准级的工具。协议类型覆盖 tcp/udp/http/https/stcp/xtcp：tcp/udp 走服务器中继；stcp 是安全模式——访客也要跑一个 frpc，凭 secretKey 点对点握手中继，端口不公开暴露；xtcp 是 P2P 模式——两端经 STUN 穿透后直传，服务器只参与握手（官方文档口径：穿透"并非对所有 NAT 类型都有效"，建议"xtcp 不通就回退 stcp"，且 natHoleStunServer 可指定自建 STUN）。这三档正好构成"中继保底、可选直连"的完整梯度，也解释了 frp 的主导地位：默认路径确定可用（中继），直连是增益而非依赖。

rathole（rathole-org/rathole，14.3k stars，Rust）定位是更高性能的 frp 替代：官方基准口径吞吐更高、连接负载下更稳、内存更省，二进制最小约 500KB（适合软路由/嵌入式）；加密用 Noise 协议（默认 Noise_NK_25519_ChaChaPoly_BLAKE2s，避免自签证书管理）或 TLS，传输支持 tcp/tls/noise/websocket；支持 tcp/udp 服务与配置热重载。注意：没有 P2P 穿透模式，纯中继——选它是为了中继路径的质量，不是为了直连。

bore（ekzhang/bore，11.5k stars，MIT）是极简派：一条命令把本地 TCP 端口发布到公网服务器，Rust 单二进制。功能少（无 UDP、无 HTTP 路由、无加密层设计），适合临时暴露和开发调试。

nps（34.2k stars）值得单独立一条警示：功能面比 frp 还宽（隧道、代理、socks5、负载均衡），但仓库 2024-05 之后无提交——维护停滞的项目在安全工具类目里是减分项，新部署不建议再选。

Mesh 组网型：EasyTier、Tailscale + 自建 DERP、ZeroTier moon

这一类不转发单个端口，而是组建虚拟局域网，任何一个节点的全部端口都对网内可见。

EasyTier（14k stars，Rust，LGPL-3.0）是较新的开源项目，架构上去中心化——节点无服务器/客户端之分，能连上任一已有节点即可入网。与受限环境高度相关的三个特性：穿透同时支持 UDP 与 IPv6、官方声明支持 NAT4 到 NAT4（双端多层 NAT）场景；穿透失败时经共享节点中继（社区公共节点或自建）；内建 KCP/QUIC 代理层抗 UDP 丢包，传输还支持 WSS——UDP 不友好的链路上有现成的降级路径。子网代理（-n 把本地网段广播进虚拟网）和 WireGuard 协议接入（作为"VPN portal"让原生 WG 客户端入网）让它能同时覆盖组网和接入两类需求。默认端口：TCP/UDP 11010、WebSocket 11011、WSS 11012、WireGuard 11013。

Tailscale + 自建 DERP：Tailscale 本体的信令与中继依赖官方协调服务器和 DERP 网络（对比篇详述过），受限环境的问题在 DERP 节点的可达性与延迟。官方文档（tailscale.com/kb/1118）明确支持自建 derper：端口要求 HTTP 80（不可改）+ HTTPS 443 + STUN 3478，服务器必须公网直连（过 NAT/防火墙/负载均衡会破坏源地址识别，云 LB 多数不支持客户端用的 HTTP 升级协议），--verify-clients 可限定只有自己 tailnet 的节点可用（否则任何知道 IP 的人都能借用）。自定义区域 ID 用 900-999，配合 OmitDefaultRegions 可以只走自建区域。官方立场值得注意：自建 DERP 是"高级操作"，优先排查直连失败或部署 peer relays，DERP 长期承压说明网络本身有问题。控制面想自托管则用 Headscale（44.4k stars，BSD-3-Clause）。

ZeroTier + moon：moon 是用户自建的补充根节点（root），客户端 orbit 后把它加进根节点集合，peer 发现与中继优先用响应快的根（docs.zerotier.com）。对受限环境的价值是把"发现+中继"从默认的全球根节点搬到自己控制的服务器上；两点注意：官方推荐至少两个 moon 节点且不与控制器同机；文档已把私有 moon 标记为弃用（不受 SLA 保护）——可用，但要有"官方主推的方向不是这个"的预期。

受限封装型：wstunnel 与 WSS 传输

当链路只放行 HTTP(S)（企业出口、校园网是典型），UDP 和非常规端口的 TCP 都过不去，剩下的路是把流量封装成 WebSocket/HTTPS 流量。

wstunnel（7.1k stars，Rust，BSD-3-Clause）是这个方向的代表：把 TCP/UDP/Unix socket/stdio/SOCKS5 封进 WebSocket（ws/wss，TLS 1.3，支持自签证书与 mTLS）、HTTP/2 或 WebTransport（HTTP/3 over QUIC，需端到端 UDP）。CLI 模仿 SSH 隧道语法（-L/-R），服务端可限制目标地址和认证路径。典型用法：WireGuard over WSS——WG 的 UDP 被限时，把它的 UDP over WebSocket 穿出去（注意 MTU 调低和路由配置）；官方文档还提供自有证书、SNI 覆写等部署选项。EasyTier 的 WSS 模式是同一思想内建化的版本。

厂商托管的一体化商业方案

自建谱系之外还有一条路：厂商托管的一体化商业组网/穿透（配套硬件路由器或客户端 + 厂商信令中继网络）。卖点是零配置门槛，代价是带宽按套餐限速、隧道细节闭源、账号体系绑定厂商。与自建路线的取舍就是对比篇里那条轴：省事与可审计不可兼得。具体产品形态在对比篇的消费级远控与企业接入层已经覆盖，本篇不重复展开。

中继选址与链路账

中继节点的位置决定体验下限。按"中继与两端的拓扑"分档，经验量级（实测因线路、时段而异）：

中继与两端拓扑典型 RTT 量级带宽成本结构定位
同区域，BGP 多宿主机房双端 5-40ms按带宽计费贵，轻量云有流量包双端同区域时的主力中继
邻接区域（跨海/相邻区域）30-80ms（高峰波动大）流量计费为主，优化线路加价区域间兜底，高峰不稳
洲际130-200ms便宜量大兜底中的兜底

三条工程结论：双端同区域的隧道，中继放互联质量好的多宿主机房，一台轻量云的流量包通常就够 SSH/远程桌面量级的使用；跨区域访问要接受高峰劣化是常态，关键交互（SSH/运维）可接受，桌面串流类体验会明显波动；多中继容灾靠协议内建——DERP 的多区域自动选择、EasyTier 的延迟优先选路都是现成的，frp 则要自己起多个 server 手动切换。

合规一句：隧道承载个人数据时，须遵守两端适用的数据保护法规与所在组织的合规政策——这与技术选型无关，但决定"能不能这么连"。

诊断方法：一套可照做的流程

第一步：判断 NAT 层数。 路由器 WAN 口地址若在 100.64.0.0/10、10/8、172.16/12、192.168/16 内，说明上面还有一层运营商 NAT。再跑 tailscale netcheck 交叉验证：输出里的公网地址与 WAN 口不一致即多层 NAT；MappingVariesByDestIP=true 即对称型 NAT——这一项直接决定穿透预期。

第二步：确认 UDP 与端口映射能力。 netcheck 的 UDP=false 意味着直连无望（只能隧道）；UPnP / NAT-PMP / PCP 全空说明路由器不支持自动映射，有公网 IP 也得手动配。

第三步：量化链路质量时段差。 对目标方向（跨网 peer 或中继 IP）跑 mtr，午间与晚高峰各一次，对比延迟/丢包。peering 劣化与长距离拥塞只有按时段测才看得出来，单次测试没有意义。

第四步：验证 IPv6 端到端。 两端各确认拿到全球单播 v6 地址（家宽看路由器前缀委托）、防火墙放行所需入站、对端能 ping 通 v6 地址。三步都过，v6 直连就是当前环境的最优路径。

第五步：按归因顺序落方案。 信令不可达（公共 STUN/DERP 连不上）→ 换自建 STUN/DERP；UDP 不通或质量差 → WSS/TCP 封装降级；NAT 组合差 → 穿透转中继（frp stcp/rathole），或先试 IPv6/映射绕开 NAT。每一步都有明确的判据，不需要猜。
