H.264 编码管线与码流拆解：从残差、量化到 NALU 与 SPS/PPS

August 24, 2026 August 24, 2026 网络技术 H.264, AVC, NALU, SPS, PPS, Profile, Level, CRF, 码率控制, Ffmpeg 网络开发实战 4231 字 9 分钟阅读
🔊

上一篇讲完了帧层面：I/P/B、GOP、PTS/DTS。这篇钻进 H.264 内部，回答两个问题：一帧画面经过怎样的管线变成字节；SPS/PPS/NALU 这些码流里的结构各管什么。选 H.264 不是因为它最新——H.265/AV1 的效率都更高（选型对比）——而是因为它是存量最大、监控/GB28181 链路的事实主力，而且后面几代标准的骨架都从它演化而来，把它拆明白，H.265/H.266/AV1 的差异一看就懂。

混合编码环路

H.264 属于「混合编码」框架——预测 + 变换 + 量化的组合，1990 年的 H.261 就是这个结构，三十多年没变过。完整环路长这样：

上半圈是主路径：先做预测（I 帧用帧内预测、P/B 帧用上一篇讲的运动补偿），拿预测值和当前像素相减得到残差；残差做变换（把能量集中到低频）、量化（丢掉人眼不敏感的成分，全管线唯一有损的步骤）、熵编码（无损压缩）后输出码流。

下半圈容易被忽略但同样关键：编码器自己要把量化后的数据反变换回来、加上预测值重构出一份「编码器视角的解码结果」，经去块滤波后存进参考帧缓存，供后续帧预测使用。解码器跑的就是这条下半环路——两端严格对称，参考帧才不会漂移。理解了这一点，「P 帧丢了为什么后面全花」就有了完整答案：不只是这帧缺了，后面所有帧的预测基础都坏在缓存里了。

下面按顺序过每个环节的关键参数。

帧内预测：拿邻居猜自己

帧内预测用当前帧已编码的相邻像素推当前块的值，消空间冗余。H.264 提供两种粒度：

模式块大小预测方向数适用
Intra 16×1616×164 种（DC、垂直、水平、平面）平坦背景
Intra 4×44×49 种（DC + 8 个方向）边缘纹理细节

原理很直白：一块平坦区域，拿左边一列像素向右外推（水平模式）就八九不离十；斜边缘用对应方向的预测。预测得越准，残差越小，码率越低。

变换与量化：唯一的有损阀门

残差经过整数 DCT 变换从空间域转到频域——能量集中到左上角的低频系数，右下角的高频系数趋近于零。H.264 用 4×4 整数变换（High Profile 增加可选的 8×8），整数运算保证编解码两端可逆、无浮点误差。变换本身不丢信息。

真正的取舍发生在量化：变换系数除以量化步长，小的高频系数直接归零。控制阀门就是 QP（Quantization Parameter，H.264/265 范围 0-51）：

  • QP 越小：步长越小，保留细节多，质量高，码率大；
  • QP 每增加 6：量化步长翻倍，码率大约减半；
  • QP 在码流里三级给出：PPS 里的初始 QP → Slice 头的增量 → 宏块级微调。

所有「同分辨率码率差 10 倍」的画质差异，本质上都是 QP 的差异。

熵编码：CABAC 与 CAVLC

量化后的系数和辅助信息（预测模式、MV 等）最后过一遍无损熵编码。H.264 有两档：

方案全称效率复杂度可用 Profile
CAVLCContext-Adaptive Variable-Length Coding基准低Baseline 起全部
CABACContext-Adaptive Binary Arithmetic Coding再省约 5-15% 码率高Main 及以上

CABAC 更省的原因：变长编码表示一个符号最少 1 bit，而算术编码可以用不到 1 bit。高频符号（比如静止画面里的 MV (0,0)）被压到远小于 1 bit，累积起来就是那一成的码率。代价是串行依赖重、并行难，低延迟硬解场景有时反而指定 CAVLC。

NALU：码流的传输单元

以上都是编码算法。码流怎么组织成字节、怎么适应网络传输，是另一层设计——H.264 分成 VCL（Video Coding Layer，编码核心）和 NAL（Network Abstraction Layer，网络抽象层）两层，VCL 的输出被封装成一个个 NALU（NAL Unit）。

裸码流（Annex-B 格式，.h264 文件、TS 流、RTSP/GB28181 载荷都是它）用起始码 00 00 01 或 00 00 00 01 切分 NALU：

起始码之后第一个字节是 NALU 头，结构是 F(1bit) | NRI(2bit) | Type(5bit)：F 是禁止位恒 0；NRI 标重要性（IDR/SPS/PPS 为最高 3，可用于丢弃策略）；Type 标单元类型：

Type名称内容类别
1非 IDR SliceP/B 帧数据VCL
5IDR Slice关键帧数据VCL
6SEI补充信息（时间戳、元数据）非 VCL
7SPS序列参数集非 VCL
8PPS图像参数集非 VCL
9AUD访问单元分隔符非 VCL

一个细节：载荷数据本身可能出现 00 00 01 字节序列被误认成起始码，所以编码时要做防竞争处理（emulation prevention）——载荷里出现 00 00 后面跟着 00/01/02/03 时插入一个 03。写解析器时这一步漏掉，特定画面就会解花。

另一个工程上高频踩的坑：Annex-B 与 AVCC 两种格式不通用。裸码流用起始码；封装进 MP4 时转为 AVCC 格式（长度前缀 + 参数集抽到 sample entry）。从 RTSP/GB28181 拿到的 Annex-B 流直接写 MP4 会花屏，必须先转换（FFmpeg 的 h264_mp4toannexb / bsf 滤镜干的就是这个活）。

SPS 与 PPS：两份「说明书」

解码器拿到 Slice 数据前，需要知道这路视频的基本参数——分辨率、Profile、参考帧数、初始 QP。这些放在参数集里：

参数集作用域关键内容Type
SPS整个序列Profile/Level、分辨率、最大参考帧数、POC 约束7
PPS一组图像熵编码类型、初始 QP、去块滤波参数8

参数集有一套「激活」机制：SPS/PPS 可以先于 Slice 传输（甚至走独立通道），处于待激活状态；某个 Slice 引用某 PPS 时它才被激活（同时激活其引用的 SPS），持续到下一个 IDR。这个设计让参数集可以被重发保护——推流链路丢了一个 SPS，后面整段都解不出来，所以实践里通常在每个 IDR 前重发 SPS/PPS。

宏块与子块

Slice 数据的实体是宏块（Macroblock），16×16 亮度像素 + 对应的 8×8 色度块（4:2:0 下）。宏块可以按画面内容切成更小的预测单元：

mermaid
flowchart TD
    A["宏块 16×16"] --> B["16×16 整块<br/>平坦区域"]
    A --> C["2 个 16×8<br/>水平运动"]
    A --> D["2 个 8×16<br/>垂直运动"]
    A --> E["4 个 8×8"]
    E --> F["再切 8×4 / 4×8 / 4×4<br/>细节区域"]
    style A fill:#2196F3,color:#fff
    style F fill:#FF9800,color:#fff

平坦背景整块跳过、复杂区域切到 4×4——划分粒度跟着内容走，这是块编码效率的基础。对照着记住：H.265 把宏块升级成最大 64×64 的 CTU、支持递归四叉树划分，是它对静态监控场景增益显著的主因之一。

Profile 与 Level

Profile 限定可用的编码工具集，Level 限定分辨率/码率/帧率上限。两个维度合起来描述「解码这路流需要什么能力」。

ProfileIDB 帧CABAC位深典型用途
Baseline66✗✗8bit视频通话、旧设备
Main77✓✓8bit广播、标准流媒体
High100✓✓8bit蓝光、流媒体主流
High 10110✓✓10bitHDR、专业制作

2026 年直接用 High：它是 FFmpeg/x264 默认、所有主流平台推荐，同 CRF 下比 Baseline 小 15-25%。Baseline 只在极老设备或特定视频会议系统里有必要。

Level 节选（码率上限按 Profile 分档，High 是 Baseline/Main 的 1.25 倍）：

Level典型能力MaxBR Baseline/MainMaxBR High
3.1720p3014 Mbps17.5 Mbps
4.01080p3020 Mbps25 Mbps
4.11080p30（最常用）50 Mbps62.5 Mbps
5.14K30240 Mbps300 Mbps
5.24K60240 Mbps300 Mbps

数据来自 ITU-T H.264 Annex A。1080p 是 8160 个宏块，恰好卡在 Level 4.0 的 MaxFS（8192）之内——「1080p 用 4.1 留余量」的惯例就是这么来的。

码率控制：CBR、VBR、CRF

最后一环：编码器怎么在各帧之间分配 bit 预算。

模式策略码率可预测性质量稳定性典型用途
CBR每秒码率恒定精确差（简单场景浪费、复杂场景不够）直播推流、广播
VBR按复杂度浮动，目标均值近似较好点播文件
CRF恒定质量，码率随内容浮动不可预测最好离线编码
Capped CRFCRF + maxrate 上限有上限保障好ABR 流媒体转码

CRF 的推荐值（越大质量越低）：

编码器范围默认视觉近无损可接受下限
x2640-51231828
x2650-51282230
SVT-AV10-63352435 左右

（SVT-AV1 的 CRF 尺度和 x264 不等价，同数值下 AV1 质量更好；各编码器的 CRF 互不可比。）

# CRF：离线编码首选
ffmpeg -i in.mp4 -c:v libx264 -crf 23 -preset medium -c:a aac -b:a 192k out.mp4

# CBR：直播推流
ffmpeg -i in.mp4 -c:v libx264 -b:v 5M -minrate 5M -maxrate 5M -bufsize 10M out.flv

# Capped CRF：ABR 转码
ffmpeg -i in.mp4 -c:v libx264 -crf 23 -maxrate 5M -bufsize 10M out.mp4

preset 一条线：ultrafast → … → medium（默认）→ … → veryslow，越慢压缩率越高，同质量体积越小。实时编码用 veryfast/fast，离线归档用 slow/veryslow。

排错速查

把这篇的机制串起来，常见故障的因果就清楚了：

症状机制层面的原因处理
花屏/马赛克P 帧丢包，参考帧缓存被污染，错误传播到下个 IDR查丢包率；缩短 GOP；请求 IDR 刷新
长时间黑屏后恢复丢了 IDR 或 SPS/PPS，整段无法起解每个 IDR 前重发 SPS/PPS
MP4 花屏但 RTSP 正常Annex-B 码流未转 AVCC 直写 MP4过 h264_mp4toannexb/格式转换
音画不同步转封装时 PTS 丢失或错乱保留并重算时间戳
延迟偏大B 帧缓冲 + 长 GOP + 大分片叠加关 B 帧、缩 GOP、换 LL-HLS/WebRTC

到这里，H.264 从像素到字节的链路完整了。但监控系统里已经开始大量出现 H.265 摄像头，浏览器端 AV1 份额也在涨——这些标准在码流层改了什么、监控厂商的 H.265+/Smart 编码又是什么原理，下一篇逐个过。
