自研 incus-hub：给多集群一个控制台

November 9, 2026 November 9, 2026 虚拟化与运维 Incus, Incus-Hub, Node.js, 备份, 运维 自托管运维手记 3536 字 8 分钟阅读
🔊

上一篇的结论是开源空白，三条路里我选自研——在已有的 incus-hub（多主机聚合页）基础上演进成「多集群控制台」，不推倒重来。这篇给出设计要点和实施顺序，外加整个系列收尾时必须交代的一件事：不互备场景下，备份就是唯一的兜底。

为什么从 incus-hub 演进

v1 已经有的底子全部复用：

已有基础v2 怎么用
Node 零外部依赖，只用 http/https/fs/pathDebian 13 官方源 Node 20.19.x 直接跑，systemd unit 现成
mTLS 客户端证书 + 每节点独立 CA换成「每集群一张证书 + 每集群 CA」
callNode() / waitOperation() 通用 REST 封装迁移握手、operation 轮询全部复用
Promise.allSettled 部分失败隔离升级成「某集群挂了只标灰」
前端聚合表 + 搜索筛选 + 演示模式加集群层级与迁移向导

不改造 Orcastra / LXD Mosaic 的理由上一篇说过：前者源码未公开且要 4 台 VM / 30 GB 内存，后者把集群摊平成主机、PHP 技术栈、最后发版 2022。都不满足「轻、Debian 13 可跑、可控」。

目标架构与配置模型

浏览器只跟 Hub 说话（默认只监听 127.0.0.1，远程走 SSH 隧道）；Hub 内部维护 clusters[] 注册表，每个集群配 endpoints[]（多成员地址做连入冗余，按顺序尝试）；Hub 用 mTLS 连到各集群任一在线成员，通过 GET /1.0/cluster/members 自动发现成员列表——以后每集群加副节点，Hub 配置不用改。实例的 location 字段标识所在成员，前端渲染「集群 → 成员 → 实例」三级树。底部是 P0 到 P3 的实施顺序：先把「集群」这层抽象立起来，再做同集群迁移加 export/import 兜底，然后才是跨集群两步握手，relay 放最后。

证书细节和 v1 不同：集群模式下证书是全集群统一的 cluster.crt，不是每台成员自签的 server.crt——把 Hub 的客户端证书在集群任一成员上 incus config trust add-certificate 一次即可全局生效。

两类迁移的编排

同集群：服务端迁移，一个请求搞定——POST /1.0/instances/<名>?target=<成员>，body 里 migration: true，然后轮询 operation。容器先 PUT state {action:"stop"}。

跨集群：上一篇画过两步握手，Hub 端的实现要点：

  1. precheck 先行：目标集群可达、目标端存在迁移后引用的 profiles/池/网络（否则到一半才报 Profile not found）、资源余量、容器停机提示、同名冲突、IP 变化提示；
  2. 源端 migration: true 拿 operation + secrets，递给目标端建实例；
  3. 幂等：每个迁移 job 落一份状态文件（tempDir/job-<id>.json），失败时删目标残留、把源实例按原状态 start 回来；「delete 源」这一步失败绝不自动重删，标记待人工处理——因为 move = copy + delete，中途失败「源还在不在」必须由编排方负责到底；
  4. 审计：谁、何时、把哪个实例从哪个集群搬到哪个集群、参数、结果、耗时。迁移凭据（secrets、operation URL）只在内存传递，不写日志、不回传前端。

网段不通时的兜底：export/import 中转——POST /1.0/instances/<n>/backups 导出 tarball 落到 Hub 的 tempDir，再上传到目标端 import。一定停机、全量拷贝、最慢，但实现最简单、最可靠，网络策略不允许放通 8443 时它是唯一可靠的「一键」方案。relay（Hub 逐字节转发两端 websocket）最重，放最后考虑。

安全设计

  • Hub 只监听 127.0.0.1，远程经 SSH 隧道 / WireGuard；节点 8443 只对 Hub 的 IP 放行；
  • 每集群一张 Hub 客户端证书，可单独吊销；skipTLSVerify 永远 false；
  • 访问口令 openssl rand -hex 32，跨集群迁移这类破坏性操作二次确认；
  • 版本前提：上一篇的 GHSA-h2j8-4crh-vhfc（迁移 websocket secrets 泄露，影响 < 7.6.0）。发稿日（11-09）补一条核实结果：Debian 打包的 incus 7.0.2-3（forky/sid）已经带上了回溯补丁（110-GHSA-h2j8-4crh-vhfc.patch），Debian 安全追踪里 GHSA-v736-5xp3-jghf 等一批 GHSA 在 forky/sid 标记 fixed；Zabbly lts-7.0 通道是否同步回溯仍要在上线前用 apt-cache policy incus 核实，或者迁移期间不给任何第三方 can_view_events。

明确不做的事

  • 不做 HA / 自动故障转移 / 自动负载均衡——集群自身也没有，需求里明确不要；
  • 不做深层网络/存储参数编辑（OVN 拓扑、DNS zones、证书管理）——交给每个集群自己的 Incendio / 官方 UI，Hub 只放跳转链接；隔着 REST 代理做这些投入产出比极差；
  • 不引入数据库、不引入前端框架、不引入 npm 依赖：job 状态用 tempDir 下的 JSON 文件，前端原生 HTML/CSS/JS；
  • 不做跨集群「实时零停机」承诺：容器必须停，VM live 有前提，跨网段 IP 必变——界面如实提示。

实施里程碑

阶段交付关键验收
P0 多集群只读聚合clusters[] 配置模型、成员自动发现、集群树前端拔掉 A 集群，B 仍完整显示
P1 同集群迁移 + 兜底/api/migrate（同集群分支）、precheck、export/import 中转、job 状态与回滚、审计集群内 A1 → A2 一键迁完；网段不通时也能跨集群搬
P2 跨集群在线迁移两步握手（pull/push）、目标端适配表单、进度与日志网段放通 8443 后 A → B 一键迁移
P3 增强（可选）relay 中转、批量迁移、evacuate 面板按实际使用反馈再做

P0 必须最先做：它把「两个集群」这一层抽象立起来，后面所有迁移都建立在这个数据模型上。P1 的 export/import 兜底刻意排在 P2 前面——它是网络不通时唯一可靠的方案，实现风险最低。

收尾：不互备，备份就是唯一的兜底

整个系列的架构选择是「实例单副本、不互备」——那么备份就不是可选项：

三档节奏：每天做全局库 incus admin sql global .dump 加关键实例 incus export，推到第三处（NAS/对象存储/另一台机器，绝不停在这两台里）；每周全量冷备（停服务后 tar 打包 /var/lib/incus + subuid/subgid + 配置），ZFS 池另做 zfs send；每月在临时单机上跑一次 incus import 恢复演练——没验证过还原的备份只是心理安慰。特别注意：2 节点时数据库副本只在 bootstrap 一台上，主节点的库要单独备份。

两句官方提醒收录在这里：快照不等于备份——快照和原始数据在同一个存储池，池没了就一起没了；incus admin sql 的 dump 是「重建配置时的准确参照」，不是一键还原。

系列收官

九篇走完：认识了 Incus（1）、在 Debian 13 上装好它（2）、组了集群并算清 quorum（3）、定了存储和内存预算（4）、打通了跨节点网络（5）、吃透了 incus move（6）、盘点了 UI 生态（7）、调研了多集群与跨集群迁移（8）、最后落回自研 incus-hub 和运维兜底（9）。两台 16G 小机器的虚拟化底座到此成形，incus-hub v2 的代码按 P0 → P3 逐步落地，有进展再更新。
