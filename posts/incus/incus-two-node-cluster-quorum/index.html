「两台一起死」是个误传：双节点集群的正确姿势

November 3, 2026 November 9, 2026 虚拟化与运维 Incus, 集群, Raft, Dqlite 自托管运维手记 2474 字 5 分钟阅读
🔊

决定组集群之前，我听到的最大警告是：「两节点集群没有容错，挂一台就全挂，两台一起死。」这句话对了一半——而错的那一半，恰恰决定了整个架构方案。这篇把 Raft 多数派的账算清楚，并给出把「1 主 + N 副」固化下来的两条路。

先看官方怎么说的

Incus 的集群状态放在一个基于 Raft 复制的 Cowsql（dqlite 的社区继任者）分布式数据库里。官方文档写得很直白：

  • 高可用集群至少需要 3 个成员，才能在失去一个成员时保住 quorum；
  • 可以创建只有 2 个成员的集群，但「强烈不建议」；
  • 建集群时，数据库只在 bootstrap 节点上跑，直到第三个成员加入才复制第二份；
  • cluster.max_voters 默认 3；双节点是官方明确认可的例外——一个 voter 就够。

把 Raft 多数派的账摊开：

成员数需要多数（全员 voter 时）可容忍故障
220
321
431（多买一台不提升容错）
532

看到这你可能会说：2 节点不就是 0 容错吗？别急，2 节点集群默认两台并不是对等的。

关键事实：默认就是「1 主 + 1 副」

因为「数据库只在 bootstrap 上跑，直到第三台加入」，所以一个纯 2 节点集群的真实形态是：

  • node1（引导节点）：唯一的 voter，唯一持有数据库副本的机器；
  • node2：一个普通的集群成员，不持有数据库、不参与投票。

于是「挂一台会怎样」要分成两种情况说：

  • node2（副）挂了 → node1 仍是 voter，多数仍在（1/1）→ 管理面照常、实例照常，incus list 照样能跑；
  • node1（主，唯一持库的那台）挂了 → 0 个 voter，数据库不可达 → 集群配置写锁死，这才是「一起死」的真正含义。

换句话说：「1 台主、另一台永远是副、副死不连累主、只有主死才致命」——这就是 2 节点集群的默认行为。「两台一起死」这个说法把「主死」和「副死」混为一谈了。

左半是保持默认 max_voters=3 的隐患：以后加第 3、4 台时新成员会被提为 voter，node2 也只是「没被复制」而不是「被强制排除」——多个 voter 之后，挂任意一台 voter 就是失去多数，管理面整体停摆。右半是固化后的形态：node1 唯一 voter，node2 走方案①（standby，持库副本、主死自动晋升）或方案②（database-client，永远副、不复制不投票）。

但默认 ≠ 固化：两个隐患要主动堵住

默认行为对，不代表可以不管：

  1. 以后加第 3、4 台时，默认 max_voters=3，新成员会被提为 voter。一旦那批「副」里有人变成了 voter，就回到「挂一个 voter = 失去多数」的老坑。
  2. node2 现在只是「没被复制」，不是「被强制排除」——版本升级、成员变更的过程中存在让它变成 voter 的路径。

所以要把拓扑显式固化，二选一：

方案①（推荐）：cluster.max_voters=1

bash
1

incus config set cluster.max_voters=1

全局只要 1 个 voter，其余成员自动成为 standby：持有数据库副本但不投票。好处是白拿一层数据库副本，而且主死时 standby 自动晋升，集群不中断地继续；代价是副节点多存几十 MB 的数据库副本，几乎可以忽略。

方案②（字面「永远副」）：database-client 角色

bash
1

incus cluster role add incus-n2 database-client

这个角色的成员永远只是访问数据库的计算节点：不复制、不投票、不可能被选为 voter 或 standby。最纯粹，但主死之后需要手动恢复。

两个方案选一个就好，别同时叠加。还有一个绝对不要做的事：把 max_voters 设成 2，或保持默认 3 只布 2 台——那会让 node2 变成第 2 个 voter，「副死连累主」就从误传变成现实了。

主死了也不是世界末日

哪怕唯一的主挂了，也不是「数据全丢」，而是「停摆待恢复」：

  • node2 上正在运行的实例不会停，只是改不了集群配置、发不了新的迁移指令；
  • 用了方案①的话，standby 会自动晋升，管理面自己恢复；
  • 手动恢复走 incus admin cluster recover-from-quorum-loss（存活节点重建数据库领导权），恢复后元数据不丢，便于重建那台坏机器。

# 组集群（bootstrap 在 node1）
incus cluster add incus-n2                    # node1 生成一次性 token，默认 3 小时有效
# node2 上：incus admin init --preseed < node2-join.yaml（填 token）

# 固化「1 主 + N 副」
incus config set cluster.max_voters=1

# 验收
incus cluster list                            # 两台 ONLINE，ROLES 看 n1=voter/leader
incus admin cluster list-database             # 2 节点时只列 bootstrap 一台 = 目标态
incus config get cluster.max_voters           # 1

验收时如果看到 n2 也是 voter（2 个 voter），说明没固化好，按上面命令纠正即可。

这对架构决策意味着什么

  • 我要的「组集群 + 指令迁移 + 不互备 + 1 主 N 副」全部是 Incus 原生行为，零额外开发；
  • 唯一的单点是主（唯一持库那台）——这是为「统一调度 + 一条命令迁移」付出的等价交换，方案①把它变成了「管理面自动故障切换」，已经超出预期；
  • 组集群 ≠ HA：不配 Ceph 多副本、不开自动故障转移，就天然不互备，正合需求。
