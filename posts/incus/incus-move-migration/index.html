incus move：一条命令背后的迁移真相

November 6, 2026 November 9, 2026 虚拟化与运维 Incus, 迁移, 集群 自托管运维手记 1727 字 4 分钟阅读
🔊

这是整个系列最核心的一篇：我要的「通过指令就能迁移」最终落到一条命令上——incus move <实例> --target <成员>。但这条命令的语义、边界和容易误解的地方，值得单独一篇讲透。

一条命令，四步自动完成

bash
1

incus move web01 --target incus-n2

命令发出后 incusd 自动编排四步：停机、用 zfs send | zfs receive 传输根盘、在目标节点启动、清理源端——不需要手动 stop/copy/start。左下两张卡是关键分界：本地存储一律停机迁移（容器约 5~30 秒，VM 可能 1 到数分钟）；共享存储（Ceph）才能 live 不停机。右下是实用开关和批量维护入口。

最重要的分界：停机迁移 vs 在线迁移

这不是参数问题，是存储架构问题：

存储后端迁移类型体验
两台各自本地盘（我的场景）停机迁移容器约 5~30 秒（ZFS send 很快）；VM 要拷 qcow2 且重启，可能 1 到数分钟
共享存储（Ceph 等）live 迁移几乎零中断，内存迭代拷贝
VM + migration.stateful=true视存储而定VM 的 live 有额外前提，官方 how-to 明确写了要先开这个配置或先停机

官方 how-to 的原话值得记两条：

“When moving a container, you must stop it first.” “When moving a virtual machine, you must either enable Live migration for virtual machines or stop it first.”

容器想不停机走的是 CRIU，但官方同样泼了冷水：只有「很基本的容器（非 systemd、无网络设备）」能可靠地活迁——实际基本都要停。结论：把停机窗口当默认预期，用 --refresh 把二次迁移的窗口缩短。

三个必须分清的语义

move 是「搬走」，不是「复制」。 迁完之后实例只存在于目标成员，原成员上没了。想留底就用 incus copy（保留原实例）：

bash
1
2

incus move web01 --target incus-n2            # 搬走
incus copy web01 web01-bak --target incus-n2  # 复制一份，原实例还在

--target 是「集群成员选择器」，不是跨集群开关。 官方 manpage 对 --target 的定义就是 Cluster member name，官方 how-to 还特意加了一句：“In this case, do not specify the source and target remote."。跨集群迁移靠的是 <remote>: 前缀语法（incus move cluster-a:web01 cluster-b:web01），那是下一篇的世界。

同集群迁移是服务端动作。 客户端只发一个请求，数据在两台服务端之间流动——这和跨 remote 的「客户端当中介」完全是两条路径。

实用参数

bash
1
2
3

incus move web01 --target incus-n2 --refresh   # 增量传输：二次迁移只传差异，窗口大幅缩短
incus move web01 --target incus-n2 --stateless # 不搬内存状态（停机迁移本就不需要）
incus move web01 --target incus-n2 --instance-only  # 不带快照

批量场景：evacuate / restore

维护一台节点（升级内核、换硬件）时，比一个个 move 省事的官方封装：

bash
1
2
3

incus cluster evacuate incus-n1    # 把 n1 上所有实例迁到其他在线成员
# ... 内核升级 / 硬件维护 ...
incus cluster restore incus-n1     # 维护完迁回（或保持现分布）

配合 incus cluster group 还能按组调度：

bash
1
2

incus cluster group create prod
incus cluster group assign incus-n1,incus-n2 prod

几个容易忽略的点

  • 集群没有自动迁移。incus move --target 是「一条命令让系统自动完成全过程」；但「负载高了自动迁」「节点挂了自动漂」这类策略触发的迁移，Incus 一概没有——要的话自己在外层写脚本/cron/监控来驱动。
  • 没有轻量 witness。有 Proxmox 经验的人会想「加个 QDevice 投票就行」——Incus 没有等价物，第三 voter 必须是一台完整的 Incus 成员。
  • 迁完记得看 IP。用默认 bridge 的实例迁完 IP 会变（上一篇讲过）；用 OVN 则网络身份跟着走。

我的实战节奏

bash
1
2
3
4
5
6

# 1) 建实例时挂 OVN（保证迁到哪都能通网）
incus launch images:debian/13 web01 --target incus-n1 --network ovn0
# 2) 一条命令迁移
incus move web01 --target incus-n2
# 3) 确认
incus list      # LOCATION 已变，状态 RUNNING，IP 正常

容器迁一次的体感：多数情况 5~30 秒，--refresh 之后更快。这个停机窗口对内部服务完全可接受——这就是我不上 Ceph 的底气。
