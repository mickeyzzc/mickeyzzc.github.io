想一个界面管多台？Incus Web UI 盘点

November 7, 2026 November 9, 2026 虚拟化与运维 Incus, Web UI, 开源生态 自托管运维手记 2618 字 6 分钟阅读
🔊

命令行已经把集群玩顺了，但「打开浏览器看一眼所有机器」的诉求始终在那里。我把 Incus 相关的 Web UI 生态翻了一遍，按「能管多少台」分层，结论先行：把「管多个独立集群」和「一键跨集群迁移」放在一起看，没有一个在维护的开源项目同时做到。

先明确官方 UI 的边界

Incus 本体不带 Web 界面。官方适配的 incus-ui-canonical（LXD UI 的 rebrand）安装后由 incusd 在 8443/ui 同源托管——这带来一个结构性限制：

  • 指向独立主机 → 只能看到这一台，管两台要开两个标签页；
  • 指向集群任一成员 → 能看到整个集群（因为实例/配置记在共享数据库里）；
  • 浏览器里的 UI 被 CORS 挡住，无法连别处的 server。

所以「一个界面管多台」从来不是 UI 变强的问题，是架构问题：要么把多台变成一个集群，要么在前面加一层聚合。

四层结构从上往下：多集群控制面（能同时看见多个集群，但只读或不可用）、多主机面板（管多台但没有「集群」概念）、单集群贴本机 UI（一台管得最深）、自研聚合。每张卡上都标了关键短板——这张图也是本篇结论的直观版。

按「能管多少台」分层看

第一层：多集群控制面（能同时「看见」多个集群）

项目现状硬伤
Operations Center（FuturFusion，Apache-2.0，62★）官方生态的舰队中枢：注册所有集群、全局事件、全局镜像服务、舰队更新只读清单（刻意设计，防止一个集群持有另一个的凭据），操作要跳回各集群自己的 UI；绑定 IncusOS
Orcastra（v1.0.0-RC4）概念上最贴：Clusters / Regions / Members 建模主程序仓库 404（官网指向的 GitHub 仓库打不开，该账号下只有文档和部署脚本仓）；完整版官方拓扑要 4 台 VM、约 30G 内存的控制面；30 个功能面里没有 migrate

Operations Center 的只读是有意为之的安全模型；Orcastra 的「看起来最像答案」恰恰最危险——没法验证源码的东西不能用。

第二层：多主机面板（能管多台，但没有「集群」这个概念）

项目现状硬伤
LXD Mosaic（GPL-3.0，614★）最成熟的多主机 UI，PHP，功能全（部署/备份/监控）遇到集群会「把各成员逐个作为独立 host 加入」——集群被摊平；最后 Release 停在 2022
LXConsole（AGPL-3.0，476★，v0.7.0 BETA）Python/Flask，多 server、实例增删改、RBAC、Web 终端“Connect and manage multiple servers”——只管多 server；迁移限「集群内成员间」
fossvps-dashboard / PayIncusPVE+Incus 混合 / NAT VPS 售卖停滞 4~10 个月，偏商用场景

第三层：单集群贴本机 UI（一台管得最深）

项目特点
incus-ui-canonical（官方，GPL-3.0）LXD-UI rebrand，Zabbly 打包随装，最稳；一次只连一个 endpoint
Incendio（GPL-3.0）LXD-UI 深度 fork，专为 Incus 重建：OVN interconnect、DNS zones、ACME、集群再均衡等 Incus 独有特性覆盖最全；很新（2★）但在活跃迭代
ixui（Apache-2.0，pre-alpha）从零手写 React，Proxmox 风；支持 move to node 跨成员迁移；迭代极快，标 pre-alpha 要多测

这一层没有「REST 代理」的隔阂，Incus 有什么就能点什么（网络拓扑、存储参数、证书、控制台）。日常精细操作我会选 Incendio 或官方 UI，但一个 UI = 一个集群。

顺带一提 fork 谱系：canonical/lxd-ui → zabbly/incus-ui-canonical（补丁版）、m41denx/incendio（深度 Incus 化）；ixui 是完全手写；官方新仓库 lxc/incus-ui（Apache-2.0）2026-08 创建，首版预定 2026-11-12——值得盯。

第四层：自研

incus-hub——我在这个系列里自己写的聚合控制台：Node 零依赖、mTLS 直连各台的 REST API、一个列表管多台、宕机标灰、部分失败隔离。它就是为「两台独立机器 + 一个界面」的诉求而生的（完整方案在下一篇展开）。

诚实提醒：自研无社区维护是宿命，换来的是完全可控和零依赖。长期用、要功能全，第三层的现成项目更靠谱；要「看得多」，第一层 Operations Center 更权威——但它的安全模型决定它只读。

一个结构性认知：聚合层的天花板

所有「聚合」方案（无论开源还是自研）都隔着一层 REST 代理。凡是贴着 incusd 才能做的深层操作——改 OVN 拓扑、调存储后端参数、管证书信任、VGA 控制台——聚合层要么做不了，要么适配成本极高。而贴本机 UI 没这层隔阂，但只能管一个集群。

这个「既要看得多、又要管得深」的矛盾，正是下一篇的主题：我要的是两个网段各一个主集群的统一管理加跨集群迁移，开源世界给过什么答案、没给什么答案。

项目数据（★ 数、许可、Release 日期、404 状态）来自 GitHub REST API 实时元数据与各项目 README，2026-11 初核对、11-09 复核。
