认识 Incus：一个引擎，两种形态

October 30, 2026 November 9, 2026 虚拟化与运维 Incus, LXC, 虚拟化, Debian 自托管运维手记 2535 字 6 分钟阅读
🔊

手头有两台 16 GiB 的小机器，底层 Debian 13。这个系列记录我把它俩从裸机一路玩到「双集群 + 自研控制台」的全过程：概念、部署、集群、存储、网络、迁移、生态调研，最后自研。今天是第 1 篇，正好赶上 Incus 7.0.2 LTS 昨天（2026-10-29）发布——一个支持到 2031 年 6 月 的 LTS 版本，起点刚刚好。

Incus 到底是个啥

一句话：在同一套工具、同一个 REST API 里，既能跑「系统容器」，也能跑「虚拟机」。

bash
1
2

incus launch images:debian/13 web01          # 系统容器：共享宿主内核，秒级启动
incus launch images:debian/13 vm01 --vm      # 虚拟机：QEMU/KVM，独立内核

来点背景：Incus 的前身是 LXD。2023 年 Canonical 把 LXD 收归旗下并改动许可证之后，原核心团队出走，在 Linux Containers 项目（就是 LXC 的那个项目方）旗下另起炉灶做了 Incus，许可证回到 Apache-2.0，社区驱动。可以把它理解成 LXD 的社区续作，而且是目前活跃度更高的那一支。

它管的不是单个进程，而是整台机器级别的资源——CPU、内存、磁盘、网络、GPU。这是它和 Docker 最本质的区别：

维度系统容器（Incus/LXC）应用容器（Docker）
隔离单位一个完整的 Linux 用户态（有 init、systemd、sshd）一个进程 + 它的依赖
内核共享宿主内核共享宿主内核
典型用法当「轻量虚拟机」用：整套 nginx+php+mysql、当 VPS跑一个微服务、一个数据库进程
你的体感在管理一台迷你服务器在管理一个程序

和 Docker / KVM / Proxmox 是什么关系

工具本质和 Incus 的关系
Docker应用容器引擎不同层次；Incus 容器/VM 里照样能跑 Docker
KVM/QEMU硬件虚拟化Incus 的 VM 形态底层就是 QEMU/KVM
libvirtVM 管理库Incus 是另一种更简单的封装，不依赖 libvirt
Proxmox VE一体化虚拟化平台最接近的对标；但 PVE 是「全家桶 OS」，Incus 是「可嵌入的引擎」

关键区分在后半句：Proxmox 是装好就用的全家桶，Incus 是你自己拼装的控制平面。引擎本身只有 REST API 和命令行，Web UI 要自己装或自己写——这正是后面几篇要展开的主题，也是这个系列最终走向自研控制台的原因。

图上从上到下三层：客户端层（命令行、Web UI、自研脚本）通过 HTTPS 8443 加 mTLS 客户端证书连到 incusd 守护进程，本机 root 也可以走 unix socket；incusd 对上暴露统一的 REST API /1.0/…，对下调度内核能力；最底层是 Linux 内核的 cgroup v2、namespaces、AppArmor，以及 ZFS/Btrfs/Ceph 存储池和 bridge/OVN 网络。所有操作都返回异步 operation 让客户端轮询——命令行、UI、自研脚本全是同一套 API 的调用方。

几点展开：

  • incusd 是核心守护进程，所有操作都经它。单机时数据存本地 SQLite；组集群后换成 dqlite（基于 Raft 的分布式 SQLite，Incus 用的社区继任者叫 Cowsql）。
  • 一切皆 REST API。这一点是「多台聚合」「自研界面」能成立的根——也是我后面能拿一个几十 KB 的 Node 脚本聚合两台机器的原因。
  • 认证不用密码，用 mTLS 客户端证书，远程走 8443（后面专门讲）。

核心对象模型

这几个名词后面每篇都会用到，先混个脸熟：

对象是什么类比
实例 (instance)一个容器或虚拟机一台迷你机器
镜像 (image)创建实例的模板系统安装 ISO
配置文件 (profile)可复用、可叠加的配置片段配置模板
项目 (project)资源隔离的命名空间租户/环境
存储池 (storage pool)实例磁盘所在（ZFS/Btrfs/LVM/Ceph）磁盘阵列/卷组
网络 (network)实例接入的虚拟网络（bridge/OVN）虚拟交换机
成员 (cluster member)集群里的一台 Incus 主机集群节点
远程 (remote)命令行里的服务器「书签」连接配置

镜像默认来自 images:（Linux Containers 维护的公共镜像服务器，海量发行版模板），第一次拉取后本地缓存，之后建实例就是秒级。

隔离靠什么

  • cgroup v2：限制实例能用多少 CPU/内存/IO。Incus 7.0 已弃用 cgroup v1，系统必须是 v2（Debian 13 默认就是）。
  • AppArmor/SELinux：限制容器内进程能碰宿主的哪些资源。Debian 13 最小安装可能没装 apparmor，会导致容器起不来——这是下一篇要讲的真坑之一。
  • namespaces：PID、网络、挂载等命名空间隔离，让每个容器像独立系统。
  • 虚拟机：走 QEMU/KVM 硬件虚拟化，内核独立，隔离级别最高，适合跑不可信负载或 Windows。

为什么选它来管这两台小机器

  1. 资源密度：容器秒级启动、共享内核，16G 的机器能塞下比 KVM 多得多的实例。
  2. 统一 API：容器和 VM 一套命令、一个 API，脚本友好。
  3. Apache-2.0 加社区驱动，不绑任何单一厂商的商业许可证。
  4. 7.0.2 LTS 支持到 2031-06，只收 bugfix 和安全更新，生产节奏刚好。

顺便说版本：7.0 的硬门槛是内核 ≥ 6.12、cgroup v2、nftables（弃用 xtables）、LXC ≥ 6.0、QEMU ≥ 8.2、dnsmasq ≥ 2.90。我选 Debian 13 (trixie) 不是随缘——它是第一个开箱内核就达标的 Debian stable（6.12 LTS），Ubuntu 24.04 的 GA 内核 6.8 反而不达标。下一篇专门讲部署，包括 ZFS、AppArmor 这些一步一个的坑。
