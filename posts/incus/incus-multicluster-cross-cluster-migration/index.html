一个界面管多个集群：开源世界给的答案

November 8, 2026 November 9, 2026 虚拟化与运维 Incus, 多集群, 迁移, 开源生态 自托管运维手记 4013 字 9 分钟阅读
🔊

需求升级了：两个网段各自组了一个独立主集群（各 1 主，以后各自加副），上面要一个 Web 前端统一管，还要能一键跨集群迁移实例。这一篇把「同集群迁移」和「跨集群迁移」拆开讲清楚——它们根本不是一回事——顺便交代跨集群的五个硬约束和开源世界的调研结论。

先把拓扑说准

三层结构：最上面是唯一的 Web 前端（incus-hub / 控制平面）；中间是两个互不共享任何东西的独立集群——集群 A 在网段 1（192.168.10.0/24，主 A1 + 副 A2），集群 B 在网段 2（192.168.20.0/24，主 B1 + 副 B2）；每个集群内部是前几篇讲过的「1 主 + N 副」形态。橙色虚线就是跨集群迁移：本质是 copy + delete，IP 必变。两个集群之间没有共享数据库，profile/网络/存储池定义互不相通——这一点决定了后面所有的难度。

关键点：两个网段 = 两个互不共享数据库的独立 Incus 集群。它们之间没有任何 dqlite 关系。这一点决定了后面所有「跨集群」的难度。

两种「一键迁移」根本不是一回事

同集群 · 不同主机跨集群 · 不同主机
典型命令incus move web01 --target incus-a2incus move cluster-a:web01 cluster-b:web01
--target 语义选本集群成员不能用来跨集群；它只是目标集群内的落点成员
配置数据库同一份，自动同步实例位置元数据两份独立库，靠客户端 remote 概念打通
profile / 网络 / 存储池集群内定义一致，天然可用不共享，目标端可能没有，必须适配
传输方式服务端迁移（server-side move），最快跨 remote = copy + delete（或 migration stream）
Web 后端难度低（一个 API 调用）高（两步握手 + 凭据传递 + 目标适配）

--target 的官方定义就是 Cluster member name，官方 how-to 明确写了 “In this case, do not specify the source and target remote”——它是集群成员选择器，不是跨集群开关。跨集群靠 <remote>: 前缀：

# 每个集群在客户端眼里就是一个 remote

# 跨集群搬走（原实例删除）；中途失败要自己判断源还在不在

# 指定目标集群内哪台成员接收（合法）
incus move cluster-a:web01 cluster-b:web01 --target incus-b2

# 传输方向：pull(默认，目标连源) / push(源连目标) / relay(客户端中转)
incus move cluster-a:web01 cluster-b:web01 --mode pull

incus move remote:... 底层就是 copy 后 delete 源——源码 move.go 里的注释原话是 “A move is just a copy followed by a delete”。它不是原子操作，中途失败「源还在不在」要由调用方负责判断。

停机与 live 的官方口径（how-to 原文）：容器移动必须先停；VM 要么先开 migration.stateful=true 要么先停；容器 live 只有 CRIU 有限支持（“only very basic containers”），实际基本都要停。--refresh（增量）、--stateless（不搬内存态）、--instance-only（不带快照）都可用。

跨集群迁移的五个硬约束

① 两个网段要能互通，否则在线迁移做不了

模式谁连谁网络要求
pull（默认）目标集群主动连源集群 8443网段 2 → 网段 1 的 8443 可达
push源集群连目标集群 8443网段 1 → 网段 2 的 8443 可达
relay客户端连两端并中转数据两端之间不必互通，但数据全部经客户端转发

服务端之间没有信任关系。stgraber 的原话：“The concept of ‘remotes’ is a purely client side one, so there is no way for one server to directly push something to another as they don’t trust each other. Instead you need the client to communicate with both sides as a trusted intermediary."——这句话既解释了聚合层（Hub）的存在价值：它就是那个「同时被两个集群信任的中间人」；也解释了为什么 relay 实现最重：Hub 得自己把两端 migration websocket 的字节流对接转发。

② profile / 网络 / 存储池不会自动跟过去

目标是另一个独立集群，它的 profile、network、storage pool 定义跟源集群毫无关系。常见报错（官方论坛实录）：Error: Migration operation failure: Profile not found、Error: Failed loading storage pool: Storage pool not found。适配手段（官方 how-to 给出的全部）：--config、--device、--storage、--target-project、--no-profiles、--profile。两个网段的实例 IP 一定变——迁移后要处理 DNS、上游反代、证书、防火墙规则，这不是 UI 点一下就能自动消化的。

③ OVN 网络不跨集群

集群内用 OVN 解决跨成员通网（第 5 篇），但两个集群是两套独立的 OVN / OVN central DB，逻辑交换机不互通。跨集群迁移等于换了一个二层/三层网络，静态 IP、ACL、负载均衡后端全要重建。

④ 自定义存储卷要单独搬

bash
1

incus storage volume copy cluster-a:pool1/vol1 cluster-b:pool2/vol1

官方 how-to 的说明：除 ceph/ceph-fs 外，存储卷只存在于创建它的成员上。7.0 起 dependent 类型的卷会跟随实例一起迁（6.23 引入），普通自定义卷仍需单独处理。

⑤ 安全：迁移 websocket 凭据泄露（高危，和跨集群场景直接相关）

GHSA-h2j8-4crh-vhfc（stgraber 发布于 2026-10-29，High，CVSS 7.1）：

“Instance, volume and snapshot migration operations embed their per-connection websocket secrets in the operation metadata. That metadata is broadcast to every event listener holding view access… A client with event-view access can read the secret and connect to an in-flight migration’s data channels before the legitimate peer, hijacking the transfer of an instance it may not otherwise read.”

  • 官方 advisory 标注：影响 < v7.6.0，修复于 ≥ v7.6.0（我直接核对过 advisory 页面）；
  • 主线的 7.0.2 LTS 不在官方 patched 列表里，Zabbly lts-7.0 通道是否回溯修补，上线前必须核实（查 Debian 安全追踪、apt-cache policy incus 看有无 7.0.3+ 安全版本）；
  • 缓解：不给任何第三方 can_view_events 权限，限制事件监听者。

这恰恰是跨集群迁移场景才高频触发的风险——同集群服务端迁移走的路径不同。

跨集群迁移是怎么完成的（两步握手）

Hub 作为可信中介的五步：先停源实例（容器必须停）；源集群上 POST /1.0/instances/web01 {migration:true} 拿到迁移 operation 和 websocket secrets；Hub 把 operation URL + 源集群证书 + secrets 递给目标集群，同时指定目标端的 profile/池/网络/IP；目标集群连源集群拉磁盘流（前提是 8443 可达）；最后 wait 两端 operation、校验、删源实例、写审计日志。红字是工程要点：move = copy + delete，中途失败必须能恢复源实例。

POST /1.0/instances 请求里 source 的关键字段（源码 shared/api/instance.go）：type: migration、mode、operation（源端 operation URL）、certificate（源集群证书）、websockets（JSON 键名 secrets）、live、instance_only、refresh。

开源符合度：逐项判定

项目单 UI 管多个独立集群一键跨集群迁移结论
Orcastra✅ 概念上最贴❌ 官网 30 个功能面里没有 migrate源码 404 + 极重（4 VM/30G 控制面），不能用，值得盯
Operations Center✅ 但只读清单，绑 IncusOS❌ 明确 downgrade to read-only舰队清单，不是操作台
lxc/incus-ui（官方第一方）❌ 官方明确不做⚠️ 计划「token 粘贴」式两 UI 流程见下文官方口径
LXD Mosaic⚠️ 把集群摊平成主机⚠️ 有跨主机 copy/move 用户报告最接近，但不是集群抽象
LXConsole⚠️ 多 server，无集群实体❌ 迁移限集群内管多台可以，管多个集群不行
Incendio / ixui / incus-ui-canonical❌ 单 endpoint（CORS）❌单集群专用，功能最深
incus-hub（我的 v1）⚠️ 当前是 nodes[]（多台主机）❌有基础，需演进（下一篇）

官方为什么「故意」不做

官方论坛 “Incus UI is open for development”（2026-11-05）里，有人问的几乎就是我的原话：项目有没有计划「manage multiple clusters in a single view - e.g. list instances across them, and move instances between them」。stgraber 2026-11-06 的回答：

“It’s not. The Incus UI is a pure javascript client for the Incus API of the server/cluster serving it. It’s not allowed to connect to anything else as CORS would prevent it.”

官方路线是：多集群只读清单（Operations Center）+ 各集群自己的 UI + 两个 UI 之间复制粘贴 migration token 完成迁移。设计动机是安全——never having one cluster (or the UI it serves) have access to another cluster。不是我要的「一个界面点一下搞定」。

直接回答

现有开源里有没有符合「单 UI 管多集群 + 一键跨集群迁移」的？——没有。 拆开看：「一个 Web 前端管多个独立集群」有 Operations Center（只读）、Orcastra（源码 404）、LXD Mosaic（摊平集群），都能「看见」但都不能精细操作；「一键跨集群迁移」没有任何在维护的开源 Web UI 做这件事——CLI 完全可以，官方 UI 只给 token 粘贴流程。两者合并：开源空白。

三条路：妥协用现成（Operations Center 全局视图 + 每集群一份 Incendio + token 粘贴，零开发）；等 Orcastra 公开源码（不可控）；或者在已有的 incus-hub 基础上自研演进——下一篇讲方案。

项目数据（★ 数、许可、404 状态）来自 GitHub REST API 实时元数据，2026-11 核对；GHSA-h2j8-4crh-vhfc 与官方论坛引文核对于 advisory 原文与 discuss.linuxcontainers.org。
