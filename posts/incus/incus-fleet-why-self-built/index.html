为什么选 Incus，为什么自己写 incus-fleet

November 24, 2026 November 25, 2026 虚拟化与运维 Incus, Incus-Fleet, 多集群, 选型, 开源 自托管运维手记 3062 字 7 分钟阅读
🔊

前九篇把小机器的虚拟化底座搭完了：装 Incus、组集群、算 quorum、定存储和内存、打通跨节点网络、吃透 incus move、盘点 Web UI 生态、调研多集群与跨集群迁移，最后落回自研的 incus-hub。这一篇补完当初三步选型的推理——从底座、到控制台、到写不写代码。

三节的数据都标了时点。除特别注明外，均为本次写作时复核。

底座选型：七个候选各自的账

场景先说清楚：各网段一个独立 Incus 集群，机器是小盒子，上面跑容器和虚机，一个人管。这个场景下每个候选的账是这样：

候选关键取舍
Proxmox VE免费、社区大，容器虚机一个界面、HA 与备份齐全；但以集群为单位，多套 PVE 没有统一视图，LXC 与 KVM 仍是两套模型
VMware vSphere生态与 vMotion 成熟；按订阅授权，个人和小团队的成本不成立
OpenStack完整的 IaaS；控制面自身十几个服务，为这点规模搭它不划算
oVirt虚机管理成熟；主维护方退出，长期支持不确定
Harvester超融合，KVM 与 K8s 一处管；管理面本身有分量
Kubernetes + KubeVirt调度与生态成熟；把「跑几个虚机」变成「运营一个 K8s」
Incus容器虚机一套 API 一个命令、单机形态轻、Apache-2.0；缺多集群、跨集群迁移与统一 UI

选 Incus 的四条理由前九篇都验过：小机器上容器共享内核，能塞下比 KVM 多得多的实例；容器和虚机一套命令一个 API，脚本不用分家；Apache-2.0 不绑厂商；月度版跟不动时，7.0.2 LTS 顶得住且支持到 2031-06。

代价也摆在明面上：Incus 只回答「一个集群里怎么管」。多集群、跨集群迁移、统一界面这三件它一件都不做——前面盘点 Web UI 生态那篇核实过官方 UI 因 CORS 只服务自己那一个 server/cluster，前面调研多集群那篇核实过官方对统一多集群操作台的答复是不做，理由是不能让一个集群（或服务它的 UI）拿到另一个集群的访问权。这三件是下面两节的题。

控制台选型：现成方案到哪一步

前面调研多集群那篇的结论是「开源空白」：要同时满足「一个界面管多个独立集群」和「一键跨集群迁移」，当时没有在维护的开源项目。后来这一格被补上了——Orcastra 公开了源码，也写上了 Migration Center。

复核后的可选方案：

项目定位与本场景的关键差距
Orcastra当时唯一同时覆盖多集群与跨集群迁移的开源项目，定位是多组织托管控制面自成一个栈，场景是托管而非自管
Operations Center官方生态的只读舰队视图只读，且绑 IncusOS
LXD Mosaic / LXConsole多主机面板管多台主机，没有集群这层抽象
官方 incus-ui / incus-ui-canonical / Incendio / ixui单集群界面一个 endpoint，CORS 挡着跨集群；官方仓库还没发版
incus-fleet（本篇）自托管多集群控制台单二进制起步，把多集群、跨集群迁移和统一界面放在一处

跟前面那篇多集群调研比，最大的变化是开源侧那格空白被补上了。剩下的差别不在功能清单，在部署量级和场景：现成方案面向多组织托管，控制面自成一个栈；我这边是自己管自己的集群，一个人。

为什么自己写

前面那篇给了三条路：妥协用现成、等源码公开、自己写。源码后来公开了，所以这里回答的不是「有没有」，而是「为什么还是自己写」。差别不在功能多少，在信任边界——面向多组织托管的方案把认证、密钥、审计集中到一套独立控制面里；我要的是一个界面管好已经组好的集群，凭据只握在自己手里，控制面轻到能跟被管的机器放在一起。

incus-hub 当时只做设计验证：clusters[] 配置模型、两类迁移编排、幂等与审计、三档备份节奏。它把「多集群控制台该长什么样」定清楚了；fleet 直接按正式项目立项，把这套设计做成能用的控制台。

incus-fleet 围绕四个具体场景做：

  • 把互不共享的集群摆进一个界面：每个集群用各自的客户端证书接入，集群之间不共享数据库，center 是唯一同时被它们信任的中间人。
  • 跨集群搬完实例还能上网：迁移流程里做 DHCP 租约收尾，覆盖 dhclient、udhcpc、systemd-networkd、NetworkManager 四种客户端；虚机支持 migration.stateful=true 在线迁移，失败或中断自动重启源实例，进度写进数据库，两个 center 共用一个库时不会重复起同一个任务。
  • 小规模部署也要轻：一个 Go 二进制内嵌 Vue 3 UI，数据库从 SQLite 起步，多实例共享才换 PostgreSQL 或 rqlite；Rust 主机代理可选，不装也能管实例。
  • 多人协作留痕：本地账号与 admin / operator / viewer 三档角色、服务端会话、任务队列与审计记录，中英双语界面。

为什么开源

前面盘点 Web UI 生态那篇说过一句自评：自研没有社区维护是宿命，换来的是完全可控和零依赖。放着不管，项目就停在我一个人手里——写的人一停，代码就没人看了。开源是能对冲这件事的动作：有第二个人能读代码、报问题、提改动，维护就不再是一个人的事。

选 AGPL-3.0 而不是 MIT 或 Apache-2.0，是它把「通过网络提供服务也算分发」写进条款：改了 fleet 并通过网络提供给用户，就得把对应源码给那些用户。README 里写得直白——这个许可让项目保持开放，同时挡住闭源的托管衍生品。对一个控制面来说这就是想要的边界：谁都能用、能改，但不能拿去闭着卖。

开源还倒逼工程化。docs/en/standards.md 定了 TDD 契约；make coverage 卡 Go 覆盖率不低于 90% 和前端 90 / 90 / 90 / 85 四条阈值；scripts/secret-scan.sh 在提交前扫私钥、凭据赋值、bearer token、运维网段和主机名，CI 再对每个 tracked 文件和每个 commit 跑一遍；中英文文档必须在同一次改动里一起改。0.2.0 起 GitHub Actions 自动出 amd64 / arm64 的 center、helper、agent 二进制和 .deb / .rpm 包。

现在长什么样

总览页：两个集群的健康状态与主机资源汇总，界面中英双语。

从上往下：浏览器的请求经 Caddy 终结 TLS 后进 center；center 左边是持久化（默认 SQLite，几个 center 共用一个库时换 PostgreSQL 或 rqlite），下边用各自的客户端证书连各个独立集群。橙色虚线是可选的 Rust 主机代理，装在每个成员上，把 facts、心跳和指标回传给 center——不装也能管实例。

部署前提

在线迁移要求各网段能互通——目标集群要连得到源集群的 8443；防火墙不允许放通时只能走停机的 copy。SPICE 远程桌面不带票据认证，5910-5989 端口段要自己加防火墙。

incus-fleet 在 github.com/mickeyzzc/incus-fleet，AGPL-3.0，v0.2.0 于 2026-11-24 发布；部署、用户手册、HTTP API 和 roadmap 都在仓库 docs/ 下，中英文各一份。整个系列的目录在系列第一篇。

底座候选的版本与发布日期核对自 Incus 官方新闻页与各项目 release 公告；控制台项目的 ★ 数、许可与发版状态来自 GitHub REST API，本次写作时复核；纳入对比的项目其能力边界核对其官方文档和仓库 README。
