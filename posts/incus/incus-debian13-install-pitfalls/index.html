Debian 13 装 Incus 7.0 LTS：五个真实的坑

October 31, 2026 November 9, 2026 虚拟化与运维 Incus, Debian, ZFS, 部署 自托管运维手记 2254 字 5 分钟阅读
🔊

环境是两台 16 GiB 的小机器、Debian 13 (trixie)。这篇的价值不在「怎么装」（官方文档都有），而在哪几步会真的卡住——以下每一条都是实机部署时真踩过、或者真会卡住人的点。

先说版本：apt install incus 装到的是 6.0.4

这是 Debian 用户最容易栽的第一跤，先单独拎出来。Debian 13 上装 Incus 有三条路：

来源装到的版本自带 Web UI适合
Debian 13 官方源6.0.4 LTS❌ 不含 UI 包只用 CLI、坚决不加第三方源
Debian 13 trixie-backports7.0.2 LTS❌ 仍要另装 UI偏好纯 Debian 打包
Zabbly lts-7.0（本文主线）7.0.2 及后续补丁✅ 同仓库提供 incus-ui-canonical要 7.0 + 官方 Web UI

直接 apt install incus 会装到官方源的 6.0.4 LTS——不是坏东西（EOL 2029-06），但不是想要的 7.0.2。官方源不含 Web UI 静态文件（打包授权原因），既然拿 UI 绕不开 Zabbly 的 .deb，不如一开始就用它的 lts-7.0：本体和 UI 同一个源、同一个版本号，升级不会错位。

如果官方源、backports、Zabbly 同时开着，apt 会在几个 7.0.2 之间挑版本，升级时来源可能来回跳。给 Zabbly 加个 pin 优先级，或者干脆只留一个源。

装完必须复核来源，别只看版本号：

bash
1
2

incus version                      # 7.0.2，不是 6.0.4
apt-cache policy incus | head -6   # Candidate 应指向 pkgs.zabbly.com

为什么是 Debian 13：内核门槛不是玄学

Incus 7.0 的最低要求：内核 ≥ 6.12、cgroup v2、nftables（已弃用 xtables）、LXC ≥ 6.0、QEMU ≥ 8.2、dnsmasq ≥ 2.90。

Debian 13 (trixie) 的 GA 内核是 6.12 LTS——刚好压线达标，它是第一个开箱即满足 7.0 门槛的 Debian stable。对比一下：Debian 12 是 6.1（不行），Ubuntu 24.04 的 GA 内核是 6.8（也不行，除非换足够新的 HWE 内核）。所以「随便选个新发行版」在这个版本节点上不成立，trixie 是少数开箱就达标的选项。

装之前先在两台各跑一遍，输出对不上就别往下走：

bash
1
2
3
4

. /etc/os-release && echo "$PRETTY_NAME"    # Debian GNU/Linux 13 (trixie)
uname -r                                    # 6.12.x
stat -fc %T /sys/fs/cgroup                  # cgroup2fs
nft --version && dnsmasq --version | head -1

五个坑加一个版本陷阱：① ZFS 在 contrib 组件里默认找不到；② DKMS 模块和运行内核没对齐；③ 最小安装缺 apparmor 容器起不来；④ 缺 dnsmasq-base 实例拿不到 IP；⑤ ZFS ARC 吃内存没封顶。右下角的橙色卡是版本陷阱——装到了官方源的 6.0.4。下面逐一展开。

坑一：ZFS 找不到包——contrib 没开

text
1

E: Unable to locate package zfsutils-linux

OpenZFS 在 Debian 的 contrib 组件里，而 trixie 默认的 deb822 源只开了 main non-free-firmware。这不是「加一个源」的问题，是每个 stanza 都要补：

bash
1
2
3
4

sed -i -E '/^Components:/ { /contrib/! s/^Components: /Components: contrib / }' \
  /etc/apt/sources.list.d/debian.sources
grep '^Components:' /etc/apt/sources.list.d/debian.sources   # 每个 stanza 都要带 contrib
apt update

坑二：DKMS 模块加载失败——内核和 headers 没对齐

ZFS 在 Debian 上是 DKMS 源码包，要为运行内核现场编译模块。linux-headers-amd64 永远拉「仓库里最新」内核的 headers，如果运行内核比它旧，DKMS 会给一个你没在跑的内核编译模块，modprobe zfs 直接失败。

bash
1
2
3
4

apt full-upgrade -y && reboot        # 新机器：一次性升到最新再重启
apt install -y zfs-dkms zfsutils-linux zfs-zed linux-headers-amd64
modprobe zfs
zfs version                          # 两行版本必须一致（用户态与内核模块）

首次 DKMS 编译约 3~10 分钟，别中断。已有业务的机器不要无脑 full-upgrade，改装 linux-headers-$(uname -r) 并确认版本一致。

坑三：容器起不来——缺 apparmor

Debian 最小安装默认没有 apparmor，容器启动会报 AppArmor 相关错误。这是 Debian Wiki 上有记录的已知问题，Ubuntu 用户永远不会想到这一层：

bash
1
2

apt install -y apparmor && systemctl restart incus
aa-status | head -5     # 确认已加载

坑四：实例拿不到 IP——缺 dnsmasq-base

托管 bridge 的 DHCP/DNS 靠 dnsmasq。用 --no-install-recommends 装 incus 时最容易把这个推荐依赖漏掉，症状是实例起来后永远拿不到 IP：

bash
1

apt install -y dnsmasq-base && systemctl restart incus

坑五：内存被吃一半——ZFS ARC 没封顶

OpenZFS 的 ARC（自适应缓存）默认可以吃掉一半以上的物理内存，16G 机器上等于实例只剩一半可用。必须显式封顶：

bash
1
2
3
4

# 注意：必须在 modprobe zfs 之后写（否则 /sys/module/zfs/... 还不存在）
echo "options zfs zfs_arc_max=4294967296" > /etc/modprobe.d/zfs.conf   # 4 GiB
echo 4294967296 > /sys/module/zfs/parameters/zfs_arc_max
arc_summary | head -20

验收清单（全过再初始化）

bash
1
2
3
4
5

apt-cache policy zfsutils-linux | head -4    # contrib 生效
zfs version                                  # 两行一致
aa-status | head -1                          # apparmor 已启用
dpkg -l dnsmasq-base apparmor | grep '^ii'
chronyc tracking | grep 'System time'        # 时间同步（集群的地基）

时间同步单独提醒：装 chrony 会自动接管 systemd-timesyncd，别两个一起跑。集群的心跳、离线判定、join token 有效期全靠时间，两台对时差必须小于 100ms。

到这里，两台机器都有了：Debian 13 + 内核 6.12 + ZFS 可用 + AppArmor/dnsmasq 齐活 + Incus 7.0.2 LTS。下一篇进入正题——把两台组成集群。先剧透一个反直觉的结论：「两节点集群挂一台就全挂」是个误传，默认行为其实已经是「1 主 + 1 副」，副的那台挂了集群照常。

依据 Zabbly 打包仓库、Debian Wiki（Incus/ZFS/DebianTrixie）与 Incus 7.0 官方 requirements，2026-11 实机核对。
