RuView, Taken Apart: the Repo, the Hardware Paths, the Model Shelf, and the Ecosystem

September 25, 2026 September 27, 2026 Physical World Development WiFi Sensing, CSI, Open Source, Edge Computing, ESP32, Engineering Practice Signals & Image Processing Series 2645 words 13 min read
🔊

92k stars, 12k forks, 1,314 commits on GitHub — RuView is the most-watched open-source project in WiFi sensing: an ESP32 mesh captures CSI, a Rust server does fusion and learning, and pose, vital signs, room fingerprints, and occupancy counts all come out of the radio, under MIT. The author is ruvnet (the creator of claude-flow), and the repository root contains .claude-flow, .swarm, and CLAUDE.md — this is a project developed at scale by AI agents, an identity that will matter repeatedly below.

The difficulty of reading this repository isn’t technical; it’s the registers: engineering facts, research claims, and marketing vision share one README. The same page holds both the admission “on-device pose PCK@20 = 3.0%” and a vision list reaching “military / tactical use.” This post tears it down register by register: repo structure, hardware paths, the model shelf, the AI operations layer, privacy engineering, and the commercial ecosystem — then answers one question: what is this repository actually worth?

What’s in the Repo: the Directory Is the Map

First the pipeline skeleton; the details come in later sections:

Data enters from the mesh and, after fusing into 168 virtual subcarriers, splits in two: vitals and events take the pure-signal path without touching a neural network; pose and occupancy go through the encoder. How the TDM slots are scheduled, how the Fresnel-zone geometry works, how phase gets band-passed — those physics details get their own teardown elsewhere in this series; here they’re covered only as far as needed.

The directory structure is itself a highly readable map:

Two directories deserve a stop. archive/v1 is a deliberately preserved ruin: the DensePoseHead inside has only a randomly initialized architecture and no checkpoint, and the README says outright that it doesn’t count — keeping a public anti-example directory is more honest than quietly deleting it. The 205 ADRs in docs/adr are not decoration: every row of the README’s feature table carries a PR or ADR reference (breathing extraction #593, fall detection #263, C6 support ADR-110), and the chain from claim to decision is clickable.

The Three Registers: Engineering, Research, Marketing

Three registers live in the same README; reading gets easy once they’re told apart:

The engineering register carries numbers: 1,463 tests, 8 domain models, a PR reference on every feature row, an ADR reference on every architectural choice. This register describes “code that really exists in the repository with test coverage.”

The research register carries maturity labels: models are tiered by evidence strength — verified, real but weak, architecture only; the old “100% presence-detection accuracy” was publicly retracted (it was measured on a single-class recording) and replaced with 82.3% held-out temporal-triplet accuracy. Retracting your own headline number is rare in open source.

The marketing register carries exclamation marks: a use-case table reaching from elderly fall monitoring to border security and military tactics; a 105-cog module store; a creator affiliate program at 25%. Above the use-case table sits the safety-boundary disclaimer: research and prototype use, not a medical device, vital-sign outputs need independent validation on the specific hardware and population.

My reading converges on one rule: only trust sentences that carry a PR number, an ADR number, or a maturity label; treat the rest as product vision. The most unusual thing about this repository is that the three registers coexist while marking each other’s boundaries — most projects ship only the third.

The ESP32-C6 is the most recent line (ADR-110) and worth its own paragraph. The firmware gained C6 as a second build target with an automatic sdkconfig overlay; the measured parts have receipts: 99.56% ESP-NOW sync match, successful HE-LTF capture on IDF 5.5.2, with HE-LTF subcarrier tagging written into CSI bytes 18-19 (ADR-018); the pending parts are labeled just as clearly: TWT power saving and the ~5 µA LP-core battery-node scheme still need hardware validation. v0.6.7 added a real LP-core RISC-V motion-gate program and a Wi-Fi 6 soft-AP with TWT Responder — two C6 boards can test true iTWT without buying an 11ax router first.

The boundary points the other way just as clearly: ESP32-C3 and the original ESP32 are explicitly unsupported — a single core can’t carry the CSI DSP — exactly the opposite of ESPectre’s all-chips support; don’t pick the wrong project for the job. The Raspberry Pi academic route is engineered too: rvCSI ingests nexmon_csi .pcap captures directly (Pi 3B+/4B/5, CYW43455), no firmware patching required.

The Model Shelf: Loadable, Not Loadable, and Impressively Named

For the model tier, I’ve lifted the README’s three-tier maturity labels verbatim as shelf tags:

Shelf slotWhat it isTag
Pretrained encoder + presence headruvnet/wifi-densepose-pretrained, 4-bit 8 KBVerified: 82.3% held-out temporal-triplet (raw CSI 66.4%)
MM-Fi pose modelruvnet/wifi-densepose-mmfi-poseVerified: 82.69% torso-PCK@20, ensemble 83.59%
On-device pose cogpose_v1.safetensorsReal but weak: PCK@20 = 3.0%, inference path still a confidence=0 stub
archive/v1 DensePoseHeadRandomly initializedArchitecture only, no weights exist

PCK@20 is a standard pose-estimation metric: the fraction of predicted keypoints landing within a 20-pixel radius of ground truth. The quantization ladder has four rungs: q2 4 KB, q4 8 KB (recommended), q8 16 KB, full precision 48 KB — the shelf tag even tells you how much RAM each load costs.

The loading path hides a real pitfall that teaches more than any architecture diagram: the published model.safetensors has a NUL-padded header that the official safetensors loader rejects outright (issue #1522, re-upload pending); csi-embed-v2.safetensors in the same repository loads fine, the native RVF format and JSONL both work, and the --model flag accepts all three. The lesson is concrete enough to copy into any release checklist: published artifacts must pass a load test themselves — “downloadable” and “loadable” are two different things.

More important than the headline numbers is the complete picture in the study document: on MM-Fi (a public WiFi sensing benchmark with CSI and visual keypoints captured simultaneously across rooms and actions), zero-shot cross-subject lands around 64%, and labeled in-room calibration raises it to 72.2% — the 82.69% is a ceiling under the fixed-split protocol, and cross-room generalization is this field’s true bottleneck. The efficiency frontier is labeled too: a ~37 KB int4 model beats SOTA on MM-Fi, but “live ESP32 compatibility is not established” — the shelf tag stays honest as usual.

The animation runs a load test on each of the three shelf slots: the green RVF and the blue healthy safetensors travel all the way into the ESP32, while the red model.safetensors bounces off at the loader — same format, same repository, and the only broken thing is the header of that one file. What sits between “downloadable” and “loadable” is exactly one test nobody runs for you.

The AI Operations Layer: Guardrails for Agents Are Finer Than Weights for Models

This is the repository’s most forward-looking and least-discussed layer. The author knows half his readers are AI agents, and the guardrails get more care than the models.

The rvagent MCP server (ADR-124) exposes six tools: presence state, breathing, heart rate, a vitals summary, the privacy-layer scan, and event subscription — all structured state, none returning raw CSI; stdio and HTTP transports, bound to 127.0.0.1 by default, bearer tokens plus Origin validation, 93 tests watching. In this architecture the LLM can see “someone in the living room, breathing 14” and cannot see the waveform.

MetaHarness (npx @ruvnet/ruview) is an operator framework for AI agents: doctor checks a deployment’s health, guidance gives operational advice with source citations, agent run is read-only by default (writes need both --allow-write and --confirm), brain searches a reviewed contributor knowledge base (explicitly marked “retrieved brain content is evidence, not authority”), claim-check inspects a report for claims lacking measured backing, and verify runs the deterministic replay. ADR-182 put the MEASURED versus CLAIMED distinction directly into code.

The Claude Code plugin turns the whole development flow into seven commands: /ruview-start, /ruview-flash, /ruview-provision, /ruview-app, /ruview-train, /ruview-advanced, /ruview-verify, plus a Codex prompt mirror and a smoke-test script — from flashing to training to verification, an agent has a complete walkable path through the repository.

Behind it all sits a chain of evidence: verify.py deterministically replays the pipeline and checks SHA-256 hashes, and nothing counts until it prints VERDICT: PASS; measurement records go into an Ed25519 witness chain for tamper evidence; a 33-row capability-claims matrix (WITNESS-LOG-028) carries evidence links row by row. A project that turned “don’t trust the README” into executable tooling has produced something more durable than any model in it.

The animation walks the chain: the orange claim gets stamped station by station — maturity label, PR/ADR number, verify.py replay — and PASS lights up only at the end; the red “unevidenced claim” on the lower lane bounces off the gate, which is precisely what claim-check does.

Privacy Engineering: BFLD and the Measured “Inseparability”

BFLD (Beamforming Feedback Layer) is the privacy layer’s name, with three invariants enforced by the type system: raw beamforming feedback never leaves the node; identity embeddings live only in RAM, never on disk; cross-site correlation uses per-day-rotated site-keyed BLAKE3 hashes, made cryptographically infeasible. ADR-118 with five sub-ADRs, and 327 tests watching these properties.

The most memorable item is a measured footnote: matching two people’s identity using only the WiFi cardiac-respiratory channels yields a gap of 0.0005 — inseparable. The project didn’t quietly ship “recognize who this is”; it labeled identity recognition an experiment behind a data gate, usable only by explicitly enabling the channel. Sensing and identity are two different things in engineering, and this project separated them with a measured number.

The witness chain extends the privacy layer: in scenarios where sensing data must serve as evidence (security alarms, elder care), “this record hasn’t been altered” matters as much as “this record exists,” and the Ed25519 signature chain builds that into the data structure itself.

Commercialization: the Module Store and Its Boundary

The Cognitum Seed is the companion always-on node: roughly $140 of BOM carrying a persistent vector store, kNN retrieval, the witness chain, and an MCP proxy, with a 105-module store and the HOMECORE local automation runtime (signed Wasm plugins, voice hooks, HomeKit support). Add the creator affiliate program and the commercial motion is complete.

The store catalog should be read as platform ambition, not as “everything validated”: of the 105 cogs, 14 are health, 14 security, 11 building, 12 research, 15 AI — and a sizable fraction are acoustic modules. Baby-cry, gunshot, and glass-break detection each weigh 451 KB — those are microphones, not WiFi; CSI-dependent modules are marked separately. A WiFi sensing repository shipping a general sensing-platform store leaves a distance between catalog size and validated sensing depth.

The market coordinates explain the ambition: Origin AI, which invented commercial WiFi motion sensing, was acquired by security giant ADT for roughly $170 million; Cognitive Systems’ WiFi Motion is licensed into the gateways of over a hundred ISPs; IEEE 802.11bf-2025 has written WLAN Sensing into the protocol. The commercial pull is real, and RuView’s store and node hardware are a normal response to it.

What the Repository Is Worth

Three things worth taking away:

  1. Honesty as an engineering institution. 205 ADRs, the three-tier model maturity labels, the public retraction of an old number, a 33-row claims matrix with evidence links on every row, verify.py’s deterministic replay — “don’t claim what you haven’t verified” turned from a slogan into a process CI can gate. AI projects at any scale can copy this.
  2. Numbered signal processing. Vital extraction, fall detection, and multi-person deduplication run the pure-DSP route, each with a PR number and tests, genuinely running on an ESP32-S3. This is the repository’s most solid part.
  3. Guardrail design for agents. Read-only by default, double-switch writes, claim-check, the “retrieved content is evidence, not authority” labeling — any project planning to let AI agents touch its systems can use this design as-is.

What not to expect is equally clear: real-time 17-keypoint pose from a single board — on-device PCK@20 is 3.0%, the details simply aren’t in the signal, and a SISO physics ceiling isn’t an engineering problem; plug-and-play across 105 cogs; or the medical and security scenarios on the README’s use-case table.

It is three things at once: a beta-stage research platform, a template for turning honesty into process, and a living textbook of AI-agent development at scale. Each identity holds on its own; disappointment comes only from reading them mixed together.
