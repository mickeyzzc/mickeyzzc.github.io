From H.265 to AV1 and AVS: Bitstream Structures Across Codec Standards, Plus Surveillance Smart Codecs

August 24, 2026 August 24, 2026 Network H.265, HEVC, H.266, AV1, VP9, AVS3, Bitstream, H.265+, Surveillance, NALU Network Development Practice 2431 words 5 min read
🔊

The first two posts stayed inside H.264. This one covers the remaining mainstream standards in one pass: what each changed at the bitstream level and why, ending with surveillance-specific “smart codecs” (H.265+ / Smart Codec) — the layer responsible for the familiar “plays fine on the same brand, storage balloons across brands” effect when an NVR ingests third-party cameras.

Data caveats up front: compression figures are ranges from standards-body verification tests or public studies (JVET/JCT-VC official tests, MDPI comparisons, AVS workgroup claims) and vary with content and bitrate; smart-codec savings are vendor marketing figures and are labeled as such. Web playback selection conclusions are in the earlier post; this one only looks inside the bitstream.

Three ways to find a boundary

Every bitstream must answer the same question: how does the receiver know where each unit ends. Three answers:

RouteStandardsBoundary detectionTrade-offs
Start codes (Annex-B)H.264 / H.265 / H.266 / AVS2 / AVS3scan for 00 00 01resynchronizes after loss (next start code is always findable); needs emulation prevention, and unit length is unknown until parsed
Length prefixAVCC / HVCC (in MP4), RTP payloadslength field before each unitfast random access; one corruption can lose all later boundaries
OBU / frame framingAV1, VP9tiny built-in header + varint (LEB128) lengthdesigned natively for containers and streaming; minimal header overhead (AV1 OBU header is 1 byte)

The same H.264/H.265 stream exists in two forms: raw (.h264/.h265 files, TS, RTSP/GB28181 payloads) as Annex-B, and inside MP4 as length-prefixed AVCC/HVCC. The “Annex-B written straight into MP4 corrupts” pitfall from the previous post is exactly this missing conversion. GB28181’s PS encapsulation is Annex-B inside.

H.265 / HEVC

Finalized 2013. It keeps the NALU framework and changes three key things: the NALU header grows to 2 bytes, VPS is added making three parameter-set tiers, and macroblocks become CTUs.

The extra header fields have jobs: F(1) + Type(6) + nuh_layer_id(6) + nuh_temporal_id_plus1(3) — layer id serves scalable/multi-view coding, temporal id serves temporal sub-layers, and H.264’s 5-bit type space (32 values) had run out, so it doubles to 64:

TypeNameMeaning
0/1TRAIL_N/Rordinary trailing slices
19/20IDR_W_RADL / IDR_N_LPIDR frames
21CRA_NUTclean random access
32VPSvideo parameter set (new)
33SPSsequence parameter set
34PPSpicture parameter set

IRAP: a richer access system than IDR

H.264 has only the strict IDR refresh point. H.265 adds three classes of IRAP (Intra Random Access Point) pictures plus two kinds of companions:

  • IDR: strictest — nothing after it may reference anything before it;
  • CRA (Clean Random Access): intra-coded and a valid decode start, but later frames are allowed to still reference frames before it — the bitstream implementation of OpenGOP;
  • BLA (Broken Link Access): a declared “broken link” access point for stream splicing.

When playback starts at a CRA, companion frames whose display order precedes the CRA but which reference earlier pictures (RASL) must be dropped entirely; RADL frames (decode order before the CRA) can stay. The cliffhanger from the previous post, animated:

Same “viewer joins mid-stream” scenario: the ClosedGOP stream must wait for the next IDR; the OpenGOP stream starts at the CRA immediately at the cost of dropping RASL frames — a brief black patch. The compression-vs-startup-speed trade-off becomes syntax. HLS/DASH ABR segments require ClosedGOP; VOD files may use OpenGOP to squeeze out extra compression.

Three-tier parameter sets and the CTU

The VPS/SPS/PPS hierarchy serves H.265’s native scalability (SHVC/MV-HEVC) — an upper container describing how a multi-layer stream is organized; for single-layer streams VPS carries little.

The macroblock upgrade is more substantial. The 16×16 macroblock becomes a CTU (Coding Tree Unit) up to 64×64, recursively quadtree-split into CUs, which then partition independently into PUs (prediction units) and TUs (transform units) — three decoupled trees, where H.264 bound them together inside the macroblock:

A fixed-camera surveillance frame is 90% static background — one 64×64 CU covers it in one shot, which is precisely the mechanism behind H.265’s gains on surveillance scenes. Packaging: H.265 in MP4 uses HVCC, same idea as AVCC.

H.266 / VVC

Finalized July 2020. NALU types narrow back to 5 bits, but several new syntax units arrive (Type 10=GDR, 13=DCI, 14–16=VPS/SPS/PPS, 17/18=APS, 19=PH). Four bitstream-level changes worth remembering:

New mechanismWhat it solvesHow
PH picture headermulti-slice pictures repeat the same parameters in every slice headerwhole-picture parameters (IRAP/GDR flags, POC, reference lists) become one standalone NALU
APS adaptive parameter setALF/LMCS filter parameters vary per picture and would bloat the PPSstandalone set in prefix/suffix positions; suffix APS enables “slice first, filter params later” for ultra-low latency
GDR gradual decoding refreshfull I frames cause bitrate spikes costly to recover fromintra refresh is spread across frames region by region, no I frame needed
RPR reference picture resamplingHEVC needed a new sequence + I frame to change resolutionmid-sequence resolution changes become legal (references get resampled), avoiding switching spikes

Plus Subpictures: tile groups can be flagged as independently decodable subpictures, so 360° viewport extraction or multi-view composition can crop-and-forward without decoding the whole picture — a directional capability for NVR multi-channel composition. Efficiency per JVET official verification tests: ~43–46% savings over HEVC for UHD SDR, 50%+ for HDR/screen content; roughly 75% total versus H.264. Decode ecosystem remains the weak point (browser status in the earlier post).

AV1: the OBU system

AOMedia, finalized 2018. It abandons NALUs/start codes entirely for OBUs (Open Bitstream Units): a 1-byte header (forbidden(1) + type(4) + ext_flag(1) + has_size(1) + reserved(1)), an optional extension header (for scalability) and an LEB128 varint length (like protobuf).

typeNameRoleH.264/265 analog
1SEQUENCE_HEADERsequence config (profile, resolution)≈ SPS
2TEMPORAL_DELIMITERtemporal-unit delimiter, zero payload≈ AUD
3 / 4FRAME_HEADER / TILE_GROUPframe header / tile data (sendable separately)≈ slice header / data
5METADATAHDR10+, film grain, timecodes≈ SEI
6FRAMEheader + tiles combined (most used)—

The four frame types are deliberate too: KEY_FRAME (≈IDR, full decoder-state reset), INTER_FRAME (≈P/B), INTRA_ONLY (intra but does not flush references — the GDR gradual-refresh idea), and SWITCH_FRAME (a lightweight access point far cheaper than KEY_FRAME, designed for temporal-scalable low-latency links).

Practical details: raw encoder output is usually wrapped in IVF (32-byte header, DKIF magic); WebM/MP4 store the OBU sequence directly (each OBU with has_size set); the RTP payload strips temporal delimiters.

VP9: frames and superframes

Google, 2013. No NALU system — the stream is a sequence of frames (uncompressed header + compressed header + tile data + optional superframe index). Two designs worth studying:

  • Superframes: multiple coded frames merge into one container chunk with the index at its end. The classic use is hidden frames — decoded but never displayed, existing only as references. VP9 has no native B frames; it emulates reordering via “hidden reference frames + superframes + show_existing_frame mini-frames” and captures much of the B-frame compression benefit;
  • Temporal scalability: temporal id + reference structure give native SVC. Google Meet’s early years ran on VP9 SVC at conference scale, and this “scalability at the frame-structure level” thinking directly shaped AV1’s SWITCH_FRAME design.

AVS2 / AVS3: the Chinese standards

The AVS workgroup was founded in 2002. AVS+ (2012/2013) targeted H.264 for HDTV; AVS2 (2016, GB/T 33475.2) targeted H.265 and beats HEVC on surveillance content — by standardizing background modeling; AVS3 (phase 1 in 2019, phase 2 in 2021) targets 8K/VR, was adopted into the DVB core specification in July 2022 (the first Chinese codec in DVB’s toolbox), and powers the CCTV-8K channel launched in January 2022.

AVS2 uses start codes with no NALU header — the start-code value identifies the unit: 0xB0 sequence header, 0xB2 user data, 0xB3 intra picture header, 0xB6 inter picture header… Slice types beyond I/P/B include several designed for surveillance:

Slice typePurpose
G frame (background)a modeled background picture, used as a long-term reference
GB framepredicted by differencing against the background frame
F frameforeground frames coding moving objects separately
S framescene-switch frame, a new random access point

A fixed-camera frame is 90%+ static background; the G/F system encodes the background once and treats foreground separately — Hikvision/Dahua later achieved the same effect in H.265+ via private SEI plus long-term reference frames, for which standardized AVS2 was the precursor.

AVS3 keeps start codes, adds a Patch layer, and grows LCUs to 128×128; tools include QTBT + extended quadtree (EQT) + derived tree (DT) partitioning, 67 intra modes, 8→16 reference frames, affine motion compensation, intra string copy (ISC, screen content), and adaptive motion-vector resolution (AMVR). Official claim: ~30% savings over HEVC.

The surveillance-ingest reality: GB28181 PS streams overwhelmingly carry H.264/H.265 — in SDP, payload 96 is the PS encapsulation (the actual codec rides in the f= field and the PS map; H.264’s stream_type is 0x1B), and the 2022 edition recommends payload 100 for H.265. AVS3 mainly lives in broadcast 8K chains with low surveillance penetration; for NVR ingestion, H.264/H.265 PS-stream parsing remains priority one.

Surveillance smart codecs: H.265+ / Smart Codec

The fundamental difference between surveillance and general video: frames sit still for hours, recording runs 24/7, storage cost is the first constraint. Vendors layer private “smart codecs” on top of the standards — different names, same toolbox:

TechniquePrincipleBitstream-level trace
Background modeling / long-term refsstatic background referenced from seconds-old framesreference distances beyond standard Level limits; AVS2’s G frame is the standardized version
Dynamic GOPstretch I-frame intervals to minutes when still; insert an I on motion triggerunevenly spaced IDRs
ROI codinglow QP on moving targets, high QP on backgroundintra-slice QP differences (standard syntax; ROI selection is private logic)
Smart denoisinglow-light noise is random and nearly incompressible; denoise firstpre-processing, invisible in the bitstream
Dynamic frame ratedrop to 5fps when still, restore on eventswidened PTS gaps
VendorNameEmphasis
HikvisionH.265+ / H.264+dynamic GOP, background modeling, ROI
DahuaSmart H.265+AI感知 coding driven by SMD/IVS detection
UniviewUltra H.265same toolbox
AxisZipstreamdynamic fps + GOP + ROI, preserving forensic detail

Vendor claims (not neutral tests): ~70–80% storage savings versus H.264, another 20–40% over standard H.265; the quieter the scene, the bigger the gain.

What NVR developers must internalize: smart codecs are private extensions, not standards. A Hikvision H.265+ stream on a Dahua NVR usually degrades to standard H.265 decoding — picture fine, compression gains gone; some implementations need vendor SDKs to handle special SEI/private NALUs. Practical guidance:

  • Parse third-party streams as standard H.264/H.265 syntax and ignore unknown SEI/private NALUs (H.265’s 40+ undefined types are reserved anyway);
  • Don’t book H.265+ storage savings in cross-brand capacity planning; ONVIF Profile S/T doesn’t standardize smart codecs;
  • Preserve rather than strip SEI during remuxing (RTSP → MP4/PS), so playback in the vendor’s own client still benefits.

The rest of the surveillance codec zoo in one line each: MJPEG is per-frame JPEG with no inter dependencies — light for multi-channel decode and forensics-friendly at roughly 1/10 of H.264’s efficiency, commonly the analytics sub-stream or compatibility fallback; H.264 SVC (Annex G) was standards-complete but rarely landed, displaced by the “main + sub stream dual encode” workaround; HEVC/VVC SCC screen-content tools matter for control-room video walls and PC capture.
