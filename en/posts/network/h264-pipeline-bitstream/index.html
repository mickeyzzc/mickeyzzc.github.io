Inside H.264: the Encode Pipeline and the Bitstream, from Residuals and Quantization to NALU and SPS/PPS

August 24, 2026 August 24, 2026 Network H.264, AVC, NALU, SPS, PPS, Profile, Level, CRF, Rate Control, FFmpeg Network Development Practice 2139 words 11 min read
🔊

The previous post covered the frame level: I/P/B, GOP, PTS/DTS. This one goes inside H.264 to answer two questions: what pipeline turns a frame into bytes, and what SPS/PPS/NALU each do in the bitstream. H.264 is not the newest — H.265 and AV1 both compress better (selection guide) — but it has the largest installed base, dominates surveillance/GB28181 links, and every later standard evolved from its skeleton. Once you take it apart, the differences in H.265/H.266/AV1 read easily.

The hybrid encode loop

H.264 is a “hybrid codec” — prediction + transform + quantization, a combination dating back to H.261 in 1990 and unchanged since. The full loop:

The upper half is the main path: prediction first (intra for I frames, the motion compensation from the previous post for P/B), subtract the prediction from the current pixels to get the residual; the residual goes through the transform (energy compacts into low frequencies), quantization (discards what the eye won’t miss — the only lossy step in the pipeline), and entropy coding (lossless) into the bitstream.

The lower half is easy to overlook but equally essential: the encoder itself inverse-quantizes its own output, adds the prediction back to reconstruct “what the decoder will see”, deblocks it, and stores that in the reference frame buffer for later frames to predict from. The decoder runs exactly this lower half — the two sides must stay symmetric or reference frames drift. With this picture, “why does one lost P frame corrupt everything after it” has a complete answer: it’s not just that frame — the prediction basis in the buffer is poisoned until the next IDR.

Now each stage’s key parameters, in order.

Intra prediction: guess from your neighbors

Intra prediction extrapolates the current block from already-coded neighboring pixels in the same frame, removing spatial redundancy. H.264 offers two granularities:

ModeBlockDirectional modesSuits
Intra 16×1616×164 (DC, vertical, horizontal, plane)Flat backgrounds
Intra 4×44×49 (DC + 8 directions)Edges and texture

The idea is plain: for a flat region, extending the left column rightward (horizontal mode) is nearly perfect; diagonal edges get their matching directional mode. The better the prediction, the smaller the residual, the lower the bitrate.

Transform and quantization: the only lossy valve

The residual is transformed from spatial to frequency domain by an integer DCT — energy packs into the top-left low-frequency coefficients while high-frequency ones approach zero. H.264 uses a 4×4 integer transform (High Profile adds an optional 8×8); integer arithmetic guarantees encoder/decoder invertibility with no floating-point drift. The transform itself loses nothing.

The real trade-off happens in quantization: coefficients are divided by a step size, and small high-frequency ones become zero. The valve is QP (Quantization Parameter, range 0–51 in H.264/HEVC):

  • Smaller QP: finer step, more detail kept, higher quality, higher bitrate;
  • QP +6: step size doubles, bitrate roughly halves;
  • QP is signaled at three levels: initial QP in the PPS → slice-header delta → macroblock-level tweaks.

Every “same resolution, 10× bitrate difference” quality gap is, at the root, a QP difference.

Entropy coding: CABAC vs CAVLC

Quantized coefficients and side information (prediction modes, MVs) pass through a final lossless stage. Two tiers:

SchemeFull nameEfficiencyComplexityProfiles
CAVLCContext-Adaptive Variable-Length Codingbaselinelowall, from Baseline
CABACContext-Adaptive Binary Arithmetic Coding~5–15% bitrate savedhighMain and above

Why CABAC wins: variable-length coding needs at least 1 bit per symbol, arithmetic coding can use less than 1 bit. Frequent symbols (like MV (0,0) in a static scene) compress to well under a bit, which accumulates into that ~10% saving. The cost is heavy serial dependency — hard to parallelize, which is why some low-latency decode paths still specify CAVLC.

NALU: the transport unit

Everything above is the coding algorithm. How the bitstream is organized into bytes and adapted for networks is a separate layer — H.264 splits into VCL (Video Coding Layer, the coding core) and NAL (Network Abstraction Layer), and VCL output is packaged into NALUs (NAL Units).

The raw format (Annex-B — .h264 files, TS streams, RTSP/GB28181 payloads) delimits NALUs with start codes 00 00 01 or 00 00 00 01:

The first byte after a start code is the NALU header, laid out as F(1bit) | NRI(2bit) | Type(5bit): F is a forbidden bit, always 0; NRI marks importance (IDR/SPS/PPS get the max 3, usable for drop policy); Type identifies the unit:

TypeNameContentClass
1non-IDR sliceP/B frame dataVCL
5IDR slicekeyframe dataVCL
6SEIsupplemental info (timestamps, metadata)non-VCL
7SPSsequence parameter setnon-VCL
8PPSpicture parameter setnon-VCL
9AUDaccess unit delimiternon-VCL

One subtlety: payload bytes can accidentally contain 00 00 01 and be mistaken for a start code, so encoders apply emulation prevention — when 00 00 is followed by 00/01/02/03, an 03 is inserted. Miss this in a parser and specific frames decode as garbage.

Another frequent pitfall in the field: Annex-B and AVCC are not interchangeable. Raw streams use start codes; inside MP4 the format becomes AVCC (length prefix + parameter sets extracted into the sample entry). Writing an RTSP/GB28181 Annex-B stream straight into MP4 produces corruption — it must be converted first (FFmpeg’s h264_mp4toannexb / bitstream filters do exactly this).

SPS and PPS: the two “manuals”

Before decoding slices, the decoder needs the stream’s basic parameters — resolution, profile, reference-frame counts, initial QP. These live in parameter sets:

SetScopeKey contentsType
SPSwhole sequenceProfile/Level, resolution, max reference frames, POC constraints7
PPSa group of picturesentropy coder type, initial QP, deblocking params8

Parameter sets have an “activation” mechanism: they can be sent ahead of slices (even on a separate channel) in a standby state; a slice referencing a PPS activates it (and the SPS it points to) until the next IDR. This allows resend protection — lose one SPS on a push link and the rest of the segment won’t decode, which is why practical setups resend SPS/PPS before every IDR.

Macroblocks and sub-partitions

The substance of slice data is the macroblock: 16×16 luma pixels plus the matching 8×8 chroma blocks (under 4:2:0). Macroblocks split into smaller prediction units based on content:

mermaid
flowchart TD
    A["Macroblock 16×16"] --> B["16×16 whole<br/>flat regions"]
    A --> C["2 × 16×8<br/>horizontal motion"]
    A --> D["2 × 8×16<br/>vertical motion"]
    A --> E["4 × 8×8"]
    E --> F["split to 8×4 / 4×8 / 4×4<br/>detailed regions"]
    style A fill:#2196F3,color:#fff
    style F fill:#FF9800,color:#fff

Flat backgrounds skip whole; complex regions split down to 4×4 — partition granularity follows content, the foundation of block-coding efficiency. For contrast: H.265 upgrades the macroblock into CTUs up to 64×64 with recursive quadtree splitting, one main reason it gains so much on static surveillance scenes.

Profile and Level

Profile bounds the set of coding tools; Level bounds resolution/bitrate/framerate. Together they describe “what it takes to decode this stream”.

ProfileIDB framesCABACBit depthTypical use
Baseline66✗✗8bitvideo calls, legacy devices
Main77✓✓8bitbroadcast, standard streaming
High100✓✓8bitBlu-ray, mainstream streaming
High 10110✓✓10bitHDR, professional work

In 2026, just use High: it’s the FFmpeg/x264 default, recommended by every major platform, and 15–25% smaller than Baseline at the same CRF. Baseline only matters for very old devices or specific conferencing systems.

Data from ITU-T H.264 Annex A. 1080p is 8,160 macroblocks, just inside Level 4.0’s MaxFS (8,192) — which is where the “use 4.1 for 1080p headroom” convention comes from.

Rate control: CBR, VBR, CRF

The last piece: how the encoder distributes its bit budget across frames.

ModeStrategyBitrate predictabilityQuality consistencyTypical use
CBRconstant per secondexactpoor (wastes on easy scenes, starves hard ones)live push, broadcast
VBRfloats with complexity, target averageapproximatedecentVOD files
CRFconstant quality, bitrate floatsunpredictablebestoffline encoding
Capped CRFCRF + maxrate ceilingcappedgoodABR transcoding

CRF recommendations (higher = lower quality):

EncoderRangeDefaultVisually losslessAcceptable floor
x2640–51231828
x2650–51282230
SVT-AV10–633524~35

(SVT-AV1’s CRF scale is not comparable to x264’s — at equal numbers AV1 looks better; CRF values never compare across encoders.)

Presets on one line: ultrafast → … → medium (default) → … → veryslow — slower compresses better (smaller at equal quality). Real-time encodes use veryfast/fast; offline archiving uses slow/veryslow.

Troubleshooting quick reference

Chaining this post’s mechanisms together, common failures map cleanly to causes:

SymptomMechanism-level causeFix
Corruption/mosaiclost P frame poisons the reference buffer; error propagates to next IDRcheck loss rate; shorten GOP; request an IDR refresh
Long black screen, then recoverylost IDR or SPS/PPS — the segment can’t start decodingresend SPS/PPS before every IDR
MP4 corrupt but RTSP fineAnnex-B stream written into MP4 without AVCC conversionrun h264_mp4toannexb/format conversion
A/V out of syncPTS lost or miscomputed during remuxpreserve and recompute timestamps
Excess latencyB-frame buffering + long GOP + large segments stackingdisable B frames, shrink GOP, switch to LL-HLS/WebRTC
