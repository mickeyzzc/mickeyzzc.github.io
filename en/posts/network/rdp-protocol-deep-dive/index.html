RDP Protocol Deep Dive: Connection Sequence, Graphics Pipeline, and UDP Transport

October 8, 2026 October 9, 2026 Network RDP, Protocol Analysis, MS-RDPBCGR, MS-RDPEGFX, MS-RDPEUDP, CredSSP, AVC444, Virtual Channels Network Development Practice 3160 words 15 min read
🔊

RDP is the most widely deployed remote graphics protocol on the planet, yet the common understanding of it rarely goes beyond “port 3389 and the mstsc client.” Microsoft publishes the full specification set as the MS-RDP family (learn.microsoft.com), and the protocol deserves a careful read: it packs four hard problems — semantic transport, hybrid encoding, multiplexed channels, and security negotiation — into one session design, and many of its trade-offs transfer directly to building your own remoting stack.

The earlier post A Comprehensive Survey of Remote Desktop and Remote Terminal Technologies covers the landscape; this article dissects a single protocol. The whole article follows one connection through its lifetime: first how two endpoints establish the connection (the protocol stack, the five-gate handshake), then how graphics travel once it is up (the graphics pipeline, UDP transport), and finally how the security layers evolved and how each frame gets scheduled. Every claim carries its specification reference (MS-RDPBCGR, MS-RDPEGFX, MS-RDPEUDP, MS-CSSP). The baseline is the current Windows Server 2025 / Windows 11 24H2 generation of clients and servers.

The Protocol Stack: PDUs All the Way Down

The big picture first, details after. A packet capture of RDP shows every packet is a set of nested envelopes — graphics data wrapped in several headers, each doing one small job. The specifications call these wrapped packets PDUs (Protocol Data Units); the term appears throughout this article, and “one complete protocol packet” is all you need to remember.

On one TCP 3389 connection, from innermost to outermost:

The animation follows one drawing order all the way down: it is produced at the RDP layer and gains one envelope per layer, while the panel on the right assembles the packet’s current structure in sync. The four envelopes, each with one job:

  • MCS layer (T.125, Multipoint Communication Service): turns one TCP connection into several independent channels — clipboard, audio, printing, and graphics each get their own flow without blocking each other. The channel id in the header is the street address of each logical flow
  • Security layer: encrypts the data and checks integrity; whether it is TLS or legacy RC4 is decided during negotiation (see the security section)
  • X.224: a connection-oriented transport protocol from the ISO family, a generation older than TCP itself. RDP uses it for two things: steady packet delivery, and borrowing its handshake messages for the first security negotiation (the star of the next section)
  • TPKT (RFC 1006): an intimidating name for the simplest job — prepend 4 bytes (version + length) to every packet so the receiver can cut complete packets out of the TCP byte stream. This is the first structure you see in a capture

The layering is inherited from the ITU-T T.120 conferencing family (RDP began as the T.128 application extension), which explains the vintage-telecom vocabulary of MCS and GCC — not Microsoft being roundabout, just the protocol’s family tree. The document mapping: connection sequence and channels in MS-RDPBCGR (Basic Connectivity and Graphics Remoting), graphics in MS-RDPEGFX, UDP transport in MS-RDPEUDP, CredSSP in MS-CSSP.

With the stack in view, walk through the connection setup in real time.

The Connection Sequence: Five Gates, No Protocol Before Authentication

Establishing an RDP session means passing five gates. Why so ceremonial? One core reason: authentication comes first, and until it passes, none of the later protocol state machines exist — the pre-authentication attack surface that BlueKeep exploited is cut away by design (details in the security section). The five gates:

In the animation the five messages light up in order: the first two gates answer “who are you,” the last three settle “how we work together.” Each message corresponds to a subsection below.

Gate One: X.224 Negotiation — Agreeing on the Secret Handshake

The client sends an X.224 Connection Request carrying an RDP_NEG_REQ structure. This step is the two ends comparing notes: the client lists the security modes it supports (the requestedProtocols bitmask) and the server picks one.

Protocol flagMeaning
PROTOCOL_RDP (0x00)Legacy RDP security layer (RC4 encryption, see the security section)
PROTOCOL_SSL (0x01)Standard TLS; authentication still happens inside the RDP session as a login form
PROTOCOL_HYBRID (0x02)TLS + CredSSP, i.e. NLA
PROTOCOL_HYBRID_EX (0x08)CredSSP plus early user authorization (RD Gateway scenarios)
PROTOCOL_RDSTLS (0x04)Microsoft’s custom RDSTLS wrapper
PROTOCOL_RDSAAD (0x10)Microsoft Entra ID (formerly AAD) authentication, used by AVD/Windows 365 (learn.microsoft.com)

The server replies with a Connection Confirm carrying RDP_NEG_RSP, whose selectedProtocol field settles the choice — or RDP_NEG_FAILURE if nothing matches. Many “can’t connect” diagnoses should look here rather than waiting for a graphics-phase error. Differences between mstsc and third-party clients in HYBRID_EX/RDSAAD support explain some “Windows client connects, third-party client doesn’t” cases in AVD environments.

Gate Two: Security Handshake — Proving Identity

The negotiated protocol determines what happens here:

  • PROTOCOL_RDP: the legacy Security Exchange PDU — the client generates a random number, encrypts it with the server’s certificate (512-bit RSA), and both sides derive RC4 session keys via MD5/SHA-1. On modern systems treat this path as legacy
  • PROTOCOL_SSL: a standard TLS handshake, after which credentials are submitted as a form inside the session — the origin of the “login dialog before authentication” behavior when NLA is off: the entire protocol stack is exposed pre-authentication
  • PROTOCOL_HYBRID: after the TLS handshake comes CredSSP (MS-CSSP, Microsoft’s credential delegation framework that hands Windows login credentials to the server securely). CredSSP ferries SPNEGO — the negotiation shell of Windows single sign-on, usually carrying the NTLMSSP challenge-response triple (Kerberos inside a domain). In between sits a pubKeyAuth field: the client sends an encrypted hash of the TLS certificate’s public key to detect man-in-the-middle manipulation under the TLS layer, and finally an authInfo field carries the encrypted credentials. This is where NLA pays off: before authentication completes, no MCS channels and no graphics pipeline exist — gates one and two are the prerequisite for everything after gate three

Before CredSSP completes, the connection carries only a few TSRequest messages over TLS; on authentication failure the server drops the connection — which is why under NLA, brute-force attempts show up in logs as “connect then immediately disconnect.”

Gate Three: MCS Connect — Declaring Everything at Once

The MCS Connect Initial PDU embeds a GCC (Generic Conference Control — think of it as “the session parameters master table”) Conference Create Request in which the client describes itself in one shot: version, desktop size and color depth, keyboard layout and IME state, supported encryption levels, and the list of virtual channels it wants to join (cliprdr for clipboard, rdpsnd for audio, rdpdr for printing, drdynvc for dynamic channels, …). The server confirms in the MCS Connect Response. This is the most fingerprinting-friendly stage in a capture — each implementation’s core data differs slightly.

Gate Four: Channel Join — Roll Call, Channel by Channel

The MCS trio: Erect Domain, Attach User (yielding a userID), then a Channel Join Request per declared channel, confirmed one by one. Static virtual channels (SVCs) take shape here; dynamic virtual channels (DVCs, MS-RDPEDYC) join only one drdynvc channel, after which EGFX, display updates, video redirection, and others open as sub-channels on demand — the design that lets RDP gain features after 8.0 without touching the base handshake.

Gate Five: Capability Negotiation — The Server Lays Its Cards Down

The server sends a Demand Active PDU laying out all its capability sets (bundles of “here is what I can do” parameters): bitmap cache parameters, order-support bits, tiered glyph caches, pointer, audio, virtual channel parameters, and EGFX capabilities. The client narrows this to the intersection and replies with a Confirm Active PDU. Then come three short PDU groups — Sync, Control (Cooperate/Request, deciding who holds input control — the basis for collaborative sessions), Font List/Font Map — and the session activates; graphics flow.

This “server lays out, client narrows” model is how RDP stays compatible with two decades of implementations: old clients simply never receive new capability sets, while modern clients run a second, finer negotiation round through EGFX caps (next section).

The Graphics Pipeline: Orders, Caches, and Hybrid Encoding

With the session active, every screen change must travel from server to client. RDP does not blindly send screenshots — it splits traffic into three parallel routes by content type: text as orders, heavy graphics through EGFX encoding, video regions as hardware-encoded streams.

Orders and Caches: Why Text Is Nearly Free

On the base route the server sends drawing orders, not pixels. Three main classes:

  • Primary orders: GlyphIndex/FastIndex (draw text), LineTo, OpaqueRect, PatBlt, MemBlt (blit) and others
  • Secondary orders: cache management — placing glyphs, bitmaps, and brushes into client-side caches
  • Alternate secondary orders: control semantics such as the Frame Marker

The text path best shows the semantic route’s bandwidth advantage: the first time a glyph is drawn, the server ships its outline into a tiered glyph cache on the client; every subsequent output is “draw glyph index 17 from cache 2 at (x, y)” — an incremental screen of text often costs under 1 KB. Scrolling rides MemBlt orders copying from client-held bitmaps, the order-based cousin of VNC’s CopyRect.

Input is symmetric: keyboard and mouse events travel as Fast-Path input PDUs (a compact format without TPKT headers), a few bytes per event. This is the foundation of RDP’s typing responsiveness — input latency is never hostage to graphics congestion.

EGFX: Heavy Graphics Go Through Encoding

Since RDP 8.0, graphics-heavy content rides EGFX (MS-RDPEGFX, the Graphics Pipeline Extension) — a sub-protocol over a dynamic virtual channel. Each PDU has a three-field header (cmdId, flags, pduLength). The key message types:

  • CapsAdvertise / CapsConfirm: the client advertises capability versions (RDPGFX_CAPVERSION_8, _81, _10 through the _10.6 series) and capability flags (AVC444, AVC444V2); the server confirms and the encoding tier is locked
  • StartFrame / EndFrame: wrap a batch of wire-to-surface operations into one frame, presented atomically
  • Wire-to-Surface-1: deliver an encoded bitmap (codecId: PLANAR lossless, RFX_PROGRESSIVE, AVC_H264, AVC444, AVC444V2) to a rectangle of a surface
  • Wire-to-Surface-2: solid fill — monochrome regions skip encoding entirely
  • FrameAcknowledge: the client reports frameId and queueDepth (frames queued client-side awaiting display); the server throttles encoding accordingly

Surfaces are EGFX’s core abstraction — think of each as an offscreen canvas: the server decomposes the desktop into surfaces (main screen, video region, window textures), encodes and updates each independently, and the client composes them onto the screen. Nearly every modern remote protocol has since re-invented this model in its own vocabulary — WebRTC tracks, streaming-engine layers.

AVC444: Two 4:2:0 Streams Assembled into 4:4:4

Mainstream H.264 hardware encoders only do 4:2:0 subsampling, and chroma loss on text edges is glaring on desktop content. AVC444’s answer is mathematical: split the 4:4:4 image into two 4:2:0 streams — the first carries the Y plane plus downsampled UV; the second (Chroma420) carries chroma residual information that the client decodes to restore full chroma (learn.microsoft.com, MS-RDPEGFX). Each stream travels in its own Wire-to-Surface message sharing one frameId, and the client acknowledges only when the whole frame has arrived.

The cost is nearly doubled encoder load, so the specification adds the v2 (AVC444V2) variant improving chroma-stream compression, and 4:4:4 is negotiable in caps — which is why the Group Policy setting “Prioritize H.264/AVC 444 graphics mode” exists: turning it off can make text-heavy scenarios smoother at the price of color precision.

The Bandwidth Profile After Convergence

A modern RDP session’s bandwidth roughly decomposes into: text/windows as orders plus caches (near zero), static regions never resent, video/animation as AVC frame streams, and solid areas as fill orders. This is the hybrid form the semantic route evolved into in the hardware-encoding era — the weaknesses of both pure-semantic and pure-video routes are patched.

UDP Transport: MS-RDPEUDP’s Dual Channels

The graphics pipeline settles “what to send”; UDP settles “how to send it over a bad network.” TCP-based RDP has a birth defect: head-of-line blocking — when one packet triggers retransmission, every PDU behind it waits. RDP 8.0 added a UDP transport extension (MS-RDPEUDP, learn.microsoft.com) with these design points:

  • Establishment: once the TCP session is ready, the server initiates a multitransport tunnel creation over a dynamic channel, and the client connects back over UDP to the server’s 3389 — the UDP channel is server-initiated, opposite to most people’s intuition
  • Dual modes: RDP-UDP-R (reliable) carries sequence numbers, ACKs, and retransmission — semantically TCP but thinner; RDP-UDP-L (lossy) never retransmits, recovering what it can via forward error correction (FEC: redundant check packets added to a group, so losing one or two is recovered in place without retransmission) — every datagram carries an RDPUDP_FEC_HEADER, and MS-RDPEUDP2 groups FEC into sets, several source packets per redundancy packet
  • Split rule: drop-tolerant data (audio samples, video frames) rides the L channel, where one lost packet costs one frame and blocks nothing; order-type data rides the R channel or stays on TCP. Much of the difference between audio and video smoothness on weak networks traces to this split
  • Encryption: the reliable channel inherits TLS protection; the lossy channel uses DTLS — two encrypted channels coexist in one session

In Azure Virtual Desktop / Windows 365’s RDP Shortpath architecture, this UDP transport moves further forward: on managed networks the client connects directly to the session host over UDP (default 3391); on public networks STUN (3478) probes the path with TURN (443) relay as fallback, and the TCP reverse connection remains only as the control channel and fallback (learn.microsoft.com). Once Shortpath is established, latency and loss resilience improve noticeably — Microsoft’s scenario data shows frame-rate gains on weak networks in particular.

Security Layers: Three Generations from RC4 to NLA

Look back at gate two of the connection sequence and you will see security is not a patch on this protocol — it is built into the handshake. RDP’s security evolution is a case of three generations coexisting in one protocol:

GenerationMechanismStatus
RDP security layerServer’s 512-bit RSA certificate + client random; RC4 session keys (40/56/128-bit) derived via MD5/SHA-1Legacy; mutually exclusive with NLA
TLSStandard TLS protects the MCS layer; authentication via an in-session formUsable, but the pre-auth attack surface is fully exposed
NLA (CredSSP)TLS + SPNEGO credential authentication; no RDP protocol surface before authenticationCurrent default

BlueKeep (CVE-2019-0708) is the abyss on the first-generation path: the RDP server binds client-requested channels to internal channels by name, and an attacker uses a crafted name to bind an external channel onto the internal MS_T120; when the channel closes, the termdd.sys kernel driver hits a use-after-free — pre-authentication SYSTEM-level RCE, wormable (thezdi.com, malwaretech.com). The lesson is structural: every protocol state machine exposed before authentication is attack surface — Microsoft pushing NLA to default amounts to moving the entire protocol surface behind an authentication wall.

Two current storylines: NTLM’s exit (NTLMv1 removed in Windows 11 24H2/Server 2025, disabled by default later) pushes CredSSP deployments toward Kerberos and certificates; and Entra ID authentication (PROTOCOL_RDSAAD) migrates AVD/Windows 365 identity from domain accounts to cloud identity — the authentication layer’s second generational change.

Adaptation and Throttling: How Frames Get Scheduled

Connection established, pipeline chosen, link healthy — one question remains: when bandwidth runs short, what gets sacrificed first? RDP’s bandwidth adaptation is not a simple “lower the quality” switch — it is a three-tier feedback loop:

  • Frame tier: StartFrame/EndFrame mark frame boundaries; the client’s FrameAcknowledge reports queueDepth, and when backlog exceeds a threshold the server slows encoding — effectively an adaptive send window
  • Region tier: the client can issue SuppressOutput to pause updates for a region and RefreshRect for targeted refresh — minimized and off-screen windows simply stop updating
  • Network tier: Network Characteristic Detection probes RTT and bandwidth with timestamped PDUs, and the server adjusts encoding parameters accordingly

Combined with EGFX’s surface decomposition, this tiered throttling is RDP’s engineering answer to the “responsive text versus smooth video” dilemma. Mapped against the latency budget table in the survey post: RDP schedules interactive input (a few bytes, reliable channel) separately from graphics load (large frames, degradable) — which is how it holds the office-scenario experience.

Implementation Reality Beyond the Spec

Three implementation-side realities worth recording. First, mstsc is the reference client, not the feature ceiling: third-party support for AVC444V2, RDSAAD, and other newer features lags, and FreeRDP’s EGFX/RDPEUDP coverage sets the ceiling for the xrdp, Remmina, and RDP-bridging ecosystems. Second, the server encoding path is governed by the OS version: the same client connecting to different Windows generations can negotiate completely different graphics tiers — when debugging “why no 4:4:4,” start from both ends’ capability-set logs; FreeRDP’s /gfx debug output is a handy tool. Third, UDP paths fail silently: when UDP 3389 (or Shortpath’s 3391) is blocked by middleboxes, the client falls back to TCP without an error — “slower but no error” cases should be checked against MTU and UDP allow-list policies.

That completes the protocol dissection. Assembling this back into the survey post’s framework: the connection sequence embodies “authentication first,” EGFX embodies “semantic + video hybrid,” and RDPEUDP embodies “bypass head-of-line blocking” — three design decisions that form the skeleton of three decades of remote graphics protocol evolution.
