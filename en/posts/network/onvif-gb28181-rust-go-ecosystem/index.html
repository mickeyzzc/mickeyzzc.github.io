The Rust and Go Ecosystems for ONVIF/GB28181: Library Selection, Source Reading, and a Hardware-Free Integration Path

August 15, 2026 Network ONVIF, GB28181, Rust, Go, MediaMTX, Moonfire NVR, ZLMediaKit, NVR Network Development Practice 2042 words 10 min read
🔊

The first three posts settled the protocol mechanics, the landscape, and the device side; the final question is concrete: which libraries to write it with. This survey went through everything usable in both ecosystems. The one-sentence verdict: ONVIF has workable libraries on both sides; the mature GB28181 implementations live on the Go/Java/C++ side while Rust’s are still young; and for streaming infrastructure (repackaging, distribution, egress) the Go ecosystem is clearly thicker.

Four parts: the ecosystem inventory (what each project is, its status, what’s worth reading in it), Rust vs Go per module, a four-phase learning route (including the complete hardware-free integration setup), and finally MiBeeNvr’s implementation order. Star counts and activity are as of 2026-08 and will drift—re-check the repos before committing to anything.

The Go Ecosystem

ONVIF Libraries: The Classic Has Aged, the Newcomer Is Small

use-go/onvif (497★), the classic Go ONVIF client:

  • What it is: an ONVIF client covering Device/Media/PTZ/Imaging/Event/Discovery, with a device.CallMethod(req) API style—build a request struct, call, parse the SOAP response.
  • Status: the last commit sits at 2024-09-29—about two years of silence; Media2 and Profile T-era H.265 support is incomplete.
  • How to use it: usable, but be prepared to fork it yourself when bugs bite. Its request/response struct definitions are complete enough that even stale, it remains a valuable template for code generation.

0x524a/onvif-go (28★, created 2025-10) takes another direction:

  • What it is: a freshly written ONVIF library with a type-safe API, context support, and concurrency-safe design; ships a virtual camera Server—a mock device end simulating multi-Profile devices, letting you test client logic without hardware; the README claims validation on Hikvision/Dahua/Axis/Bosch real devices.
  • Status: actively updated (pushes through 2026-07), but only 28 stars and a tiny community.
  • How to use it: good for evaluation and prototyping; read the source before production use (an ONVIF client isn’t a big codebase) and judge the engineering quality. “Active but small” is the status—don’t depend on it with MediaMTX-grade expectations.

GB28181: gowvp/owl Proves Go Can Ship a Full GB Platform

gowvp/owl (791★, still updated as of 2026-08):

  • What it is: the most mature GB28181 platform in Go and the closest reference to MiBeeNvr’s positioning—based on GB28181-2022 (compatible with 2016/2011), with ONVIF/RTMP/RTSP ingestion, ZLMediaKit as the media layer, and a management UI.
  • Distinctives: built-in local YOLO detection (self-styled “Chinese Frigate alternative”) and HomeKit bridging; one-command Docker deployment; signaling built on panjjo/gosip.
  • What to read: its SIP signaling implementation is the fastest path to understanding the GB platform business loop—walking the register/keepalive/catalog state machines, the INVITE-to-ZLMediaKit stream handoff, and the playback signaling sequence in source beats ten tutorials.

The Rust Ecosystem

ONVIF: oxvif Works

oxvif (latest v0.15.0 on crates.io, published 2026-08-04—three releases within two weeks):

  • What it is: the most complete ONVIF client on the Rust side: Device/Media (Media1+Media2)/PTZ/Events/WS-Discovery, with docs claiming ~95% coverage of Profile S/T operations.
  • Distinctives: built-in WS-Security, HTTP Digest, and mock device features (mock, mock-server features)—unit-test the client without real cameras, which matters for CI.
  • Status: a dozen-odd repo stars, but the release cadence and documentation read like a serious project.
  • How to use it: read the source before production use; an ONVIF client never touches media data, so the codebase is reviewable at modest cost.

patrickelectric/onvif-rs takes the generative route:

  • What it is: types and operations auto-generated from the official XSD schemas, avoiding hand-written SOAP—an idea worth borrowing: ONVIF’s WSDL/XSD is a ready-made interface definition, and generation beats handwriting for reliability.
  • Status: no pushes since 2023-09; a fork of lumeohq/onvif-rs. Read it as the reference implementation of “generative clients”; don’t depend on it directly.

GB28181: Both Directions Are Early

siprs (v0.1.2, published 2026-07):

  • What it is: an ambitious project—a complete SIP protocol stack in pure Rust plus a GB28181 adaptation layer, layered as a standard SIP stack (core/message/transport/transaction/dialog), with built-in Gb28181Device (device side) and Gb28181Server (platform side: registration, catalog subscription, play/playback/download, alarms, mobile position), claiming WVP-PRO signaling compatibility.
  • Status: version 0.1.2, one-star repo. “Right direction, just started” is the generous reading.
  • How to use it: excellent study material for SIP stack internals (transaction state machines, dialog management are textbook-grade); premature for production—the GB adaptation layer’s completeness needs per-signaling verification on your side.

gmv (305★ on Gitee, 190★ on the GitHub mirror, updated through 2026-08):

  • What it is: a full-stack GB28181 platform in pure Rust, compatible with both 2016 and 2022: signaling service (SIP) and streaming service (RTP/PS parsing; H.264/H.265 in, HTTP-FLV/fMP4/DASH out) decoupled for independent deployment, with an online demo.
  • How to use it: the closest to “deployable” among Rust GB platforms—which also says the deployable ones in this ecosystem fit on one hand. Reading its RTP/PS parsing layer helps a lot with understanding the GB media plane.

Moonfire’s “zero-transcode direct-to-disk” approach deserves expansion: recording without transcoding means CPU cost is essentially network packet handling; the storage format is raw track data plus an index, and playback generates MP4s from index ranges on demand. It’s the most economical architecture for a home NVR—MiBeeNvr’s storage rewrite took cues from exactly this.

The Cross-Language References You Can’t Skip

For GB development, three non-Rust/Go projects are the de-facto learning baselines:

ProjectLanguagePositionWhat to read
WVP-GB28181-proJavaThe de-facto GB platform standard (7.2k★): Spring Boot + ZLMediaKit + MySQL/RedisThe first reference for the GB business loop (device management, cascading, playback dispatch); note the README self-describes as based on the 2016 edition

SRS’s line—“please lower your expectations; the GB pits are too deep to fill”—belongs on a poster. Even when self-developing in Go/Rust, the hard parts (PS parsing, SIP signaling state machines) should start from reading ZLMediaKit’s and WVP’s implementations—most GB pits have already been stepped in and written into someone’s code.

The pragmatic conclusion: it’s layering, not either-or. Platform services, signaling orchestration, and fast-iterating backends fit Go; a core media engine or storage engine chasing zero-copy, low latency, and memory safety is Rust’s home turf—Moonfire and str0m split exactly that way. For a Go-based project like MiBeeNvr, there’s no reason to switch languages just for GB support.

Learning Route: Four Phases

The classic mistake in learning these protocols is starting from the spec and giving up in chapter three. Follow “tools first → read implementations → hands-on integration → advanced compliance”; every step pays off visibly.

Phase 1: Concepts and Tools

  • ONVIF: on onvif.org, read the discovery and security chapters of the Core Specification plus the Profile S/T capability lists (don’t read cover to cover—use them as dictionaries); install ONVIF Device Manager (the community-standard Windows debugging tool) and scan a real or simulated device to see what Profiles and stream URIs look like.
  • GB28181: download the GB/T 28181-2022 text (free from openstd.samr.gov.cn), focusing on chapter 4 (protocol structure), chapter 9 (signaling flows), and the appendices on codes and MANSCDP; again, read against packet captures, not linearly.
  • Tools first: Wireshark with udp.port==3702 (ONVIF discovery), the sip filter (GB signaling), and Telephony → RTP → Stream Analysis (PS streams). Seeing real messages before reading the spec changes the efficiency completely.

Phase 2: Read Mature Implementations

  • Go route: close-read gowvp/owl (the GB signaling loop + the ZLMediaKit handoff) and MediaMTX (gortsplib’s RTSP state machine, protocol interconversion).
  • Rust route: read oxvif (SOAP construction and session management) and Moonfire NVR (zero-transcode storage and the streaming thread model).
  • Behavior baseline: use WVP-GB28181-Pro as the business-loop reference (Java—reads fast); go straight to ZLMediaKit source for PS demuxing.

Phase 3: Hands-On Integration (No Hardware)

The critical phase—run the full chain without buying cameras:

  • GB side: EasyGBD (github.com/EasyDarwin/EasyGBD) simulates the device, compatible with 2011/2016/2022; run SRS (built with GB28181 enabled) or ZLMediaKit as the platform. Watch the full chain—REGISTER → 401 → registered → keepalive → platform INVITE → RTP/PS push—matching each step in Wireshark.
  • ONVIF side: start a simulated device via onvif-go’s virtual camera or oxvif’s mocks, then discover, fetch Profiles, and exchange stream URIs with ONVIF Device Manager or your own client—all five steps (Probe → ProbeMatch → GetCapabilities → GetProfiles → GetStreamUri) walked end to end.
  • Close the loop: once both ends work, chain “simulator → platform → browser viewing”—a complete minimal NVR prototype.

Phase 4: Advanced and Compliance

  • Read the engineering chapters of SRS’s official GB28181 docs (the pitfall guide).
  • Compare the 2011/2016/2022 differences to understand why version negotiation is a mandatory platform capability.
  • For government/enterprise projects, study the GB 35114 national-crypto system and MPS testing requirements (the codec & security layer of the landscape post).

MiBeeNvr’s Implementation Path

Collapsing the survey into an execution order:

  1. Complete ONVIF capabilities (in progress): v0.9 shipped zero-config discovery; next, align the media and metadata interfaces to Profile T—especially HTTPS media streaming, positioning ahead of the 2027 Profile S cutoff.
  2. Evaluate the GB28181 uplink: assess the self-developed signaling effort against gowvp/owl’s SIP implementation (panjjo/gosip); on the media plane, prefer integrating ZLMediaKit for PS demuxing over hand-writing it.
  3. Keep the media architecture: the RTSP-pull plus WebRTC/FLV/HLS/SRT-egress shape stays—egress is complete, ingress extends as needed.
  4. Vendor adapter layer: reserve the slot in the architecture (interface abstraction + per-vendor adapters); fill in Hikvision ISAPI and other private APIs when concrete requirements arrive.
  5. Compliance capability slots: audit logs, tiered permissions, and data destruction get reserved interfaces in the storage-layer design—no retrofitting before acceptance.
