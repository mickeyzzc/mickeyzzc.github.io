A Map of Distributed Consensus: From Paxos to DAG-BFT — Boundaries and Selection Across Four Families

August 12, 2026 Architecture & Design Distributed Systems, Consensus, Paxos, Raft, BFT, Blockchain, Selection Tech & Engineering Selection Series 3993 words 19 min read
🔊

etcd uses Raft, Cosmos uses Tendermint, Bitcoin uses PoW, Sui uses Mysticeti — they’re all “consensus,” but they do not solve the same problem. Electing a leader among a few known nodes in a datacenter and reaching agreement on a ledger among anonymous nodes on a public chain sit a full order of magnitude apart in their assumptions. Mashing every consensus algorithm onto one throughput axis is why so many selection guides read like mush.

This post groups mainstream consensus into four families by fault model and works inward from the concrete problem of how nodes agree on a single value: first the design space carved out by three boundaries, then each representative algorithm’s message flow and what it optimizes, and finally selection. Key algorithms get a sequence/state diagram, and there’s a go run-nable PoW example at the end.

What consensus actually solves

Start with a concrete scene. You have 3 database replicas — in Beijing, Shanghai, Shenzhen — holding the same account balance. A transfer wants to change the balance from 100 to 90. If each replica updates on its own, and Beijing updates, Shanghai misses the message due to network jitter, and Shenzhen receives a reordered stale message — the three copies now disagree, and later reads will see three different balances.

Consensus is the problem of making those 3 replicas eventually reach one, irrevocable agreement on “balance = 90,” even if one of them crashes and a few messages are lost.

Two concepts are worth separating up front; it helps everything afterward:

  • Single-value consensus: agreeing on one value. This is the foundational problem; Paxos’s original paper (single-decree / synod) solves only this.
  • State Machine Replication (SMR): real systems don’t need agreement on one value, they need agreement on the order of a sequence of operations — transfer 1, transfer 2, transfer 3 must apply in the same order on every replica. Multi-Paxos / Raft / PBFT are all, at heart, “single-value consensus chained into SMR.”

Once SMR clicks, it’s obvious why consensus is the foundation under anything with trusted state: database replica consistency, etcd/ZooKeeper leader election and config sync, blockchain ledger ordering — all built on it.

Why there’s no one algorithm to rule them all: three boundaries

If a universal algorithm existed, we wouldn’t need all these names. Three theoretical boundaries box the design in.

Boundary 1: how badly can a node fail — the fault model

ModelWhat a node can doExample
Crash-stopHalts suddenly, doesn’t liePower loss, process crash
Crash-recoveryRestarts, disk state recoverablePull the plug, reboot
ByzantineAnything: lie, forge, colludeHacked node, public-chain attacker

CFT (Crash Fault Tolerant) algorithms assume nodes only crash; BFT (Byzantine Fault Tolerant) algorithms assume nodes can lie. That’s the first dividing line — how much do you trust the nodes across from you.

Boundary 2: FLP impossibility — why not “fully async + deterministic”

In 1985, Fischer, Lynch, and Paterson proved: in a strictly asynchronous network (no bound on message delay), no deterministic consensus protocol can guarantee both safety and liveness, even if only one node is allowed to crash.

The intuition is straightforward: the algorithm can’t tell “a node crashed” from “it’s just slow” — if it keeps waiting, it may wait forever (loses liveness, system stalls); if it pushes on without it, the node may surface an old message later and cause a conflict (loses safety, two contradictory decisions). Neither road works.

So every practical protocol makes a concession: either assume partial synchrony — there exists some unknown Global Stabilization Time (GST) after which the network behaves (Raft/PBFT/Tendermint all rely on this); or add randomization to break symmetry (HoneyBadger), so the adversary can’t stall the system precisely. Hold onto this — almost every “why is X designed this way” below traces back to it.

Boundary 3: the fault-tolerance ceiling — why BFT needs 3f+1 but CFT only 2f+1

This ceiling is worth deriving in full.

  • CFT tolerates at most f < n/2: i.e. needs n ≥ 2f+1 nodes. It works by majority quorums — any two majorities (each more than half) must intersect, and since CFT nodes don’t lie, the node in the intersection keeps the two majorities from conflicting.
  • BFT needs n ≥ 3f+1: i.e. tolerates at most f < n/3 malicious nodes.

Why the extra f? The key is “the intersection must contain at least one honest node.” In BFT each majority quorum is 2f+1 nodes, so any two quorums intersect in at least f+1; if there are only f malicious nodes total, then at least 1 of those f+1 is honest — and that honest node is what makes it impossible for two quorums to confirm conflicting values. CFT nodes don’t lie, so the intersection only needs to be non-empty (2f+1 suffices); BFT nodes do lie, so the intersection must be “at least one honest,” which is what forces 3f+1.

Remember this derivation and you’ll have the reason behind every “PBFT uses n=3f+1” and “each phase collects 2f votes.”

Now into the message flows, family by family.

The CFT family: nodes only crash

2PC: the earliest attempt, and why it blocks

Two-Phase Commit (2PC) is the oldest “consensus,” serving atomic commit for distributed transactions. It has a coordinator and several participants:

  1. The coordinator sends Prepare; each participant votes “can commit” or “no.”
  2. If all say yes, the coordinator sends Commit; otherwise Abort.

Its hard failure is blocking: if the coordinator crashes before sending Commit, participants get no final decision and dare neither commit (others might abort) nor abort (others might commit) — they wait forever. 3PC adds a PreCommit phase and timeouts to soften this, but still goes inconsistent under network partition, so it’s rarely used directly in production.

More importantly, 2PC solves “atomic commit” (a thing is either fully done or fully not done), not general state machine replication, and it’s acutely sensitive to the coordinator as a single point. So modern systems usually run Paxos/Raft for replication and layer transactions on top.

Paxos: preemption by ballot number

Paxos (Lamport, 1998) was the first asynchronously fault-tolerant consensus proved correct. Its core, in one sentence: use a globally unique, monotonically increasing “proposal number (ballot)” to stake territory — a higher number always overrides a lower one — and once a value is accepted by a majority, every later proposal must adopt that value.

It runs in two phases; the message flow between Proposer and Acceptor looks like this:

mermaid
sequenceDiagram
    participant P as Proposer
    participant Q as Acceptor set
    P->>Q: ① Prepare(ballot=N) broadcast to all Acceptors
    Q-->>P: ② Promise, a majority: "I won't accept older numbers" + echoes any accepted value
    Note over P: quorum reached; if any value was already accepted, reuse it
    P->>Q: ③ Accept(ballot=N, value) broadcast
    Q-->>P: ④ Accepted, a majority
    Note over P,Q: majority Accepted → that value is chosen

The two phases do two different jobs:

  • Prepare/Promise (preempt + probe): the Proposer asks with number N, “can I propose with N?” The Acceptor’s rule: if N is larger than any number I’ve promised, I’ll promise not to accept any smaller number, and I’ll tell the Proposer the value I’ve already accepted (if any). This step both stakes territory and probes “did someone already fix a value here.”
  • Accept/Accepted (fix the value): once the Proposer has a majority of Promises it sends Accept. Key rule: if any Promise carried an already-accepted value, the Proposer must use that value (the one with the highest accepted number), not its own intended value; only if nobody accepted anything can it use its own new value.

Round 1 (A moves first):
  A sends Prepare with ballot(1,A) → a1/a2/a3 have seen nothing bigger, reply Promise (empty).
  A gets a majority (a1/a2), nobody accepted anything → A uses its own X.

Round 2 (B arrives later, wants Y):
  B sends Prepare with a bigger ballot(2,B).
  a1/a2 have already accepted (1,A,X); since (2,B)>(1,A) they reply Promise and echo "I accepted X."
  B gets a majority of Promises and, by the rule, must reuse X (it cannot switch to Y).
  B sends Accept(2,B, X) → the final value is still X.

No matter how badly B wants Y, the outcome is X — that’s Paxos safety. When two Proposers “duel” concurrently, neither may reach a majority (they keep interrupting each other); randomized backoff (whichever backs off first yields) breaks the symmetry — a standard fixture of real Paxos implementations.

Paxos’s trouble is that it only defines “single value.” Turning it into usable log replication (Multi-Paxos) means adding a stable Leader, log slots, retransmission — every implementation re-lives the pain. Hence its reputation for being hard to understand and hard to implement.

Raft: splitting consensus into three subproblems

Raft (2014) has one goal: understandability. Its premise is “Paxos is hard because the Proposer/Acceptor/Learner roles are tangled,” so Raft uses a strong Leader to make data flow one-directional: all client requests go to the Leader, and the Leader pushes to Followers.

It splits consensus into three sub-problems. First, roles and election:

mermaid
stateDiagram-v2
    [*] --> Follower
    Follower --> Candidate: election timeout, no Leader heartbeat
    Candidate --> Leader: won a majority of votes
    Candidate --> Follower: saw a higher term, or timed out again
    Leader --> Follower: saw a higher term
  • Term: Raft’s unit of time, a monotonically increasing logical clock. Each election opens a new term.
  • Leader election: every node has a randomized election timeout (say 150–300ms). Whoever times out first becomes a Candidate, increments the term, votes for itself, then solicits votes (RequestVote) from others. A majority of votes makes it Leader. The randomized timeout is key — it makes nodes almost never start elections simultaneously, avoiding repeated ties.
  • Log replication: client sends a command to the Leader → Leader appends it locally → sends it to all Followers via AppendEntries (heartbeats reuse this) → once a majority of Followers confirm, the Leader marks the entry committed and notifies Followers. AppendEntries carries PrevLogIndex/PrevLogTerm for log matching, ensuring every replica’s log converges.
  • Safety: a handful of rules guarantee “a committed entry is never lost or overwritten” — for instance, “the Leader’s log is always the most complete” (a node only votes for a candidate whose log is at least as up-to-date as its own).

Raft is now the de facto cloud-native standard — etcd, Consul, TiKV, CockroachDB all run it or a variant. The trunk to hold onto is “strong Leader + randomized election timeout + log commits on majority.”

The BFT family: nodes lie

Nodes can do anything; you need n ≥ 3f+1. The classic is PBFT (1999); its three phases exist to defend against two attacks at once under “f malicious nodes”: a faulty primary and replicas disagreeing among themselves.

PBFT: why three phases

mermaid
sequenceDiagram
    participant PR as Primary
    participant R as Replica set (n=3f+1)
    PR->>R: ① Pre-Prepare: primary broadcasts the proposal
    R->>R: ② Prepare: replicas broadcast to each other, each collects 2f
    R->>R: ③ Commit: replicas broadcast to each other, each collects 2f
    Note over R: 2f Commits collected → each replica executes locally

Each phase defends against a different bad case:

  • Pre-Prepare: the primary (primary = view mod n) proposes. But the primary might be malicious — say, sending different things to different replicas. So the primary’s word alone doesn’t count.
  • Prepare: replicas broadcast “I received this proposal” to each other; each must collect 2f Prepares (plus its own implicit one — over 2f+1). This step ensures “all honest replicas agree on what we’re voting on this round,” squeezing out the primary’s room to misbehave.
  • Commit: another round of broadcast, another 2f collected. This step ensures “even if some replica goes offline next, the others won’t execute a value nobody else can confirm” — leaving room for view-change later.

Why both Prepare and Commit? Because a single layer of majority can’t simultaneously allow “replace a bad primary” and “don’t overturn an already-executed value after replacement.” Two layers of voting plus the 2f threshold (in 3f+1, a 2f+1 block of verifiable signatures outweighs f malicious ones) nail safety down. The cost is O(n²) communication — every replica talks to every other.

When the primary crashes or misbehaves, replicas swap it with view-change (new primary = (view+1) mod n). Just about every BFT algorithm after PBFT is trying to make view-change cheaper.

HotStuff / Tendermint / IBFT: what each optimizes

  • HotStuff (2019): turns PBFT’s “replicas all talk to each other” into “each phase, only the Leader aggregates a +2/3 signature and rebroadcasts” — dropping communication from O(n²) to O(n) (linear), and it supports pipelining (multiple blocks in flight). Aptos’s AptosBFT descends from it. (HotStuff and Ethereum’s Casper FFG are structurally kin — Dahlia Malkhi co-authored HotStuff and also wrote up Casper FFG through a BFT lens.)
  • Tendermint / CometBFT (Cosmos): rotating proposers + two vote rounds for instant finality — once a block gets +2/3 precommits it’s irreversible. Clean finality, at the cost of a full vote per block.
  • IBFT / QBFT: PBFT’s lineage landing in the EVM world. IBFT is EIP-650 (2017; formal paper arXiv:2002.03613 by Moniz et al.), one of the most-deployed permissioned-chain consensuses in Quorum / enterprise Ethereum; QBFT is the EEA’s evolution of IBFT with Dafny formal verification, used by GoQuorum and Hyperledger Besu — deterministic finality, no forks.
  • HoneyBadger: another route — reliable broadcast plus cryptographic randomization for consensus in a fully asynchronous network, no partial-synchrony needed, partition-resistant but lower throughput.

A point often confused: QuePaxa is CFT, not BFT

QuePaxa (SOSP'23, EPFL DEDIS, Escaping the Tyranny of Timeouts in Consensus) gets labeled “async BFT” in a lot of write-ups. I checked its official repo and Cloudflare’s post — both state plainly: QuePaxa is crash fault tolerant, “like Raft-based systems, we do not handle Byzantine faults.” It doesn’t target malicious nodes; it targets a pain Multi-Paxos/Raft share — using timeouts for leader replacement, so a slow or DDoSed leader stalls the whole system in timeout waits.

QuePaxa uses randomized hedging delays plus a multi-armed bandit to pick leaders dynamically, making safety independent of timeouts: a slow leader can’t bog down correct nodes, and under WAN DoS the median latency stays under 380ms. The paper reports ~584k cmd/s on LAN and ~250k cmd/s on WAN — same order as Multi-Paxos (the baselines are Multi-Paxos/Raft/EPaxos, all CFT). Cloudflare’s Meerkat (2026) is its first public implementation, in Rust, with PoCs up to 50 global replicas — but as of writing it’s still an internal experiment, not in production. Don’t be misled by “it’s deployed.”

It belongs in the BFT chapter only because it shares the “timeout-free” theme with async BFT — not because it tolerates Byzantine faults.

Public-chain PoX: replace trust with economic cost

A public chain is no-admission, anonymous, churn-heavy — you can’t assume “known honest,” so PoX flips it: make malice cost more than it pays, replacing identity with compute or capital.

PoW: a lottery paid in compute

PoW (Proof of Work) is blunt: nodes (miners) race to find a nonce so the block header’s hash has enough leading zeros. Hash functions are unpredictable — you can only brute-force — so it’s hard to compute, trivial to verify: mining burns massive compute, but checking takes one SHA-256.

// Minimal PoW demo: increment nonce until the hash has enough leading zeros. go run main.go
package main

import (
	"crypto/sha256"
	"encoding/hex"
	"fmt"
	"strconv"
	"strings"
	"time"
)

func mine(prefix string, difficulty int) (uint64, string, time.Duration) {
	target := strings.Repeat("0", difficulty)
	var nonce uint64
	start := time.Now()
	for {
		data := prefix + strconv.FormatUint(nonce, 10)
		sum := sha256.Sum256([]byte(data))
		hash := hex.EncodeToString(sum[:])
		if strings.HasPrefix(hash, target) {
			return nonce, hash, time.Since(start)
		}
		nonce++
	}
}

func main() {
	const difficulty = 4 // leading-zero bits; +1 difficulty roughly doubles expected work
	nonce, hash, elapsed := mine("block:micke:", difficulty)
	fmt.Printf("nonce = %d\nhash   = %s\nelapsed = %v\n", nonce, hash, elapsed)
	fmt.Println("Verification takes one SHA-256 — that's PoW's \"hard to compute, easy to verify\".")
}

The longest-chain rule is the soul of PoW consensus: when two miners produce blocks at the same time and fork, the rule is “always follow the longest (most cumulative work) chain.” To rewrite an already-produced block, an attacker would need to recompute more hashes than the honest network — i.e. control 51% of hash power, prohibitively expensive. That’s where PoW safety comes from. The downsides are just as blunt: energy heavy, BTC only ~7 TPS, and only probabilistic finality (the deeper a block is buried in the longest chain, the less likely it’ll ever be undone — but never exactly 0).

PoS: skin in the game

PoS (Proof of Stake) swaps “race on compute” for “race on deposit.” Validators stake funds (ETH on Ethereum) for voting rights; proposers are picked pseudo-randomly, weighted by stake. Ethereum’s Gasper = Casper FFG (two vote rounds on checkpoints to finalize) + LMD-GHOST (fork choice).

Safety comes from slashing: a validator that double-signs or makes surround votes gets its deposit burned. So an attack costs “at least 1/3 of total stake burned” — malice becomes a money-losing bet; that’s economic finality. It solves PoW’s energy problem and introduces new challenges: nothing-at-stake (solved by slashing) and long-range attacks (old keys replaying history; mitigated by weak-subjectivity checkpoints).

Other PoX variants: DPoS (EOS 21, Tron 27 producers) has token holders elect a few block producers — high throughput, more centralized; PoA uses identity as permission, common on testnets; PoH (Solana) uses a verifiable delay function as a cryptographic clock paired with PoS for high TPS, but its known block schedule makes it a DDoS target.

DAG-BFT: breaking the linear throughput ceiling

Traditional consensus lines transactions up into linear blocks: one Leader produces a block, broadcasts it to everyone, confirms, then produces the next. Throughput is choked by two things — block production is serial, and what’s broadcast is an ever-growing block. More nodes and bigger blocks just compound the jam.

A DAG (directed acyclic graph) organizes blocks as a graph where replicas produce blocks in parallel, and the key move is splitting “data dissemination” from “consensus ordering”:

Narwhal is the mempool layer: validators broadcast transaction batches in parallel, naturally forming a DAG, with throughput around ~160k TPS. Bullshark runs consensus over that DAG. Mysticeti (Sui, NDSS'25) goes further as an “uncertified DAG” — it doesn’t wait for full signature certificates and commits directly on the graph in 3 rounds (the BFT lower bound), pushing latency down to ~390ms, about 80% lower than Bullshark. Shoal / Shoal++ (Aptos, FC'24 / NSDI'25) layer pipelining and leader reputation on Narwhal, proactively routing around slow leaders and eliminating timeout stalls in most scenarios.

A few more directions on the DAG line: Avalanche drops BFT voting for repeated random sampling of a few peers, an “avalanche” positive feedback that converges sub-second, leaderless; Hashgraph (Hedera) uses gossip-about-gossip plus virtual voting for async BFT; Algorand picks committees via VRF cryptographic sortition; Slipstream (arXiv 2024) combines “dynamic availability” (longest-chain-like, tolerates nearly half the nodes offline and still produces blocks) with a “finality gadget” (BFT, needs 2/3 active) on one DAG — the available chain keeps liveness, the final chain keeps finality.

A note on EPaxos: it’s a leaderless, conflict-tolerant Paxos variant where any replica can act as a temporary leader; non-conflicting commands take a fast path. Its fast-path quorum is F + ⌊(F+1)/2⌋ (for 5 replicas, F=2, that’s 3). Some write-ups show F + ⌊F/2⌋ + 1, which evaluates to 4 for F=2 and contradicts “same as a plain majority at 5 replicas” — the correct form is the one with (F+1)/2.

A few concrete rules:

  • Internal systems, trusted nodes: Raft by default (easy to operate); Multi-Paxos if you already have a Paxos stack; 2PC layered over replication for distributed transactions.
  • Permissioned/consortium chain, malicious nodes: for deterministic finality pick PBFT / HotStuff / IBFT; for fully async, high-adversary settings pick HoneyBadger.
  • Public chain, anonymous, censorship-resistant: for max decentralization and security pick PoW; for low energy and stronger finality pick PoS (Gasper-like); accept weaker decentralization for TPS with DPoS.
  • Throughput is the bottleneck: prefer DAG-BFT (Mysticeti / Shoal); they sidestep linear BFT’s O(n²) cost at 100+ nodes by separating data from consensus.
  • Financial settlement needs irreversibility: pick deterministic finality (Tendermint / PBFT / HotStuff / Mysticeti); if “deeper = safer” is acceptable, PoW’s probabilistic finality is simpler.

One thread ties it together: internal → Raft; permissioned and malicious → BFT; public and secure → PoW/PoS; throughput ceiling → DAG-BFT. As for timeout-free async CFT like QuePaxa, it targets control-plane scenarios that are geo-distributed, fear slow leaders and DDoS — wait until Meerkat is actually in production before selecting it.
