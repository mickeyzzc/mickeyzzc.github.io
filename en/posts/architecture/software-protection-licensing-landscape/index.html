Software Protection and Licensing Landscape: From Keygens to Denuvo, Why Local Verification Always Breaks

October 7, 2026 October 7, 2026 Architecture & Design Software Protection, License Enforcement, Keygen, DRM, Reverse Engineering Tech & Engineering Selection Series 3435 words 17 min read
🔊

In February 2026, a tool called Hypervisor appeared that could bypass Denuvo anti-tamper without a game-specific crack — the price being that Secure Boot and a few Windows virtualization features had to be turned off. By April, the community confirmed that every single-player, non-VR game previously protected by Denuvo was vulnerable to the method. In September, the group RUNE stripped Denuvo out of Assassin’s Creed Mirage entirely; Denuvo responded by shipping updated protection versions and filing a DMCA lawsuit against the distributors. Four decades into the software licensing arms race that began with serial numbers, the strongest commercial anti-tamper scheme now holds out for a matter of months.

This post walks through the major protection technologies in the order they were attacked: serial numbers and keygens, online activation, hardware dongles, obfuscation and anti-tamper, hardware roots of trust, white-box cryptography, and SaaS. Every generation answers the same question — how does a program confirm that “this machine is allowed to run this code” — and every generation’s crack history points to the same fact: verification logic runs on a machine the attacker fully controls, so anything verifiable can be bypassed. What differs is only the cost of the bypass, and who pays it.

The Nature of the Problem: Verifier and Attacker Share a Machine

License enforcement is, mathematically, a decision function: it takes an authorization input (a serial number, a license file, an activation code) plus the runtime environment (hardware, clock, network), and outputs allow or deny. Every protection technique does the same thing — moves part of that function somewhere the attacker cannot reach:

  • Hide the algorithm inside the binary → obfuscation and virtualization
  • Hide the key inside hardware → dongles, TPM, TEE
  • Move the decision to a server → online activation, license servers
  • Never ship the code at all → SaaS

With that map in place, each section below is the history of “where it was moved” and “how it was brought back.” Start with the first generation — to this day, “keygen” is what most people picture when they hear “software crack.”

Keygens: The Mathematical Dead End of Symmetric Verification

Shared software in the 1990s was licensed with a serial number: the program contained a verification routine, and the user’s key passed through bit operations, checksums, and segmented table lookups until the remainder matched and the software unlocked. The critical detail is that this verification routine ships in its entirety inside the distributed binary — a cracker disassembles it, wraps it in a small standalone program, and generates valid keys forever. That is a keygen: not “guessing passwords,” but reusing the verification algorithm in reverse.

The problem in the diagram is the dashed edge: the verification algorithm and the data it checks live in the same trust domain, and both belong to the attacker. As long as the algorithm is symmetric — the verifier knows nothing the attacker cannot also know — a keygen is mathematically unavoidable.

The fix became industry standard around 2000: asymmetric signatures. The license file is signed with the vendor’s private key and binds a hardware fingerprint, an expiry date, and feature flags; the program embeds only the public key for verification. With the private key out of reach, deriving it from the public key is computationally infeasible — once RSA 2048 became the norm, the legitimate keygen was dead. Software that still ships with keygens today is essentially old products or small utilities that never upgraded to signatures.

But asymmetric signatures solve only half the problem. They guarantee the attacker cannot forge a valid key; they do not guarantee the program performs the check at all — the verification code is still local, and one jnz changed to nop skips it. So the mainstream of cracking shifted from “computing a key” to “patching out the check” — keygen nfo files have said cracked by for years, because the two were always one workflow. Public-key cryptography closed the “forge the authorization” path; it never closed the “skip the check” path.

Online Activation: Moving the Verdict to a Server

The next step against patches was moving the verdict server-side. Windows XP Product Activation set the precedent for mainstream consumer software in 2001: within 30 days of installation you had to contact Microsoft’s servers and exchange a hardware-bound digital certificate, or the system degraded into lockdown. Enterprise volume licensing got a separate mechanism, KMS (Key Management Service): an on-premise KMS host, with clients renewing every 180 days.

The elegance of server-side verdicts is that patching the client is no longer enough — you have to make the client believe it “really reached Microsoft.” The cracker answer was to stage the entire conversation locally: a KMS emulator impersonates the KMS host on the machine itself, the client renews against the fake server every 180 days, a scheduled task keeps it fresh, and nothing ever expires. Today the open-source project Microsoft Activation Scripts (MAS) packages this work into four methods:

HWIDUses generic installation keys to obtain a hardware-bound digital license from Microsoft’s own activation serversPermanent

The HWID row is the striking one: pirated activation flows through Microsoft’s official endpoints and ends with a digital license Microsoft itself issued. Every check on the client genuinely passed — the signature is real, the server is real, the certificate is real — only the premise “this machine deserves activation” is fake. Online activation moved verification to the server, but the gap “the server’s verdict is based on data the client reports” is baked into the protocol.

Enterprise licensing converged on the same shape in the same period: license files signed with RSA/ECDSA, bound to machine fingerprints and expiry dates, backed by license servers for floating seats — FlexLM/FlexNet in the EDA industry, CodeMeter and Sentinel EMS in industrial software, and newer SaaS licensing services like Cryptlex and Keygen. Their common weak points are engineering, not cryptography: JWT libraries used with the wrong algorithm (the alg: none class of historical bugs), private keys mishandled, license server APIs left unauthenticated, offline grace periods defeated by clock rollback. The licensing system itself became an attack surface.

The signature chain has produced no shortage of failures in recent years: in 2020 SolarWinds’ build system was breached and the attackers signed backdoored Orion updates with a legitimate certificate; in 2022 two of Nvidia’s code-signing certificates were stolen in the intrusion and later showed up in malicious drivers; in 2023 3CX’s signed desktop client was poisoned through its supply chain; the same year, Microsoft’s consumer-account signing key was stolen and used to forge Azure tokens that read government mailboxes. None of those incidents involved a licensing system, but the conclusion transfers directly — no matter how strong the signature, custody of the signing key is everything.

Hardware Dongles: Making the Key a Plug

If software cannot hold a key, make the key hardware. Dongles became popular from the late 1980s, first on parallel ports and later USB: the program periodically issues a challenge-response exchange with the dongle, with the key and response logic sealed in the dongle’s firmware and nothing to reverse on the software side. HASP, Rainbow, and Sentinel dominated the CAD, EDA, and industrial software markets for decades.

The crack path was equally direct: the dongle’s answers must travel through a driver back into the software, so dump the dongle’s storage cells and write a virtual driver that impersonates the real thing at the USB layer — dongle emulation. The hardware’s raise in attack cost was real, but every check still ends with a comparison in software, and virtual machines, driver hooks, and firmware reverse engineering gradually flattened the “hardware-grade” claim.

More embarrassing was the protector’s own breach. In 2017, Gemalto’s Sentinel component hasplms was hit by a buffer-overflow vulnerability (CVE-2017-11498) affecting everything from HASP SRM to Sentinel LDK, and attackers used it to steal the Sentinel source code — the internals of a top commercial dongle scheme have been public ever since. Dongles still live in high-value B2B software today, but as hybrids of software licenses and hardware certificates; products relying purely on “the dongle is plugged in, therefore safe” have mostly left the stage.

Obfuscation and Anti-Tamper: Turning Code into a Maze

If the critical logic will be seen, make it unreadable. The evolution of this line: compression packers like UPX → encryption packers with anti-debugging → control-flow flattening (the OLLVM family) → virtualization. Virtualization is the current state of the art: Themida and VMProtect compile protected x86 code into a custom bytecode executed by an embedded private interpreter — the binary no longer contains the original instructions, only a virtual instruction set that changes with every build.

The attack, from academia and industry alike, is symbolic execution plus IR lifting: trace the VM interpreter with a symbolic executor, lift the bytecode behavior back into LLVM IR, and hand it to a conventional optimizer to recover control flow. Public research (Triton-based VMProtect devirtualization, tools like NoVmp) already automates “pure function”-level virtualized code; whole-program recovery still costs serious manual effort, but the roadmap is public. Runtime packers remain an unsolved problem for generic automated unpacking — the flip side of that sentence is that for a determined, well-resourced analysis, a packer is a progress bar.

The gaming industry’s Denuvo pushed this line to its commercial extreme: anti-tamper code interwoven with the game itself, customized per title, with an explicit goal — hold the launch window. Game sales concentrate in the first weeks after release, and once the window passes the protection has done its job. This model held steady for years, until the February 2026 Hypervisor tool changed attack layers: it never touches Denuvo’s code, instead distorting integrity checks from the virtualization layer, and one tool works across every protected game — misaligned with a defense model built on per-title customization. Denuvo’s response — updated protection versions plus a DMCA lawsuit — is the standard move of every protection generation once a generalized attack catches up.

Obfuscation raises the cost curve; it does not provide a proof. It works against automated attacks and merely delays targeted, well-funded analysis.

Hardware Roots of Trust: The Only Generation to Reach the Physical Layer

The first three generations failed for the same root reason: the key or logic needed for verification ultimately exists in software on the attacker’s machine. The hardware root of trust line set out to end that — keys are generated and stored inside the chip, private keys cannot be exported, and verification runs in an isolated execution environment.

The names are familiar: TPM 2.0 (Windows 11 made it an installation requirement), Pluton from Microsoft and the chip vendors, Apple’s Secure Enclave, ARM’s TrustZone TEE. The licensing and content-delivery shape is remote attestation: the device signs a statement of “my boot chain and code hashes” with a hardware private key, and the server releases authorization or content keys only after verifying that signature.

Mobile got here first. Google shut down SafetyNet in January 2025, and its successor Play Integrity tiers its verdicts: the basic verdict relies on software signals and can be bypassed on rooted devices with spoofed fingerprints, while the strong integrity verdict is bound to hardware key attestation — defeating it takes a leaked TEE key, not a software trick. On the Apple side, Secure Enclave plus App Attest is the same architecture. For the first time in software licensing history, the attack threshold climbed to the physical layer.

The physical layer is under fire too. Intel SGX’s attack history makes the point: Plundervolt in 2019 used voltage glitching to extract data from enclaves, SGAxe in 2020 lifted sealed private keys outright, and ÆPIC Leak in 2022 uncovered an architectural side channel — and Intel’s answer was not to keep patching but to cut SGX from client CPUs entirely and move to TDX in the datacenter. The Widevine tiering on the content side tells the same story: L1 puts keys in a TEE, L3 implements them in software — L3 keys have been repeatedly extracted on rooted devices, and the security tier gap directly marks the fate of pure-software schemes.

The honest positioning of this generation is trading platform binding for attack cost. It works, at the price of a closed device ecosystem and compatibility baggage — the controversy over Play Integrity locking out GrapheneOS, which fully supports hardware attestation, is the other face of that price. For most teams building their own licensing systems, this generation is not an option; it is a fait accompli you inherit by depending on a platform.

White-Box Cryptography: Hiding the Key in Math, Broken by Statistics

Between “software cannot hold a key” and “not every device has a TEE,” cryptography offered an intermediate answer: white-box cryptography. The idea is to mathematically dissolve the key into lookup tables and obfuscated logic so that the key exists at no single location — even an attacker with total control of the execution environment who observes every intermediate computation should not be able to extract it.

The attack landed in 2016: differential computation analysis (DCA) ported differential power analysis from hardware side channels into software — statistically correlating intermediate values along execution traces against key candidates until the key floats out. The field never recovered: across three WhibOx contests (2017, 2019, 2021), every entry had its key extracted within the contest window; white-box ECDSA fell in 2022; and when masking and shuffling countermeasures appeared, higher-order DCA escalated right along with them — countermeasures raise the cost without changing the outcome.

The positioning is the same as obfuscation: a hardening measure, not a security proof. Telecom and DRM still deploy it, but only layered with TEEs or server-side checks as defense in depth; a deployment leaning on white-box as the main line of defense is no longer recommended by academia or industry.

AI Enters: The Inflection Point on the Reverse-Engineering Cost Curve

Every generation above was broken by labor-intensive specialists: reading disassembly, writing symbolic executors, unpacking, tracing protocols. That labor curve bent visibly around 2025, and the evidence is benchmarks and competitions rather than anecdotes.

On decompilation, LLM-assisted research (the Chisel line) already generates semantically equivalent, readable, compilable high-level code from binaries; Ghidra and IDA with LLM plugins for type recovery and comment generation have made AI a routine part of the reverse engineer’s workflow. The stronger evidence is DARPA’s AI Cyber Challenge (AIxCC): at the August 2025 DEF CON finals, the winning system ATLANTIS (the Georgia Tech and KAIST joint team) autonomously found vulnerabilities, validated exploits, and produced patches for real open-source infrastructure software, with the winning systems open-sourced per the competition rules. That capability shares a toolchain with breaking license checks — locating the verifier, finding the decision branch, understanding obfuscated logic are all within its range.

The impact on the two sides is asymmetric: the cracking side gains an order-of-magnitude reduction in the cost of “understanding a hundred thousand lines of obfuscated code”; the defense side can use AI to generate denser obfuscation and piracy detection, but obfuscation remains where the previous section left it — raising cost without proving security. The arms race accelerates on both sides, and the drop is steeper on the comprehension-cost side.

SaaS: No Shipped Code, Nothing to Reverse

Licensing has one answer that steps outside the technical fight entirely: don’t ship the software. Adobe moved its entire product line to Creative Cloud subscriptions in 2012 and revenue climbed year after year; Microsoft 365, Figma, and today’s per-token LLM APIs all made the same architectural decision — the value-producing logic runs on the server, the client is a shell, and a pirated client has nothing to connect to. There is nothing to crack.

That does not mean the problem disappeared; it means the attack surface moved. In the SaaS era, cracked software became stolen credentials: account theft and resale, leaked session tokens, gray-market clients rebuilt on reversed APIs, and straight-up scanning of committed .env files in code repositories for cloud keys. For defenders, anti-piracy becomes an identity and credential security problem — MFA, anomaly detection, key rotation, all the familiar machinery. The binary that used to be reversed became a login page that gets credential-stuffed; the difficulty did not drop, the battlefield just moved.

Three patterns run down that chart: the farther the decision point is from the attacker, the safer (local checks are weakest; server-side and hardware are strongest); cryptography itself has never been broken head-on — every failure was in the engineering around it: key custody, implementation, protocol; and generalized attacks eventually catch customized defenses — the output of a generic tool is reused by every subsequent crack, while a customized defense starts from zero each time.

What Real Products Use

Map the technologies back to real products and every category settles on the combination that matches its distribution shape, price point, and piracy exposure — not the “strongest” option:

  • Offline B2B (EDA, industrial software, medical devices): signed license files bound to machine fingerprints and expiry dates, floating license servers from the FlexNet/CodeMeter/Sentinel line; enforcement runs through audit clauses in contracts. The shape has barely changed in twenty years — at enterprise price points, legal remedies pay better than continued hardening.
  • Consumer software (Adobe CC, Microsoft 365): subscription plus online checks, deliberately light on the client; the real assets — cloud sync, asset libraries, AI quotas — live server-side, and the local binary is not where the value is.
  • Developer tools (JetBrains): license servers first, signed offline activation codes for air-gapped customers.
  • Consumer indie software: ship through the App Store, Steam, or the Microsoft Store and let the platform provide accounts and hardware attestation — the platform cut buys exactly that.
  • Games: Denuvo billed monthly, removed once the launch window closes; what is protected is the steepest stretch of the sales curve.
  • APIs and cloud services: no client to crack, so the defense lives entirely on the credential side — MFA, quotas, anomaly detection.

The common thread across all six: enforcement strength stops near “cracking costs more than the legitimate revenue at stake in that category” — nobody configures for “uncrackable.”
