Shipping an App to Every NAS and Router OS: Packaging and Listing Differences Across fnOS, ZSpace, UGREEN, Synology, QNAP, TrueNAS, OpenWrt, and iStoreOS

July 29, 2026 July 29, 2026 Architecture & Design NAS, App Distribution, Docker, Packaging, Listing, OpenWrt, Selection Tech & Engineering Selection Series 4030 words 9 min read
🔊

In October 2024, TrueNAS SCALE 24.10 “Electric Eel” ripped out its k3s backend and moved the entire app layer from Helm Charts to Docker Compose. Overnight, every old tutorial telling you to add a “custom train” to TrueNAS stopped working — 24.10 also deleted the “Add Catalog” button. That same year, fnOS, ZSpace, and UGREEN each launched or rebuilt their app centers: fnOS’s .fpk, UGREEN’s freshly opened developer portal in May 2026, all racing to build an app ecosystem.

Lined up side by side, these signal that NAS / router OS app distribution is splitting into two tracks: native proprietary formats plus review-gated stores (Synology, QNAP, TerraMaster), and Docker images plus a thin wrapper (TrueNAS, Unraid, fnOS, ZSpace, UGREEN). The open-source NAS (OMV) and router OSes (OpenWrt, iStoreOS) lean almost entirely on Docker and the system package manager.

This piece breaks down “how do I get an app onto each of the 14 major platforms”: packaging format, store policy, signing requirements, third-party sideloading channels, and how far an indie developer can realistically get. If you only want to know “I have an app, where do I ship first,” jump straight to the decision tree at the end.

The key observation: the bottom-right two quadrants (Docker-first and system-package-manager) are the indie developer’s main battleground. Synology / QNAP / TerraMaster have heavy review cycles on their native stores — but Docker runs on all of them too. We’ll go through each below.

A fact that runs through this whole piece: outside a few native proprietary formats, Docker runs underneath all 14 platforms. Build one multi-arch OCI image (linux/amd64 + linux/arm64) and you have a base that runs everywhere. The remaining differences are only “how does this image land in their store / package format.”

International NAS: proprietary formats and review gates

Synology DSM — .spk + review-gated; the community source is the real outlet

Synology’s .spk is the most mature proprietary format in this space, but also the highest barrier to list. DSM 7 tightened the rules: all packages are forced to drop privileges (a sc-${packagename} system user, no more root), the self-signed CSR workflow was removed from the UI, and only packages Synology signs during the publishing flow appear in the official Package Center. To go official you sign the Developer Distribution Agreement and pass review.

The real outlet for indie developers is third-party community sources: Package Center → Settings → Package Sources → Add. Type one in and it shows up under a “Community” section. The largest is SynoCommunity (packages.synocommunity.com, repo at github.com/Synocommunity) — set trust level to “Synology Inc. and trusted publishers.” You can self-host a Package Source too. Manual install (uploading an .spk directly) also works, though unsigned packages can be blocked by trust settings.

A few DSM 7 gotchas to know upfront:

  • Privilege dropping is mandatory. Legacy packages (Duplicati, FileBot, etc.) had to be rewritten en masse; your package must declare and use the sc- scoped user.
  • Build per DSM major version × CPU architecture. The toolchain matrix is real maintenance; a DSM 7.2.x toolchain mismatch surfaces as invalid file format.
  • Synology advertises ~1M downloads/month platform-wide — but only for what’s past review. Community sources don’t get that exposure.

QNAP QTS / QuTS hero — .qpkg submitted via Helpdesk; signature expiry is an old wound

QNAP’s .qpkg is built with QDK (QNAP Development Kit, github.com/qnap-dev/QDK). As with Synology, QNAP signs during review — the developer cannot self-sign, which is why third-party apps in App Center carry an exclamation-mark warning (unsigned).

The submission path is counterintuitive: build the .qpkg → test by manual install → install the “Helpdesk” app on a NAS → submit the package and metadata via Helpdesk → QNAP reviews. There is no “add a third-party repository” mechanism like Synology’s, so distribution basically means manual .qpkg upload. Admins can enable “Allow installation of applications without a valid digital signature” under App Center → Settings → General to sideload.

Two gotchas:

  • Digital signatures expire. When one does, App Center stops the app and users must reinstall an updated build — this has caused mass app outages historically.
  • On modern QNAP, Container Station (Docker) is increasingly the preferred route, and many “apps” in App Center are thin wrappers around Docker. If your app is already containerized, going through Container Station is far less work than building a .qpkg.

TerraMaster TOS — .tpk, open-source SDK but the smallest ecosystem

TerraMaster’s .tpk (TOS 7 also accepts .deb) has an OpenWrt-like directory structure and is primarily aimed at C/C++ cross-compiled apps, with the toolchain at github.com/TerraMasterOfficial/app-pkg-tools (includes the TOS 7 app development and publishing guide, plus review criteria in Review_Standards.md). Containerized apps go through Docker.

The developer program is the oldest among Chinese NASes (launched 2020), with two listing channels: the official app market (apply + review), and the TNAS community app platform (tmnascommunity.eu, self-service publishing after registering an account, around 100 free apps). The community store is often more current than the official one — Jellyfin, for instance.

Gotchas: official docs are sparse, especially around UI integration; .tpk native dev is C/C++ cross-compile, heavier than a pure Docker workflow. Most indie apps just ship as containers.

Docker-first platforms: the image is the app

TrueNAS SCALE — pure Docker Compose since 24.10, no third-party catalog

This is the platform that changed the most, and deserves its own section. 24.10 “Electric Eel” removed the k3s/Kubernetes backend entirely and moved the app layer to Docker Compose; the official catalog moved to github.com/truenas/apps, and the old truenas/charts (Helm era) is deprecated. Later releases 25.04 “Fangtooth” and 25.10 “Goldeye” continue the Compose line.

24.10 also deleted the “Add Catalog” option — the third-party catalogs of the Helm era (most notably TrueCharts) became invalid, TrueCharts dropped SCALE support, and recommended users migrate to standalone Docker / Proxmox. As of 25.04, custom trains are still not back (feature request at forums.truenas.com/t/custom-app-trains/25215).

How an indie dev actually ships here:

  1. Publish a standard Docker image (Docker Hub / GHCR).
  2. Users install via the TrueNAS UI’s “Custom App” wizard (point at an image, configure env / volumes / ports) or by pasting raw Docker Compose YAML.
  3. Unless your app is merged into the official truenas/apps repo (via PR), there is no store listing, no discoverability, no review.

Bottom line: getting an app to run on TrueNAS is trivial (it’s just Docker); getting discoverability is hard — the official catalog is PR-based and third-party catalogs were cut. Any guidance referencing k3s/Helm/TrueCharts/“Add Catalog” on TrueNAS is obsolete in 2026.

Unraid — Community Applications is the de facto store

Unraid’s “app” is a Docker container plus an XML template (defining image, network, ports, paths, variables, stored at /boot/config/plugins/dockerMan/templates-user). There is no native package format and no signing.

The distribution channel is Community Applications (CA) — a community-maintained plugin installed by nearly every Unraid user, aggregating 2,000+ Docker containers and plugins. It is effectively the Unraid app store (community-run, not made by Unraid the company).

The listing process is the lightest of any platform: host your template XML in a GitHub repo → submit the repo URL to ca.unraid.net/submit (or the forum submission thread) → pass a lightweight human curation → appear in the default repository list, visible to essentially every Unraid user. Reference template repo github.com/selfhosters/unRAID-CA-templates, template-writing guide selfhosters.net/docker/templating/templating/.

Gotcha: Unraid’s volume mapping uses share paths (/mnt/user/...), not arbitrary host paths; a template that doesn’t map to shares will confuse users. The XML template is Unraid-specific and non-portable — keep the Docker image generic and ship a separate Unraid template.

fnOS — .fpk wrapping Docker; a community store has already formed

fnOS’s .fpk is its own proprietary format, but underneath it’s a Docker image + docker-compose.yml + metadata, described by the community as “the APK/IPA of fnOS.” Built with the official fnpack (community wrapper fnpackup). There is no public developer portal or API yet; listing is by application — a Feishu form at trim-nas.feishu.cn/share, business contact jubao@infinities.com.cn, community at club.fnnas.com (the “应用中心&Docker” board).

But the sideloading channels are fully open, which is the practical indie path:

  • Manual .fpk install: App Center → Settings → Manual install → upload .fpk (officially opened for offline install in November 2025).
  • Docker: first-class — many official apps are themselves containers, with full Compose support.
  • SSH: enable under System settings → Terminal and SNMP (root login disabled by default; sudo passwd root, then edit sshd_config).

A community ecosystem has already grown up: github.com/conversun/fnos-apps is a third-party store with 115 self-hosted apps repackaged as .fpk (Plex, Emby, Jellyfin, qBittorrent, Immich, etc.), auto-synced daily. There’s also a community “FnDepot” decentralized app-source spec.

Gotcha: a .fpk tag-mismatch pitfall — if your compose references a bare tag 1.0.x but you pushed v1.0.x, install fails with a misleading manifest unknown / EOF. The .fpk spec has no official docs; it’s reverse-engineered from community projects.

ZSpace (ZOS) — review-gated store; Docker is the practical route

ZSpace has no documented native packaging format; distribution is effectively Docker images plus curated official apps. The new app store from October 2025 splits into three categories: official apps, third-party apps, and Docker apps, with hot-update support.

The indie path is narrow: the store has no public self-service portal, and third-party apps land via authorization-by-agreement — ZSpace negotiates rights with the upstream app’s author, then lists it. An “open platform” has only been announced for the enterprise EZOS line, with no public self-serve developer registration. The realistic routes are Docker (Compose support since April 2025) and SSH (enable in system settings, log in as admin then sudo -i for root; the prompt shows ZOS).

Gotchas: SSH config can reset after some system updates, needing re-enabling; the store is new and the third-party catalog is small and curated.

UGREEN UGOS / UGOS Pro — the most developer-friendly of the Chinese NASes

UGREEN is the only Chinese NAS with a public, formally launched developer portal open to individuals. The “UGREEN Cloud Developer Platform” at developer.ugnas.com went live on May 22, 2026 (announcement at lulian.cn/news/2185.html), positioned globally, with launch partners including Tencent Games and MiniMax.

Apps run on Docker (voted “feature of the year” by the community), and the store wraps containers with one-click install that auto-handles volume mapping and PUID / permissions. Process: apply at developer.ugnas.com (or email developers_bd@ugreen.com) → submit your app → UGREEN review → publish to the UGOS Pro App Center → users get one-click install with a 30-day full free trial. Open to individuals and teams; no registration fee, deposit, or revenue-share terms are publicly disclosed (commercial terms must be confirmed separately).

Sideloading is fully open too: Docker (enable it first in App Center, off by default), SSH. UGOS Pro SSH is under Control Panel → Terminal (port 22); legacy UGOS is under Device management → Debug functions, on port 922 — the two generations differ, don’t confuse them.

Gotchas: positioned as “low threshold entry, high standard review” — easy to get in, strict to pass (security + UX); commercial terms aren’t public and must be negotiated; the developer platform only launched in May 2026, so the ecosystem is still ramping and will change fast.

Open-source NAS and router OSes: the system package manager reigns

OpenMediaVault (OMV) — Debian + apt; Docker via OMV-Extras

OMV is a Debian-based open-source NAS with no app store of its own; app distribution goes through Debian’s apt package manager and the web UI plugin system. The standard path to Docker is OMV-Extras (wiki.omv-extras.org): System → Plugins, search for compose → install openmediavault-compose (7.x for OMV7, 8.x for OMV8) → Services → Compose → Settings → “Reinstall Docker” → then run docker-compose.yml files directly in the web UI.

For an indie dev, shipping an app to OMV means shipping a Docker image plus a compose file — no store, no review, no discoverability. OMV’s philosophy is “you’re the admin.” Getting a Debian-native package into the official repos follows Debian’s standard packaging/sponsorship process, unrelated to NAS.

OpenWrt — migrating from .ipk/opkg to .apk; LuCI apps are standard

This is the big migration that must be explained for router OSes. As of OpenWrt 25.12 (kernel 6.12), apk (Alpine’s package manager) is the default and .apk is the package format; the legacy opkg / .ipk is still used on ≤ 24.10 with a huge install base but is deprecated. The official “opkg to apk cheat sheet” covers the transition. Snapshot branches have been apk-first since late 2024.

Packaging paths:

  • Buildroot / SDK: each package is a Makefile under package/ with a define Package/... block. Indie developers use the OpenWrt SDK to build a single package without compiling the whole tree.
  • Official feeds: github.com/openwrt/packages (community apps/libs) and github.com/openwrt/luci (LuCI web UI apps, luci-app-*). Submission historically went through mailing-list patches with Signed-off-by:; GitHub PRs are now explicitly accepted.
  • Signing: repositories are signed. opkg used usign (Ed25519, keys in /etc/opkg/keys/, verifying Packages.sig against the Packages index); the apk era supports local signing keys (landed October 2024).
  • LuCI apps: a luci-app-foo is a web page bolted onto the LuCI admin interface — Makefile + controller + CBI model + static assets. This is the canonical way to ship a configurable app on OpenWrt.

Attended Sysupgrade (ASU) is a must-mention in a distribution context: a standard sysupgrade wipes packages you added after flashing. ASU (auc CLI, or luci-app-attendedsysupgrade, or the newer owut tool) sends your board plus installed-package list to sysupgrade.openwrt.org (code at github.com/openwrt/asu), which rebuilds a custom firmware image on demand. Packages in the official feed get baked into users’ ASU-rebuilt images automatically; a self-hosted feed does not — that’s the practical value of getting into the official feed.

Gotchas: musl libc by default (not glibc), so prebuilt glibc binaries won’t run; no systemd — init is procd; many devices have only 8/16/32 MB of flash, so heavy apps must live on external storage; kernel and kmod versions are tightly coupled. The realistic indie path is either the official feed (quality bar and maintainer review) or, more realistically, self-hosting a signed feed (ipk/apk on GitHub Pages, added by users to opkg.conf/apk config).

ImmortalWrt — the OpenWrt fork for China, with more packages

ImmortalWrt is an OpenWrt fork (github.com/immortalwrt/immortalwrt) positioned as “more packages ported, more devices supported, with default optimized profiles and localization for mainland China users.” It maintains its own feed (github.com/immortalwrt/packages), adding many China-specific apps (proxies, local services, drivers) that can’t go upstream. Firmware selector at firmware-selector.immortalwrt.org.

For distribution: an app that can’t pass upstream OpenWrt review may fit ImmortalWrt. Constraints are the same as OpenWrt (musl, no systemd, BusyBox), it tracks the apk migration, and has CERNET / Nanjing University mirrors for fast downloads in China.

Containers on OpenWrt — the de facto path for heavy apps

Running anything heavier than a LuCI config page on a router mostly means Docker/OCI images:

  • Host-side packages: dockerd + docker-compose + luci-app-dockerman (pulls in the deps), or luci-app-docker, or Podman. LXC is also supported (lxc + luci-app-lxc, sharing the host kernel).
  • Distribution: standard Docker/OCI images via any registry — there is no OpenWrt-specific container packaging.
  • Prerequisite: real disk; devices with only internal flash need external storage / overlay first.

This is the path of least resistance for an indie developer — it sidesteps musl, flash limits, and kernel coupling because your image brings its own userspace. Conversely, OpenWrt itself can run inside Docker/LXC (AlbrechtL/openwrt-docker, wukongdaily/openwrt-istoreos), commonly for “bypass routing” on x86 NUCs / Proxmox — don’t confuse this with “running containers on OpenWrt.”

iStoreOS / iStore — an app-store aggregation layer over OpenWrt

iStoreOS is a router / NAS OS built on official OpenWrt by the LinkEase team, whose signature feature is the iStore app store. The key distinction: iStore itself is distributed as OpenWrt .ipk packages (luci-app-store + luci-lib-taskd etc., served from istore.linkease.com/repo/all/store/), but the apps inside it are a mix — lightweight ones are standard luci-app-* .ipk plugins, heavy ones are Docker containers with a one-click install entry. So iStore isn’t a pure Docker store; it’s a unified storefront over both ipk plugins and Docker images, with a “Docker” tab plus DPanel managing the container side.

Repos: github.com/linkease/istore (UI: github.com/linkease/istore-ui), package cache github.com/linkease/istore-packages (so plugins don’t break firmwares on surprise updates). Docs at doc.istoreos.com/zh/guide/istore/.

The listing path (there is no public formal submission spec — inferred from the repos and community guidance): package your app as a standard OpenWrt luci-app-* ipk or a Docker image → open an issue / PR at github.com/linkease/istore or github.com/linkease/istore-packages → the LinkEase team reviews and, if accepted, lists it; dependencies may be cached in istore-packages. The community (koolcenter.com) redirects all submission questions to github.com/linkease/istore/issues, corroborating that GitHub is the channel. Acceptance criteria aren’t public — recommend opening an issue to ask first.

Gotchas: the iStore store domains (istoreos.com, linkease.com) must be directly reachable (DNS / whitelist issues are the most-reported problem); Docker on iStoreOS needs adequate storage (the official “iStore Enhance” tool exists partly to fix image-pull speeds via mirrors); the primary targets are x86-64 and arm64.

Two platforms you can’t get onto

Huawei Home Storage: no app distribution mechanism for third-party developers. Only a small set of official partner plugins (Baidu Netdisk / Xunlei / Wanwu) installable via the AI Life mobile app. No open platform, no SDK, no store. Docker has never shipped (promised “later” since the 2022 presale, still undelivered as of mid-2026), and SSH isn’t provided — the single biggest community complaint. If your goal is to run a self-developed app here, there’s currently no path.

Lenovo Personal Cloud: essentially a closed device. No real app store or native packaging format, no public developer portal. Docker is preinstalled on some newer firmware but still beta / unofficial; SSH isn’t officially exposed — users enable it via the client’s “remote assistance” feature, or flash community-modded firmware to get root (TTL, then root login on port 22, disks mounted under /sata). This is a hobbyist channel only, not a publishing platform.

A few directly reusable scenario mappings:

  • “I just have a Docker image and want to cover everything fastest”: a multi-arch OCI image (amd64 + arm64) pushed to Docker Hub and Aliyun registry.cn, plus a generic docker-compose.yml. Covers fnOS, ZSpace, UGREEN, TerraMaster, TrueNAS, Unraid, QNAP (Container Station), and OMV. Ship this set first; stores come after.
  • “I want store discoverability on Chinese NASes”: UGREEN first (the only public portal), then fnOS’s .fpk community store (conversun/fnos-apps), then ZSpace via a business agreement for authorization.
  • “I want store discoverability on international NASes”: Synology via SynoCommunity (not the official Package Center), QNAP via Container Station Docker, Unraid via a CA template (lightest), TrueNAS via Custom App (no discoverability — accept it).
  • “A lightweight native router app”: build a luci-app-foo ipk/apk for OpenWrt and self-host a signed feed; aim for the official feed via PR if you want it baked into ASU images; for China-specific apps, consider ImmortalWrt.
  • “A heavy app that needs to run on a router”: don’t build a native package — ship a Docker image and land it via luci-app-dockerman / iStore’s Docker tab.
  • Huawei / Lenovo: abandon official distribution; don’t invest.

A few common misconceptions

“NAS app stores work like phone app stores — register and you’re in.” They don’t. Synology and QNAP are review-gated and require signing an agreement; ZSpace is authorization-by-agreement; TrueNAS has no store in the traditional sense at all. Only UGREEN (China) and Unraid’s CA (international) come close to a lightweight “register and ship” flow.

“Publishing a Docker image means you’re listed.” Depends on the platform. Unraid’s and UGREEN’s Docker wrappers carry a store listing; TrueNAS’s Custom App is “runs but isn’t listed”; fnOS needs an extra .fpk wrap to enter the community store. Image-runnable ≠ store-discoverable.

“Just follow the old TrueNAS tutorial and add a custom train.” Invalid since October 2024. 24.10 cut k3s and “Add Catalog,” and TrueCharts has exited. In 2026 TrueNAS has only the official catalog (PR-based) and direct Custom App / Compose pasting.

“OpenWrt is still opkg + .ipk.” As of 25.12 the default is apk + .apk. Snapshot branches migrated in late 2024. New packaging scripts should produce both ipk and apk, or target a specific version only.

“iStoreOS is a pure Docker store.” It isn’t. iStore is a unified storefront over both ipk plugins (lightweight luci-app-*) and Docker containers (heavy apps); the two coexist.

“Signing is the hard gate on every platform.” Only Synology and QNAP have a clear official signing flow you must go through. The rest (especially the Chinese NASes) have undisclosed signing requirements, and the gate is review, not cryptographic signing. Don’t read “undisclosed” as “mandatory signing.”
