Needle 2 Explained: A 14MB On-Device Tool-Calling Model

September 4, 2026 September 6, 2026 AI Tools Needle, On-Device AI, Function Calling, Edge Computing, Small Models AI Engineering Series 2716 words 13 min read
🔊

In August 2026, YC-backed Cactus Compute released Needle 2: 45M parameters, quantized to CQ2 the whole model ships as a single 14MB binary, a full session peaks at about 28MB of RAM, Apache-2.0 licensed, with a paper on arXiv (2607.18363). The official tagline is “foundation model for tiny devices,” but it is not a multi-billion-parameter language foundation model — it does exactly one thing: take a user instruction plus tool schemas, and emit a JSON function call.

This post walks through its architecture and engineering trade-offs, goes through hands-on cases on four integration paths (Python, CLI, C API, WASI), then places it among on-device models to answer: who is actually in the same lane, where the gaps are, and when to pick which.

Why call a 45M model “foundation”

The original Needle was a 26M-parameter encoder-decoder (12 encoder layers + 8 decoder layers, no FFN anywhere), distilled from Gemini 3.1 tool-calling data: 200B tokens of pretraining took 27 TPU-hours, followed by post-training on 2B tokens of single-shot function-call data — 45 minutes. Needle 2 moves to a more radical minimal architecture (more below); the task definition stays the same.

The “foundation” claim holds for one reason: it is not trained against any specific app. The tool list is a runtime input variable — feed it your devices’ schemas and it can call those devices; swap the schemas, weights unchanged. Foundation here means “a general substrate for device control,” not “a general chatbot.”

The single-task trade-offs

Needle 2’s behavior design is deliberately rigid:

  • Every input resolves to a function call. Off-topic input returns an empty array []; there is no free-text fallback. When it does need to talk to the user, it goes through a built-in type: respond pseudo-call with function_calls left empty.
  • Optional fields are omitted, not guessed, when there is no evidence. For device control, guessing a room name is far more dangerous than refusing to act.
  • Environment state arrives as system facts. Date, timezone, battery, network, and location are injected at session start as facts, and relative times like “tomorrow” or “tonight” are only resolvable when a date fact is present — closing the hallucination gate at the source.
  • One toolset per session. Later turns are bare queries against the same tools; reset() rolls back the conversation but keeps the tools.

This design maps to instruction-to-action pipelines: voice assistants, smart home, robots. Conversation is a by-product. Structured extraction uses the same exchange format: declare the record schema as the only tool, and grammar guarantees the output is well-formed — there is no separate “JSON mode.”

Three stages are worth unpacking: with many tools, a built-in contrastive head embeds schemas for retrieval and only the top-5 enter the context each turn; during generation, tool schemas are compiled into a byte-level grammar constraining every decoded token, so malformed JSON is impossible; confidence comes from a separate calibrated head (the minimum of a post-hoc head score and the decode probability), and below the threshold the call is not executed — it escalates. That last part is what makes running on an offline device acceptable.

One detail is very debugging-friendly: the returned reasoning field carries the model’s short derivation for each argument ('ten minutes' -> minutes 10). It bypasses the grammar — only the call itself is locked down, so the derivation stays natural and readable. When you need to check how the model interpreted a sentence, that field is the first place to look.

How 14MB happens

Fewer parameters is only step one: 45M at bf16 is still 90MB. The footprint comes from architecture plus quantization. The architecture is called SAN (Simple Attention Network), with a few key pieces:

  • No FFN. The FFN holds most of a Transformer’s parameters; SAN replaces it with a Hadamard multiplicative layer — per-channel scaling, an order of magnitude fewer parameters.
  • Walsh-Hadamard transform for token mixing. A fixed matrix, n log n complexity, zero parameters.
  • Engram memory. Hashed n-gram tables act as part of the KV memory; recurring patterns cost no network weights.
  • Hyper-connections. Multi-lane residuals replace the single residual stream, with four residual lanes in parallel.
  • Sinkhorn normalization. Routing logits pass through doubly-stochastic normalization for training stability.

On the quantization side, Cactus’ own CQ2 (a bit over 2 bits per parameter — 45M × 2.5 bits ≈ 14MB) bakes the weights and the inference engine into one binary — no PyTorch, no llama.cpp dependency — running on ARM64, x86-64, ARMv7, RISC-V, WebAssembly, and even MIPS32el (Ingenic camera and router SoCs).

Bounded memory is another engineering point: a 256-token sliding window with tool schemas pinned as KV sinks, so RAM stays flat no matter how long the session runs — about 28MB at peak. That fits the budget of an ESP32-P4 (an MCU with PSRAM); community reports even got it running inside 11MB on an ESP32-S3.

Official speed numbers: roughly 500 tok/s decode on a Raspberry Pi 5, 400–1,500 tok/s on a Meta Quest 3S or Apple Vision Pro, 300–700 tok/s on sub-$200 Android phones. CPU only, no NPU required.

Integration: from decorators to raw schemas

Install the Python package first:

sh
1

pip install cactus-needle

Needle decides what to call and how to fill arguments by reading tool descriptions, so the description is everything. There are three levels of description granularity, from quickest to most controlled.

Quickest: decorate a function. Type hints become the parameter schema, the docstring becomes the tool description, and run() completes the whole loop — model picks the call, your code executes it, the result feeds back, and a final answer comes out:

python

import needle

@needle.tool
def get_weather(city: str):
    "Get the current weather for a city."
    return {"city": city, "temp_c": 27, "sky": "clear"}

agent = needle.Needle(tools=[get_weather])
print(agent.run("what's it like in Lagos right now?")["reasoning"])

Grammar-level constraints: needle.Field with Annotated attaches constraints inline, and ranges, regexes, lengths, and item counts all compile into the decode grammar. In this money-transfer tool the amount must be greater than 0 and at most 10,000, and the recipient must match a handle regex — the model is not “asked” to comply, it is physically unable not to:

from typing import Annotated

@needle.tool
def send_money(
    amount: Annotated[float, needle.Field(gt=0, le=10000, description="USD, up to 10,000")],
    to:     Annotated[str,   needle.Field(pattern=r"^@[a-z0-9_]+$", description="recipient handle")],
    memo:   Annotated[str,   needle.Field(max_length=80)] = "",
):
    "Send money to a handle."
    return {"sent": amount, "to": to}

Field covers most common validation needs: description, enum, const, ge/le/gt/lt, multiple_of, min_length/max_length, pattern, format, min_items/max_items, unique_items.

confidence is the minimum of two signals: the calibrated head’s score for “full input plus the just-generated call,” and the decode probability of the call tokens themselves. Both must agree before execution, so the failure mode is “refuse and escalate,” not “execute wrongly.”

Extraction is the same exchange format in another role: declare a record schema as the only tool. extract() takes a Pydantic model and returns a typed object. With a single declared tool the grammar admits only that call — equivalent to forced tool_choice; schema conformance is guaranteed, not requested:

Manual loop: when you do not want run() to manage everything, complete() returns the bare call — you execute it and feed the result back. In multi-step chains, later arguments can depend on earlier results: call search_for_contact first, take the contact_id, then call send_instant_message; a final type: respond turn produces a plain-text summary:

python
1
2
3
4
5

import json
response = agent.complete("dim the living room to 30")
if response["type"] == "call":
    result = set_lights(**response["function_calls"][0]["arguments"])
    response = agent.complete(json.dumps(result))   # feed the result back

The decorator only assembles a JSON schema — needle.Needle(tools=...) accepts raw schema arrays directly, the same shape as the CLI’s tools.json. Migrating from an OpenAI toolchain works too: {"type": "function", "function": {...}} wrappers are accepted and normalized by the engine.

Two ways to drive the CLI — one-shot queries, or a local HTTP server for other processes on the same machine:

# One-shot query
./needle --tools tools.json --prompt "dim the living room to 30"

# Local HTTP server (POST /complete {"input": "..."})
./needle --tools tools.json --serve

# Large tool catalogs: cache tool vectors on disk
./needle --tools tools.json --tool-index tools.idx --serve

Retrieval engages automatically beyond 5 tools: each schema is encoded once by the built-in contrastive head at init, and each turn admits only the top-5 scoring tools into the context, with the grammar rebuilt over that subset. An unselected tool is not “unlikely” — it is unreachable, which beats soft prompting by a wide margin. tools.idx caches vectors keyed by schema fingerprint: unchanged schemas load instantly, and only changed ones recompute.

System facts are an optional turn declaring the environment:

text
1

date: 2026-07-21 Tue 14:30; locale: en-US; device: phone; battery: 62%

Supported keys include date, locale, device, battery, network, location, user, and assistant. “Tomorrow at 7am” resolves to an absolute time only when a date: fact exists; otherwise it passes through verbatim. Instructional text placed here does not steer the model — it is a fact channel, not a prompt-injection point.

Embedded targets use the C API: include needle.h, link the platform’s libneedle.a, and drive four lifecycle functions — needle_load / needle_init / needle_complete / needle_reset:

c
1
2
3
4
5

int rc = needle_load(model_bytes, model_size);
if (rc < 0) return 1;
rc = needle_init(system_prompt, tools_json, nullptr);
if (rc < 0) return 1;
rc = needle_complete(query, 256, output, sizeof(output));
if (rc < 0) return 1;

One gotcha: the return-value semantics are not uniform. needle_load returns a negative value on failure, but needle_init and needle_complete return positive values on success (cached-prefix token count / generated token count). Always test >= 0 — do not treat nonzero as an error. Also note the API owns a process-global conversation: one worker process loads one model artifact and owns one engine and KV cache. To serve concurrent sessions or multiple fine-tuned versions, spawn multiple workers.

The WASI route packages the engine as a WASI Preview 2 component (exporting cactus:needle/engine@2.0.0); the WIT contract exposes the same load / init / complete / reset functions, with model bytes passed in at runtime — the same component loads the base model or a fine-tune without recompiling the engine, and each component instance owns its session with no hidden host state. Browsers and Node use needle.js + needle.wasm. The point of the web route: the whole text-in-JSON-out capability runs inside the browser, and desktop apps can embed it the same way.

Fine-tuning is fully open: train end to end on your own tools and domain data, export .cact, and distribute it like the base model. The official playground turns “generate data → train → export” into a button-driven flow; the original Needle’s rule of thumb was at least 120 examples per tool. In effect it swaps “prompt engineering for your devices” for “lightweight training for your devices” — the work does not disappear, it changes shape.

Comparing against its actual peers

First, sort out positioning. Two groups share the stage with Needle 2 on-device.

Dedicated function-calling models — same task; the contest is call accuracy and minimum hardware:

ModelVendorParamsNotes
Needle 2Cactus Compute45MText→JSON, 14MB at CQ2, Apache-2.0
FunctionGemmaGoogle270MGemma 3 270M fine-tuned for function calling, released December 2025 with a training recipe
Octopus v2Nexa AI2BReleased 2024, focused on on-device function calling on Android

General-purpose small LLMs — tool calling included, with the extra parameters buying conversation and general semantics:

ModelVendorParamsNotes
LFM2.5-230MLiquid AI230MHybrid convolution + attention, officially recommended for extraction and lightweight agentic pipelines
Gemma 3 270MGoogle270MPositioned as a fine-tuning base; FunctionGemma’s foundation
Qwen3-0.6BAlibaba0.6BThe most capable generalist in this class; tool calling is one skill among many
Apple on-device FMAppleUndisclosed (widely estimated ~3B)Apple Intelligence local foundation model, closed source

Cactus’ own benchmark conclusion: Needle 2 trades wins with FunctionGemma 270M, LFM2.5-230M, and the Apple on-device model, while being 5–70x smaller and quantized to 2 bits against their f16. That is a restrained claim — but two caveats: the benchmarks are self-reported, and tool sets and schema complexity differ across papers, so cross-paper numbers are not directly comparable anyway.

The real divide is the hardware floor. Every other model in the tables needs a phone-class device with hundreds of MB of memory; Needle 2 targets MCUs with tens of MB. The several-times-larger parameter count of a 270M model buys schema-understanding generalization and conversational fallback. Needle 2 cuts all of that and gets back three things: MCU-class deployment, grammatically guaranteed JSON, and memory that does not grow with the session.

The two lines are not “which is stronger” — they divide the work: when you must talk to users and handle open input, go general; when inputs and outputs are both structured device control, the specialist is far more cost-effective.

When to pick it, when not

Good fits:

  • Instruction routing for voice assistants, smart home, robots: one utterance maps to one device function call
  • Intent detection and structured extraction inside an app: declare a record schema, output is grammatically valid
  • Privacy-sensitive pipelines that must run fully offline
  • Hardware budgets at the MCU / wearable tier, where a 1B model does not fit
  • In-browser embedding: the WASM build runs the whole text-in-JSON-out capability in the browser; desktop apps can do the same

Poor fits:

  • Open-ended conversation: it has none; type: respond is a fallback, not a chatbot
  • Long context: the 256-token window is a hard ceiling — do not expect it to read documents
  • Multi-step agent orchestration: a 45M model lacks the semantic robustness for complex planning; general small models hold up better

To close: Needle 2 did not invent a new task. It turned “on-device function calling” from a side skill of general LLMs into a dedicated model, and pushed the hardware floor from phones down to MCUs through architecture plus quantization. Self-reported benchmarks, a single-vendor ecosystem, and a brand-new paper are all risks worth watching. But “single 14MB binary, 28MB RAM, grammatically valid JSON” are concrete numbers — concrete enough to try on an ESP32-P4 before deciding whether to wire it into your device pipeline.
