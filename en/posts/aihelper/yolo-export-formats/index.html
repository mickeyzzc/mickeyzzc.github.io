YOLO Model Export Explained: 22 Formats, Parameters, and How to Choose

September 3, 2026 September 6, 2026 AI Tools YOLO, Model Deployment, ONNX, TensorRT, OpenVINO, Edge AI AI Engineering Series 2168 words 11 min read
🔊

When I wrote “YOLO Deployment” in May 2026, the official Ultralytics export table had 17 rows. By September, when this post came together, it had grown to 22 — every new row is an NPU vendor pipeline: ExecuTorch, Axelera, DEEPX, Hailo, Huawei Ascend, Apple Core AI, and the like. The direction of growth is clear: training frameworks and inference hardware are drifting apart. PyTorch handles training, each deployment target runs its own runtime, and export is the only bridge between the two.

The good news: the API hasn’t changed. It’s still one line:

python
1
2
3
4

from ultralytics import YOLO

model = YOLO("yolo26n.pt")
model.export(format="onnx")

Many formats, one usage pattern: change the format argument. The real work lives in two tables — which format to pick, and which arguments to pass. This post lays out both, then adds a selection cheat sheet.

The Full 22-Format Table

Strictly speaking it’s 1 source format plus 21 export targets: the PyTorch row is the model itself, and the parentheses in the other 21 rows hold the value format accepts. The artifact column is what lands on disk after export — single file or directory; why that distinction matters comes later.

Format (format)ArtifactPrimary target

Three details in this table deserve their own mention:

  • Metadata. Everything except pb ships with Ultralytics metadata (class names, input size, task type). So after YOLO("yolo26n.onnx") loads the artifact, predict and val work directly — preprocessing and postprocessing configuration travel with the model instead of living in your code.
  • Aliases and rerouting. tensorrt/trt normalize to engine; since 8.4.83, tflite and tfjs are deprecated — passing them prints a warning and actually exports LiteRT, because Google folded TFLite and TF.js into LiteRT. The format="tflite" calls in this series’ older posts still run, but the artifact comes from the LiteRT pipeline.
  • Directory artifacts. OpenVINO, SavedModel, RKNN and friends export a directory, not a single file, following the same yolo26n_<format>_model/ pattern (say yolo26n_rknn_model/). Copy the whole directory when deploying; missing an XML or weight file only surfaces as a load error on the device, which is miserable to debug in the field.

Each family has a distinct job. ONNX and TorchScript are interchange formats — not necessarily the fastest by themselves, but accepted by nearly every toolchain. Server engine formats (TensorRT, OpenVINO) are fastest on their own vendor’s hardware and don’t travel well. The edge and NPU family is the biggest simply because every chip vendor ships its own toolchain, and Ultralytics wires up one export per vendor.

Export Arguments: Fewer Switches Than You’d Think

The official argument table runs about twenty rows, but the ones you actually touch day to day are these:

ArgumentDefaultWhat it does
formattorchscriptTarget format, 1 of 21
imgsz640Input size; when omitted, the size recorded in the checkpoint is used
quantizeunset (FP32)16=FP16, 8=INT8; successor to half/int8
dynamicFalseVariable input sizes; only TorchScript / ONNX / OpenVINO / TensorRT / CoreML / MNN
simplifyTrueonnxslim graph simplification, applies to every ONNX-based export
opsetlatestONNX opset version; lower it when a runtime can’t parse
nmsFalseBakes NMS into the model; conf/iou/max_det take effect with it
end2endunsetYOLO26/YOLOv10 only; False falls back to the classic NMS pipeline
batch1Static batch ceiling; Edge TPU is always 1
deviceautocpu / 0 / mps / npu / dla:0; TensorRT requires GPU
dataauto-pickedINT8 calibration dataset YAML
workspaceautoTensorRT builder workspace cap (GiB)
nameper formatNPU chip model: RKNN defaults to rk3588, Hailo to hailo8l, Ascend to Ascend310B4

Three of these deserve expansion:

quantize takes over from half/int8. The half=True and int8=True flags in older posts (including this series) emit deprecation warnings and map to quantize=16 and quantize=8; the old flags still work. INT8 is post-training quantization (PTQ) and needs a few hundred representative images for calibration — point data at a dataset YAML and size it with fraction. When you don’t specify one, Ultralytics picks a task-appropriate calibration set, but calibrating on your own business data is the only way to trust the accuracy.

nms and end2end. nms=True bakes post-processing into the model, so the artifact outputs final boxes and the deployment side skips its own NMS code; the conf and iou thresholds get fixed at export time. YOLO26 and YOLOv10 are already end-to-end NMS-free architectures — their output is final detections. Conversely, end2end=False drops back to the classic NMS pipeline, useful when an older inference environment can’t digest the new output format.

dynamic and batch together. dynamic=True allows variable input sizes, but a dynamic batch needs an explicit maximum (say batch=16) — leave it out and the export fails, at least in my testing. For fixed-size camera pipelines, don’t enable dynamic at all: static shapes get much better engine optimization.

The Export Pipeline, and Where It Stops

Whatever format you pick, the first half of the pipeline is identical: gradients off, conv+BN fusion, one forward pass on a dummy input to capture the graph, detection head rewired for the target format. The paths split after that:

    A --> C["Via ONNX<br/>TRT RKNN<br/>Hailo Ascend"]
    A --> D["Via TF<br/>SavedModel<br/>LiteRT"]

    classDef path fill:#2196F3,color:#fff
    class A src
    class B,C,D path

Three families. Direct conversion: TorchScript, CoreML, ExecuTorch, PaddlePaddle, IMX500, and OpenVINO — recent versions convert straight from torch.fx, bypassing ONNX. The ONNX family is the biggest: TensorRT, MNN, TF SavedModel, RKNN, Ascend, DEEPX, QNN, and Hailo — eight toolchains that first render the graph as ONNX and then hand it to their own compilers; that is exactly the step opset and simplify control. The TF family serves LiteRT and Edge TPU through the ONNX → SavedModel → tflite chain. Quantization happens during conversion: FP16 is a weight-precision conversion; INT8 is post-training quantization that runs a few hundred forwards over data to collect activation ranges. After conversion, the artifact is loaded and run once to verify, and class names, imgsz, and task are written into the metadata.

Twenty-one targets look universal; every cell has preconditions. On the model side, the whole API serves the Ultralytics family only; CoreML’s built-in NMS is detection-only; IMX500 accepts just v8n/11n; for an arbitrary PyTorch model, only ONNX and TorchScript are truly universal. On the machine side, TensorRT needs an NVIDIA GPU with matching CUDA; rknn-toolkit2, the Hailo compiler, and CANN are Linux-only toolchains; the Edge TPU compiler fails outright on non-x86 Linux — in practice, NPU formats get exported on a dedicated Linux build box.

The most fundamental limit is operator coverage: export is operator-level translation, and one unsupported operator fails the whole thing. YOLO reaches this width because its graph is nothing but Conv/Concat/Upsample and Ultralytics maintains every vendor pipeline; bring a model with heavy attention or dynamic shapes and the same table shrinks fast — Swin and RT-DETR’s ONNX exports are notoriously painful.

The three formats left off the matrix have the narrowest feature sets: pb supports none of quantization, dynamic sizes, or NMS, and drops metadata; PaddlePaddle and ExecuTorch exports accept only imgsz/batch/device — usable, but with nothing to tune. The NMS column means NMS baked in at export time; Meta is the Ultralytics metadata block described above.

Footnotes to the matrix: INT8 is PTQ everywhere and always needs data for calibration; CoreML’s built-in NMS applies to detection tasks only; IMX500 forces NMS on for detect/pose/segment, no flag needed; TensorRT FP16 requires exporting on a GPU device.

Performance: Orders of Magnitude, Not Promises

Same-machine comparison, drawn from Ultralytics’ official benchmarks and the runtimes’ own published numbers:

Comparison (same machine)Typical magnitudeNotes
TensorRT FP16 vs PyTorch FP322–5×engine is bound to GPU architecture and TRT version
OpenVINO vs PyTorch (CPU)1.5–4×INT8 adds another step
ONNX Runtime vs PyTorch (CPU)1.2–2×gains come mostly from graph optimization
NCNN vs TFLite (ARM phones)1.5–3×ncnn’s long-standing benchmark claim
INT8 vs FP161.3–2×mAP loss must be validated with val

These are magnitudes, not promises. imgsz, batch, how you write post-processing, and the exact chip all move the number — on the same card, 640 and 1280 inputs can differ by a full 2× in speedup ratio. Ultralytics runs one inference pass automatically after export; before shipping, measure mAP with yolo val model=xxx.onnx data=.... Both numbers need to pass before the export counts as done.

Selection Cheat Sheet

Servers: follow the hardware — each vendor’s silicon runs best on its own engine.

    A["Server deploy"] --> B["NVIDIA GPU<br/>TensorRT"]
    A --> C["Intel CPU<br/>OpenVINO"]
    A --> D["TF Serving<br/>SavedModel"]
    classDef q fill:#FF9800,color:#fff
    classDef a fill:#4CAF50,color:#fff

TensorRT on NVIDIA cards is a no-brainer; OpenVINO on Intel platforms; SavedModel if TF Serving is already in the stack. AMD GPUs and Apple Silicon desktops have no dedicated engine format — ONNX Runtime or CoreML it is.

Edge and NPU: identify the chip first, the format second.

    A["Edge deploy"] --> B["iPhone/Mac<br/>CoreML"]
    A --> C["Android<br/>LiteRT NCNN"]
    A --> D["Dev-board NPU<br/>RKNN Hailo"]

    class B,C,D a

iPhone and Mac go through CoreML — the .mlpackage drags straight into Xcode. On Android, NCNN has long led on low-end ARM chips; MNN is the peer alternative. RK3588 takes rknn with the name argument set; the Raspberry Pi AI Kit is Hailo silicon, the Raspberry Pi AI Camera is Sony IMX500 (n-series models only); the NPU inside Snapdragon phones takes qnn.

ONNX is the intermediate stop for many export pipelines — the artifact paths give it away:

mermaid
flowchart TD
    A["yolo26n.pt"] --> B["ONNX"]
    B --> C["TensorRT"]
    B --> D["RKNN"]
    B --> E["QNN"]
    classDef hub fill:#2196F3,color:#fff
    classDef eng fill:#4CAF50,color:#fff

    class B hub
    class C,D,E eng

TensorRT, RKNN, QNN, and Hailo exports all pass through ONNX internally — the opset argument controls exactly that step. So when a vendor format fails to export, debug at the ONNX layer first; an old onnxruntime choking on a new opset is the most common failure.

ScenarioFirst choiceAlternative

x86 servers, Intel CPU/iGPUOpenVINOONNX Runtime

Compressed to one sentence: get the pipeline working on ONNX first, then migrate to the target hardware’s native format. ONNX alone usually captures most of the available speedup; what a vendor engine adds has to be paid for in portability and toolchain coupling — run yolo val and decide with numbers.
