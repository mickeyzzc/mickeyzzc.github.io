Alerting Tools Technical Research: Core Implementations and the Case for Building Your Own (2026)

October 28, 2026 October 28, 2026 Observability Alerting, On-Call, Notification Push, Technical Research Observability Series 2853 words 14 min read
🔊

I am planning to build an alerting / notification tool, and before writing any code I went through the technical implementations of the existing players: what the core mechanisms are, which designs can be borrowed directly, and whether each layer still has room for a newcomer. This is the research result, not a buying guide — the assessment is in the last section. All mechanisms were verified against source code or official docs (2026-10); star counts come from the GitHub API at the same point in time.

Framework: putting them into four layers first

  • L1 notification delivery: only responsible for getting a message onto a phone.
  • L2 alert routing / aggregation / noise reduction: receives upstream events, deduplicates, classifies, silences, and forwards by rule.
  • L3 incident management / on-call: scheduling, escalation policies, incident timelines, retrospectives, phone calls.
  • L4 integrated platforms: metrics + logs + traces + alerting bundled into one product.

Collection (Prometheus, Zabbix and the like) counts as L0 and is not covered here. The path of one alert from birth to acknowledgement:

ntfy — the minimal model most worth copying

Mechanism: the server is an extremely lean topic-based message broker. The topic is the URL path, publishing needs no registration, and an HTTP PUT / POST with X-Title / X-Priority / X-Tags headers is the complete write protocol. Subscribers pick a form by scenario: a long-lived HTTP JSON / SSE stream, a WebSocket, or a one-shot pull with poll=1 + since= — since= accepts a timestamp, a duration, or a message ID, and messages missed while offline are replayed from the server’s SQLite cache (per-topic replay is capped at 10 MB; beyond that it truncates and returns an X-Messages-Truncated header). The message body is a fixed JSON schema (id / time / event / priority / tags / actions / attachment); on Android the FCM bridge wakes the app, which then connects to the stream. Attachments are uploaded separately and stored on disk — messages carry only the URL and metadata.

Self-build perspective: standing up a rough server prototype in Go is a small job, which shows the code in L1 is not the barrier. The real barrier is the channels: Android keep-alive needs FCM (overseas) or a vendor push channel (China, requires enterprise credentials), iOS needs an APNs .p8 credential, and WeChat reach requires a service-account qualification. What lets Bark and ServerChan hold their ground is channels, not code.

Gotify / Apprise — two interface designs worth borrowing directly

  • Gotify: applications send with an app token, clients receive with a client token; REST in, WebSocket out. Messages are written to the server database, clients subscribe over WebSocket for real-time delivery and catch up from the database after reconnecting — this “storage decoupled from delivery” pattern is worth copying as-is rather than inventing your own. The app / client dual token is a clean permission model: applications can only write, clients can only read.
  • Apprise: the most borrowable aspect is its extension pattern — every notification channel is a URL scheme parser (bark://host/key, discord://id/token), configuration is a string, and adding a channel never touches the caller. The core library is a stateless converter in pure Python: it takes a unified Notify object and routes it to the matching scheme’s plugin, which serializes it into that channel’s API call. If you want a “universal notification outlet,” write a plugin registry following this pattern.

Routing and noise reduction: the densest layer in algorithms

Alertmanager — four core designs that made the de facto standard

  • Deduplication and routing: every alert is reduced to a fingerprint computed from its label set as its unique identity, and alerts sharing a fingerprint collapse into a single stream; routes are trees of nested matchers, an alert walks down to the deepest matching node, child routes inherit parent configuration, and the continue flag decides whether matching stops or keeps descending — routing rules for new services and new teams extend naturally.
  • Grouping: group_by names a label set as the aggregation key; alerts in one group merge into a single notification after group_wait; group_interval controls the pace of follow-ups for newly added alerts in the group; repeat_interval controls the resend period for unresolved alerts. The combination of these three timing parameters covers essentially all of the “don’t flood me” requirements. There is also a per-alertname limit switch that cuts quantity before availability during same-name alert floods.
  • Silences and inhibition: a silence is a manual mute of “matchers + a time window”; inhibition is a rule of the form “when A fires, suppress B” (source_matchers match + target_matchers match + equal label equality), and it is what keeps a datacenter-level failure from drowning you in instance-level alerts.
  • High availability: Prometheus pushes to every replica instead of load balancing; replicas sync the silence table and delivery state via a gossip protocol (memberlist), and the same notification is sent by exactly one replica.

Self-build perspective: routing trees plus grouping windows are already the de facto standard, so rewriting them buys no differentiation. Alertmanager is an Apache-2.0 Go single binary with a silence management API — a self-built tool should either consume it directly or copy this semantic set in full; nobody uses a half-baked version.

Healthchecks — a state machine you can copy verbatim

Mechanism: every check is a Period (expected heartbeat interval) plus a Grace Time (lateness allowance), or a cron expression defines the expected cadence (evaluated internally with cronsim, which adds timezone and sub-minute semantics on top of crontab); HTTP / email pings flip up / down / late states, a flip is an event, and events trigger notifications. It has a built-in smtpd for email heartbeats and ships with Apprise as the notification outlet; every check exposes its own ping URL — a script, cron job, or K8s Job pings the URL once and that counts as a heartbeat — and a /metrics endpoint scraped by Prometheus lets you watch the health of the checks themselves.

Self-build perspective: the dead-man switch is the easiest chunk of a complete alerting product. Copy the Period + Grace model and the state-flip logic directly; do not invent your own.

Monitoring and alerting platforms: already full

Uptime Kuma — the template for a single-process everything

Mechanism: a Node.js single process; probe scheduling runs as in-process periodic tasks (minimum 20-second interval) across a dozen probe types — HTTP(s) / TCP / keyword / JSON query / WebSocket / Ping / DNS / Push / Docker containers; results are pushed to the frontend via Socket.IO, storage is a single SQLite file, and all 90+ notification channels are implemented in-process. No message queue, no microservice split — it proves a product of this size needs only a single process.

Self-build perspective: 93k stars, free, one Docker to run — there is no room in this layer. The single-process architecture itself is worth borrowing for small and mid-sized products.

Nightingale n9e — “not taking over storage” is the architecture decision most worth copying

Mechanism: Prometheus / VictoriaMetrics / Elasticsearch / ClickHouse / Loki are registered as data sources; alert rules live centrally in n9e, and a built-in engine evaluates them uniformly across heterogeneous sources (rule expressions can be PromQL, log queries, or SQL) — storage and collection are entirely reused from the existing ecosystem, and n9e only owns the alerting plane. Events flow through a processing pipeline: label rewriting and enrichment, subscription, silencing, conditional routing — with execution records kept throughout (evaluation queries, events, and notification results are all inspectable); rules are distributed across evaluation engines, and n9e-edge pushes evaluation close to remote data sources. The v9 AI assistant and MCP Server sit on top of this alert event stream.

Self-build perspective: this is the positive reference for building an alerting layer in China, and it also means there is no room for “yet another open-source alerting layer.” What is worth copying is the architecture decision: do not build your own storage — turn existing TSDBs and log stores into data sources; and make event processing an explicit pipeline instead of ifs scattered through code.

On-call and incident management: the heaviest layer technically

PagerDuty — dissecting the scheduling engine

  • Event side: Events API v2 — external monitoring POSTs an event (event_action is trigger / ack / resolve, carrying a dedup_key), and events sharing a dedup_key fold into the lifecycle of one incident.
  • Scheduling side: an on-call schedule is multiple rotation layers (each with rotation length, start offset, and time-window restrictions) stacked by priority, with overrides inserted temporarily; an escalation policy is a chain of “notification target + escalation_delay” that automatically drops to the next level when unclaimed until someone acknowledges. Phone calls are placed through a PSTN gateway.

Self-build perspective: the scheduling engine is the largest engineering effort and the entire barrier of this layer. The algorithms themselves are mature and publicly documented, so implementing them to spec is not hard — the difficulty is all in the edge cases: cross-timezone rotations, holiday calendars, nested overrides, and night-shift swaps.

incident.io / Rootly — two product forms worth borrowing from

  • incident.io: the whole product hangs on Slack — a Slack App handles slash commands and button callbacks; incident channels are auto-created, the timeline scrolls inside the channel, and role claiming and status changes are all Slack-interaction driven; the event lifecycle from detection to closure happens in Slack, and the web console handles configuration and retrospectives. AI investigation and MCP are an add-on layer on the event stream (the website calls it the Nexus production intelligence model).
  • Rootly: API-first — every object (incident, schedule, escalation policy) has an API before it has a UI, schedules and policies ship with a Terraform Provider, and all state is codifiable — this is the prerequisite for customers daring to migrate off PagerDuty.

Self-build perspective: the most borrowable point of the collaboration layer is “all incident state is exportable.” With Opsgenie users being pushed off the platform, migration capability (importer + dual-run switchover) is itself a product feature, and it deserves to be the first-priority design goal of a self-built product.

Grafana OnCall — a cautionary tale

Mechanism: a Django / Celery backend with a Grafana plugin frontend; authentication depends on Grafana’s externalServiceAccounts feature flag; SMS and phone either require your own Twilio configuration or go through Grafana Cloud. The open-source version entered maintenance mode in March 2025 and was archived in March 2026.

Self-build perspective: the fate of an open-source edition hard-bound to its own platform is being archived. Either make the open-source edition genuinely independent, or state plainly that the path is cloud — do not do a middle ground.

Opportunity assessment: if I were to build it

Three verified market facts first: overseas on-call pricing is 19-20 USD / user / month (incident.io and Rootly website prices) — enterprises will pay for this layer; Opsgenie shuts down on 2027-04-05 and Atlassian officially requires migration beforehand; PagerDuty’s stock is down roughly seventy percent from its peak and it laid off 15% in August 2026 (Nasdaq quotes and earnings) — the leader has hit its growth ceiling.

  • Red ocean, skip it: L1 delivery (ntfy at 35k stars, Bark, ServerChan, PushDeer — free and mature), L0 monitoring (Uptime Kuma at 93k stars), L2 routing (Alertmanager as the de facto standard plus Apprise fan-out). The common traits: free, maintainable by one or two people, no room to charge.
  • Unrealistic, avoid: a global SaaS to compete with PagerDuty / incident.io. The scheduling engine can be implemented from public docs, but brand, ecosystem integrations, and funding are a decade of accumulation — latecomers have no place.
  • Three directions with cracks:
    1. China-native on-call. With Opsgenie exiting, incident.io / Rootly not supporting Chinese IM and phone channels, and Nightingale focused on alert rules rather than incident collaboration, a privatized product offering “WeCom / DingTalk / Feishu + phone escalation + scheduling engine + retrospectives” enters against the migration window.
    2. China channel plugins. Adding WeChat service-account and vendor push channel plugins to Apprise / Bark — a small wedge; first verify whether the channel qualifications are obtainable, then talk product.
    3. Opsgenie migration helper. One-shot business in the 2026-2027 window, either as a migration tool or a service.
  • Where AI fits: Nightingale, incident.io, and Rootly all place AI on top of the alert event stream, which shows AI is an add-on layer, not the product itself. For a self-built tool, MCP integration is a low-cost bonus, not a selling point.

One final reality check: most of these projects are maintained by one or two people, and those sustaining themselves either have a commercial company behind them (Nightingale for Flashcat) or live on sponsorship (Uptime Kuma). Think through the monetization path before starting, or you will likely end up with yet another archived repository.
