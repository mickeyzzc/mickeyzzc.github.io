Migrated but No Network? The Two-incusbr0 Layer-2 Trap

November 5, 2026 November 9, 2026 Virtualization & Ops Incus, Networking, OVN, Bridge Self-Hosting Ops Notes 888 words 5 min read
🔊

The cluster was up and incus move worked — then came the second big trap of clustering: an instance moves from node1 to node2, its IP changes, the network breaks, and “migration succeeded” turns into “migration incident”. This post explains why, and why I picked OVN out of the three fixes.

Where the trap is: same name ≠ same network

incus admin init creates a host-local managed bridge — incusbr0 — on every node. Both bridges share a name, but they are two unconnected layer-2 broadcast domains:

  • Instances on node1 get 10.10.11.x, on node2 10.10.12.x, each NATting out on its own;
  • A container on n1 and a container on n2 cannot ping each other even with routing configured (unless traffic detours through host routing and back — slow and fragile);
  • After migration the instance IP necessarily changes, and upstream config (DNS, reverse proxy, firewall rules) must follow.

Top half: the default state — each node’s incusbr0 (10.10.11.0/24 and 10.10.12.0/24) is a disconnected layer-2 island; instances cannot reach each other. Bottom half: the fix — instances attach to an OVN overlay (ovn-* components + OVS on each member, Geneve over UDP 6081) and enjoy cross-node layer-2 connectivity that follows migrations; the alternative is a br0 physical bridge on each node.

The trap multiplies with migration: migration already has a downtime window, and if the network is broken on arrival the availability loss doubles. “Migrate at will” only works once the network is solved.

Three fixes

Option A: physical NIC bridging (simplest for two nodes)

Bridge each node’s uplink NIC into br0; instances join the physical layer-2 and take management-network IPs from the upstream router:

bash
1
2
3
4

# first bridge the physical NIC into br0 with netplan/NetworkManager, then hand it to Incus:
incus network create br0 bridge bridge.external_interfaces=enp1s0 \
  ipv4.address=none ipv6.address=none
incus profile device set default eth0 parent=br0

Pros: cross-node connectivity for free, IPs survive migration, no extra components. Cons: instances sit directly on the management network; be careful to move the management IP onto br0 before unplugging the physical port — do not lock yourself out (have a monitor or out-of-band access ready).

Option B: split subnets + static routes (workable, tedious)

Keep the two incusbr0s, add static routes between the hosts, and disable rp_filter:

bash
1
2
3

ip route add 10.10.12.0/24 via 192.168.10.12 dev enp1s0   # on node1
ip route add 10.10.11.0/24 via 192.168.10.11 dev enp1s0   # on node2
sysctl -w net.ipv4.conf.all.rp_filter=0

It works, but IPs still change (different subnets), asymmetric routing is on you, and the config is fiddly. Not worth it in a small environment.

Option C: OVN distributed networking (my pick)

OVN is natively supported by Incus clusters: one logical switch spanning the nodes; instances attached to it enjoy layer-2 connectivity and the network identity follows migrations:

bash
1
2
3

# prerequisite: ovn-* components + Open vSwitch 3.3+ on each member (OVN 24.03+)
incus network create ovn0 --type=ovn
incus launch images:debian/13 web01 --network ovn0

The honest cost: OVN needs its central DB (on two nodes it lands on one of them, with no failover home — a single point); Incus 7.0.2 requires Open vSwitch 3.3 / OVN 24.03. For “trade a bit of complexity for zero network reconfiguration after migration”, it is the right call.

Verifying migration + network together

bash
1
2
3
4

# create the OVN network → launch an instance → migrate → confirm IP and reachability
incus launch images:debian/13 web01 --network ovn0 --target incus-n1
incus move web01 --target incus-n2
incus list            # web01 RUNNING on n2, the ovn0-leased IP intact

Odds and ends worth recording

Service exposure: 7.0.2 added incus port-forward, tidier than the old proxy device:

bash
1
2
3

incus port-forward create incusbr0 8080 tcp 10.10.11.5 80
# the old way (still fine):
incus config device add c1 web proxy listen=tcp:0.0.0.0:8080 connect=tcp:127.0.0.1:80

Port list (for firewall rules):

PortProtocolPurpose
8443TCP/HTTPScluster API, member heartbeats, web UI — management net only, never the public internet
8444TCP/HTTPSoptional dedicated metrics endpoint — monitors only
6081UDPOVN Geneve tunnel — between nodes
67/68, 53UDPdnsmasq (inside managed bridges)

A dark corner when Docker shares the host: Docker sets the FORWARD chain default policy to DROP, and instances may suddenly lose the internet. Ensure net.ipv4.ip_forward=1, or allow incusbr0 → uplink in the firewall.

Summary

  • The default bridge is a per-host layer-2 island; settle the network design before relying on migration;
  • For “zero reconfiguration after migration”: OVN (this series’ choice) or a physical bridge;
  • OVN solves cross-node connectivity inside one cluster — the between-clusters problem returns in the 11-08 post.
