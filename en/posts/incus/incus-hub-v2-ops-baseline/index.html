Building incus-hub: A Console for Multiple Clusters

November 9, 2026 November 9, 2026 Virtualization & Ops Incus, Incus-Hub, Node.js, Backup, Operations Self-Hosting Ops Notes 1549 words 8 min read
🔊

Yesterday’s conclusion was an open-source gap, and of the three roads I picked self-building — evolving the existing incus-hub (a multi-host aggregation page) into a multi-cluster console rather than starting over. This post lays out the design and the order of implementation, and closes the series with the one thing a no-replication architecture owes: backups as the only safety net.

Why evolve incus-hub

Everything v1 has gets reused:

Existing foundationHow v2 uses it
Node with zero external dependencies (http/https/fs/path only)Runs directly on Debian 13’s stock Node 20.19.x; the systemd unit already exists
mTLS client certificates + per-host CABecomes “one certificate per cluster + per-cluster CA”
callNode() / waitOperation() REST helpersReused for handshake and operation polling
Promise.allSettled partial-failure isolationUpgraded to “a dead cluster greys out, the rest keep working”
Frontend aggregate table + search/filter + demo modeGains the cluster hierarchy and a migration wizard

Not adapting Orcastra or LXD Mosaic, as covered last post: the former has no public source and wants 4 VMs / 30 GB of control plane; the latter flattens clusters into hosts, is PHP, and last shipped in 2022. None satisfy “light, runnable on Debian 13, controllable”.

Target architecture and config model

The browser talks only to the Hub (listening on 127.0.0.1 by default; remote access over an SSH tunnel); inside, the Hub keeps a clusters[] registry where each cluster lists endpoints[] (several member addresses as redundant entries, tried in order); the Hub connects over mTLS to any online member and discovers the member list via GET /1.0/cluster/members — adding replicas later requires no Hub config change. An instance’s location field says which member it sits on, and the frontend renders a cluster → member → instance tree. The bottom strip is the P0–P3 order: establish the cluster abstraction first, then intra-cluster migration with the export/import fallback, then the cross-cluster handshake, with relay last.

One certificate detail changes from v1: in cluster mode the certificate is the cluster-wide cluster.crt, not each member’s self-signed server.crt — trust the Hub’s client certificate once on any member with incus config trust add-certificate and it applies cluster-wide.

Orchestrating both migrations

Intra-cluster: server-side, one request — POST /1.0/instances/<name>?target=<member> with migration: true in the body, then poll the operation. Containers stop first via PUT state {action:"stop"}.

Cross-cluster: yesterday’s two-step handshake; the Hub-side essentials:

  1. precheck first: target cluster reachable, target-side profiles/pools/networks referenced by the migration exist (failing midway with Profile not found is too late), resource headroom, container-stop notice, name collisions, IP-change notice;
  2. Source returns operation + secrets from migration: true; the Hub passes them to the target to create the instance;
  3. Idempotency: every migration job writes a state file (tempDir/job-<id>.json); on failure, delete target leftovers and start the source again in its original state; a failed “delete source” is never retried automatically — it gets flagged for manual handling. Because move = copy + delete, whether the source still exists after a failure is the orchestrator’s responsibility to the end;
  4. Audit: who, when, which instance, from which cluster/member to which cluster/member, parameters, result, duration. Migration credentials (secrets, operation URL) pass through memory only — never logged, never returned to the frontend.

Fallback when the subnets cannot talk: export/import relay — POST /1.0/instances/<n>/backups exports a tarball into the Hub’s tempDir, then uploads it to the target with an import. Always downtime, full copy, slowest — but the simplest and most reliable to implement, and the only dependable “one click” when firewall policy forbids opening 8443. Relay (the Hub splicing both ends’ websockets byte by byte) is the heaviest and goes last.

Security design

  • The Hub listens on 127.0.0.1 only; remote access via SSH tunnel / WireGuard; each node’s 8443 accepts only the Hub’s IP;
  • One Hub client certificate per cluster, revocable independently; skipTLSVerify stays false, always;
  • Access token openssl rand -hex 32; destructive cross-cluster migrations require a second confirmation;
  • Version prerequisite: yesterday’s GHSA-h2j8-4crh-vhfc (migration websocket secrets leaked to event listeners, affects < 7.6.0). A verification note as of publishing day (11-09): Debian’s incus 7.0.2-3 package (forky/sid) already carries the backported patch (110-GHSA-h2j8-4crh-vhfc.patch), and the Debian security tracker marks GHSA-v736-5xp3-jghf and a batch of other GHSAs fixed in forky/sid; whether the Zabbly lts-7.0 channel synced the backport still needs an apt-cache policy incus check before going live — or simply grant no third party can_view_events during migrations.

What it deliberately does not do

  • No HA, no automatic failover, no automatic load balancing — the cluster has none either, and the requirements say no;
  • No deep network/storage editing (OVN topology, DNS zones, certificate management) — that belongs to each cluster’s Incendio / official UI; the Hub only carries jump links. Through a REST proxy the cost-to-value is terrible;
  • No database, no frontend framework, no npm dependencies: job state lives in JSON files under tempDir; the frontend is plain HTML/CSS/JS;
  • No “real-time zero-downtime” cross-cluster promises: containers stop, VM live has prerequisites, cross-subnet IPs change — the UI says so, no varnish.

Milestones

PhaseDeliversAcceptance
P0 read-only multi-cluster aggregationclusters[] model, member auto-discovery, cluster-tree frontendUnplug cluster A; cluster B still renders fully
P1 intra-cluster migration + fallback/api/migrate (intra-cluster branch), precheck, export/import relay, job state + rollback, auditA1 → A2 one-click inside a cluster; cross-cluster still works with subnets isolated

P3 enhancements (optional)Relay, batch migration, evacuate panelDriven by actual usage

P0 goes first: it establishes the “cluster” abstraction everything else builds on. P1’s export/import fallback deliberately precedes P2 — it is the only reliable path when subnets cannot talk, and the lowest-risk to implement.

Closing: no replication means backups carry everything

The architecture this series chose is single-copy instances with no mutual replication — which makes backups mandatory, not optional:

The three-tier cadence: daily — global database incus admin sql global .dump plus incus export of key instances, pushed to a third place (NAS / object storage / another machine; never parked on these two boxes); weekly — a full cold backup (stop the service, tar /var/lib/incus plus subuid/subgid and configs), with zfs send for the pool on top; monthly — one incus import restore drill on a scratch machine, because a backup never proven recoverable is a placebo. Note in particular: on two nodes the database replica exists only on the bootstrap, so the leader’s database needs its own backup.

Two official reminders, recorded here: a snapshot is not a backup — snapshots and the data they protect share the same pool, and losing the pool loses both; and the incus admin sql dump is “an accurate reference for rebuilding configuration”, not a one-click restore.
