incus move: What One Command Actually Does

November 6, 2026 November 9, 2026 Virtualization & Ops Incus, Migration, Cluster Self-Hosting Ops Notes 811 words 4 min read
🔊

This is the heart of the series: “migrate by command” boils down to one line — incus move <instance> --target <member>. But the command’s semantics, boundaries, and common misunderstandings deserve their own post.

One command, four automated steps

bash
1

incus move web01 --target incus-n2

incusd orchestrates four steps after the command: stop, transfer the root disk via zfs send | zfs receive, start on the target node, clean up the source — no manual stop/copy/start needed. The two cards bottom-left mark the key boundary: local storage always means downtime migration (about 5–30 seconds for containers, 1 to several minutes for VMs); shared storage (Ceph) is what enables live migration. Bottom-right: the practical flags and the batch-maintenance entry points.

The most important boundary: downtime vs live migration

This is not a flag question, it is a storage architecture question:

Storage backendMigration typeExperience
Local disks on each node (my case)Downtime migrationContainers ~5–30 seconds (zfs send is fast); VMs copy the qcow2 and reboot, 1 to several minutes
Shared storage (Ceph etc.)Live migrationNearly zero interruption, iterative memory transfer
VM + migration.stateful=trueDepends on storageVM live migration has extra prerequisites; the official how-to says enable this or stop first

Two quotes from the official how-to worth memorizing:

“When moving a container, you must stop it first.” “When moving a virtual machine, you must either enable Live migration for virtual machines or stop it first.”

Container live migration rides on CRIU, and the official docs pour cold water on it too: only “very basic containers (non-systemd, without a network device)” migrate reliably — in practice, containers stop. Conclusion: treat a downtime window as the default expectation, and use --refresh to shrink repeat migrations.

Three semantics to keep straight

move means “move away”, not “copy”. After the move the instance exists only on the target member; it is gone from the source. To keep the original, use incus copy:

bash
1
2

incus move web01 --target incus-n2            # move away
incus copy web01 web01-bak --target incus-n2  # duplicate; the original stays

--target is a “cluster member selector”, not a cross-cluster switch. The official manpage defines --target as Cluster member name, and the how-to adds: “In this case, do not specify the source and target remote.” Cross-cluster migration uses the <remote>: prefix syntax (incus move cluster-a:web01 cluster-b:web01) — that is the next post’s world.

Intra-cluster migration is server-side. The client sends one request; data flows between the two servers directly — a completely different path from cross-remote moves, where the client is the intermediary.

Useful flags

bash
1
2
3

incus move web01 --target incus-n2 --refresh   # incremental: repeat migrations transfer only the delta
incus move web01 --target incus-n2 --stateless # do not transfer memory state (downtime migration does not need it)
incus move web01 --target incus-n2 --instance-only  # exclude snapshots

Batch: evacuate / restore

For node maintenance (kernel upgrades, hardware work), the official wrapper beats moving instances one by one:

bash
1
2
3

incus cluster evacuate incus-n1    # move every instance off n1 to online members
# ... kernel upgrade / hardware maintenance ...
incus cluster restore incus-n1     # move them back (or keep the new distribution)

incus cluster group adds group-based scheduling:

bash
1
2

incus cluster group create prod
incus cluster group assign incus-n1,incus-n2 prod

Easy-to-miss points

  • Clusters do not migrate automatically. incus move --target is “one command, the system completes the whole process”; but policy-driven migration (“load high → move”, “node down → drift”) does not exist in Incus — script it yourself with cron/monitoring.
  • No lightweight witness. Proxmox users think “just add a QDevice vote” — Incus has no equivalent; a third voter must be a full Incus member.
  • Check the IP after migrating. Default-bridge instances change IPs on arrival (last post); OVN-attached ones keep their network identity.

My working rhythm

bash
1
2
3
4
5
6

# 1) create the instance on OVN (network survives any migration)
incus launch images:debian/13 web01 --target incus-n1 --network ovn0
# 2) one-command migration
incus move web01 --target incus-n2
# 3) confirm
incus list      # LOCATION changed, state RUNNING, IP fine

Container migrations take 5–30 seconds in practice, faster with --refresh. That window is acceptable for internal services — the reason I skip Ceph.
