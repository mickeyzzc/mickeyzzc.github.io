Installing Incus 7.0 LTS on Debian 13: Five Real Pitfalls

October 31, 2026 November 9, 2026 Virtualization & Ops Incus, Debian, ZFS, Deployment Self-Hosting Ops Notes 1158 words 6 min read
🔊

The setup: two 16 GiB boxes on Debian 13 (trixie). The value of this post is not “how to install” (the official docs cover that) but which steps genuinely trip you up — every item below either did bite or will bite on a real deployment.

Version first: apt install incus gets you 6.0.4

The easiest first stumble for Debian users, so it goes first. There are three routes on Debian 13:

SourceVersionBundled Web UIFits
Debian 13 official repo6.0.4 LTS❌ no UI packageCLI only, no third-party repos
Debian 13 trixie-backports7.0.2 LTS❌ UI still separateDebian-native packaging preference
Zabbly lts-7.0 (this series)7.0.2 plus patches✅ ships incus-ui-canonicalWant 7.0 + official Web UI

A plain apt install incus installs 6.0.4 LTS from the official repo — not bad (EOL 2029-06), just not the 7.0.2 you probably want. The official repo does not ship the Web UI static files (packaging/licensing reasons); since getting the UI requires Zabbly’s .deb either way, starting on Zabbly lts-7.0 keeps the daemon and UI on one source at one version, so upgrades stay aligned.

With official + backports + Zabbly all enabled, apt picks among several 7.0.2s and the source may flip between upgrades. Pin Zabbly’s priority, or keep a single source.

After installing, verify the source, not just the version:

bash
1
2

incus version                      # 7.0.2, not 6.0.4
apt-cache policy incus | head -6   # Candidate should point at pkgs.zabbly.com

Why Debian 13: the kernel requirement is real

Incus 7.0 requires: kernel ≥ 6.12, cgroup v2, nftables (xtables dropped), LXC ≥ 6.0, QEMU ≥ 8.2, dnsmasq ≥ 2.90.

Debian 13 (trixie) ships the 6.12 LTS kernel — just above the line, and it is the first Debian stable that meets the 7.0 requirements out of the box. For comparison: Debian 12 has 6.1 (no), Ubuntu 24.04’s GA kernel is 6.8 (also no, unless you move to a new enough HWE kernel). So “just pick a new distro” does not hold at this version boundary; trixie is one of the few that qualifies as installed.

Run this on both machines before anything else; if the output does not match, stop:

bash
1
2
3
4

. /etc/os-release && echo "$PRETTY_NAME"    # Debian GNU/Linux 13 (trixie)
uname -r                                    # 6.12.x
stat -fc %T /sys/fs/cgroup                  # cgroup2fs
nft --version && dnsmasq --version | head -1

The five pitfalls plus one version trap: ① ZFS lives in the contrib component and is not found by default; ② the DKMS module is built against a kernel you are not running; ③ minimal installs lack apparmor so containers will not start; ④ missing dnsmasq-base means instances never get an IP; ⑤ ZFS ARC eats memory unless capped. The orange card bottom-right is the version trap — the 6.0.4 from the official repo. Details below.

Pitfall 1: ZFS package not found — contrib is off

text
1

E: Unable to locate package zfsutils-linux

OpenZFS lives in Debian’s contrib component, and trixie’s default deb822 sources enable only main non-free-firmware. It is not “add one repo” — every stanza needs the fix:

bash
1
2
3
4

sed -i -E '/^Components:/ { /contrib/! s/^Components: /Components: contrib / }' \
  /etc/apt/sources.list.d/debian.sources
grep '^Components:' /etc/apt/sources.list.d/debian.sources   # every stanza must carry contrib
apt update

Pitfall 2: DKMS module fails to load — kernel/headers mismatch

ZFS on Debian is a DKMS source package compiled against your running kernel. linux-headers-amd64 always tracks the newest kernel in the repo; if the running kernel is older, DKMS builds the module for a kernel you are not running and modprobe zfs fails.

bash
1
2
3
4

apt full-upgrade -y && reboot        # fresh machine: get current, then reboot
apt install -y zfs-dkms zfsutils-linux zfs-zed linux-headers-amd64
modprobe zfs
zfs version                          # both lines must match (userland and kmod)

The first DKMS build takes 3–10 minutes; do not interrupt it. On a box with existing workloads, skip the full-upgrade and install linux-headers-$(uname -r) instead, confirming versions match.

Pitfall 3: containers will not start — apparmor missing

Debian minimal installs ship without apparmor; container startup fails with AppArmor errors. This is a documented Debian Wiki known issue that Ubuntu users never think about:

bash
1
2

apt install -y apparmor && systemctl restart incus
aa-status | head -5     # confirm loaded

Pitfall 4: instances never get an IP — dnsmasq-base missing

The managed bridge’s DHCP/DNS is handled by dnsmasq. With --no-install-recommends this recommended dependency is the easiest to lose; the symptom is instances that boot and never get an address:

bash
1

apt install -y dnsmasq-base && systemctl restart incus

Pitfall 5: half your RAM gone — ZFS ARC uncapped

OpenZFS’s ARC (adaptive cache) may take more than half of physical RAM by default; on a 16G box that leaves instances half a machine. Cap it explicitly:

bash
1
2
3
4

# must come after modprobe zfs (otherwise /sys/module/zfs/... does not exist yet)
echo "options zfs zfs_arc_max=4294967296" > /etc/modprobe.d/zfs.conf   # 4 GiB
echo 4294967296 > /sys/module/zfs/parameters/zfs_arc_max
arc_summary | head -20

Acceptance checklist (all green before init)

bash
1
2
3
4
5

apt-cache policy zfsutils-linux | head -4    # contrib in effect
zfs version                                  # two matching lines
aa-status | head -1                          # apparmor enabled
dpkg -l dnsmasq-base apparmor | grep '^ii'
chronyc tracking | grep 'System time'        # time sync — the foundation of clustering

One note on time sync: installing chrony automatically takes over from systemd-timesyncd; do not run both. Cluster heartbeats, offline detection, and join-token expiry all depend on the clock; keep the two machines within 100ms.

At this point both machines have: Debian 13, kernel 6.12, working ZFS, apparmor and dnsmasq in place, Incus 7.0.2 LTS. Next post: clustering the two — with a spoiler that “a two-node cluster dies entirely if one node dies” is a myth; the default is already “1 leader + 1 replica”, and losing the replica costs nothing.
