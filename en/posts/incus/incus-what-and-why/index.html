Incus in One Look: System Containers and VMs in a Single Engine

October 30, 2026 November 9, 2026 Virtualization & Ops Incus, LXC, Virtualization, Debian Self-Hosting Ops Notes 1107 words 6 min read
🔊

I have two 16 GiB boxes running Debian 13. This series records the whole journey of taking them from bare metal to “two independent clusters plus a self-built console”: concepts, deployment, clustering, storage, networking, migration, ecosystem research, and finally building my own tooling. Part 1 lands the day after Incus 7.0.2 LTS was released (2026-10-29) — an LTS supported until June 2031, a good starting point.

What Incus actually is

One sentence: system containers and virtual machines under the same toolset and the same REST API.

bash
1
2

incus launch images:debian/13 web01          # system container: shared host kernel, starts in seconds
incus launch images:debian/13 vm01 --vm      # virtual machine: QEMU/KVM, its own kernel

Some background: Incus is the continuation of LXD. In 2023 Canonical took LXD in-house and changed its license; the original core team left and built Incus under the Linux Containers project (the org behind LXC), returning to the Apache-2.0 license as a community-driven project. Think of it as the community successor to LXD — and currently the more active branch.

Incus manages machine-level resources — CPU, memory, disk, network, GPU — not single processes. That is the fundamental difference from Docker:

DimensionSystem container (Incus/LXC)Application container (Docker)
Unit of isolationA complete Linux userland (init, systemd, sshd)One process + its dependencies
KernelShares the host kernelShares the host kernel
Typical useA “lightweight VM”: a full nginx+php+mysql stack, a VPSOne microservice, one database process
What you feel like managingA tiny serverA program

How it relates to Docker / KVM / Proxmox

ToolEssenceRelationship to Incus
DockerApplication container engineDifferent layer; Incus containers/VMs can run Docker just fine
KVM/QEMUHardware virtualizationIncus VMs are QEMU/KVM under the hood
libvirtVM management libraryIncus is a simpler encapsulation, no libvirt dependency
Proxmox VEAll-in-one virtualization platformClosest competitor; but PVE is an “appliance OS”, Incus is an “embeddable engine”

The key distinction is in that last row: Proxmox is an appliance you install, Incus is a control plane you assemble yourself. The engine ships only a REST API and a CLI; the web UI is something you install or build — which is exactly what the later posts dig into, and why this series ends with a self-built console.

Three layers top to bottom: the client layer (CLI, web UI, custom scripts) reaches incusd over HTTPS on port 8443 with an mTLS client certificate (local root can use the unix socket instead); incusd exposes the unified REST API /1.0/… upward and orchestrates kernel capabilities downward; at the bottom, the Linux kernel provides cgroup v2, namespaces, AppArmor, plus ZFS/Btrfs/Ceph storage pools and bridge/OVN networking. Every operation returns an asynchronous operation the client polls — CLI, UI, and custom scripts are all just callers of the same API.

A few points expanded:

  • incusd is the core daemon; everything goes through it. Standalone, state lives in a local SQLite; clustered, it becomes dqlite (Raft-replicated distributed SQLite; Incus uses the community continuation called Cowsql).
  • Everything is the REST API. That is the root cause of why “aggregate many hosts” and “build your own UI” are possible at all — and why a few dozen KB of Node later in this series can aggregate two machines.
  • Auth is not passwords but mTLS client certificates on port 8443 (covered in a later post).

The core object model

These terms appear in every later post:

ObjectWhat it isAnalogy
InstanceA container or a VMA tiny machine
ImageTemplate to create instances fromAn install ISO
ProfileReusable, stackable config fragmentA config template
ProjectNamespace for resource isolationTenant / environment
Storage poolWhere instance disks live (ZFS/Btrfs/LVM/Ceph)Disk array / volume group
NetworkVirtual network instances attach to (bridge/OVN)A virtual switch
Cluster memberOne Incus host in a clusterA cluster node
RemoteA “bookmark” to a server in the CLIA connection profile

Images default to images: (the public image server run by Linux Containers, with a huge distro catalog); the first pull is cached locally, so subsequent instance creation is near-instant.

What the isolation rests on

  • cgroup v2: limits per-instance CPU/memory/IO. Incus 7.0 dropped cgroup v1 — the system must be v2 (Debian 13 defaults to it).
  • AppArmor/SELinux: constrains what container processes may touch on the host. Debian 13 minimal installs may lack apparmor, which breaks container startup — one of the real pitfalls covered next time.
  • namespaces: PID, network, mount namespaces make each container look like an independent system.
  • Virtual machines: QEMU/KVM hardware virtualization, independent kernels, strongest isolation — for untrusted workloads or Windows.

Why it fits these two small boxes

  1. Density: containers start in seconds and share the kernel; a 16G box fits far more instances than KVM would.
  2. One API for both containers and VMs — script-friendly.
  3. Apache-2.0, community-driven, no single-vendor commercial license.
  4. 7.0.2 LTS is supported until June 2031 and only takes bugfix and security updates — a sane production cadence.

On versioning: the 7.0 requirements are kernel ≥ 6.12, cgroup v2, nftables (xtables dropped), LXC ≥ 6.0, QEMU ≥ 8.2, dnsmasq ≥ 2.90. Debian 13 (trixie) is not a random pick — it is the first Debian stable whose stock kernel (6.12 LTS) meets the bar; Ubuntu 24.04’s GA kernel 6.8 does not.
