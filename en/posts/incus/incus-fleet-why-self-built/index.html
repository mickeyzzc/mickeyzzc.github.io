Why Incus, and Why I Wrote incus-fleet Myself

November 24, 2026 November 25, 2026 Virtualization & Ops Incus, Incus-Fleet, Multi-Cluster, Selection, Open Source Self-Hosting Ops Notes 1516 words 8 min read
🔊

The first nine posts built the virtualization base on a small self-hosted setup: installing Incus, forming the cluster, working out quorum, settling storage and memory, wiring up cross-node networking, taking incus move apart, surveying the web UI ecosystem, researching multi-cluster and cross-cluster migration, and landing on the self-built incus-hub. This post completes the reasoning behind the three decisions: the base, the console, and whether to write the code at all.

Every section carries its data timestamp. Unless noted otherwise, everything was re-verified at writing time.

Choosing the base: what each of seven candidates costs

The scenario first: one independent Incus cluster per network segment, machines are small boxes running containers and VMs, one person operating them. In that scenario the accounting looks like this:

CandidateKey trade-off
Proxmox VEFree, large community, one UI for containers and VMs, HA and backups; but cluster-scoped, so several PVE installs with no unified view, and LXC and KVM remain two models
VMware vSphereMature ecosystem and vMotion; subscription licensing does not work for an individual or a small team
OpenStackFull IaaS; the control plane alone is a dozen services, disproportionate at this scale
oVirtMature VM management; main maintainer withdrew, long-term support uncertain
HarvesterHyperconverged, KVM and K8s in one place; the management plane carries real weight
Kubernetes + KubeVirtMature scheduling and ecosystem; turns “run a few VMs” into “operate a K8s”
IncusOne API and one command for containers and VMs, light in standalone form, Apache-2.0; no built-in multi-cluster, cross-cluster migration or unified UI

The four reasons for Incus were all verified across the first nine posts: shared-kernel containers pack far more instances onto small machines than KVM would; containers and VMs share one command set and one API so scripts do not fork; Apache-2.0 ties you to no vendor; and when monthly releases get hard to follow, 7.0.2 LTS holds the line until 2031-06.

The cost is equally plain: Incus only answers “how do I manage one cluster.” Multi-cluster, cross-cluster migration and a unified UI — it does none of the three. The earlier UI-ecosystem survey verified that the official UI only ever serves its own server/cluster because of CORS; the multi-cluster research post verified upstream’s answer to a unified multi-cluster console is no, on the grounds that one cluster (or the UI serving it) must never hold access to another. Those three items are the subject of the next two sections.

Choosing the console: what is available

The earlier multi-cluster research concluded with “an open-source gap”: nothing maintained combined “one UI over many independent clusters” with “one-click cross-cluster migration”. That cell was later filled — Orcastra published its source and documented a Migration Center.

The options, re-verified at writing time:

ProjectPositioningKey gap for this scenario
OrcastraThe only open-source project at the time covering both multi-cluster and cross-cluster migration; aimed at multi-tenant hostingIts control plane is a stack of its own; hosting many organizations, not self-management
Operations CenterRead-only fleet inventory from the official ecosystemRead-only, and tied to IncusOS
LXD Mosaic / LXConsoleMulti-host panelsManage many hosts, with no cluster abstraction
Official incus-ui / incus-ui-canonical / Incendio / ixuiSingle-cluster UIsOne endpoint, CORS blocks the rest; the official repo has not shipped
incus-fleet (this post)Self-hosted multi-cluster consoleStarts as a single binary; multi-cluster, cross-cluster migration and one UI in one place

Compared with that earlier multi-cluster research, the biggest change is that the open-source gap got filled. What remains differs in deployment weight and scenario: the existing projects target multi-organization hosting with a control plane of its own; mine is one person managing their own clusters.

Why I wrote it

That earlier post offered three roads: settle for what exists, wait for the source to go public, or build it. The source did go public, so the question here is not “is there anything” but “why still write my own”. The difference is not the feature list, it is the trust boundary — hosting-oriented designs centralize authentication, keys and audit into a separate control plane; I want one screen over clusters that are already formed, credentials held only by me, and a control plane light enough to sit beside the machines it manages.

incus-hub was design validation only: the clusters[] model, both migration orchestrations, idempotency and audit, the three-tier backup cadence. It settled what a multi-cluster console should look like; fleet was greenlit as a proper project and turned that design into something usable.

incus-fleet is built around four concrete scenarios:

  • Put clusters that share nothing into one screen: each cluster is reached with its own client certificate, the clusters share no database, and the center is the only intermediary they both trust.
  • Keep networking working after a cross-cluster move: the migration flow handles the DHCP lease cleanup, covering dhclient, udhcpc, systemd-networkd and NetworkManager; VMs support live migration with migration.stateful=true, the source restarts automatically on failure or interruption, progress goes into the database, and two centers sharing one store will not start the same migration twice.
  • Stay light at small scale: one Go binary with an embedded Vue 3 UI, SQLite to start and PostgreSQL or rqlite only when several centers share a store; the Rust host agent is optional, and instances can be managed without it.
  • Keep collaboration auditable: local accounts with admin / operator / viewer roles, server-side sessions, a task queue with audit trails, and a bilingual UI.

Why open it

The earlier UI-ecosystem survey had a line of self-assessment: self-built means no community maintenance, the price of full control and zero dependencies. Left alone, the project stops with me — when the person writing it stops, nobody reads the code. Open source is the move that hedges this: a second person can read the code, report a problem, send a change, and maintenance stops being a one-person job.

AGPL-3.0 rather than MIT or Apache-2.0 because it puts “serving over a network counts as distribution” into the terms: modify fleet and make it available to users over a network, and you must give those users the corresponding source. The README says it plainly — the license keeps the project open while preventing closed-source hosted derivatives. For a control plane that is exactly the boundary wanted: anyone can use it, anyone can change it, nobody can take it closed and sell it.

Open source also forces engineering discipline. docs/en/standards.md sets the TDD contract; make coverage gates Go coverage at 90% or above and the frontend at 90 / 90 / 90 / 85; scripts/secret-scan.sh inspects private keys, credential assignments, bearer tokens, operator subnets and hostnames before a commit, and CI runs the same scan over every tracked file and every commit; the English and Chinese docs must change in the same commit. From 0.2.0, GitHub Actions publishes amd64 / arm64 binaries for the center, helper and agent, plus .deb and .rpm packages.

What it looks like now

Dashboard: health for both clusters plus host resource totals; the UI is bilingual.

Top to bottom: the browser’s requests pass through Caddy for TLS termination into the center; persistence hangs off the left (SQLite by default, PostgreSQL or rqlite when several centers share one store), and the independent clusters below are reached with their own client certificates. The dashed Rust host agent sits on every member, reporting facts, heartbeats and metrics back to the center — it is optional; instances can be managed without it.

Deployment prerequisites

Live migration requires the segments to reach each other — the target cluster must connect to the source’s 8443; where a firewall forbids that, only a stopped copy is possible. The SPICE remote desktop has no ticket authentication; firewall the 5910-5989 port range yourself.

incus-fleet lives at github.com/mickeyzzc/incus-fleet, AGPL-3.0, v0.2.0 released 2026-11-24. Deployment, the user guide, the HTTP API and the roadmap are all under docs/ in the repository, in both languages. The full series catalogue is in the first post of the series.
