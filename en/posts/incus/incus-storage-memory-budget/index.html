Storage Choices and Memory Budget on a 16 GiB Box

November 4, 2026 November 9, 2026 Virtualization & Ops Incus, ZFS, Btrfs, Storage Self-Hosting Ops Notes 809 words 4 min read
🔊

The storage backend decides more than performance — it decides whether migration is a downtime event or a live one. That is the one sentence this post rests on. Along the way: the memory budget for a 16G box, because an uncapped ZFS ARC is a memory thief.

The conclusion first

incus move fundamentally means moving instance disks from A to B:

  • If A and B share one storage (Ceph and friends), no data moves — only runtime state does → live migration, no downtime;
  • With local disks on each node (my case), data is physically copied → downtime migration, seconds to tens of seconds for containers, longer for VMs.

So the first storage question is not “which is fastest” but “am I willing to pay Ceph’s price for zero-downtime migration”. My answer: no. Two 16G boxes cannot carry Ceph’s minimum of 3 monitors + OSDs, and “no mutual replication” makes its replication useless here. Accept the short downtime window on local disks — that is the entire cost.

Driver comparison

DriverTraitsMigration friendlinessVerdict for 16G
ZFSCopy-on-write, native snapshots/compression/quotas, zfs send/receive★★★ (send speeds up downtime migration)Important data, SSD, willing to tune ARC
btrfsCopy-on-write, in-kernel, low memory overhead★★★The low-friction pick if you skip ARC tuning
LVMBlock-device volumes, good performance★★Only if you already have an LVM layout
dirPlain directory with disk files★ (plain file copy)Experimenting only
CephDistributed shared pool, replication★★★★★ (live migration)⚠️ not worth it on 2×16G

The bar shows one 16 GiB node split up: 2 GiB host system, 4 GiB ZFS ARC cap, 9–10 GiB for instances, 1 GiB buffer; a separate 4 GiB swap sits below. The bottom row compares storage drivers by migration friendliness — local storage always means downtime migration, only shared storage (Ceph) enables live, and the data is physically copied either way; ZFS just copies faster.

Memory budget (per 16G node)

UseAmountNotes
Host system + incusd + dnsmasq1.5–2 GiBLeave room, do not squeeze
ZFS ARC2–4 GiB (must cap)Uncapped it defaults to over half of RAM
Instance memory9–10 GiB≈ 20 GiB across both machines

Swap4 GiB (physical partition)Never on a ZFS zvol — deadlock risk

Post 2 gave the ARC capping command (zfs_arc_max=4294967296 in /etc/modprobe.d/zfs.conf); here is the routine check:

bash
1
2
3

arc_summary | head -20
cat /sys/module/zfs/parameters/zfs_arc_max    # 4294967296
zpool status && zpool list

If you would rather not carry the ARC overhead at all: switch the preseed’s driver: zfs to driver: btrfs and the ARC disappears; btrfs snapshots and compression are enough at this scale. On a 16G box that is a perfectly legitimate choice — ZFS is not a religion, it is a trade-off.

Why ZFS (and what it actually buys)

  1. Native snapshots in seconds, nearly free → incus snapshot before every change, rollback is one command;
  2. Transparent compression: images and instance disks typically shrink 20–40%;
  3. zfs send | zfs receive: makes the downtime of incus move much shorter than plain file copying — same downtime category, smaller window;
  4. Snapshot scheduling delegated to Incus:
bash
1
2
3

incus config set c1 snapshots.schedule "0 3 * * *"
incus config set c1 snapshots.pattern "auto-{{ creation_date }}"
incus config set c1 snapshots.expiry "7d"

({{ creation_date }} is an Incus-side snapshot naming placeholder — a literal config for Incus; Hugo leaves it untouched.)

If you have a dedicated data disk

If the system disk is a small NVMe, a loop-file pool (size: 40GB in the preseed) performs meh. With a dedicated disk, give the pool the whole device:

bash
1
2

incus storage create local zfs source=/dev/sdb --target incus-n1
incus storage create local zfs source=/dev/sdb --target incus-n2

This wipes the disk — double-check the device name.

One last time

The reality of local storage: instance data exists on exactly one machine. Lose that machine, its instances go offline — wait for it to come back or rebuild from backup. That foreshadows “no replication means backups carry everything”, the subject of the final post.
