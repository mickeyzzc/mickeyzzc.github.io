One UI for Multiple Clusters: What Open Source Offers

November 8, 2026 November 9, 2026 Virtualization & Ops Incus, Multi-Cluster, Migration, Open Source Self-Hosting Ops Notes 1767 words 9 min read
🔊

The requirement grew: two independent clusters, one per subnet (each starting with a single leader, replicas to follow), one web frontend above both, plus one-click cross-cluster migration. This post separates “intra-cluster migration” from “cross-cluster migration” — they are not the same thing at all — and covers the five hard constraints of going cross-cluster, plus what the open-source survey concluded.

Pinning the topology down

Three layers: a single web frontend at the top (incus-hub / the control plane); below it two clusters sharing nothing — cluster A on subnet 1 (192.168.10.0/24, leader A1 + replica A2) and cluster B on subnet 2 (192.168.20.0/24, leader B1 + replica B2), each internally shaped like the “1 leader + N replicas” from earlier posts. The orange dashed line is cross-cluster migration: copy + delete in essence, with an IP change guaranteed. There is no shared database between the clusters; profiles, networks, and pool definitions are disconnected — that fact creates every difficulty below.

The key point: two subnets = two independent Incus clusters with no shared database and no dqlite relationship of any kind.

The two “one-click migrations” are not the same thing

Intra-cluster · different hostsCross-cluster · different hosts
Typical commandincus move web01 --target incus-a2incus move cluster-a:web01 cluster-b:web01
--target meaningPicks a member of this clusterCannot cross clusters; at most the landing member inside the target cluster
Config databaseOne copy; instance location metadata syncs automaticallyTwo independent databases; bridged by the client-side remote concept
Profiles / networks / poolsDefined cluster-wide, naturally availableNot shared; the target may lack them entirely and needs adaptation
TransportServer-side move, fastestCross-remote = copy + delete (or a migration stream)
Backend difficultyLow (one API call)High (two-step handshake + credential passing + target adaptation)

The official definition of --target is Cluster member name, and the how-to adds “In this case, do not specify the source and target remote” — it is a member selector, not a cross-cluster flag. Cross-cluster relies on the <remote>: prefix:

incus move cluster-a:web01 cluster-b:web01 --mode pull

incus move remote:... is copy followed by delete under the hood — the move.go comment says “A move is just a copy followed by a delete”. It is not atomic; after a failure, whether the source still exists is the caller’s problem.

Official wording on downtime (how-to): containers must stop before moving; VMs either enable migration.stateful=true or stop; container live migration via CRIU only works for “very basic containers” — in practice, everything stops. --refresh, --stateless, and --instance-only all apply.

Five hard constraints of cross-cluster migration

① The subnets must be able to reach each other, or online migration is impossible

ModeWho connects to whomNetwork requirement
pull (default)Target cluster connects to the source’s 8443subnet 2 → subnet 1:8443 reachable
pushSource connects to the target’s 8443subnet 1 → subnet 2:8443 reachable
relayClient connects to both and relaysEnd-to-end connectivity unnecessary, but all data crosses the client

Servers hold no trust in each other. stgraber: “The concept of ‘remotes’ is a purely client side one, so there is no way for one server to directly push something to another as they don’t trust each other. Instead you need the client to communicate with both sides as a trusted intermediary.” — which both justifies the aggregator’s existence (the Hub is that trusted intermediary) and explains why relay is the heaviest to implement: the Hub must splice the two ends’ migration websockets byte by byte.

② Profiles / networks / pools do not follow the instance

The target is another independent cluster with its own definitions. Real errors from the official forum: Error: Migration operation failure: Profile not found, Error: Failed loading storage pool: Storage pool not found. The complete adaptation toolkit from the how-to: --config, --device, --storage, --target-project, --no-profiles, --profile. The instance IP will change across subnets — DNS, reverse proxies, certificates, and firewall rules all need follow-up; no UI click can absorb that automatically.

③ OVN does not span clusters

OVN solves cross-member networking inside one cluster (post 5), but two clusters run two independent OVN / OVN central databases with unconnected logical switches. Cross-cluster migration means landing on a different layer-2/layer-3 network: static IPs, ACLs, and load-balancer backends all need rebuilding.

④ Custom storage volumes move separately

bash
1

incus storage volume copy cluster-a:pool1/vol1 cluster-b:pool2/vol1

Per the how-to: except for ceph/ceph-fs, storage volumes exist only on the member where they were created. Since 7.0, dependent volumes travel with the instance (introduced in 6.23); ordinary custom volumes still need manual handling.

⑤ Security: migration websocket credential exposure (High — and specific to this scenario)

GHSA-h2j8-4crh-vhfc (published by stgraber, 2026-10-29; High, CVSS 7.1):

“Instance, volume and snapshot migration operations embed their per-connection websocket secrets in the operation metadata. That metadata is broadcast to every event listener holding view access… A client with event-view access can read the secret and connect to an in-flight migration’s data channels before the legitimate peer, hijacking the transfer of an instance it may not otherwise read.”

  • The advisory states: affected < v7.6.0, fixed in ≥ v7.6.0 (I verified the advisory page directly);
  • The 7.0.2 LTS this series runs is not on the patched list; whether the Zabbly lts-7.0 channel backported the fix must be verified before going live (check the Debian security tracker, apt-cache policy incus for a 7.0.3+ security release);
  • Mitigation: never grant can_view_events to third parties; limit event listeners.

This risk fires precisely in cross-cluster migration scenarios — intra-cluster server-side moves take a different path.

How cross-cluster migration actually runs (two-step handshake)

The Hub as trusted intermediary, five steps: stop the source instance (containers must stop); POST /1.0/instances/web01 {migration:true} on the source returns a migration operation plus websocket secrets; the Hub hands the operation URL, the source cluster certificate, and the secrets to the target cluster along with the target-side profiles/pool/network/IP; the target pulls the disk stream from the source (requires 8443 reachability); finally wait on both operations, verify, delete the source, and write the audit log. The red note is the engineering rule: move = copy + delete, so a mid-flight failure must end with the source instance restored.

Key fields of the source object in POST /1.0/instances (from shared/api/instance.go): type: migration, mode, operation (the source operation URL), certificate (the source cluster certificate), websockets (JSON key secrets), live, instance_only, refresh.

Why upstream “deliberately” does not do it

On the forum thread “Incus UI is open for development” (2026-11-05), someone asked essentially my exact question: is it a goal to “manage multiple clusters in a single view - e.g. list instances across them, and move instances between them”. stgraber’s answer (2026-11-06):

“It’s not. The Incus UI is a pure javascript client for the Incus API of the server/cluster serving it. It’s not allowed to connect to anything else as CORS would prevent it.”

The official route: a read-only multi-cluster inventory (Operations Center) + each cluster’s own UI + pasting a migration token between two UIs. The motive is security — never having one cluster (or the UI it serves) hold access to another. It is not the “one screen, one click” I want.

The direct answer

Does anything open source combine “one UI over many clusters” with “one-click cross-cluster migration”? — No. Broken down: for seeing multiple clusters there is Operations Center (read-only), Orcastra (source 404), and LXD Mosaic (clusters flattened) — all can look, none can operate; for one-click cross-cluster migration, no maintained open-source web UI does it — the CLI handles it fine, and the official UI offers a token-paste flow. The combination is an open-source gap.

Three roads: compromise with what exists (Operations Center for the global view + an Incendio per cluster + token pasting — zero development); wait for Orcastra to publish source (uncontrollable); or evolve the existing incus-hub into the tool — the design is next post’s subject.
