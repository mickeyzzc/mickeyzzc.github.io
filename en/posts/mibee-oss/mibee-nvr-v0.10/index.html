MiBeeNvr v0.10.0-preview.1: End-to-End H.265 + Timelapse v3 + Auth Modernization + Architecture Cleanup (Paving the Way for Sidecar AI)

July 28, 2026 MiBeeOSS NVR, Go, H.265, WASM, WebCodecs, Timelapse, MJPEG, WebSocket, Auth, Architecture Refactor, Sidecar, AI, Open Source MiBee Open Source Projects Series 2845 words 14 min read
🔊

v0.10.0-preview.1 is MiBeeNvr’s largest release since 0.8.0. The theme isn’t “add features”, it’s clean up the foundation: end-to-end H.265, Timelapse rewritten to v3, low-latency MJPEG, modernized auth, and a sweep of architecture cleanup across config / DI root / API routing / frontend player.

Why this much refactor at this point? After v0.9 paid off the accumulated engineering debt, the NVR’s mainline is heading in two directions — stronger AI capabilities, and support for more cameras. Both require a main process with clear internal structure, pluggable protocols, and AI inference that doesn’t block the video pipeline. The trade-offs discussed in the earlier research posts (frontend codec selection, streaming protocol landscape, NVR remote-access P2P survey, storage media selection) start landing in this release. A dedicated section at the end explains how this cleanup ties into the sidecar AI roadmap.

One thing up front: the v0.9 post announced that v0.9.x would be the last stable/compatible baseline since v0.1.0, and the next major would introduce breaking changes with precise migration paths. This release delivers on that promise: every breaking change is listed at the end, with grep commands and migration steps — no silent breakage. This is a preview (release candidate), not recommended for production. Read the breaking-changes section and the upgrade guide before upgrading. Full notes at the GitHub release.

End-to-End H.265

Before 0.9.x, H.265 was half-finished: live playback depended on WebCodecs, which requires an HTTPS secure context, so plain-HTTP LAN playback was impossible; merge outputs frequently black-screened on Edge; and timelapse merges simply didn’t work. This release fixes the entire H.265 chain — live, recording, merge, playback — end to end.

The biggest change on the playback side is the @yume-chan/libde265 WASM decoder. H.265 live now plays on plain-HTTP LANs without requiring HTTPS. The frontend does automatic probing: prefer WebCodecs under HTTPS (for hardware acceleration), fall back to WASM software decoding otherwise. The detailed comparison was written up earlier in H.264/H.265/H.266 Web frontend playback selection — WebCodecs is the optimal path but has the secure-context gate, WASM is the fallback. This release chains them into a single degradation-aware pipeline.

This diagram shows the two decode paths for H.265 live: WebCodecs first under HTTPS for hardware acceleration, WASM software decode for everything else. Both terminate at the player — there’s no “can’t play” exit.

A decoder alone isn’t enough. Multi-cam H.265 grids trigger a nasty “freeze storm” in browsers — one stream’s decode stall drags down the entire grid’s frame polling. This release abstracts the frontend player into a testable state machine — the Player Orchestrator, under web/src/lib/player/.

The state machine has three states: ok means stable for 30+ seconds; degraded means decode anomalies were detected but no action yet — an 8-second debounce window avoids flipping protocols on a transient network blip; failed means it’s confirmed broken, demote immediately to the next candidate in the chain. If webrtc → flv → hls → mjpeg all fail, degrade to a static snapshot. The 8s debounce was tuned the hard way — too short and transient jitter triggers false demotions, too long and the user stares at a frozen frame. The Player Orchestrator is designed as DOM-independent pure logic, unit-testable without jsdom; dispatch.ts documents the Svelte 5 synchronous-dispatch trap and the workaround.

The rest of the chain is all timing and data-consistency problems:

  • Encoding persistence — “probe once, persist forever”. ONVIF camera encoding used to be re-probed on every startup; mismatches between the probe result and the actual stream caused black screens and protocol storms. Now probed once and dual-written to YAML + DB; subsequent boots just read it.
  • Parameter-set timing fix — SPS/PPS/VPS capture moved ahead of the RecordEnabled gate. The previous ordering judged recording-enablement before capturing parameter sets, so in live-only (no-recording) mode the parameter sets were never captured and playback black-screened.
  • Playback routing — routes based on runtime codec plus authoritative MSE probing; H.265 is forced onto the WASM path instead of incorrectly landing on MSE.
  • Playable timelapse merges — fixed the hvcC box’s numNalus; switched to conservative Main-tier defaults (avoiding parsing self-contradictory SPS, which resolved Edge’s HEVC extension rejection); periodic merges now correctly distinguish H.265/H.264 frames — previously only JPEG was collected, so H.265 cameras always failed timelapse merges.

Timelapse v3

The timelapse system is rewritten end-to-end as v3. The v0.7 rewrite switched the merge path from JPEG sequences to a pure-Go NAL→MP4 muxer, but the merge window still had a 1h hard cap — values like 8h/12h/24h/7d/30d/natural-day were silently clamped to 1h in code. The v0.9.1 post noted this doc/code mismatch — the docs described a capability that didn’t exist. v3 actually removes the cap.

v3’s main threads:

  • Merge window unbound. natural-day / 8h / 12h / 24h / 7d / 30d now actually take effect, no clamping. Default changed from 1h to natural-day (a midnight-aligned 24h window in your configured timezone). The natural-day timezone alignment is also fixed — Local timezone under some configs would shift the window.
  • DB-backed periodic merges. A new timelapse_merges table (schema v28→v29) gives every long-window merge output a full DB record: camera, window, duration, codec, frame count, status. The frontend discovers, plays, and deletes merge outputs via /api/timelapse/merges*. Previously these intermediates were orphaned files with no structured metadata.
  • Codec-aware playback. The merge endpoint response carries an X-Timelapse-Codec header, and the frontend picks the player accordingly — <video> for H.264/H.265, JPEG frame cycler for MJPEG.
  • Continuous merge chain. Periodic merges fold prior intermediates to avoid unbounded accumulation. If you want to keep intermediate files for debugging, there’s an optional retain_intermediate_mp4 flag (default false; saves ~1.5GB/day/camera).
  • repair remerge-h265 CLI — specifically repairs historical H.265 timelapse merges that Edge couldn’t play.

Low-Latency MJPEG + Cross-Network WebRTC

MJPEG cameras like the ESP32 MiBeeCam used to do HTTP polling — one request per frame, with latency and connection overhead to match. This release switches to WebSocket streaming (wsstream): a single connection pushes frames continuously, cutting both latency and connection cost.

On the WebRTC side, a new streaming.webrtc.ice_servers config — a list of STUN/TURN servers — is added. WebRTC used to be LAN-only; with ICE servers configured, cross-network access works. The selection of remote-access approaches — self-hosted signaling, commercial P2P products, the security red lines of white-label P2P — was compared in detail in the NVR remote-access P2P survey and the P2P signaling/relay survey; this release wires up the ICE configuration layer first.

Architecture Cleanup

This section is the real mainline of the release, and the landing point of “paving the way for sidecar AI”. The refactor concentrates on three places:

  • Config split by subsystem. All config used to live in one file, with the camera / merge / timelapse / transcoding / streaming / health / ingest / ai / server subsystems interleaved. Now each subsystem is its own file, and the entry point only loads and assembles. The public API is fully preserved; runtime behavior is unchanged.
  • DI composition root split. pkg/app/run.go is the dependency-injection assembly point; helper logic and route assembly used to be mixed together. Now they’re split into separate helpers.go and router.go, and the composition root does one thing: decide what gets injected into what.
  • Routes registered by domain. All API endpoints used to be registered in a single Routes() method — a classic god-method. Now they’re split into domain-scoped registrars — cameras, recordings, timelapse, transcoding, streaming, settings each have their own registration function, and the entry point loops over them. No endpoints lost.

The split itself doesn’t change runtime behavior, but it changes the answer to “where do I touch to add something new”. Before, adding a new protocol or AI capability meant finding a spot in one giant config file and wedging an endpoint into a god-method; now each domain is its own file, and changes stay within their subsystem. This is the precondition for the sidecar roadmap — with a clean main-process structure, external capabilities can be hung on cleanly.

Accompanying engineering changes:

  • API bandwidth optimization: gzip compression (measured volume drops by an order of magnitude), ETag (If-None-Match→304), a lightweight view=summary endpoint, recording-list limit clamp (default 50 / max 500), and omitempty on CameraRow fields. Frontend grid-polling traffic drops substantially.
  • Settings information-architecture rewrite: left-sidebar navigation + unified save + destructive-action confirmation. Fixed a regression where switching categories lost unsaved changes.
  • Frontend merge-utils extraction: merge utilities moved out of the route component into lib/; route components no longer carry business logic.
  • Recordings page gallery view removed — previewed in v0.9. Default timeline, focused on the core scenario.

Two cleanup items worth calling out separately:

TUTK dtls dead-code deletion — a complete ChaCha20Poly1305 DTLS implementation, deleted as a unit after confirming zero references. The TUTK protocol itself uses a different DTLS path; this implementation was an early experiment left behind. Clearing dead code means the later sidecar protocol-adaptation layer won’t step on these landmines.

AI INVALID_PROTOBUF root cause — this bug took the most time. The initial suspicion was CDN truncation of model downloads, but the real root cause was that the streaming-gzip middleware appended a spurious gzip trailer to binary responses. AI model files are binary protobuf; passing through the gzip middleware got them incorrectly “completed” with trailer bytes, which broke ONNX Runtime parsing. The fix is a 4-layer defense:

  1. Middleware root cause — binary content-types skip gzip.
  2. Download layer — retry + Range requests + atomic write.
  3. Docker image — AI models pre-baked, no runtime download.
  4. Frontend cache self-heal — auto-redownload on detected corruption.

Full postmortem in docs/known-issues-ai-onnx-gzip-trailer.md. This fix has direct relevance to the sidecar roadmap — once AI inference moves into a sidecar, model distribution and integrity verification become core problems, and this release’s 4-layer defense is the foundation.

CI flake elimination — goroutine lifecycle management (startup-bg service + backfillWg + service-layer goroutine joins) eliminated the TempDir cleanup race; the full go test ./... suite passes cleanly in a single run for the first time. CI upgraded to Node 24 actions. These look unglamorous, but the sidecar architecture introduces more concurrent processes and async lifecycles; an unstable CI makes iteration impossible.

Key Stability Fixes

Selected cross-module fixes:

  • Merge-MP4 leak — deleting a recording previously removed only the DB row and source frames, leaving the merged MP4 on disk. This release deletes merge outputs alongside recordings, and adds a repair reclaim-orphan-merges CLI to clean up historical leaks. After upgrade, run a --dry-run to see how much space is reclaimable (20ms default delete interval, USB-HDD friendly).
  • Recording timeline truncation — a lightweight /api/recordings/timeline endpoint avoids loading everything. A Xiaomi camera with frequent reconnects can produce 5000+ fragments in a day; full load would hang.
  • Autodiscover stabilization — IP-roaming dedup, recorder storms on unchanged endpoints, endpoint URL normalization (scheme/host/port/trailing-slash). Stabilized after several rounds of fixes.
  • Startup scan blocking — async startup scan + bounded reconcile, 8-minute block → 8-second startup.
  • Merge backlog unblock — retiring a legacy singleton unblocked the backfill loop; 8500+ pending entries drained.
  • ONVIF recording_enabled=false silent recording, MJPEG migration OOM (frame-count limit), platform-aware AVI segment duration (≤2GB RAM→30s, >2GB→5min).

Breaking Changes (Read Before Upgrading)

Full migration steps are in the official upgrade guide. The key ones:

1. Config: combined protocol strings rejected (hard error, blocks startup)

0.10.0 rejects combined protocol strings at startup. Grep first:

bash
1

grep -nE 'protocol:\s*".*_(h264|h265|mjpeg|jpeg)"' /path/to/mibee-nvr.yaml

Any matching line must be split:

yaml

2
3
4

8

# ❌ Before (0.9.x accepted, 0.10.0 rejects)
- id: "front-door"
  protocol: "rtsp_h264"

# ✅ After
- id: "front-door"
  protocol: "rtsp"
  encoding: "h264"

Applies to every protocol value with an underscore: rtsp_h264 / rtsp_h265 / rtsp_mjpeg / http_jpeg / onvif_jpeg, etc.

2. DB schema v28 → v29

The recordings.merged column is dropped (the migration auto-backs-up via VACUUM INTO to <db>.pre-v29-backup first; rows with merged=1 are updated to merge_status='merged' as a safety net). < v0.9.x cannot upgrade directly to 0.10.0 — upgrade to 0.9.x first.

3. API endpoints removed — GET /api/timelapse/{id}/thumbnail and /preview return 404, replaced by the /api/timelapse/merges family. External scripts need migration; the NVR’s own frontend has already switched.

4. Default-value changes — cleanup.disk_threshold_percent 95→85 (avoiding the HDD performance cliff past 90% full); timelapse.merge_duration default "1h"→"natural-day" (note: rolling-window merge merge.rolling_window is still capped at 1h).

5. Post-upgrade recommendation — run mibee-nvr repair reclaim-orphan-merges --dry-run to check for historically leaked merge MP4s.

Sidecar AI Architecture Vision

This section covers direction, not implementation — the detailed design will come in a follow-up post.

The architecture cleanup above isn’t cleanup for its own sake. The NVR is heading in two explicit directions: stronger AI capabilities (more complex detection models, multimodal inference, event triggering) and support for more cameras (more protocols, more vendors, more edge scenarios). Both share a constraint: AI inference and protocol adaptation cannot drag down the main process’s video pipeline — recording, live streaming, and merging must stay stable and low-latency.

I previously designed microservice sidecar architectures at an internet company. The core idea of the sidecar pattern: keep the main process lightweight and stable, and hang the variable capabilities (AI inference, protocol adaptation, data enrichment) off the side as independent processes/containers that communicate over well-defined interfaces. This structure is proven in service meshes — Envoy, Linkerd, and the like are all sidecars. The NVR scenario’s particular wrinkle is that video frames are a high-throughput data stream, so the data channel between sidecar and main process needs dedicated design.

mermaid
flowchart TD
    NVR["NVR main process<br/>record/live/merge"] <--> BUS["Frame bus<br/>shm / UDS"]
    BUS --> AI["AI inference sidecar<br/>detection/events"]
    BUS --> PROTO["Protocol adapter sidecar<br/>new camera protocols"]
    NVR <--> CTRL["Control / health channel<br/>config + metrics"]
    AI --> CTRL
    PROTO --> CTRL

    classDef core fill:#E3F2FD,stroke:#1565C0,color:#1565C0
    classDef bus fill:#FFF3E0,stroke:#E65100,color:#BF360C
    classDef side fill:#E8F5E9,stroke:#2E7D32,color:#1B5E20
    classDef ctrl fill:#F3E5F5,stroke:#9C27B0,color:#6A1B9A
    class NVR core
    class BUS bus
    class AI,PROTO side
    class CTRL ctrl

This sketch makes three points:

  1. The main process stays lightweight — recording, live streaming, and merging (the core video pipeline) don’t move; AI inference moves out.
  2. AI and protocol adaptation are independent sidecars — they can be upgraded, scaled, and crashed independently without affecting the main process. Adding a new vendor’s proprietary protocol means adding a protocol-adapter sidecar; the main-process code is untouched.
  3. Two channels, physically separated — the frame bus carries the high-throughput data stream (shared memory or Unix Domain Socket), while the control/health channel carries config and metrics. The two have completely different QoS requirements and are physically separated.

Why is this release’s cleanup a precondition? Because for sidecars to attach cleanly, the main process must first have clear domain boundaries — config split by subsystem, routes registered by domain, auth made stateless (HMAC tokens don’t consume main-process memory). Once those are done, the sidecar attachment points are clean. The 4-layer defense for AI model distribution (the gzip-middleware root cause fix) is foundation for the same reason — model integrity verification becomes more critical in the sidecar scenario.

The specifics of sidecar IPC protocols, deployment form (same-host process vs container vs Pod), and AI model distribution will be covered in a follow-up post. This release puts the main-process foundation in place first.
