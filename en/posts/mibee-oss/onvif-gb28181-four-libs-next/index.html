Five Protocol Libraries, One Release Day: onvif-go Reaches v2, the GB28181 Device Side Closes Out, and onvif-c Debuts

September 21, 2026 September 21, 2026 MiBeeOSS Go, Rust, C, ONVIF, GB28181, IP Cameras, ESP32, Open Source MiBee Open Source Projects Series 2534 words 12 min read
🔊

MiBee’s camera access runs on two protocols: ONVIF, the de facto standard internationally that Hikvision, Axis, and Dahua all speak, and GB/T 28181, China’s national surveillance standard that government and state-owned projects cannot avoid. The protocol stack is open-sourced as five independent libraries split by protocol × language × role, all extracted from production code, and in the latest release round all five tagged on the same day: onvif-go entered the stable v2 line, onvif-device-rs shipped to crates.io, gb28181-go and gb28181-rs closed out the 2022 device-side surface, and onvif-c debuted as the fifth member. This post goes library by library through capability boundaries, key design decisions, and remaining limitations, stated as released.

A starter example per protocol

Both pick the most common entry scenario, both in Go — the one language with a full-coverage library for each protocol; the Rust and C READMEs carry the equivalents with the same seam shapes.

package main

import (
    "context"
    "fmt"
    "log"

    "github.com/mickeyzzc/onvif-go/v2/onvif"
)

func main() {
    client, err := onvif.NewClient("http://192.168.1.100/onvif/device_service",
        onvif.WithCredentials("admin", "pass"),
        onvif.WithAutoClockSkew()) // survive clock-diverged cameras — top cause of Hikvision 401s
    if err != nil {
        log.Fatal(err)
    }
    if err := client.Initialize(context.Background()); err != nil {
        log.Fatal(err)
    }

    info, _ := client.Device().GetDeviceInformation(context.Background())
    fmt.Printf("%s %s (fw %s)\n", info.Manufacturer, info.Model, info.FirmwareVersion)

    profiles, _ := client.Media().GetProfiles(context.Background())
    mainToken := onvif.SelectMainProfile(profiles) // highest resolution, not profiles[0]
    uri, _ := client.Media().GetStreamURI(context.Background(), mainToken)
    fmt.Println("main stream:", uri.URI)
}

onvif-go: three releases from v1.2 to v2.2

Three releases in quick succession, each with one job.

v2.0.0 graduated from the rc series as the library’s first stable release. Two big pieces landed. The server-side Events PullPoint service is real: CreatePullPointSubscription, PullMessages (long-polling), Renew, and Unsubscribe are served on per-subscription addresses, hosts inject their own analytics events through the PublishEvent seam, and the WSPullPointSupport advertisement finally agrees with the implementation. The client now parses canonical double-layer notifications — conformant cameras wrap tt:Message inside wsnt:Message, and only by reaching through the wrapper do MotionAlarm State and Score arrive. Migrating from v1 is mostly an import-path swap (the module path gained a /v2 suffix). For ecosystem context: use-go/onvif, the most-starred Go ONVIF library, not only went dormant — it no longer compiles on current Go releases, which is precisely the case for keeping a stable line of your own.

v2.1.0 is the wire-format correctness release: ground truth for wire formats switched to the official WSDL/XSD set. The most representative fix: against strict devices like Dahua, PTZ/imaging/certificate requests previously went out as empty shells — namespace misplacement meant the device could not recognize the fields, so it answered HTTP 200 and silently did nothing. A full WSDL audit corrected every remaining misassignment in both directions. Both new capability areas point at Profile M: a Media2 client with the codec-agnostic configuration model, where GetVideoEncoderConfigurationOptions reports one entry per supported encoding — the right way to talk to H.265/AV1-era cameras; and an Analytics client plus a metadata stream parser covering rules and analytics module CRUD, frames, tracked objects, bounding boxes, and geo locations. The server gained TLS (Profile T’s transport baseline). One upgrade note: within the v2 line, this release changed wire bytes on the affected surfaces — wire-format correctness outranks byte stability — so if your consumer has a parser pinned to the old shapes, read the CHANGELOG before upgrading.

v2.2.0 closed the last PTZ gap with the Rust twin: the server now serves the full preset/configuration family (SetPreset, RemovePreset, GetConfigurations, GetNodes, all with WSDL-correct namespaces), and the client’s GetConfigurations decodes pan/tilt and zoom limits — previously parsed and dropped.

onvif-device-rs: naming settled, parity reached

The name carries an episode: the crates.io name onvif-rs is held by an abandoned 2018 placeholder, so the library used to be consumable only as a git dependency. The resolution — the crate ships to crates.io as onvif-device-rs, installable with cargo add (latest 0.7.0); the repository keeps its original name, and the README documents the disambiguation from lumeohq’s same-named client.

v0.7.0 is a twin release with onvif-go v2.2.0, and the capability-gap list between the two is now empty: SystemReboot wire answers (protocol answer only, no reboot side effect), WS-Discovery Hello/Bye announcements (best effort — a lost announcement never stops Probe answering), a TLS listener (behind the tls cargo feature, off by default, fail-closed on incomplete certificate config), and the full events pull-point family (hosts inject via publish_event, fan-out to every live subscription, Concrete/ConcreteSet topic filters, long polling). Create actions stay behind WS-Security while reads are open; with events disabled the routes 404 and the wire is byte-identical.

The security fix hits exactly where this library lives: quick-xml 0.36 → 0.41 (RUSTSEC-2026-0194/0195, high 7.5). Both advisories concern untrusted-XML parse surfaces — this library’s day job. Parsing loops were restructured onto the new event model, and entity-carrying passwords now accumulate correctly across split text events.

GB28181 device side: the twin closure

gb28181-go v0.11.0 and gb28181-rs v0.12.0 are a pair of twin releases with one goal: feature-completing the standard’s platform→device surface — every control, configuration, subscription, and intercom flow gets a decoded wire path and a host callback.

  • Control/configuration: the DeviceControl sub-command set (IFrameCmd, RecordCmd, GuardCmd, AlarmCmd, TeleBoot, PTZCmd passthrough); bit-level PTZCmd decoding, with Go and Rust sharing one golden byte table that is generated from the platform-side constructors — encode and decode cannot drift; DragZoom; DeviceConfig plus ConfigDownload and HomePosition.
  • Subscriptions/notifications: a SUBSCRIBE/NOTIFY framework with alarm, catalog-change, and mobile-position notifiers; the §9.4.2 MediaStatus completion notification — sessions aborted by BYE stay silent, no false reports.
  • Intercom: receive (G.711 sink), upstream (device-to-platform 20ms RTP), and end-to-end voice broadcast (platform initiates, device acknowledges, audio INVITE back-call, platform delivers RTP). The negotiated upstream audio law is exposed to hosts.
  • Lifecycle: graceful deregistration (REGISTER with Expires: 0 through the full 401 dance) and SIP-Date time observation.

gb28181-rs carries three items of its own: X-GB-Ver protocol negotiation (2022 Annex I, opt-in — unconfigured keeps the wire byte-identical), minimal answers for the 2022 five information queries, and an ILP32 compile fix — 32-bit targets build again, with a dedicated CI job keeping it that way.

The fix worth recording is gb28181-go’s ACK race: the gosip upstream rewrites the top Via of in-flight requests without a lock (upstream issue #87), so under concurrency an ACK can attach to the wrong dialog. After all ACK paths were rebuilt from a pre-send INVITE snapshot, the race detector’s 89 reports went to zero. The fix also explains the split — why the device side insists on hand-written SIP while the platform side builds on gosip: the device’s SIP subset is small enough to hand-write and fully control; the platform faces messier scenarios, where borrowing a proven stack pays.

The platform side: a full GB28181 platform extracted from MiBeeNvr

The platform side shares the device side’s provenance — production code: extracted wholesale from MiBeeNvr’s GB28181 implementation (extraction completed in v0.2.1), and incremental merges since produced the package list now in the README:

  • platform/: device/channel registry with keep-alive liveness, MPEG-PS demux (with a PSM-less audio fallback heuristic), RTP port pool, PTZ and A505 command building, RTP receive/reassembly (UDP and TCP-passive, jitter buffer, SSRC latch). Three of four migration batches have landed, as the README states.
  • platform/sip/: a full platform server on gosip — digest auth, keep-alive/offline detection, catalog refresh plus three SUBSCRIBE kinds, INVITE/BYE session management, and a row of firmware-quirk patches (speculative ACK, REGISTER source-port rotation, long-GOP IDR watchdog).
  • platform/cascade/: cascade — this platform registers as a lower platform to an upper one: aggregated catalog upload, INVITE forwarding, playback from recorded segments.
  • psmux/: the PS/RTP muxer (H.264/H.265, G.711, >60KB access-unit splitting) shared by device push and cascade forwarding.
  • conformance/: a device↔platform localhost loopback suite — a real device.Server against a real platform SIP server, from digest registration to byte-exact RTP/PS round-trips, re-verified on every CI run.
  • security35114/: an opt-in (build-tagged) implementation of GB 35114-2017 A-level security — SM2-certificate mutual authentication on REGISTER, VKEK negotiation inside the SM2 envelope, keyed-SM3 Note-header integrity, on both device and platform sides.

Single-binary platforms came along for free: PS demux lives inside the library, no external media-server process — and these packages are extracted from MiBeeNvr’s GB28181 ingestion code in the first place, so any other Go project can use them the same way.

onvif-c: the fifth member

The bottom block in the diagrams. Several ESP32 camera firmwares (four board-variant repos) each carried their own ONVIF implementation — duplicated maintenance — so the shared part is now extracted into a plain C component: onvif-c v0.1.0.

It is the most “physical” of the five libraries, and the constraints are written into the design:

  • ~10KB of code, zero third-party dependencies, targeting ESP-IDF. No XML parser: action detection via strstr(), responses assembled with snprintf(), per-request buffers only. The memory model is simple enough to call safely from sensor callback context.
  • The surface is a deliberate minimal-sufficient set: exactly the actions an NVR asks when adding a camera (GetSystemDateAndTime, GetDeviceInformation, GetCapabilities, GetProfiles, GetStreamUri, GetSnapshotUri), plus Pull-Point events on the MotionAlarm topic (State plus a 0-100 Score).
  • PullMessages does not long-poll; it returns immediately — esp_http_server workers never block, a hard constraint of the ESP-IDF threading model.
  • Every board-specific fact lives behind one configuration seam, onvif_c_config_t: manufacturer, model, serial, IP, stream URI, HTTP port, events gate — nothing hardcoded. The firmware-side port layer is about a hundred lines.
  • Byte stability remains the contract, finer-grained than the Rust version: Device/Media envelopes use soap:/tds:/trt:/tt: prefixes (lowercase utf-8 declaration), Events envelopes use s:/tev:/wsnt: (uppercase UTF-8). Both styles coexist because each is what real NVRs actually speak in production — the README says outright: do not “unify” them.
  • The deliberate non-goal is in the Security section: no ONVIF authentication. Any host that can reach the device gets answers; deploy only on fully trusted networks or behind an authenticating reverse proxy. A scope decision for a minimal library, not an oversight.

On quality, tools/onvif_probe.py runs a no-hardware smoke test across every served action plus a full subscription cycle — exit 0 means all green.

Who runs them in production

“Polished by real devices” is not a figure of speech: all five libraries came out of products and still run in them every day.

  • MiBeeNvr: the self-hosted NVR, 7×24 on low-power hardware. Its onvif-go client talks to commercial Hikvision and Axis cameras, and its gb28181-go platform side takes GB28181 device registrations — the platform packages were extracted from exactly that code.
  • The MiBee Eye open camera family: turning Linux boards into ONVIF/GB28181 cameras — mibee-eye-go runs the gb28181-go device side plus the onvif-go virtual camera, mibee-eye-rs runs gb28181-rs plus onvif-device-rs, and both device libraries were extracted from exactly this camera line; mibee-eye-notebook turns a PC’s webcam and microphone into an ONVIF/GB28181 device, with the GB 35114 security feature switched on.
  • Four ESP32 camera firmwares (esp32s3-n16r8-cam, ai-thinker-esp32-cam, seeed-esp32s3-cam, luatos-esp32s3-a10-camera): they carry the onvif-c component in lockstep, and library changes go through real hardware before release.

One production line, one NVR: it talks ONVIF to commercial cameras and GB28181 to self-built firmware at the same time — client, device, and platform roles grinding against each other on the same line. Every interop fix in these libraries started as a problem a real device reported there.

Engineering floor

Everything these libraries parse is untrusted input — SOAP request bodies, discovery Probe datagrams, MANSCDP messages, digest and UsernameToken fields — and the CI of all five repos keeps fuzz or property tests running on every one of those surfaces.

The Go and Rust twins share one set of golden byte tables: cross-language consistency of the media plane and signaling is maintained by assertion, and whoever changes a serialization turns red first — no reliance on the phrase “same design”.

“Real devices before specs” is these libraries’ working principle, and this round gave it a precise division of labor: since v2.1.0, wire-format ground truth is the official WSDL/XSD — real devices feed interop behavior (auth ladder, clock skew, firmware-quirk patches), the specs pin where each element belongs. Two different jobs, no longer conflated.

Status and limitations

  • onvif-go v2.2.0: first stable line. v1 to v2 is mostly an import-path swap; within v2, note v2.1.0’s wire-format corrections before upgrading.
  • onvif-device-rs v0.7.0: capability parity with onvif-go, distributed on crates.io.
  • gb28181-go v0.11.0: device side closed against GB/T 28181-2022; platform side usable, three of four migration batches landed.
  • gb28181-rs v0.12.0: same capabilities as the Go twin; no platform role, by design.
  • onvif-c v0.1.0: no authentication; single event subscription; there is no crates.io for a C component — vendoring into the firmware project is the distribution.
