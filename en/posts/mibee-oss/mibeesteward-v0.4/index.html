MiBeeSteward v0.4.0: Router-Resident Discovery + OpenWrt Deployment + Device-Persistence Rewrite

July 29, 2026 MiBeeOSS Go, OpenWrt, Router, Passive Discovery, Device Discovery, Open Source MiBee Open Source Projects Series 3546 words 17 min read
🔊

When v0.3.0 shipped container images, there was a non-negotiable precondition: the container had to run with --network host to see the full ARP table, otherwise MAC discovery dropped to zero. The root cause was the network namespace — the container couldn’t see the host’s /proc/net/arp packed with 30 rows.

v0.4.0 pushes that constraint to its logical conclusion: what if the discovery program runs on the gateway itself? The gateway is the choke point for all LAN traffic. DHCP leases, the conntrack connection table, hostapd’s wireless clients, dnsmasq’s DNS query log — this data is right there, no need to SNMP-poll a switch, no port scanning, zero extra network traffic. This release lets the center or agent reside directly on the router and taps these four passive sources.

The theme is three things: router-resident discovery, first-class OpenWrt deployment, and a device-persistence rewrite. Full release notes at GitHub Release v0.4.0.

Two Concepts First: ARP and the “Tier-1 Sources”

The rest of this post is all about “how many devices each deployment form can see,” and the root of that visibility is buried in two concepts — the ARP table and the tiers of passive data sources. Nail these two first, and the comparison charts below become self-evident.

The ARP Table: A Device’s “Phonebook”

Devices talk to each other by IP address, but a network card only understands MAC addresses (the card’s physical serial, burned in at the factory, globally unique). How is the contradiction resolved? Through ARP (Address Resolution Protocol) — before a device talks to some IP, it shouts on the LAN, “Who is 192.168.1.5? Tell me your MAC.” The named device answers, and both sides record the “IP ↔ MAC” mapping into a table, so next time they look it up directly instead of shouting again. That table is the ARP table, readable directly from /proc/net/arp on Linux.

Why is this table the lifeline of device discovery? Because it records “who this machine has talked to recently.” In a LAN, the gateway (router) talks to every device, so its ARP table is the most complete — essentially the device roster of the entire LAN. An ordinary host that has only dealt with a few devices has a sparse ARP table.

So which ARP table a process can read determines the range of MACs it can discover — that’s the very root of the four deployment-environment differences below. When a discovery system reads a full ARP table, it’s effectively got hold of the LAN’s phonebook.

Tiers of Passive Sources: Tier-1 vs Tier-2

“Passive discovery” means recognizing devices from data the system already has — without active probing (no port scanning, no SNMP queries). MiBeeSteward splits these data sources into two tiers:

  • Tier-1 (read locally): data the host itself already has — the DHCP lease file, the conntrack connection table, hostapd’s WiFi clients, dnsmasq’s DNS log. Reading them is just reading local files, zero network traffic. The catch: the host itself must be the gateway — only the gateway has dhcp_leases, runs hostapd, logs DNS queries.
  • Tier-2 (fetch across devices): data you ask other devices for — SNMP-polling a switch/router’s ARP table, listening to mDNS / SSDP multicast. More than just the gateway holds an ARP table (switches do too), so Tier-2 has wider applicability — but it costs network traffic and is less real-time than Tier-1 (the ARP table is “communicated recently,” conntrack is “communicating right now”).

This diagram contrasts the trade-off between the two tiers: Tier-1 is precise and real-time but requires the host to be the gateway; Tier-2 has wider applicability but fetches across the network. v0.4.0’s core move is to fill in Tier-1 — once the program runs on the router, all four local sources come online, which is exactly why the router form has the highest fidelity in the environment comparison above.

With these two concepts as a foundation, the four-environment comparison below becomes clear: the entire difference comes down to two things — “how complete an ARP table it can read” and “whether it can turn on the Tier-1 sources.”

Router-Resident Discovery: Four Sources When the Host IS the Gateway

MiBeeSteward’s passive discovery has always had two tiers: Tier-1 is “data the host itself can read locally,” Tier-2 is “data you have to fetch across devices” (SNMP ARP, mDNS/SSDP multicast). v0.2.0’s passive discovery went the Tier-2 route — polling the router’s SNMP ARP table, reading local /proc/net/arp, listening to multicast. v0.4.0 fills in Tier-1, and it only makes sense when the host itself is the gateway.

The four sources each cover a slice of “things only the gateway knows”:

SourceFile / originWhat you see
dhcp_leases/tmp/dhcp.leases etc.Every client the router has handed a lease to
conntrack/proc/net/nf_conntrackConnections active right now — a real-time “who’s online” view
hostapdhostapd client listWhich devices are currently on WiFi
dns_logtailing dnsmasq query logWhat domains a device has queried recently (an identification hint)

conntrack deserves a specific callout. An SNMP ARP table tells you “this device’s IP and MAC communicated recently,” but conntrack tells you “this device is talking to someone right now” — only flows that haven’t timed out in the last 30 seconds remain in the connection table. For the question “is this device actually online,” conntrack is closer to ground truth than the ARP table.

All four sources are opt-in and degrade gracefully. Don’t enable them in config and they aren’t read; enable them but the file is missing (say this router doesn’t run hostapd, it’s a pure wired gateway) and the source disables itself with a logged reason rather than crashing the program. This is the same philosophy as v0.3.0’s no-op stubs for LLDP/CDP raw frames in the unprivileged image — degrade when capability is missing, don’t pretend to run.

Deployment Landscape: What Router, Bare Metal, VM, and Container Each See

MiBeeSteward can run in four environments. The difference isn’t “which is more advanced,” it’s a common root cause: which network namespace the program runs in, and whether that namespace is a member of the LAN broadcast domain. That fact decides how much it can see.

The ARP table and the Tier-1 sources are the two lifelines of passive discovery — the former decides whether MACs can be seen in full, the latter decides whether the gateway’s “currently online / leased / WiFi clients” view is reachable. Active probing (TCP / SNMP / HTTP port scanning) gets out in all four environments, but it only answers “which ports are open on this IP,” not “which MACs exist on this network.” The trade-offs of each environment break down below.

Router (OpenWrt)

The program IS the gateway. All four Tier-1 sources come online — this data already lives locally on the router with zero extra network traffic:

  • dhcp_leases → every client the router has leased to, including dormant devices (they no longer answer ARP, but the lease record persists).
  • conntrack → connections active right now, a real-time “who’s online” snapshot.
  • hostapd → which devices are currently on WiFi (the wireless client list).
  • dns_log → which domains a device has queried recently (fed to the identification engine as a hint).

MAC discovery needs no SNMP polling of switches, because the gateway itself maintains the LAN’s neighbor relationships. Fidelity is the highest, and so is real-time accuracy: conntrack reflects connections active right now, not the ARP table’s “communicated recently.”

The vast majority of gateways in home and small-office networks run OpenWrt — GL.iNet, Xiaomi, Asus routers either ship OpenWrt natively or can be flashed. This is the highest-coverage gateway landing point. But OpenWrt isn’t ordinary Linux: flash is tiny (16 / 32MB, not enough for a Go binary’s dependency chain), the init system is procd rather than systemd, services default to UCI config and run unprivileged, and the CPU is ARMv7 / MIPS. v0.4.0 adapts to each — the procd init scripts (deploy/openwrt/mibee-steward.init and mibee-agent.init) are UCI-configured services that start on boot, restart on crash, and run unprivileged; a new ARMv7 build target covers low-power routers, with the init scripts deduped so center and agent share a single target. The cost is tight router resources, but it buys the highest-fidelity gateway’s-eye view.

Bare-Metal Host

The program runs on bare-metal Linux as a member of the LAN. What’s visible and what isn’t:

  • ✅ Full ARP table — the host’s /proc/net/arp, the neighbor table the host has accumulated from talking to other devices on the LAN. As long as this machine has normal traffic with the LAN, the table is full; on the test LAN it measured 31 / 31.
  • ✅ Raw frames / eBPF — LLDP / CDP raw-frame transmission and eBPF passive observation all work (regular user or root with the appropriate capabilities).
  • ✅ All active probing — port scanning, SNMP, TLS cert collection all available.
  • ❌ Tier-1 sources — this machine isn’t the gateway, so there’s no dhcp_leases / conntrack / hostapd / dns_log to read.

This is the highest fidelity among non-gateway forms. Managed via systemd unit, available since v0.1.0. It has one shortcoming: dormant devices (the ones that don’t answer ARP) can’t be seen in full — but that’s a limitation shared by every non-gateway form; only the router’s dhcp_leases catches them.

Virtual Machine

A VM’s fidelity depends entirely on its NIC mode, and the root cause is still the network namespace. One table captures the visibility difference between the two modes:

NIC modeARP tableCan seeCannot see
Bridgedfullthe entire LAN’s neighbors—
NATvirtual gateway onlythe host, the virtual gatewayall other hosts on the LAN
  • Bridged NIC: the VM’s virtual NIC bridges directly onto the physical LAN, joining the same broadcast domain — equivalent to a bare-metal host. It reads the full ARP table; fidelity ≈ bare metal.
  • NAT NIC: the VM has its own isolated network, with traffic NAT’d through the host — equivalent to a Docker bridge container. The VM only sees the virtual gateway; the rest of the LAN is invisible, and MAC discovery degrades.

This is the easiest thing to trip over on a VM: the same VM, with the NIC switched from bridged to NAT, can drop from “full strength” to “near zero.” libvirt / KVM defaults frequently give you NAT, and VirtualBox’s host-only + NAT combo works the same way. If discovery results look wrong inside a VM, the first thing to check is the NIC mode, not the program.

Container

The most finely subdivided form. v0.3.0 shipped three compose profiles specifically for it, and the root cause is still the netns. The ARP tables the three profiles can read differ by an order of magnitude:

ProfileARP table it can readDiscovery fidelity
bridge (default)only the docker0 gateway entry0 / 26, MAC discovery goes to zero
host (recommended)the host’s full ARP table30 / 31, ≈ bare metal
macvlanthe container’s own ARP as a LAN devicefull; talks directly to the LAN

bridge is the easiest to misuse: it’s the docker default and thus most convenient, but the container sits in an isolated netns where TCP / SNMP / HTTP active probes can get out, while /proc/net/arp only reads the docker0 gateway entry. So host is the only choice for production scanning.

Containers add a second dimension: privilege. The official image on GHCR is an unprivileged variant, where LLDP / CDP raw frames + eBPF ship as no-op stubs (they need CAP_NET_RAW / CAP_BPF / CAP_NET_ADMIN). If you need them, build a privileged variant locally with make docker-build-priv. The good news is that active probes — Bridge-MIB / Q-BRIDGE / CDP / STP / TLS / port scanning — don’t depend on raw sockets at all, so a plain host-networked container already finds the vast majority of devices.

How to Choose

  • A flashable OpenWrt router at home → install the agent on the router; gateway’s-eye view, highest fidelity, zero extra traffic.
  • An always-on Linux physical machine (home server, workstation) → bare metal with systemd, ≈ bare-metal fidelity.
  • Only a VM → make sure the NIC is bridged; under NAT, discovery is largely dead.
  • Just want to try it quickly → docker with host networking; never run production scanning on the default bridge.

In one line: settle the netns membership first, then talk about discovery fidelity. Same program, same config — change the deployment form and the results can differ wildly. The entire difference comes down to which ARP table it can read.

Device-Persistence Rewrite: Closing the Dual-Write Fissure

This is the lowest-level and most easily overlooked change in this release, but it fixes a long-standing correctness problem.

The Problem: Two Independent Write Paths

Before v0.4.0, a device row (one row in the devices table) had two independent write paths with inconsistent semantics:

mermaid
flowchart TD
    SYNC["Synchronous scan path"] -->|"writes devices"| ROW["device row"]
    SCHED["Scheduled scan path"] -->|"writes devices<br/>different semantics"| ROW
    ROW --> BAD["Same row overwritten by two paths<br/>with different semantics<br/>→ inconsistency"]

    classDef src fill:#E3F2FD,stroke:#1565C0,color:#1565C0
    classDef bad fill:#FFEBEE,stroke:#C62828,color:#B71C1C
    class SYNC,SCHED src
    class ROW,BAD bad

A synchronous scan (the user clicking “scan now” in the UI) and a scheduled scan (triggered by cron) ought to be the same operation, but each path maintained its own device-writing logic. The timing of field updates, null handling, and the pacing of the state machine all differed. The result: the same device could end up with inconsistent rows depending on which path wrote last — a bug that’s extremely hard to reproduce because it depends on which path wins the race.

The Fix: A Single Write Authority

v0.4.0’s approach is to establish a single device writer. runner.applyDeviceBridge becomes the sole authority for the device row’s lifecycle — all writes funnel through this one entry point:

mermaid
flowchart TD
    SYNC["Synchronous scan"] --> BRIDGE["runner.applyDeviceBridge<br/>sole write authority"]
    SCHED["Scheduled scan"] --> BRIDGE
    BRIDGE --> ROW["device row<br/>both paths leave identical rows"]

    classDef src fill:#E3F2FD,stroke:#1565C0,color:#1565C0
    classDef proc fill:#FFF3E0,stroke:#E65100,color:#BF360C
    classDef ok fill:#E8F5E9,stroke:#2E7D32,color:#1B5E20
    class SYNC,SCHED src
    class BRIDGE proc
    class ROW ok

After the change, synchronous and scheduled scans leave byte-identical rows — same input, same output. This isn’t a performance optimization, it’s a correctness fix: it eliminates the “whoever writes last wins” indeterminism between the two paths.

Device-Replacement Detection

A related problem is device replacement. A router gets swapped, a camera gets swapped, but the MAC stays the same (say you reflashed the firmware) — the IP changed but the identity fields (vendor, model) are stale. v0.4.0’s rule: when the MAC matches but the IP differs, the IP-holder wins and its identity fields are force-overwritten. This prevents dirty data where “the device was replaced but the portrait is stuck on the old values.”

Silent-Failure Fix

The router_arp and multicast Tier-2 sources had a subtle problem in v0.3.0: when a file was missing or permissions were insufficient, they failed silently — no error, no log, just a gap in the result set, and you had no idea they weren’t working. v0.4.0 changes them to disable themselves with a logged reason, the same graceful-degradation treatment as the Tier-1 sources above.

Network Reconciliation: Flagging IP Drift

This is a background job that pairs with router-resident discovery.

DHCP renewal, a device waking from sleep and re-onlining, a manual IP change — all cause a device’s IP to drift. If it drifts outside its registered network block, the configuration and reality no longer agree: you registered a device on 192.168.1.0/24, but it now shows up on 192.168.2.0/24 — either the device physically moved, or the network config is wrong.

The reconciliation job scans in the background, surfaces devices whose IP has drifted outside their block, and flags them for human correction rather than auto-fixing. This is a deliberate trade-off: auto-migrating an IP easily conflates “the device actually moved” with “the config is wrong,” which masks the real problem. Let it bubble up to a human, and the human decides.

Configurability

Detection thresholds and heartbeat cadence used to be hardcoded — tuning them meant editing code. v0.4.0 lifts several key parameters to config + environment variables:

ParameterMeaning
scanner.lost_thresholdHow many consecutive failed probes before a device is judged “lost”
heartbeat.tick_interval_secondsHeartbeat polling interval
heartbeat.offline_thresholdHow many consecutive missed heartbeats before offline
heartbeat.offline_backoff_ticksBackoff cadence after going offline

Each supports a MIBEE_* environment-variable override; passing 0 means use the default. The env-var override is handy for container deploys — you can tune with docker run -e instead of editing a config file.

UI and Frontend Hardening

This release moves a fair amount of frontend. The substantive ones:

  • Sidebar regrouped. Topology is merged into the Devices page instead of occupying its own entry — topology is a dimension of the device view anyway, and splitting it into a standalone page was fragmentary.
  • Search / sort / pagination all moved server-side. Previously the front end pulled everything and filtered locally, which choked once data grew; now the server handles it, and result sets don’t get lost no matter how large.
  • DataTable XSS fix. Values are escaped via an html() helper, closing an injection point in table rendering.
  • Zod schema validation added to seven forms. The front end validates before submitting, cutting down invalid requests.

On device types, phone and printer were added, driven entirely by YAML data files — adding a device type is now just adding a YAML entry, the same data-driven path as v0.2.0’s fingerprint library.

Rate-Limit Adjustment

The global rate limit was raised from 100 to 600 (rate_limit.global_per_minute). The reason: after v0.3.0, multi-tab sessions and background polling competed for the same quota — opening a few tabs ate the limit and blocked legitimate scan requests. At 600, multi-tab sessions work normally; SPA static assets are also exempted and don’t count against the limit.

Upgrade

center / agent are both drop-in upgrades — just replace the binary. The Docker path is docker pull of the new tag and restart.

Known Limitations

A few that carry over from v0.3.0 unchanged in v0.4.0:

  • Single-instance SQLite — center is still single-instance, no cluster. Not planned until scale demands it.

The v0.4.0 throughline is clear: the discovery system goes from “a probe running on the side” to “an insider running on the gateway.” Once the host is the traffic choke point, data you used to fetch across devices — DHCP leases, conntrack, hostapd, DNS logs — becomes local file reads: zero extra network traffic, and higher real-time fidelity to boot. If you have an OpenWrt-flashable router, install the agent and try router-resident mode — that “gateway’s-eye view” of discovery completeness is something ordinary deployment forms can’t match.
