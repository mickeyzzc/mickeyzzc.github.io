onvif-c Tutorial: Adding an ONVIF Device to Your ESP32 Firmware

October 3, 2026 MiBeeOSS C, ONVIF, ESP32, IP Cameras, Open Source MiBee Open Source Projects Series 2259 words 11 min read
🔊

onvif-c is the most “physical” of the five protocol libraries: a plain C ONVIF device component for ESP-IDF with a footprint around 10KB and zero third-party dependencies. When an ESP32 camera firmware needs to be discovered by an NVR, answer device-information queries, hand out stream URIs, and report motion events — this one component covers it. There is no XML parser inside: action recognition is strstr(), responses are assembled with snprintf(), and the memory model is simple enough to call safely from sensor callback context. The four MiBee camera firmware repos carry it in lockstep, and library changes go through real hardware before release.

The client side does not use this component: for connecting to cameras use onvif-go or onvif-device-rs. This post is all about the device side.

The component itself requires esp_http_server, lwip, and esp_hw_support. Both ESP-IDF v5.5 and v6.0 are supported (CI builds both). Optional mDNS is handled specially: since IDF v5.x mdns is a managed component, so if your project declares espressif/mdns the support compiles in (advertising _onvif._tcp), and if it doesn’t, it compiles out cleanly — no code changes either way.

#include "onvif_c.h"
#include "esp_http_server.h"

static httpd_handle_t s_httpd;

static const char *my_ip(void)
{
    static char         ip[16] = "0.0.0.0";
    esp_netif_ip_info_t info;
    esp_netif_t        *sta = esp_netif_get_handle_from_ifkey("WIFI_STA_DEF");
    if (sta && esp_netif_get_ip_info(sta, &info) == ESP_OK) {
        snprintf(ip, sizeof(ip), IPSTR, IP2STR(&info.ip));
    }
    return ip;
}

static const char *my_stream_uri(void)
{
    static char uri[64];
    snprintf(uri, sizeof(uri), "http://%s:81/stream", my_ip());
    return uri;
}

static bool my_events_gate(void)
{
    return true;
}

void app_main(void)
{
    /* ... start WiFi and esp_http_server first (s_httpd = ...) ... */

    const onvif_c_config_t cfg = {
        .manufacturer     = "MiBee",
        .model            = "MiBeeCam",
        .hardware_id      = "ESP32-S3",
        .firmware_version = "v0.1.0",
        .serial           = "aabbccddeeff",
        .uuid             = "f472b01e-0000-1000-8000-aabbccddeeff",
        .ip               = my_ip,
        .stream_uri       = my_stream_uri,
        .events_enabled   = my_events_gate,
        .mdns_hostname    = "mibeecam-demo",
    };
    onvif_c_start(s_httpd, &cfg);
}

Walking through it:

  • onvif_c_start hangs the routes onto the existing httpd (/onvif/device_service, /onvif/media_service, plus /onvif/events_service when events are on) and starts the WS-Discovery task. It requires the httpd to have gone through httpd_start already.
  • Four callbacks are mandatory — serial, uuid, ip, stream_uri; miss any one and onvif_c_start returns ESP_ERR_INVALID_ARG. The ip callback may return NULL or "0.0.0.0" while WiFi is down; the services retry on their own, no notification needed.
  • Strings are taken by reference, not copied — the header says “must outlive onvif_c_start”. Use static buffers or literals as in the example, never stack temporaries.
  • uuid carries no urn:uuid: prefix; it doubles as the WS-Discovery device UUID, and NVRs remember devices by it — pinning one beats regenerating on every boot.
  • All board differences collapse into this one struct: manufacturer, model, IP, stream URI, HTTP port, events gate — zero hardcoding in the library.

The Port Layer: Writing serial and uuid for Real

#include "esp_mac.h"

static char s_serial[13];
static char s_uuid[37];

static const char *my_serial(void)
{
    if (s_serial[0] == '\0') {
        uint8_t mac[6] = {0};
        esp_read_mac(mac, ESP_MAC_WIFI_STA);
        snprintf(s_serial, sizeof(s_serial), "%02x%02x%02x%02x%02x%02x",
                 mac[0], mac[1], mac[2], mac[3], mac[4], mac[5]);
    }
    return s_serial;
}

static const char *my_uuid(void)
{
    if (s_uuid[0] == '\0') {
        uint8_t mac[6] = {0};
        esp_read_mac(mac, ESP_MAC_WIFI_STA);
        // deterministically derived from the MAC; the point is "same on every boot"
        snprintf(s_uuid, sizeof(s_uuid),
                 "f472b01e-0000-1000-8000-%02x%02x%02x%02x%02x%02x",
                 mac[0], mac[1], mac[2], mac[3], mac[4], mac[5]);
    }
    return s_uuid;
}

The stream-URI callback follows your actual service — return rtsp://<ip>:554/stream for an RTSP firmware, or http://<ip>:81/stream for MJPEG over HTTP. The reference port layer is main/onvif_port.c in the esp32s3-n16r8-cam firmware, about a hundred lines: identity from MAC/efuse, IP from the WiFi manager, the stream URI from the RTSP server, and an events gate reading configuration.

Where the Library Sits

    NVR -->|"UDP 3702"| DISC["Discovery task<br/>Probe / Hello"]

    DISC --> LIB
    LIB -->|"callbacks"| FW["Firmware port layer<br/>~100 lines"]

    classDef nvr fill:#E3F2FD,stroke:#1565C0,color:#1565C0
    classDef lib fill:#F3E5F5,stroke:#9C27B0,color:#6A1B9A
    classDef fw fill:#E8F5E9,stroke:#2E7D32,color:#1B5E20

    class HTTPD,DISC,LIB lib
    class FW fw

The NVR enters through two doors: WS-Discovery on UDP 3702 (answering Probes, sending Hello every ~30 seconds) and SOAP actions over HTTP. The library recognizes the action with strstr(), pulls live values through port-layer callbacks (IP, stream URI), assembles the response with snprintf(), and hands it back to esp_http_server. Per-request buffers only, no dynamic state.

Events: One-Line Injection

Reporting a motion event is one function:

c
1

onvif_c_motion(true, 87);   /* MotionAlarm State=true  Score=87 */

Call it directly from sensor or CSI callback context — it never blocks (lock contention drops the event) and does no I/O; the event is queued only while “a live Pull-Point subscription exists AND the events_enabled gate returns true.” Calling it with no subscribers is a no-op. Inside a detection task:

 1

void motion_task(void *arg)
{
    for (;;) {
        if (read_pir_or_motion_detector()) {
            onvif_c_motion(true, 87);          /* replace 87 with your own score */
        } else {
            onvif_c_motion(false, 0);          /* report recovery too, so the NVR can clear */
        }
        vTaskDelay(pdMS_TO_TICKS(1000));
    }
}

The subscription model has three values to know: a single subscription where a new one replaces the old (two NVRs subscribing to the same camera will bump each other); one hour granted termination with 120-second idle expiry, renewed by the NVR’s Renew; and PullMessages that returns immediately without long-polling — esp_http_server workers must never block, a hard constraint of the IDF threading model rather than laziness. The onvif_c_events_subscribed() diagnostic tells you whether a subscription is alive, which doubles as a “is anyone watching” signal (skip expensive detection when nobody subscribes).

Discovery and the Watchdog

The WS-Discovery responder answers Probes on UDP 3702 multicast and sends periodic Hellos, retrying through socket and multicast-membership failures until WiFi is up. wdt_watch_discovery is opt-in: it subscribes the discovery task to esp_task_wdt — the loop paces itself with a 5-second receive timeout, so a wedged task stops feeding the watchdog and it fires. Initialize the watchdog in the host project, then flip the flag:

    .trigger_panic = true,
};
ESP_ERROR_CHECK(esp_task_wdt_init(&wdt_cfg)); // explicitly initialized since ESP-IDF v5.x

const onvif_c_config_t cfg = {
    /* ... */
    .wdt_watch_discovery = true,
};

With mDNS enabled (the project declares espressif/mdns), mdns_hostname gives the camera a _onvif._tcp local-discovery path on top, and mdns_instance defaults to the model.

Acceptance: onvif_probe.py

Acceptance testing needs no NVR: tools/onvif_probe.py runs the full smoke test from a laptop.

console
1

python tools/onvif_probe.py 192.168.1.123 15

It exercises all six actions (GetSystemDateAndTime / GetDeviceInformation / GetCapabilities / GetProfiles / GetStreamUri / GetSnapshotUri), then a complete event subscription cycle (CreatePullPointSubscription → PullMessages loop → Renew → Unsubscribe), prints human-readable progress lines, and ends with a machine-readable JSON line:

json
1
2

{"ip": "192.168.1.123", "checks": {"GetSystemDateAndTime": true, "...": true},
 "pulls": 15, "errors": [], "events": 0, "all_required": true}

Exit 0 means every required action answered; exit 2 means creation or the first call failed. A missing events service does not fail the run (matching firmware with events disabled). Wire it into CI or production testing to verify the ONVIF surface automatically after every flash.

Memory and Threading Model

Why onvif_c_motion is safe from a sensor callback: no dynamic allocation inside the component, no held locks across threads — the three core files (XML responses, Probe answering, the event ring) are pure C with no ESP-IDF dependency and use per-request buffers that are returned when done; the esp_idf/ layer only hangs the SOAP handlers on esp_http_server and runs discovery as its own task. That is also why it serves multiple NVRs polling at once without jitter: every request assembles its own packet and shares no state.

The two namespace-prefix dialects are deliberate: Device/Media envelopes use soap:/tds:/trt:/tt: (a lowercase utf-8 declaration), Events envelopes use s:/tev:/wsnt: (uppercase UTF-8) — each style is the field-proven bytes real NVRs talk. When an integrator asks, the answer is in the README: do not “unify” them.

How Production Projects Use It

The component was born in production: extracted from the MiBee Cam firmware and vendored by four ESP32 camera firmware repos in lockstep, with library changes passing real hardware before release. For acceptance, any commercial NVR or ONVIF Device Manager works as the consumer. Feature by feature:

FeatureProduction projectHow it’s used
Base integration / vendoringesp32s3-n16r8-cam · seeed-esp32s3-cam · luatos-esp32s3-a10-camera · ai-thinker-esp32-camAll four board firmwares carry it; it answers the entire ONVIF surface an NVR needs from an ESP32 camera
The port layeresp32s3-n16r8-cammain/onvif_port.c, the ~100-line reference implementation: identity from MAC/efuse, IP from the WiFi manager, stream URI from the RTSP server, a config-backed gate

Start reading from esp32s3-n16r8-cam — the best-endowed board (ESP32-S3 plus OV3660), and its onvif_port.c is where this post’s port-layer section came from. The other three repos show the same component under different constraints: ai-thinker-esp32-cam is the tightest-resource version on the classic ESP32 with OV2640, seeed-esp32s3-cam adds G.711 audio to its RTSP, and luatos-esp32s3-a10-camera runs on a PSRAM-less single chip. One component ported four ways under four constraints is itself the evidence that the config seam is clean.
