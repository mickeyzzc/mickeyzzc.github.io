Where Should MiBeeSteward Live: Soft Router, Host, or Center+Agent — Tested

September 18, 2026 September 18, 2026 MiBeeOSS Go, OpenWrt, Soft Router, Passive Discovery, Device Discovery, Open Source MiBee Open Source Projects Series 1710 words 9 min read
🔊

MiBeeSteward (GitHub, AGPLv3, single Go binary) does device-layer discovery, identification, and asset registry. It supports three deployment shapes: directly on a soft router, on an ordinary host in the network, or — for multi-subnet networks — one center with several lightweight agents. How do the shapes differ in scanning capability, passive-discovery visibility, and resource cost? This post is a controlled comparison on a single network.

Conclusions

  • Active scanning and identification: no difference across shapes. Same version, same parameters — the alive set and duration align to the millisecond, type verdicts agree 100%. Identification quality tracks the fingerprint-material version, not the install location.
  • Passive discovery: the soft-router shape wins, because of where it sits. Only the gateway has the DHCP lease table and the conntrack connection table; the host shape covers most active devices through recursive ARP expansion and mDNS/SSDP multicast listening, but those two sources are physically out of reach.
  • Cross-subnet: the distributed shape puts one collector per subnet with subnet membership correct by construction; a dual-arm soft router also sees both subnets from one box, but passive discovery currently does not filter by subnet membership — devices from both segments mix into one list.
  • Resources: center steady state 110–165 MB, full-scan peak ≈ steady state +50 MB; a 512MB router cannot hold it.

Test environment

A home network with two /24 subnets: the primary one holds thirty-odd everyday devices (phones, laptops, cameras, Mi Home gear, dev boards); the second, quieter one holds a NAS and a few always-on hosts. A dual-arm RK3568 (4GB) soft router interconnects the two subnets and plays the “soft-router shape”; a 4GB ARM host (Armbian) in the second subnet plays the “host shape” and doubles as the distributed shape’s center; an armv7 dev board in the primary subnet runs the distributed shape’s agent. Text and screenshots are sanitized (documentation IP ranges, generic device names).

Method

  • One source tree, one version, built twice: the OpenWrt ipk on the soft router, the bare binary under systemd on the host; both ARM64.
  • Databases wiped; accumulation starts from zero.
  • Each shape enables the passive sources it can: DHCP lease table and conntrack on the soft router; ARP cache, multicast listening, and SNMP polling of the gateway’s ARP table on the host. No artificial leveling — each shape runs as it naturally would.
  • Identical scan parameters (full pipeline, /24, 50 concurrency), triggered in the same second on both sides.
  • Order: 8 minutes of passive observation (no scans) → full scan → memory sampling.

The gap comes entirely from the sources.

The router’s 42 stack three signals: the DHCP lease table records every device that ever took an address, including dormant IoT devices that answer no active probe at all — cloud-bound Mi Home devices close every local credential-free channel (no mDNS replies, common TCP ports closed), but the DHCP handshake must happen, and lease hostnames (viomi-waterheater-xxx, chuangmi-camera-xxx) plus the hostname fingerprint material file them with brand attached. conntrack provides the live connection table — whoever is talking is right there. The ARP cache, paired with an identification scan triggered per new IP, means devices enter the ledger named and typed, never as bare IPs.

The host’s 34 rest on two mechanisms: each newly discovered IP triggers an identification scan, and the scan traffic makes the peer’s ARP entry flow back into the local cache, so the set of “already-communicated IPs” expands recursively; add the mDNS/SSDP self-advertisements any host on the L2 network can hear (the NAS’s avahi service set, DLNA SERVER headers). The host shape’s passive discovery is adequate, and its ceiling is just as clear: the lease table and the connection table are a function of position.

Active scanning: 107.667 s vs. 107.640 s

MetricSoft routerHost
Full scan duration107.667 s107.640 s
Liveness verdicts3535

Twenty-seven milliseconds apart — scheduler noise; liveness verdicts identical. Scanning behavior is platform-independent — duration is decided by the probe-timeout structure, and the two machines’ CPU difference shows up nowhere. Identification aligns too: on the 35 shared devices, type verdicts agree 100% (same fingerprint material, same evidence). The only difference was one NAS’s software brand — the host happened to hear its SSDP SERVER header (MiniDLNA/1.3.3), an accident of passive evidence’s timing window.

The devices banked during the passive phase merge cleanly into the scan results: the host’s 34 were all re-covered, with no blind spots of their own; 7 of the router’s 42 were unreachable by scanning — all devices from the other subnet, visible through conntrack’s view of cross-subnet traffic. That is a capability the soft-router shape carries with it: as the inter-subnet router, forwarding-table entries for cross-subnet traffic are laid out in front of it.

The distributed shape: center + agent

The center (~24MB, embedded Web UI) keeps the ledger; the agent (~18MB bare binary) is deployed per subnet, started by systemd, configured with the center’s address and a token. The agent scans its segment with the exact same pipeline as the center: this round measured ~110 s per /24 — aligned with the two ARM64 machines’ 107.6 s. Different instruction set, same scanning behavior.

Reporting is a pull model: the agent only initiates outbound HTTPS and polls the command channel about every 60 seconds — no inbound ports on either side, and an agent behind NAT works as usual. Each report carries a state hash; when the network is unchanged, the center takes the fast path and only renews leases instead of merging per device. Device identity is keyed by MAC — the same device discovered on any subnet is one and the same asset.

The last row is the distributed shape’s key deployment constraint: the center runs no heartbeat probes against the agent’s network — liveness comes from leases refreshed by scan reports, and leases have a deadline. The agent’s scan interval must therefore be shorter than the lease TTL — the current version uses a 15-minute lease with the agent scanning every 5 minutes by default, leaving a two-round margin. Factor this in when adjusting scan intervals, or devices will be marked offline between rounds.

Measured memory

RK3568 soft router (4GB)center~164 MB187 MBfine
ARM host (4GB)center~112 MB175 MBfine
MT7981 travel router (512MB)center——OOM, would not install
Same deviceagent—OOM at 103 MB during initsame

Identical peaks — the same scan working set. The ~50MB steady-state gap is the router side’s passive-source caches (lease tracking, connection tracking, per-IP observation cache). For /24-scale networks, “full-scan peak ≈ steady state +50 MB” works as a capacity-planning rule of thumb.

The verdict for 512MB devices is simply that it does not fit: on an MT7981 travel router with 512MB (stock firmware, ~90MB usable in normal operation), the process needs 90–100MB just to load the fingerprint library and identification engine — both center and agent hit OOM. The install script ships a low-memory profile for such cases (SQLite page cache 64→8MB, concurrency halved, a Go soft memory limit), and startup runs a free-memory preflight that refuses to start when short. Let a 512MB box keep being a router.

Recommendations

  • Single-subnet home network: one soft router with memory to spare (≥1GB) doing everything — the most complete passive view, with the DHCP lease table and conntrack in hand.
  • Multiple subnets or growing scale: the center on an always-on host keeping the ledger, one agent per remote subnet. Each segment gets its own collector, subnet membership correct by construction; the agent can also run on that segment’s router (OpenWrt form B), reading the same DHCP leases and conntrack — effectively replicating the soft-router shape’s passive advantage on every segment.
  • One dual-arm router covering two subnets: workable and saves a device, but note that passive discovery is not yet filtered by subnet membership — devices from both segments mix into one list.
  • 512MB little boxes: cannot hold it; let them route.

The project is open source on GitHub (AGPLv3): repository and releases (single-file Linux amd64/arm64 binaries, OpenWrt ipk/apk packages) — install and you get exactly the interface in the screenshots. The fingerprint material is plain data files; add a rule following the fingerprint spec if one of your devices goes unrecognized. Deployment questions are welcome in Discussions.
