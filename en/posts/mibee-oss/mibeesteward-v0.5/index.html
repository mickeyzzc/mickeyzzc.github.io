MiBeeSteward v0.5.0: SNMPv3 + Multi-Role RBAC + Device Config Backup

August 20, 2026 MiBeeOSS Go, SNMP, RBAC, Config Backup, Network Management, Open Source MiBee Open Source Projects Series 3132 words 15 min read
🔊

Across the four releases from v0.1.0 to v0.4.0, MiBeeSteward assembled a complete internal-network device-management pipeline: active scanning and fingerprint identification handle discovery and classification; the agent and passive sources introduced in v0.2.0 (SNMP ARP, mDNS/SSDP multicast listening) extended discovery across multiple LANs, and v0.4.0 went further by letting the center and agent reside on the router, reading DHCP leases, conntrack, hostapd clients, and DNS query logs directly; heartbeat probing maintains online status while change detection emits device-added/changed/lost events; LLDP, CDP, and Bridge-MIB data feeds the L2 topology; TLS certificates of internal HTTPS services are collected as well. Deployment targets cover physical machines, VMs, containers, and OpenWrt routers.

The boundary of this capability set is the internal network, and the assumed environment is personal or small-team use. v0.5.0 extends along two directions: first, adaptation to stricter environments — SNMP moving to v3, a multi-role permission model, and device config backup, corresponding to the three realities of enterprise networks where v2c is disabled, the system is shared by multiple people, and config changes are subject to audit; second, extending the probing range beyond the internal network with synthetic probing of external endpoints.

SNMPv3 Support

MiBeeSteward relies on SNMP to collect device identity and topology data from switches and routers; before this release it supported v1 and v2c. v2c authenticates with a cleartext community string that travels unencrypted on the wire — one packet capture exposes it. It fails most corporate security baselines, and a significant share of hardened environments disable it outright. In such networks MiBeeSteward’s SNMP collection was entirely unusable — one of the main blockers to enterprise adoption.

v0.5.0 adds SNMPv3 support (USM model, both authNoPriv and authPriv security levels); device identity collection and all topology walks work fully under v3. SNMP credentials are stored encrypted with AES-256-GCM, and the admin UI never echoes passphrases.

v1 / v2c (before)v3 (v0.5.0)
AuthenticationCleartext communityUSM user + auth protocol (MD5 / SHA / SHA-2)
TransportCleartextEncrypted at the authPriv level (AES / DES)
Credential handlingCommunity distributed via configEncrypted at rest, redacted on read
Hardened environmentsUsually disabledWorks normally

Two boundaries: existing v1/v2c deployments behave identically after upgrading — no extra configuration is needed until the first v3 credential is created; and agent-side v3 support is deferred (credential distribution and rotation in a distributed deployment needs its own design), so agents keep v1/v2c.

Multi-Role Permissions and Network Scoping

The previous permission model had only two tiers, admin and user, where user could see every network and device. Fine for a single person; two defects appear once the system is shared: there is no distinction between “may operate” and “read-only”, and there is no way to restrict a user’s data visibility. On-call staff only need to view status; in branch-office or managed-service-provider scenarios each party should see only its own networks.

v0.5.0 rebuilds the model as three roles plus object-level scoping:

  • Roles: admin (full permissions), operator (may run scans and device operations, cannot manage users or permissions), viewer (read-only). Existing user accounts keep working as viewers after the upgrade — no data migration.
  • Network grants: an admin assigns each non-admin user the set of networks they may see.
  • Scope mode rbac.scope_default defaults to open — non-admins see every network, identical to the old behavior. Set to closed, a non-admin sees only granted networks; unauthorized resources return 404 rather than “access denied”, so the existence of a resource is not leaked.

Device Config Backup

The first question in a network post-mortem is usually “when was the config changed, and by whom”. MiBeeSteward could not answer it before: it records device state, but never collected the devices’ own running configurations.

v0.5.0 adds config backup: on a schedule it logs into routers, switches, and firewalls over SSH, pulls the running-config, and stores it in versioned form. Unchanged content does not create a new version; a change records a new version and emits a device_config_changed event, which enters change detection and notification-rule processing. The device detail page provides the config history and a diff between any two versions — config changes are now traceable.

The feature is off by default (scanner.config_backup.enabled); enabling it requires a master key and an SSH credential bound to the device. The real-router end-to-end verification (GL-MT3000) is deferred to the next release; the code path is complete and verified at the API level.

Built-In Event Notification

Before this release, obtaining “send a notification when a device goes offline” meant deploying Prometheus and Alertmanager on the side — maintaining two monitoring systems for one notification is disproportionate to the need.

v0.5.0 ships a built-in notification rule engine: rules are configured by event type (lost, recovered, added, changed, config changed), scope (all, one network, one device), and target channel (webhook, email); matched events are delivered through the existing notification dispatcher. Each rule carries an independent cooldown window per device, so a device with a flapping connection does not raise repeated alerts. Its position is event routing, not an alerting engine: no thresholds, silences, or routing trees — when those are needed, the Prometheus stack remains the answer.

External Synthetic Probing

Discovery and monitoring previously stopped at the internal network. v0.5.0 adds a probing module that periodically tests explicitly configured external endpoints: the http / tcp / icmp modules check availability, while the tls module — and https targets — collect the full certificate chain: expiry, issuer, trust verdict, TLS version, and cipher suite. The internal TLS certificate inventory capability thus extends to public hostnames: availability of your own sites, the mail server’s TLS port, and certificate expiry can all join the same monitoring and alerting.

That covers the functional changes. The sections below record implementation details and internal improvements by topic, for consulting during deployment and for locating code when reading the source.

SNMPv3 Implementation Details

  • Encrypted credential vault: the new snmp_credentials table stores USM credentials (user, auth/priv passphrase + protocol, security level), encrypted at rest with AES-256-GCM, keyed by security.master_key (exactly 32 bytes, overridable via MIBEE_SECURITY_MASTER_KEY).
  • Probe side: the SNMP probe’s version loop gains Version3; authNoPriv (MD5/SHA/SHA-2) and authPriv (+ AES/DES) credentials are tried per target. The 8-OID identity collection and the LLDP-MIB / CDP-MIB / Bridge-MIB / Q-BRIDGE-MIB / STP-MIB / IF-MIB topology walks all work under v3.
  • API & UI: credential CRUD encrypts on write and redacts on read — passphrases never echo back; scan forms and device pages carry v3 options with a security-level dropdown.

RBAC Implementation

The one-size-fits-all RequireAdmin middleware is replaced by a capability graph plus object-level grants:

  • Every route is gated by a capability (CapDeviceRead, CapScanTrigger, CapDeviceWrite, …); roles map to capability sets, admin inherits everything. The users.role CHECK widened; the old user value remains a legacy alias for viewer.
  • Network grants land in the user_network_grants table, with admin APIs (/api/v1/users/{id}/network-grants, /api/v1/networks/{id}/grants) and a users-page UI.
  • Closed-mode scoping covers the entire read surface: device lists and detail, scanner tasks/runs/results, changes, and topology are filtered uniformly; the scanner side is object-scoped as well — scan_tasks.network_id stamps each task’s owning network, and non-admins only see and trigger tasks within their own networks.
  • Fail-safe: an unrecognized rbac.scope_default value falls back to open, so a typo in the config file cannot instantly blind every non-admin.

Config Backup Implementation

Flow explanation: the scheduled sweep picks router/switch/firewall devices with bound credentials, pulls the running-config over SSH, and hashes it — identical content gets discarded; only a change lands a new version and emits device_config_changed. Every row in the version list is a genuine change, with no duplicate snapshots.

  • Vendor command matrix: JunOS uses show configuration | display set; HP / Aruba / H3C / Comware use display current-configuration; Cisco IOS/NX-OS, Arista, Huawei VRP, Mikrotik, and unknown vendors fall back to show running-config. Host keys are recorded via TOFU (trust-on-first-use).
  • Storage & read side: versions land in device_configs (versioned per device_uuid); the read APIs are GET /devices/{id}/configs for the list and /diff?a=&b= for a two-version compare; the device detail’s Config History tab renders hand-colored unified diffs.
  • SSH credentials share the same AES-256-GCM master-key cipher as SNMPv3 — encrypt on write, redact on read.

Notifier Rule Model

The rule engine subscribes to the change-detection Watcher and routes matched events through the existing dispatcher (webhook/email channels, 3 workers, per-user read state). The rule model is a single notification_rules table:

  • Event types: device_lost / device_recovered / device_added / device_changed / device_config_changed
  • Scope: all / one network / one device by UUID
  • Target channel and enable toggle
  • cooldown_minutes (default 30) per (rule × device), layered on top of the change detector’s own liveness cooldown — two windows of flap suppression.

Probing Implementation

  • http / tcp / icmp reuse the heartbeat probers; tls (and https targets) call CollectCertChain for the full chain, with SNI auto-derived.
  • The engine re-reads enabled targets on a 10s tick, so CRUD applies without restart; next-due times resume from last_run_at after a restart (no startup storm); a global 8-probe concurrency bound; scheduled and manual runs of one target are mutually exclusive.
  • Three tables: probe_targets / probe_results (append-only history) / probe_tls_certs (current chain, delete-then-insert; a transient handshake failure keeps the last known-good chain — deliberately different from the scanner’s current-state semantics: probing cares about the last healthy state).
  • Prometheus metrics: mibee_probe_up / mibee_probe_duration_seconds / mibee_probe_cert_expiry_timestamp_seconds; deploy/prometheus/alert_rules.yml ships two example alert rules (target down, certificate expiring).
  • Results retention via retention.probe_results_days (default 30 days), swept by the existing cleanup service.

Liveness as a Time Series and the Identity Key

Device liveness was previously modeled as discrete device_changed events — one change-log row per status flip. After the test network ran for a while, the log had accumulated 70k+ rows, the vast majority produced by devices sleeping and waking; real changes were buried. The v0.5.0 fix has three layers:

  • The device_liveness time series: the heartbeat store records one verdict sample per device per tick, batched through the existing buffered-write / WAL infrastructure. Upper layers query OnlineRatio (online fraction over a window, separating jitter from real transitions), OfflineDuration, LivenessHistory. devices.status remains the source of truth; the series is disposable.
  • Tiered events: status flips are consumed by the liveness tier and no longer write device_changed; device adds, changes, and losses keep their original semantics.
  • Satellite tables keyed by device_uuid: heartbeat targets and satellite tables key on the stable UUID rather than the changeable IP, so address changes no longer fork history; this also fixed the regression where a device’s second scan showed stale data (#129).

The diagram shows where events go: every tick’s verdict sample enters the time series (feeding online-ratio and offline-duration queries), but only genuine status flips reach the event tier — digested by the liveness tier, so the change log no longer accumulates “online again / offline again” records.

Two companion fixes: the lease sweeper’s flap count decays instead of hard-resetting, so a flapping device trends toward lost rather than ping-ponging forever; and silent-device retention — scanner-discovered devices with no heartbeat are auto-pruned, MAC-bearing ones after 7 days (retention.silent_device_days_mac), MAC-less identities after 24 hours (retention.silent_device_hours_no_mac). Manually registered devices are never auto-deleted; coming back online resets the clock. Device detail gained last-seen / offline-since / last-online fields.

The MAC U/L Bit: A Misjudgement and Its Correction

One feature in this release shipped, lasted three weeks, and was then overturned. Worth recording.

Phase 1 (#118) treated the U/L bit (locally administered bit) of the MAC’s first octet as a “randomized MAC” verdict: bit set → address deemed random → device identity downgraded from MAC to (ip, network_id), to avoid treating iOS/Android privacy-randomized addresses as stable identities.

Per IEEE 802 / RFC 7042, the U/L bit only means “this address was assigned locally” — it cannot distinguish iOS/Android privacy randomization (changes on every reconnect) from a soft-router, hypervisor NIC, or manually configured local address (locally assigned but long-term stable). The test network exposed the problem immediately: 7 stable soft-routers and NASes were mislabelled “randomized”, and one R68s was split across two networks by the identity downgrade.

The correction (#123): the identity downgrade is reverted wholesale — device identity is MAC-primary again (with the (ip, network_id) fallback only when no MAC is known). The bit remains a pure observability flag: the field was renamed mac_is_randomized → mac_is_locally_administered, the UI label “Randomized” → “Locally Admin.”, and the tooltip states plainly that the bit cannot tell random from fixed. The multicast bit’s semantics are unambiguous and unchanged.

Conclusion: a single binary flag cannot carry semantics as heavy as “randomized” — its definitional boundary stops at “locally administered”.

OUI Vendor Inference: Longest-Prefix Across Three Registries

OUI lookup resolves a MAC to its IEEE-registered vendor via longest-prefix match across three registries: MA-S (/36, 9 hex digits), MA-M (/28, 7 hex), MA-L (/24, 6 hex).

Longest-prefix is mandatory because MA-S / MA-M sub-blocks are carved out of another vendor’s /24 OUI and assigned to someone else. Without it, a MAC starting 8C1F64B14 gets labelled “IEEE Registration Authority” (the /24 block registrant) when it actually belongs to Murata (the /36 sub-assignee).

Matching starts from the longest block: /36 (MA-S) first, falling back to /28 (MA-M), then /24 (MA-L); the matched prefix and organization name are recorded into scan_attributes.

  • New fields oui_prefix (the matched 6/7/9-hex block) and oui_vendor (the IEEE organization name — the NIC silicon vendor). It is kept separate from the existing vendor field, which is the device’s self-declared brand via SNMP/HTTP/TLS; the two differ in OEM, rebrand, and virtualization cases.
  • Out-of-box coverage: when scanner.oui_path is empty, an embedded curated table auto-seeds (go:embed, a hand-maintained CC-BY-SA subset); the full IEEE dataset (All rights reserved factual data) stays an optional runtime download and is not folded into the fingerprint corpus (license boundary detailed in docs/fingerprint-spec.md §8).
  • scripts/fetch-oui.sh was rewritten to fetch and merge the three IEEE CSVs; it also fixes a pre-existing error — the download host was standardeee.org instead of standards-oui.ieee.org, so the old script had been pulling from a non-canonical mirror.

Other Improvements

  • Dead metrics fixed. The HeartbeatFailures alert rule had sat in the config, but mibee_heartbeat_checks_total and five sibling metrics were registered yet never incremented in production code — the alert expression was permanently 0. The root cause was the collectors living in the handler package, where incrementing from the service layer would create an import cycle. They moved into the neutral internal/metrics package with all producers wired; prometheus.metrics_path also went from “configurable but hard-coded to /metrics” to actually honored.
  • sqlc drift guard. The committed internal/db generated code had lagged behind the schema since #233 — a full regenerate broke roughly ten call sites. This release fixed the query column sets, converged regeneration to an empty diff, and added a CI sqlc-verify job (v1.31.1): a diff from sqlc generate fails the build, so schema and query changes must ship with regenerated code.
  • Topology visualization. Layered force-directed layout with the legend doubling as a per-layer visibility filter; search dims non-matching nodes; selecting a node highlights its neighbors; edges drill into local/remote port, VLAN, and STP role; large graphs stay interactive via incremental rebuilds.
  • HTTP surface hardening. RealIP honors only proxies configured in server.trusted_proxies — no more unconditional trust of X-Forwarded-For, so client IPs cannot be spoofed via the header; service-layer validation errors became typed sentinels, mapped by handlers with errors.Is to 400s — user input mistakes no longer return 500s.
  • Frontend. Confirmation gates on destructive batch actions; unsaved-changes guards on five edit modals; keyboard-accessible DataTable rows; scanner-page cancel via AbortController; the SSE “disconnected forever” fix; locale-aware date/number formatting; distinct empty vs error states. The first .svelte page render tests landed (login / devices / scanner / probe).
  • Layering debt cleared. The last four mutating handlers that wrote to the DB directly (network CRUD, agent token, agent command, scanner result bulk delete) moved into service layers — the handler/service convention now has no remaining exceptions.

Upgrading

  • All new config is default-off: scanner.config_backup is off and rbac.scope_default is open — behavior after upgrade is identical to v0.4.0.
  • The users.role CHECK widened; old user rows keep working as viewers; new tables (device_liveness, snmp_credentials, ssh_credentials, device_configs, user_network_grants, probe_targets / probe_results / probe_tls_certs, notification_rules) are created idempotently on startup.
  • Migrations run automatically, with a pre-migration VACUUM INTO backup.
  • Center / agent are drop-in binary replacements; on Docker, pull the new tag and restart. Binaries are CGO-free (pure Go + modernc.org/sqlite) — amd64 steward is 25 MB, agent 18 MB; the GHCR image remains the unprivileged variant — build the privileged one locally with make docker-build-priv for LLDP/CDP raw frames and eBPF.

Deferred and Limitations

  • Agent-side SNMPv3 (#241): the distributed credential-distribution design is unsettled; agents stay on v1/v2c.
  • Config-backup real-router end-to-end smoke (GL-MT3000, #137): next release.
  • Center remains single-instance SQLite, unchanged.
