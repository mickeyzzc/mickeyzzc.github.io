onvif-device-rs Tutorial: Building an ONVIF Camera in Rust

October 2, 2026 MiBeeOSS Rust, ONVIF, IP Cameras, Open Source MiBee Open Source Projects Series 2684 words 13 min read
🔊

onvif-device-rs covers the other half of ONVIF: where onvif-go is “connect to cameras,” this library is “be the camera” — it makes an NVR discover your device, read its information, pull its stream, drive its PTZ, and receive its events, all over ONVIF. Use it to turn a Linux board or an industrial PC into an ONVIF camera, to build test fixtures for NVR development, or to bring a PC webcam into an NVR. It fills the previously empty slot of an ONVIF device-side implementation in Rust, extracted verbatim from MiBee’s Raspberry Pi camera firmware with byte-stable responses interoperating against MiBeeNvr byte for byte.

This post is written to a “copy it and use it” standard: from cargo new to a complete virtual-camera program, every config documented field by field, every injection seam with a full implementation.

Installation and Project Setup

console
1
2
3

cargo new my-onvif-camera && cd my-onvif-camera
cargo add onvif-device-rs tokio --features tokio/full
cargo add anyhow log env_logger

The current crates.io release is 0.7.0 with an MSRV of Rust 1.80. The naming needs one paragraph of history: the crates.io name onvif-rs is held by an abandoned 2018 placeholder, and lumeohq’s same-named library is a WSDL-generated client, unrelated to this project — so the crate publishes as onvif-device-rs while the repository keeps its original name, with the disambiguation written up in the README.

There is exactly one optional feature: tls (off by default). The reason is written in the Cargo.toml comment — products embedding the library depend on default features and must not gain a TLS dependency stack silently. Enable it explicitly when you want HTTPS.

Zero-Hardware First Run

Self-check before writing code. device_demo is a single-process smoke test — playing both the server and a “foreign NVR”: anonymous time query → an unauthenticated request must 401 → a full digest-authenticated stream pull → the multicast Probe, all asserted. Exit 0 means the whole surface passes:

console
1
2

cargo run --example device_demo            # one self-check pass, then exit
cargo run --example device_demo -- --serve # keep serving for curl / ONVIF Device Manager / NVR poking

Two more examples: ptz_demo (the eleven PTZ verbs with simulated motion) and imaging_demo (parameter get/set with a range fault).

use std::sync::Arc;
use std::time::Duration;

use onvif_device_rs::config::DeviceConfig;
use onvif_device_rs::device::{DeviceHandler, DeviceServiceHandlers};
use onvif_device_rs::discovery::DiscoveryServer;
use onvif_device_rs::media::{
    GetProfilesHandler, GetSnapshotUriHandler, GetStreamUriHandler, OnvifMediaConfig,
};
use onvif_device_rs::ptz::PtzState;
use onvif_device_rs::server::{OnvifConfig, OnvifServer};

#[tokio::main(flavor = "current_thread")]
async fn main() -> anyhow::Result<()> {
    let device_ip = detect_local_ip(); // your host knows its own IP
    let port = 8080u16;

    // 1. server config: port and credentials
    let config = OnvifConfig {
        port,
        username: "admin".to_string(),
        password: "set-a-real-password".to_string(),
        ..Default::default()
    };
    let mut server = OnvifServer::new(&config);

    // 2. device identity: all six fields surface in the NVR's device list
    let device = Arc::new(DeviceServiceHandlers::new(
        DeviceConfig {
            name: "My Camera".into(),
            manufacturer: "My Company".into(),
            model: "Cam-X".into(),
            firmware: "1.0.0".into(),
            hardware_id: "cam-x".into(),
            serial_number: "SN-001".into(),
        },
        port,
        device_ip.clone(),
    )?);

    // 3. Device service: the time query must stay anonymous (digest needs the time first)
    server.register_anonymous_action("GetSystemDateAndTime");
    for action in ["GetDeviceInformation", "GetCapabilities", "GetServices", "GetScopes"] {
        server.register_handler(action, Box::new(DeviceHandler(Arc::clone(&device))));
    }

    // 4. Media service: one media config feeds the three handlers
    let media = Arc::new(OnvifMediaConfig::new(1920, 1080, 25, 2_000_000, 8554, device_ip.clone()));
    server.register_handler("GetProfiles", Box::new(GetProfilesHandler::new(Arc::clone(&media))));
    server.register_handler("GetStreamUri", Box::new(GetStreamUriHandler::new(Arc::clone(&media))));
    server.register_handler("GetSnapshotUri", Box::new(GetSnapshotUriHandler::new(media)));

    // 5. PTZ: the state machine plus every verb
    let ptz_state = Arc::new(PtzState::new());
    for action in ["ContinuousMove", "AbsoluteMove", "RelativeMove", "Stop", "GetStatus",
                   "GetPresets", "SetPreset", "GotoPreset", "RemovePreset", "GetNodes",
                   "GetConfigurations"] {
        server.register_handler(action, Box::new(onvif_device_rs::PtzHandler(Arc::clone(&ptz_state))));
    }
    // the host runs a 50ms loop to advance the state machine (ContinuousMove moves here)
    tokio::spawn({
        let state = Arc::clone(&ptz_state);
        async move {
            loop {
                state.tick(50);
                tokio::time::sleep(Duration::from_millis(50)).await;
            }
        }
    });

    // 6. events: inject when your detector fires
    let events = server.enable_events();

    // 7. start the SOAP server and discovery
    let mut soap = server.start().await?; // 0.0.0.0:8080
    let mut discovery = DiscoveryServer::with_identity(&device_ip, port, "My Camera", "Cam-X")
        .with_uuid("f472b01e-0000-1000-8000-000000000001") // pinned UUID: no phantom device after restart
        .start()
        .await?; // UDP 3702

    // 8. example: inject a motion event every 30 seconds
    for _ in 0.. {
        tokio::time::sleep(Duration::from_secs(30)).await;
        let mut ev = onvif_device_rs::Event::new("tns1:VideoSource/MotionAlarm");
        ev.data.push(onvif_device_rs::SimpleItem::new("State", "true"));
        ev.data.push(onvif_device_rs::SimpleItem::new("Score", "87"));
        events.publish_event(ev);
    }

    // teardown (unreachable in the example; call from your exit path)
    discovery.shutdown().await?;
    soap.shutdown().await?;
    Ok(())
}

Walking through it:

  • Device identity: the six DeviceConfig fields surface in the NVR’s device list, and DeviceServiceHandlers::new validates them — empty fields and unknown placeholders are rejected outright. The library refuses to let a “My Camera, unknown, unknown” device appear in a real NVR, so state the identity explicitly (serial_number may stay empty).
  • The anonymous allowlist: GetSystemDateAndTime is a hard ONVIF requirement — the client needs the device time without auth before it can compute a digest. Leave this out and everything below 401s.
  • The action model: one handler per action. A single DeviceHandler instance serves several Device-service actions; the three Media handlers are data-driven — one OnvifMediaConfig::new(width, height, fps, bitrate, rtsp_port, ip) feeds the answers for GetProfiles/GetStreamUri/GetSnapshotUri.
  • The PTZ state machine: PtzState is pure — when the NVR sends ContinuousMove it records the velocity vector, tick(50) advances the position, GetStatus reports where it is. Feed the state machine’s output into a real gimbal (or into nothing) and the NVR sees a camera with fully working PTZ semantics.
  • The two servers: OnvifServer serves SOAP over TCP, DiscoveryServer answers Probes on UDP 3702 multicast (Hello on start, Bye on shutdown). Both handles are #[must_use] — dropping one stops the server.

Verify with any ONVIF client (the onvif-go CLI, say): onvif-quick -host <your-ip>:8080 -user admin -pass set-a-real-password — discovery, auth, streaming, and PTZ should all answer.

The NVR enters through two doors: multicast discovery (Probe in, ProbeMatches out) and SOAP over HTTP (action requests in, responses out). Request parsing is namespace-agnostic — clients may use any prefixes; response serialization uses explicit prefixes (tds:/trt:/timg:/tt:) with XML escaping on every interpolated value. Your host code lives entirely in handlers and the injection interfaces.

The Byte-Stability Contract

One rule belongs at the top, and the README prints it in bold: do not change response element names, namespace prefixes, or attribute order without re-running consumer interop tests. The reason: consumers like MiBeeNvr match responses by local element names on the raw byte stream, without a full XML parse — changing one element name can break the other side. The crate’s tests pin this with golden response strings, and changing a golden is treated as a breaking change.

The mirror side holds too: if the NVR’s parser is a byte-matcher, upgrading this library requires nothing on their end — the goldens guarantee the wire format does not move.

Auth: Writes Protected, Reads Open

The auth trio: verify_username_token with constant-time comparison (empty nonce means PasswordText, non-empty means PasswordDigest — the digest is BASE64(SHA1(base64_decode(Nonce) + Created + Password))), ReplayGuard’s nonce cache plus freshness window against replays, and per-source lockout after auth_failure_limit failures for auth_lockout_secs.

The default policy is pragmatic: actions whose names start with Set/Remove/Create/Go require WS-Security while reads stay open — an NVR’s polling reads should not trip over a password, but anything that changes configuration must authenticate. There is no reverse switch for “lock everything”; you can go fully open by supplying no credentials plus allow_no_auth = true (for tests).

Fail-closed is hard: an empty password without an explicit allow_no_auth makes start() error out — a configuration that looks safe but runs naked does not survive startup. To pre-check requests inside your own handlers, parse_soap_request(xml) is public and returns ParsedSoap{action, body_xml, username_token}.

The Media Plane: Config as Advertised

One distinction to keep in mind: this library returns URIs, not media. The resolution, bitrate, and RTSP port you put into OnvifMediaConfig are written faithfully into GetProfiles and GetStreamUri responses, but whoever serves RTSP on port 8554 is your host (an RTSP server, an ffmpeg pipeline, anything). The library answers “what does the NVR ask” correctly; “the stream itself” is fed by you.

The full OnvifMediaConfig (new(w, h, fps, bitrate, rtsp_port, ip) covers the common case, struct literals for the rest):

FieldNotes
camera_width / camera_height / camera_fps / camera_bitrateEncoder parameters written into GetProfiles
rtsp_port / stream_pathGetStreamUri composes rtsp://<ip>:<port><path>
snapshot_port / snapshot_pathWhere GetSnapshotUri points; port 0 means “not supported” (a proper fault)
profile_token / video_source_token / encoder_tokenThe three token kinds; NVRs pick streams by token
encodingVideoEncoding::H264 and friends
video_source_nameThe video source name
device_ipLoopback sources fall back here (the reverse-proxy case)

GetStreamUri with an unknown profile token fails open to the primary stream, so an NVR holding a stale token still gets a stream.

PTZ: A Gimbal Without Motors

Every PtzState method:

MethodBehavior
tick(dt_ms)Host-called every ~50ms; advances ContinuousMove travel and AbsoluteMove easing
continuous_move(vel) / stop()NVR-issued; records the velocity vector / zeroes it
absolute_move(target) / relative_move(delta)Exponential easing to the target / relative nudge
save_preset(name) / save_preset_with_token / goto_preset / remove_preset / list_presetsThe preset family, in memory
get_position() / get_status()Current position (x/y ∈ [-1,1], zoom ∈ [0,1]) and motion state

Feed the state machine’s output into a real gimbal — or into nothing — and the NVR sees a camera with fully working PTZ semantics. That is the point: adding PTZ meaning to motor-less devices, and testing an NVR’s PTZ logic without hardware.

Events: publish_event Injection

enable_events() returns an Arc<EventsService>; the injection side is one function:

rust
1
2
3
4

let mut ev = Event::new("tns1:VideoSource/MotionAlarm"); // topic
ev.data.push(SimpleItem::new("State", "true"));
ev.data.push(SimpleItem::new("Score", "87"));
events.publish_event(ev); // safe no-op with no subscribers

Once enabled, the event service routes CreatePullPointSubscription, PullMessages (long-poll), Renew, and Unsubscribe inside the library, with subscription addresses hanging off the SOAP listener; publish_event fans out through each subscription’s topic filter. Built-in constants worth knowing: the subscription queue holds 100 events and drops the oldest for slow consumers; subscriptions default to one hour with a 24-hour maximum, renewed by the NVR; a single pull waits at most 60 seconds (an NVR asking for PT0S — return immediately — is also valid). With events disabled the routes answer 404 and the wire is byte-identical to before — capability advertisements fold in the same way.

struct MyParams; // bridge to your ISP/sensor

impl onvif_device_rs::imaging::ImagingParams for MyParams {
    fn get_param(&self, name: &str) -> Result<f64, onvif_device_rs::imaging::ImagingParamError> {
        match name {
            "Brightness" => Ok(read_brightness()), // normalized to [0.0, 1.0]
            _ => Err(onvif_device_rs::imaging::ImagingParamError::InvalidName(name.into())),
        }
    }
    fn set_param(&self, name: &str, value: f64) -> Result<(), onvif_device_rs::imaging::ImagingParamError> {
        write_brightness(value)
    }
}

onvif_device_rs::imaging::register_imaging_actions(&mut server, Arc::new(MyParams));

register_imaging_actions registers GetImagingSettings/SetImagingSettings/GetOptions in one call; parameters use ONVIF names (Brightness, Contrast, Exposure…), values are normalized to [0,1], and out-of-range writes return ImagingParamError::OutOfRange{value, min, max}, which becomes a proper fault. Exposure and white-balance modes have default implementations you can override.

Discovery and TLS

DiscoveryServer details: with_identity(ip, port, name, hardware_id) puts the name and hardware ID into the NVR’s discovery list; with_scopes adds custom scopes; with_uuid pins the EndpointReference UUID — without it, NVRs that remember devices by UUID see a brand-new camera on every process restart. ProbeMatches are unicast UDP replies, which can hit a full send buffer under bursty load; the library retries up to three times with exponential backoff.

With the tls feature enabled, set tls_cert_file/tls_key_file — both or neither, since “half a certificate” errors at startup with no silent HTTP fallback. Certificates are read once at start; later file changes need a restart.

How Production Projects Use It

The natural consumers of a device-side library are projects that “turn something that isn’t a camera into one.” This library was extracted verbatim from MiBee’s Rust camera firmware and has two running hosts, feature by feature:

FeatureProduction projectHow it’s used
Identity / media config / discoverymibee-eye-rsThe ONVIF face of the Rust camera: OnvifMediaConfig advertises its RTSP stream and DiscoveryServer makes it appear the moment an NVR searches
PTZ state machine / event injectionmibee-eye-rsDetector output flows to subscribed NVRs via publish_event, and PTZ semantics work fully against commercial NVRs
Multi-protocol coexistence / GB 35114mibee-eye-notebookA PC’s webcam and microphone become one ONVIF/GB device, with RTSP/RTMP output and ONVIF access coexisting in one process

For complete implementations: mibee-eye-rs ships “a Linux board as an ONVIF camera” as a full product — capture, encoding, RTSP serving, ONVIF answering, and event push in one program, with matching code for every seam in this post (how the media config is filled, where events originate, how the UUID is pinned). mibee-eye-notebook is the same library in PC form, the reference for “no V4L2 hardware, wire up the system camera instead.” Sparring with the onvif-go client is ready-made: run mibee-eye-rs on one side and add it with onvif-go’s onvif-quick or MiBeeNvr on the other — discovery, auth, streaming, and events verify end to end on the spot.
