MiBeeNvr's Lock-Free Camera Manager: From Seconds to Milliseconds at Cold Start

November 26, 2026 November 26, 2026 MiBeeOSS Go, Concurrency, Streaming, Open Source MiBee Projects Series 1262 words 6 min read
🔊

The camera list was unusable for the first few minutes after boot: in a 9-camera deployment a single /api/cameras request took 14.9 seconds, then fell back to 1.4 seconds while continuing to stutter. The surveillance grid’s latest-frame polls stalled with it — during a camera reconnect, each tile refreshed only every few hundred milliseconds.

The bottleneck was neither decoding nor the network. The camera manager had one coarse-grained cm.mu (sync.RWMutex), and the lifecycle path held it across slow I/O: Stop joins goroutines, startup dials and performs an ONVIF handshake, and saving configuration writes to disk. Any camera starting, stopping, or updating put every reader in a queue.

Where the lock sat

cm.mu covered the manager’s entire state: recorders, hubs, configuration, and start failures all lived behind that one lock. Readers were frequent — the /api/cameras list, a latest-frame poll every 500ms per tile, and health-status sampling. Once a writer got in, the slow operation held the lock for its whole duration.

The most visible case was the ONVIF recorder’s own r.mu. Start held it from beginning to end: Connect, GetProfiles, GetStreamURI, the RTSP DESCRIBE probe, the HTTP MJPEG probes, and the delegate recorder’s start — several seconds of handshake. During that window, Status(), Delegate(), and RTSPURL() for that camera were all blocked, and the latest-frame poll goes through exactly that path. One camera reconnecting froze its tile in the grid.

The cost of a global lock is not one slow operation; it is that any single camera can hold up every reader. The shape measured before the change: /api/cameras took 14.9s at startup, then 1.4s with ongoing stutter; latest-frame polls took hundreds of milliseconds during reconnect; an ONVIF restart on one camera blocked reads on other cameras for seconds.

A snapshot replaces the big lock

The fix separates state from state change. The manager gained snapshot atomic.Pointer[snapshot], holding four maps:

  • recorders: camera ID to the running recorder
  • hubs: camera ID to StreamHub, shared by pull and push paths
  • configs: camera ID to the config pointer
  • failedStarts: start failures surfaced to health checks for auto-remediation

Once a snapshot is Stored, nobody may mutate it in place. Every read — GetRecorder, GetHub, Status, statusSnapshot, CameraCount, GetCameraConfig, stream-key resolution — performs a single atomic Load and then reads the map directly, taking no lock. All four maps are published together, so the view is aligned: a camera’s recorder, hub, and config never straddle two versions.

All writes go through apply():

func (cm *CameraManager) apply(fn func(s *snapshot) *snapshot) {
    cm.configMu.Lock()
    defer cm.configMu.Unlock()
    cur := cm.loadSnapshot()
    next := fn(cur.clone())
    cm.snapshot.Store(next)
}

clone() is shallow: map headers are copied, pointers are shared. Immutability of recorders, hubs, and configs comes from the lifecycle path — replace the pointer, never edit the field in place. At 10–50 cameras the copy is nanoseconds, and configMu covers only that step.

GetOrCreateHub’s check-then-create also became atomic: the fast path reads the snapshot; the slow path checks again inside apply, so two concurrent calls return the same hub instead of building one each.

The two paths in the diagram are now separate: reads touch only the snapshot and leave after one atomic load; a lifecycle operation touches configMu only to publish, while the expensive dialing, handshake, and start/stop happen outside the lock, serialized per camera by a short mutex in a sync.Map. Reads and slow I/O no longer share a lock.

Locks hold for an instant

The manager still has locks; each one now has a single job:

  • configMu: serializes apply()’s snapshot copy, config-slice mutation, and disk write. Only nanosecond map copies and millisecond disk writes — never network I/O or recorder start/stop.
  • auxMu: guards auxiliary lifecycle bookkeeping (schedule monitors, keyframe extractors, frame pollers), kept apart from the registry read path.
  • startStopMu: serializes top-level Start/Stop. Application wiring runs Start detached so readiness does not wait on cameras; Stop can arrive while Start is still registering recorders, and without this lock it would miss the ones being registered.
  • lifecycleMu plus withCameraLifecycle: one lazily created *sync.Mutex per camera in a sync.Map, wrapping only a single start/stop/restart.

That last one is the essential addition. The snapshot made reads non-blocking but did not stop two goroutines from starting the same camera at once: a manual restart colliding with a health-triggered restart, or a config update colliding with rediscovery, let the second call overwrite the first recorder in the snapshot. The first one’s goroutine kept running with no way to reach it — a leak until process exit. withCameraLifecycle serializes operations for one camera only; different cameras do not wait for each other. Removing a camera also deletes its mutex from the sync.Map so the key set stays bounded.

The ONVIF recorder got the same treatment: Start takes a short lock only for the “already running” guard, runs the whole handshake outside r.mu, then publishes delegate, stream URL, and status under a short lock at the end. Status() snapshots the delegate pointer under a short lock and calls it outside. A multi-second handshake no longer stalls status reads.

Numbers

Recorders can start in parallel because the slow handshake no longer holds a global lock. apply() only publishes the result, so one camera dialing slowly does not block another from registering.

Not every lock should go

The same concurrency document records several refactors that were evaluated and not adopted. They show where the line sits.

StreamHub.Broadcast uses a different pattern: it takes h.mu only to snapshot the consumer list, releases it, then invokes each consumer callback. Each hub has one RTP producer, and subscribe/unsubscribe happen only on play/stop events, so the lock sees no contention on the hot path. A proposal to replace the consumer list with a copy-on-write atomic pointer and CAS-based add/remove was rejected: the IDR cache still needs h.mu, so COW would leave two synchronization mechanisms side by side, and CAS retries plus per-operation allocations bought nothing.

EventBus subscriber channels are multi-producer, single-consumer: many cameras and goroutines call Publish concurrently. A hand-rolled SPSC ring has the wrong topology here — under multiple producers it loses writes or corrupts memory. Go channels were already the right primitive.

Inside the recorder, fields are split into three tiers: lifecycle and per-segment state (status, cancel, muxer, segStart, audioTrackID) stay under mu for multi-field consistency; cross-goroutine codec configuration (codec, audio) is written once into atomic.Pointer and read-only after publication; and the fields owned by writeFrames (trackID, paths, frame counters) deliberately have no lock because a single goroutine touches them.

What made the difference was lock hold time and access pattern: a lock spanning slow I/O makes readers wait; shrinking publication to one map copy separates reads from writes. A lock with no contention does not need an atomic pointer, and a field owned by one goroutine does not need a lock. Lock-free is the conclusion of those two checks, not the goal.
