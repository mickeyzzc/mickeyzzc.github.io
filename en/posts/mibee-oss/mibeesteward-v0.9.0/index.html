MiBeeSteward v0.9.0: Phones Come and Go — the Asset Archive Remembers

November 7, 2026 November 9, 2026 MiBeeOSS Go, Device Management, Network Discovery, Asset Management, Open Source MiBee Projects Series 1621 words 8 min read
🔊

The most numerous devices on a network aren’t servers — they’re phones, and the most transient ones too: on the office WiFi at nine in the morning, gone by six, absent all weekend. A phone upgrade leaves the old handset behind, never to connect again; a guest’s phone visited once, and never again. The old handling was blunt: offline past a threshold, the sweeper deleted the row, history included — and when the same phone ever connected again, it was a “new device”, with nothing to connect it to the last seen time, the old IP, the services it once ran.

The timeline ends at v0.8.0 with a scanner that only answers “who is online right now”. v0.9.0 answers the other half: will it come back?

The Archive: Deleted Becomes Remembered

The most common case first: the phone that commutes daily never touches the archive at all. The global threshold defaults to 7 days, overridable per device, and a sixteen-hour overnight gap is nowhere near it — daily comings and goings are unaffected. The archive takes the other two kinds: anything silent for 7+ days (the old phone an upgrade retired, the NAS sitting idle in the closet), and devices without a MAC (24-hour fast lane).

An archived device is stamped archived_at with history fully retained — not a deleted row. Returning has an acceptance bar: 60 consecutive minutes online restores it to the inventory. That bar exists precisely for transient devices — an archived phone that flickers past once (connects on the way by) only records an online_blip and stays archived; genuinely coming back, 60 straight minutes buys back its identity. Two manual switches override everything: force_active never auto-archives, force_archive never auto-restores.

Every move in or out of the archive writes an event. This stream has a different retention policy from everything else: the change log keeps 30 days, liveness keeps 7, archive events are kept forever — the day that one-time guest phone showed up last year, and the network it connected from, has exactly one answer, and it lives here.

The Learned Cycle

A 7-day threshold can’t cover every rhythm of coming and going. The supplier’s accountant visits once a month, always with the same phone — by the letter of the rules it deserves archiving every time, and gets misfired every time. v0.9.0 doesn’t ask the user to tune the threshold; it has the system recognize the cycle: appearance points are taken from the archive event stream, and at ≥3 points spanning 60+ days with adjacent intervals orbiting within ±25% of the median, the device is marked periodic with its cycle days and exempted from auto-archiving. Manual touches don’t count as appearance points — people are not device behavior.

Two guards keep it from getting clever: the learner stays silent while the effective threshold is 30 days or more (a monthly-scale threshold never defers to heuristics), and a stale pattern — silent for two full cycles — must see the device actually return once before exempting again. A device already in the archive is restored the moment its cycle is recognized.

The 60-day learning window is why archive events are kept forever — the two features are each other’s precondition; pull either one and the other collapses.

Tags Become a Dictionary

The tag column on the device table used to be free text, where searching “camera” and “cam” searched two different worlds. It’s now a proper dictionary: the four built-ins (internal / external / temporary / pending) carry delete protection — the last two are self-explanatory about who they serve, guest devices and unclaimed new faces — with per-device many-to-many tagging, batch tagging from the list, tag filtering, and automatic backfill of old data. The device table also picked up the fields asset management owed: lifecycle state, owner, and asset number.

From Install to First Scan

A new system doesn’t bleed users over missing features; it bleeds them right after install, when they’re staring at an empty dashboard with no idea what to click first. This release compresses that road: the bare binary runs as-is — with no config file it generates a minimal valid one (random jwt_secret, permissions 0600) and the admin password is created in the browser; an existing config file is never rewritten no matter how broken, because a broken config should fail loudly. The dashboard’s “Scan networks” button sits on a new endpoint that enumerates the host’s own IPv4 interfaces, offering on-link networks with /24 suggestions — a DHCP-issued /16 no longer baits a first scan of sixty-five thousand hosts. LAN interfaces come pre-checked; one click creates the daily task and fires it immediately. On an empty inventory the dashboard shows a three-step card whose steps check themselves off from server state — create a task and the first line strikes itself out; you never click “done”. When the first scan completes, the toast becomes “First scan complete — N devices found”, straight into the inventory. On the router side, the OpenWrt installer now enumerates every network on a multi-LAN router, and the agent reports the host’s actual subnets up from /proc/net/route — the center backfills missing network CIDRs, filling blanks only, never overwriting.

How Big a Box for a Thousand Devices?

The repo carries a benchmark document and a synthetic-load harness, loadgen: it simulates an entire device layer on the loopback network — each synthetic device takes one 127.x.y.z address, ICMP is answered by the kernel for free, and TCP/UDP responders pose as an SNMP agent, HTTP services, SSH banners, and RTSP servers with real payload shapes. The scanner’s probe, classification, and write paths run untouched — the benchmark measures the real pipeline, not a mock. The same subnet gets an accuracy comparison against nmap -sn producing a recall/precision confusion matrix — the hosts MiBee reports beyond nmap are deliberately counted TCP-connect-only devices that a rootless nmap -sn can’t reach; the surplus is a feature, not an error.

Ahead of the v0.9.0 release the harness ran a low-resource benchmark: the whole binary squeezed into a cgroup limited to 30% of one core plus 256 MB of memory, driving a thousand-device synthetic plane —

That is the resource class of a Raspberry Pi Zero 2 W and entry-level routers — one SBC standing calmly as the center of a thousand-device LAN; beyond that, scale goes to agent fan-out while the center only aggregates. The methodology is honest about its limits: the loopback plane has no packet loss or ARP, so wall-clock scan time underestimates a real LAN; every 127/8 address answers ICMP, so the survival count measures pipeline throughput, not discovery accuracy — the doc says plainly how each number should be read.

The Topology Gains 3D

The L2 topology graph gained a three.js 3D scene that swaps with the existing ECharts 2D canvas in one click, with the choice persisted in the URL for sharing. Both canvases consume one set of render rules — sizes, badges, and edge styles are all pure functions now, so the two views cannot drift apart. The 3D layer bands stand the structure up: gateways on top, switches in the middle, endpoints at the bottom; the layout is deterministic, the same network always the same shape, refreshes don’t reshuffle; dragged node positions survive polling rebuilds; the hover card identifies any point without a click; three label-density levels keep 94 nodes legible by name. The cost stayed contained: three.js plus d3-force-3d at ~640 KB ships as a lazy-loaded chunk fetched on first switch to 3D; without WebGL you stay on 2D. Verified on a rig of 94 real devices and 279 edges.

A pile of old rendering bugs went with it — the most telling one: edges pointing at “unidentified neighbors” had never rendered at all, the canvas was missing edges while the legend over-counted, and nobody had noticed.

Also Fixed

Two with a picture. The pull model has no backpressure: an agent offline for a day racks up 650+ pending commands, and after reconnecting, new probe plans queue behind hours of stale rescans — probe commands now coalesce as full plan snapshots and scan commands dedupe by payload, with no work lost. The task form’s pre-filled ports never matched the backend’s actual defaults — the form showed five ports, but a task saved without expanding the advanced section ran four; defaults now have one source, pinned by tests. The rest: scheduler pickup under load measured 2.5–5.5 minutes and the task page’s polling would puncture through and give up silently — it now degrades its rhythm and keeps watching for 2 hours, showing an honest “queued” badge; failed notification deliveries retry with backoff (30s doubling to a 5-minute cap, default 30-minute window); agent-rs gained DNS retries and a properly wired remote_ops switch; and the stale-topology-colors-after-theme-switch family got cleared out too.

Upgrading

Schema v8 → v9, still the fresh-database policy: scripts/backup.sh, start a new database, rescan to repopulate; within v9, minor upgrades are a binary swap. deb/rpm, the OpenWrt package trio, and GHCR images all ship in this release; the full asset list is on the v0.9.0 release page.
