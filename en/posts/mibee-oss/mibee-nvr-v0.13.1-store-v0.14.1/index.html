MiBeeNvr Release Log: Store Ships 0.13.1 While the Repo Reaches 0.14.1

October 31, 2026 MiBeeOSS MiBeeNvr, NVR, ONVIF, GB28181, FnOS, NAS, Go, Open Source MiBee Projects Series 1343 words 7 min read
🔊

On October 30, MiBeeNvr’s two distribution channels each took a step on the same day: the GitHub repo tagged v0.14.1, and the fnOS app store finished reviewing and publishing v0.13.1. Back in late September the store onboarding application hadn’t even gotten a reply (noted in the previous release log); this time review plus publication landed within one day, which caught me off guard. The catch: the approved version now trails the repo by two — 0.14.0 and 0.14.1 have yet to reach the store.

This post covers the two versions together: why 0.13.1 exists and what known bug it carries; what 0.14.1 fixed; and a recap of 0.14.0 in between, since 0.14.1 builds on it and this blog had only covered up to the 0.13.0 preview.

v0.13.1: A Patch Release Forced by the Store Form Factor

v0.13.0 introduced the first-boot setup code: the initialization wizard requires a code printed only in the startup logs, so no other device on the LAN can race to claim the admin account. The design is fine on a server deployment, but store installs on fnOS or Synology come with no terminal — the “startup logs” the prompt points to are unreachable, and initialization dead-ends at step one. v0.13.1 (October 19) is a patch release with exactly one fix:

  • The wizard opened through the fnOS unified gateway no longer asks for the code: requests arrive verified by the gateway as the NAS admin, and LAN peers cannot forge gateway identity, so the security model stands; direct access via IP:9090 still requires the code
  • The code is also written to setup-code.txt in the data directory — for Docker deployments that’s the mounted volume, visible from any file manager; it is deleted automatically once initialization completes, and refreshed on every restart until then
  • The prompt now states the real retrieval path per deployment form (volume file / container log via docker logs)

What makes this bug worth recording is where it came from: the store form factor pushed a requirement back onto the project, and the patch release is the answer.

The known bug needs stating too: in v0.13.0 / v0.13.1, the RTMP ingest crashes when it receives a push carrying an audio track — a null-pointer defect in gortmplib v1.0.2 with unregistered audio-track callbacks. When a publisher such as OBS or ffmpeg pushes a stream with audio, the process SIGSEGVs, auto-reconnect turns it into a crash loop, and the whole NVR appears to reboot repeatedly with a black UI. Only RTMP ingest with an audio track is affected (RTMP ingest is off by default); recording, playback, and live viewing of pull-based cameras are untouched. Fixed in 0.14.0 (gortmplib bumped to v1.0.4 with the callbacks registered). If you run RTMP ingest on the store’s 0.13.1, move to 0.14.x as soon as you can.

v0.14.0: The Ground 0.14.1 Stands On

The October 24 feature release carries a lot; here is the backbone:

  • Remote access: no public IP or port mapping needed — the Web UI and the BeeProbe app are reachable from outside. The built-in tunnel prefers NAT-traversal direct connections and falls back to relay when needed, with end-to-end encryption; device enrollment carries Ed25519 identity keys and self-heals re-enrollment after credential rotation breaks it. Off by default; background research in the NVR remote access survey
  • Standalone recording and live monitoring: network pickups (GB28181 voice channels / RTSP audio) join as first-class audio devices — zero-decode passthrough monitoring with instant start and a real waveform, linked audio tracks on the recording timeline, WAV export
  • Device management rebuild: cameras and pickups managed in one place, group collapsing plus type filtering
  • SIP doorbell: Doorbird-style doorbells and intercoms connect, with incoming-call popups and call records; DLNA casting: a built-in UPnP AV media server pushes recordings straight to a TV
  • Weekly recording schedules: per-camera time-range × weekday combinations, overnight ranges supported, nothing written outside the plan
  • Camera clock correction: a built-in SNTP server plus a one-shot sync probe, keeping time drift from wrecking search and authentication
  • GB/T 28181 graduates to production support: validated end to end on Hikvision 2026-firmware devices; full-duplex voice intercom; GB35114 Level-A SM certificate mutual recognition
  • Native Linux packages (deb / rpm, amd64/arm64, one-command install); a new Russian UI

Fixes worth noting: recording segments now roll over at IDR boundaries, so segment edges drop no footage; timelapse merge windows interrupted by restarts self-heal; the old-firmware ONVIF auth downgrade fix (0.14.1 takes this further); WebSocket upgrade compatibility behind the fnOS unified gateway; the update check only recognizes proper release tags, so dev builds no longer falsely report updates. The playback-refusal anti-recurrence trio (forced media-cache revalidation, SPA build fingerprints, orphan-row sweep at startup) also landed here. Code contributions from genelee26 (weekly schedules, IDR segmentation, adaptive write density) and Urdin-at (Russian UI).

The storage and I/O work of 0.13.0 already has its own benchmark post, so I won’t repeat it here.

v0.14.1: Discovery and Intake of Legacy Devices

The October 30 compatibility release focuses on bringing two kinds of old devices in.

Both ONVIF pain points on old firmware live in protocol details. The auth ladder used to wedge on one old-firmware behavior: after a rejected Digest exchange, the device returns an empty 200 response body, the client stops dead instead of stepping down, and such cameras stay stuck at initialization forever after discovery. The ladder now advances correctly through PasswordText / Basic / anonymous (onvif-go v2.7.1). Endpoint resolution now prefers GetServices: old firmware often reports a stale service address or one pointing at the wrong host, and the new path resolves the correct Media and event endpoints; SOAP now uses the canonical compact wire format, which old models picky about wire shape handle better (onvif-go v2.7.0). The NVR’s own raw-SOAP implementation is fully retired in favor of onvif-go, and stream-URI probing is gated on demand, so freshly discovered cameras no longer get probed more than needed.

GB/T 28181-2011 legacy device and platform interop: GB2312 encoding parsing fixed, 2011-style message shapes pinned, and three DeviceInfo response wire-format fixes — cascading up to old superior platforms no longer errors out (gb28181-go v0.15.0).

One data fix as well: editing a camera no longer silently drops its “recordings include audio” setting.

New features ship off by default:

  • The four fnOS packages: the Release page now carries both native and Docker fpk packages — a native package (app name mibee-nvr-native, no Docker dependency, a single static binary with the embedded Web UI, roughly 30 MB idle, pick aarch64 or x86 by machine) and Docker packages (offline with both architectures embedded, online at KB scale pulling per architecture). Native and Docker can coexist with separate ports and data directories; the trade-off is no FFmpeg, so transcoding features are unavailable while recording, live, API, and notifications are unaffected
  • Opus audio tracks from RTSP cameras record and play back directly; HTTP-FLV live streams carry AAC audio, so browser live view has sound
  • Outbound alert webhook: events forwarded to a custom HTTP endpoint with HMAC signing, off by default
  • GB35114 Levels B / C (per-frame video signing and media encryption) target -tags gb35114 source builds and the gb28181-go ecosystem; official builds exclude them and Level-A behavior is unchanged

Dependency housekeeping came along: onvif-go v2.7.1, gb28181-go v0.15.0, a full dependency sweep clearing security alerts; license headers gained SPDX identifiers (AGPL-3.0-only).

Two Channels, Two Cadences

The version gap between the channels is now a real two releases. Store users on 0.13.1 have the setup-code fix, and the RTMP bug too (moot unless you enable ingest); reaching 0.14.x takes another review round. Users who skip the store can grab the four fpk packages or pull the Docker image at 0.14.1 from the Release page right now — post-upgrade behavior matches 0.14.0, with all new features off by default or zero-config, and database plus storage structures migrating automatically.

This time, review and publication of 0.13.1 landed on the same day. Whether the store channel keeps that pace for 0.14.x — the next review round will tell.
