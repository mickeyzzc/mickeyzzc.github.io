MiBeeNvr v0.11.0: fnOS Installs, GB/T 28181, and the Full-Day Timeline

August 17, 2026 September 1, 2026 MiBeeOSS NVR, Go, GB28181, SIP, Playback, Timeline, FnOS, Docker, AGPL, Open Source MiBee Open Source Projects Series 1734 words 9 min read
🔊

A few days after v0.10.0 went stable, fnOS users’ feedback boiled down to one sentence: it won’t install. Two older debts got settled in the same release: Hikvision/Dahua cameras couldn’t enroll — you either bought their NVR or stood up a separate GB platform; and playback showed one 30-second segment at a time, so reviewing a whole day meant clicking through segment by segment.

It installs now

  • All three install blockers are fixed: stalling on image downloads, a dead desktop icon, and a port field that rejected 9090 outright
  • The offline package bundles the full image set — works the moment it’s installed, no network needed
  • The online package is a few dozen KB and picks whichever of the China mirror or the official registry answers faster
  • The one-click install script auto-selects the same way
  • Synology, QNAP, and ZSpace store templates landed too

Easier to integrate

  • Hikvision/Dahua cameras enroll with a few filled-in fields — no vendor NVR, no separate platform (via the GB/T 28181 national standard)
  • Fully automatic after registration: a camera card per channel, recording starts on its own
  • PTZ, zoom, presets, and voice intercom work; the recordings on the camera’s own SD card are searchable and replayable
  • Hand Home Assistant-style integrations a dedicated key you can revoke on its own, without touching the global password
  • An IP change no longer breaks clients — they track the device, not the address

Playback that works

  • A whole day’s recordings stitch into one timeline — scrub to any moment
  • Segment switches no longer black-flash; the handover is invisible
  • Blank stretches from power cuts scrub right through without stalling
  • Authenticated live streams play on iPhone again

If it doesn’t install, it isn’t released.

MiBeeNvr paid off the accumulated engineering debt in v0.9.0 and shipped the stable release in v0.10.0 — H.265 WASM live view, multi-NAS distribution, the AI false-positive fix. After stable, v0.10.1 fixed the fnOS installs and v0.11.0 added the online package and the China mirror; the two big items in v0.11.0 itself are GB/T 28181 ingest and the playback rework. The license changed from MIT to AGPL-3.0-only — read the license section before upgrading.

fnOS install fixes

The three blockers, in the order users hit them.

The first was blunt: install stuck pulling images. The package shipped as a docker-project, which pulls images from ghcr.io at install time. ghcr frequently times out from mainland China, and when the network stalls, the install just hangs.

The second took some work. Install succeeded, but clicking the desktop icon did nothing. Turned out the Web UI’s X-Frame-Options: DENY was rejecting the desktop’s cross-origin iframe embed. Switched to a configurable CSP frame-ancestors, reinstalled — still nothing. The value http://* only matches the default port 80, while the fnOS desktop runs on a non-default port like :5666. Changed to scheme sources http:/https:, which allow any port, and it finally opened.

The third was fnOS’s own quirk: a text field’s min/max got treated as string-length validation. Port 9090, four characters, rejected outright. Switching to a pattern regex fixed it.

v0.10.1’s answer was to decouple install from the network: amd64 and arm64 images are docker saved into an offline .fpk (~160MB), loaded locally with docker load at install — no registry access at all. The app form also moved from docker-project to native. There was a timing problem: fnOS’s docker-project apps auto compose-up at install, which fires before any lifecycle hook, so the offline image hadn’t been loaded yet and it failed with No such image. The native form lets the app’s own startup script own the load and run, which puts the order right.

v0.11.0 builds this into a dual-package strategy and adds the China mirror on the Docker side:

The two package paths: the offline one carries both architecture images and works immediately; the online one probes whether ghcr or the Alibaba Cloud ACR mirror has lower latency at startup and pulls from there. Docker images now ship to both registries in sync — in China, pull this one:

bash
1

docker pull registry.cn-hangzhou.aliyuncs.com/mickeybeehome/mibee-nvr:latest

The one-click installer auto-selects the same way. Synology, QNAP, and ZSpace store templates landed in this release too.

Playback rework

Recordings are stored on disk in 30-second segments. On playback, finishing a segment meant remounting the next file, with a black flash in between; the timeline only worked within a single segment, so reviewing a whole day meant clicking through one segment at a time. That had been there since the early versions; v0.11 finally reworks it.

The black flash is gone via double buffering. When the main <video> reaches 80%, the next segment is prefetched and mounted on a standby <video>; when ended fires, the standby takes over — the switch is invisible.

AVI recordings gained a frame-browse mode — seekable, seamless across segments. VOD fragments auto-rebuild on 404, and recording switches got chunk prefetch plus day-data caching.

GB/T 28181 national-standard support

Integrating Hikvision or Dahua cameras used to mean buying their NVR or deploying a dedicated GB platform. These devices all speak GB/T 28181 — the video-surveillance national standard, over SIP signaling, labeled “platform access” or “28181” in the device admin page. v0.11 lets MiBeeNvr play that platform itself.

The device just REGISTERs in; everything after that is automatic: catalog query, a camera card per channel, INVITE to pull the stream, recording starts.

Post-registration capabilities: PTZ direction, zoom, and presets; voice intercom (browser mic straight to the device speaker); device-side recording search and playback with speed control and seeking; alarm, catalog, and mobile-position subscriptions. Cascading works too — the NVR registers to an upper GB platform as a lower level, aggregates local cameras into a catalog, and forwards RTP/PS when the upper platform requests a channel. Remux only, no transcode; the upper platform needs nothing special.

Three required fields in the config:

gb28181:
  enabled: true
  sip_listen: ":5060"
  server_id: "34020000002000000001"
  realm: "3402000000"
  password: "yourpassword"
  port_range: "30000-30050"
  media_transport: "udp"        # udp | tcp-passive | tcp-active

On the device, fill in the NVR’s IP, port 5060, the same ID and password — registration succeeds within seconds. Full parameters are documented in the repo’s config.example.yaml.

Two things to watch. An empty password means no authentication: anything that can reach port 5060 can register. On a public deployment, always set one. And the feature is still experimental — the code follows GB/T 28181-2016, validated against in-house devices and a simulator, but the full regression on commercial Hikvision/Dahua units isn’t done yet. It’s off by default; leaving it off changes nothing.

Other changes

  • LAN discovery: the NVR generates a UUID on first start and persists it; /api/health carries device_id and device_name, so clients track the device rather than the IP, and an IP change no longer breaks them. Discovery runs two paths: an mDNS announcement, _mibee-nvr._tcp, plus a UDP 49090 broadcast responder for networks where multicast is restricted
  • App tokens: mbv_-prefixed keys issued per device, individually revocable, hot-reloaded, with last-used tracking. Hand one to a Home Assistant-style integration and revoke just that one when needed
  • The 401s on authenticated HLS in iOS: playlist requests now issue a scoped mbs_session cookie, which unblocks players like AVPlayer that can’t set per-request headers
  • WebRTC audio with zero transcoding: G.711 and Opus go straight into the WebRTC track
  • The setup wizard now patches credentials onto the loaded config; pre-set listen addresses, AI backend config, and camera lists survive it
  • Fixed the incident where two pathological GB streams ate the host’s memory — PES reassembly buffers are now bounded
  • GB live freezes: long-GOP session recycling and stale WebRTC hub binding cleanup

License change

Starting with v0.11.0 the license is AGPL-3.0-only; v0.10.1 and earlier stay MIT forever. Impact by scenario:

Your usageImpact
Just using/running it (including commercially)Zero obligations, same as before
Distributing a modified versionMust be open-sourced under AGPL-3.0
Building on the pkg/ extension interfacesUnaffected, linking exception
A separate process calling the NVR over HTTP/WebSocketCompletely unaffected

For most people it’s simply no impact: run it, record, watch — zero obligations. Open source is required in exactly one case: you modified the code and distribute the result.

GET /api/cameras/{id}/protocols response fields are now snake_case, aligned with the other endpoints:

Old fieldNew field
Protocolprotocol
Availableavailable
Reasonreason

Scripts calling this endpoint need updating.

AAC live audio degrades on plain HTTP. The FAAD2 WASM fallback was GPL-2.0 and got removed to keep the license clean; AAC live preview now needs WebCodecs — HTTPS or localhost. G.711 live audio and AAC inside recordings are unaffected.

No database migration; the new GB tables are created automatically on first start.

# One-click install (amd64 / arm64 / armv7, auto-selects the best registry)
curl -fsSL https://raw.githubusercontent.com/Mi-Bee-Studio/MiBeeNvr/main/install.sh | sudo bash

# Docker (ACR mirror recommended in China)
docker pull registry.cn-hangzhou.aliyuncs.com/mickeybeehome/mibee-nvr:latest

fnOS users: manual install of the .fpk in the App Center, offline or online. Back up nvr.db and mibee-nvr.yaml before upgrading, then curl /api/health after swapping the binary to confirm.
