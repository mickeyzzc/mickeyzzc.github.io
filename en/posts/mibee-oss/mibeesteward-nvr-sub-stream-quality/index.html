MiBeeNvr's Sub-Stream System: No More Lag or Heat on Phone Surveillance

November 26, 2026 November 26, 2026 MiBeeOSS Streaming, HLS, WebSocket, Open Source MiBee Projects Series 1260 words 6 min read
🔊

The two most annoying things about watching surveillance on a phone: it gets hot, and the video stutters. Open four or five tiles on the surveillance grid and every one of them is receiving a high-resolution main stream. The phone decodes and receives at the same time, the battery visibly drains, and the picture keeps hitching. Most people’s first reaction is to replace the phone or switch WiFi to 5 GHz. The bottleneck is not the network; it is the stream being delivered.

A camera usually outputs more than one stream: the high-resolution main stream for recording, and a lower-resolution, lower-bitrate sub-stream that was meant for previews. MiBeeNvr turns the sub-stream into an on-demand first-class citizen — whoever watches triggers the pull, and when nobody watches, the sub-stream pull stops on its own. Recording always uses the main stream, completely separate from previews.

Who Pays the Cost

Without on-demand sub-streams, previews can only follow the same main stream used for recording, and the viewer pays the full cost of that stream: bandwidth at the main stream’s bitrate, decoding at the main stream’s resolution. With several tiles open, those costs multiply by the number of streams. That is where the heat and dropped frames come from.

Now there is a layer of separation. The surveillance grid has a Smooth / HD toggle in its header, defaulting to Smooth; the single-camera live page has a per-camera quality switch; GB28181 cascade uploads can be switched to the sub-stream per camera too, so upper-platform previews stop saturating the uplink; and external AI analysis consumes sub-stream segments at roughly 1/4 to 1/16 of the decoding cost of the main stream. All these consumers share one premise: the recording path on the main stream does not move.

The cost shifts to one extra RTSP pull on the NVR side, but that pull exists only while someone wants the sub-stream.

Pull on Demand

The sub-stream’s lifecycle is governed by reference counting. Every endpoint that wants the sub-stream calls Acquire when it connects and increments refs; on disconnect it calls Release and decrements refs. A count of zero does not stop the pull immediately — an idle timer is armed, 30 seconds by default. If another Acquire arrives in that window, the timer is cancelled and the same pull is reused. Only when the timer actually fires does the RTSP pull stop, the source get deleted, and onRecycle fire so the app layer can unsubscribe its consumers.

There is an easy-to-miss detail here: recycling happens in the timer callback, the actual teardown is detached into its own goroutine, and the callback checks refs again — if someone re-acquired in the gap, the existing source is kept rather than killing a freshly established reference. In code this is the same-hub identity guard. WebRTC WHEP holds references at session scope (SetOnSessionEnd), released only when the session ends.

The diagram walks through one viewing session end to end: a request comes in and takes a reference, or joins an existing one; the first Acquire starts the RTSP pull and publishes to StreamHub(camid/sub); disconnecting drops a reference, and only after 30 seconds idle at zero does recycling happen. The main-stream hub is not in the picture — it has no reference relationship with this chain.

The timeouts are all visible in configuration: idle_timeout_s defaults to 30, ready_timeout_s to 8 (a typical RTSP connect plus first keyframe takes 1–4 seconds); each dial attempt is 5 seconds with backoff retries until the ready timeout; and 15 seconds without a frame while live triggers a reconnect. The sub-stream target can be a hand-entered RTSP URL or an ONVIF sub-stream profile token (leave it blank to auto-discover the second-highest resolution profile besides the main one). ONVIF metadata can be inaccurate — advertising H.264 while serving H.265 — so the NVR trusts the actual RTSP DESCRIBE probe.

All Four Endpoints

All four live endpoints can ask for the sub-stream, but the spelling differs:

EndpointSub-stream request
WebSocketstream/ws?quality=sub
HTTP-FLVstream.flv?quality=sub
HLSpath form .../stream/sub/index.m3u8
WebRTC (WHEP)POST .../stream/webrtc?quality=sub

HLS uses a path instead of a query because segments are addressed relatively — a query string cannot ride along with every segment. The sub path segment is part of the resource identity; index.m3u8 is the multivariant playlist name, with stream.m3u8 and playlist.m3u8 accepted as compatibility aliases, and any other name returns 404 rather than an empty playlist. Low-Latency HLS is on by default and the playlist carries #EXT-X-PART partial segments.

WHEP has a hard constraint: WebRTC can only carry H.264, so an H.265 sub-stream falls back to main; a genuine sub-stream session is established only when the sub-stream is actually H.264.

The frontend adds a black-screen guard. effectiveQuality() requests sub only when the sub-stream codec is known to be H.264, or the browser can decode H.265 via MSE; with an unknown codec it starts on main, and switching quality re-mounts the player. /protocols reports sub_stream with available / source / reason / codec, and consumers must read it reactively — a one-off read pins the quality to the main stream.

Say the Fallback Out Loud

Fallback is routine: no sub-stream configured, a failed pull, or an H.265 sub-stream meeting WHEP’s H.264-only support all land on the main stream. The point is not to make the client guess.

FLV, HLS, and WHEP still have HTTP semantics, so the X-Stream-Quality: main|sub response header reports what was actually served — note, actually served, not what was requested. The frontend seeing main never black-screens, and scripts can act on it.

WebSocket cannot do this: the 101 upgrade response is written by the upgrader itself, so headers set before the upgrade never reach the client. The negotiated quality therefore travels in-band as the first message — QualityInfo, type 0x06, wire format {type:1}{quality_len:1}{quality}, where quality is the ASCII string main or sub. The server’s ServeWS sends it before CodecInfo (0x01), and sends it to audio-only viewers as well; older clients that do not recognize the type simply ignore the message.

Three protocols place the answer in three different spots: an HTTP response header, an HLS resource path, and a WebSocket first frame. What generalizes is this: report the stream actually delivered rather than the one requested; put the answer where the client is guaranteed to receive it; carry it in a dedicated field that old clients can safely skip.

Make It Visible

Nothing needs guessing during troubleshooting. The sub_stream entry of GET /api/cameras/{id}/protocols gives availability, source, and reason; in the flow snapshot from GET /api/streams, the main stream and camid/sub are two separate hubs, consumer id prefixes distinguish ws / flv / hls / webrtc and other types, and the counters are cumulative — diffing two polls yields fps and bitrate. The dashboard’s link tree draws the sub-stream as its own dashed branch with differential fps/kbps and consumer types; it appears while consumers exist and disappears after recycling.

Three log keywords are worth knowing: sub-stream live for a pull starting, recycled reason=idle for idle recycling, and WHEP: sub-stream not servable over WebRTC for an H.265 sub-stream falling back to main — expected behavior, not a failure.
