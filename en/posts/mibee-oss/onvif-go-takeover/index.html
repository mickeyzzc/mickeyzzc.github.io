Taking Over onvif-go: Real-Camera Fixes, Zero Dependencies, and Service Facades

August 27, 2026 August 27, 2026 MiBeeOSS Go, ONVIF, IP Cameras, Open Source MiBee Open Source Projects Series 1869 words 9 min read
🔊

MiBeeNvr talks to cameras over ONVIF, and this library is what sits underneath. ONVIF is the de facto standard for IP video surveillance equipment: device discovery, media profiles, PTZ control, event subscriptions — all one set of SOAP-over-HTTP service conventions. Any brand that claims ONVIF compliance can, in theory, be integrated through the same calls.

onvif-go is that stack implemented in Go. We did not write it from scratch: its upstream was 0x524a/onvif-go — the previous author reshaped it into its modern form of a client plus a virtual camera server (the git history still traces back to earlier Go ONVIF attempts in the community). But upstream stalled entering 2026: the last merged PR landed in mid-January, the v1.0-through-v1.1.3 release cadence from late 2025 never resumed, and three Improve Test Coverage issues filed in November 2025 sit unclaimed to this day. Meanwhile we hit two problems in our own camera pool that could only be fixed inside the library.

We forked in July 2026, fixed the two real-camera issues first, then rebuilt the engineering foundation and shipped v1.2.0 in August. The rest of this post comes in three parts: what the library can do, how the two camera fixes came about, and the engineering ledger of the takeover.

Why upstream stopped where it did

The facts first. The upstream timeline went roughly like this:

  • November 2025: v1.0.0 through v1.1.3 shipped within a week; device, media, PTZ, imaging, and discovery services took shape;
  • December 2025: Event and DeviceIO services added, Media WSDL operations completed;
  • mid-January 2026: the last merge; nothing substantial on main since.

Judged purely as a tool project, “feature-complete so no more updates” is defensible — the protocol is stable and code does not rot that fast. Our situation was different: MiBeeNvr depends on this library for nearly everything. Discovery, configuration reads, stream URIs, PTZ, events — all of it goes through here. When the library freezes, the whole camera-integration layer of the NVR freezes with it. Faced with a bug there were only two options: route around it, or fix it ourselves.

The two real-camera issues below settled the argument: routing around was not possible.

What the library can do

ONVIF splits device capabilities into a group of SOAP services, and the library exposes seven client-side service facades to match:

FacadeEntry pointTypical operations
Deviceclient.Device()Device information, capabilities, system time, reboot; network/WiFi/certificate/storage config
Mediaclient.Media()Profiles, stream URI, snapshot URI, video encoder, audio, OSD overlay
PTZclient.PTZ()Continuous/absolute/relative move, stop, presets, status
Imagingclient.Imaging()Imaging settings read/write, focus drive
Eventsclient.Events()PullPoint subscription and event pulls
DeviceIOclient.DeviceIO()Relay outputs, video output configuration
Securityclient.Security()Device-side user management

Around the client core, four supporting pieces deserve their own mention:

  • discovery package: WS-Discovery multicast probing plus directed probing. A single call to discovery.Discover(ctx, timeout) returns every discoverable device on the network;
  • server package: a virtual ONVIF camera implementing Device/Media/PTZ/Imaging. Automated tests cover request—response semantics without any physical camera attached — particularly useful in CI;
  • testing package: mock server, golden files, capture replay. The captures directory under testdata holds SOAP recordings from real cameras across brands as regression material — bugs get fixed against actual wire traffic, not guesses from spec documents;
  • cmd/: four small CLI tools — discover, onvif-quick, onvif-diagnostics, onvif-server.

Callers deal with just two layers: Client and facades. Client handles connection, credentials, and clock skew — transport concerns only — while operations live on the facade of their respective service domain and funnel into internal/soap for SOAP enveloping and WS-Security signing. One detail that matters for embedded deployments: go.mod contains no require block at all — the library depends solely on the standard library.

On compatibility, the library has been verified against Hikvision, Axis, Dahua, Bosch, Amcrest, HiSilicon-OEM hardware, and a minimal ESP32 ONVIF implementation — part of that via our own camera test fleet.

Two fixes straight from real cameras

Both problems were fixed within the first week of the takeover, and both are the direct evidence for why takeover was necessary.

Clock skew broke authentication

Symptom: at some deployment sites, a Hikvision camera rejected every authenticated request with sender not authorized. Credentials were correct; the digest algorithm was correct.

The root cause lives in the time window of the WS-Security UsernameToken digest. Password_Digest is computed from a nonce, the Created timestamp, and the password, and receivers validate whether Created falls within their replay window — ±5 minutes on Hikvision. The NVR host follows NTP; cameras are not necessarily hooked up to it. Once clocks diverge, Created drifts outside the window and the entire batch of digests becomes invalid. This only surfaces on sites where clocks disagree — in the lab, where every camera ticks in sync, nothing reproduces.

The fix adds SetClockSkew to both Client and the underlying SOAP layer: measure the offset between device time and local time via GetSystemDateAndTime, then convert Created into the device’s clock frame when signing. Whoever owns the validation window gets their own clock used for signing. The default offset is zero — behavior identical to before unless configured.

The diagnosis itself was not hard; the barrier was thinking of clocks at all. The error message points at authorization failure, so credentials and hashing naturally get checked first. The real tell is comparing host time against the camera’s reported system time once.

A capability list advertising a dead address

Background: when a camera changes IP due to DHCP reassignment or AP roaming — an everyday case an NVR must self-heal from — GetCapabilities may keep listing stale addresses in XAddrs. media_service and other sub-services still carry the IP the camera remembers: the device answers at its new address while its capability list advertises an old dead one.

The existing fixLocalhostURL handled firmware quirks that advertise loopback addresses (127.0.0.1, localhost, ::1), but had no answer for “stale yet routable”. The result: GetProfiles targeted the dead address, failed with no route to host, and blocked recorder startup.

The fix is fixServiceURL: whenever a capability XAddr host disagrees with the device_service endpoint host, rewrite it to the address we actually reached the camera on — which is current by definition — preserving each sub-service’s own port. The loopback correction became a subset of it.

mermaid
flowchart TD

    CMP -- "yes" --> USE["Use as-is"]
    CMP -- "no" --> RWR["Rewrite to reachable IP<br/>keep service ports"]
    RWR --> GO["Sub-service endpoints<br/>point at correct new address"]

This unlocked the NVR’s IP rediscovery loop: once rediscovery updates the device_service address, Initialize now produces endpoints pointing at the new address, and the self-healing cycle no longer stalls at “found the new IP but cannot use it”.

Those are the changes visible at the usage level. What follows is the engineering ledger of the takeover, written for people evaluating migration costs or planning to read the source.

Engineering ledger

Identity and toolchain reset

  • Module path moved from github.com/0x524a/onvif-go to github.com/mickeyzzc/onvif-go, effective with v1.2.0;
  • Go 1.26, with .go-version pinning the toolchain;
  • Six CI workflows consolidated into ci.yml (lint + race tests + build) and release.yml (cross-platform CLI artifacts); dead codecov, sonar, and stale workflow configs removed;
  • golangci-lint config rebuilt to the same v2 ruleset MiBeeNvr uses; Makefile restructured;
  • LICENSE keeps the original copyright notice via a continuation line, still MIT; README rewritten as a continuation statement.

None of this is technically deep, but it decides whether a fork stays a pile of private patches or becomes a project others can collaborate on — whatever people go get should be a complete identity, not an island.

Getting the baseline green

Six failing tests dated back to upstream. After working through them they fall into two groups. One genuine bug: StorageConfigurationData.StorageURI lacked an xml tag, so the field name never matched the StorageUri element devices actually emit and storage URIs always parsed empty — fixed by adding the explicit tag. The rest were defects in the tests themselves: a SOAP 1.1 envelope fed to an Envelope type that only understands 1.2, assertions frozen at pre-loopback-fix semantics, Windows loopback interface naming breaking a probe.

make test has been green since. Everything that followed was demolition work done on a floor that screams the moment something breaks — attempt large-scale refactoring before that step and you are knocking out load-bearing walls blindfolded.

Zeroing third-party dependencies

Upstream had pulled in an RTSP toolchain along the way: rtspeek had exactly one consumer, the two-thousand-line interactive CLI onvif-cli. The call this time was to cut the whole thing — CLI deleted, along with a dozen overlapping or stale examples, an accidentally committed Linux ELF, one-off scripts, and duplicate capture directories. After go mod tidy, go.mod carries no require block at all.

For a library meant to run inside firmware and stay resident in an NVR long-term, the dependency tree is audit cost. That cost is now zero.

API consolidated into service facades (BREAKING)

The largest change. Upstream bolted hundreds of operation methods flat onto the Client type while the type also carried connection management, SOAP, and download transport — three jobs at once. The consolidation produced the two-layer structure in the architecture diagram above:

Client retains exactly four transport concerns — connection, credentials, clock skew, download. The seven facades are stateless, constructed on demand, and sharing a single Client across goroutines is safe. Companion moves: the 3.9k-line media.go split into five topic files (profiles/stream/encoder/audio/osd), and all one hundred thirty types formerly buried inside method bodies hoisted to package level with zero name collisions — tests, the server package, and external tools can reference these ONVIF structures directly for the first time.

Tree-wide formatting (gofumpt + goimports) landed in an isolated commit to keep later diffs reviewable; golangci-lint findings are down to zero.

Migration notes

Replacing the import path takes one command:

# v1.1.x and earlier
go get github.com/0x524a/onvif-go

# v1.2.0 onward
go get github.com/mickeyzzc/onvif-go

Method calls migrate mechanically per the table below; tags v1.0.0 through v1.1.7 remain in the repository as historical reference.

v1.1.x flat methodv1.2.0 facade call
client.GetDeviceInformation(ctx)client.Device().GetDeviceInformation(ctx)
client.GetProfiles(ctx) / client.GetStreamURI(...)client.Media().GetProfiles(ctx) / client.Media().GetStreamURI(...)
client.ContinuousMove(...)client.PTZ().ContinuousMove(...)
client.CreatePullPointSubscription(...)client.Events().CreatePullPointSubscription(...)

If you are starting fresh against multi-brand ONVIF cameras and want no third-party dependency tree on the SOAP/XML side, use this continuation line directly; for existing deployments migrating over, apart from the import path and facade call replacements there is nothing else to migrate.
