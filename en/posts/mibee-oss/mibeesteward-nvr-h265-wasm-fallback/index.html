MiBeeNvr's H.265 WASM Live Playback: Honest Degradation Based on Decode Time

November 17, 2026 November 26, 2026 MiBeeOSS H.265, WASM, Streaming, Open Source MiBee Projects Series 2047 words 10 min read
🔊

Browser support for H.265 is patchy: WebRTC’s WHEP track cannot carry H.265 at all, HTTP-FLV’s mpegts.js cannot decode it, and HLS over MSE looks “supported” in quite a few browsers while silently dropping the fMP4 bytes and leaving the picture stuck at readyState=1 (HAVE_METADATA). Pick the wrong protocol for an H.265 camera and you get a black screen with a spinner.

MiBeeNvr covers this path with a libde265 WASM software decoder: NAL units go into WASM, come out as YUV, are converted to RGBA, then render through Canvas2D or WebGL2/WebGPU. It does not need HTTPS — WebCodecs is undefined in a non-secure context — so plain HTTP can still play H.265. But software decoding moves the cost from the server to the viewer’s CPU: a 4K stream measured about 0.2fps against a 15–25fps source. Once decode falls behind, the backlog grows and the viewer ends up looking at green or white concealment blocks across the lower half of the frame.

Mainstream NVRs have another answer to the same problem: transcode H.265 into H.264 before handing it to the browser, so compatibility is settled on the server side. go2rtc and Frigate take that route; MiBeeNvr takes the problem into the browser with a WASM software-decode fallback, then adds a degradation layer driven by measured decode time. The two routes pay for the fix on different machines and in different code.

What others do

go2rtc is a zero-dependency standalone streaming application that accepts and emits RTSP, WebRTC, MSE, HLS and more. Its attitude toward H.265 is spelled out in the codecs-madness table in its README: WebRTC and MSE carry H.265 only on Desktop Chrome 136+, Edge and Android Chrome 136+; on the Apple side WebRTC H.265 requires Safari 18+, iPhone Safari 14+ has MSE marked flatly no!, while HLS does carry H.265 on Apple devices. The same device gives a different answer depending on the protocol.

Its answer is to select a route rather than decode locally. Codec filters on the URL — ?mp4 or ?video=h264,h265&audio=aac — pick a suitable track from the sources already present; if a needed codec is missing, an FFmpeg source is added to supply it. The README is blunt about this: there are no plans to embed complex transcoding algorithms inside go2rtc; FFmpeg does that job, hardware acceleration included. Automatic matching across sources (multi-source two-way codec negotiation) is one of its main features. The README’s negotiation example is concrete: a camera can send H.264/H.265 video and AAC/PCMU/PCMA audio, while the browser receives H.264/VP8/VP9/AV1 and sends OPUS/PCMU/PCMA. The audio sides do not overlap, so an FFmpeg source is attached to the same stream to produce OPUS. It does not change the browser’s decoder; it fills in the stream. For go2rtc, H.265 belongs to protocols and tracks.

Frigate pushes that route further. Its live-view docs recommend configuring cameras for H.264 + AAC and explicitly warn against smart codecs such as H.264+ and H.265+, because those non-standard modes remove keyframes and lengthen startup time; the I-frame interval should match the frame rate or the first decodable frame arrives too late. The player fallback chain is MSE → WebRTC → jsmpeg: with go2rtc configured, MSE is the default, WebRTC is attempted when MSE fails or two-way talk is needed, and jsmpeg is the last resort. When playback fails, the UI prints an explanation — startup, mse-decode and stalled each come with a “what it means / what to try” note. WebRTC itself cannot carry H.265; Frigate’s troubleshooting guide tells owners of H.265 cameras to point live view at an H.264 substream and keep the H.265 main stream for recording, or transcode with go2rtc’s #video=h264#hardware, with a warning that software HEVC transcoding is very CPU heavy. Its troubleshooting order follows the same logic: read the go2rtc logs, try the MSE and WebRTC links separately in the web UI on port 1984, then inspect the codecs actually negotiated via /api/go2rtc/streams. Only after H.265 is confirmed does transcoding come up.

Both treat “can I watch this” as “does the server produce a track the browser can decode”, with the UI explaining and steering the user toward a config change. The price is transcoding CPU: go2rtc hands it to FFmpeg, and Frigate’s own docs admit software HEVC transcoding is expensive and recommend hardware acceleration. That route assumes you control the server and have headroom for transcoding. MiBeeNvr’s case is plain HTTP with no HTTPS and no guarantee of a transcoding service, so the problem is taken into the browser instead.

Where the corruption comes from

For every frame, the WASM decoder calls libde265’s pushNal and decode. A failed push breaks the reference chain: the following P-frames have no reference and decode into pictures with concealed regions. What error concealment fills in is not the original picture content but the decoder’s attempt to keep the whole frame from collapsing; on a surveillance feed those blocks are more conspicuous than a missing frame. libde265 warnings (error codes ≥1000) are quieter — not hard errors, but the pictures they produce can still carry hidden areas that flash onto the screen.

The old strategy was to push through: keep feeding, keep decoding, retry on failure. On a weak client that does not work. As soon as decode time stays above the frame interval, the queue only gets longer and the picture gets worse.

Measuring instead of guessing

The degrade decision now ignores device models and static capability tables. It looks at two measured numbers.

The first is decode time: timestamp on entry to decode(), timestamp on exit, difference smoothed with an EMA — _decodeMsEma = ema * 0.8 + ms * 0.2. The second is the source frame interval: milliseconds derived from the 90kHz PTS delta between consecutive frames ((pts - lastPts) / 90), smoothed with a 0.9/0.1 EMA, accepting only intervals from 1 to 10000ms and falling back to 66ms when none is available.

The two EMAs use different weights on purpose. Decode time shows up as short spikes, so 0.2 lets the value follow a single stutter. The frame interval comes from source PTS and is held steadier with 0.1, so one jittery frame cannot inflate the budget. The budget is the source interval rather than a fixed number — 1080p at 20fps and 4K at 15fps leave very different amounts of time for decoding, and a fixed 66ms would misjudge the former as undecodable.

The first 4 frames are ignored so the EMA and the interval can settle. After that, _decodeMsEma above 1.5 times the budget enters keyframe-only mode; it takes a drop below 0.5 times the budget to leave it. The gap between the two thresholds is deliberate — decode time hovering near one value cannot flip the mode back and forth.

Keyframes only

In keyframe-only mode, _keyframeOnly makes every non-keyframe return null — one IDR per GOP, a stable still image instead of a growing pile of half-decoded bad frames. This is not merely dropping frames: output collapses to one independently decodable picture per GOP, so a broken reference chain cannot poison the next round. A separate guard does something similar after a failed push: _skipUntilKeyframe is set and everything up to the next IDR is skipped; a clean picture clears the flag and normal decoding resumes.

Pictures that libde265 reports with warnings are no longer forwarded in degraded mode either. They carry concealed regions, and a single flash of one is visible corruption; dropping them leaves the last clean frame on screen. The trade is explicit: no frame rate, but no corrupted picture. When the stream resolution drops or the client catches up and decode time falls below half the budget, full frame rate resumes on its own.

Capability tables lie

The protocol-selection layer uses the same idea. Browsers offer a ready-made answer: MediaSource.isTypeSupported('hvc1'). On Chromium/Edge it returns true because the OS has an HEVC decoder registered for native <video> playback. But the MSE SourceBuffer silently drops appended fMP4 bytes, video.buffered stays empty, and hls.js and mpegts.js stall at readyState=1 with a black screen.

go2rtc’s codecs-madness table is about the same reality: the H.265 answer changes with the protocol on one device. The difference is that it publishes the table for people to configure against, while MiBeeNvr refuses to assume the table is right and runs the probe. Create a throwaway MediaSource, add a SourceBuffer for video/mp4; codecs="hvc1.1.6.L93.B0", append a real HEVC init segment, wait for updateend, then check whether video.buffered.length is greater than zero. The result is cached in sessionStorage under mibee_mse_h265_probe so a session does not pay for the probe twice. A real probe has to create a MediaSource, append bytes and wait for events, so it cannot sit in the synchronous path of every protocol switch; the cache is session-scoped, meaning a new tab probes again and one bad result does not carry into later sessions. Until the probe completes, H.265 is treated as unsupported and routed to the WASM/WebCodecs player, which is the path known to produce frames. Likewise, probeCaps() probes webCodecs, mseH265, wasmH265, webgpu, webgl2 and hevcDecode once and caches the result, instead of re-probing inside a reactive path and triggering a reconnect storm.

Telling the user

Degradation is not a quiet swap that leaves a convincing-looking black screen behind. Players report state through a statechange event and the status dot in the top-left corner follows the real state. Before a downgrade, the last clean frame is captured as a freeze frame, so a protocol switch shows a still image rather than a black flash. Across protocols, a failure demotes immediately, a sustained degraded state demotes after 8 seconds to debounce a brief rebuffer, and a toast fires once; when H.265 cannot go over WebRTC, the UI says outright that it switched to another protocol for compatibility. A user-pinned protocol is respected — automatic degrade and upgrade both leave it alone. Similar to Frigate printing the reason for a player failure in the UI, MiBeeNvr carries the state on the status dot, so the user can tell which path is live without opening the browser console.

Where the trade lands

Both routes skirt the same fact: H.265 compatibility has no single answer. The transcode route keeps the uncertainty on the server and hands the browser only H.264; the software-decode route keeps it in the browser and contains it with runtime feedback.

Transcode route (go2rtc / Frigate)Client-side decoding (MiBeeNvr)
Where compatibility is settledServer produces a track the browser can decodeBrowser decodes H.265 to YUV and renders it
Who pays CPUThe server; transcode headroom needed, hardware acceleration preferredThe viewer; a 4K stream measured far below source frame rate
Implementation costCodec negotiation + FFmpeg source + config guidanceEMA, two thresholds, keyframe mode, real capability probe, state reporting
What the user sees on failureUI explains and suggests an H.264 stream or transcodingStatus dot, freeze frame and one toast
Protocol prerequisiteWebRTC needs a secure context and port setupPlain HTTP works; no HTTPS dependency

Static capability tables lie: isTypeSupported and browser version tables are only claims; injecting real data and backing it with runtime feedback is more reliable. A degrade decision needs hysteresis — enter at 1.5, leave at 0.5, or jitter around the threshold will flip the mode back and forth. Degradation should be visible: with a status, a freeze frame and a notice, there is no need to pretend nothing happened through a silent swap.

The choice itself is fairly concrete: if the camera can be switched to H.264 and the server has transcode headroom, the transcode route is the simpler one, which is what Frigate recommends. Client-side WASM earns its keep when the only source is H.265, the path is plain HTTP, and there is no appetite for another transcoding process on the server — at the price of the whole runtime layer described above.

The transcode route puts CPU and complexity on the server; WASM puts both in the browser.
