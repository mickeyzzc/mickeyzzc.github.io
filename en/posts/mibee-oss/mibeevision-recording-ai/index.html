MiBeeVision: An Understanding Engine for MiBeeNvr's Recordings

November 9, 2026 November 9, 2026 MiBeeOSS NVR, Object Detection, ONNX, ByteTrack, Self-Hosted, Rust MiBee Projects Series 3329 words 16 min read
🔊

The NVR keeps one promise: footage is always being recorded. Once the recordings pile up, a new problem appears — who watches dozens of gigabytes of playback? Scrubbing timelines afterwards to find “when did that person walk in” still relies on human eyes. MiBeeNvr’s browser-side AI watches the live view while the page is open, and stops the moment the tab closes. What is missing is a component that runs independently of any page, around the clock, over the recordings.

That is MiBeeVision: the video-AI post-processing engine of the MiBee ecosystem and the “AI brain” of MiBeeNvr — it runs object detection, multi-object tracking and zone rules over the NVR’s recordings, produces structured events with bounding-box snapshots, and writes everything back to the NVR. The division of labor in one sentence: the NVR makes sure footage is captured, MiBeeVision makes sure it is understood. Recordings are analyzed segment by segment as they appear; every segment in the recording list carries an AI badge, and people or vehicles appearing, zone intrusions, line crossings and loitering all become events you can look up later.

How it relates to the NVR’s built-in browser AI

MiBeeNvr ships with browser-side AI detection whose inference runs in a Web Worker. The two are complements, not substitutes, and the boundary is precise:

Browser AI (built into the NVR)MiBeeVision (server-side)
Runs inA Web Worker inside the browserA standalone process (same host as the NVR or a separate machine)
When it analyzesThe live view while the page is openRecordings, segment by segment, 7×24 regardless of any page
Event retentionMostly live on-screen boxesStructured events in a database + boxed snapshots, traceable
RulesROI polygons (targets inside an area)Event rules: zone intrusion / line crossing / loitering
Where results goThe live viewWrite-back to the NVR: AI badges in the recording list + the AI events page

The two switch independently and do not affect each other. Browser AI alone means judgment exists only while someone is watching; Vision alone means the live page loses its instant boxes. Running both — someone watching in real time, everything searchable afterwards — is the complete setup.

Technical form

  • Rust single binary: Linux x86_64 / aarch64, no external dependencies — the only bundled file is the ONNX Runtime shared library (the inference runtime is loaded dynamically, which is why its path must be given explicitly).
  • FFmpeg decoding: consumes NVR recording segments directly, no pre-transcoding needed — whatever format the recordings are in, it decodes them.
  • Embedded web config page (default port :9092): enter the NVR address and API key, pick a camera, draw rule zones, effective on save — fully graphical, no hand-edited config files.

Making it a standalone process rather than folding AI into the NVR’s main program is a deliberate architectural choice: analysis is continuously CPU-hungry work, and the NVR host (often a low-power NAS or ARM box) may not carry it well. A separate process can be moved to another machine without touching capture or playback on the NVR.

Architecture: Source → Pipeline → Sink

Vision uses a layered pipeline, each layer behind an interface and composed by configuration:

LayerRoleDetails
SourceProduce recording segmentsSame host as the NVR: local_file (shared recording directory, reads files directly); separate machine: http_download (downloads segments from the NVR). Changes take effect on save
PipelineTurn frames into judgmentsFFmpeg decode → YOLOv8n detection (ONNX Runtime) → ByteTrack multi-object tracking → zone intrusion / crossing / loitering rules
SinkTurn judgments into recordsEvents into SQLite/libSQL; a boxed snapshot per event; state and events written back to the NVR

The two Source modes encode two deployment philosophies: local_file requires Vision to share the NVR’s recording storage directory — zero network copying, suited to running the analyzer on the NVR host itself; http_download makes split deployment possible — the CPU-hungry analysis load moves off the NVR host, which keeps doing its own job while the analysis machine pulls segments and crunches them. Both are selected and saved in the config page; switching needs no command line.

The runtime form is a resident serve process: it stays up and continuously consumes newly generated recording segments. Camera selection, rule zones and transport mode all change in the config page; saving restarts the pipeline automatically.

Three design principles worth stating separately:

  • Decoupled from the NVR: Vision is an independent process — if the NVR dies, Vision is unaffected, and the reverse holds too. An analysis component should not share a fate with the storage component. The NVR remains the data and semantic hub: it decides which segments Vision analyzes, and consumes what Vision concludes.
  • Every layer is replaceable: segment sources, detection models and event outputs sit behind interfaces. Swapping a model, a store, or adding an output channel is “add one implementation”, not “rewrite the chain”.
  • Zero cloud dependency: inference, rule judgment and storage all happen locally, with no calls to any external service.

Detection has no knobs: YOLOv8n is built into the binary — no model downloads, no model selection; decoded frames go straight into the detector. This is a deliberate trade-off: Lite’s positioning is “install and it works”, and model swappability is left to later editions.

Tracking is the link between detection and rules, and the one most easily underestimated. Detection boxes go to the ByteTrack tracker frame by frame for cross-frame association: the same target keeps the same ID across consecutive frames and forms a trajectory. Tracking upgrades “there is a box in every frame” into “where this target came from, where it went, and how long it stayed” — without trajectories, loitering detection and crossing-direction judgment are impossible; without tracking, the same target re-appearing across frames gets counted again and again, and the event list drowns in duplicates of one target.

The three event rules

All three rules are configured per camera in the config page (rule name + zone vertices), effective on save. The overview first:

RuleTriggerTypical scenes
Zone intrusionTarget enters a drawn areaYards, shop entrances, warehouses
Line crossingTarget crosses a drawn boundary line (direction judged)Fences, yard gates, passages
LoiteringTarget dwells in an area too longPerimeters, doorways, ATMs

The three split by “spatial semantics”, each answering a different real-world question.

Zone intrusion answers “who entered where they should not”. Draw a polygon in the config page — a corner of the yard, a warehouse doorway, the counter of a shop — and the moment the tracker judges a target has entered, the event fires. It fits scenes where “appearing is the anomaly”: the normal state is empty, and presence is the signal.

Line crossing answers “who crossed from the wrong side”. It draws not an area but a boundary line, with direction judged — fences, yard gates and passages where entry is only legitimate from one side fit best. Direction is the dimension intrusion rules cannot express: walking out through the yard gate is daily life; climbing in from outside is an event. Same line, reversed direction, reversed meaning.

Loitering answers “who has been here too long”. Entering the area is not the signal; dwelling past a time threshold is — someone pacing along a perimeter, lingering at a doorway, standing at an ATM. It is built on the trajectories tracking provides: without “how long has this same target been here”, loitering cannot be judged.

One camera can carry several rules at once, each with its own areas and lines, independent of each other.

One port: :9092 (the embedded config page), deliberately offset from MiBeeNvr’s :9090 and MiBeeSteward’s :8080, so all three ecosystem components can run side by side.

Working with MiBeeNvr

Vision and the NVR are natural partners: the NVR provides the footage, Vision provides the judgments, and the judgments return to the NVR for display. Three wiring steps:

  1. Generate an API key on the NVR: “Settings → AI Detection → Generate API Key”; the key starts with mbv_;
  2. Enter it in Vision’s config page: open http://<vision-host>:9092, enter the NVR address, paste the mbv_ key, click “Test connection and fetch cameras”;
  3. Pick a camera, draw rules: choose the camera to analyze (Lite: one), enter rule names and zone vertices, click “Save” — the pipeline restarts automatically and analysis begins.

Two prerequisites; missing either one shows up as “the config page opens, but no events ever appear”:

PrerequisiteWhat missing it causes
ORT_DYLIB_PATH must point at the bundled libonnxruntime-*.soThe inference library fails to load and the pipeline cannot process segments (the config page still opens — highly misleading)
Use the mbv_ API key, not the web login token (mbs_)Event write-back returns 401, and the NVR’s AI status stays empty forever

The mbs_ token is valid only for browser sessions; the mbv_ API key is what gets issued to external components like Vision. They look alike and their uses are strictly separated.

Two deployment topologies; pick the transport ([transport].type) in the config page and save:

TopologyTransportRequirement
Vision on the same host as the NVRlocal_fileVision can read the NVR’s recording storage directory directly (paths match)
Vision on a separate machinehttp_downloadVision can reach the NVR over the network; segments download before analysis

If the log shows “failed to open video, skipping: No such file or directory” on a split deployment, it is almost always local_file used on a topology with no shared storage — transport mode and topology must match.

Results flow along three lines: after the NVR’s segments are analyzed, one line becomes the AI status badges in the recording list (in progress / completed), one becomes AI events (zone intrusion / line crossing / loitering) written back to the NVR’s AI events page, and one becomes boxed snapshots kept locally in Vision. The end-to-end self-check is explicit: the config page status area shows “pipeline running / NVR connected”, and a few minutes later the AI status column in the NVR’s recording list shows completed.

On version pairing: Vision runs its own version line (mibee-vision-vX.Y.Z), independent of NVR version numbers; use an NVR version from the same period or newer than Vision Lite so the AI status and event interfaces are available.

The final self-check: the status area shows “pipeline running / NVR connected”, and a few minutes later the AI status column in the recording list shows completed — once that word appears, the whole chain is up.

How events become notifications: the Bell hand-off

Vision itself sends no notifications; its output is events written back to the NVR. The notification exit sits one ecosystem ring away: MiBeeNvr has built-in alert-notification outbound — camera offline, picture freeze, storage health, motion detection, AI events, doorbell and GB28181 alerts are POSTed as mibee-alert/1 JSON messages to a webhook receiver, with AI events typed ai.detection (snapshot URL carried in the notification). MiBeeBell is the out-of-the-box receiver for that outbound stream — so the full chain reads: Vision produces an event → written back to the NVR → the NVR’s alert rules send it out → Bell’s pipeline dedupes, cools down and silences → delivered to your chosen channels. Each ring does its own job: Vision does not overstep into notifications, and Bell does not care about detection.

Where the alternatives sit

Video AI is a crowded field with three basic plays: all-in-one NVR+AI, an AI layer added to an existing NVR, and generic vision API servers.

RouteRepresentativesWhat you getWhat you pay
All-in-one NVR+AIFrigate (MIT, open source)Recording + detection in one; Coral TPU / OpenVINO / GPU / CPU inference tiers; MQTT events + official Home Assistant integration; Frigate+ subscription for custom model trainingHand your whole recording pipeline to it; notifications and display are built outside
Smart-home NVRScryptedSmooth HomeKit / HA integrationNVR capabilities revolve around the home platform
Generic vision APIDeepStack (discontinued) / CodeProject.AI / DOODSAn API that returns boxes and labels, consumable by anythingRule semantics, tracking, event lifecycle, and write-back display are all DIY; upstream maintenance risk is yours
Commercial NVR + bolt-on AIBlue Iris + CodeProject.AIMature recording on Windows + external detectionCommercial license; a resident Windows box; the AI process needs caretaking
Commercial smart NVRAcuSense / WizSense classLocal smart detection out of the boxLocked to vendor hardware and cloud activation; closed event ecosystem
AI layer for an existing NVRMiBeeVisionDetection → tracking → rules → events → write-back in one piece, output living inside the NVR, notifications via BellBound to the MiBeeNvr ecosystem; Lite is single-camera CPU

Frigate is the recognized all-in-one benchmark of the open-source lane: recording and detection unified, the broadest hardware-acceleration ecosystem, and a nearly seamless experience for Home Assistant users. Choosing it means handing over the recording pipeline too — for users with an existing NVR that is a migration, and notifications/display still get built outside it. The Frigate+ subscription adds custom-trained models, one path around a fixed built-in model, at the cost of an ongoing subscription.

Blue Iris + CodeProject.AI is the Windows playbook: a commercial NVR with a generic AI process attached. The maintenance risk of this “generic API” route has become visible over the last couple of years: DeepStack’s site went down and the community migrated wholesale; after CodeProject.AI took over, 2025 saw community discussion about its future and complaints about reliability in the 2.8/2.9.5 releases. An API server only returns boxes and labels — zone-rule semantics, event lifecycle, and write-back display all need another layer built on top.

Scrypted, Shinobi and Viseron each have their own AI paths, leaning smart-home, plugin ecosystem, and local-first respectively, with uneven maintenance cadence and ecosystem breadth. Commercial smart NVRs work out of the box, but getting their events into your own notification chain is basically second-system development.

MiBeeVision occupies the “AI layer for an existing NVR” position: detection, tracking, rules, events and write-back display in one piece, with the output living inside the NVR (AI badges + the AI events page) and notifications flowing through the NVR’s outbound alerts plus the Bell pipeline — no NVR replacement, no second system. The boundaries, stated just as plainly: it is bound to the MiBeeNvr ecosystem and is not a generic NVR component; Lite is single-camera CPU inference with the YOLOv8n model fixed (not swappable); multi-camera and GPU acceleration are in the planned edition. For deep Home Assistant integration or Coral acceleration, Frigate is the more mature answer.

A few common questions

Does it need a GPU? Lite does not: ONNX Runtime CPU inference runs on an ordinary x86 server or ARM device. GPU acceleration (CUDA / TensorRT) and multi-camera belong to the Pro edition (planned, TBA).

Where do results live? Two places: on the NVR, the AI badges in the recording list + the AI events page; in Vision locally, structured events (SQLite/libSQL) + boxed snapshots. The NVR side is for viewing results; the Vision side keeps the raw records.

What about analyzing recordings that already exist? Batch re-analysis of stock footage is on the Pro capability list (planned, TBA). Lite currently targets continuous analysis of newly produced recordings.

Windows / macOS? Not provided; current platforms are Linux x86_64 / aarch64. To view results from those desktops, open the NVR’s page — results live in the NVR, and the analysis host’s operating system does not matter.

Editions, license and boundaries

MiBeeVision runs its own version line (mibee-vision-vX.Y.Z), independent of MiBeeNvr version numbers; the two evolve separately. Two tiers:

DistributionFree with the MiBeeNvr releases hubTBA

The license situation, stated plainly: the software itself is proprietary, copyrighted by MiBee Studio, with the Lite edition distributed free through the MiBeeNvr releases hub; the bundled detection model YOLOv8n is licensed by Ultralytics under AGPL-3.0, and using this program for detection constitutes acceptance of that model’s obligations — commercial closed-source distribution requires separate authorization (or replacing the model with a permissively licensed one).

The boundaries, one more time: Lite is single-camera, CPU inference, fixed model, aimed at continuous analysis of new recordings; it is bound to the MiBeeNvr ecosystem and not a generic NVR component; batch re-analysis, multi-camera and GPU acceleration sit on the Pro roadmap with timing TBA. Its place in the studio ecosystem: the NVR handles capture, playback and alert outbound, Steward handles device assets, Bell handles the notification pipeline, and MiBeeVision fills in “what actually happened in the footage”.
