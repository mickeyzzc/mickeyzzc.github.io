Four Releases in One Day: Steward on the Router, Nvr on the Desktop, and the onvif-c / serialtap Debuts

September 20, 2026 MiBeeOSS MiBeeSteward, MiBeeNvr, ONVIF, OpenWrt, ESP32, Serial Debugging, Go, Open Source MiBee Open Source Projects Series 1866 words 9 min read
🔊

On September 20, 2026, four repositories tagged releases on the same day — and they each happen to cover one stretch of the chain:

  • See what’s on the network — MiBeeSteward v0.6.0
  • Get your homemade camera recognized — onvif-c v0.1.0
  • Record the footage and play it back anytime — MiBeeNvr v0.13.0-preview.1
  • Have someone take notes on the serial console while you debug firmware — serialtap v0.1.0

The first two are routine iterations of existing projects; the last two are tagging v0.1.0 for the first time. What’s worth playing with in each release — and why it was built that way.

MiBeeNvr v0.13.0-preview.1: It Runs on Your Own Computer, and Streams Stack Higher

The most tangible change is the deployment form: the NVR no longer belongs only to servers. Windows gets a double-click Setup exe that settles into the system tray (open UI, quit, and the listen address all live in the tray menu); macOS gets a DMG with a menu-bar helper. The engineering beneath this form ran deeper than it looks: the Windows build compiles with the GUI subsystem so there is no cmd window at any point; upgrades swap the binary while running; the uninstaller stops the live service before deleting itself instead of dying half-removed; and the macOS menu-bar assistant went through several rounds of on-metal fixes for dialog visibility and quit-then-resurrect behavior. Desktop mode defaults to 127.0.0.1 with a local passwordless trust model — a deliberate boundary: the desktop form serves the machine it runs on; for remote access, return to the server deployment. Unsigned DMGs need right-click → Open on first launch.

Running on your own computer unlocks a practical trick: designate a few cameras to record as material, with files landing directly on the local machine — editing, evidence, demos, no copying from elsewhere.

Watch-only users are covered too: the storage settings gain a global “record by default” toggle — off means every camera without an explicit override (GB28181 auto-enrolled channels included) goes live-only, hot-applied on save.

The heavy lifting this release is storage and I/O, aimed at one question: how does a low-power device survive multi-stream writes:

  • Per-segment writer state: retained FDs, write coalescing, lock sharding — concurrent streams no longer squeeze through one lock
  • fallocate preallocation before writes, a finalizing truncate at close — less filesystem-metadata churn
  • posix_fadvise page-cache management with an adaptive merge buffer, so a big merge can’t eat the memory alive
  • A process-level I/O budget scheduler: merge, cleanup, and transcoding share one token bucket and yield to the recording main path — background load never starves recording
  • Deletes are billed too: a byte-rate guardrail plus directory-locality grouping, so cleaning old recordings stops hammering SD cards and USB disks
  • Fragments from flapping cameras fold in one batch, write amplification down to 1/N

Alongside: planned WAL checkpointing (idle-passive, journal-size capped) and adaptive GOMEMLIMIT (playing along with systemd/Docker memory quotas). Two off-by-default experimental features (sequential-append buckets, a transcode fragment floor) wait for the brave.

MJPEG recordings became single-file AVI containers this release — the old one-file-per-frame layout was an I/O stove on low-power devices: a 15fps MJPEG camera manufactures 900 tiny files per minute, and the directory entries and metadata write amplification eat you alive. Old recordings play as-is; mibee-nvr repair mjpeg-containerize migrates on demand. Speaking of MJPEG: those cameras now also have a proper RTSP output address (RTP/JPEG, RFC 2435) that third-party monitoring software can pull directly.

On the reliability front, several externally reported real bugs fell: SDP-only parameter-set cameras going fully dark in live view (common with older cameras whose handshakes yield no parameter sets), hls.low_latency being silently ignored, and empty playlists turning from fake data into 404s; a series of cross-engine merge × transcode races closed one by one.

Two acquisition notes: the mobile app is delayed by ICP filing; the fnOS store application is in with no callback yet, so installs and upgrades still run through GitHub — but this release fixes the SPA crash and login flip-flop behind fnOS unified gateways, with offline and online packages both shipping. Also new: a Gitee mirror (latest stable only) and the official Home Assistant integration.

Note this is a preview: features frozen, published for early validation; deployed instances’ update check never pushes previews — production waits for stable. Worth noting too: a new contributor landed 45 merged PRs in their first cycle, including the bulk of the storage I/O work.

MiBeeSteward v0.6.0: First, See What’s on the Network

A network and IoT asset inventory tool — it answers “what exactly is connected, and whose is each thing.” This release’s keyword: move into the router. Packages come in three forms — tarball, opkg .ipk, apk .apk — and the installer derives the network from uci, enables router-resident passive sources, and fixes ICMP permissions; agent enrollment can be inline or deferred (the service stays down, steps printed in the log). LuCI gains a services entry once installed; changing the port or password is page clicks — first run never touches SSH, the password is created in the browser, and the installer prints no temporary credentials.

Living on the router means seeing what nothing else sees: WiFi association records (who, how strong, since when), DHCP allocations (who holds which IP, claiming what hostname), DNS queries (who asks for what). This release feeds DHCP-lease hostnames and overheard mDNS/SSDP announcements straight into the fingerprint classifiers — smart plugs, robot vacuums, and air monitors that never answer any probe still get branded; a new Mijia-ecosystem hostname corpus covers a dozen-plus previously silent device families. The loose end from last week’s controlled comparison — passive sightings on dual-homed routers attributed to the wrong segment — is fixed with IP→CIDR attribution and per-source counters.

Worried about scanning your own home? Demo mode spins up a fake network to play with, cleared by one click.

The distributed form gained multi-vantage probing: plans go down the command channel to each agent, results stream back per vantage, and the UI compares them side by side; agent network scans schedule natively, and roaming devices are no longer killed by stale leases. SNMPv3 credentials live only in the agent’s local encrypted vault — names travel, secrets don’t.

On the engineering side, the headline is openapi.yaml as the single source of API truth: the TS and Go clients are generated from it, CI checks for drift, and the frontend’s hand-written wire types are retired — the “trend chart reads a nonexistent field” bug fixed this round is the classic way those types crash. Two upgrade notes: list endpoints are uniformly pagination-wrapped and bare arrays are gone (adjust hand-rolled scripts accordingly); the (ip, network) unique index was never enforced on fresh installs and is deduped and rebuilt on first start after upgrade, backup taken first. The quality campaign pushed CI coverage to 85% and dug out four real bugs, all fixed.

Binaries are CGO-free; 32-bit ARM routers build locally with make build-linux-arm.

onvif-c v0.1.0: The Fifth Member of the Protocol Library Family

The ONVIF and national-standard stacks were previously four libraries: Go’s onvif-go and gb28181-go, Rust’s onvif-rs and gb28181-rs. Today the puzzle gains its fifth piece, onvif-c — a plain-C device-side library for ESP-IDF.

Its origin is mundane: the several ESP32 camera firmwares each carried their own ONVIF implementation, a maintenance burden three times over; the shared part is extracted and tended in one place, leaving only board-specifics (manufacturer, model, serial, IP, stream URI, HTTP port) in the firmware, all behind a single onvif_c_config_t seam — nothing hardcoded in the library.

The coverage is a deliberate “minimal sufficient set” — exactly the actions an NVR asks when onboarding a camera:

  • SOAP Device/Media: GetSystemDateAndTime, GetDeviceInformation, GetCapabilities, GetProfiles, GetStreamUri, GetSnapshotUri
  • Pull-Point events: the MotionAlarm topic with State and a 0-100 Score
  • WS-Discovery responder: UDP 3702 multicast, unicast ProbeMatches, a Hello broadcast every 30 seconds, retrying until WiFi is up
  • Optional mDNS: _onvif._tcp, compiled out cleanly when espressif/mdns isn’t in the build

A few design choices deserve calling out. The event service does no long polling — PullMessages returns immediately, so esp_http_server workers never block; under ESP-IDF’s threading model that’s a hard constraint. There is no XML parser and no dynamic state: actions are detected with strstr(), responses assembled with snprintf(), all buffers per-request — a ~10KB footprint, zero third-party dependencies, 95% line coverage. The motion-detection hook is non-blocking and safe to call from sensor-callback context (a WiFi-CSI callback, say):

c
1

onvif_c_motion(true, 87);   /* MotionAlarm State=true Score=87 */

Its production pedigree shows in the details: response XML is byte-stable against MiBeeNvr (the NVR-side parser never flinches), field-tested against Hikvision-class clients. tools/onvif_probe.py <ip> is the no-hardware smoke test covering every action plus the full subscription cycle.

One boundary, stated flatly: this library does no ONVIF authentication. Anyone who can reach the port gets answered — trusted LAN only. A deliberate trade-off for leanness, not an oversight.

serialtap v0.1.0: A Byproduct of Debugging at Scale

A byproduct of writing those ESP32 firmwares: once boards multiply, opening a serial monitor on each one is a slog — hence a plug-and-record collector for Linux.

The most deliberate part of the design is identity: the USB physical port (by-path) is the device — re-enumeration changing ttyUSB numbers doesn’t matter, and identical adapters without serial numbers (CH340 ships none) don’t collide either. A 1-second poll finds devices, one collector goroutine per device, collecting on plug and stopping on unplug; CH340/CH343/CP210x/FTDI/native USB-CDC all recognized.

Logs are dual-channel: serial-date.log carries everything (millisecond per-line timestamps), while events-date.log carries only events — built-in ESP-IDF failure signatures (rst:0x reset banners, E ( error-level lines, Guru Meditation, WDT, Backtrace), extensible with your own regexes. decode-backtrace hands Backtrace address frames to addr2line for source-file:line output, auto-discovering the ESP-IDF toolchain. Post-crash review goes from eyeballing tens of thousands of lines to reading the event stream and opening the translated stack.

Debugging firmware eventually means flashing. The flash safety gate settles the classic accident of esptool and a resident collector fighting over the port: the flash command is orchestrated over a unix socket — yield → esptool → auto-resume — so the board is never dragged into ROM download mode by both ends; release temporarily yields the port to external tools, auto-reclaiming after 3 idle seconds.

Behind it sits a field finding worth recording: opening or closing a serial device pulses the board’s reset line — even on the ESP32-S3’s native USB-JTAG port, where the USB_SERIAL_JTAG peripheral implements CH340-compatible auto-reset semantics in silicon, measured as rst:0x15 (USB_UART_CHIP_RESET) 3 milliseconds after open. That’s host-side CDC handshake behavior; userspace cannot sidestep it. Hence serialtap’s discipline: open each physical device exactly once and hold it, never reopening periodically. The silent watchdog is off by default and enabled only for devices guaranteed to log periodically. Line assembly spans read chunks, and a trailing partial line at port close lands with a …partial marker — zero-loss logging.

A pure-Go static binary: no CGO, no libudev, fully vendored for offline builds, linux-amd64/arm64 cross-compilation copy-and-run.
