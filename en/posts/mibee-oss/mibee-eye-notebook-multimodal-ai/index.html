mibee-eye-notebook's Multimodal AI: How Nine Local Models Divide the Work, and How It Compares

October 3, 2026 October 7, 2026 MiBeeOSS Multimodal, Voice Interaction, Object Detection, VLM, Rust, ONNX MiBee Open Source Projects Series 3027 words 15 min read
🔊

The previous two surveys covered full-modal interaction — seeing, hearing, speaking, turn-taking, acting — from both the model and pipeline angles. This post lands on practice: what mibee-eye-notebook (below: notebook) is attempting is exactly running that multi-model cooperation approach inside one Rust project. First a breakdown of how it combines its models, then a comparison with a batch of open-source projects heading the same direction — where they converge, and where each makes different trade-offs.

What the Notebook Is

One sentence: a local capture agent that runs on a laptop (or any Linux machine). It captures the machine’s camera and microphone, encodes to H.264/AAC, and serves the streams over RTSP / RTMP / ONVIF / GB28181 to an external NVR — a “software camera” for MiBee NVR. It is one member of the MiBee Eye family, sharing frontend and API specs with mibee-eye-rs, mibee-eye-go, and mibee-eye-webui.

The engineering base determines what can be built on top, so three constraints up front — every model choice below follows from them:

  • Rust single binary: six crates (protocols / streaming / web / security / capture / observability), no ffmpeg and no Python at runtime — video encoding is in-process OpenH264, and all AI inference goes through three native routes: ONNX Runtime, llama.cpp, and sherpa-onnx (local dialogue requires a CPU with AVX2)
  • Resource budget: <5% idle CPU, <200MB memory, ≤16 concurrent streams (semaphore-controlled; inference thread counts are capped automatically so they don’t starve the audio callbacks) — these three numbers are design targets, not benchmark reports. This budget immediately rules out “keep one large model listening to everything”
  • Offline-first: all model files live in a local models/ directory and work without network; every engine is fail-open — a missing model or uncompiled feature only removes the capability bit from the API, never takes the service down

Nine Engines, Four Layers

The on-device intelligence currently spans nine model engines, layered by how often they run:

Three peripherals sit outside: PP-OCR v4/v5 (on-demand API, not in the always-on path), MeloTTS (reads LLM replies aloud), and pyannote segmentation + ct-transformer punctuation (meeting mode: transcribe meetings and separate speakers). All models together are about 1.7GB, all Apache-2.0 or MIT.

The layering encodes one simple principle: cheap models run always-on; expensive models trigger on events. Silero VAD takes under 1ms per frame and NanoDet-m is a lightweight detector — those two run 24/7. Qwen3 and Qwen3-VL are the most expensive compute here and are only invoked when the triage engine passes an utterance, an alarm edge fires, or the dialogue asks about the scene.

Walking the Voice Loop

The voice path is the densest model cooperation — six steps from microphone to speaker:

Step by step — what each one judges, and what happens when it errs.

Wake + voiceprint gate (who is speaking). The wake word runs on sherpa-onnx’s streaming zipformer; a hit does not immediately open the capture window — first CAM++ verifies the voiceprint of the wake-word utterance itself: extract an embedding from the last verify_window_secs of audio, match against enrolled profiles, and only open the window above threshold. Strangers get a log line and nothing else. While idle the device records nothing and sends no audio out; the keyword model only compares very short audio fingerprints locally, and the capture window after a hit defaults to 4 seconds. The voiceprint gate and YAMNet audio events are off by default — the microphone is privacy-sensitive input, and every listening feature has to be switched on by hand. The verification gate is itself fail-open: with verification enabled but nobody enrolled, the device lets people through rather than locking itself. This is the practical equivalent of “personalized VAD” from the previous survey: respond only to enrolled users. Two companion designs: enrollment reuses the KWS path (say the wake word N times to enroll — no separate enrollment UI), and every interaction’s transcript is attributed to the best-matching enrolled speaker (record tagging). The source comments include an honest qualifier: this is a convenience filter, not a security boundary — short-utterance voiceprints are forgiving, and a family member with a similar voice may pass. That sentence belongs in the docs of anyone shipping voiceprint features.

Transcription (what was said). paraformer transcribes the captured utterance offline — Mandarin by default, swappable to a trilingual checkpoint (Mandarin/Cantonese/English) by changing one file pair in the same engine. The transcript goes out as a voice_transcript SSE event.

Triage (whether to answer). The step I find most interesting — and the one forced by false wakes: in earlier versions everything after a wake went straight to the dialogue model, so a line from the TV or a cough got a serious, considered reply, and every such reply added one more thing that butts into the room’s conversation. Laya is a 322M-parameter non-autoregressive classifier (mmBERT, 924MB int8) that scores each transcript on three classes: answer (worth replying) / device (a device command) / ignore (hear nothing). Below the confidence floor (default 0.35) it only reports a voice_decision event and does not act — the decision engine is itself fail-open, and callers keep their previous behavior (pass everything to the LLM) when the model is missing. Its position is in front of the LLM: a casual “nice weather today” gets stopped at the 322M classifier without waking the 4-bit-quantized Qwen3. This is precisely the “two-stage gate” pattern from the previous survey — a lightweight classifier saves LLM calls and latency. Choosing a non-autoregressive model for triage has one more rationale: a single forward pass produces the result, no token loop, predictable latency.

Reply and playback. What passes triage goes to Qwen3 (llama.cpp, greedy decoding, /no_think to disable thinking mode), the reply is spoken through MeloTTS, and a chat_reply SSE reaches the frontend. TTS is the only engine running as a subprocess — sherpa-onnx’s offline-tts CLI — because it links GPL espeak-ng, and the process boundary keeps GPL code outside the Apache-2.0 main binary.

There is also a follow-up window: for a few seconds after one wake, further utterances need no new wake (the follow_up flag on transcripts) — a session window implementing “wake once, wake-word-free within the session”.

Walking the Alarm Path

Vision and audio alarms form the other cooperation chain, in the opposite direction: not “human triggers models” but “models trigger human”.

    A["Camera video"] --> B["NanoDet detection<br/>+ ByteTrack tracking"]
    B --> C["Rising edge + cooldown<br/>alarm decision"]
    C --> D["alarm SSE<br/>+ GB28181 NOTIFY"]
    C --> E["Qwen3-VL<br/>async description"]
    style A fill:#FF9800,color:#fff
    style B fill:#2196F3,color:#fff
    style C fill:#9C27B0,color:#fff
    style D fill:#4CAF50,color:#fff
    style E fill:#4CAF50,color:#fff

Detection and decision. NanoDet-m detects objects in captured frames; a ByteTrack subset tracks them (riding the detection boxes, zero extra inference); users draw intrusion and tripwire zones in the UI, and zone_events come from the geometry between tracks and zones. Alarm triggering is rising edge + cooldown: an object appearing fires once, and the cooldown suppresses repeats — without edge logic, a person sitting on the sofa would fire an alarm every second.

Description never delays the alarm. The alarm frame is handed asynchronously to Qwen3-VL (llama.cpp’s mtmd multimodal path, 2B Q4_K_M + mmproj projector) for one Chinese sentence (“someone pushed the door open” level), delivered as alarm_description SSE. The scheduling design is worth recording: single-flight (one description in flight at most) plus a 120-second minimum interval — detection-box jitter cannot stack a queue of inference tasks — and the description never delays the alarm itself: the alarm fires first, the description arrives after. The VLM is the slowest link on this path (seconds on CPU); putting it on an async branch behind the alarm is “expensive models must not block” applied a second time.

Audio alarms. YAMNet classifies rolling 0.96-second windows of microphone audio (baby cry, dog bark, siren class events), vote smoothing (3 consecutive votes to accept) suppresses false hits, per-class cooldown suppresses repeats, and accepted edges emit an alarm with source: "audio". Silero VAD’s speech-presence flag feeds the voice loop at the same time — if a person is speaking, the voice shouldn’t be classified as an anomalous event; the two engines share one 16kHz monitor stream, audio’s version of “one producer, many consumers”.

“What Do You See”: How Perception Reaches the Dialogue

The alarm path runs “models trigger human”; the reverse direction exists too — ask “what do you see” in the chat panel, and the results accumulated by the always-on perception layer enter the conversation. The implementation is a scene block: real-time detections carry count and position (“2×person, center of frame”), the latest VLM description carries a staleness annotation (“23 seconds ago, may lag”), face recognition and zone triggers likewise — every item carries a time validity, expired items are dropped, and if nothing is fresh the whole block is omitted. The request returns a grounded field with three states: scene (reuse the perception loop’s scene block), vlm (grab a JPEG frame now and hand it to Qwen3-VL, answering about the “right now” picture), none (assemble nothing). The LLM now receives more than a transcript — questions like “what is the person in the middle doing” have answers, and the answers anchor to real detection boxes rather than model invention. One hard engineering constraint: the dialogue Qwen3 and the frame-description Qwen3-VL share a single llama.cpp backend instance, and visual inference runs serialized — the VLM’s preprocessing reuses mutable buffers, and two concurrent requests hitting the same instance collide. On-demand frame answers are therefore slow (seconds on CPU); what that buys is memory shared by one instance, with no second copy of the model. The dialogue can also be pointed at a cloud model: cloud answers first, local takes over on failure — offline remains the default path. NanoDet’s always-on output thereby has three consumers: alarm decisions, alarm descriptions, and the dialogue scene block.

Meeting Mode: The Multiparty Version of “Who Is Speaking”

With [meeting] enabled, the notebook becomes a meeting recorder: a pyannote segmentation model (1.5MB, MIT) cuts “who spoke when”, CAM++ embeds and clusters each segment into speakers, paraformer transcribes segment by segment, and ct-transformer adds punctuation. Four small models chained into a “segment → attribute → transcribe → tidy” pipeline. Recording happens only after you press start; processing runs asynchronously, with the docs quoting one-tenth to one-fifth of the recording duration; the audio is deleted by default once processed, text only; and --selftest-meeting <wav> verifies the cluster count directly on any multi-speaker audio file. The models README records a real measurement: at the default 0.5 threshold, zero-shot clustering split a 4-speaker sample into 5 clusters — tune the threshold per room. Writing known defects into the docs like this is far more credible than the four characters “meeting notes support”.

Who Else Does This

Multi-model cooperation is not notebook’s invention. As of October 2026, this batch of active open-source projects is all doing the same thing — assembling multimodal capability from multiple single-modal models. Five categories by setting:

The closest relatives, expanded:

Frigate (36.3k★, the de-facto NVR standard) wires its multimodal cooperation almost isomorphically to notebook’s alarm path: motion detection → object detection → snapshot → VLM sees only the event frame. Its GenAI layer added Ollama, llama.cpp, Gemini, and OpenAI providers after 2025, with qwen3-vl:4b as the local default example — the same model family and trigger pattern as notebook’s alarm descriptions. The difference: Frigate’s VLM never sees the raw stream, only event snapshots — stricter gating than notebook.

xiaozhi-esp32 (30.4k★, the largest AI-hardware project in the Chinese maker world) represents the edge-cloud split: the ESP32 does only wake word (ESP-SR), echo cancellation, and Opus encoding; ASR/LLM/TTS all live on the server (free Qwen realtime for registered personal users, or self-hosted xiaozhi-esp32-server). 138 board configs, device-side MCP controlling speaker/LED/servo. Its coexisting “classic pipeline + end-to-end voice model” tracks are exactly the cascade-vs-S2S routes from the earlier surveys living in one product. Notebook takes the opposite side — stuffing the whole chain back onto the device — two trade-offs for different power and network assumptions.

Home Assistant’s Wyoming ecosystem teaches the degradation ladder best: the docs spell out three tiers — weak hardware runs speech-to-phrase (fixed-phrase recognition, a few hundred commands fully on-device), N100-class runs full local Whisper, and only rare languages fall to cloud. The companion Voice PE hardware ($69) runs the wake word on an ESP32-S3 with a XMOS XU316 chip doing AEC/noise-suppression/AGC — a dedicated DSP for the audio front end and a general chip for protocols, the same division of labor as in-cabin zone voice. Notebook currently has only “one local tier + per-engine fail-open” without explicit tiers — a gap.

Screenpipe (21.8k★) proved the commercial viability of “continuous recording + retrieval”, and demonstrated licensing as an architectural decision: converting from MIT to a source-available commercial license while staying local-first. Its technical direction is worth noting — shifting from constant recording toward event-driven capture (accessibility tree first, OCR fallback) — fundamentally “cheap gates first, expensive models later”, the same principle as notebook’s layering applied to a different sensing domain.

Open-LLM-VTuber (14.0k★) has the highest stack overlap with notebook (sherpa-onnx + FunASR + CosyVoice lineage); its licensing is MIT code with Live2D sample assets licensed separately — the same deliberate “which parts are open” design as notebook quarantining GPL TTS in a subprocess.

Two counterexamples are equally informative: OpenRecall (2.9k★) has had no updates for 13 months — the “clone Rewind” direction doesn’t survive on ideas alone without engineering discipline. Brilliant Labs’ Noa was once the open-source AI glasses benchmark (Whisper + GPT-4o + Moondream multi-agent cloud stack); in 2026 the org has emptied its public repos — when multimodal products die, it’s usually not a model problem.

Four Patterns They All Converge On

Putting these projects side by side with notebook, healthy multi-model projects converge on four patterns:

  1. Gated cascade, not one model. Every active project runs cheap always-on perception (wake word, VAD, motion detection, OCR) with expensive models triggered by events (LLM, VLM). None keeps a large model running all the time. That isn’t a capability limitation — it’s what the arithmetic of power, latency, and false triggers forces, and the conclusion derived in the previous survey is independently confirmed across dozens of projects
  2. Degradation ladders are table stakes. Wyoming’s three tiers, Willow’s 400 on-device commands, xiaozhi’s dual-track pipeline, Screenpipe’s local-Whisper-or-Deepgram choice — capability tiers matched to hardware beat all-or-nothing deployment
  3. License isolation is an explicit architectural layer. GPL TTS in a subprocess (notebook), Live2D assets licensed separately (VTuber), piper split into GPL and MIT lines, Screenpipe going commercial — multi-model projects assemble components with wildly varying licenses, and “which parts are open” must be decided as design
  4. The tooling layer is converging on MCP. xiaozhi’s device + cloud MCP, Screenpipe’s MCP server, Omi’s MCP — the “act” stage after multimodal perception is unifying on one protocol

Notebook’s differentiated position in this coordinate system: Rust single binary + fully local + no Python dependency. Most of the ecosystem is Python or TypeScript services stapled together (the faster-whisper + Ollama + Piper recipe has been copied by countless single-digit-star projects), with a runtime shape of “a house full of processes”. Notebook packs nine models into one process (plus one exiled TTS subprocess); the cost is finding a Rust-native route for every engine (ORT / llama.cpp / sherpa-onnx), and the payoff is the deployment surface: one binary + one directory of model files, pulled up by systemd.

What’s Deliberately Left Out, and Next

Against the full picture of the previous surveys, notebook’s multimodal stack has clear blanks: after transcription, response policy is a single Laya classifier with no state machine (the in-session silence/backchannel/answer three-way decision is unimplemented; the follow-up window listens unconditionally); the VLM only sees single frames (triggered by alarm edges, or grabbed on request from the dialogue), no continuous video understanding; TTS is offline whole-sentence synthesis with no streaming first-packet optimization — end-to-end voice latency is still far from the 800ms product line in the survey.

Those blanks are essentially the next few versions’ work list. Whether and in what order to fill them uses the same criterion as this post’s layering: whichever blank blocks the complete “cheap gate + expensive model on demand” loop gets filled first.
