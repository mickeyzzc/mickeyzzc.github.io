MiBeeNvr: From v0.1.0 to v0.10.0

May 6, 2026 September 19, 2026 MiBeeOSS NVR, Go, RTSP, ONVIF, H.265, Xiaomi Camera, Timelapse, Transcoding, Streaming, Open Source MiBee Open Source Projects Series 6693 words 32 min read
🔊

MiBeeNvr is the NVR I wrote for the cameras in my own home. v0.1.0 shipped on May 6, 2026; v0.10.0-preview landed on July 28 — nine releases in under three months (v0.8 never got its own release post; the problems it exposed became the backbone of v0.9). Each version used to have its own post; this one merges the v0.1.0–v0.10.0 release notes into a single timeline: what each step did, and why.

Why Write Another NVR

I have several kinds of cameras at home: a few Xiaomi ones, some DIY ESP32 units, and multiple Raspberry Pi CSI cameras. I wasn’t happy with cloud storage, for concrete reasons: Xiaomi cameras are viewable by default only through the Mi Home app, and recordings either live on an SD card (limited capacity, constant card swapping) or in the cloud — a few dozen RMB a month, plus the privacy concern of handing your footage to someone else who may train AI on it or pass it to third parties. The ESP32 cameras recorded to SD cards with no convenient way to browse or play back.

I tried the open-source options too: ZoneMinder requires a full LAMP stack — deploying it was more work than building my own project; Shinobi’s configuration is a maze; Frigate is good but AI-detection-focused and Docker-bound, too heavy for my taste.

So the goals were clear:

  • Single binary, download and run
  • Low resource usage, must run on a Raspberry Pi
  • Multiple camera types, especially Xiaomi’s private protocol
  • Clean web UI, automatic cleanup of old recordings

Nothing off the shelf fit, so I wrote one.

Architecture and Tech Choices

MiBeeNvr is written in Go with a Svelte 5 frontend — the whole SPA is compiled to static assets and embedded into the binary, so deployment is a single file. The backend stack:

  • modernc.org/sqlite: pure-Go SQLite, no CGO, cross-compiles without pain
  • chi for routing; gortsplib for RTSP/RTP; pion/rtp for real-time streaming

SQLite because it’s a single file, needs zero deployment, its concurrent reads are plenty for home use, and most importantly there’s no database server to install. The design stance is blunt: one binary, no external dependencies, AMD64/ARM64 cross-compilation, YAML config, built-in web UI.

The overall data flow as of v0.2.0 — recording, storage, post-processing, live streaming, and network egress are each their own layer:

Cameras feed the recorders; recorders write to storage (MP4 segments plus SQLite metadata) and branch frames to on-demand HLS live streams; storage is post-processed by the merge and cleanup engines; the right edge is the API, web UI, WebDAV, and FTP.

The recording pipeline itself is straight-line: RTSP in, RTP depacketization, MP4 muxing, segment files written on a fixed duration, metadata into SQLite. HTTP JPEG sources (ESP32-style) enter the same muxing path via periodic frame grabs.

v0.2.0: Live Views, Recording Merge

v0.1.0 could only play back recordings, not show live views; recordings were 30-second segments — 2880 files per camera per day; every camera shared one retention setting. v0.2.0 (2026-05-12) closed these gaps with 15 features; the highlights:

On-demand HLS live streaming. Built on gohlslib — starts when a client requests, releases when nobody’s watching; async frame writes decouple live streaming from the recording pipeline. H.264 and H.265 both supported. A low-resolution sub-stream can be configured for automatic fallback under bandwidth pressure.

Automatic segment merging. Small segments of the same camera get merged into larger MP4s periodically, with per-camera or global policies and a merge-progress panel in the UI. Fewer files means faster management and faster database queries.

Per-camera retention days. Front door keeps 30 days, balcony keeps 7 — each camera gets its own retention_days.

Direct ESP32-CAM support. A new HTTP JPEG protocol means cheap MJPEG-only cameras connect without protocol conversion; the frontend got a Canvas-based MJPEG frame player, much smoother than refreshing JPEG images.

Easier installation. Dual-architecture Docker image, one-line install script, interactive mibee-nvr init, a health check command, automatic bcrypt hashing of plaintext passwords. Protocol and encoding became two independent fields (rtsp + h265), retiring combined strings like rtsp_h264.

This release also laid the ONVIF device-discovery framework, plus Chart.js statistics, theme auto-detection, English/Chinese switching, and responsive layout.

v0.3.x: Built-in Xiaomi Support and Multi-Protocol Streaming

v0.3.0 (05-20) focused on deep Xiaomi integration; v0.3.1 (05-22) brought multi-protocol streaming. The architectural back-and-forth between them deserves its own section.

From go2rtc Dependency to Built-in

Xiaomi cameras don’t speak standard RTSP — they use the proprietary miss (Mi Secure Streaming) protocol with multiple layers of encryption; knowing the camera’s IP doesn’t let VLC pull the stream. Early on, go2rtc handled the conversion: sign in with a Xiaomi account to get the device list and keys, establish a P2P connection, decrypt, and feed a standard stream to the NVR. No flashing, no disassembly.

mermaid
sequenceDiagram
    participant NVR as MiBeeNvr
    participant CLOUD as Xiaomi Cloud
    participant CAM as Camera
    NVR->>CLOUD: Xiaomi account login
    CLOUD-->>NVR: passToken + device list
    NVR->>CAM: CS2/TUTK P2P handshake
    CAM-->>NVR: miss encrypted stream
    NVR->>NVR: decrypt → record/live

Account authentication exchanges keys, the P2P handshake sets up the link, and after that the video flows over the LAN — decrypted, then into the recording and live pipelines.

The problems surfaced quickly: CS2 P2P connections stalled after about 20 minutes; go2rtc is a separate project, hard to debug when things break; and two containers meant port conflicts and resource contention.

Phase two tried porting go2rtc’s Xiaomi code into a plugin system — Go interface registration, init() wiring, even a gRPC process-isolation experiment. Reality: the live path gained several intermediate hops, performance dropped noticeably, and the codebase got harder to follow — a simple feature now crossed process boundaries.

v0.3.0 deleted the plugin system entirely and moved the Xiaomi code into the built-in internal/xiaomi/ package — one binary, no external processes, no Docker dependency. The lesson from this round: at this stage of the project, simplicity beats extensibility. (Protocol breadth came back later — that extensibility lives in StreamHub, below.)

The built-in flow is three steps: sign in with a Xiaomi account in the web UI, the device list appears, click add and recording starts. .camera. cameras, .cateye. doorbells, and .feeder. pet feeders are all recognized, with no conversion container needed:

Archived Recordings

Replacing a camera (broken, moved, upgraded) used to mean losing its history — traditional NVRs delete the data with the camera. v0.3.0 introduced three states: Active (recording), Disabled (paused), Archived (read-only). Archiving asks you to type DELETE, merges the segments, removes the camera from the live list, and keeps every recording — playable, downloadable, individually deletable, with its own retention period.

StreamHub and Six Streaming Protocols

In v0.3.0 the only live protocol was HLS, with 5-15 seconds of latency — not good enough for monitoring. v0.3.1 introduced StreamHub, a multi-consumer frame dispatcher: recorders broadcast frames to StreamHub, and HLS/WebRTC/FLV consumers subscribe independently. Adding a protocol means writing one new consumer; recorder code stays untouched.

ProtocolLatencyCodecsDirectionUse case
WebRTC (WHEP)<1sH.264PullLive preview, intercom
HTTP-FLV1-3sH.264/H.265PullLow-latency web monitoring
LL-HLS2-5sH.264/H.265PullLow-latency fallback
HLS5-15sH.264/H.265PullMaximum compatibility
RTMP—H.264PushOBS and push tools
SRT—H.264PushRemote/unstable networks

WebRTC uses the WHEP standard (pion/webrtc v4), max 2 peers per H.264 camera, idle eviction, plus zombie-connection detection; RTMP (gortmplib) accepts push ingestion, so OBS can push straight in; SRT (gosrt) receives pushes over unreliable networks. The frontend ProtocolSwitcher switches protocols in one click, showing estimated latency per protocol and hiding options an H.265 camera can’t use.

Also in this release: 15+ security fixes (path validation, auth hardening, rate limiting, SQL-injection protection), a complete frontend migration to Svelte 5 runes (500+ i18n keys), and a first-run Setup Wizard that detects browser capabilities and recommends a protocol (LL-HLS > WebRTC > HTTP-FLV > HLS).

v0.4.0: Audio in Recordings, Self-Healing Cameras

v0.4.0 (05-25) tackled two gaps: MP4 recordings were silent, and a disconnected camera needed a human to notice and restart it.

Audio Recording

Enabled per camera with audio_enabled: true. RTSP cameras usually carry AAC; Xiaomi and ONVIF devices usually carry G.711 μ-law/A-law — which MP4 doesn’t natively support. The solution: custom box types (ulaw/alaw) that wrap the raw frames with zero transcoding and zero CPU cost; AAC uses the standard mp4a box. The trade-off: some generic players don’t recognize the custom boxes — MiBeeNvr’s own player handles them fine.

Health Monitoring

Context: the most common community complaint was Xiaomi cameras dropping connections, but without access to the user’s LAN there was no way to tell whether the cause was the network, the firmware, or the protocol implementation. So beyond auto-recovery, health events get recorded — users screenshot the history page and attach it to an issue, and diagnosis gets targeted.

Three detection layers, shallow to deep:

    L1["Connection<br/>RTSP/ONVIF/CS2"] --> L2["Stream quality<br/>fps/bitrate/keyframes"]
    L2 --> L3["Picture<br/>freeze/black detection"]
    L3 --> SCORE["Health score engine"]

The connection layer watches RTSP sessions, ONVIF responses, and CS2 P2P heartbeats; the stream layer tracks frame rate, bitrate, and keyframe intervals; the picture layer detects frozen and black frames. Each layer has its own thresholds and cooldowns; results feed a scoring engine — connection weighs most (nothing else matters when it’s down), stream quality next, picture as the backstop (connected and streaming but the image is frozen: likely the camera itself).

At most N consecutive recovery attempts, then it stops and marks the camera faulty — no infinite loops. Retries back off exponentially (1s→2s→4s→8s) so devices and networks don’t get hammered. Alerts per camera have cooldowns. Health events persist, the web UI has a timeline page, and GET /api/cameras/{id}/health returns per-camera details.

Playback Stability and the Raspberry Pi

HLS used to start writing a segment at an arbitrary frame — a segment that doesn’t begin with a keyframe renders as black. It now waits for the next IDR frame, trading a little boundary precision for a decodable first frame in every segment. A credit-based frame-rate throttle gives consumers a frame budget — one credit per frame consumed, producers send only when credit remains — so low-power devices stop choking on frame bursts. Two LL-HLS parameters were tuned for the Raspberry Pi: backBuffer 0.5→2.0s and liveSync 2→3s, which turned “stutters constantly” into “basically smooth” on a Pi.

ARMv7 binaries arrived (Raspberry Pi 2/3-class devices), covering amd64/arm64/armv7. The test suite passed 1651 cases at 60.7% coverage. Also: ONVIF codec auto-detection, Xiaomi cloud metadata sync, and encrypted storage for sensitive config fields.

rpi-cam: Building Our Own ONVIF Server

Developing an ONVIF client has a practical problem: you need a running server to talk to — protocol docs and packet captures only go so far. The Raspberry Pi 3B + OV5647 running MediaMTX had no ONVIF server mode, so the NVR couldn’t discover it; existing options were slow, Device-service-only, or CGO-bound. MiBeeNvr’s client uses 0x524a/onvif-go, so a server on the same library is naturally compatible — that became rpi-cam: full Profile S (Device/Media/PTZ/Imaging) + WS-Discovery, RTSP (gortsplib, same library as MediaMTX), RTMP push, camera-parameter control, digital PTZ, zero CGO.

Measured on a Raspberry Pi 3B (905MB RAM), replacing MediaMTX:

Sharing the library between client and server also paid off in development: PTZ, Imaging, and Event were developed on both ends simultaneously — change the client, verify against rpi-cam immediately, fix on the spot. Real cameras can’t match that loop: they may not support the operation at all, and their error messages say little.

Hardware Transcoding

Many cameras only output H.265, which browsers still struggle to play. The v0.5.0 transcoder detects the input codec and spins up hardware-accelerated transcoding (H.265→H.264) on demand, with freeze-frame protection during transitions, plus a monitoring page for job status and performance.

Transcoding depends on hardware, though: the Pi 3B’s VideoCore IV GPU can’t hardware-decode H.265, and software decoding on 905MB RAM and a Cortex-A53 @ 1.2GHz is a lost cause. Enter the Banana Pi BPI-M5 as the transcoding node — Amlogic S905X3 with a Mali-G31 MP2, H.265 4K@60fps hardware decode:

Reconnect Strategy and Community Issues

Recorder reconnection changed from pure exponential backoff to tiered backoff with jitter: 1s→5s→10s→60s, each tier jittered, so a mass disconnect doesn’t produce a synchronized reconnect storm. The RTSP connection timeout became configurable.

A batch of community-reported stability issues got fixed:

  • A full CS2 buffer no longer rebuilds the whole P2P session — the oldest frame is dropped to make room, because losing one frame beats rebuilding a session. Also fixed the ~20-minute connection hang (a UDP write data race).
  • Docker first-start crash: auto-generated config left HLS defaults empty and segment_count failed validation with 0 — autoInitConfig now calls ApplyDefaults() first.
  • A run of deployment issues: missing DB directory (unable to open database file (14)), UGREEN NAS permission mismatches, containers losing permissions across restarts.
  • TUTK-only models (like the Xiaomi Outdoor Camera 4 Pro zoom edition) need a commercial license and are explicitly unsupported; cameras that offer RTSP should use RTSP.

ONVIF compatibility was stated honestly at the time: rpi-cam proves our own implementation correct, but real commercial cameras will surface edge cases — report them with the camera model.

v0.6.0: Timelapse, Transcoding, Observability

Once recording was running, storage became the first emergency: one 1080p camera writes tens of GB per day, and 30-day retention eats most of a 1TB disk. The loudest community request was timelapse — for cameras that mostly stare at still scenes, compressing to timelapse takes about 5% of the space. v0.6.0 (06-05) is where timelapse and transcoding landed.

Timelapse v1

The pipeline is multi-stage: RTSP/MJPEG sources emit JPEG frames at an interval → still-scene detection skips frames → sequences on disk → rolling and daily merges. The default grab interval is 30 seconds with a 5% random jitter — synchronized grabs across cameras spike the CPU when RTSP sessions open at once. Still-scene skipping reuses the health module’s freeze detection (adjacent-frame histogram comparison); after 3 consecutive still periods, grabbing pauses until the scene changes.

Merging had two paths. Go-native merge wraps JPEG frames directly into MP4 as H.264 IDR frames — pure mux, zero encoding, about 5% CPU on a Pi 3B for 10 concurrent 1080p streams, at the cost of file size. FFmpeg merge re-encodes to H.264, 5-10× smaller, better for long-term archive. The rolling merger keeps one merge goroutine per camera and cancels the old one when a new segment lands — a classic race where the old goroutine’s defer cleanup could delete the new goroutine’s registration; fixed with an ownership ID check (cleanup only deletes if it’s still the active entry).

Transcoding and Backfill

A SQLite-backed job queue; finished recordings enter the queue via the event bus, the frontend polls job status, failed jobs retry. The most useful piece is backfill: pick a historical date range and batch-create transcode jobs with a target codec of h264/hevc/mjpeg. On ARM, when no hardware encoder is detected (/dev/dri/renderD128 or a V4L2 encode node), it falls back to libx264. History cleanup is paginated so a mass delete can’t bloat the SQLite WAL.

Laying Groundwork

internal/ai/ set up the ONNX Runtime inference framework — CGO decoupled via subprocess, YOLOv11n model ready, waiting on a feature flag. Observability: Prometheus metrics and VictoriaLogs remote logging, so community issues get diagnosed from data instead of guesswork.

A batch of fixes and hardening: non-standard H.265 SPS fields that black-screened hls.js — SPS gets intercepted and patched before HLS writes; COOP/COEP headers enabled only under HTTPS (strict mode breaks WebSocket over plain HTTP); a 5-second frame watchdog in recorders that reconnects when SPS/PPS never arrive, preventing goroutine leaks; PTS validity checks at recording start, preventing zero-duration recordings from turning the frontend’s total duration into NaN; the test suite cut from ~340s to 88s (parallelization + WAL + mock clock); docs split from one 2000-line api-reference into 19 module files, kept in sync in English and Chinese.

Everything was validated against real cameras before release; the three self-built camera projects were adapted in the same round — see camera-test-machines: three camera test rigs.

v0.7.0: Timelapse v2 and Dual-Lens Xiaomi Cameras

The community quickly listed v0.6 timelapse’s hard defects: JPEG sequences ate storage, H.265 cameras produced unplayable timelapses, dual-lens Xiaomi cameras only captured the main lens, and H.265 HLS occasionally panicked outright. v0.7.0 (06-14) is organized around those.

Timelapse v2

The core change: merging no longer goes through FFmpeg or intermediate JPEG sequences. The keyframe extractor caches SPS/PPS from the first frame; every keyframe lands on disk as raw H.264/H.265 NAL units; the merge is a pure mux into MP4 — zero encoding, directly playable output.

H.265 HLS Panic and Connection Stability

The #20 H.265 HLS panic: when the first frame of an H.265 stream arrives before the muxer is initialized, the write path hit an uninitialized pointer. The refactored StreamHub owns muxer lifecycles centrally — writes check readiness first, and an unready muxer triggers automatic re-initialization instead of a panic. #18, Xiaomi cameras reconnecting in loops, was the connection-layer version of the same class: after UDP miss-connect timeouts, mishandled PONG responses wedged the connection state machine, which looked like the device dropping and reconnecting forever. Fixes: robust PONG handling, jittered backoff, and clearing stale CS2 buffer data on reconnect.

Dual-Lens Xiaomi Cameras

Dual-lens devices (CW500, Outdoor Camera 4) expose both lenses under one device ID. v0.7.0 added lens selection when adding a camera — the channel parameter is applied at MISS URL resolution, and each lens gets its own recorder instance with independent recording, transcoding, and timelapse. Also fixed: special characters in passwords corrupted the URL in connection tests — “test always fails but recording works” being the most confusing failure mode there is.

Transcoding Layers and Frontend Cleanup

The transcoding module was restructured into three layers: job pipeline (SQLite queue + worker pool), hardware detection (V4L2M2M/VAAPI/NVENC, probed once at init and cached — undetected backends get disabled), and encoder abstraction (one command-construction interface for hardware and software encoders). Before, adding an encoder meant touching four or five places; now it’s one layer. libx265 software encoding arrived, so H.265 cameras can be transcoded without changing codec even without hardware encoders.

The frontend Dashboard got a big cleanup: the browser-side AI detection module (detection without tracking, of little practical use and resource-hungry) was removed from the frontend (the backend ONNX framework stayed); the camera Enabled toggle was removed — it tangled with the recorder/streaming/transcoding state machines and disabled cameras would occasionally still record via the event bus; camera start/stop now flows exclusively through the recorder lifecycle; transcoding jobs moved to a dedicated history page.

Camera Projects in Lockstep

The three self-built camera projects that provide the test fleet updated in the same round: MiBeeHomeCam renamed to MiBee Cam with ONVIF WS-Discovery (Synology and Milestone NVRs discover it automatically), MJPEG moved to its own port, and a frame broadcaster that ended the PSRAM contention; rpi-cam migrated to mibee-eye-raspi, broadening from “Raspberry Pi” to any libcamera-compatible ARM board (identical behavior on Banana Pi M5 and Orange Pi 5); MiBeeCam fixed a leftover bug with hard-coded test WiFi credentials.

v0.9.0: Zero-Config Discovery, Debts Repaid

v0.8 never got a release post. The storage bottlenecks and camera-manager lock problems it exposed became central themes of v0.9.0 (07-19): with 9 cameras on a Banana Pi M5, /api/cameras took 14.9 seconds on cold start — not slow iteration, but the manager’s RWMutex held by second-long operations (recorder starts, ONVIF handshakes) while every read queued behind it. This release was regression-tested on 9 real cameras (CW500 dual ×2, DS-2CD2047G2, Outdoor Camera 4, IMILAB A1, Dafang, Xiaofang, Aqara G2, Xiaomi pan-tilt).

ONVIF Zero-Config Discovery

Adding an ONVIF camera used to mean: know the IP → settings page → fill in the profile manually; past five cameras it’s a chore. v0.9 does dual-mode discovery: passive listening for WS-Discovery Hello on UDP 3702 (devices are sensed the moment they come online), plus an active Probe scan every 60 seconds (minimum 30, respecting Pi 3B performance). Discovered devices flow through one registration pipeline: dedup by endpoint + stable_id (covering archived devices) → enrichment (brand/model/serial persisted) → devices without credentials enter pending_activation, the frontend shows an activate button, one password entry later they’re live — activation runs a real GetStreamURI + RTSP DESCRIBE test, no more HTTP HEAD only. A 10-second grace period at startup keeps the scanner from missing devices still doing DHCP.

Storage Read/Write Split

Recorders locking out readers was v0.8’s chronic pain, along with N+1 queries and full-scan COUNT(*). The rewrite: under WAL, one serial writer connection and three parallel readers (reader DSN carries query_only=1):

A new calendar-aggregation endpoint separates the calendar view from Gallery paging. Startup runs a merge-integrity scan (entries marked merged whose files are missing get reset — playback falls back to frames instead of 404), and the merge manager gained post-merge verification: a missing output MP4 blocks deleting the source frames.

Lock-Free Camera Manager

The approach: copy-on-write atomic snapshots plus per-camera lifecycle locks. All read paths go through an immutable atomic snapshot — fully lock-free; writes hold a nanosecond-scale map copy plus disk I/O, never across I/O; a per-camera mutex serializes individual start/stop, so ONVIF handshakes no longer hold any global lock. FFmpeg Optional; TUTK Legacy Devices

FFmpeg was the only third-party binary dependency — every deployment started with “is it installed?” v0.9 demoted it to an optional accelerator: recording, playback, live, relay, timelapse, and merging all run without FFmpeg; only pixel-level H.265↔H.264 transcoding needs it. A new pure-Go MP4 box probe package, mediaprobe (codec/duration/resolution/frame-count), is 10-100× faster than ffprobe -count_frames.

Old Xiaomi devices (Dafang, Xiaofang, Aqara G2, etc.) use the proprietary TUTK P2P protocol and previously couldn’t connect to any NVR. This release ported go2rtc’s TUTK transport into an independent implementation: TransCode/XXTEA transforms, session0/16/25 types (session25 with a 5-deep reorder buffer), a custom ChaCha20-Poly1305 DTLS suite, and 7 legacy models supported. The MISS protocol gained two-way audio, PTZ control, RPC wake-up for battery devices, and auto/hd/sd quality selection.

Debt Ledger

  • Surveillance-grid protocol auto-selection: each tile picks its protocol by camera codec and browser capability, with a runtime degradation chain webrtc→flv→hls→mjpeg and a static snapshot as last resort; ONVIF full automation closed 4 old issues (metadata persistence, real stream tests, profile-by-resolution, Hikvision digest time skew).
  • Data repair CLI: repair duration fixes duration=0 entries (FastProbeDuration reads only the stts box — 100× faster than full parsing; 4285 segments repaired in ~30 minutes against a 10+ hour estimate), repair merge-status, and repair fragments for permanently unmergeable dead segments.
  • golangci-lint v2 across the codebase, a batch of data races fixed, all Go/npm dependencies upgraded.
  • Cross-module fixes: the camera start endpoint passed the HTTP request’s ctx into the recorder, so returning the response cancelled the context and killed the recorder — “started, then instantly stopped”; merge-window timezone offsets; the timeline’s 2000-entry cap truncating recent history (raised to 10000); add-camera deduplicating by ID only, letting the same device register twice (777MB of duplicate video in production) — now endpoint + stable_id double dedup.

The announcement also landed here: v0.9.0 is the last stable/compatible release since v0.1.0; the next major version will break things (with precise migration paths, no silent breakage); long-term deployments should pin v0.9.x.

The v0.9.1 Patch

Shipped the next day, four fronts:

  • i18n: a script cross-checking code references against the translation dictionaries found 19 keys referenced but missing — users saw raw key names in the UI; the whole push-out config section was hard-coded English, adding 14 keys. en/zh dictionaries went 1341→1377 with zero parity gaps.
  • Recording fragments: the MP4 muxer holds every sample in memory until a segment closes, so longer segments mean more memory. Platform-aware caps: ≤2GB available RAM tops out at 30 seconds, >2GB at 2 minutes — fragment counts halved. Periodic backfill (default 10 minutes, batches of 500) keeps historical pending segments from re-accumulating.
  • Community bugs: TUTK was supported but the add-camera vendor precheck hadn’t been updated and still blocked it as incompatible; Synology 9090 port conflicts got documentation; “use global default” for merge policy did nothing — the DELETE path called an Upsert whose COALESCE preserved the old values, so nil was a no-op; a new ClearCameraMerge actually clears.
  • Doc audit: all public docs went through an accuracy pass (9 CRITICAL + 3 MODERATE + 1 MINOR, 18 files). Highlights: two-way audio had the protocol backwards (docs said CS2-only, reality was TUTK-only); the timelapse docs described merge windows that didn’t exist — 8h/24h/7d/30d were silently clamped to 1h; a wrong Prometheus metric name. The README positioning also changed from “Raspberry Pi NVR” to cross-platform lightweight NVR — it had long been running on x86, Banana Pi, and Synology.

v0.10.0: Full H.265 and the Architecture Cleanup

v0.10.0-preview.1 (07-28) is the biggest release since 0.8.0. The theme isn’t features — it’s cleaning the foundation. The breaking changes promised in v0.9 all landed here, documented with migration steps, no silent breakage. Note: this is a preview; not recommended for production.

Full H.265 Pipeline

Through 0.9.x, H.265 was half-finished: live views depended on WebCodecs, which requires an HTTPS secure context — plain-HTTP LANs got nothing; merged outputs often black-screened in Edge; timelapse merging didn’t work at all. This release fixes the whole chain end to end.

The live side gained the @yume-chan/libde265 WASM decoder, so plain HTTP works. The frontend probes automatically: prefer WebCodecs under HTTPS for hardware acceleration, fall back to WASM software decoding — both paths reach the player, and “can’t play” isn’t one of them.

ok means stable for 30+ seconds; degraded means anomalies detected but an 8-second debounce window passes before acting — no protocol switching on a single network blip; failed means it’s down, fall to the next candidate — webrtc → flv → hls → mjpeg in order, static snapshot if everything fails. The 8-second debounce came from hard experience: too short and transient jitter triggers switches; too long and users stare at a frozen tile.

The rest of the chain was timing and data consistency: codec probe results now dual-write to YAML + DB (probe once, persist forever) instead of re-probing every boot — probe/stream mismatches caused black screens and protocol storms; SPS/PPS/VPS capture moved ahead of the record-enabled gate (live-only mode previously never captured parameter sets, black-screening playback); playback routes by runtime codec plus authoritative MSE detection, forcing H.265 onto WASM instead of mistakenly onto MSE; timelapse merging got the hvcC box’s numNalus fixed and conservative Main-tier defaults (unblocking Edge’s HEVC extension), and periodic merges now distinguish H.265/H.264 frames — previously JPEG-only, so H.265 cameras’ timelapse merges failed by construction.

Timelapse v3

v0.7’s rewrite removed FFmpeg but kept the 1h merge-window hard cap — 8h/24h/30d values were silently clamped, as the v0.9.1 audit confirmed when it found the docs describing a capability that didn’t exist. v3 removes the cap for real: natural-day/8h/12h/24h/7d/30d all work, and the default moved from 1h to natural-day (local midnight-aligned). A new timelapse_merges table (schema v29) gives every merge output a full DB record (camera, window, duration, codec, frame count, status), with merges APIs for discovery, playback, and deletion. Periodic merges fold intermediate products away by default (about 1.5GB per camera per day saved); responses carry an X-Timelapse-Codec header so the frontend picks the right player — <video> for H.264/H.265, frame carousel for MJPEG.

MJPEG, WebRTC, Auth

MJPEG cameras like the ESP32 used to poll over HTTP — one request per frame, latency and connection count both stuck. They now stream over a single WebSocket connection, improving both. WebRTC gained an streaming.webrtc.ice_servers config (STUN/TURN lists), enabling cross-network access beyond the LAN. Auth switched to HMAC-signed stateless tokens — no server-side session memory, controlled expiry, and another piece of sidecar groundwork.

The Architecture Cleanup

Three refactors, zero runtime behavior change:

  • Config split into per-subsystem files (camera/merge/timelapse/transcoding/streaming/health/ai/server); the entry point only loads and assembles
  • The DI composition root split out helpers and router; it only decides “who gets injected into whom”
  • API routes moved from one god-method to per-domain registrars, with zero endpoints lost

What changed is the answer to “where do I add new things”: a new protocol or AI capability now stays inside its own subsystem instead of hunting for a slot in a giant config and a god-method. That’s the precondition for the sidecar route.

Supporting engineering: gzip for API responses (an order of magnitude smaller) + ETag + view=summary light endpoints + recordings list limits (50 default / 500 max), cutting grid polling traffic sharply; the recordings page dropped the gallery view (as announced in v0.9 — timeline and list views absorbed it); a dead ChaCha20-Poly1305 DTLS implementation in the TUTK code was deleted after confirming zero references — leave dead code around and the future sidecar protocol layer will trip on it; CI flakiness was rooted out (goroutine lifecycle management), and the full go test ./... passed in one shot for the first time.

The AI detection INVALID_PROTOBUF bug took the longest: first suspected CDN truncation of model downloads, but the real cause was the streaming-gzip middleware appending a wrong gzip trailer to binary responses — ONNX models are binary protobuf, “completed” into garbage by the middleware. The fix is four layers of defense: the middleware skips gzip for binary content types; the download layer adds retry + Range requests + atomic writes; the Docker image pre-bundles models so runtime downloads disappear; the frontend cache re-downloads when it detects corruption. Model distribution and integrity checks are exactly what sidecar AI will hinge on, so this defense is groundwork.

Stability fixes worth singling out: deleting recordings now removes their merged outputs too (they used to leak on disk), with repair reclaim-orphan-merges to clean historical leaks (--dry-run first to see the reclaimable space; 20ms delete spacing keeps USB disks happy); startup scans went async, turning an 8-minute block into an 8-second start; the merge backfill backlog drained 8500+ pending entries.

Breaking Changes

  • Combined protocol strings (rtsp_h264, http_jpeg, etc.) are hard-rejected at startup; split into protocol + encoding fields
  • DB schema v28→v29 (auto-backup to <db>.pre-v29-backup first); nothing below v0.9.x can jump straight to 0.10.0
  • /api/timelapse/{id}/thumbnail and /preview removed, replaced by the /api/timelapse/merges family
  • Default changes: disk cleanup threshold 95→85 (avoiding the HDD performance cliff past 90%), default merge window natural-day

Full migration steps live in the repo’s upgrade guide (English and Chinese).

The Sidecar AI Direction

The cleanup isn’t cleanup for its own sake. Two directions lie ahead: stronger AI (heavier detection, multimodal inference, event triggers) and more cameras (more protocols, more vendors). The shared constraint: inference and protocol adaptation must never drag down the video pipeline — recording, live, and merging stay stable and low-latency.

The main process stays light and stable; AI inference and protocol adaptation hang off as independent sidecars — independently upgradable, independently crashable, and a new vendor protocol is just another sidecar. Sidecar IPC protocols and deployment shapes get their own write-up later; this release put the main process’s domain boundaries in order first.
