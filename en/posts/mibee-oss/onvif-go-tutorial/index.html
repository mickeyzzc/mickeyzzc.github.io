onvif-go Tutorial: Connect Cameras, Pretend to Be One, Test Your NVR

September 29, 2026 MiBeeOSS Go, ONVIF, IP Cameras, Open Source MiBee Open Source Projects Series 3105 words 15 min read
🔊

onvif-go is the library that plays the “connect to cameras” role in MiBee’s camera-access stack: when your program needs to discover, authenticate, pull streams from, or control a camera over ONVIF — or pretend to be a camera so an NVR can connect to it — this is the one. It ships both roles, client and virtual-camera server, and its compatibility matrix (Hikvision, Axis, Dahua, Bosch, Amcrest, HiSilicon OEMs, a minimal ESP32 implementation) was fed by real packet captures. MiBeeNvr runs its ONVIF access on this library.

This post is written to a “copy it and use it” standard: one section per feature, each with a complete runnable program and a line-by-line walkthrough, so you can land each part in your own project as you read. The code comes from the repo’s README and examples, with signatures checked against the current release.

Installation and Project Setup

The library has zero third-party dependencies, the module path carries the /v2 suffix, and Go 1.26+ is required:

console
1
2
3

mkdir my-nvr && cd my-nvr
go mod init example.com/my-nvr
go get github.com/mickeyzzc/onvif-go/v2

Most projects only need import "github.com/mickeyzzc/onvif-go/v2/onvif" — the client facade, discovery helpers, and error sentinels all start there; discovery and the virtual-camera server live in the discovery/ and server/ subpackages, imported when used.

The repo also ships four CLI tools with prebuilt binaries for linux/macOS/Windows; probing a camera with them before writing code saves time:

console
1
2

go install github.com/mickeyzzc/onvif-go/v2/cmd/onvif-diagnostics@v2.2.0
onvif-diagnostics -host 192.168.1.100 -user admin -pass camera-password
  • discover: ONVIF discovery across the subnet;
  • onvif-quick: runs the main operations against one camera;
  • onvif-diagnostics: scans eleven primary operations and emits a JSON report — the README says to run this before filing an issue;
  • onvif-server: starts a virtual camera.

First Camera in Five Minutes

package main

import (
	"context"
	"fmt"
	"log"

	"github.com/mickeyzzc/onvif-go/v2/onvif"
)

func main() {
	client, err := onvif.NewClient("192.168.1.100",
		onvif.WithCredentials("admin", "camera-password"),
		onvif.WithAutoClockSkew())
	if err != nil {
		log.Fatal(err)
	}
	if err := client.Initialize(context.Background()); err != nil {
		log.Fatal(err)
	}

	info, err := client.Device().GetDeviceInformation(context.Background())
	if err != nil {
		log.Fatal(err)
	}
	fmt.Printf("%s %s (fw %s)\n", info.Manufacturer, info.Model, info.FirmwareVersion)

	profiles, err := client.Media().GetProfiles(context.Background())
	if err != nil {
		log.Fatal(err)
	}
	mainToken := onvif.SelectMainProfile(profiles)
	uri, err := client.Media().GetStreamURI(context.Background(), mainToken)
	if err != nil {
		log.Fatal(err)
	}
	fmt.Println("main stream:", uri.URI)
}

Walking through it:

  • NewClient accepts three endpoint shapes: a full URL, IP:port, or a bare IP — the latter two get /onvif/device_service appended automatically. WithCredentials sets the login; WithAutoClockSkew makes the client read the device clock once without auth, compute the offset, and factor it into later signatures. This cures most Hikvision 401s.
  • Initialize does three things: measures clock skew, fetches capabilities, and resolves each service’s XAddr. The third part matters in practice — many cameras advertise stale IPs in capabilities, and the library fixes those addresses before caching them.
  • client.Device() and client.Media() are service facades: one long-lived entry point per ONVIF service, alongside PTZ(), Imaging(), Events(), Media2(), Analytics(), DeviceIO(), and Security().
  • SelectMainProfile is not profiles[0]: it picks the highest-resolution profile, breaks ties with naming hints (main/sub variants in several languages), and only falls back to the first entry when no resolution info exists at all. It exists because plenty of cameras put the sub stream at profiles[0].
  • uri.URI is an RTSP address. Verify immediately with VLC or ffplay: ffplay -rtsp_transport tcp "rtsp://192.168.1.100:554/Streaming/Channels/101".

Your program sits on top, and onvif-go splits into two roles below it: as a client it connects to real cameras on the right; as a server it becomes a virtual camera — handy for testing an NVR’s discovery, streaming, and PTZ logic without hardware. Both roles share the same wire-format code and serve as each other’s first test cases.

package main

import (
	"context"
	"fmt"
	"log"
	"time"

	"github.com/mickeyzzc/onvif-go/v2/discovery"
)

func main() {
	ctx, cancel := context.WithTimeout(context.Background(), 6*time.Second)
	defer cancel()

	devices, err := discovery.Discover(ctx, 5*time.Second)
	if err != nil {
		log.Fatal(err)
	}
	for _, d := range discovery.FilterONVIFDevices(devices) {
		fmt.Printf("%-14s %-20s %s\n", d.GetName(), d.Hardware, d.GetDeviceEndpoint())
	}
}

FilterONVIFDevices removes the ghosts — Synology boxes, Windows hosts, printers — that answer every Probe. On a real network this step is close to mandatory. To fill in names, locations, and serial numbers for the discovery results, add a parallel enrichment pass:

go
1

enriched, err := discovery.EnrichDevices(ctx, filtered) // concurrency 8 by default

The Device fields are worth knowing in full:

FieldMeaning
EndpointRefThe WS-Discovery urn:uuid endpoint address, a stable transport-level ID
Name / Hardware / LocationParsed from scopes; empty when the device does not advertise them
XAddrsDevice service addresses — connect to these
Types / Scopes / MetadataVersionDevice types, raw scopes, metadata version

One trap is written right in the field comments: EndpointRef is not a serial number. To correlate the same camera across protocols (ONVIF here, GB28181 there) use d.Info.SerialNumber — matching EndpointRef against a serial silently never matches.

Passive listening takes the opposite approach — cameras announce themselves with Hello on power-up, and other NVRs’ probes produce answerable traffic, so a long-running listener accumulates a device inventory on its own:

Auth and Clock Skew

mermaid
flowchart TD
    START["Send request<br/>default PasswordDigest"] --> OK{"Accepted?"}
    OK -->|yes| DATA["Got a response"]
    OK -->|"401 / 403"| NEXT["Try next rung<br/>PasswordText → HTTP Basic → None"]
    NEXT --> STICK["Winning mode<br/>sticks for later calls"]

    classDef ok fill:#E8F5E9,stroke:#2E7D32,color:#1B5E20
    classDef warn fill:#FFF3E0,stroke:#E65100,color:#BF360C
    class DATA,STICK ok
    class START,NEXT warn

The library supports four auth modes:

ModeOn the wireUse case
AuthDigestWS-Security UsernameToken, PasswordDigest (default)Nearly all cameras
AuthPasswordTextUsernameToken with the password in clearOld firmware that only accepts this
AuthHTTPBasicHTTP Basic headerDevices authenticating at the HTTP layer
AuthNoneNo credentialsAuth-free devices, minimal ESP32 implementations

Real cameras have every quirk imaginable, hence the auth ladder — when the primary mode fails with an auth-class error (HTTP 401/403, a NotAuthorized fault, or a 200 carrying a fault), the ladder moves down; the first mode that works sticks:

go
1
2
3

client, err := onvif.NewClient(endpoint,
	onvif.WithCredentials("admin", "camera-password"),
	onvif.WithAuthFallback(onvif.AuthPasswordText, onvif.AuthHTTPBasic, onvif.AuthNone))

When every rung fails you get onvif.ErrUnauthorized, reliably testable with errors.Is.

Why clock skew kills digest: the PasswordDigest signature string includes a Created timestamp, the device checks it against its own clock, and once the skew exceeds the window (anywhere from dozens of seconds to a few minutes per vendor) everything is rejected as invalid — which looks like “the password is right but I still get 401.” WithAutoClockSkew calls GetSystemDateAndTime once without auth during Initialize, computes the offset, and factors it into later signatures.

Don’t guess when troubleshooting — use the diagnostic:

go
1
2

diag, err := client.DiagnoseAuth(context.Background())
fmt.Println(diag.Status, diag.ClockSkew, diag.Detail)

The three Status values map to actions: AuthStatusOK needs nothing; AuthStatusClockSkew means fix the camera’s NTP (or let WithAutoClockSkew carry you meanwhile); AuthStatusBadCredentials means the password is actually wrong. Credentials can also change at runtime: client.SetCredentials(user, pass); suspect the ladder is stuck on an old rung — client.ResetAuthLadder(); suspect a stale capabilities cache after the camera changed IP — client.InvalidateCapabilitiesCache() and re-run Initialize.

profiles, err := client.Media().GetProfiles(ctx)
if err != nil {
	log.Fatal(err)
}
for _, p := range profiles {
	fmt.Printf("profile %-10s %dx%d\n", p.Token, p.VideoEncoderConfiguration.Resolution.Width, p.VideoEncoderConfiguration.Resolution.Height)
}

mainToken := onvif.SelectMainProfile(profiles)
subToken := onvif.SelectSubProfile(profiles, mainToken)

uri, err := client.Media().GetStreamURI(ctx, mainToken)
snap, _ := client.Media().GetSnapshotURI(ctx, mainToken)
fmt.Println(uri.URI, "|", snap.URI)

The two selectors do different jobs: SelectMainProfile picks the highest resolution; SelectSubProfile picks the largest profile strictly smaller than the main one — a second profile at the same resolution does not count as a sub stream. That guard exists because some Amcrest models ship two tokens pointing at the same stream.

GetStreamURI asks for RTP-Unicast/RTSP by default; pass a StreamSetup to GetStreamURIWithOptions for HTTP tunneling or multicast. Once you have the address, SetSynchronizationPoint makes the camera emit an I-frame immediately — a big wait-saver in multi-camera rotation UIs; multicast scenarios also get StartMulticastStreaming/StopMulticastStreaming.

Feed the returned uri.URI to any RTSP player to verify:

console
1

ffplay -rtsp_transport tcp "rtsp://192.168.1.100:554/Streaming/Channels/101"

The media plane itself (recording or relaying with pion, for example) lives in your program — this library handles everything about “asking the camera”: addresses, profiles, encoder parameters.

	log.Fatal(err)

presetToken, err := ptz.SetPreset(ctx, mainToken, "front gate", "")

	log.Fatal(err)

	fmt.Println(p.Token, p.Name)
}

// limits and status
cfgs, _ := ptz.GetConfigurations(ctx, mainToken) // pan/tilt/zoom space limits
status, _ := ptz.GetStatus(ctx, mainToken)

PTZSpeed X/Y values run from -1 to 1 — normalized velocity the camera converts to actual angular speed; AbsoluteMove takes a PTZVector target position, RelativeMove nudges. Home position (GotoHomePosition/SetHomePosition) covers the “look at the door, then return” pattern. Focus lives on client.Imaging(): Move/StopFocus plus the auto-focus modes, and GetImagingSettings/SetImagingSettings for brightness, contrast, and exposure.

package main

import (
	"context"
	"errors"
	"fmt"
	"log"
	"os"
	"os/signal"
	"syscall"
	"time"

	"github.com/mickeyzzc/onvif-go/v2/onvif"
)

func main() {
	client, err := onvif.NewClient("192.168.1.100",
		onvif.WithCredentials("admin", "camera-password"),
		onvif.WithAutoClockSkew())
	if err != nil {
		log.Fatal(err)
	}
	if err := client.Initialize(context.Background()); err != nil {
		log.Fatal(err)
	}

	ctx, stop := signal.NotifyContext(context.Background(), os.Interrupt, syscall.SIGTERM)
	defer stop()

	stream, err := client.Events().SubscribeEvents(ctx, func(msg onvif.NotificationMessage) {
		fmt.Printf("[%s] %s %s\n",
			msg.Message.UtcTime.Format("15:04:05"),
			msg.Topic, msg.Message.PropertyOperation)
		for _, item := range msg.Message.Data {
			fmt.Printf("    %s = %s\n", item.Name, item.Value)
		}
	}, &onvif.SubscribeEventsOptions{SubscriptionDuration: time.Hour})
	if errors.Is(err, onvif.ErrEventsNotSupported) {
		log.Fatal("this camera has no event service")
	} else if err != nil {
		log.Fatal(err)
	}

	<-ctx.Done()
	_ = stream.Unsubscribe(context.Background())
}

Trigger a motion event while it runs:

text
1
2
3

[14:32:07] tns1:VideoSource/MotionAlarm Changed
    State = true
    Score = 87

The tunables in SubscribeEventsOptions:

FieldDefaultMeaning
SubscriptionDuration1hTotal subscription lifetime, renewed automatically
RenewMargin5mHow early to renew
PullTimeout30sPer-poll wait
MessageLimit10Max messages per pull
FilteremptyTopic filter

Events arrive as NotificationMessage{Topic, Message(EventMessage), ProducerAddress, SubscriptionID}, where EventMessage carries PropertyOperation (Created/Changed/Deleted), UtcTime, and three SimpleItem groups (Source/Key/Data, each Name+Value). One wire-format detail worth knowing: conformant cameras wrap tt:Message inside wsnt:Message, and only by reaching through that wrapper do MotionAlarm State and Score arrive — the managed subscription handles it. If you bypass it and call the CreatePullPointSubscription/PullMessages/RenewSubscription/Unsubscribe primitives for fine-grained polling control, you unwrap those layers yourself.

package main

import (
	"context"
	"log"
	"time"

	"github.com/mickeyzzc/onvif-go/v2/server"
)

func main() {
	config := server.DefaultConfig()
	config.Port = 8081
	config.Username = "admin"
	config.Password = "nvr-test"
	config.SupportEvents = true

	srv, err := server.New(config)
	if err != nil {
		log.Fatal(err)
	}
	ctx := context.Background()
	if err := srv.Start(ctx); err != nil {
		log.Fatal(err)
	}
	log.Printf("virtual camera: %s", srv.ListenAddr())

	// push a motion event to subscribed NVRs every 30 seconds
	for range time.Tick(30 * time.Second) {
		srv.PublishEvent(server.Event{
			Topic: "tns1:VideoSource/MotionAlarm",
			Data: []server.SimpleItem{
				{Name: "State", Value: "true"},
				{Name: "Score", Value: "87"},
			},
		})
	}
}

On the NVR, add the “camera” at http://<your-ip>:8081 by hand and it can be discovered, read, streamed, and receive events. PublishEvent fans out to every live PullPoint subscription and is a safe no-op with no subscribers; an empty PropertyOperation defaults to Changed, and UtcTime is stamped at publish time.

For NVR development it is the test fixture — discovery, streaming, PTZ, and events all testable without hardware. A few advanced switches:

go
1
2
3
4

config.Profiles = []server.ProfileConfig{ /* multi-lens: Token/Name/VideoSource/VideoEncoder... */ }
config.AdvertiseHostProvider = func() string { return detectOutboundIP() } // XAddr follows DHCP changes
config.AuthProtectedActions = []string{"SystemReboot"}                     // extra write-actions to protect
config.TLSCertFile, config.TLSKeyFile = "cert.pem", "key.pem"              // HTTPS (Profile T transport baseline)

When a stream URI changes at runtime (a transcoder moved ports, say) call srv.UpdateStreamURI(profileToken, "rtsp://127.0.0.1:8554/live"); to customize one action’s response with request context, hang it on srv.RegisterContextHandler(action, func(rc *soap.RequestContext, body []byte)). The server’s auth policy is “credentials protect write-type actions only” (Set*/Remove*/Create*/Go* plus SystemReboot), leaving reads open.

The cheapest verification is a self-test loop: point this library’s client at your own server and run discovery, auth, streaming, and events end to end — the conformance loopback tests in examples/ do exactly that.

How Production Projects Use It

The heavyweight ONVIF clients in the ecosystem are NVRs and VMSes — recorders from Hikvision, Axis, and friends interoperate through it, and ONVIF Device Manager is the common manual-probing tool; onvif-go’s compatibility matrix (Hikvision, Axis, Dahua, Bosch, Amcrest, HiSilicon OEMs, a minimal ESP32 implementation) was fed by capturing those real devices. The captures came from the projects below, which run every day in production:

FeatureProduction projectHow it’s used
Discovery (active / passive / directed)MiBeeNvrThe discovery layer of camera onboarding: subnet scans, a resident listener accumulating inventory, directed probes across segments
Auth + clock skewMiBeeNvrThe first gate when connecting commercial cameras; WithAutoClockSkew is the default defense against Hikvision-flavored 401s
Streams / snapshots / main-sub selectionMiBeeNvrONVIF signaling yields RTSP URIs and encoder parameters, feeding its own recording, live-view, and playback pipelines
Virtual camera servermibee-eye-goTurns a Linux board’s UVC camera into an ONVIF Profile S camera; RTSP gateway mode wraps an existing RTSP stream as a camera for commercial NVRs

Two entry points for complete implementations. For the NVR side (a client talking to real cameras), read MiBeeNvr — a self-hosted recorder running as a single binary on low-power ARM, with this library as its ONVIF access layer; every model in the compatibility matrix has an interop record behind it. For the device side (a server being a camera), read mibee-eye-go — pure Go, zero CGO, USB/UVC capture; every seam of the onvif-go server has a working answer there.
