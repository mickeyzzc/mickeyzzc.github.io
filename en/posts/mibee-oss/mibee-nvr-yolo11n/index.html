MiBeeNvr's AI Detection: Why Inference Runs in the Browser, and Why YOLO11n

July 28, 2026 MiBeeOSS NVR, YOLO, ONNX, AI, Object Detection, WebGPU MiBee Open Source Projects Series 2053 words 10 min read
🔊

MiBeeNvr’s Smart Features include an AI detection option that runs inference entirely in the browser — the backend server does no inference at all. The ONNX model file is served to the browser, and ONNX Runtime Web executes it client-side. The model is Ultralytics’ yolo11n.onnx.

This isn’t a common choice among NVR products. Most open-source NVRs (Frigate, the go2rtc ecosystem) put AI inference on the backend, because the backend has access to the raw stream, runs persistently, and can use a GPU. Moving inference into the browser is a deliberate architectural trade-off, not a stopgap. This post breaks down two things: why inference lives in the browser, and — given that premise — why YOLO11n.

Why Inference Runs in the Browser

The root cause of this decision is MiBeeNvr’s core positioning: a single binary, zero external dependencies, runnable on a 1GB-RAM ARM device. AI detection is an add-on feature; it can’t turn around and require a hardware upgrade, and it certainly can’t break the single-binary constraint.

The most direct path to backend inference is libonnxruntime. But it’s a C library, which means Go has to link it via CGO. The moment CGO enters the picture, the costs cascade: ARM cross-compilation needs a C toolchain, the binary is no longer statically linked, Docker images must carry the matching glibc version, and each architecture (amd64/arm64/armv7) needs a separate build. A dependency introduced for an “add-on feature” drags the entire project’s deployment model back into complexity — not worth it.

Moving inference to the browser sidesteps every one of these constraints:

  • The backend stays pure Go with no C, keeping the single binary and zero cross-compilation burden
  • Inference compute scales with viewer count (each viewer infers the stream it’s watching), not with camera count — 5 cameras with 1 person watching runs 1 inference; a backend scheme would run 5 persistent ones
  • The browser has already decoded the video frame (<video> element), so inference reuses it — no need for the backend to re-transmit the raw stream or decode again
  • The model file is only 5.4MB; it downloads once, gets cached by the Cache API, and loads instantly thereafter

The backend does only three things in the entire AI chain: store config, serve the model file, and relay the video stream. Frame data never passes through the backend’s inference path.

The cost of this architecture is equally clear: close the browser and inference stops; with no viewer watching, no detections are produced. So it suits “real-time lightweight detection” — overlaying boxes while you watch the feed. Scenarios that need 24/7 persistence, post-hoc re-inference of recorded segments, or GPU-accelerated heavy models are a separate system, covered below.

Engineering the Browser-Side Inference

Once browser-side inference is settled, several engineering problems can’t be avoided. How these are solved reveals the trade-offs of this architecture better than “which model” does.

Robust Model Distribution

The model file downloads from Ultralytics’ GitHub release. GitHub releases are served via Azure blob CDN with a 1-hour signed URL. On networks from China to GitHub, connections get silently truncated — not an error, just TCP dying mid-transfer, leaving a partial file on disk. On the next NVR start, it sees the file, assumes it’s complete, serves it to the browser, and ONNX Runtime Web fails to parse the truncated protobuf with ERROR_CODE 7 (INVALID_PROTOBUF).

So download_model.go implements a three-layer defense:

  1. Range resume — uses HTTP Range requests to continue from the existing .part file size, rather than restarting from scratch each time
  2. Backoff retry — on failure, backs off at 1s/2s/4s/8s/16s, up to 5 attempts
  3. Integrity verification — after download, strictly checks size against Content-Length (with a 5MB absolute floor as a backstop), and only then atomically renames .part → final filename; if it fails, starts over

These three layers are independent defenses — retry covers network jitter, Range covers large-file truncation, size-check catches silent truncation. If any layer fails, the model never gets served in a corrupted state.

The ONNX Runtime Web Loading Trap

How ORT is loaded hits a very deep pitfall. The intuitive approach is import('onnxruntime-web') via Vite’s code-splitting. But this triggers a highly misleading bug: Vite’s ESM code-splitting breaks ORT’s internal import.meta.url-based WASM/worker path resolution, ORT can’t find its wasm files, and the error it reports is INVALID_PROTOBUF — the exact same error code as a corrupted model.

Debugging this took a while because the error points to “model is broken” when the real cause is “Vite broke ORT’s wasm loading path”. The eventual fix is to skip Vite’s import entirely, load the UMD bundle via <script src="/ort.min.js">, and manually set ort.env.wasm.wasmPaths = '/ort/'. Additionally, since the page lacks COOP/COEP headers, there’s no SharedArrayBuffer, so numThreads = 1 is forced.

The Inference Pipeline

The ObjectDetector class implements the full pipeline, from VideoFrame to Detection[]:

flowchart LR
    VF["VideoFrame"] --> PRE["Preprocess<br/>letterbox 640"]
    PRE --> INF["ONNX inference"]
    INF --> PARSE["Output parse<br/>84×8400"]
    PARSE --> NMS["NMS"]
    NMS --> MAP["Inverse letterbox"]
    MAP --> EMA["EMA smoothing"]

    classDef step fill:#E3F2FD,stroke:#1565C0,color:#1565C0
    class VF,PRE,INF,PARSE,NMS,MAP,EMA step

Step-by-step:

  • Preprocess: OffscreenCanvas does letterbox resize to 640×640, gray padding (114), RGBA → CHW Float32 normalized to [0,1]. OffscreenCanvas instead of a regular canvas avoids doing pixel shuffling on the main thread.
  • ONNX inference: output tensor [1, 84, 8400] — 4 box coords (cx/cy/w/h) + 80 class scores = 84 channels, 8400 anchors.
  • Output parse: per anchor, take the max of the 80 class scores, sigmoid activation, filter below the confidence threshold, convert cxcywh → xyxy.
  • NMS: sort by confidence, greedily suppress overlapping boxes with IoU > 0.45.
  • Inverse letterbox: map boxes from the 640×640 coordinate space back to original frame coordinates.
  • EMA smoothing: exponential moving average (alpha=0.3) tracks detection boxes; unmatched boxes are removed after 15 frames — otherwise a target briefly leaving and re-entering the frame causes flicker.

Frame skip (frame_skip) defaults to inferring every 3 frames (~10fps on 30fps video), filling skipped frames with cached smoothed results.

Detection results are only drawn as a canvas overlay in that browser tab — they are not reported to the backend. Each viewer tunes parameters independently (confidence, NMS threshold, frame skip, EMA alpha), persisted in localStorage.

Why YOLO11n

The browser-side-inference premise directly narrows the model selection.

The first filter is ONNX export maturity. Running ONNX in the browser requires the model’s ONNX export to be clean and community-verified. Swin-style transformers have complex ONNX exports with many dynamic shapes; YOLO-NAS exports depend on the supergradients framework; RT-DETR’s ONNX file exceeds 50MB. The YOLO family’s ONNX export is a first-class citizen in Ultralytics’ tooling, with the most community-validated cases, so it naturally enters the candidate pool.

The second filter is model size. The browser has to download the model; the 5.4MB YOLO11n loads in 1-2 seconds on most networks and opens instantly after Cache API caching. A 20MB+ model means a 5-10 second first load — a cliff-edge experience drop. So only nano-tier models qualify.

Among YOLO’s nano tier, the three-generation comparison of YOLO11n, YOLOv8n, and YOLOv5nu (data from the official Ultralytics benchmark, COCO val2017, 640 input):

MetricYOLOv5nuYOLOv8nYOLO11n
mAP50-9534.337.339.5
Params (M)2.63.22.6
FLOPs (B)7.78.76.5

Note: this uses YOLOv5nu (the anchor-free updated release, Ultralytics’ current default), not the original 2021 v5n. The old v5n has mAP 28.0 and 1.9M params, but the accuracy gap is too large for a same-generation comparison.

YOLO11n has the highest accuracy (39.5) while tying YOLOv5nu on params (2.6M) and having the lowest FLOPs (6.5B). Its accuracy-speed ratio is the best of the three. YOLOv8n is close on accuracy but has 34% higher FLOPs and a 15% larger model file.

In the browser scenario, the FLOPs gap is tangible. Devices without WebGPU run the WASM SIMD backend, and the single-frame inference time difference between 6.5B and 8.7B FLOPs measures roughly 80-120ms vs 110-150ms on an Intel laptop. With frame_skip=3, each inference is amortized over a ~100ms interval — YOLOv8n starts to struggle.

YOLO11n’s structural improvements over YOLOv8n concentrate on two points, both aimed at efficiency:

C3k2 replaces C2f. YOLOv8’s backbone and neck use C2f; YOLO11 switches to C3k2. C3k2 is a subclass of C2f whose inner repeating unit is switchable — shallow layers use a standard Bottleneck (behaving like C2f but with narrower channels), deeper layers switch to C3k (a CSP module with configurable kernel) for finer feature extraction. Higher parameter efficiency for the same receptive field.

C2PSA spatial attention. YOLO11 adds C2PSA after SPPF and before the neck — a CSP module with position-sensitive attention. The input channels split in half: one half skips through, the other passes through several PSABlocks (multi-head self-attention + FFN), then they merge. This lets the model focus on key image regions, helping with small objects and occlusion. YOLOv8 has no such module. This is one of the main reasons YOLO11n surpasses YOLOv8n on mAP despite fewer params.

The net effect of these two improvements is the table above: +2.2 mAP, tied params, −25% FLOPs. For browser-side inference, lower FLOPs means less per-frame CPU time, which means smoother at the same frame_skip — or fewer skipped frames and fewer missed detections at the same smoothness.

The Division of Labor with MiBeeVision

MiBeeNvr also integrates another AI option — MiBeeVision, an independent Rust AI backend. It is not an alternative to browser-side inference; the two divide labor, coexisting within the NVR to cover different scenarios.

Browser-side YOLO handles real-time lightweight detection — overlaying boxes while you watch the feed, zero deployment, works the moment you plug in a camera. The cost: no viewer means no detection, and the model is constrained to nano-tier by browser compute.

MiBeeVision handles heavy inference — it runs on a separate machine with a GPU or NPU, doing post-hoc analysis on recorded segments or running heavy models the browser can’t. It authenticates via API key (mbv_ prefix) and writes detection results back to the NVR via POST /api/ai/events, where they’re stored in the database for historical lookup. Recordings with active AI events are also protected by the cleanup policy and won’t be mistakenly deleted.

These two paths are separated within the NVR’s /api/ai/* surface: status/config/zones serve the browser-side ONNX config and ROI zones; events/stats are MiBeeVision’s write-back and queries. Both coexist in one NVR, each handling its own domain.

For plug-and-play real-time detection, use the browser side — it’s there by default. For 24/7 persistence, heavy models, or GPU acceleration, deploy MiBeeVision as a complement. That’s why both systems exist — not one replacing the other.

The Selection Logic Chain

Stringing the trade-offs together, YOLO11n wasn’t picked at random — it’s the result of a chain of constraints:

  1. Single binary, no CGO → inference can’t be on the backend → move it to the browser
  2. Browser downloads the model → model must be small → only nano-tier qualifies
  3. ONNX export must be mature → the YOLO family
  4. Best accuracy-speed ratio in the nano tier → YOLO11n

The model’s own structural advantages (C3k2, C2PSA) are a bonus on the last link of this chain, not the starting point. The starting point is “given the constraint of browser-side inference, we need a nano-tier model that can actually run” — and YOLO11n happens to hit the best balance across accuracy, params, and FLOPs in the nano tier.
