MiBeeReach: Remote Desktop, Terminal, SSH and Tunneling in One Binary

November 3, 2026 November 4, 2026 MiBeeOSS Rust, Remote Desktop, QUIC, WebRTC, NAT Traversal, Self-Hosted, Privacy MiBee Projects Series 1322 words 7 min read
🔊

My complaints about commercial remote-access software are specific: the free tier throttles speed and caps hours, ads pop up on schedule, traffic flows through the vendor’s servers, and not one knob for image quality or latency belongs to me. I used Sunflower and ToDesk for a while and evaluated self-hosting RustDesk’s server edition before deciding to build one from zero. That is MiBeeReach: a single-binary remote access platform in Rust with remote desktop, remote terminal, remote SSH, tunneling, and cross-network P2P all inside. The name joins the MiBee brand with Reach — making any machine behind NAT reachable from outside, on your terms.

Capability map: one entry point for remote operations

CapabilityWhat it does
Remote desktopVideo + input + clipboard (text/image/files) + desktop audio + file transfer + multi-monitor + view-only mode
Remote terminalRemote shell (ConPTY / PTY), LAN direct or P2P
Remote SSHBuilt-in SSH server; a standard ssh client connects directly
TunnelingInternal TCP ports exposed via stream relay, with per-stream targets
Management consoleGUI: connection profiles / workspace / embedded terminal / SSH tabs / device pairing

Controlled machines run Windows and Linux (Wayland); controllers run Windows and macOS. Every capability shares one transport abstraction and one device identity — adding a capability (terminal, SSH, tunnel) is not stacking a new product, it’s declaring one more stream type within the negotiation on the same connection. Both ends declare what they support and work within the intersection; data streams are routed by type tags, never by implicit open/accept ordering.

Transport design: one connection, two kinds of streams

The hardest transport problem in remote desktop is packet loss. Video frames are “newest is most valuable” by nature — losing one costs a gap in that frame; waiting for retransmission costs latency for every frame behind it — head-of-line blocking. Input, clipboard, and files are the opposite: not a single byte may arrive out of order. So Reach gives each class its own delivery semantics over the same QUIC connection:

The animation shows exactly this contrast: the same lost packet #2 queues everything behind it on a reliable ordered stream and the picture freezes; on the datagram lane only that frame is gone and rendering continues.

The video path: screen capture → encode → intra-frame fragmentation → datagrams straight out → reassembly and decode on the receiver, with forward error correction and reassembly handled at the protocol layer. On the cross-network path video rides a negotiated unordered data channel, falling back automatically to an ordered channel when the peer doesn’t support it — the fallback keeps sessions usable on weak links.

Beyond the LAN: a self-deployed P2P base

Besides LAN direct connections, cross-network sessions run on a self-deployed P2P base: signaling, STUN, TURN, and the data plane are all under our own control. Devices bind through a pairing code — pair once, device credentials land on disk, and later sessions authenticate with the device’s own signing identity with tokens refreshing automatically. When a controller holds both a LAN address and a P2P address it picks automatically: probe LAN direct first, fall back to P2P on failure.

The base isolates by product, account, and device namespaces; tenants can’t see each other. Even relayed paths on the data plane never see plaintext — end-to-end encryption is a hard constraint. That was the line I drew when deciding whether to rent a ready-made tunneling service: controllable quality and latency is the payoff of building from scratch, controllable traffic paths is the payoff of self-deploying, and neither gets discounted.

Security model

LAN path: QUIC’s self-signed TLS solves encryption but not authentication, so Reach layers a PSK challenge-response gate on top of the transport — connections without the pairing key are rejected outright, paired devices connect with zero prompts, and the key is generated or reset with one command.

Cross-network path: platform-level token authentication plus device-side Ed25519 signed handshakes, DTLS on the data plane.

Within a session: permission masks (control, clipboard, file transfer) are enforced by the controlled end; view-only mode takes effect via a configuration frame; and the local screen goes dark while a remote session is active — saving bandwidth, and keeping session content away from bystanders.

Resources and image quality

The standing cost of a remote-desktop endpoint is mostly the encoder and the capture loop. Reach converges both for static screens: when nothing moves, the capture interval backs off exponentially; after several consecutive static rounds the encoder is released, and a new frame brings it back to full speed instantly. The dark backdrop itself skips encoding the whole screen. The result: at idle the controlled end’s CPU usage drops from double digits to near zero, and a Raspberry Pi 400-class board can sit long-term as a controlled machine.

Tunable quality and latency is the payoff of owning the stack: frame rate, capture scaling, and capture timeout are all runtime parameters; the encoder is switchable between software and AMD hardware encoding, and with hardware support per-frame encode time cuts by more than half. Weak-network behavior is designed in too: a QoS probe drives a downgrade state machine — when the bitrate can’t keep up, frame rate drops before resolution does.

From zero, no shell

Reach doesn’t stand on any existing remote-access stack. Screen capture is our own: Windows uses DXGI Desktop Duplication on a zero-copy path, Linux uses three Wayland backends selected by session environment. Encoding is our own wrapper: openh264 software encoding as the base, AMD AMF hardware encoding as an optional build. Rendering, input injection, clipboard, and audio capture are all platform-specific implementations, split into separate Windows/Linux/macOS modules that business code reaches through platform aliases — zero changes across platforms.

Dependency management follows an explicit discipline: permissively licensed libraries (MIT / Apache / BSD) are used directly — quinn, russh, openh264, and Tauri are all on that list; copyleft-licensed projects are read for design and algorithms, with not a line of code carried over. For closed-source distribution this isn’t a style preference, it’s a compliance prerequisite.

reach desktop host     --bind 0.0.0.0:7777      # controlled end
reach desktop connect  --host 192.168.1.10:7777 # controller
reach terminal connect --host 192.168.1.10:7778
reach ssh host                                  # standard ssh client connects
reach tunnel connect   --local 127.0.0.1:8080 --target 127.0.0.1:80
reach ui                                        # GUI console

The controlled end installs as a bare tray process; the controller’s console uses Tauri for low-frequency configuration and session management — connection profiles, embedded terminal, SSH tabs, and device cards live there. Video frames render in a native window and never pass through the console’s IPC: a GUI’s JSON bridge can’t carry video throughput.

The studio now uses it to take over Raspberry Pis, test machines on the LAN, and personal laptops. Throttling, ads, privacy — after one round of self-deployment, none of those bills exist anymore.
