MiBeeNvr: From v0.1.0 to v0.12.0

September 1, 2026 October 18, 2026 MiBeeOSS NVR, Go, RTSP, ONVIF, GB28181, Xiaomi Camera, Adaptive Recording, Substream, H.265, Timelapse, Transcoding, Observability, Open Source MiBee Open Source Projects Series 7795 words 37 min read
🔊

MiBeeNvr is an NVR built for a home camera fleet. v0.1.0 shipped on May 6, 2026; v0.12.0 on September 1 — twelve releases in a bit over four months. This post merges the per-release notes from v0.1.0 through v0.12.0 into one timeline: what each step did, and why. The house style for mechanisms is plain words first, then a picture, then the parameters. The v0.13.0 performance benchmarks are a separate post, linked at the end.

The Whole Picture

The fact sheet as of v0.12.0:

  • One static binary (Go, Svelte 5 frontend compiled and embedded), amd64/arm64/armv7, zero external dependencies (FFmpeg is an optional accelerator)
  • Camera side: ONVIF (full Profile S + zero-config discovery), Xiaomi’s CS2/TUTK private protocols (dual-lens channels, two-way audio, PTZ), standard RTSP, HTTP JPEG/MJPEG, GB/T 28181, WHIP/WebRTC push
  • Streaming: WebRTC (WHEP) / HTTP-FLV / LL-HLS / HLS / RTMP / SRT, plus a built-in RTSP output (rtsp://<NVR-IP>:8554/<camera_id>)
  • Recording: continuous and adaptive (motion-aware) modes, three generations of the timelapse pipeline, a transcoding queue with backfill, per-camera disks, activity-ranked cleanup
  • Self-healing and observability: three-layer health checks, a stream diagnostics tree, latency badges, decode-level recording audits

The evolution falls into four phases: v0.2–v0.4 builds the recording and streaming base; v0.5–v0.7 fills in protocols and storage (full ONVIF, transcoding, timelapse); v0.9–v0.10 pays down engineering debt (performance, H.265 end to end, architecture cleanup); v0.11–v0.12 targets distribution and storage efficiency (GB/T 28181, all-day playback, substreams, adaptive recording, observability).

Why Write an NVR at All

The starting point was a concrete home setup: a few Xiaomi cameras, several ESP32-built ones, and multiple Raspberry Pi CSI units. The problems with cloud storage enumerate cleanly — Xiaomi cameras default to the Mi Home app only; recordings go to an SD card (limited capacity, constant swapping) or to the cloud (a monthly fee, data on someone else’s servers); ESP32 cameras recording to SD cards are awkward to browse and play back.

The open-source options were each weighed: ZoneMinder drags in a full LAMP stack, heavier to deploy than the project being built; Shinobi is configuration-heavy; Frigate leans on AI detection and requires Docker — too heavy for the target hardware. The requirements narrowed to four lines:

  • A single-file binary that runs on download
  • Light enough for a Raspberry Pi
  • Multiple camera types, especially Xiaomi’s private protocol
  • A clean web UI with automatic cleanup of old recordings

Nothing off the shelf fit, and the project began.

Tech Choices and Overall Architecture

Go for the core, Svelte 5 for the frontend — the SPA compiles to static assets embedded into the binary. Key backend choices:

  • modernc.org/sqlite: a pure-Go SQLite, no CGO, painless cross-compilation
  • chi for routing; gortsplib for RTSP/RTP; pion/rtp for live streams

SQLite won on single-file, zero-deployment, and read concurrency good enough for home use. The design brief in one sentence: one binary, no external dependencies, YAML config, built-in web UI.

The overall data flow as of v0.2.0 — recording, storage, post-processing, streaming, and network egress each on their own track:

Cameras feed the recorder; the recorder writes storage on one track (MP4 segments plus SQLite metadata) and branches frames to on-demand HLS on another; above the storage sit the merge and cleanup engines; on the right are the API, web UI, WebDAV, and FTP exits. The recording pipeline itself is direct: RTSP comes in, RTP is depacketized, muxed into MP4, written per segment duration, metadata into SQLite; HTTP JPEG sources (ESP32-class) enter the same mux path via timed frame pulls.

Development also produced a few ESP32 camera firmwares designed as upstream capture endpoints for MiBeeNvr: MiBeeCam (ESP32-S3-A10, MJPEG plus motion detection), an AI_Thinker ESP32-CAM firmware (ten-dollar boards, SD card and NAS upload), and MiBee Cam (XIAO ESP32-S3 Sense, AVI segmented recording, later with ONVIF discovery). Hands-on test records for the three hardware projects are in camera-test-machines.

v0.2.0: Live Streaming and Segment Merging

v0.1.0 could play recordings but had no live view; recordings came in 30-second pieces — 2,880 files per camera per day; and all cameras shared one retention period. v0.2.0 (May 12) landed 15 features; four matter most.

HLS on demand. Built on gohlslib: sessions start when a client asks and release when nobody watches; async frame writes decouple streaming from the recording pipeline. H.264 and H.265 both supported; under bandwidth pressure the stream can fall back to a configured low-resolution substream.

Automatic segment merging. Small segments of the same camera merge into large MP4s on a schedule, per-camera or global policy, with a merge progress panel in the web UI. File counts drop; management and database queries both speed up.

Per-camera retention. Thirty days for the front door, seven for the balcony — each camera its own retention_days.

ESP32-CAM direct connect. A new HTTP JPEG protocol means ten-dollar MJPEG-only cameras need no transcoding tricks; the frontend ships a Canvas-based MJPEG frame player.

This version also laid the ONVIF discovery groundwork, plus Chart.js statistics, light/dark themes, bilingual UI, mibee-nvr init interactive setup, and automatic bcrypt hashing of plaintext passwords.

v0.3.x: Xiaomi Built-in and Six-Protocol Streaming

v0.3.0 (May 20) centered on deep Xiaomi integration; v0.3.1 (May 22) added multi-protocol streaming. Between the two sits an architectural reversal worth recording.

From External Dependency to Built-in

Xiaomi cameras skip standard RTSP in favor of the private miss protocol (Mi Secure Streaming), multiply encrypted — knowing the camera’s IP doesn’t let VLC pull the stream. The first solution leaned on go2rtc for protocol conversion: log in with a Xiaomi account for the device list and keys, establish a P2P connection, decrypt, and hand standard streams to the NVR. No reflashing, no disassembly.

sequenceDiagram

The problems surfaced fast: CS2 P2P connections stall after about 20 minutes; go2rtc being a separate project makes failures hard to attribute; two containers to maintain, with port and resource contention.

The second attempt ported go2rtc’s Xiaomi code into a plugin system — Go interface registration, init() mounting, even a gRPC process-isolation experiment. Reality: several extra hops on the live-preview path visibly hurt performance, and a simple feature now needed cross-process communication. v0.3.0 deleted the plugin system wholesale and moved the Xiaomi code into the built-in internal/xiaomi/ package — one binary, no external processes. The lesson from that round: at this stage, simplicity beats extensibility. When protocols multiplied later, streaming-side extensibility was handled by StreamHub instead.

The built-in experience is three steps: log in with the Xiaomi account in the web UI, the device list appears, click add and recording starts. .camera. devices, .cateye. peepholes, and .feeder. feeders are all recognized:

Archiving Cameras

When a camera is replaced (broken, moved, upgraded) its history should survive — traditional NVRs delete data with the camera. v0.3.0 introduced three states: Active (recording), Disabled (paused), Archived (read-only). Archiving asks for a typed DELETE confirmation, merges fragments, moves the camera off the live list, and keeps recordings fully playable and downloadable.

StreamHub and Six Streaming Protocols

In the v0.3.0 era live viewing was HLS-only, 5-15 seconds of latency. v0.3.1 introduced StreamHub — a multi-consumer frame dispatcher: the recorder broadcasts frames to StreamHub; HLS/WebRTC/FLV each subscribe; adding a protocol means implementing one new consumer, with zero recorder changes.

WebRTC follows the WHEP standard (pion/webrtc v4), at most 2 peers per H.264 camera with idle eviction; RTMP push intake is built on gortmplib — the source-level comparison of that path is in gortmplib vs go2rtc vs FFmpeg; SRT on gosrt takes remote pushes over unstable links. This release also added 15+ security hardenings, the Svelte 5 runes migration, and a Setup Wizard that probes browser protocol support and recommends LL-HLS > WebRTC > HTTP-FLV > HLS.

v0.4.0: Audio and Self-Healing

v0.4.0 (May 25) tackled two things: MP4 recordings were silent, and camera disconnects waited for a human to restart them.

Audio Recording

Per-camera audio_enabled: true. RTSP cameras usually carry AAC; Xiaomi and ONVIF devices usually G.711 μ-law/A-law — the MP4 container has no native G.711, so the implementation packs raw frames into custom box types (ulaw/alaw) with no transcoding and zero CPU cost; AAC goes through the standard mp4a box. The trade-off: some general-purpose players don’t recognize the custom boxes; MiBeeNvr’s own player does. StreamHub grew audio broadcasting in step, so previews and recordings both carry sound, and segment merges preserve the track.

Three-Layer Health Checks and Bounded Recovery

The context: the most-reported community issue was frequent Xiaomi disconnects, and a developer can’t reach into a user’s LAN to tell network from firmware from protocol bug. So besides automatic recovery, health events had to be recorded for diagnosis.

Detection runs in three layers, shallow to deep: the connection layer watches RTSP sessions, ONVIF responses, CS2 P2P heartbeats; the stream layer tallies frame rate, bitrate, keyframe interval; the picture layer detects frozen and black frames. Each layer has independent thresholds and cooldowns, feeding a scoring engine — connection weighted highest (nothing else matters without it), stream next, picture as backstop. Recovery respects safety bounds:

At most N consecutive recovery attempts, then stop and mark the fault — no infinite loops; backoff 1s→2s→4s→8s so devices and the network aren’t hammered; per-camera alert cooldowns. Health events persist, a timeline page exists in the web UI, and GET /api/cameras/{id}/health returns per-camera detail.

Playback Stability and the Raspberry Pi

HLS could previously start a segment on any frame, handing players a segment whose first frame isn’t decodable — a black frame. The fix waits for an IDR frame before opening a segment, trading a little boundary precision for a decodable first frame everywhere. A credit-based frame-rate limiter gives consumers frame budgets so low-power devices aren’t flooded. Two LL-HLS parameters were tuned for the Pi (backBuffer 0.5→2.0s, liveSync 2→3s); playback on Pis went from routine stutter to mostly smooth. An ARMv7 binary joined the set (Pi 2/3, OneCloud-era boxes), completing amd64/arm64/armv7.

rpi-cam: A Companion ONVIF Server

ONVIF client development has a practical problem: you need a runnable server to test against. The Raspberry Pi 3B + OV5647 on hand ran MediaMTX, which has no ONVIF server mode; existing options were slow, Device-service-only, or CGO-bound. Hence rpi-cam: full Profile S (Device/Media/PTZ/Imaging) + WS-Discovery, RTSP (gortsplib), RTMP push, camera parameter control, digital PTZ — zero CGO. On the Pi 3B (905MB RAM) versus MediaMTX: 15-25MB vs ~45MB memory, plus ONVIF server and camera control that MediaMTX lacks. Client and server sharing one library (0x524a/onvif-go) has a compounding benefit: PTZ, Imaging, and Event develop on both ends at once — every client change verifies against rpi-cam immediately. Real cameras may not implement an operation and rarely explain errors; that iteration speed is unattainable against them.

Hardware Transcoding

Many cameras emit H.265 only, which browsers can’t play directly. This version’s transcoding auto-detects input codec and starts hardware-accelerated H.265→H.264 on demand, with freeze-frame protection during switchover and a task status page. Transcoding is hardware-bound: the Pi 3B’s VideoCore IV has no H.265 decode, so a Banana Pi BPI-M5 joined as the transcode node — Amlogic S905X3 with Mali-G31 MP2, H.265 4K@60fps decode, and gigabit Ethernet for more concurrent cameras.

Reconnect strategy moved from pure exponential backoff to tiered backoff with jitter (1s→5s→10s→60s), so simultaneous disconnects don’t stampede. A batch of community stability reports got fixed: CS2 buffer-full no longer rebuilds the whole P2P session (drop oldest, push newest); first-start Docker crash (autoInitConfig now calls ApplyDefaults first); TUTK-license-only models (e.g. Xiaomi Outdoor Camera 4 Pro tri-zoom) get an explicit unsupported notice.

v0.6.0 and v0.7.0: Timelapse, Transcode Backfill, and Groundwork

Once recording ran, storage complained first: one 1080p camera writes tens of GB a day; 30-day retention eats most of a 1TB disk. v0.6.0 (June 5) built timelapse; v0.7.0 (June 14) rewrote it.

The v0.6 pipeline: RTSP/MJPEG sources pull JPEG frames on an interval (default 30s with 5% jitter, avoiding synchronized RTSP session CPU spikes) → stillness detection skips frames (reusing the health module’s freeze detection; 3 unchanged cycles pause pulling) → sequence to disk → rolling merge. Two merge paths: native Go packs JPEG frames directly as H.264 IDR frames into MP4 (pure mux, ~5% CPU on a Pi 3B for ten 1080p streams, at the cost of file size); FFmpeg re-encodes to H.264 (5-10× smaller).

The transcoding system landed in this version: a task queue in SQLite, recordings auto-enqueued via the event bus on completion, frontend polling of task state, failed tasks retryable; the most useful piece is backfill — pick a historical date range and batch-create transcode tasks (target codec h264/hevc/mjpeg), with automatic libx264 fallback on ARM when no hardware encoder is detected (/dev/dri/renderD128 or a V4L2 encode node). History cleanup became paginated, avoiding huge single deletions bloating the SQLite WAL.

Two roads were paved at the same time: internal/ai/ set up the ONNX Runtime inference framework — CGO decoupled through a subprocess, YOLOv11n model ready, one feature flag short; observability gained Prometheus metrics and VictoriaLogs remote logs, so community issues were diagnosed from data. Fixes worth recording: non-standard H.265 SPS fields black-screening hls.js — SPS intercepted and patched before HLS writes; COOP/COEP headers enabled only under HTTPS (strict mode breaks WebSocket over HTTP); a 5-second frame watchdog on the recorder that reconnects when SPS/PPS never arrive, preventing goroutine leaks; PTS validity checks at recording start so zero-duration recordings stop producing NaN totals in the frontend.

The community quickly enumerated the flaws: JPEG sequences eat storage, H.265 cameras’ timelapse won’t play, dual-lens Xiaomis only expose the main lens, H.265 HLS occasionally panics. The v0.7 rewrite’s core: merging no longer goes through FFmpeg or intermediate JPEG sequences — the keyframe extractor caches SPS/PPS on the first frame, then writes each keyframe as H.264/H.265 NAL units; merging is a pure mux into MP4, output directly playable:

The extractor has two modes: interval (config-driven, for MJPEG sources) and IDR (reuse the RTSP stream’s IDR frames — the camera owns the GOP, the extractor only filters NALs and caches parameter sets, near-zero cost). This version also added Xiaomi dual-lens channel selection (CW500 and Outdoor Camera 4 lens pairs map to independent recorders) and refactored transcoding into three layers (task pipeline / hardware probing / encoder abstraction) so adding an encoder touches one place instead of four or five.

Two representative stability fixes landed here: issue #20’s H.265 HLS panic — the muxer might not be built when an H.265 stream’s first frame arrives, and the write path walked straight onto an uninitialized pointer; the refactored StreamHub centralized muxer lifecycle, triggering automatic recovery and re-initialization instead of panicking. Issue #18’s repeated Xiaomi reconnects — UDP miss connect timeouts mishandled the PONG response and wedged the connection state machine into a visible offline-reconnect loop; the fix covered PONG robustness, backoff with jitter, and clearing CS2 buffer residue on reconnect. The frontend got a cleanup pass in the same release: the browser-side AI detection module only detected without tracking — little practical use, real resource cost — was removed from the frontend (the backend ONNX framework stayed); the camera Enabled toggle was entangled with the recording/streaming/transcoding state machines (a disabled camera could still be triggered into recording by the event bus), so start/stop moved wholly into the recorder lifecycle. The three self-built camera projects updated in step: MiBeeHomeCam renamed MiBee Cam with ONVIF WS-Discovery auto-discovery (Synology- and Milestone-class NVRs can find it), MJPEG moved to a dedicated port, and a frame broadcaster landed to resolve PSRAM contention; rpi-cam migrated to mibee-eye-raspi, its scope widening from the Raspberry Pi to all libcamera-compatible ARM boards (Banana Pi M5 and Orange Pi 5 behaving identically).

v0.9.0: Zero-Config Discovery, Paying the Performance Debt

v0.8 got no release post; the storage bottleneck and camera-manager lock problems it exposed became v0.9.0’s (July 19) main line: with 9 cameras on a Banana Pi M5, /api/cameras took 14.9 seconds on cold start — not slow iteration, but the manager’s RWMutex held for writes by second-scale operations (recorder startup, ONVIF handshakes) while every read queued behind it. The release was regression-tested against 9 real cameras (CW500 dual ×2, DS-2CD2047G2, Outdoor Camera 4, IMILAB A1, Dafang, Xiaofang, Aqara G2, Xiaomi pan-tilt).

A Lock-Free Camera Manager

Copy-on-write atomic snapshots plus per-camera lifecycle locks: all read paths take immutable atomic snapshots — lock-free; write paths hold a nanosecond-scale map copy and never span I/O. Measured:

Storage Read/Write Split

Recording writes blocking queries was the other sore point, plus N+1 queries and full-scan COUNT(*). The rewrite: under WAL mode, a single serial writer connection and three parallel readers (DSN with query_only=1):

The serial writer preserves transaction order; the reader pool cashes in on WAL’s concurrent reads; full-scan counts became a 2-second TTL cache. Startup now scans merge integrity (rows marked merged whose files vanished get reset, playback falls back to frames instead of 404), and the merge manager grew post-merge verification — a missing output MP4 blocks deletion of source frames.

Zero-Config ONVIF Discovery and the Rest

Adding an ONVIF camera used to mean knowing the IP and hand-filling a profile. v0.9 added dual-mode discovery: passive listening for WS-Discovery Hello on UDP 3702 (devices announce on join) and an active Probe every 60 seconds. Discovered devices flow through one enrollment pipeline: dedupe by endpoint + stable_id → enrich (brand/model/serial persisted) → no-credential devices land in pending_activation with an activate button in the UI — activation performs a real GetStreamURI + RTSP DESCRIBE test.

FFmpeg became an optional accelerator: recording, playback, streaming, relay, timelapse, and merging all run without it; only pixel-level transcoding still wants it. A pure-Go MP4 box probe (mediaprobe) replaced ffprobe -count_frames, 10-100× faster. Older Xiaomi devices (Dafang, Xiaofang, Aqara G2) got a self-built TUTK P2P transport: TransCode/XXTEA encryption, three session types, a custom ChaCha20-Poly1305 DTLS suite — seven legacy models supported; MISS gained two-way audio, PTZ, and RPC wake for battery devices.

Debt-repayment highlights: grid protocol auto-selection with a runtime downgrade chain (webrtc→flv→hls→mjpeg); repair CLI (repair duration reads only the stts box — 4,285 clips fixed in 30 minutes versus an estimated 10+ hours); camera start leaking the HTTP request ctx into the recorder (“started then immediately stopped”); duplicate enrollment of the same device (777MB of redundant video accumulated in production) fixed with double dedupe. v0.9.1 followed with: i18n dictionary parity at zero missing keys; MP4 muxer segment memory caps by RAM tier, halving fragment counts; and a full documentation audit — most notably confirming the timelapse docs described a merge-window capability that didn’t exist (8h/24h values were silently clamped to 1h), a debt v0.10 paid.

v0.10.0: H.265 End to End and the Architecture Cleanup

v0.10.0-preview.1 (July 28) wasn’t about features but about cleaning the foundations; the breaking changes announced in v0.9 landed here — all documented, with migration steps, nothing silently broken.

H.265 End to End

0.9.x H.265 was half-finished: streaming depended on WebCodecs, which requires an HTTPS secure context — plain-HTTP LANs couldn’t play; merge products often black-screened on Edge; timelapse merging didn’t work. This version fixed the whole path. Streaming gained the @yume-chan/libde265 WASM decoder, playable over plain HTTP; the frontend auto-probes — HTTPS prefers WebCodecs hardware acceleration, otherwise WASM software decode — both roads reach the player; “can’t play” is not an exit:

Multi-view H.265 grids could trigger a “freeze storm” — one stuck decode dragged the whole grid’s frame polling down. The frontend player became a unit-testable state machine: ok means stable for 30+ seconds; degraded means decode anomalies detected but an 8-second debounce window runs first; failed means confirmed dead, downgrade to the next protocol in the chain — all failing ends in a static snapshot. The 8-second debounce was tuned the hard way: too short triggers on transient network jitter, too long leaves users staring at a frozen tile.

The rest of the path was timing and data-consistency work: codec probing now double-writes YAML + DB (probe once, persist forever); SPS/PPS/VPS capture moved ahead of recording decisions (live-only mode previously never captured parameter sets — black playback); timelapse merges fixed the hvcC numNalus and switched to conservative Main-tier defaults (Edge’s HEVC extension stopped refusing to play).

Timelapse v3

The v0.7 rewrite removed FFmpeg but the 1h merge-window cap remained. v3 actually lifted it: natural-day/8h/12h/24h/7d/30d all real, default moving to natural-day (local midnight alignment). A new timelapse_merges table gives every product a full DB record; periodic merges fold intermediates (about 1.5GB saved per camera per day by default).

MJPEG, WebRTC, and authentication moved in this version too: ESP32-class MJPEG cameras previously polled HTTP — one request per frame, with latency and connection counts stuck; they moved to a single streaming WebSocket push. WebRTC gained streaming.webrtc.ice_servers (STUN/TURN list) — configure and it works across networks, no longer LAN-only. Authentication switched to HMAC-signed stateless tokens — no server session memory, controllable expiry, and groundwork for the sidecar architecture. Accompanying engineering and stability: API gzip (an order of magnitude smaller) + ETag + view=summary lightweight endpoints + recording-list limits, cutting grid polling traffic sharply; deleting a recording now also deletes its merged products (previously leaked on disk), with repair reclaim-orphan-merges to reclaim historical leaks (--dry-run previews the reclaim; the 20ms deletion interval is kind to USB disks); startup scans went async, an 8-minute block becoming an 8-second start; the merge-backfill backlog drained 8,500+ pending items.

Architecture Cleanup and the Sidecar Direction

Refactoring concentrated in three places with zero runtime behavior change: config split by subsystem; the DI composition root split into helpers and router; API routing moved from one god-method to per-domain registration. What the split changes is “where a new thing goes” — the precondition for the sidecar route: the main process stays light and stable; AI inference and protocol adapters mount as independent sidecars over a frame bus (shared memory or UDS), with control/health on a separate channel. The reasoning behind browser-side inference is its own post: MiBeeNvr’s AI detection.

This version also chased the AI model-download INVALID_PROTOBUF to ground: the streaming-gzip middleware was appending a broken gzip trailer to binary responses — ONNX models are binary protobuf and the middleware “completed” them into corruption. The fix is four layers of defense: skip binary content-types in the middleware; retry + Range requests + atomic writes in the download layer; models pre-baked into the Docker image; corrupted frontend caches self-heal by re-downloading.

Breaking changes: combined protocol strings (rtsp_h264 etc.) hard-error at startup; DB schema v28→v29 (auto-backup before migration); disk cleanup threshold default 95→85 (avoiding the HDD performance cliff past 90%).

v0.11.0: Installability, GB/T 28181, and All-Day Playback

Days after the v0.10.0 final release, fnOS user feedback condensed to one sentence: it won’t install. Two old scores got settled alongside: Hikvision and Dahua cameras couldn’t join; playback showed one fragment at a time.

The fnOS Install Fixes

Three obstacles, in the order users hit them: installs stuck pulling images (ghcr.io frequently times out from China) — v0.10.1 packed both architecture images via docker save into the .fpk (~160MB) with local docker load at install time, fully offline, and the app switched from docker-project to native form (docker-project auto-runs compose up during install, before any lifecycle hook — the offline image isn’t loaded yet and it fails with No such image); clicking the desktop icon did nothing — the web UI’s X-Frame-Options: DENY refused the cross-origin iframe, replaced with CSP frame-ancestors, and http://* only matches port 80 while the fnOS desktop runs on :5666, so protocol-scheme sources http:/https: finally worked; port 9090 rejected — fnOS text-field min/max was being validated as string length, four characters refused, switched to a pattern regex. v0.11.0 built on this with dual packages: the online package is a few dozen KB and probes ghcr vs Alibaba ACR latency at startup; the install script auto-selects likewise; Synology, QNAP, and ZSpace store templates landed too.

Playback Redone

Recordings live on disk as 30-second fragments. Playing past one meant remounting the next file with a black flash in between; the timeline only worked within a fragment. The black flash fell to double buffering — the main <video> prefetches the next fragment onto a standby <video> at 80%, and when ended fires the standby takes over:

The timeline side built an on-demand fMP4 slicer joining a whole day’s recordings into one continuous timeline; gaps between recordings (power loss, maintenance) can be dragged across directly. AVI recordings gained a frame-browser mode; VOD slices self-rebuild on 404. Password-protected live streams play on iPhone now — playlist requests hand out a scope-limited mbs_session cookie, which works for players like AVPlayer that can’t attach headers per request.

GB/T 28181 Enrollment

Hikvision and Dahua devices all speak GB/T 28181 — China’s video-surveillance interconnect standard over SIP, labeled “platform access” or “28181” in their admin pages. v0.11 let MiBeeNvr be that platform: devices REGISTER in, everything else is automatic — catalog query, a camera card per channel, INVITE for streams, recording begins. Post-registration abilities: PTZ, voice talkback (browser mic straight to device speaker), device-side recording search and playback, alarm and mobile-position subscriptions. Cascading works too — the NVR joins a parent platform as a child, aggregates its cameras into a catalog, and forwards RTP/PS on demand, pure remux with no transcoding. Three required settings:

Other updates, highlights: LAN discovery switched to device identity over IP — a persistent UUID generated on first start, /api/health carrying device_id and device_name, so clients survive the NVR changing IP; discovery runs mDNS (_mibee-nvr._tcp) plus a UDP 49090 broadcast responder, covering multicast-restricted networks. WebRTC audio went zero-transcode — G.711 and Opus reuse into WebRTC tracks directly. The setup wizard switched to incremental credential writes, no longer wiping preconfigured listen addresses, AI backend settings, or camera lists. The incident of two abnormal GB streams exhausting host memory was fixed (PES reassembly buffers capped), along with GB live-stream freezes (long-GOP session recycling, stale WebRTC hub binding cleanup).

License Change

v0.11.0 moved from MIT to AGPL-3.0-only; v0.10.1 and earlier stay MIT forever. Merely running it (commercial use included) carries zero obligations; the only case requiring source disclosure is distributing a modified build; programs built against the pkg/ extension interfaces have a linking exception; independent processes talking to a running NVR over HTTP/WebSocket are entirely unaffected. Plain-HTTP AAC live audio was downgraded (the FAAD2 WASM fallback is GPL-2.0 and was removed for license hygiene — AAC live preview now needs WebCodecs, i.e. HTTPS or localhost; G.711 live and AAC in recordings are unaffected).

v0.12.0: Substreams, Adaptive Recording, and Full-Path Observability

This version attacked two daily annoyances: watching cameras on a phone ran hot and stuttery (thumb-sized grid tiles pulling full-resolution streams); hallway cameras wrote tens of GB a day that nobody ever reviewed. The former fell to the substream system, the latter to adaptive recording; a built-in RTSP output and full-path observability came along.

The Substream System

Cameras commonly emit a main stream (full resolution) and a substream (a few hundred p). Recording from the main stream is correct; previews, grids, and cascade forwarding pulling full-resolution streams is pure waste. v0.12.0 made the substream a first-class input across five links:

Discovery and configuration: ONVIF cameras are zero-config — discovery records the second profile’s token automatically; non-ONVIF cameras take a hand-filled RTSP URL. On-demand pull: reference counting — a pull exists only while someone watches, and the last viewer leaving disconnects after a 30s (configurable) idle timeout:

Quality switching: grids default to the substream with a one-click HD toggle, remembered per browser.

Cascade reporting: when cascading to a parent platform, each camera can opt to report its substream — the parent’s playback pulls the low-resolution stream, with automatic fallback to main if the substream won’t come up. Analysis layer: designated cameras can dual-record low-resolution segments pushed to an external AI backend, with the 4K main-stream recording untouched.

Implementation notes worth keeping: codec detection trusts no ONVIF profile metadata (a camera was caught advertising H.264 and emitting H.265) — the RTSP DESCRIBE SDP is the source of truth; when a camera changes address, the retry loop periodically re-resolves and follows the new IP; a failed substream falls back to main with an X-Stream-Quality header stating what was actually returned.

Built-in RTSP Output

Third-party systems whose only intake is RTSP pulling — Synology Surveillance Station, industrial SCADA, old decode-to-wall boxes — previously had nothing to fill in. v0.12.0 ships an RTSP server, on by default: rtsp://<NVR-IP>:8554/<camera_id>, H.264/H.265 passed through untranscoded; it shares the FLV/HLS hub source with zero-copy frame reuse; readers joining mid-stream start at the previous keyframe (GOP cache replay) rather than consuming broken-reference P frames.

Adaptive Recording

The motivation came from a 48-hour soak test: a hallway camera wrote tens of GB a day, the overwhelming majority of which no human would ever review. Under continuous recording, the disk pays full price for still frames.

Compressed-domain activity score. v0.12.0 added an “adaptive (motion-aware)” recording mode alongside continuous (recording_mode: adaptive; continuous remains the default and adaptive must be opted into): an activity score computed in the compressed domain — each P frame’s size against a rolling baseline, no pixel decoding, negligible CPU; quiet stretches record keyframes only, activity restores full rate seamlessly. The score reflects whether pixels changed, not what changed — people, cars, and light shifts all count; deciding “is it a person” belongs to an external AI backend.

Gate details. The NVR watches each P frame’s byte count against a rolling baseline (maintained with MAD — median absolute deviation — for jitter resistance). A calm stretch (default 60 seconds) enters sparse mode: one keyframe per 30 seconds, audio paused. An activity spike (default 5× baseline, spike_factor tunable) exits sparse and restores full rate immediately. Encoder-noise spikes during sparse mode (static H.265 scenes randomly emit large P frames) don’t break the calm accrual singly — they must cluster within 2 seconds to count as activity, so a passing car doesn’t throttle down and one noise frame doesn’t throttle up:

Why the switch loses no frames. While sparse mode runs, a GOP ring buffer in memory always holds the most recent complete GOP. The instant an activity spike is detected, the buffered GOP — the continuous footage just before the spike — is flushed to disk first, then full-rate recording resumes: the sparse→full switch point leaves no hole in the recording; playback neither corrupts nor gaps:

All parameters are optional: calm_threshold (calm duration, default 60s), timelapse_interval (sparse keyframe interval, default 30s), spike_factor (sensitivity, default 5, lower = more sensitive).

Three supplementary triggers. Audio: G.711 tracks compute per-second loudness (dBFS); crossing the threshold (default -45) exits sparse immediately, with the previous 3 seconds (configurable) of the audio ring backfilled into the exiting segment — tune the threshold to site noise floor; a machine room with constant ambient sound wants it raised. External: POST /api/cameras/{id}/adaptive/trigger lets doorbell, sensor, or any external system pull a camera back to full rate. Activity heatmap: every recording segment carries an activity score; the playback timeline renders it as block color (green→red), so “did anything happen around 3pm” no longer depends on scrubbing blind.

Measured numbers (static-scene camera): a 248-second sparse segment wrote 5.6MB against ~190MB full-rate for the same period (~34×); the camera’s hourly average was 688MB versus a 2,700MB full-rate baseline — three quarters saved. Active periods behave identically to continuous mode; playback stays continuous.

What sparse mode writes, and how it plays back. Sparse segments get compressed at the merge layer: long-dwell samples squeeze to 100ms frame spacing (100/300/500 selectable), so normal-speed playback is a natural timelapse; an optional ambient-audio layer records low-bitrate sound through sparse stretches, mixed down by envelope at merge time. Database rows keep wall-clock time; the playback page’s day-timeline seek maps through timeline_map into the product — one file auto-speeding: real-time where there’s activity, fast-forward where there isn’t.

Watermark cleanup followed the same ranking: segments with near-zero activity delete first, active ones last, “retain N days” semantics unchanged. The activity score reflects whether pixels changed, not what changed — people, cars, and light shifts all count; deciding “is it a person” belongs to an external AI backend, not the NVR (the browser-side inference reasoning is in MiBeeNvr’s AI detection).

Per-Camera Disks and fnOS

Multi-disk machines previously had one recording root for the whole box. v0.12.0 allows a per-camera root: switching is hot (new segments go to the new disk immediately), history moves via a background migrator — rate-limited (15MB/s default), window-restrictable, verified before source deletion. On fnOS: logged-in desktop users enter the NVR via gateway SSO; web-install.sh covers the HTTP app-store path so installing no longer needs SSH.

Intake and GB/T 28181 Additions

WHIP push intake (browsers, phones, OBS pushing WebRTC directly in as a camera); bidirectional H.265 RTMP (the enhanced-RTMP hvc1 codec both ways — H.265 cameras forward natively to supporting platforms); GB device SD-card recording search and download (INVITE s=Download sessions); DeviceControl commands (reboot, factory reset, config backup); cascade v2 (audio uplink, multiple parents, proactive NOTIFY on catalog changes, per-camera catalog visibility); same-IP dual-protocol devices no longer suppressed by IP dedupe.

The same 48-hour soak quantified GB UDP fetch loss at ~16% — IDR-sized bursts overflow the NIC soft-interrupt path, each loss breaking the P-frame reference chain into macroblock corruption. Cascade media defaulted to tcp-passive (deployments explicitly configured for udp unaffected).

Upgrade notes: audio tracks in recordings are off by default (per-camera switch; live preview and audio triggers unaffected — enable per camera as needed); the database migrates incrementally and automatically (recordings gains motion_score, activity_flags, and timeline_map columns), with a pre-upgrade backup of nvr.db and mibee-nvr.yaml advised.

Full-Path Observability

When live view stuttered, the previous diagnostic toolkit was reading logs and counting frames. v0.12.0 instrumented the stream path: stream view (frame/byte/loss/consumer counters per camera from source to every protocol exit, main and sub counted separately); a stream diagnostics tree (per-camera aggregation, status-colored, substream branches included); latency badges (exact end-to-end for FLV, estimates for HLS/WebRTC, visible in the grid); a three-state stream indicator (last_frame_age_s distinguishing online / never-streamed / broken — separating “camera died” from “NVR is stuck”); frame breadcrumbs at every hop.

Recording audits: written ≠ playable. A background job hourly samples and decode-checks landed recordings — and this observability feature immediately caught three of the NVR’s own defects, all reproduced in the long test, none of which error at write time:

  • Timestamp collapse: recording timestamps previously came from consumption time; a backlog burst meant a batch of frames consumed at once, timestamps collapsing onto one point with the reference chain damaged from there — fixed by anchoring on frame arrival time
  • Sparse-exit double write: exiting sparse flushed the GOP buffer, re-writing keyframes already on disk into duplicate POCs — fixed with flush dedup
  • Misaligned merge products: rolling-merge output didn’t force IDR starts, corrupting at joins — fixed by forcing IDR-aligned segments

After the fixes, decode errors in the audits went to zero on the same deployment. The takeaway is worth stating: recording-pipeline correctness is the decoder’s call, not the write path’s.

Live-view stability got its own batch of hard fixes in this release. A single slow client that read a few KB and dropped could lock an entire camera’s FLV pipeline — everything was written synchronously inside the viewer lock, and once a half-closed client’s kernel buffer filled, the blockage cascaded over every other request and the frame fan-out; now the lock only admits and registers, with writes moved outside and a 10-second write timeout. On low-power devices whose wasm H.265 decode can’t keep up, the old version rendered broken reference frames from the backlog (half-screen green/white); the new version honestly degrades to keyframe mode based on decode-time estimation — the picture settles into a per-GOP-updated still instead of corruption. The TUTK-channel legacy-camera 10-20 second disconnect loop (residual handshake write-timeout clearing), dead transfer targets (a stall watchdog), and the FLV player’s destroy/init rebuild loop were each fixed. Loopback login bypass became configurable (auth.local_bypass, off by default, bare-metal deployments only — reverse-proxy or Docker-published-port setups must keep it off, or every remote request is admitted via 127.0.0.1). On the engineering side: the ONVIF client library moved to the v2 service-facade version, and the GB protocol stack was extracted into the standalone open-source library gb28181-go — the main repository keeps only the assembly layer; tutorials for the five protocol libraries are later in this series.
