MiBeeSteward: From v0.1.0 to v0.5.0

July 5, 2026 September 20, 2026 MiBeeOSS Go, Device Management, Network Discovery, SNMP, Distributed, OpenWrt, Open Source MiBee Open Source Projects Series 3504 words 17 min read
🔊

MiBeeSteward is the device management and monitoring system I wrote for my own studio: one Go binary stringing network-device discovery, classification, monitoring, and management into a single line. v0.1.0 shipped on July 5, 2026; v0.5.0 landed on August 20 — five releases evolving a “single-subnet scanner” into “a distributed system that passes enterprise audits”. Each version used to have its own post; this one merges the v0.1.0–v0.5.0 release records into a single timeline: what each step did, and why.

Why Build It

Studio ops pain is never one specific problem — it’s the “not knowing” that accumulates as devices multiply: which device is alive, what services run on it, when a new machine joined the network. Accumulated ignorance eventually becomes an outage.

My previous answer was a patchwork: Zabbix for monitoring, Nmap for scanning, Excel for assets, Prometheus for metrics. Each tool is fine alone; together they are data silos, duplicated configuration, and heavy deployment. So I rebuilt it in Go with one goal: a single binary, zero external dependencies (pure Go + modernc.org/sqlite, CGO-free), download-and-run, ARM64-first — no pressure on a Raspberry Pi or mini host.

Nothing exotic in the stack: Chi routing, sqlc-generated queries, koanf config, JWT auth; a SvelteKit 5 + Tailwind 4 + ECharts frontend embedded via go:embed; native SNMP/ICMP/TCP/HTTP probing; eBPF via cilium/ebpf behind an optional build tag, zero dependencies in the default build.

The positioning deserves clarity: it is not an NVR and not an alerting platform — its core answers “what is happening on this network”. The relationship to existing tools in one line each: NetBox is an asset database that doesn’t care whether devices are online; Zabbix and Nagios are heavyweight monitoring platforms whose full deployment needs a database, a web tier, and a pile of agents; Nmap outputs a line of open ports and leaves the business meaning to you; and in the Prometheus ecosystem, node_exporter only exposes metrics — nobody answers “which devices should be monitored at all”. MiBeeSteward takes a slice of each and kneads them into one binary with “is it alive” at the core and asset management as a byproduct. For recording, use MiBeeNvr from the same studio; for alerting, wire up Alertmanager.

The v0.1.0 Foundation: Probing, Scanning, Fingerprints

The Probe Subsystem

“Periodically ask if it’s alive” is the most basic capability. Four probe types (ICMP/TCP/HTTP/SNMP) implement one Prober interface; a decorator adds exponential-backoff retry (1s→2s→4s) with a three-strike rule — 3 consecutive failures before marking offline, automatic recovery, no false alarms from network jitter.

Scanner v2: Scan, Then Identify

This is the most distinctive piece. Traditional tools fall into two camps: scanners (Nmap) do ports and nothing else; monitoring systems (Zabbix) assume you already know what to monitor. Scanner v2 bridges the gap — a five-layer plugin architecture (Probe → Classifier → ServiceHandler → Persistence → Orchestrator) that translates “open ports” into “this is a Hikvision camera running RTSP and ONVIF”.

Adding a protocol means implementing the Classifier and Handler interfaces and registering them; the orchestrator and persistence layers never get touched.

eBPF Passive Observation and Prometheus Integration

The eBPF passive observer is experimental (make build-with-ebpf, kernel BTF ≥ 5.8): a TC ingress program attached to the NIC sniffs ONVIF WS-Discovery multicast and TCP signature bytes, feeding active probing as corroboration (confidence 0.6). The value of the approach is “watch without speaking” — for probe-sensitive environments (industrial control, medical gear), passive sniffing generates zero traffic.

Prometheus integration is native rather than push-based: /metrics exposes its own gauges, /sd serves HTTP service discovery for all devices, and /api/v1/dashboard/query is a read-only proxy into an existing Prometheus. Drop it into a running Prometheus + Grafana stack with no extra exporters.

v0.2.0: Distributed Discovery and Change Detection

v0.1.0 had two obvious shortcomings: the center saw only its own LAN, while the studio’s reality is one subnet each for office, machine room, and home test rigs; and it recorded state without telling you what changed — the newly added NAS and the IP-hopping Raspberry Pi both drowned in the device list. v0.2.0 (07-13) went after both.

center + agent: A Pull Model That Passes NAT

A new mibee-agent binary runs in the remote LAN, scans locally with the same scannerv2 engine, and reports to the center. The protocol is a push-report + pull-command hybrid where the agent is the only active party and the center opens no inbound ports — outbound HTTPS from the agent suffices; NAT traversal needs zero firewall holes.

mermaid
sequenceDiagram
    participant A as mibee-agent
    participant C as center
    A->>C: POST /agents/report<br/>(live devices + state hash)
    C-->>A: 200 OK
    loop every 60s
        A->>C: GET /agents/commands
        C-->>A: pending commands (maybe empty)
        A->>C: POST /commands/{id}/ack
        Note over A: execute scan<br/>15min hard deadline
        A->>C: POST /commands/{id}/complete
    end
    Note over A,C: center down: backfill<br/>queue (cap=100), ordered replay

The report channel pushes live devices every 30 seconds; the command channel pulls ad-hoc scan commands every 60. Two engineering details were paid for in blood: agent-triggered scans carry a 15-minute hard deadline — without one, a stuck TCP read pins a command in “acknowledged” forever while the agent looks alive but does nothing; and while the center is down, the agent queues reports in a 100-entry in-memory buffer replayed in order on recovery — brief restarts never sever a network’s view.

The Anti-Entropy Hash Fast Path

A quiet subnet’s 30-second report is byte-identical to the last; running the full device bridge (fingerprinting, inference, writes) each time solves the same problem repeatedly. The fix: each report carries an X-Network-State-Hash (SHA-256 over the identity + classification fields of the live set); on a match the center only refreshes lease timestamps, on a mismatch it re-runs the bridge per device. The hash covers only fields whose change is a real change — RTT and last_seen vary naturally and stay out, or the fast path would never trigger. The design borrows from Dynamo-style anti-entropy, heavily simplified: truth lives only on the agent side, and the center never merges replicas — it only decides whether to recompute. One hash comparison suffices.

Dual-Track Offline Detection

The center’s own subnets judge offline by consecutive scans: miss_count +1 per round without the device, offline after 2 consecutive misses. Agent-managed subnets judge by lease: each report refreshes a 5-minute TTL, a background LeaseSweeper runs every 60 seconds, and expiry means offline — at a 30-second report interval, roughly 10 consecutive missed reports. They aren’t unified because the signals differ: scan-driven signals are discrete rounds where miss_count has meaning; report-driven signals are “how long since last seen”, and when an agent goes silent there are no rounds at all — waiting for “the next round” would stall the verdict. Both tracks write the same table and emit the same device_lost event; consumers can’t tell them apart.

Change Detection and Passive Discovery

The change engine is a Watcher inside the center writing three event types to change_log: device_added, device_changed (identity fields changed), and device_lost. device_changed tracks 12 fields (name, type, brand, model, MAC, IP, status, open ports, services, two URLs, scan attributes), each event storing a structured before→after diff rather than a full snapshot — you read “IP moved from .143 to .144” directly. Consumption goes through paginated queries, an SSE live stream, and the mibee_changes_total counter.

Passive discovery closes the scheduled-scan blind spot: devices joining between rounds would wait for the next one. Three sources, each individually toggleable — the router’s SNMP ARP table (widest cross-subnet coverage), the local ARP cache (reading /proc/net/arp, zero traffic), and multicast listening (mDNS + SSDP, listen-only, catching cameras, printers, IoT, Macs, UPnP).

The MAC-first known-host pre-check is the key optimization: a device drifting from .143 to .144 on DHCP renewal is recognized by MAC without triggering an expensive identification scan. A device coming online at 2 AM still gets its device_added event immediately.

Fingerprints Become Data

v0.1.0’s identification rules were Go if/switch statements — adding a signature meant a code change and a recompile. v0.2.0 turned rules into YAML data loaded at startup by a RuleClassifier — adding a device signature is writing one YAML line. Roughly 2554 rules ship out of the box: 20 handwritten builtins + ~2534 imported from Rapid7’s Recog corpus (Apache-2.0, license-clean; nmap’s NPSL is deliberately not imported for licensing). The few things declarative rules can’t express stay in Go with documentation (SNMP bitmask heuristics, camera cross-evidence fusion, byte-offset classifiers), and a parity test asserts the data-driven classifier matches the handwritten one it replaced byte-for-byte — migration-induced behavior changes get caught in CI. The engine was also extracted as the standalone mibee-fingerprints-go module for reuse.

This release also opened the L2 topology story: Bridge-MIB neighbor probing walks switch FDB tables to learn which MAC sits behind which port, stored in device_neighbors. The probe set grew from 13 to 15, adding SMB2 Negotiate (dialect and OS string), reliable FTP banners, and TLS certificate CNs (identifying OpenWrt/GL.iNet/iStoreOS — the last needs CN and issuer-organization jointly).

v0.3.0: Topology, Certificates, Containers

v0.3.0 (07-18) closed three specific tails: incomplete topology, unmanaged TLS certificates, and deployment friction.

L2 Topology: Why Three-and-a-Half MIBs

v0.2.0 had Bridge-MIB alone, which drops edges in multi-vendor environments. Three additions each cover one slice:

MIBProvidesMerge key
Bridge-MIBMAC↔ifIndex base adjacencyMAC
CDP-MIBVendor neighbor identity (device id, platform string, IP)device id
Q-BRIDGE-MIBVLAN-aware MAC→portMAC
STP-MIBPort roles (root/designated/forwarding/blocking)STP port id

The differing merge keys matter — three data streams land in device_neighbors and are finally merged into one row per device by MAC plus EnrichDeviceByMAC. IF-MIB ifName resolution translates numeric ifIndexes into human-readable GigabitEthernet0/1; CDP/LLDP platform strings (like Cisco ISR4321) feed the RuleClassifier, and MAC matching links topology neighbors to known devices — v0.2.0’s perpetually-NULL neighbor_device_id was exactly this missing link. The frontend renders the full typed radial topology graph with edges colored by discovery protocol.

The TLS Certificate Inventory

Since v0.1.0, TLS services only had their certificate CN scraped as a fingerprint — “how many days until this cert expires” was unanswerable, and intranets full of self-signed certificates break the day one lapses. v0.3.0 added full chain collection for 8 TLS-wrapped protocols (https/ldaps/smtps/imaps/pop3s/ftps/ircs/telnets; handler count 21→29). The implementation shares one CollectCertChain core across all 8 handlers — Go’s crypto/tls completes the handshake at tls.Dial, and PeerCertificates returns the full chain regardless of what application protocol runs on top, so sharing is the natural outcome. Data lands in host_tls_certs with an (ip, port) index for per-device queries and a not_after index for “expiring within N days” sweeps. Frontend status colors: green=valid, amber=expiring within 15 days, red=expired.

Container Images and netns Fidelity

The first official multi-arch images shipped to GHCR. Behind the three compose profiles lies this release’s hardest engineering finding, measured on a 31-device test LAN:

Deployment formDevice MACs discovered
Bare metal31 / 31
docker --network host30 / 31
docker default bridge0 / 26

The bridge-mode MAC count of zero is not a bug — it’s the physical fact of network namespaces: passive discovery reads /proc/net/arp, and a NAT-ed container has its own netns whose ARP table holds only the bridge gateway, because the container has never communicated directly with other LAN hosts.

So the bridge profile suits UI demos only; production scanning uses host (shares the host netns, fidelity ≈ bare metal), and macvlan makes the container appear as a LAN device. In the unprivileged image, LLDP/CDP raw frames and eBPF are no-op stubs — they need capabilities like CAP_NET_RAW, and the stubs degrade gracefully instead of pretending; those who need them run make docker-build-priv locally. Active probing (TCP/SNMP/TLS/Bridge-MIB) needs no raw sockets, so a host-network container already discovers the vast majority of devices. The same fact applies to VMs: bridged NICs ≈ bare metal, NAT NICs discover almost nothing — when results look wrong in a VM, check the NIC mode before blaming the program.

v0.4.0: Router-Resident Discovery

Containers need host networking and physical hosts miss sleeping devices, so the more radical position is: run the discovery program on the gateway itself. The gateway is the mandatory path for all LAN traffic — DHCP leases, the connection table, WiFi clients, and DNS query logs are all right there. v0.4.0 (07-29) wired in these four Tier-1 local sources (Tier-2 being the cross-device queries v0.2.0 already had: SNMP ARP, multicast listening):

SourceFromWhat it sees
dhcp_leases/tmp/dhcp.leases etc.Every client ever leased, including sleeping devices
conntrack/proc/net/nf_conntrackConnections active right now — a real-time “who’s online”
hostapdclient listDevices currently on WiFi
dns_logdnsmasq query logDomains recently queried, an identification signal

conntrack deserves the spotlight: the ARP table says “communicated recently” while conntrack says “talking right now” — much closer to truth for liveness. All four sources are opt-in and degrade gracefully: off means unread; on but missing (a wired-only gateway without hostapd) means self-disabled with a log line, never a crash.

OpenWrt became a first-class citizen: procd init scripts (UCI-configured, autostart, crash restart, unprivileged) plus an ARMv7 build target covering routers with only 16/32MB of flash. The four deployment environments’ fidelity differences in one sentence: settle the netns membership and gateway question first, then talk fidelity — the router form runs all Tier-1 sources with zero extra traffic, bare metal sees 31/31, host containers 30/31, bridge containers and NAT VMs zero.

One long-lurking correctness bug also died: device rows previously had two independent write paths (interactive scans and scheduled scans) with inconsistent semantics — the same device could hold conflicting rows depending on which path wrote last, a bug nearly impossible to reproduce. v0.4.0 established a single device writer (runner.applyDeviceBridge as the sole arbiter of device-row lifecycle); both paths now leave byte-identical rows. Alongside: when MAC matches but IP differs, the IP holder wins and identity fields are force-overwritten (no stale portraits on device replacement), and a background reconciliation task flags devices whose IPs drifted outside their registered subnet for human correction — auto-migration would conflate “the device moved” with “the config is wrong”.

v0.5.0: Three Things Enterprises Ask For

By v0.4.0 the intranet chain was complete. Bringing the system into a company or stricter environment hits three walls: SNMP stops at v2c (plaintext community strings fail security audits, and hardened environments disable it outright — collection dies); permissions have only admin/user tiers (shared use can’t separate operators from viewers); and “who changed this config and when” is unanswerable. v0.5.0 (08-20) dismantled them one by one.

SNMPv3

The USM model at authNoPriv and authPriv security levels: authentication upgrades to username + MD5/SHA/SHA-2, with encrypted transport (AES/DES) under authPriv. Credentials are stored AES-256-GCM encrypted and never echoed in the UI. Device identity collection and all topology walks (LLDP/CDP/Bridge/Q-BRIDGE/STP/IF-MIB) work fully under v3. Existing v1/v2c deployments behave unchanged after upgrade; agent-side v3 was deferred — credential distribution and rotation in a distributed setup needs its own design.

Role-Based Access Control

Three roles — admin/operator/viewer — with legacy user accounts auto-mapping to viewer. Every route carries a capability, roles map to capability sets; per-network grants live in user_network_grants. The scope default is open (legacy behavior); closed restricts non-admins to granted networks:

Unauthorized resources return 404 rather than “forbidden” — no existence leaks, so closed mode doubles as tenant isolation. Foolproofing: an unrecognized config value falls back to open; a typo never blinds every non-admin at once.

The vendor command matrix: JunOS uses show configuration | display set; HP/Aruba/H3C/Comware use display current-configuration; Cisco IOS/NX-OS, Arista, Huawei VRP, Mikrotik, and unknown vendors fall back to show running-config; host keys follow TOFU. Unchanged content produces no new version — every entry in the version list is a real change; changes emit device_config_changed events flowing into change detection and notifications. The device detail page diffs any two versions. SSH credentials share the same AES-256-GCM encryption as SNMPv3. Off by default; on-metal end-to-end validation (GL-MT3000) landed in the next release.

Notifications, Probing, Liveness as a Time Series

Built-in notifications: rules keyed by event type (lost/recovered/added/changed/config-changed), scope (all/per-network/per-device), and channel (webhook/email), with a per-(rule × device) cooldown (default 30 minutes) layered atop the change detector’s own — two windows of debounce. The positioning is event routing, not an alerting engine — no thresholds or routing trees; those still belong to the Prometheus stack.

External probing: the probe range extends past the intranet to public endpoints; http/tcp/icmp reuse the heartbeat probers, while tls and https targets reuse CollectCertChain for full chains — expiry, issuer, TLS version, cipher suites. The engine re-reads config on a 10-second tick (changes apply live), restores next-due times from last_run_at after restart (no startup storm), and caps concurrency at 8. The certificate table is delete-then-insert, keeping “the last known-good chain” — a transient handshake failure shouldn’t wipe known-good state.

Liveness as a time series: device liveness was previously modeled as discrete device_changed events — every flip wrote a row, and the test network accumulated 70,000+ change-log rows that drowned real changes in sleep/wake churn. v0.5.0 moved it to a device_liveness time series — one verdict sample per device per tick, feeding online-ratio, offline-duration, and history queries; state flips are consumed by the liveness layer, leaving only lost/recovered events. Satellite tables moved to stable device_uuid keys, so address changes no longer fork history.

Two Identity-Level Corrections

The MAC U/L-bit misjudgment. The first cut treated the U/L bit (locally administered) of the MAC’s first byte as the “randomized MAC” test — bit set meant identity demotion, to avoid treating iOS/Android privacy randomization as stable identity. Per IEEE 802/RFC 7042, that bit only means “locally assigned” and cannot distinguish “changes on every reconnect” from “the soft-router or virtualization NIC’s locally-set but long-stable address”. The test network called the bluff immediately: 7 stable soft routers and NAS boxes were flagged as randomized, and one R68s got split across two subnets by the demotion. The correction: demotion withdrawn entirely, back to MAC-first identity; the bit remains a pure observation flag, the field renamed mac_is_locally_administered with the UI label following. One binary bit cannot carry semantics as heavy as “randomized”.

OUI longest-prefix matching. OUI vendor lookup walks three IEEE registries by longest prefix: MA-S (/36, 9 hex digits), MA-M (/28, 7), MA-L (/24, 6). Longest prefix is mandatory: MA-S/MA-M sub-blocks are carved out of other vendors’ /24 OUIs and reassigned, so without it a MAC starting 8C1F64B14 gets labeled “IEEE Registration Authority” (the /24 registrant) when it actually belongs to Murata (the /36 assignee). New oui_prefix and oui_vendor fields stay separate from the existing vendor (self-reported brand) — they differ in OEM, rebrand, and virtualization cases. A latent bug fell too: the OUI download domain read standardeee.org, while the correct one is standards-oui.ieee.org — the old script had been fetching from a non-authoritative copy.
